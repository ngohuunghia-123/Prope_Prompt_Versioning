Make **SC2** true — in the **restated** form, because the ROADMAP's wording and the lock file's AC-6 both
describe a world ADR-0046 replaced.

The ROADMAP says: *"With batch dispatches saturating a configuration, an arriving interactive dispatch is
admitted without waiting, and every unadmitted batch dispatch is counted in `shed_total{priority=batch}`."*
The lock file's AC-6 says the same thing against `max_concurrency 8` and `reserved_interactive 4` —
**two columns that no longer exist.**

`.planning/research/PITFALLS.md` gap 2 gives the restatement this plan is built against, and it is three
claims rather than one:

> **each cap holds within its own process, their sum is never exceeded upstream, and a saturated
> `worker` does not affect `app`'s admission latency.**

Under ADR-0046 the original scenario — batch saturating a configuration and an interactive dispatch
arriving — **cannot occur in one process at all**, because `app` holds no batch dispatch and `worker`
holds no interactive one. The property became structural. What is left to assert is that the structure
is real: two objects, two counters, no shared state, and a sum that holds at the provider.

**D-190 — One `asyncio.Semaphore` per (process, configuration), sized once at first use. A changed
column takes effect at the next process restart.**

Chosen: exactly what ADR-0046 says — *"a plain local `asyncio.Semaphore`"* — one per
`provider_config_id`, created lazily on first dispatch for that configuration from the column belonging
to this process's class, and never resized.

Rejected: **re-reading the column on every dispatch.** It is a database round trip before every
dispatch on the interactive path, inside a 10 ms overhead budget that is itself a share of the gateway's
50 ms. ADR-0046 rejected the PostgreSQL-coordination option on exactly that ground; re-reading a column
for the limit is the same cost without even buying the coordination.

Rejected: **a resizable gate — an in-flight counter plus an `asyncio.Condition` — so a tuned column
takes effect without a restart.** It is more machinery than the ADR asked for, on the one path with a
sub-millisecond budget, and the interesting bug is exactly at the moment of interest: shrinking the
limit while permits are held has to mean *no new admissions until it drains*, and getting that subtly
wrong produces a cap that is silently wrong under load, which is the failure class this whole ADR
exists to prevent.

**Consequence, stated rather than discovered:** tuning `interactive_concurrency` requires restarting
`app`; tuning `batch_concurrency` requires restarting `worker`. On the single VM ADR-0033 fixes that is
`docker compose restart <service>`, and A-134 already expects these numbers to be tuned as a **sum**
after a real load test rather than adjusted live. Write it at the constant so the operator finds it.

Reversibility: **cheap.**

---

**D-191 — Interactive fails fast; batch waits to its own deadline and is shed on expiry. `OQ-064`.**

Chosen: two behaviours, selected by the gate's fixed class.

- **Interactive**: a non-blocking acquire. No slot means an immediate `DispatchError` —
  `rate_limited`, `origin=prope`, `fallback_eligible=True`, `retryable=True` — and
  `shed_total{priority="interactive", reason="no_slot"}`. ADR-0016 in its own words: *"If interactive
  cannot be admitted immediately it fails fast with `rate_limited{origin=prope}` rather than
  waiting — on a path with a 50 ms budget, a queue is a slower error, and the gateway has a fallback
  answer to serve."*
- **Batch**: wait for a slot, bounded by the dispatch's own `deadline_ms`. Admitted within the deadline
  means the run is **slowed**, which is what INT-015 promises: *"A run can be slowed — never failed — by
  production load."* Not admitted by the deadline means `shed_total{priority="batch", reason="deadline"}`
  and the same `rate_limited{origin=prope}` value, `retryable=True`, so evaluation's own loop (A-053)
  decides what to do.

**This resolves a three-way disagreement rather than picking a favourite, and `OQ-064` names it.** SC2
requires *"every unadmitted batch dispatch is counted in `shed_total{priority=batch}`"*, which needs
batch to be refusable. INT-015 promises a run is *"never failed by production load"*. ADR-0046 makes
batch structurally unable to contend with interactive at all. All three hold under the chosen shape:
batch is never shed **because of production load** (there is no interactive dispatch in `worker` to lose
a slot to), only because of **its own cap relative to its own deadline** — which is precisely what
`ProviderBatchStarved` is supposed to mean under ADR-0046, and its consequence section says so: *"`ProviderBatchStarved` correspondingly means the batch cap is too low, and nothing else."*

Rejected: **batch fails fast too.** It would make `shed_total{priority=batch}` easy to satisfy and it
breaks INT-015's promise to evaluation — an eval suite submitted while another is running would error
rather than queue, and A-057 turns that into run errors rather than results.

Rejected: **batch waits unbounded.** Then `shed_total{priority=batch}` is permanently zero, SC2's second
clause is unassertable, and a stuck configuration holds evaluation's executor open forever.

Reversibility: **cheap** for the behaviour, **costly** for the metric — a counter that has been zero for
a quarter and starts moving reads as a regression rather than as a definition change.

---

**D-192 — The two-process property is asserted as *two objects with no shared state*, plus a sum
measured at one provider — not by spawning two interpreters.**

Chosen: the restated AC-6's three claims are asserted with **two `AdmissionGate` instances**, one per
class, driving **one** stub provider concurrently, plus a structural assertion that no module-global
counter, semaphore or registry is shared between them.

Rejected: **spawning a real second Python process.** It would prove the same three claims with far more
machinery — a second interpreter, a second event loop, a shared observation point, and a flakiness
budget — and it would prove them about `multiprocessing`, not about the design. The property under test
is *"there is no object through which one class could take the other's slot"*, and that is a statement
about this process's module graph, which a single process can assert **directly and completely**.

Rejected: **asserting the sum by adding two counters Prope keeps.** The claim is *"their sum is never
exceeded **upstream**"*. Upstream is the provider. The number therefore comes from the stub's own
observed maximum concurrent in-flight requests, the same way plan 11-01's request count comes from the
stub rather than from a spy.

**What this does not prove, stated so the verifier does not over-read it:** that two OS processes each
initialise their gate from the right column. That is a property of `app.py` and `worker.py`'s
composition, and it is asserted separately by reading each file's installation call and by driving each
composition root's installation directly.

Reversibility: **cheap.**

**`admission.py` — the caps, sized once, and the two shed paths.**

`AdmissionGate.__init__(priority_class: Priority, limit_for: Callable[[str], Awaitable[int]])` stays as
11-01 built it. Add:

- `self._semaphores: dict[str, asyncio.Semaphore]` and `self._limits: dict[str, int]`, both keyed by
  `provider_config_id`. `async def _semaphore_for(provider_config_id)` creates on first use from
  `await self._limit_for(provider_config_id)` and **caches both**. Write D-190 at that method: the
  column is read **once per configuration per process lifetime**, a changed value takes effect at the
  next restart, and re-reading it per dispatch is the rejected coordination option wearing a different
  hat.
- `limit_for` is bound at the composition root to a function that reads
  `interactive_concurrency` or `batch_concurrency` — **whichever column belongs to this gate's class** —
  through `workspace_transaction`. The gate itself never names a column; the binding does. State why:
  a gate that chose its own column would be one `if` away from choosing the wrong one, and ADR-0046's
  whole mechanism is that the process decides.

`async def acquire(self, provider_config_id: str, *, deadline_ms: int) -> AbstractAsyncContextManager[None]`
— an `@asynccontextmanager` whose body is:

1. `started = time.perf_counter()`.
2. **Interactive branch**: attempt the acquire without waiting. In practice that is
   `semaphore.locked()` checked and then an immediate acquire, or `asyncio.wait_for(..., timeout=0)`
   — **whichever form does not lose the permit on a cancel**; read `asyncio.Semaphore`'s current
   behaviour on disk before choosing, because a cancelled `acquire` that has already been granted a
   permit is the classic leak and it leaks the one resource this module is bounding. Comment which form
   was chosen and why.
   No slot → observe `admission_wait_seconds` with the elapsed time, increment
   `shed_total{priority="interactive", reason="no_slot"}`, and raise `Shed(reason)` — an internal
   exception caught in `dispatch.py` and turned into the `DispatchError` value (D-182: the seam returns
   values; the module may still use exceptions inside itself).
3. **Batch branch**: `await asyncio.wait_for(semaphore.acquire(), timeout=deadline_ms / 1000)`. Timeout
   → observe the wait, increment `shed_total{priority="batch", reason="deadline"}`, raise `Shed`.
4. On admission: observe `admission_wait_seconds{priority}` with the elapsed time — **including a zero
   for an immediate admission**, because a histogram that only records the slow cases has no p95.
5. `try: yield` / `finally: semaphore.release()`. The release is in a `finally` with no condition on it.

`Shed` carries a `reason` from a closed set `{"no_slot", "deadline"}` matching the metric's label
values exactly, and the docstring says the set is closed and where the other end of it is.

**`dispatch.py` — where the slot is held, and how long.**

- Non-streaming: the `async with gate.acquire(...)` wraps the request and the decode. It does **not**
  wrap the credential read or the address resolution — those happen before, so a configuration whose
  address is refused never consumes a slot.
- **Streaming: the slot is held for the life of the stream**, not for the life of the request that
  opened it. Concretely, the `AsyncExitStack` that holds the gate's context manager is entered before
  `stream_chat_completion` and **closed in the stream generator's `finally`**, so a caller that
  abandons the iterator after two chunks still releases the slot when the generator is closed. Write
  the reason at the code: a stream that has yielded one chunk is still occupying a connection and a
  share of the provider's concurrency, so releasing at the end of the *request* would let a hundred
  half-read streams sit outside the cap. And note the consequence honestly — a caller that neither
  exhausts nor closes the generator holds a slot until garbage collection, which is why `dispatch`
  documents that the stream must be consumed or closed, and why the test abandons one deliberately.
- Catch `Shed` and return the `DispatchError`: class `rate_limited`, `origin=prope`,
  `retryable=True`, `fallback_eligible=True`, and `retry_after_ms` **absent** — Prope does not know when
  a slot will free and inventing a number would make evaluation's retry loop back off against a guess.
  Quote ADR-0016's `origin` sentence at the construction: *"so 'the provider throttled us' and 'Prope
  shed us' are never the same number."*

**Metrics.** `prope_provider_access_shed_total{priority, reason}` and
`prope_provider_access_admission_wait_seconds{priority}`, both with closed label sets fixed in source.
The wait histogram's buckets follow `observability.py`'s stated rule — **every number this project
asserts on is a bucket edge** — so `0.001` is an edge (the p95 < 1 ms row) and the range runs from tens
of microseconds to seconds, because a batch wait is legitimately seconds long while an interactive one
is a refusal above a millisecond.

**`tests/provider/test_admission_gate.py`** — the unit-level accounting, no provider needed:

- an interactive gate at limit 2 with 2 slots held: a third acquire raises `Shed("no_slot")`
  **immediately** — assert the elapsed time is under a small bound as well as asserting the raise, since
  a queue that eventually failed would also raise;
- `shed_total{priority="interactive", reason="no_slot"}` incremented by exactly one;
- a batch gate at limit 2 with 2 slots held: a third acquire **waits**, and succeeds when one is
  released — assert it returned a slot rather than raising, which is INT-015's *slowed, never failed*;
- the same batch gate with a 50 ms `deadline_ms` and no release: raises `Shed("deadline")` and
  increments `shed_total{priority="batch", reason="deadline"}`;
- `admission_wait_seconds` records an observation for an **immediate** admission (count moves, sum stays
  near zero);
- the release happens on an exception inside the `async with` body;
- **the abandoned-stream case**: build a streaming dispatch, read two chunks, `aclose()` the generator,
  and assert the gate's in-flight count is back to zero — asserted through the gate's own semaphore
  value, and repeated for the case where the generator is dropped and explicitly closed rather than
  exhausted;
- a **negative control**: with the gate's limit raised above the offered load, nothing is shed and the
  counters do not move. Without it a broken acquire that always raises would pass several of the cases
  above.
