**D-197 — The 60-second claim is asserted three ways, because each one alone proves the wrong thing.**

Chosen: three assertions, and the plan says which weakness each one covers.

1. **The constant is `60.0`**, asserted as a value. A test that only drives an injected clock proves the
   mechanism and says nothing about the number, and the number *is* the criterion.
2. **The mechanism, through the injected clock.** Two caches — standing for `app` and `worker` — read
   the credential, the row is rotated underneath them, and the clock advances past the TTL. Both
   dispatch with the new credential, observed at the stub's `Authorization` header. Nothing is
   invalidated, nothing is restarted, no message is sent.
3. **The mechanism in real time, with a short TTL injected.** The same sequence with a sub-second TTL
   and a real `asyncio.sleep`, so the expiry is proven to be time-based rather than an artefact of the
   fake clock's shape. It is one short test and it is the only one that would catch a cache whose
   expiry compares against a captured `now` rather than a live one.

Rejected: **sleeping sixty seconds.** It buys nothing that (1) and (3) together do not, and a
sixty-second test in a suite that runs on every phase gate is a tax paid forever.

Rejected: **asserting only through the injected clock.** A-092's promise is a number. The number has to
appear in an assertion.

Reversibility: **cheap.**

**D-198 — The event's emptiness is asserted by scanning every column of the stored row, not by checking
a field.**

Chosen: read the `credential_rotated` row back through `migrate_engine` — the owner role, subject to no
policy — serialise **every column** to text, and assert that neither the old credential, nor the new
one, nor either one's last four characters appears anywhere in it. Then assert the row's `details` is
empty, and that the actor and the timestamp are present and correct.

Rejected: **asserting `event.details == {}`.** It checks the field the designer thought about. The claim
is about the whole row, and the ways a secret reaches an audit log are the fields nobody thought about —
a message, a summary, a `target_label`.

**`last_four` is included in the forbidden set on purpose**, and it is the one that will look wrong to a
reader: `last_four` is displayed on the dashboard and is loggable. AC-8 says the event *"contains no
part of either credential"*, and the last four characters are part of the credential. A dashboard field
and an audit row are different surfaces with different rules, and this is the stricter one.

Phase 4's registry seeds all four provider actions with **empty `detail_keys`**, and phase 5's `append`
enforces the allow-list at the write — so this property is structural before it is tested. The test
asserts the structure held rather than establishing it, and says so.

Reversibility: **one-way** — an event already written with a secret in it cannot be unwritten, at the
database privilege level.

**`credential_cache.py` — finish what 11-01 started, and write the argument at the constant.**

`CREDENTIAL_TTL_SECONDS = 60.0` gets its full comment if 11-01 left it short:

- A-092's number, and it is a **TTL rather than an invalidation**.
- It exists in **two processes**, and neither knows about the other. That is not an oversight of a
  distributed design; it is the design. `deployment_target` puts interactive dispatch in `app` and batch
  dispatch in `worker`, and both caches expire independently.
- **Nothing invalidates it, and nothing will.** ADR-0012 is the same answer for the gateway's 30 s
  resolution cache, and the lock file records that a broker exists and this module uses none of it. A
  second broker queue and broker-based cache invalidation are both recorded project rejections
  (ORCHESTRATION §5). Write that here, because *"just publish an invalidation"* is the first thing a
  reader will propose.
- The worst case is stated as arithmetic: a rotation at *t* is picked up by a process whose entry was
  read at *t − ε* at *t − ε + 60*, so the bound is 60 s and not 120 s, and it holds independently in
  each process.

Make sure the cache is keyed on `provider_config_id`, holds a `str`, stores an absolute expiry rather
than a duration, and has **no** `invalidate`, `clear` or `evict` method reachable from outside — a test

**`tests/provider/test_credential_cache_ttl.py` — the arithmetic the lock's `test_plan.unit` names.**

- `CREDENTIAL_TTL_SECONDS == 60.0`. One line, and D-197 says why it is not redundant.
- A read at `t` and again at `t + 59` performs **one** decrypt (instrumented), and the second returns
  the same plaintext.
- A read at `t` and again at `t + 61` performs **two** decrypts.
- Exactly at `t + 60`: assert which side of the boundary the implementation takes and pin it, so a later
  "cleanup" that flips `>=` to `>` fails. State in the test which was chosen and that the choice is
  arbitrary but must be stable.
- Two cache instances, one entry each, with **different** clocks: advancing one does not expire the
  other. That is the two-process property in miniature.
- `credential_decrypt_seconds{cache="hit"}` and `{cache="miss"}` each move exactly when expected.
- **A negative control**: with the clock frozen, an unbounded number of reads performs exactly one
  decrypt. Without it, a cache that never caches would pass several cases above.

**`tests/integration/test_credential_rotation_effective.py` — AC-8's first clause, end to end.**

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the rotate route -> `provider.credential` | The one write path for a plaintext third-party secret, and the point at which the old one stops being valid upstream while still being cached here. |
| the credential cache -> time | The only invalidation mechanism in the design. Nothing else can make a stale credential stop being used. |
| a rotation -> `history.history_event` | An append-only row that outlives everything it describes and cannot be deleted at the database privilege level. |
| `dispatch()`'s return value -> two consumers | Two modules branch oppositely on one taxonomy, built in phases weeks apart. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-39 | Information disclosure | a secret in an append-only audit row | high | mitigate | `detail_keys` seeded empty and enforced at the write (ADR-0024), plus a whole-column scan asserting neither credential nor either one's last four characters appears anywhere in the stored row. The row can never be deleted, so this is a one-way property |
| T-11-40 | Elevation of privilege | a revoked credential still in use | medium | accept-with-bound | Bounded at 60 s by expiry, in each process independently, with no invalidation channel by decision (A-092, ADR-0012's shape). The bound is asserted as a number and the delay is asserted as real. A rotation is not a revocation of upstream access — the workspace revokes at the provider — so the residual is Prope continuing to present a key its owner has already invalidated |
| T-11-41 | Repudiation | a rotation that committed without its record | high | mitigate | One transaction (ADR-0023). Provoked by making the append fail and asserting the old ciphertext survives, no event exists, and the next dispatch after the TTL still carries the old credential |
| T-11-42 | Information disclosure | a readable history of a secret | high | mitigate | The `credential` row is replaced in place, never appended; asserted as a row count of one after two rotations, with the ciphertext changed each time |
| T-11-43 | Tampering | an invalidation channel appearing later | medium | mitigate | Asserted structurally: no module under `src/prope/provider_access/` imports `prope.broker`, and the rotation test asserts queue depth is unchanged. A second broker queue and broker-based invalidation are both recorded project rejections |
| T-11-44 | Denial of service | unbounded metric cardinality | medium | mitigate | Three declared identifier labels dropped, each with a written note; the project-wide registry walk is extended rather than duplicated; phase 12 owns the final call with the same per-metric posture phase 9 used for `OQ-053` |
| T-11-45 | Tampering | a dispatch refused for spend | medium | mitigate | Structural: no parameter named for cost and no import of `prope.call_ledger`. A-029's *"never a dispatch here"* asserted rather than intended |
