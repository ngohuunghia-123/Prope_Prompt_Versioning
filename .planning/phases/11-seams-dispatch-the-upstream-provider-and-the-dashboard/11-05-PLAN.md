<objective>
Serve INT-027 — **ten operations across six `/api/v1/providers` paths** — and make **SC6** true:
*"deleting a bound configuration is refused by the foreign key with a count and no query into the
registry's tables; disabling it stops dispatch and keeps the configuration and catalogue readable."*

SC6 is the criterion with a cross-phase problem, and it is resolved here rather than discovered in
execution. Three decisions carry it, plus one about the vocabulary the routes have to declare.

---

**D-193 — Ten operations, four actions, and six of them borrow `provider.configure` because the closed
vocabulary has no read. `OQ-061`.**

The four declared actions are `provider.configure`, `provider.rotate_credential`, `provider.disable`
and `catalogue.read` — the lock file's `apis.consumes`, `interfaces.md`'s per-module table, and
access-control's 25-row seed all agree. **There is no `provider.read`.** Ten operations have to map onto
four names.

Chosen:

| Operation | Declared `ManagementAction` | Why |
|---|---|---|
| `POST /providers` | `provider.configure` | The action's own name |
| `GET /providers` | `provider.configure` | See below |
| `GET /providers/{id}` | `provider.configure` | See below |
| `PATCH /providers/{id}` | `provider.configure` | Plus a **second** `may()` for `provider.disable` when the body sets `status` |
| `DELETE /providers/{id}` | `provider.configure` | Deleting is stronger than disabling; mapping it to the softer permission would let someone who may only disable also delete |
| `POST /providers/{id}/credential` | `provider.rotate_credential` | The action's own name |
| `POST /providers/{id}/verify` | `provider.configure` | It writes `last_verified_at` and `verification_status` |
| `GET /providers/{id}/models` | `catalogue.read` | The action's own name, and INT-016's declared check |
| `POST /providers/{id}/models/refresh` | `provider.configure` | It calls upstream and writes rows |
| `POST /providers/{id}/models` | `provider.configure` | It writes a row |

Rejected: **giving the reads `catalogue.read`.** It is the only non-credential-bearing action in the
set and it looks like the polite choice — and it is wrong, because access-control's seed gives
`catalogue.read` to **Owner, Reviewer and Viewer**. A read of a provider configuration returns
`base_url`, `status`, `verification_status` and the credential's **last four characters**, and INT-027
names its consumer as *"the web SPA — Workspace Admin"*. Handing that to a Viewer widens a
credential-adjacent surface to three more roles to avoid raising a question.

Rejected: **inventing `provider.read`.** A-115 makes the vocabulary closed and access-control owns it;
adding a member is a row in another module's seed, which ORCHESTRATION §5 forbids and which would also
be invisible to `registered_actions()`'s consumers until phase 7's migration moved.

**`OQ-061` carries this and one more instance of the same shape**, because they are one question:
**two closed vocabularies owned by other modules do not cover this module's declared surface.** The
second instance is history's: the 31-name action registry has `provider_configured`,
`provider_updated`, `provider_disabled` and `credential_rotated` and **no delete action at all**, while
A-014 says every state change writes an event. See D-195.

Reversibility: **cheap** — a declaration per route.

---

**D-194 — The refusal is the engine's; the count is derived from `pg_constraint` afterwards, and no
registry table is named in Prope's source. `OQ-062`.**

Chosen: `DELETE` issues the delete inside the transaction and lets the foreign key refuse it. The
handler catches SQLAlchemy's `IntegrityError` wrapping asyncpg's `ForeignKeyViolationError`, rolls back,
and **then** counts — by asking `pg_constraint` which tables carry a foreign key whose `confrelid` is
`provider.provider_config`, and counting rows in each for this id.

Rejected: **a pre-flight `SELECT count(*)` that decides whether to delete.** It makes the refusal an
application decision with the foreign key as decoration — and it is a race: a revision created between
the count and the delete would be deleted out from under. AC-10 says *"refused by the foreign key"* and
means it.

Rejected: **asking prompt-registry.** `provider-access -> prompt-registry` is a forbidden dependency and
the lock file says the constraint exists *"precisely because provider-access may not read prompt-registry
to find out."*

Rejected: **hard-coding `SELECT count(*) FROM registry.revision WHERE provider_config_id = :id`.** It
names another module's table in this module's source — the forbidden edge written down — and it does not
even run today, because `registry.revision` does not exist until phase 13.

**The `no_sql_interpolation` gate is respected without an exemption, and that is a constraint on how
this is written.** `tests/architecture/test_no_sql_interpolation.py` requires every `text(...)` argument
to be a plain string constant, so the count cannot be an f-string. Build it with SQLAlchemy's identifier
constructs — `select(func.count()).select_from(table(name, column(col), schema=schema))` — which quote
identifiers properly and involve no `text()` call at all. Before use, assert the discovered schema,
table and column names match a conservative identifier pattern; the names come from `pg_class` rather
than from a request, and the assertion is defence in depth rather than the primary control.

**`OQ-062` names the conflict this leaves.** ROADMAP SC6 says the refusal happens *"with no query into
the registry's tables"*, while `apis.exposes`' DELETE line and INT-027 both require the response to say
*"how many revisions bind the configuration"*. **The count has no other source**, so the two clauses
cannot both hold literally. What is preserved is every property either clause was protecting: the
decision is the engine's, no module edge is opened, no registry table name appears in Prope's source,
the rows are never named, and the query runs **only** on the refusal branch — never on the success path,
and never before the delete.

Reversibility: **cheap** for the count; **one-way** for the response shape, which the SPA renders.

---

**D-195 — Deleting a configuration writes no history event, and the absence is stated rather than
faked. `OQ-061`, second clause.**

The registered vocabulary for this module is four actions and none of them is a deletion. Chosen:
**`DELETE` appends nothing**, and the route's docstring says so, names `OQ-061`, and points at what does
survive — the configuration's `provider_configured`, `provider_updated`, `provider_disabled` and
`credential_rotated` events, which are never deleted at the database privilege level (ADR-0054) and
whose `target_id` is a **value rather than a foreign key**, so they outlive the row they describe.

Rejected: **appending `provider_disabled` for a delete.** It is the nearest registered action and it is
a false statement in an audit log. The one thing that must never happen to this table is that it says
something that did not happen.

Rejected: **adding a 32nd action.** `history.history_action_registry` is property-history's `data.owns`
and its seed is phase 4's; ORCHESTRATION §5 forbids writing to another module's table. The fix has a
named owner and `OQ-061` routes it there.

The rest of the event mapping, decided here so it is not re-litigated: `POST /providers` →
`provider_configured`; `PATCH` setting `status` to `disabled` → `provider_disabled`; `PATCH` otherwise
(including re-enabling) → `provider_updated`; `POST /verify` → `provider_updated`, because it writes
`last_verified_at` and `verification_status`; `POST /credential` → `credential_rotated`; catalogue
refresh and manual add → **no event**, because the catalogue is discovered data rather than a decision
and four registered actions do not stretch to it (same `OQ-061`).

Reversibility: **cheap** in code; **one-way** in the record, because an event that was never written
cannot be back-filled.

**D-196 — The foreign-key refusal is asserted NOW against a real foreign key the test creates, and the
assertion against `registry.revision` is routed to phase 13 by name. `OQ-063`.**

`registry.revision` — the table whose foreign key does the refusing — **does not exist until phase 13**,
and `.planning/REQUIREMENTS.md` maps PA-10 to phase 11 regardless. Something has to give.

Chosen: `tests/integration/test_config_delete_refused_while_bound.py` creates a **real referencing
table** in a scratch schema (outside the eight declared ones, so ADR-0045's coverage walk is unaffected)
with a real foreign key to `provider.provider_config(id)`, grants `prope_app` `SELECT` on it, and drops
it in a `finally`. The production code path is exercised **unchanged**: it discovers the constraint from
`pg_constraint`, counts through it, and renders the 409. When phase 13 creates `registry.revision` with
the same foreign key, **the same code counts it with no edit**, which is the property that makes the
stand-in worth something.

Rejected: **creating `registry.revision`, or the foreign key, from this phase.** `registry.revision` is
prompt-registry's `data.owns`. ORCHESTRATION §5 and the orchestrator's own instruction both forbid it.

Rejected: **deferring the whole criterion to phase 13.** The refusal *rendering*, the count derivation,
the 409 body and the no-registry-name property are all provider-access's and all buildable now. Deferring
them would hand another module a criterion it does not own.

Rejected: **a mock.** The claim is that a database refuses; a mock that raises `IntegrityError` asserts
that the handler catches `IntegrityError`.

**Routed, with a named owner: phase 13** — the phase that creates `registry.revision` and its foreign
key — **asserts the live form**: a revision bound to a configuration, a delete attempted, a 409 with a
count of 1. `OQ-063` records the traceability conflict (a requirement mapped to phase 11 whose declared
mechanism is created in phase 13) and `deferred-items.md` carries the routing.

Reversibility: **cheap.**

**`src/prope/provider_access/configurations.py` — the row reads and writes.**

One function per operation, each taking the sessionmaker and the session's `workspace_id`, each opening
exactly one `workspace_transaction`, and each performing its history `append` **inside that same
transaction** (A-044, ADR-0023). Write at the module: a rotation that committed without its event, or an
event without its rotation, is the lock file's own chaos clause failing, and the reason it cannot happen
is that there is one transaction rather than two calls that usually both succeed.

`unique(workspace_id, display_name)` is phase 10's constraint; catch its `IntegrityError` and render a
`409` with a dedicated `ErrorCode`, never a 500.

**`src/prope/provider_access/api.py` — one router, ten operations, six paths.**

```
POST   /api/v1/providers                          provider.configure
GET    /api/v1/providers                          provider.configure
GET    /api/v1/providers/{provider_config_id}     provider.configure
PATCH  /api/v1/providers/{provider_config_id}     provider.configure  (+ provider.disable on a status change)
DELETE /api/v1/providers/{provider_config_id}     provider.configure
POST   /api/v1/providers/{provider_config_id}/credential      provider.rotate_credential
POST   /api/v1/providers/{provider_config_id}/verify          provider.configure
GET    /api/v1/providers/{provider_config_id}/models          catalogue.read
POST   /api/v1/providers/{provider_config_id}/models          provider.configure
POST   /api/v1/providers/{provider_config_id}/models/refresh  provider.configure
```

Every operation: `require_usable_session` (phase 9's gate — **not** the bare `require_session`; only
the two `/auth` routes carry that), `declares_action(...)`, `get_sessionmaker`, then

1. read the row inside `workspace_transaction` — under RLS a configuration in another workspace returns
   **zero rows**, which is `visible=False`;
2. `may(session, actor, action, subject)` with the subject's attributes **passed in** from the row just
   read (ADR-0020: this module supplies them; access-control reads nothing);
3. `refusal_for(visible=…, allowed=…, action=…)` and raise it if not `None`. **No handler writes a 404
   or a 403 itself.** A-045 and phase 9's rule: not-found when the actor cannot see the subject, forbidden
   naming the missing permission when they can.

**The `PATCH` status change is the one operation with two permissions**, and the reason goes at the
handler: `provider.disable` is its own action in the closed vocabulary, so a body that sets
`status = disabled` requires it **in addition to** the route's declared `provider.configure`. The
declared action is the floor and the narrower one is checked on the branch that needs it. A second
