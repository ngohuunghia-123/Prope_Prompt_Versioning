**D-66 — `record_event` is RENAMED to `append`, not wrapped by it.**
Chosen: one function, one name, and the old name gone from `src/` and `tests/` alike.
Rejected: **a thin `append()` that calls `record_event()`.** It reads as the cheaper change and it is
not. It leaves two public entry points into the one path whose whole guarantee is that it runs
exactly once inside the caller's transaction, and the second one is the one a future module reaches
for by grep. It also double-books `check_event`: plan 04-02's docstring already says *"`record_event`
calls it and **nothing else may**, and Phase 5's `append()` wraps `record_event` and must not call it
a second time: a second call double-counts `append_rejected_total`, and the lock's alert makes every
increment a page."* A wrapper is a live invitation to exactly that. A rename cannot make the mistake.
Also rejected: **keeping `record_event` as a deprecated alias.** There is no external consumer to
deprecate for — the only callers are four test files in this repository, and the module has been
public for one phase.
Cost, stated: four test files change import and call site in this plan.
Reversibility: **cheap.**

**D-67 — `HistoryEventDraft` loses its eleventh field; `append()` mints the id and returns it.**
Chosen: the draft carries exactly INT-006's ten envelope fields — `workspace_id`, `actor_type`,
`actor_id`, `action`, `target_type`, `target_id`, `scope_prompt_id`, `reason`, `details`,
`occurred_at` — and `append()` mints `hev_` + ULID at the write and returns it as a `str`.
Rejected: **keeping `id` on the draft** (plan 04-02's shape, declared in Phase 4's `deferred-items.md`
§3 as a widening handed forward to this phase). Two grounds. It puts a field in the envelope that
INT-006 does not name, on a seam five modules build against, and every one of those five would then
carry a `hev_`-prefixed default factory's worth of knowledge about an identifier convention that is
the provider's (A-045, ADR-0003). And it makes the id **caller-supplied**, which on an append-only
table is an id a caller can collide with: `pk_history_event` is on `id`, so two callers minting from
the same clock millisecond is an `IntegrityError` inside somebody's release rather than inside this
module. Minting at the one site that writes removes the question.
Also rejected: **returning `None`** and letting the caller re-read. INT-006's `apis.exposes` line
says `-> void`, and a caller that needs the id it just wrote would have to query for it — on a table
with no natural key for "the row I just inserted". The widening is one return value and costs a
caller nothing; it is **raised as `OQ-035`, not absorbed**, because `docs/` is read-only and a
silently widened seam is what OQ files exist to stop.
Reversibility: **costly** — five modules will be written against the return value from Phase 7 on.

**D-68 — `append()` reads the process registry cache; the registry stops being a parameter.**
Chosen: `async def append(session, event) -> str`, with the registry read from the process-lifetime
cache ADR-0038 mandates. `check_event(event, registry)` keeps its explicit mapping, because the unit
test's whole value is a registry it built itself.
Rejected: **keeping `registry` in the public signature** (Phase 4's shape, chosen there precisely
because *"Phase 5 owns the process-start global"*). It makes five modules each thread a mapping
through their own service layers to reach a function whose declared signature is `append(event)`, and
five threading paths are five chances to pass a stale, invented, or empty one. ADR-0038's failure
mode is named and specific: an empty vocabulary makes every append fail with `unknown_action` while
nothing else notices.
Reversibility: **costly** — same reason as D-67; it is the signature Phase 7 onward is written to.

**D-69 — the cache is installed at process start in `app` and `worker`, and a failure to load fails
startup.** See the `checkpoint:decision` in Task 3, which carries both options in full. Adopted:
**the load raises out of the lifespan and out of `run_worker`.** `adopted: UNCONFIRMED`.
Reversibility: **cheap** — one `try/except` either way.

**D-70 — `read()` returns a plain tuple of events; the caller derives the next cursor.**
Chosen: `-> tuple[HistoryEvent, ...]`, exactly the lock's `read(scope, cursor, limit) -> [event]`.
Rejected: **a page envelope** `HistoryPage(events, next_cursor)`. INT-007 says *"cursor-paginated"*
and the lock says `-> [event]`, and the two are only in tension if the seam has to compute the
cursor. It does not: this project already derives it at the HTTP edge, at
`src/prope/call_ledger/api.py:528` — `next_cursor = items[-1].price_row_id if len(items) == page.limit
else None`. prompt-registry's `/activity` route does the same with `events[-1].id`. Returning an
envelope would widen `-> [event]` **and** duplicate a computation the project already owns.
Reversibility: **cheap.**

**`src/prope/property_history/domain.py` — drop the eleventh field.**

Remove `id` from `HistoryEventDraft` entirely: the field, its default factory, and the
`__post_init__` clause that refused a non-`hev_` value. Move `EVENT_ID_PREFIX = "hev_"` to
`append.py`, which is now the only site that mints one. The remaining ten fields keep their order and
their defaults exactly as they are.

The docstring paragraph that currently explains the eleventh field is **replaced, not deleted**, and
what replaces it is the record of the decision:

> `id` is **not** a field here, and its absence is a decision rather than an omission. INT-006's
> envelope names ten fields and `id` is not among them; unlike `seq` it is not declared
> database-assigned either, because A-045 and ADR-0003 make a `hev_`-prefixed ULID the provider's to
> mint. Phase 4 carried it as an eleventh field with a default factory so `record_event` could return
> a value the caller already held, and declared the widening as owed to this phase. It is discharged
> the cheap way: :func:`append` mints the id at the one site that writes and **returns** it, so the
> envelope matches the seam and the identifier convention stays inside the module that owns it. The
> return is itself a widening against `-> void` and is raised as `OQ-035` rather than absorbed.

Keep every other `__post_init__` rule byte-for-byte: `occurred_at` must be timezone-aware,
`actor_id` must be present unless `actor_type` is `SYSTEM`, `reason` if present must be at most 500
**characters**. Their reasons are already written at the code and none of them changes.

**`src/prope/property_history/registry.py` — ADR-0038's process cache, and only that.**

`load_action_registry(session)` is unchanged: same statement, same `MappingProxyType`, same
`RuntimeError` on zero rows naming `history.history_action_registry`. What is added is the cache and
its two accessors, in `enqueue.handoff()`'s register — a module-level slot, one function that fills
it, one that reads it, one that clears it for the test rig.

```python
_REGISTRY: Mapping[str, RegisteredAction] | None = None


def install_registry(registry: Mapping[str, RegisteredAction]) -> None: ...
def registered_registry() -> Mapping[str, RegisteredAction]: ...
def reset_registry() -> None: ...
```

Four things must be argued at the code and not merely observed:

1. **The slot holds the proxy, never a dict.** `install_registry` stores exactly what
   `load_action_registry` returned — a `MappingProxyType` over a dict whose only other reference has
   already gone out of scope. ADR-0038's Consequences say why in as many words: *"a mutable
   module-level dict is how a later 'just refresh it here' turns into a race that fails a user's
   release."* Add a type check? No — state instead that the only caller is a composition root and the
   only argument is that function's return value, and that `Mapping` in the annotation is the
   contract. A defensive `isinstance` here would be checking our own two call sites.
2. **`registered_registry()` raises rather than returning empty.** `RuntimeError`, naming
   `install_registry` and both composition roots by module path. An empty mapping would make every
   `append()` fail with `unknown_action` — a `PropertyHistoryAppendRejected` **page** per failed
   append, blaming the caller for a composition bug. The refusal names what is missing, which is the
   standing project rule (ORCHESTRATION §3: *never zero, and a refusal names what is missing*).
   Say explicitly that this is a *different* `RuntimeError` from `load_action_registry`'s: that one
   means the migration did not run, this one means the process did not install what the migration
   seeded, and a reader hitting either needs to know which.
3. **`reset_registry()` exists for the test rig and for nothing else**, and says so, in
   `reset_handoff`'s register. Name the case: a test that drives two lifespans in one process, or one
   that must prove `registered_registry()` refuses before an install. It is not a refresh path —
   ADR-0038 rejects a refresh path by name — and the docstring must say that, because `reset` plus
   `install` is a refresh spelled in two calls and somebody will notice.
4. **No TTL, no expiry, no timestamp.** One sentence, so the absence is a decision on the page rather
   than a gap. ADR-0038 rejected a 60-second TTL explicitly: *"the refresh would fire every 60 seconds

**The decision.** ADR-0038 requires the registry to be *"read into an immutable in-process mapping
once at process start"* in both the `app` and `worker` containers. That makes the load the first thing
in either process that opens a database connection at startup — `app.py` today builds an engine and
does not connect until `/readyz`. So a question with no precedent in this repository has to be
answered: **what does a process do when that load fails?**

<checkpoint:decision>

**Option A — the load raises, and startup fails.**
The lifespan and `run_worker` let the exception out. Compose's restart policy retries.
*Pros:* the process either has the vocabulary or does not exist, which is the only state a reader has
to reason about. ADR-0038's one named sharp edge — *a migration applied by hand against a running
instance* — stays a function of process start time and nothing else. A `RuntimeError` from
`load_action_registry` (*the migration has not been applied*) surfaces at deploy, where somebody is
watching, rather than at the first release attempt hours later.
*Cons:* a transient PostgreSQL outage at boot becomes a restart loop rather than a `/readyz` 503. On
one VM with no HA (ADR-0033) that is louder than the alternative and it is also noisier — the operator
sees a crash loop where the actual fault is "the database is down", which `/readyz` would have named.

**Option B — the load is caught, logged, and the process starts without a registry.**
`registered_registry()` then raises for the life of the process and every `append()` fails.
*Pros:* preserves the shape `app.py` already argues for the broker — *a dependency that is not there
does not stop this process from serving* — and `/readyz` names the database, which is more information
than a crash loop.
*Cons:* it converts a transient outage into a **permanent** one. There is no retry, no TTL and no
invalidation path — ADR-0038 rejects all three by name — so the process serves 200 on `/readyz` the
moment the database returns, while every state change in the product fails with a
`PropertyHistoryAppendRejected` page whose stated meaning is *"a caller bug that has just failed a
user's transaction"*. The page would be true and its cause would be a lie. Recovering needs a manual
restart that nothing tells anyone to perform.

**Reversibility: cheap.** One `try/except` either way, in two files, with no data consequence.

**ADOPTED: Option A. `adopted: UNCONFIRMED`.**
The deciding argument is not startup semantics, it is what the metric means afterwards. Option B
leaves a process that looks healthy and cannot record anything, and routes the alarm to the module
whose alert already says every increment is *somebody else's* bug. A crash loop is a worse-looking
failure and a better-behaved one: it names the real dependency, it heals itself when the dependency
returns, and it cannot produce a state where the audit log is silently unavailable — which is the one
outcome this module exists to prevent. Recorded in `deferred-items.md` and owed a numbered item in
`05-UAT.md`.

</checkpoint:decision>

**`src/prope/property_history/read.py` — new.**

Module docstring, four paragraphs, in `append.py`'s register:

1. **The load-bearing negative, first, because it is INT-007's own opening.** This function performs
   no permission check and **has no way to**. There is no actor parameter, no import of
   access-control, and nothing in this package imports another Prope module at all — that is what
   A-044 traded away to break the cycle, and it is why property-history depends on nothing. A caller
   that reaches this without having checked has leaked another workspace's decision trail; **RLS is
   the backstop (ADR-0045), not the control.** Name `tests/architecture/test_property_history_depends_on_nothing.py`
   (plan 05-02) as the file that makes the absence checkable rather than intended.
2. **Ordered by `seq`, never by `occurred_at`, and the mistake is available to be made.** The
   timestamp column stays for display and for the review-turnaround duration, which is exactly why
   somebody will sort on it. A-125 and ADR-0024 make `seq` the only sort key; approve-and-release
   writes two events with the same timestamp in one transaction (A-076), so a timestamp sort shows the
   one screen whose job is the sequence of decisions an arbitrary sequence *"roughly half the time,
   for exactly the two-event cases that matter most"*.
3. **The session is handed in and this function opens nothing.** Same contract as `append`, same
   reason (ADR-0023). A read that opened its own session would read outside the caller's transaction,
   which on a screen rendered mid-transaction is a different set of rows than the caller is about to
   commit — and it would carry no tenant, so under ADR-0035's inversion it would return **zero rows**
   rather than raising.
4. **Assignment order is not commit order, and that is why this paginates `seq` DESCENDING.** Two
   concurrent transactions can take `seq` 5 and 6 and commit 6 first, so a reader between the two
   commits sees 6 with no 5. A *what is new since `seq > N`* poll would then **permanently** skip row
   5 — it committed after a higher `seq` was already returned, and an ascending poll never looks back.
   INT-007 paginates descending, where a late-committing lower `seq` simply appears on a later page.
   Inside one transaction — the case PH-04 is about — the order is exact. Across transactions it is
   not, and the difference is the reason for the direction. Phase 4's `deferred-items.md` handed this
   to this phase as documentation; **plan 05-02 asserts it** and this paragraph names that test.

2. `test_two_events_in_one_transaction_come_back_newest_seq_first_against_the_clock` — the sharp one.

   order**, in one transaction. `read()` returns **B then A** — B has the higher `seq` and the earlier

   implementation that sorted by `occurred_at ASC` would return B then A *for the wrong reason*, which
   the assertion on `seq` catches. State in the docstring why this differs from PH-04's test: Phase 4
   asserts *identical* timestamps, which proves `seq` is a tiebreak; this asserts *inverted* ones,
   which proves `seq` is the sort key. Both are needed and neither implies the other.
3. `test_another_prompt_and_another_workspace_do_not_appear` — three events: one on the prompt under
