<objective>
Close **PH-03** and prove ROADMAP **SC1** — *"A prompt with a full lifecycle returns all ten of its
events in one query in submission order, with nothing from another prompt or another workspace."*

This is the assertion the whole `scope_prompt_id` column exists for. A-119's argument is that the
events a user expects on a prompt's Activity screen are *"written by four modules against six target
types"*, and that this module **may not join to any of their tables** — so without a scope column the
query is impossible rather than merely slow. The test writes the lifecycle through the seam, reads it
once, and asserts the story is complete, ordered, and contains nothing that is not about that prompt.

**D-76 — AC-3's tenth event is the revision that registration itself mints, and the reading is
recorded rather than assumed.**

The lock's AC-3 enumerates the lifecycle as *"created, revised twice, submitted, approved, released,
its suite edited, access granted, restored"* and then says **all ten** events are returned. Counting
the verbs gives **nine**. Phase 4 found the gap and handed it here without resolving it, on the
grounds that AC-3 belongs to the phase that owns it.

Chosen: **registration writes two events** — `property_created` for the property and
`revision_created` for the revision it is registered with — so the enumeration reads
`property_created`, `revision_created`, `revision_created`, `revision_created`,
`revision_submitted`, `revision_approved`, `revision_released`, `eval_suite_updated`,
`access_granted`, `revision_restored`. Ten, across four modules, and every name is a seeded registry
row.

The derivation, stated because it is derived and not read: `prompt-registry.lock.yml`'s `apis.exposes`
names `POST /api/v1/prompts` as *"register a prompt property"* and `POST
/api/v1/prompts/{prompt_id}/revisions` as *"creates the **next** immutable revision"*. *Next* presumes
a first, and the first cannot come from the route that makes the next one. `prompt_registry`'s
`revision` table carries `unique(prompt_id, revision_number)` *"allocated inside the creating
transaction (A-048)"*, and a property with no revision has no body to release. So registration mints
revision 1, and its `revision_created` is the tenth event.

Rejected: **treating "revised twice" as three revisions.** It reads the same arithmetic into a phrase
that plainly means two, and it leaves `property_created` as the only event a registration writes —
which would make a prompt's first Activity entry a property with no revision, and would make
`revision_created` a five-event module's fourth event rather than its second.
Rejected: **counting the release as two events** (`revision_approved` + `revision_released` from an
approve-and-release). AC-3 already lists *approved* and *released* separately, so it would be
double-counting the same pair, and A-076's approve-and-release is Phase 4's AC-4, not this one.
Rejected: **calling the lock wrong and asserting nine.** ROADMAP SC1 says ten in this phase's own
success criteria; a phase that satisfies its criterion by disagreeing with it has not satisfied it.

**`OQ-033` records the gap**, names the two files that say ten over an enumeration of nine, and states
the adopted reading and its derivation so a human can confirm or correct it. `docs/` is not edited.
Reversibility: **cheap** — one event in one test, if the reading is wrong.

**D-77 — the decoys are written through `append()` on real transactions, and one of them is the
silent failure rather than an obvious one.**

Chosen: four decoys. A different prompt in the same workspace; the **same prompt id** in
`WORKSPACE_B`; an event with no prompt at all (`workspace_created`); and — the one worth the most —
a `revision_created` whose `target_id` is one of this prompt's own revisions but whose
`scope_prompt_id` is **null**.

That fourth decoy is the lock's own most-feared failure written as a test: *"the write succeeded and
the event is simply absent from that prompt's Activity feed ... silent in the direction that matters —
a screen that looks complete and is not."* Asserting it here fixes the semantics of the column while
they are still cheap to fix: **`scope_prompt_id` and not `target_id` is what selects into the
Activity**, so a later module that stamps the target and forgets the scope produces exactly this row
and this test says what it costs. Phase 6 owns the *metric* that detects it
(`prope_property_history_null_scope_prompt_total`); this owns the *behaviour* it detects.

Rejected: **seeding the decoys with `seed_history_events`.** The cross-workspace decoy in particular
has to be written inside `workspace_transaction(..., WORKSPACE_B)` through `append()`, because that is
the only arrangement that also proves `prope_app` **can** write it — a decoy the owner role inserted
proves the read filters rows the application could never have written anyway.
Reversibility: **cheap.**
