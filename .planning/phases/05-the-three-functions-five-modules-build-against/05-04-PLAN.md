**D-78 — PyYAML is pinned in the dev group, and the lock files are parsed rather than scanned.**
Chosen: `pyyaml==6.0.3` in `[dependency-groups] dev`, with the argument at the line.
Rejected: **reading the lock files as text.** It avoids a dependency and it is the wrong trade twice
over. A hand-rolled reader for 700-line YAML files with folded block scalars, quoted scalars and
prose containing `: ` is a second parser to maintain in a test whose job is to be trusted. And the
precedent is bad in a specific, recorded way: `property-history.lock.yml` **did not parse as YAML at
all** until the step-6 sweep normalised 25 scalars, which its own change log describes as the finding
that *"made the rest checkable — every earlier step's claim about this file rested on reading it rather
than on loading it."* A test that reads rather than loads is the same mistake one level down.
Also rejected: **leaving `import yaml` to resolve transitively.** It works today only because
`uvicorn[standard]` pulls PyYAML for its config-file support. Nothing declares that, nothing tests it,
and a future narrowing of that extra — or a uvicorn release that drops it — breaks a **contract test**
with an `ImportError` that reads as unrelated. Declaring it costs one line and makes the dependency a
decision.
Version: `6.0.3`, which is already the version resolved in `uv.lock`, so declaring it must not move any
other pin. **Dev group, not runtime** — no production code parses YAML and none should.
Reversibility: **cheap.**

**D-79 — the derivation is three-way, and the per-module count is asserted as well as the set.**
Chosen: extract the names from (a) the five writing modules' own `outputs[]` entries addressed to
property-history; cross-check against (b) the same lists as `property-history.lock.yml` restates them
in its `inputs[]` block; and check both against (c) the count each of those `inputs[]` entries declares
in its opening words (*"5 events — …"*, *"8 events — …"*). All three must agree before the registry is
compared to anything.
Rejected: **extracting from one source.** AC-6 says *"the union of the five lock files' event lists"*,
which is (a) — but (a) is prose, and an extraction bug over prose is silent in the direction that
matters: it drops a name and the registry looks like it has an extra. (b) and (c) are two independent
statements of the same fact written by a different pass on a different day, and an extraction that
satisfies all three is an extraction that is working.
Rejected: **asserting only the union.** A union assertion passes when `access_granted` is attributed to
prompt-registry instead of access-control — which is exactly the *"one misfiled event"* the original
reconciliation found, and `module_map.md` really did list it under the wrong module. So the test also
groups the registry by `writing_module` and compares per module.
Reversibility: **cheap.**

**D-80 — `registered_actions()` reads the table, takes a session, and returns all five columns.**
Chosen: `async def registered_actions(session) -> tuple[RegisteredAction, ...]`.
The three authorities disagree with each other and the disagreement is `OQ-034`:
`property-history.lock.yml` `apis.exposes` says `-> [{action, target_type, detail_keys}]` — three
fields; `interfaces.md` INT-008 says `[{action, target_type, detail_keys, requires_reason}]` — four;
the table has five columns and `RegisteredAction` carries all five. And **neither declared signature
has a parameter**, while ADR-0038's Consequences say in as many words that *"`registered_actions()`
continues to read the table rather than the cache ... a test that checks the cache against the lock
files instead of the database would assert nothing about what `append()` will accept after the next
migration"* — and ADR-0023 forbids this module opening a connection of its own. A table read with no
connection is not expressible.
Chosen resolution: the session is a parameter (forced), and the return carries all five fields (a
superset of both declared shapes, so no consumer of either is broken).
Rejected: **returning three or four fields to match one authority.** It would pick a winner between two
specs by omission, and `writing_module` is the field D-79's per-module assertion needs — dropping it
would make the misfiled-event check impossible from the seam INT-008 exists to provide.
Rejected: **reading the process cache**, which ADR-0038 rules out by name and which would make this
test assert that a mapping loaded from the table matches the lock files — true and worthless the day
the process is older than the migration.
Reversibility: **cheap** — the only consumer inside this repository is this test, and Phase 23's
route-table assertion is the next one.

**The extraction, which is the whole of this task.** The five `outputs[].what` values are **prose
paragraphs, not lists**, and both obvious approaches fail:

- A permissive `[a-z_]+_[a-z]+` over the whole paragraph **over-extracts**. release-control's carries
  `version_id`, `previous_version_id`, `break_glass`, `set_revision_status`, `target_type` and
  `action registry`; prompt-registry's carries `scope_prompt_id`; evaluation's carries `prompt_id`,
  `version_id` and `suite_version`; access-control's carries `prompt_grant`, `target_type`,
  `target_id`, `actor_id`, `detail_keys`, `requires_reason` **and `access_level_changed`, which is a
  real action belonging to a different module**. That last one is the dangerous case: it would make the
  union still come out right and the per-module attribution wrong.
- The same regex also **under-extracts**: `retired` has no underscore and is one of the 31.

**What works is a structural parse of the leading run.** In every one of the five paragraphs the
action list is the opening comma-separated run, and it ends at the first item that is not a bare
identifier. Walk the comma-separated items of `what`, and for each:

1. Strip whitespace, and strip a leading `"` (access-control's folded scalar opens with one).
2. Match `[a-z][a-z0-9]*(?:_[a-z0-9]+)*` at position 0. If it does not match, **stop**.
3. If the match consumed the whole item, take the name and continue to the next item.
4. Otherwise look at the first non-space character after the match. If it is a **terminator** —
   `.` `(` `:` `;` or an em dash — take the name and **stop**: the list has ended and prose has begun.
5. Otherwise **stop without taking it**: the item is a phrase (`with the prompt_id`), not a name.

Run against the files as they stand today, that recovers `5, 8, 4, 4, 10` — the terminators actually
exercised are `.` after `retired`, an em dash after `review_task_closed` and `credential_rotated`, `(`
after `user_tombstoned`, and the phrase rule after `eval_run_interrupted`. **This is a planner's
verification against the current files, not a guarantee**: if a lock file's prose has changed, the
extraction will yield the wrong count and the count assertion will say so with the module named. Fix
the extraction, widen the terminator set with a comment saying which paragraph forced it, and never
"fix" it by hardcoding a name.

**The three derivations.** Write one helper per source, each returning `{module_id: [names]}` or
`{module_id: count}`:

  extraction over its `what`.
- `_restated_by_property_history()` — load `property-history.lock.yml`, take the `inputs[]` entries
  whose `contract_ref` contains `INT-006` (assert there are exactly five, which also excludes the
