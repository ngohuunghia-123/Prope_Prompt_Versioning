<objective>
Prove ROADMAP success criterion 4 — **PH-09 and PH-10 / AC-9 and AC-10** — in both halves: a removed
member's `actor_id` is unchanged on every event they wrote, and no history row is ever removed by
anything, with no expiry job that could remove one.

**The finding this plan is built on is that there is nothing to build.** OQ-017 was resolved by the
user as ADR-0054: tombstone the `access.user` row, keep `actor_id`. The lock file records the
consequence in its own words — *"THIS MODULE CHANGES IN NO WAY, and that is the finding rather than an
absence of one"* — because `actor_id` is a **value and not a foreign key** (A-122), so an erased
account cascades nowhere, no query breaks, and the append-only privilege is not spent. A guarantee that
holds because nothing was built is exactly the kind that decays silently, so this plan asserts it three
ways: the rows survive a tombstone, the engine refuses to change them, and **no code path exists** that
could.

**What is standing in for what, said plainly.** AC-9 says *"a member is removed from a workspace"* and
AC-10 says *"a prompt property is retired and a consumer key revoked."* Access-control is Phase 7,
prompt-registry is Phase 13. None of those operations exists. What **does** exist is the vocabulary:
`user_tombstoned`, `retired` and `api_key_revoked` are three of the thirty-one registered actions Phase
4 seeded, so this phase can write the events those operations will write and assert the property that
matters — that writing them changes nothing about what came before. The real cross-module proof lands
in **Phase 8**, whose ROADMAP success criterion 4 already reads *"a tombstone writes one
`user_tombstoned` event per workspace the person belonged to, with empty `details` and no reason"*, and
in **Phase 15** for retirement. Routed in `deferred-items.md` with those phases named.

## D-89 — PH-09 is asserted as the tombstone's module-side half plus a source gate, not deferred to Phase 7

**Chosen.** Write events as an actor across two workspaces, append `user_tombstoned` for that actor in
each, and assert every earlier row is byte-identical — plus a source gate proving no code anywhere
could have changed them.

**Rejected: deferring PH-09 to Phase 7.** PH-09 is this phase's requirement. ORCHESTRATION §9 requires
every requirement a phase owns to be ticked or explicitly not ticked with the reason recorded, and
"the module it depends on is three phases away" is not a reason when the property under test is a
property of *this* module's rows.

**Rejected: creating an `access.user` stand-in table.** `access` is named in
`EXPECTED_ABSENT_SCHEMAS`; creating it here reddens `tests/architecture/test_tenant_coverage.py` and
pre-empts Phase 7's schema. The tombstone's other half — nulling `email`, `display_name` and
`password_hash`, deleting sessions — is genuinely access-control's and is asserted there.

**What is therefore not proven here, stated rather than implied:** that access-control *calls*
`append()` once per workspace when it tombstones. That is Phase 8's AC-14 and it is named in
`deferred-items.md`.

**Reversibility: cheap.**

## D-90 — "no expiry job exists" is a source-and-composition property, not an absence of observed behaviour

**Chosen.** `tests/architecture/test_no_history_deletion_path.py` walks `src/prope/` and `alembic/` for
any statement that removes or mutates a history row, and parses `src/prope/worker.py`'s `supervise({…})`
map to assert no property-history job is composed.

**Rejected: running the worker and asserting rows survive.** That proves no job ran during the test
window, which is a much weaker claim than the one AC-10 makes and would pass against a sweep on a
five-minute interval.

**Rejected: relying on the privilege alone.** `prope_app` holding no `DELETE` is Phase 4's AC-2 and it
is the enforcement — but it is not the whole of AC-10, which says *"no expiry job exists that would
remove one."* A job written against `prope_migrate`, or a `DELETE` in a migration, would satisfy the
privilege and violate the criterion. The source gate is what covers the difference, and ADR-0025 says
so explicitly: *"Combined with A-121, there is no code path in Prope that removes a history row. The
absence of a deletion job is part of the guarantee, not an omission."*

**The one declared exception:** the history migration's `downgrade()` `DROP TABLE`. It goes in the
gate's `ALLOWED` list with its reason — a downgrade runs as `prope_migrate` and is a deployment action,
which is precisely the sanctioned exceptional route ADR-0025 keeps open.

**Reversibility: cheap.**
