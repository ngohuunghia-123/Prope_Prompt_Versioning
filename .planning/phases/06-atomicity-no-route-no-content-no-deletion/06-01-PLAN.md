<objective>
Prove ROADMAP success criterion 1 — **PH-01 / AC-1** — against a process that is actually killed:
a state change and its history event, written in one transaction, are either both there or both gone,
at every interleaving this environment can produce.

This is the tracer for Phase 6. It is the only plan in the phase that drives every layer the module
touches in one path — `workspace_transaction` → a state-change INSERT → `append()` → `COMMIT` → an
owner-role read — and it does it through a second, real process, because the property under test is
about process death and nothing that runs inside the test process can demonstrate it. Everything after
this plan expands off the rig it builds: plan 06-06 adds two more `tests/chaos/` modules to it.

**What is being stood in for, said plainly.** AC-1 is written about a *release* row and its
`revision_released` event. There is no release-control module — it is Phase 22 — so this plan asserts
the same property with a **stand-in state-change row**, and the real cross-module proof (a
`release.release` row and its event, killed at the same points) lands in **Phase 23/24**, where
release-control's writes exist and where ROADMAP SC2 for Phase 23 already requires that "a grant and
its event cannot exist without each other". Nothing about the guarantee changes: what makes AC-1 true
is that `append()` runs on the caller's open transaction and opens none of its own (ADR-0023), and
that property is identical whichever table the caller's other write went to. What is genuinely not
proven here is that release-control *calls* `append()` — which is `failure_modes` row 1, the omitted
call, and is a code-review boundary in this module and a contract test in Phase 23.

## D-81 — the stand-in state-change row is `ledger.workspace_retention`

**Chosen.** The child writes one row into `ledger.workspace_retention` — the workspace's retention
window — as the state change, then appends the history event in the same transaction.

**Rejected: a second `history_event` row as the stand-in.** It is the cheapest option and it is the
weaker one. The property AC-1 protects is that *two writes to two different tables* commit together,
and a bug in which `append()` acquired its own connection while the state change stayed on the
caller's would be invisible if both rows went to the same table through the same function. The
stand-in has to cross a table boundary or it is not standing in for anything.

**Rejected: a test-only table.** Creating one in `history` puts an undeclared table in a schema
`tests/architecture/test_tenant_coverage.py` walks; creating one in a new schema reddens
`EXPECTED_ABSENT_SCHEMAS`. Both are a red test in another module's file, caused by a fixture.

**Rejected: `ledger.call_record`.** It carries the gateway `version_id` CHECK, the currency
invariant and the pricing derivation, so the fixture would be four-fifths about call-ledger and the
one-fifth that is about atomicity would be the hardest part to read. `workspace_retention` is three
columns, `prope_app` holds `SELECT, INSERT, UPDATE` on it (`alembic/versions/0004_workspace_retention.py`),
it is tenant-scoped so **one** `workspace_transaction` covers both writes, and the autouse
truncate fixture already cleans it.

**Reversibility: cheap.** One `text()` constant and one count query. Phase 23 replaces it with a real
release row and deletes nothing else.

## D-82 — the kill is a real external kill of a real child process, at an announced point

**Chosen.** `tests/chaos/kill_point_child.py` is run as `python -m tests.chaos.kill_point_child` in a
`subprocess.Popen`. It connects, opens the transaction, does its work up to the kill point it was
given, prints a single announcement line to stdout, flushes, and then blocks forever. The **parent**
reads that line and calls `Popen.kill()`.

**Rejected: `os._exit()` inside the child.** A process that kills itself chooses its own instant, and
the instants it can choose are exactly the ones between statements — which are the easy ones. The
interesting instant is inside a socket write the process does not control.

**Rejected: monkeypatching `session.commit` to raise, or injecting a failure into `append()`.** Both
assert the injection. Worse, an exception is a thing application code can catch, and INT-006's whole
failure contract is that the raise *is* the mechanism — a test built on a catchable failure would pass
against an implementation that caught it.

**Rejected: `pg_terminate_backend` on its own.** That kills the *server side*. The client survives and
receives an error it could handle, which is a different failure mode (and a real one, worth its own
test in plan 06-06's revoked-INSERT clause). It is not "the process is killed".

**On Windows, which is this host: `Popen.kill()` is `TerminateProcess`.** It is unconditional, runs no
`finally`, no `atexit`, and no asyncio shutdown — which is the one property of `SIGKILL` this test
needs. `loop.add_signal_handler` being unimplemented here is irrelevant: nothing installs a handler.

**Reversibility: cheap.**

## D-83 — the commit window is asserted as a disjunction over a jittered repeat, not at a fixed point

**Chosen.** For the `about_to_commit` kill point the parent kills after a **jittered** delay drawn
from a seeded RNG, repeated `COMMIT_RACE_ITERATIONS = 12` times, and asserts on every repeat that the
two counts are *equal* — both 1 or both 0 — recording the observed distribution in the failure message.

**Rejected: asserting a specific outcome for a kill during `COMMIT`.** There is no specific outcome,
and demanding one would be demanding the wrong thing. Once the commit record is on disk the
transaction is committed no matter what happens to the client; before that it is not. The property is
that there is no third answer.

**Rejected: skipping the commit window.** It is the only interleaving where *both* outcomes are
genuinely reachable, so it is the only one where "either both or neither" is a claim rather than a
restatement of "the transaction never committed". AC-1's words are "by any interleaving"; a test that
covered only the interleavings with one possible answer would satisfy the sentence and not the point.

**Reversibility: cheap.** A constant and a seed.
</objective>

**`tests/property_history/__init__.py` — four additions, in the file's established `#:` voice.**

1. `INSERT_STATE_CHANGE` — a `text()` constant:

```sql
INSERT INTO ledger.workspace_retention
       (workspace_id, retention_window, updated_by, updated_at)
VALUES (:workspace_id, :retention_window, :updated_by, :updated_at)
ON CONFLICT (workspace_id) DO UPDATE
SET retention_window = EXCLUDED.retention_window,
    updated_by       = EXCLUDED.updated_by,
    updated_at       = EXCLUDED.updated_at
```

**Four columns, and the fourth is easy to miss.** `ledger.workspace_retention` carries
`updated_by text NOT NULL` alongside `retention_window` and `updated_at` — read the DDL in
`alembic/versions/0004_workspace_retention.py` rather than trusting this snippet, because an omitted
`NOT NULL` column turns every kill test into a test of a failing `INSERT`. The `retention_window` value
must also satisfy `ck_workspace_retention_window_is_positive`, which is why `STATE_CHANGE_WINDOW` below
is a positive `timedelta` and not a literal at the call site.

Its `#:` block must carry three things and read as a decision rather than a convenience. **What it is
standing in for** — release-control's release row, which does not exist until Phase 22, and the fact
that this plan's objective records the substitution and names Phase 23/24 as where the real one lands.
**Why this table** — D-81's argument in one paragraph: it crosses a table *and* a schema boundary from
`history`, `prope_app` holds `INSERT` and `UPDATE` on it, it is tenant-scoped so one
`workspace_transaction` covers both writes, and the autouse truncate fixture already cleans it.
**And the rule that keeps it honest**: this statement is issued on the session the caller already
holds — never through `prope.call_ledger.retention_settings.set_retention_window`, which opens its
own transaction and would therefore commit the state change independently of the event, quietly
inverting the exact property the test exists to prove. Say that in those words, at the constant,
because reaching for the existing writer is the obvious thing to do and it is wrong here.

Every value is bound. Nothing is interpolated —
`tests/architecture/test_no_sql_interpolation.py` walks `src/prope/` only, so this file is outside the
gate and the discipline has to be written down instead.

2. `COUNT_STATE_CHANGE` — `SELECT count(*) FROM ledger.workspace_retention WHERE workspace_id = :workspace_id`.
   `#:`: read through `migrate_engine` only, so a zero means the row is not there rather than that the
   reader could not see it.

3. `COUNT_BACKENDS_NAMED` — `SELECT count(*) FROM pg_stat_activity WHERE application_name = :name`.
   `#:`: this is the parent's *wait* condition and it is load-bearing. `Popen.kill()` returns as soon
   as the operating system has torn the child down; the PostgreSQL backend on the other end of the
   socket does not notice until its next read, and until it does, the child's uncommitted transaction
   is still open and its `INSERT`s are still there for a reader that could see them. A count taken in
   that window reads the *pre-abort* state. Every assertion in Task 2 therefore waits on this returning
   zero first, and a test that skipped the wait would be green for the wrong reason roughly as often
   as the machine was fast.

4. `KILL_POINTS` — a `tuple[str, ...]` naming the four announcement points, and a
   `STATE_CHANGE_WINDOW = timedelta(days=7)` constant so the row's value is a fixture fact rather than
   a literal repeated in two files. The four names, in the order the child reaches them:
   `"after_state_change"`, `"after_append"`, `"about_to_commit"`, `"never"`. Its `#:` must state that
   `"never"` is not a kill point but the **positive control** — the run that is allowed to finish — and
   that the parent asserts BOTH rows for it, because every "neither" in this file is only evidence if
   the same fixture can produce a "both".

4. Execute `INSERT_STATE_CHANGE` with `workspace_id`, `retention_window=STATE_CHANGE_WINDOW`,

   same person, which is what makes them a state change and its record rather than two unrelated
   writes), and `updated_at=day(1)` — every one bound, never formatted.
5. If the kill point is `after_state_change`, **announce and block** (see below).
6. Load the registry with `load_action_registry(session)` — on the same session, which is what the
   process-start cache would have handed it, and the child is not the place to test the cache.
   **Note in a comment** that this read is not part of the property under test and that if a future
   Phase 5 shape makes the registry a process global the child takes it from there instead.
7. Write the event through the module's public write path with a `HistoryEventDraft` whose `id` is the
   `--event-id` argument, `workspace_id` the `--workspace` argument, `actor_type` `ActorType.USER`, a
   non-null `actor_id`, and an `action` / `target_type` pair that is in the seeded registry, carries no
   required reason and has an empty `detail_keys` — so the append is valid on its own merits and any
   absence is attributable to the kill. Reuse `history_event_values()`'s choice of action rather than
   picking a second one; if the helper returns a mapping rather than a draft, build the draft from it
   so there is still exactly one place the action is chosen.
8. If the kill point is `after_append`, announce and block.
9. If the kill point is `about_to_commit`, announce and block **without** blocking forever — see
   below.
10. Leave the `workspace_transaction` context, which commits. Print a final `committed` line and exit 0.

**The announcement protocol, written down at the function that implements it.** Announcing is:
`print(point, flush=True)` on `sys.stdout` followed by the blocking behaviour for that point.
`flush=True` is not decoration — a killed process's buffered stdout is lost, and a parent that killed
on a timeout instead of on a line would be killing at an unknown point, which is the one thing this
whole file exists to avoid.

For `after_state_change` and `after_append`, blocking is `await asyncio.Event().wait()` — an event
nothing sets. The child sits inside its open transaction until the parent kills it.

For `about_to_commit`, blocking is **not** indefinite: the child announces and then immediately falls
through into the commit. The parent's jittered delay is what decides whether the kill lands before the
commit record reaches disk, inside the round trip, or after. Write at that branch why it is different
from the other two: a child that waited for permission to commit would only ever be killed *before*
the commit, which is `after_append` under another name.

For `never`, no announcement is printed before the work; the child prints `committed` and exits.

**Two rules for the child, stated in its module docstring.**

- **It writes nothing that the module under test would not write.** No `commit()`, no `rollback()`, no
  second connection, no retry. If the child had to do something clever to make the transaction hold
  together, the transaction is not what is holding it together.
- **It has no assertions.** Every claim is the parent's, read through the owner role. A child that
  checked its own work and reported success would be a child whose report is the thing being trusted,
  and it is going to be killed.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a writing module -> `append()` | The caller supplies every field and owns the transaction. Not an authentication boundary; it is the boundary across which the atomicity promise is made, and the only place it can be broken. |
| the process -> the database connection | A transaction's fate is decided on the server. Everything the client believes about it between the last statement and the commit acknowledgement is a guess, and this plan is about which guesses are safe. |
| the test parent -> a child process it kills | The parent trusts a line on stdout to know where the child got to. A missing or unflushed line means the parent kills at an unknown point and reports a result about an interleaving it did not produce. |
