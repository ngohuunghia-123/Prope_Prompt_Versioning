## D-94 — the load target is a default-running proxy plus a marked, skipped full-duration run

**Chosen.** Two tests in one module. A **proxy** that runs in the default suite — a few seconds of
paced appends with the Activity read running concurrently, asserting both p95 targets — and a
**full-duration** run at 200 appends/sec for 10 minutes, carrying Phase 3's registered `load` marker,
skipped by default with its reason visible, executed **once** during this plan with its numbers
recorded in the SUMMARY.

**Rejected: putting the ten-minute run in the default suite.** ORCHESTRATION §10a runs the full suite
once per phase, at the gate, for eighteen more phases. Ten minutes on every one of those is two hours
of wall time bought for a number that does not change between phases.

**Rejected: `addopts = "-m 'not load'"`.** That changes the default selection for the whole repository.
`uv run pytest -q` is literally §9's gate; redefining what it covers is a repo-wide decision this phase
would otherwise take unilaterally. Phase 3 argued exactly this and chose `skipif`; the same reasoning
applies unchanged.

**Rejected: no proxy at all.** A performance criterion proven only by a test nobody runs is a
performance criterion nobody is checking. The proxy is what makes a regression visible at the gate.

**Reversibility: cheap.** A marker, a skip condition and a Makefile target.

## D-95 — the reconciliation query ships now, with one writer's stand-in and its coverage stated

**Chosen.** `RECONCILE_STATE_CHANGES` is written as a named statement constant beside
`INSERT_STATE_CHANGE`, and a test proves it detects an omission by removing an append and watching the
query report the mismatch.

**Rejected: deferring it to Phase 23.** The lock calls it *"the only automated defence against the
silent-omission failure mode"*, and that failure mode is the one it also calls *"the most serious
failure mode in the module."* A defence that arrives in Phase 23 leaves Phases 8, 14 and 17 to invent
three different versions of it, and the version that ships is whichever module wrote it first.

**Rejected: writing it as a generic cross-module query today.** It would have to guess at four modules'
table shapes. What ships is the query's **shape** — a per-workspace count of state-changing operations
compared against a per-workspace count of the events those operations must have written — with the
extension points named in the docstring and the four owning phases listed.

**What this therefore does not prove, stated in the test rather than only here:** that any real writing
module calls `append()`. That is `failure_modes` row 1, whose detection the lock itself describes as
*"Not detectable from this module's metrics… a missing append produces no signal at all"*, and whose
remaining uncovered case is a write bypassing its own module's service layer — a code-review boundary,
not a technical one.

**Reversibility: cheap.**

Prove the sentence the lock file writes: the writing module **fails loudly rather than proceeding
without a trail**. That is two claims — the failure is visible, and the state change does not survive
it — and both are asserted.

**Structure the whole module around one context manager, `_insert_revoked(migrate_engine)`**, an
`asynccontextmanager` that:

- issues `REVOKE INSERT ON history.history_event FROM prope_app` as `prope_migrate` on entry;
- asserts, immediately, that `has_table_privilege('prope_app', 'history.history_event', 'INSERT')` is
  now **false** — so a revoke that silently did nothing cannot produce a vacuous pass;
- yields;
- in a `finally`, issues `GRANT INSERT ON history.history_event TO prope_app` and asserts
  `has_table_privilege` reports **true** again before returning.

Write four sentences at that context manager, and they are the most important prose in the file. The
container is session-scoped. Nothing else in the suite repairs a grant. A leaked revoke fails every
later test with a permission error in a file belonging to another module, which is the hardest failure
in this repository to attribute. And the assertion after the restore exists because a `GRANT` that
errors inside a `finally` during exception handling is exactly the case where nobody looks at the
output.

**Test 1: `test_the_append_fails_loudly_when_insert_is_revoked`.** Inside the context manager, open a
`workspace_transaction`, write the stand-in state-change row with `INSERT_STATE_CHANGE`, then attempt
the append. Assert:

- the append raises, and the raised exception is a database error rather than
  `HistoryAppendRejected` — the distinction matters, because a rejection means a caller bug and this is
  an environment fault, and `RejectionReason` has no member for it and must not grow one;
- `append_failed_total` incremented by exactly one — this is what "loudly" means, and it is why plan
  06-05's eighth metric exists;
- `append_rejected_total` did **not** move.

Then leave the transaction, and assert through `migrate_engine` that **neither** row survives: no
history event and **no state-change row**. That second assertion is the whole clause — *rather than
proceeding without a trail* — and it holds for the reason plan 06-01 proves at length, that the two
writes share one transaction.

**Test 2: `test_a_valid_append_works_immediately_before_and_immediately_after`.** The bracketing
control. Append successfully before entering the context manager and again after leaving it, asserting
both rows land. Without it, a test that failed for an unrelated reason — a broken fixture, a wrong
workspace — would look like a successful demonstration of the revoke.

**Test 3: `test_the_grant_is_restored_even_when_the_body_raises`.** Enter the context manager, raise a
deliberate exception inside it, catch it outside, and assert `has_table_privilege` reports the grant
restored. This is the test that protects the rest of the suite from this file.

**Do not use `grant_table`** from `alembic/ddl.py` here: it issues the module's whole grant matrix and
would silently repair unrelated privileges, which would make a real regression in the migration
invisible. Two explicit statements, and say why at the call site.

Phase 4 proved that one bad append fails one transaction. This proves the isolation claim: that under
concurrency, a bad append fails **its own** transaction and **no other**.

**The workload.** `CONCURRENT_WRITERS = 32` coroutines run with `asyncio.gather`. Each writer opens its
own `workspace_transaction` and performs one append. A deterministic subset — every third writer, so
the count is arithmetic rather than random — carries an unregistered `details` key and is expected to
be rejected; the rest are valid and expected to commit. Spread the writers across **two** workspaces,
because a rejection contaminating a neighbour is at least as likely to do it through a shared session
as through a shared tenant, and one workspace would not distinguish them.

`gather(..., return_exceptions=True)` so a rejection does not cancel its siblings — and say at the call
that this is the point: with `return_exceptions=False` the first rejection would cancel the gather and
the test would be measuring `asyncio`'s cancellation semantics rather than PostgreSQL's isolation.

**The assertions, all four of which are arithmetic rather than approximate.**

1. The number of results that are `HistoryAppendRejected` with `reason is RejectionReason.UNKNOWN_DETAIL_KEY`
   equals the number of bad writers exactly. Not "at least" — an unexpected extra rejection is the
   contamination this test exists to find.
2. The number of results that are not exceptions equals the number of good writers exactly.
3. Through `migrate_engine`: the committed event count equals the number of good writers, and every
   committed event's id is one a good writer minted. **The id check is what makes this a test about
   isolation** rather than about counting — a count could be satisfied by the wrong rows.
4. `append_rejected_total` on the `unknown_detail_key` label moved by exactly the number of bad
   writers, and `append_failed_total` did not move at all — a rejection is a caller bug, not a
   database failure, and the two counters must not blur.

**One more assertion that costs nothing and is the real prize.** Each **good** writer also writes a
stand-in state-change row in its own transaction, using `INSERT_STATE_CHANGE` with its own workspace
and a distinct window value. Assert the surviving state-change rows correspond exactly to the good
writers. That is the clause's *and no other* half stated at the level a reader cares about: a
neighbour's state change was neither lost nor half-applied while somebody else's append was being
refused.

**On `seq` gaps, so nobody reads one as evidence.** Some of the good writers' `INSERT`s will consume
sequence values that a neighbouring rollback also consumed, and rolled-back values are never returned —
so the committed events' `seq` values will have gaps. Phase 4's plan 04-03 already established that a
gap is normal and is never evidence that an event was deleted. Restate it in this module's docstring,
because this is the first test in the repository that produces gaps *at scale* and it is where somebody
will first notice them.

**`tests/property_history/__init__.py`** — add `RECONCILE_STATE_CHANGES`, a `text()` constant that, for
one workspace, returns the count of state-changing operations and the count of the events those
operations must have written, side by side:

```sql
SELECT (SELECT count(*) FROM ledger.workspace_retention
        WHERE workspace_id = :workspace_id)                     AS operations,
       (SELECT count(*) FROM history.history_event
        WHERE workspace_id = :workspace_id
          AND action = :action)                                 AS events
```

Its `#:` block is the longest in the file and carries four things.

**What it is.** The lock's *"reconciliation query"*, and the only automated defence against a failure
whose defining property is that it produces **no signal at all** — a state change written with no
event. Every metric in this module counts appends that happened; nothing can count the call that was
never made.

**What it counts today.** One writing module's stand-in operation, because none of the five real
writers exists yet. So this proves the query's **shape**, not the system's completeness.

**How it grows, with the owners named.** Each writing module adds one `(operation count, expected
action)` pair as it lands: **access-control in Phase 8** (grants, revocations, tombstones),
**prompt-registry in Phase 14** (properties, revisions, retirements), **evaluation in Phase 17** (suite
edits, run lifecycle), **release-control in Phase 23** (approvals, releases, withdrawals). The
statement is written as a two-count comparison rather than as one hard-coded pair so that adding a
module is adding a row to a parametrised test, not rewriting the query.

**What it will never cover**, quoted from the lock so nobody has to go and find it: *"a write that
bypasses its own module's service layer, which is a code-review boundary, not a technical one."*

**`tests/integration/test_history_reconciliation.py`** — three tests.

1. `test_a_matched_workspace_reconciles`. Perform N state-change operations, each paired with its
   append in the same transaction, and assert the query returns `operations == events == N`.

2. `test_an_omitted_append_is_detected`. **This is the test that gives the query its value.** Perform
   N operations but write the append for only N−1 of them — the omission simulated by calling
   `INSERT_STATE_CHANGE` alone in one transaction, which is precisely what a new endpoint or a repair
   script would do. Assert the query returns `operations == N` and `events == N − 1`, and that the
   comparison flags the mismatch. Write at the test that this is the only way to know the query works:
   a reconciliation that always reports a match is indistinguishable from one whose two counts are
   computed from the same source.

3. `test_the_query_is_scoped_to_one_workspace`. Run the same fixture in two workspaces with different
   counts and assert each reconciles independently. A query that summed across tenants would report a
   match whenever two workspaces' errors cancelled — which is the arithmetic accident that makes a
   global reconciliation useless.

**The module docstring** must state, in its own words, that the mitigation for `failure_modes` row 1 is
*reduced rather than removed*, and that the lock says so first.
