## D-91 — `prope_property_history_rows_total` ships **unlabelled**, resolving OQ-030 in the direction ADR-0030 points

`docs/brainstorm/open_questions/OQ-030.md` was raised by Phase 4 planning and says, in its own words,
that it **blocks Phase 6**. It is now Phase 6. The lock declares
`prope_property_history_rows_total # gauge, labels: workspace_id`;
`src/prope/observability.py:1-33` states that `workspace_id` is deliberately never a label; and
`tests/broker/test_publish_confirm_failures.py`'s `test_workspace_id_is_never_a_metric_label` asserts
that over **every** `prope_*` metric and is green today.

**And a second finding OQ-030 did not anticipate, which is OQ-037.** Dropping the label makes the
gauge *unmeasurable by any role the running process has*. An unlabelled global count needs a
cross-workspace read, and under ADR-0035 a `prope_app` query with no `app.workspace_id` set returns
**zero rows** — so the gauge would read 0 forever, which is the failure mode `worker.py`'s
`ObservedWorkspaces` docstring already describes for a different sweep. The labelled form would need a
workspace enumerator, and `access.list_workspaces()` is Phase 7's; inventing a fifth `SECURITY DEFINER`
function here is refused outright (§2). So: **the gauge is declared and left unset**, with the setter
routed to Phase 8, and the reason written at the declaration.

That is not a dodge, and the precedent is in this repository: `src/prope/observability.py`'s D-40
paragraph argues at length that all eighteen call-ledger metrics are defined at import *even where
nothing increments them yet*, because `REGISTRY.get_sample_value` answers `None` — not `0.0` — for a
metric nothing has touched, so a metric defined lazily is indistinguishable from one that was never
wired, and no alert can be written against a series that does not exist. **Shipping the declaration is
shipping the metric**; shipping a wrong number would not be.

## D-92 — `prompt_scoped` becomes a column on `history_action_registry`

`failure_modes` row 3's mitigation says *"The registry records which actions are prompt-scoped, so the
check is data-driven rather than a list in code."* `data.owns` lists the registry's fields as
`action, target_type, detail_keys, requires_reason, writing_module` — five, and none of them is that
one. The mitigation names a column the schema does not have.

**Chosen: add it.** One additive migration: `ALTER TABLE history.history_action_registry ADD COLUMN
prompt_scoped boolean NOT NULL DEFAULT false`, then an `UPDATE` setting it true for the actions whose
subject lives under a prompt, then `DROP DEFAULT` so a future insert must state its intent.

**Rejected: deriving it in Python from `target_type`.** That is precisely *"a list in code"*, which the
mitigation rejects by name — and the list would have to be maintained beside a registry that already
exists to stop lists being maintained in six places. It would also put the decision about which
target types are prompt-scoped in a module the writing modules do not read.

**Rejected: leaving `null_scope_prompt_total` unwired.** It is one of the seven declared metrics and
one of the three declared alerts reads it. A counter with no producer is the shape D-40 argues against
from the other side: it exists and is permanently zero, which is indistinguishable from healthy.

**Reversibility: cheap to drop, costly to have got wrong.** The column is additive and nothing outside
this module reads it; dropping it is one migration. What is not cheap is a wrong *value* — an action
marked not-prompt-scoped never trips the guard, so the Activity feed is quietly incomplete and the one
counter that would have said so stays at zero. The seed values are therefore listed explicitly in the
migration with the reason for each, not derived by a rule.

**Raised as OQ-038**, against `data.owns → history_action_registry → fields` and `failure_modes` row 3.

## D-93 — an eighth metric, because one of the three declared alerts has no series

`observability_requirements.alerts` declares **PropertyHistoryWriteFailure** — *"append errors
excluding rejections, over 5 min, page"* — and `observability_requirements.metrics` declares no series
that counts them. `append_rejected_total` counts the refusals the alert explicitly excludes; nothing
counts a database error.

**Chosen: ship `prope_property_history_append_failed_total`, unlabelled**, incremented in an `except`
that **re-raises unchanged**, and write the alert against it.

This is the same shape as call-ledger's `prope_call_ledger_dlq_depth`: T-005's mitigation required a
gauge that the metrics block did not list, Phase 2 shipped it, and Phase 3 raised OQ-022 rather than
absorbing the discrepancy. **A mitigation declared in one section and absent from the other is a
mitigation nobody built.**

**Rejected: writing the alert against `up` or against an absence.** An alert that fires on the
process being down is a different alert. **Rejected: dropping the third alert.** The lock says why it
exists: *"the alert exists so that 'the audit log stopped' is never inferred late from an empty
screen."*

**The increment must not change behaviour.** `except HistoryAppendRejected: raise` comes first, so a
rejection is never counted as a failure; then `except Exception: append_failed_total.inc(); raise`.
Nothing is swallowed, nothing is logged that was not logged before, and the caller's transaction fails
exactly as it did.

**Reversibility: cheap.** **Raised as OQ-039.**
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a caller's draft -> a metric label | A label value that a caller can choose is an unbounded series set with extra steps. Every label in this plan comes from the registry row or from a closed set fixed in source. |
