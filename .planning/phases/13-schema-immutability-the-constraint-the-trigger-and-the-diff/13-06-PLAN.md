One module. It is the behavioural half of the owed **AC-9**, and its docstring must say what the coverage
walk in `tests/architecture/test_tenant_coverage.py` does and does not prove: the walk proves a column, a
setting and a policy **exist**; this file proves what they **do**, in the direction that fails open.

Seed, as the owner through `migrate_engine`: one prompt property and two revisions in `WORKSPACE_A`, and
one prompt property and one revision in `WORKSPACE_B`. Seeding as the owner keeps the seed independent of
the policy under test.

1. **The wrong tenant sees nothing.** Inside `workspace_transaction(app_sessionmaker, WORKSPACE_B)`,
   `SELECT count(*) FROM registry.revision` returns **1** — B's own — and a `SELECT` filtered to A's
   `version_id` returns **0**. Then the positive control, in a separate block through `migrate_engine`:
   the same query as the owner returns **3**. Without that control the whole file passes against an empty
   database, which is the failure `tests/security/test_append_only_privilege.py`'s docstring names.
   Repeat for `registry.prompt_property`.
2. **No tenant sees nothing, rather than everything.** Open a session from `app_sessionmaker` **without**
   `workspace_transaction` — a bare `session.begin()` with no `set_config` — and assert both tables
   return **0** rows. This is the direction ADR-0045 is written about and the one that fails **open** if
   the predicate is wrong: a policy written as `workspace_id = current_setting('app.workspace_id')` with
   the one-argument form would *raise* here, and one written with a `COALESCE` default would return
   everything. Assert zero rows **and** assert that no exception was raised, because "it raised" and "it
   returned nothing" are different outcomes and only one of them is the decision.
3. **A mis-stamped INSERT is refused, not merely invisible.** Inside
   `workspace_transaction(app_sessionmaker, WORKSPACE_A)`, attempt an `INSERT INTO registry.revision`
   whose `workspace_id` is `WORKSPACE_B`. Expect a `DBAPIError` naming the row-security policy
   (`new row violates row-level security policy`). Say at the assertion that this is the `WITH CHECK` half
   of `enable_tenant_rls`, which `alembic/ddl.py` writes out explicitly precisely so it *"cannot be
   dropped by accident"* — and that without it the row would be written and then be invisible to
   everyone, which is worse than a refusal because nothing would ever surface it. Repeat for
   `registry.prompt_property`.
4. **A cross-tenant parent is refused by the foreign key.** Inside `WORKSPACE_A`'s transaction, attempt an
   `INSERT INTO registry.revision` with `workspace_id = WORKSPACE_A` — correctly stamped, so the policy
   is satisfied — but `prompt_id` naming **B's** prompt. Expect a foreign-key violation naming
   `fk_revision_prompt_property`. This is D-222 asserted: referential-integrity checks bypass row
   security, so the parent lookup **would** find B's row, and the only thing refusing it is
   `workspace_id` being inside the key. Docstring: with the single-column key the lock's `notes` imply,
   this insert **succeeds**, and the resulting pair of rows is invisible to every tenant-scoped query in
   the system. That sentence is the whole reason the composite key exists.
5. **The released pointer cannot cross tenants either.** Inside `WORKSPACE_A`, attempt
   `SET_RELEASED_POINTER` against **B's** `Approved` revision. Expect a foreign-key violation naming
   `fk_prompt_property_released_revision`. Same argument, on the constraint that carries BR-03 — and it
   is worth its own test because a cross-tenant release is a way to serve another workspace's prompt text
   from your own model name.
6. **`prope_report` reads both and writes neither.** Through `report_engine`: `SELECT` from both tables
   returns every row across both workspaces (ADR-0037's `BYPASSRLS` full-read credential), and
   `has_table_privilege('prope_report', 'registry.prompt_property', 'INSERT' | 'UPDATE' | 'DELETE')` is
   `False` for all three, on both tables. Note that prompt bodies are inside this role's remit by
   decision — `provider.credential` is the only table in Prope it cannot read (D-166) — and that OQ-006
   governs the classification question while A-020 holds the line until it is answered.

One module. Its job is to make a **silent removal** loud: a later migration that drops a constraint, drops
a grant, or adds a column nobody declared should redden a test here rather than be discovered by a phase
three milestones away.

Its docstring says what it is **not**: it does not restate the five generic invariants
(`test_schema_invariants.py` covers `registry` since plan 13-01 added it to `GENERIC_SCHEMAS`) and it does
not restate the coverage walk. It asserts the things that are specific to this schema and that no generic
rule would notice.

1. **The constraint inventory, as an exact set.** Query `pg_constraint` joined through `pg_class` and
   `pg_namespace` for `nspname = 'registry'`, and assert the set of `(table, conname, contype)` triples
   equals a module-level constant listing every one plan 13-01 created. **An equality, not a
   containment** — the whole value is that adding or removing a constraint requires editing this line,
   which is the same posture `test_migration_chain.py`'s explicit table list already takes and for the
   reason its comment gives: *"a deliberately explicit list, so a table appearing or vanishing from a
   pristine upgrade is an edit somebody made rather than a count that quietly moved."*

   The three whose loss would be worst get a **named** individual assertion as well, with a message
   saying what the loss costs, because a set-equality failure names a diff and not a consequence:
   - `fk_prompt_property_released_revision` — *"BR-03 is not enforced; an unapproved revision can be
     released, which `00_context.md#success` calls the failure that makes the product worthless"*;
   - `ck_prompt_property_released_status` — *"the pointer's status column is no longer pinned to
     `Approved`, so the foreign key above can be satisfied by a `Draft` revision"*;
   - `ck_prompt_property_retired_has_no_release` — *"A-052 survives only as an application check"*.

2. **The index inventory**, the same way, over `pg_indexes` for the schema: the two unique constraints'
   backing indexes, `uq_prompt_property_model_name`, `ix_prompt_property_search_text_trgm` and
   `ix_prompt_property_workspace_updated_at`. Assert the trigram index's `indexdef` contains
   `gin_trgm_ops` — the operator class is the thing that makes substring matching indexed rather than a
   sequential scan, and an index rebuilt without it would keep every AC-10 assertion passing while
   quietly moving the search off the index.

3. **The column inventory.** For both tables, assert the exact column-name set against a module constant
   that carries the lock's declared field list **plus** the two declared deviations, each with a comment
   naming its OQ: `prompt_property.released_version_status` (`OQ-070`) and nothing else. Say in the
   comment that this list is the place a future undeclared column becomes visible, which is what makes
   the OQ mechanism enforceable rather than aspirational.

4. **The grant matrix, from the engine's side.** For `prope_app`:
   `has_table_privilege` is `True` for SELECT and INSERT and `False` for DELETE on both tables;
   `has_table_privilege(..., 'UPDATE')` is **`False`** on both — a column-level grant does not confer the
   table-level privilege, and asserting that explicitly is what documents the shape. Then
   `has_column_privilege` per column: `True` for exactly the columns plan 13-01's two
   `grant_column_update` calls named, and `False` for every other column of both tables, iterating the
   column list rather than spot-checking. Write at the loop why the exhaustive form is used: a
   spot-check of `search_text` and `namespace` would pass against a grant list that had accidentally
   gained `name`.

5. **The extensions exist and are where the code expects them.** `pg_trgm` and `unaccent` are both
   installed, and `public.unaccent('tiêu đề')` returns `'tieu de'` — asserted as a behaviour, because
   *"the extension is installed"* and *"the fold does what the tests assume"* are different claims and

6. **Nothing else lives in `registry`.** Exactly two tables, exactly three functions, exactly two

   phase.

`tests/prompt_registry/__init__.py` gains only shared constants if two of this plan's modules need the
same thing. Prefer local constants; this is the last plan in the phase and there is nobody left to share
with.
