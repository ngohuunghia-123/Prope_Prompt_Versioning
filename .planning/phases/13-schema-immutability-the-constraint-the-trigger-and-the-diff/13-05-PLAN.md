## D-230 — The diff is a pure function; reading the two revisions is a separate half

**Chosen.** `compute_diff(before: Revision, after: Revision) -> RevisionDiff` is pure: no session, no
clock, no I/O, no metric. `get_diff(session, from_version_id, to_version_id) -> RevisionDiff` reads both
rows through plan 13-02's `get_revision` and calls it.

Three things fall out and each is worth the split on its own:

1. **SC2's budget is measurable.** A number that includes two indexed reads and a network round trip is a
   number about the database. The load test measures `compute_diff` at the cap and the integration test
   measures `get_diff` end to end, and the two are reported separately so a regression is attributable.
2. **The pathological input is testable without a database.** Building two 32 KiB bodies of identical
   lines through `create_revision` costs two transactions per case; calling the pure function costs
   nothing.
3. **INT-011 names `get_diff` as the seam release-control consumes**, and that seam must be the reading
   one. The pure function is an implementation detail this module exposes because its own tests need it,
   and the docstring says so rather than letting a second module discover it and depend on it.

**Rejected: one function taking two version ids and doing everything.** It is the shape INT-011
literally describes and it makes the pathological case a database fixture.

**Reversibility: cheap.**

## D-229 — The quadratic guard difflib removed is replaced by a counted one, and a degraded diff says so

**Chosen.** Three things, in order, inside `compute_diff`:

1. **Trim the common prefix and suffix** of identical lines before matching. Standard practice in every
   real diff implementation, linear, and it collapses the most common shape in this product — a 32 KiB
   prompt with one paragraph edited — from a full matrix to a handful of lines.
2. **Count the candidate pairs** the matcher would actually consider, in O(n+m), with two `Counter`s:
   `candidate_pairs = sum(before_counts[line] * after_counts[line] for line in shared_lines)`. That is
   exactly the work `SequenceMatcher.find_longest_match` does — for each line of `a` it walks every
   position of that line in `b` — so it is a measurement rather than a proxy.
3. **If `candidate_pairs > MAX_DIFF_CANDIDATE_PAIRS`, do not run the matcher.** Emit the trimmed middle
   as one replace hunk (everything removed, everything added) and set `exact = False`.

**The hazard this closes is real and it is created by a decision the lock file already made.**
`autojunk=False` is required — INT-011 and the lock's `libraries_frameworks` both say so, because
autojunk *"silently discards lines appearing in more than 1% of a sequence longer than 200 elements,
which on a 32 KiB body with repeated short lines produces a diff that looks WRONG rather than slow"* —
and the lock also records the consequence in one clause: *"Disabling it removes the quadratic-case
guard."* At A-050's cap a body can be tens of thousands of lines. Two such bodies made of repeated
identical lines are hundreds of millions of candidate pairs, which is seconds in Python, not
milliseconds. **The lock says the cost is *"under test rather than assumed"* — this is the plan where it
is put under test, and a test that discovered a ten-second diff without a guard in place would be a
finding rather than a passing criterion.**

`MAX_DIFF_CANDIDATE_PAIRS = 2_000_000`, with the arithmetic written at the constant: the matcher's inner
step is a dictionary lookup and a comparison, on the order of 50–100 ns in CPython, so two million pairs
is roughly 100–200 ms — inside the 300 ms budget with room for the field comparison and the hunk
assembly. For realistic content the trimmed middle is small and the shared-line product is a few
thousand, so the ceiling is never approached; it fires only on inputs whose exact diff would be
unreadable anyway. Close with the house sentence: **a tunable judgement, not a repo decision, recorded so
that changing it is a visible act; unvalidated at real scale, like every number of this kind in this
codebase.**

**`exact` is a field on the result, not a log line.** A degraded diff that looked identical to an exact
one would be the silent failure this whole project keeps refusing. Phase 14 serialises it, and
`deferred-items.md` routes that to phase 14 by name along with the sentence the SPA needs — *"this
comparison is too large to align line by line; the whole body is shown as replaced"* — because an
untranslated boolean on a Vietnamese-only UI is a key nobody added (ADR-0053).

**Rejected: `autojunk=True`.** It is difflib's own answer to this problem and the lock rejects it by
name, for a reason that is about correctness rather than speed.

**Rejected: a wall-clock timeout around the matcher.** It makes the result non-deterministic — the same
two revisions diff differently on a loaded machine — and a review screen whose evidence changes between
refreshes is worse than one that is honestly coarse.

**Rejected: capping the line count instead.** A line count is a bad proxy: 30,000 distinct lines diff
quickly and 3,000 identical ones do not. Counting the pairs measures the thing that actually costs.

**Reversibility: costly.** `exact` is a field phase 14 serialises and the SPA renders, so removing it is
an API change.

**Result types**, all `@dataclass(frozen=True, slots=True)`, declared here rather than in `domain.py` so
this plan shares no file with the two that run beside it:

```python
class HunkKind(StrEnum):        # or a str constant group in the file's existing style
    EQUAL = "equal"
    INSERT = "insert"
    DELETE = "delete"
    REPLACE = "replace"

@dataclass(frozen=True, slots=True)
class BodyHunk:
    kind: HunkKind
    before_start: int      # 0-based line index into the BEFORE body
    before_lines: tuple[str, ...]
    after_start: int
    after_lines: tuple[str, ...]

@dataclass(frozen=True, slots=True)
class FieldChange:
    field: str             # "provider_config_id" | "upstream_model" | "parameters" | "fallback_answer"
    changed: bool
    before: object | None
    after: object | None

@dataclass(frozen=True, slots=True)
class ParameterChange:
    key: str
    kind: str              # "added" | "removed" | "changed"
    before: object | None
    after: object | None

@dataclass(frozen=True, slots=True)
class RevisionDiff:
    from_version_id: str
    to_version_id: str
    from_revision_number: int
    to_revision_number: int
    body_hunks: tuple[BodyHunk, ...]
    fields: tuple[FieldChange, ...]           # always four, in a fixed order
    parameter_changes: tuple[ParameterChange, ...]
    exact: bool
```

Four decisions to write **at** these types, because each is the kind a reader will otherwise second-guess:

- **`fields` always carries four entries, changed or not** (A-015's *"field-level comparison of provider,
  upstream model, parameters, and fallback answer"*). A reviewer needs to see that the provider did not
  move as plainly as that it did; a list of only-what-changed makes *"nothing else changed"* an inference
  from absence, and absence is not evidence on a screen where an approval is recorded.
- **`parameter_changes` is a decomposition, not a replacement.** `parameters` still appears in `fields`
  as one entry with `changed` set, and the per-key list sits beside it. Two JSON blobs rendered as
  *"changed"* is a field-level comparison in name only, and the per-key form costs a dict comparison.
- **`before_lines` / `after_lines` keep line endings**, produced by `str.splitlines(keepends=True)`. A
  diff that normalises line endings hides a change in them, and a prompt body is fed verbatim to a model.
- **`exact` is `False` only when the guard fired.** Say at the field what a client must render (D-229),
  and that the string itself is the SPA's i18n key rather than anything this module produces (ADR-0053).

**`compute_diff(before: Revision, after: Revision) -> RevisionDiff`** — pure. In order:

1. `before_lines = before.body.splitlines(keepends=True)`, same for after.
2. **Trim.** Count the shared prefix and the shared suffix (guarding the two from overlapping on
   near-identical inputs), record their lengths, and match only the middles. Emit the prefix as one
   `EQUAL` hunk, the middles' hunks, then the suffix as one `EQUAL` hunk. **Every hunk's indices are into
   the untrimmed bodies**, so a caller renders line numbers without knowing the trim happened — say that
   at the code, because off-by-one here is the defect this optimisation actually produces.
3. **Count candidate pairs** over the trimmed middles with two `collections.Counter`s, exactly as D-229
   describes, and compare against `MAX_DIFF_CANDIDATE_PAIRS`.
4. **Over the ceiling:** one `REPLACE` hunk covering both middles, `exact = False`. **Under it:**
   `SequenceMatcher(None, before_middle, after_middle, autojunk=False).get_opcodes()`, mapped to hunks,
   `exact = True`. Write at the constructor that the first argument is `None` (no `isjunk`) and that
   `autojunk=False` is the whole reason this call is written out rather than using
   `difflib.unified_diff`, **which constructs its own `SequenceMatcher` with `autojunk` left on**. That
   sentence is the one that stops somebody replacing four lines with a one-line stdlib call.
5. **The four fields**, in the fixed order `provider_config_id`, `upstream_model`, `parameters`,
   `fallback_answer`. `changed` is `before != after` — for `parameters` that is a plain dict comparison
   and for `fallback_answer` it must treat `None` and `""` as **different**, because one means *no
   fallback configured* and the other means *an empty fallback*, and collapsing them would be the
   "never zero, no fourth state" failure in miniature.
6. **The parameter decomposition**: keys in after and not before are `added`, in before and not after are
   `removed`, in both with different values are `changed`. Sorted by key so two runs produce the same
   output — a review screen that reorders between refreshes is a review screen people stop trusting.

**`get_diff(session, from_version_id, to_version_id) -> RevisionDiff`** — reads both through
`get_revision`, then calls `compute_diff`. It raises:

- `RevisionNotFound(version_id)` when either read returns `None`. Under the tenant policy a revision in
  another workspace reads as absent, which is A-116 falling out of the policy again; say so at the branch.
- `RevisionsNotComparable(from_version_id, to_version_id)` when the two rows' `prompt_id`s differ.
  Comparing revisions of two different prompts produces a diff that is technically correct and
  semantically meaningless, and INT-024's route is `/prompts/{id}/diff?from=&to=` — the prompt is in the
  path, so a mismatch is a caller bug. Both errors carry identifiers only.

**Module docstring**, at this repository's density, carrying six things: A-015's *textual, not
consequence-language* and the risk the lock records alongside it (a reviewer can approve a change whose
effect they do not understand; the eval suite and cost delta are the compensating controls, and **no
surface may claim the eval guarantees no degradation**); A-047's *computed on demand and never stored*
with ADR-0002's three reasons; the `autojunk=False` requirement and what autojunk would do; D-229's
guard, its constant and its arithmetic; the pure/reading split (D-230) and that INT-011's seam is
`get_diff`; and the A-046 declaration — **this module holds two prompt bodies in memory on every call and
emits neither, and its two errors carry identifiers only**.

One module, entirely pure — no `app_sessionmaker`, no container. Construct `Revision` instances directly.

Cover, each as its own test with a docstring naming what it protects:

1. **The self-diff.** Identical bodies and identical fields: no non-`EQUAL` hunks, four unchanged fields,
   `exact=True`. This is the assertion that fails if the trim logic double-counts.
2. **A single-line edit** in the middle of a 500-line body: one non-`EQUAL` hunk, correct untrimmed
   indices on both sides, and the surrounding `EQUAL` hunks covering everything else with no gaps and no
   overlaps. Assert the **reconstruction property** rather than the hunk list shape: concatenating every
   hunk's `before_lines` in order yields the original before-body exactly, and the same for after. That
   single assertion catches every off-by-one the trim can produce, and it keeps passing when the hunk
   granularity changes.
3. **An insert at the very start** and **a delete at the very end** — the two cases a prefix/suffix trim
   gets wrong first. Reconstruction property again.
4. **Two bodies with no shared lines at all.** The trim contributes nothing and the matcher does
   everything; assert `exact=True` and reconstruction.
5. **Two bodies that are identical except one is a prefix of the other.** This is where a naive
   prefix-and-suffix trim can overlap and consume the same lines twice; assert reconstruction, which is
   what would catch it.
6. **`autojunk` would have changed the answer.** Build a body of 300 lines in which one short line — say
   `"\n"` — appears 20 times (over 1% of a sequence longer than 200), edit one **other** line, and assert
   the repeated line still appears inside `EQUAL` hunks and is aligned rather than dropped. Docstring:
   this is the assertion INT-011's `autojunk` paragraph exists for, and it is the one that fails if
   somebody replaces the explicit `SequenceMatcher` with `difflib.unified_diff`.
7. **The guard, from both sides.** Construct a pair whose candidate-pair count is just **under**
   `MAX_DIFF_CANDIDATE_PAIRS` and assert `exact=True` with real hunks; construct one just **over** and
   assert `exact=False` with exactly one non-`EQUAL` hunk covering the trimmed middles. Derive both
   inputs from the constant rather than from a hard-coded line count, so changing the constant changes
   the test's inputs rather than breaking it.
8. **The four fields and the parameter decomposition**, as listed in Task 1's acceptance criteria.
