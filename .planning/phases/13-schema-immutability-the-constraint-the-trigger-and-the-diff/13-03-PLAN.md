a refusal that tells the owner **which** release is in the way, and once as a constraint that holds when

ADR-0002 records why the refusal exists rather than the alternative: *"Allow retiring a prompt with an

## D-232 — The retire refusal is a domain error naming the release; the engine is the backstop

**Chosen.** `retire_prompt_property` reads `released_version_id` **inside the transaction it would write
`status` in**, and if it is set, raises `PromptHasActiveRelease(prompt_id, version_id, revision_number)`
without writing anything. Separately, `ck_prompt_property_retired_has_no_release` (plan 13-01) refuses
the same row shape at the engine.

**Two mechanisms, two jobs, and the plan says which is which** so a later reader does not delete one as
redundant. SC3 requires *"refused with a message naming the release"*, and a CHECK constraint's message
names a constraint, not a release — so the message needs the command. The constraint needs to exist
anyway, because A-052 has to survive the writer that never called the command: a data fix, a backfill, a
future importer. This is the same split D-237 makes for A-050's caps one file over, and the same split
D-221 explicitly *refuses* for BR-03 — the difference being that there, the constraint alone is the
requirement, and here, the message is part of it.

**The read and the write share a transaction, and that is load-bearing.** Reading the pointer in one
transaction and writing the status in another leaves a window in which a release lands between them.
Under `REPEATABLE READ` that would be a serialisation failure; under this project's default
`READ COMMITTED` it is a lost guard. Sharing the transaction closes it, and the constraint closes it
again if anybody splits them later.

**Rejected: raising a `409`-shaped object.** HTTP shapes belong to the edge (phase 14), and a domain
error that already knows its status code is a domain error the next caller cannot reuse. The error
carries the facts; INT-024 says the edge renders `409` for a conflict and `422` for validation, and phase
14 decides which this is.

**Rejected: withdrawing the release as part of retiring.** It is the convenient shape and it is refused
outright: `clear_released_revision` is release-control's (INT-014), it takes a `release_id` that records
who decided, and a retire that silently withdrew would be a release decision with no decision record.

**Reversibility: cheap** on the error type, **costly** on the constraint (a landed migration).

## D-233 — One event per changed fact, and no event for a field that did not move

**Chosen.** `update_prompt_property` compares each of the five mutable fields against the row it just
read, writes only what changed, and appends **exactly one event per changed fact that has a name in the
vocabulary**: `owner_changed` when `owner_id` moves, `access_level_changed` when `access_level` moves.
Title, purpose and tags move with **no event of their own**, because the closed 30-name vocabulary
(ADR-0024, plan 04-01) has no name for them and this module may not widen it.

**That asymmetry is real and is written at the code rather than left to be discovered.** A title edit is
invisible in the Activity feed. It is not invisible in the *data*: `updated_at` moves, `search_text` is
rewritten, and the prompt rises to the top of the default list (ADR-0048). Whether the vocabulary should
gain a `property_edited` name is a question for property-history's owner, not something a registry phase
invents — and inventing it would fail plan 04-01's registry allow-list at runtime, which is the
vocabulary being closed doing its job.

**Rejected: one `property_updated` event carrying a `details` diff.** The vocabulary has no such name,
and plan 04-01 seeds every registry action with an **empty** `detail_keys` allow-list, so a `details`
payload would be rejected by the append. Both halves would have to change in another module's schema.

**Rejected: writing an event even when nothing changed.** An audit trail whose rows include *"the owner
was set to the owner it already had"* is an audit trail people stop reading.

**Reversibility: cheap.**

---

## D-234 — An owner transfer is an ordinary update, and the assumption it rests on is named at the code

**Chosen.** `owner_id` is one of the five mutable fields, changed through the same command as the others,
recorded as `owner_changed`. No transfer workflow, no acceptance step, no second party.

A-051 is the proposed default — *"an owner is one person; transfer is an explicit recorded action"* — and
**OQ-008 is open**: whether an owner is a person or a team, and what happens on transfer or departure.
The lock's own risk row says the mitigation is that `owner_id` is *"a single indirection; if OQ-008
answers 'team', it points at a principal table instead of a user table"*. So the code must not
denormalise the owner's name anywhere, and the docstring must say that is deliberate rather than an
oversight.

The related fact that is already decided and must not be re-opened here: a departing person is
**tombstoned, never deleted** (ADR-0054), and `owner_id` is a value rather than a foreign key, so a
tombstoned owner's prompts keep an owner id that still resolves to a row. Nothing in this plan needs to
handle a missing owner, and nothing in it may add a foreign key to `access.user`.

**Reversibility: cheap** while OQ-008 is open and nothing denormalises the name.

### `src/prope/prompt_registry/properties.py`

```python
async def retire_prompt_property(
    sessionmaker, *, workspace_id: str, prompt_id: str, actor_id: str, now: datetime,
) -> None
```

One `workspace_transaction`. Inside it, in this order:

1. `SELECT status, released_version_id FROM registry.prompt_property WHERE id = :prompt_id` — a whole
   `text(...)` constant, **columns named explicitly, never `*`**. No row → `PromptPropertyNotFound`.
   Write at that branch that under the tenant policy a prompt in another workspace is indistinguishable
   from one that does not exist, which is A-116 falling out of the policy rather than being coded.
2. `status == "Retired"` → `PromptAlreadyRetired`.
3. `released_version_id is not None` → read the revision number for it
   (`SELECT revision_number FROM registry.revision WHERE version_id = :version_id`) and raise
   `PromptHasActiveRelease`. **Write the reason for the second read at the code**: AC-5 asks for a message
   naming the release, and a bare `rev_01J…` ULID names nothing a human recognises — the revision number
   is what a person has on screen.
4. `UPDATE registry.prompt_property SET status = 'Retired', updated_at = :now WHERE id = :prompt_id`.
5. `await append(session, HistoryEventDraft(action="retired", target_type="property",
   target_id=prompt_id, scope_prompt_id=prompt_id, details={}, occurred_at=now, ...))` on the same
   session.

**The read at step 1 and the write at step 4 are in one transaction and that is the point** (D-232).
Say so at the function, and name the constraint that catches the case where somebody later splits them.

**Do not clear the released pointer.** Do not touch `released_version_status` or `released_at`. Say why
at the function, citing INT-014.

```python
async def update_prompt_property(
    sessionmaker,
    *,
    workspace_id: str,
    prompt_id: str,
    actor_id: str,
    now: datetime,
    title: str | None = None,
    purpose: str | None = None,
    tags: Sequence[str] | None = None,
    access_level: AccessLevel | None = None,
    owner_id: str | None = None,
) -> None
```

`None` means *not supplied*, which is `PATCH` semantics and must be stated at the signature — none of
these five columns is nullable, so `None` can never mean *set to null* and there is no ambiguity to
resolve. Write that sentence; it is the first thing a reader wonders.

Inside one `workspace_transaction`:

1. Read the current row's five mutable fields plus `status`, columns named explicitly.
2. `status == "Retired"` → raise `PromptAlreadyRetired`. A retired prompt is terminal; editing its title
   is not a state A-049 contemplates, and permitting it silently would make *"terminal"* untrue. **Say at
   this branch that it is an agent judgement**: no authority states it, and the alternative — permitting
   edits to a retired prompt's metadata — is defensible. It is chosen because `Retired` is described as
   terminal and because the narrower behaviour is the reversible one.
3. Build the `SET` list from the supplied fields that actually **differ** from what was read. If nothing
   differs, return without writing and without appending — and comment that this is deliberate (D-233).
4. One `UPDATE` naming only the changed columns plus `updated_at`. **The statement must still be a plain
   string constant** — `tests/architecture/test_no_sql_interpolation.py` refuses a composed one, and the
   walk covers this module. So write **one statement per changed-field combination? No.** Write a single
   statement that assigns every mutable column using `COALESCE(:param, column)` — every parameter is
   bound, the statement is one constant, and a `None` parameter leaves the column alone:

```sql
UPDATE registry.prompt_property
   SET title        = coalesce(:title, title),
       purpose      = coalesce(:purpose, purpose),
       tags         = coalesce(:tags, tags),
       access_level = coalesce(:access_level, access_level),
       owner_id     = coalesce(:owner_id, owner_id),
       updated_at   = :now
 WHERE id = :prompt_id
```

   Write two sentences at it. First: `coalesce` is what lets this be one bound statement instead of a
   composed one, and the composed one is refused by a source gate for a reason that has nothing to do
   with this module. Second: the **column list in the `SET` is what PostgreSQL checks the column-level
   `UPDATE` grant against**, so this statement names exactly the five mutable columns plus `updated_at`
   and naming a sixth — `search_text`, `namespace`, `name` — would fail at the engine even when the bound
   value is `NULL`. That is D-226 and A-021 acting on a statement that never intended to write them, and
   it is worth knowing before somebody adds a column here.

5. Append one event per changed fact with a registered name: `owner_changed` if `owner_id` moved,
   `access_level_changed` if `access_level` moved. Both `target_type="property"`,
   `target_id=prompt_id`, `scope_prompt_id=prompt_id`, `details={}`.
6. Nothing for title / purpose / tags — with the D-233 paragraph written at the code: the vocabulary is
   closed, this module may not widen it, the edit is still visible in `updated_at` and in `search_text`,
   and whether a `property_edited` name should exist is property-history's question and not this
   module's.

Update the module docstring to cover the two new commands, and add one paragraph carrying D-234: an
owner transfer is an ordinary update; A-051 is a **proposed default** and OQ-008 is open; `owner_id` is a
single indirection and **nothing anywhere denormalises the owner's name**, which is what keeps the answer
cheap; a departing person is tombstoned rather than deleted (ADR-0054) and `owner_id` is a value rather
than a foreign key, so nothing here needs to handle a missing owner.

**`tests/integration/test_retire_guard.py`** — the file AC-5 names by path.

owner sees and it is the application's; the **refusal** is what holds when nobody called the command and
it is the engine's. A test that asserted only the first would pass against a build in which a data fix
could retire a released prompt.

`UPDATE` on `status` as `prope_app` (the one column that carries an `UPDATE` grant), then set the
released pointer with `SET_RELEASED_POINTER` binding `'Approved'`. Note in a comment that this is
standing in for phase 14's `set_revision_status` and `set_released_revision`, that both are that phase's,
and that going through raw SQL here is deliberate rather than a shortcut — it keeps SC3's assertion
independent of code this phase does not write.

   expect `PromptHasActiveRelease`. Assert the message contains the `version_id` **and** the revision

   AC's second clause, and the one a test that only checked the exception would miss.
2. **The refusal names no prompt text.** Plant a distinctive marker string inside the body, the change
   summary and the fallback answer of the released revision, and assert none appears in the raised
   message or in any captured structlog record. A-046, asserted rather than intended.
