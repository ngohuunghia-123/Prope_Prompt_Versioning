<objective>
Make **AC-13** true. Tombstoning a person nulls `email`, `display_name` and `password_hash`, deletes
every session they hold, and makes a sign-in with the former email byte- and timing-identical to one
with an email that never existed — while every history event they ever caused stays exactly where it
is, with their `actor_id` unchanged.

This is ROADMAP success criterion 4 and it is the phase's only *irreversible* operation. ADR-0054 §8:
*"Nothing un-tombstones a row and no endpoint restores a name."*

## D-112 — the tombstone is ONE transaction that moves the tenant marker between workspaces

**Chosen.** `tombstone_user` opens one session and one transaction, and inside it issues
`SET_TENANT` — the constant `src/prope/db/session.py` already exports — once per workspace the person
belonged to, doing that workspace's deletions and its `user_tombstoned` append while the marker points
at it. The account-level `UPDATE access."user"` needs no marker at all, because that table carries no
tenant column and has no policy (ADR-0042's enumeration).

**Why this needed deciding rather than choosing.** A-151 says *"One transaction"*, and it lists work
in `session`, `role_binding`, `prompt_grant` and `workspace_member` — four tenant-scoped tables — for a
person who may have belonged to several workspaces. ADR-0035's policy admits exactly one workspace at
a time, and `workspace_transaction` takes its workspace as a **constructor argument** precisely so
that *"there is deliberately no method that could set a second workspace inside an open transaction."*
So the one shape the specification asks for is the one shape the seam declines to offer.

The marker is a transaction-local `set_config(..., true)`, so re-issuing it inside the same
transaction is exactly what it is for and everything reverts at `COMMIT`.

**Rejected: one transaction per workspace, plus one for the account row.** It is what the existing
seam offers and it breaks the operation's whole point. Every ordering has a bad intermediate state: the
account row cleared first leaves an erased person holding live sessions that `access.lookup_session`
would still honour, because that function reads `session` and knows nothing about `user.status`; the
account row cleared last leaves a person whose grants and sessions are gone and whose name is still
there — a half-erasure that reads as a completed one. A-151 said *one transaction* and this is why.

**Rejected: a `SECURITY DEFINER` function that deletes across workspaces.** Fifth object, forbidden,
and worse in kind — ADR-0051's rule is that a definer function returning *rows* (or, here, performing
*writes*) does the work with the policy off, so a defect in it is a cross-tenant write with nothing
behind it.

**Rejected: a new tenant-moving context manager in `src/prope/db/session.py`.** A general seam built
for one caller is a seam a second caller finds, and the second caller will be a list endpoint that
wants to read two workspaces. This uses the constant that is already public and adds no API.

**So the deviation is declared and then fixed in place.** `src/prope/db/session.py`'s module docstring
gains one paragraph naming `prope.access_control.tombstone` as the **only** module in Prope that moves
the marker, saying why (an account-scoped operation in a tenant-scoped schema), and saying that
`tests/architecture/test_tenant_marker_movers.py` asserts the list is exactly that one file. A second
mover is a failing test, not a review comment — which is the same move ADR-0042 made for the definer
set and ADR-0045 for `GLOBAL_TABLES`.

**Reversibility: costly.** Not because the code is hard to change, but because the alternative shapes
are all worse and rediscovering that costs the same analysis again. The architecture test is what
makes the choice visible.

## D-113 — the tombstone refuses an active membership and refuses a second run

**Chosen.** Two pre-conditions, both checked inside the transaction before anything is written, both
raising a named refusal:

- **`ActiveMembershipRefused`** if any `workspace_member` row for the person is `active`. A-151 states
  the pre-condition and gives the reason: *"each removal writes its own `member_removed` event in its
  own workspace, which is the trail of departure. The tombstone is the account-level act that follows,
  and refusing it while a membership is active keeps the two facts separately recorded rather than
  collapsed into one ambiguous event."*
- **`AlreadyTombstoned`** if `status` is already `tombstoned`. ADR-0054 §8 makes the operation
  one-way; running it twice would append a **second** `user_tombstoned` event per workspace into the
  one table nothing can be removed from, and would overwrite `tombstoned_at` and `tombstoned_by` with
  a later, wrong pair.

**Rejected: making the second run a silent no-op.** Idempotence is the reflex and it is wrong here.
A tombstone request against an already-tombstoned account is a caller that thinks it is doing
something; answering *"fine"* hides a duplicate administrative act on the one operation in the product
that cannot be undone.

**The composition with A-117, worked out rather than assumed.** A person cannot be removed from a
workspace while they are its last Admin (plan 07-04), so they cannot reach *no active membership*, so
they cannot be tombstoned — and the deferred constraint trigger plan 07-04 installed on
`role_binding` is therefore never met by this command with an Adminless outcome. Plan 07-04's SUMMARY
records this chain; this plan **asserts** it: tombstoning the sole Admin of a workspace is refused,
and the refusal comes from the membership pre-condition rather than from the trigger.

**Reversibility: cheap.**

## D-114 — `tombstone_user` has no `reason` parameter, at any layer

**Chosen.** The function signature is
`tombstone_user(sessionmaker, *, user_id, tombstoned_by) -> tuple[str, ...]` (the workspaces an event
was written into). There is no `reason`, no `note`, no `details`, and no `**kwargs`.

ADR-0054 §7 is unusually direct about why: `requires_reason` is how this project normally makes a rare
action accountable, and here *"it would be the exact mechanism by which the erased name walks back into
the append-only table a human sentence at a time. `'John Smith left the company'` is a free-text reason
nobody would flag in review, written into the one table from which nothing can ever be removed."*

**Rejected: accepting a reason and dropping it.** A parameter that is accepted and ignored is a
parameter somebody wires through, and Phase 8's route would have a field to put on a form. Having
nowhere to put it is the control. Phase 4's registry already seeds `user_tombstoned` with
`requires_reason = false` and empty `detail_keys`, so `append()` would refuse a reason anyway — but
relying on that means the refusal happens at the audit table rather than at the API, which is one
layer too late to stop the field existing in the UI.

The accountability that `requires_reason` normally supplies comes from `tombstoned_by`, which is an id.

**Reversibility: cheap** in code, **one-way in effect** — a reason accepted once is in the trail
forever.
</objective>

### `src/prope/access_control/tombstone.py`

`async def tombstone_user(sessionmaker, *, user_id: str, tombstoned_by: str) -> tuple[str, ...]`,
returning the workspace ids an event was written into. **No `reason` parameter** (D-114), and the
docstring says so in ADR-0054 §7's own words.

The module docstring is where ADR-0054 lives in the source tree. It must carry, at length:

- **What erasure means here**, quoted: an unresolvable identifier, which is a claim about re-linking.
  Inside a running Prope no path leads from a tombstoned `actor_id` back to a name — the `user` row
  holds none, no registered action's `details` allow-list includes one (A-124), and no log line or
  metric label carries one (A-046, ADR-0030).
- **The path that survives is the backup.** ADR-0036 keeps nightly dumps for 30 days, so the name
  persists in every dump taken before the tombstone, erasure is complete only after the retention
  window passes, and the recovery runbook re-applies every tombstone recorded after the dump's
  timestamp — read from the `user_tombstoned` events that survive in the restored history because
  history is never deleted. **This is a residual, not a gap**, and the docstring is where the person
  who runs a restore will actually look.
- **The history trail is not touched, at all** — no row deleted, no `actor_id` nulled, blanked,
  re-pointed or anonymised. `prope_app` could not do so if it tried (ADR-0025), and that privilege is
  what makes this claim checkable rather than promised.
- **D-112's transaction shape**, and the sentence that this is the only account-scoped operation in a
  tenant-scoped schema.

The body, in order:

1. Open a plain session (`sessionmaker()`) and one `session.begin()`. **Not `workspace_transaction`**
   — there is no single workspace, and the first read is account-level.
2. Read the person: `SELECT status, tombstoned_at FROM access."user" WHERE id = :id FOR UPDATE`. The
   row lock is load-bearing and gets a `#:` note: two concurrent tombstones would otherwise both pass
   the pre-condition and both append events.
3. `AlreadyTombstoned` if `status = 'tombstoned'`. Not-found handling: if the row does not exist,
   raise the same not-found-shaped refusal a route will render — or, if no such refusal exists yet in
   `domain.py`, raise `LookupError` with the id and record in the SUMMARY that Phase 8 owns the
   mapping. Do not invent an HTTP status here.
4. Read every `workspace_member` row for the person, **of any status**, with the marker unset. Under
   RLS that returns **zero rows** — which is the trap in this whole command, and the reason it must be
   written down at the statement. `workspace_member` carries `workspace_id` and is policied, so the
   list of workspaces cannot be read from it before a workspace is known. **Resolve it the only way
   that is available without a definer function**: `access.list_workspaces()` returns every workspace
   id (it is one of the four sanctioned functions and plan 07-01 shipped its Python caller), and the
   command then visits each, setting the marker, and reads that workspace's `workspace_member` row for
   this person. Write out at the loop that this is O(workspaces) per tombstone, that the operation is
   rare and administrative, and that the alternative — a fifth definer function returning the person's
   memberships — is forbidden and would be a row-returning bypass, which ADR-0051 rules out by shape
   as well as by count.
5. **Pass one, per workspace with a membership row of any status**, with `SET_TENANT` issued for that
   workspace first:
   - `ActiveMembershipRefused` if that row's `status = 'active'` — collected across all workspaces and
     raised **once**, naming all of them, so an admin fixing it learns the whole list rather than one
     at a time.
6. **Pass two, per workspace** (only reached if pass one refused nothing), marker set per workspace:
   - `DELETE FROM access.role_binding WHERE workspace_id = :ws AND user_id = :u`
   - `DELETE FROM access.prompt_grant WHERE workspace_id = :ws AND grantee_user_id = :u`
   - `DELETE FROM access.session WHERE workspace_id = :ws AND user_id = :u`
   - `UPDATE access.workspace_member SET status = 'removed'` where it is not already — **retained,
     never deleted**
   - `append(session, user_tombstoned)` with `target_type = "user"`, `target_id = user_id`,
     `actor_id = tombstoned_by`, `workspace_id = ws`, `scope_prompt_id = None`, `details = {}`,
     `reason = None`
   - **`access.api_key` is not touched.** Put the sentence at the place a reader would expect a fifth
     statement: a key belongs to the workspace, not to its creator, and revoking one on an HR event
     would break a consuming product's traffic silently.
7. **The account row, last, and with no marker needed**:
   `UPDATE access."user" SET email = NULL, display_name = NULL, password_hash = NULL,
   must_change_password = false, status = 'tombstoned', tombstoned_at = now(), tombstoned_by = :by
   WHERE id = :u`. `last_login_at` is deliberately **unchanged** — A-151: a timestamp is not
   identifying, and zeroing it would destroy the only signal that an account was ever used. Note that
   `ck_user_tombstone_is_complete` (plan 07-01) refuses this statement at the engine if any of the
   three columns is left non-NULL, so a partial version of this `UPDATE` is a failure rather than a
   silent half-tombstone.
8. Commit by leaving the `session.begin()` block; return the workspace ids.

**Every statement is a module-level `text()` constant with bound parameters.** No f-strings, no
`.format`, no concatenation — `tests/architecture/test_no_sql_interpolation.py` walks this file and
