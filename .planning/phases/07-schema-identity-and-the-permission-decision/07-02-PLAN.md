## D-104 — `may()` is visibility AND permission, and each half is its own union

**Chosen.**

```
allow  =  visible(actor, subject)  AND  permitted(action, actor, subject, facts)

visible    = the actor owns the subject
           | a prompt_grant names the actor on this subject
           | the subject's access_level is `workspace`
           | the subject is not a prompt              (a workspace, a key, a price row)

permitted  = the action is in the union of the actor's roles' matrix rows
           | the actor owns the subject and the action is in OWNER_ACTIONS
           | a grant names the actor and the action is in GRANT_ACTIONS[level]
```

Both halves are unions. Nothing subtracts inside either, and the conjunction is not a subtraction —
it is ADR-0020's own split made explicit: *"Access-control supplies the role bindings, the grants, and
the matrix … Neither side can answer alone."* The subject's attributes are the caller's half of the
answer, and `access_level` is the field that carries it.

**Rejected: a role-granted action is an unconditional allow.** This is the literal reading of A-111 —
*"allows the action if **any** of the actor's workspace role bindings grants it"* — and it destroys the
product's central privacy claim on contact with the seeded matrix. Viewer, Owner and Reviewer all hold
`prompt.read` in A-007's placeholder, so under an unconditional reading every member of a workspace
reads every prompt in it, and BR-01 — *prompts are private by default*, the top adoption barrier in
the survey and a non-negotiable — is implemented nowhere. It would also make AC-9 inexpressible:
*"an actor whose visibility comes entirely from grants … returns mode=ids listing exactly the granted
and owned prompts"* has no meaning if a role already granted everything.

**The reconciliation is A-111's own closing paragraph**, and it is quoted at the code:
*"BR-01's private-by-default is a **starting state** — a prompt nobody has been granted is invisible —
not a rule that removes a permission somebody else added."* Invisibility is not subtraction. A
subject nobody made visible was never in the set.

**Rejected: deny-override grants**, for A-111's and ADR-0020's stated reason — the answer would depend
on evaluation order, and *"why can't this person do this"* becomes a search instead of a lookup.

**Reversibility: moderate.** The shape is one function and every caller sees a `bool`, so changing it
is local — but every existing grant and binding would have to be re-read under new semantics, which is
exactly why A-111 rates itself `moderate` too.

## D-105 — the decision is a pure function over already-read facts; the read is separate

**Chosen.** `permissions.py` has two functions and one value object:

```python
@dataclass(frozen=True, slots=True)
class PermissionFacts:
    role_actions: frozenset[str]
    grant_level: GrantLevel | None
    is_active_member: bool

def decide(*, action: str, actor: Actor, subject: Subject, facts: PermissionFacts) -> Decision
async def may(session: AsyncSession, actor: Actor, action: str, subject: Subject) -> bool
```

`decide` touches no I/O. `may` reads the facts in **one** statement and calls `decide`.

Two things this buys, and the second is why it is a decision rather than a style:

1. **AC-03's test lands at the path the lock names.** `docs/modules/access-control.lock.yml` gives
   AC-3's `test_ref` as `tests/unit/test_effective_permission_is_a_union` — and every existing file
   under `tests/unit/` in this repository has no container in its fixture graph, while a union over
   role bindings self-evidently needs rows. Splitting the decision out makes the lock's path and the
   repository's convention the same choice instead of opposing ones. The read half is proven
   separately, against the live database, in `tests/integration/test_permission_matrix_is_rows.py`.
2. **The union becomes visible as a union.** `decide`'s body is three `or`ed predicates under one
   `and`; there is no evaluation order to get wrong and no branch in which a later rule can undo an
   earlier one. That is A-111's guarantee expressed as a shape rather than as a comment.

**Rejected: one function that reads and decides.** Shorter, and its test is a database test that
proves the union and the query at once — so a defect in either is attributed to both, and the lock's
own `test_plan.unit` line (*"The union rule across role bindings and grants"*) has nowhere to live.

**Reversibility: cheap.**

## D-106 — the vocabulary check runs first, returns a bool, and never raises

**Chosen.** `may()` checks `action in ACTIONS` **before the tenancy comparison and before any
statement is issued**, increments `prope_access_control_unknown_action_total`, logs the action, and
returns `False`.

**Order matters and it is asserted.** If the check ran after the read, an unknown action would still
deny — and it would also issue a query, so the counter that is supposed to say *a caller is sending an
action the vocabulary does not hold* would come with a database round trip per bad call. The test
proves the ordering by passing a session object that **raises if it is used at all**, which is the
only way to assert *no query was issued* rather than *the query returned nothing*.

**Two failure modes that look alike and must not be conflated**, written at the function:

- An **unknown action** is a deny, is counted, and **raises nothing** (AC-04, A-115). The safe failure
  is also a silent one, which is why the counter exists and why `AccessControlUnknownAction` pages on
  any non-zero value.
- An **unevaluable check** — the database is unreachable, the statement fails — **raises**, and
  INT-001 says *"raises, and no caller catches it … a caller that wraps this call in a `try` has
  introduced the bug this seam is shaped to make impossible."* `prope_access_control_check_error_total`
  is incremented on the way out and the exception is re-raised unchanged.

`may()` returns a plain `bool`, per INT-001's *"Returns: allow or deny. Nothing else — no reason
string, no partial answer, no list."* `decide()` returns a `Decision(allowed, ground)` where `ground`
is a closed token used for the **log line** and never for a metric label — the lock requires that
*"a denied check logs the action and the subject id, because 'why can't this person do this' is the
support question this module will be asked most, and it cannot be answered from a counter."*

**Reversibility: cheap.**

## D-107 — a `consumer_key` actor is denied by `may()`, and the denial is counted

**Chosen.** `may()` denies any actor whose type is `consumer_key`, on ground `actor_is_a_key`.

INT-001's actor is `{type: user | consumer_key, id, workspace_id}`, so the type exists in the
contract — and **no caller passes one.** The four declared consumers of INT-001 are prompt-registry,
release-control, evaluation and provider-access, all of which act for a person; the gateway, which is
the only caller holding a key, uses INT-003 and INT-004 instead, and a key's authority is its
`scope_model_names` and nothing else (A-081). A key holds no role binding and no membership, so the
matrix read would return an empty set and the honest answer would be deny anyway — this makes it deny
for a **stated** reason instead of by arithmetic on an empty set.

**Rejected: raising on a key actor.** Under INT-001's raise-is-a-5xx rule that turns a caller's
programming mistake into an outage of the caller's endpoint. Deny-and-count is the fail-closed
direction and it is visible in `check_total{result="deny"}`.

**Reversibility: cheap.** If a key actor ever needs `may()`, this is one branch and one ground.
</objective>

### `src/prope/access_control/permissions.py` — the pure half

`Decision` is a frozen slotted dataclass with two fields: `allowed: bool` and `ground: str`. `ground`
is drawn from a module-level closed set of tokens fixed in source — `role_binding`, `ownership`,
`prompt_grant`, `unknown_action`, `not_a_member`, `foreign_workspace`, `actor_is_a_key`,
`not_visible`, `no_permission` — declared as constants so a tenth cannot appear by accident, in the
discipline `enqueue._classify_publish_failure` models. Say at the class that `ground` exists for the
**log line and for a human**, that INT-001's return is a bare `allow | deny`, and that `may()` is what
throws the ground away — so no caller can branch on it and nothing downstream can grow a dependency on
a reason string.

`decide(*, action, actor, subject, facts) -> Decision`, in this order, with a `#:` comment naming the
authority for each step:

1. **`action not in ACTIONS`** → `Decision(False, UNKNOWN_ACTION)`. First, before anything else, so
   the caller who typed the action wrong learns nothing about the subject (A-115).
2. **`actor.type is not ActorType.USER`** → `Decision(False, ACTOR_IS_A_KEY)` (D-107).
3. **`actor.workspace_id != subject.workspace_id`** → `Decision(False, FOREIGN_WORKSPACE)`. RLS makes
   the read return nothing anyway; this makes the answer a stated deny rather than an empty-set
   accident, and it is the branch a unit test can reach without a database.
4. **`not facts.is_active_member`** → `Decision(False, NOT_A_MEMBER)`. ADR-0022's *member removal is
   effective at once* is this line: a person removed while holding an open session is refused on their
   next action, not at expiry. The lock's own failure-mode row describes exactly this and calls the
   behaviour correct.
5. `owns = subject.owner_id is not None and subject.owner_id == actor.id`
6. `visible = owns or facts.grant_level is not None or subject.access_level is AccessLevel.WORKSPACE
   or subject.type is not SubjectType.PROMPT` → if false, `Decision(False, NOT_VISIBLE)`. Comment the
   last disjunct: a workspace, an API key or a price row has no per-subject visibility model — the
   membership check at step 4 is the whole of it — and `access_level` is a prompt-registry column
   (**OQ-043**).
7. `permitted = action in facts.role_actions | (owns and action in OWNER_ACTIONS) | (grant and action
   in GRANT_ACTIONS[level])` — written as three named booleans `or`ed together, each on its own line
   with the ground it would carry, so the union is legible as a union and the ground of an allow is
   whichever source produced it. If none, `Decision(False, NO_PERMISSION)`.
8. Otherwise `Decision(True, <the winning ground>)`.

The module docstring carries D-104's argument at length — this is where it lives in the source tree,
and A-111's closing paragraph is quoted in it verbatim, because a reader who has just read *"allows
the action if any of the actor's workspace role bindings grants it"* will otherwise read step 6 as the
subtraction A-111 forbids.

**Nothing in this file imports another module's package**, and the docstring says so and says why:
ADR-0020's forbidden edge is the reason this module's dependency list has one entry, and the shape
that keeps it there is `owner_id` and `access_level` arriving as parameters. A helpful refactor that
looked one of them up is exactly what the contract test in Phase 8 exists to catch.

### `may()` — the read half

`async def may(session: AsyncSession, actor: Actor, action: str, subject: Subject) -> bool`.

**It takes a session and opens no transaction.** The caller has already opened one with
`workspace_transaction` — it has to have, because it read the subject to get `owner_id` and
`access_level` — so this function runs inside it, on the caller's connection, exactly as
property-history does (ADR-0023). Say that at the signature and say the consequence: a raise here
leaves the caller's transaction to unwind, and there is nothing here to commit.

Order:

1. Vocabulary check and the key-actor check, from `decide`'s first two steps, **before the read**
   (D-106). Reached by calling `decide` with a sentinel `PermissionFacts` — no. Do it explicitly here
   with the same two constants, and add a comment saying the duplication is deliberate: `decide` must
   stay total over any facts it is given for the unit test to mean anything, and `may` must not query
   before it knows the action is real. Two lines, one reason, written down.
2. **One statement** producing all three facts, as a `text()` constant `READ_PERMISSION_FACTS` with
   three named parameters (`workspace_id`, `user_id`, `subject_id`):
   - the actor's active membership, as a boolean
   - the union of `role_permission.action` over the actor's `role_binding` rows, as an array
   - the `prompt_grant.level` for `(workspace_id, subject_id, user_id)`, or NULL
   One round trip, because the performance row budgets `may()` at p95 < 5 ms for exactly the shape
   *"actor holding 2 role bindings, subject with a grant"* — three round trips would spend that budget
   on latency alone. Write the budget at the constant.
   The statement runs **under the tenant policy**: `role_binding`, `workspace_member` and
   `prompt_grant` all carry `workspace_id` and all are policied, so a caller who somehow reached here
   without a tenant context gets zero rows and therefore a deny. Say that — it is ADR-0035's inversion
   doing this module's fail-closed work for free.
3. `decide(...)`, then the observability, then `return decision.allowed`:
   - `check_duration_seconds.labels(action=..., result=...)` around the whole call
   - `check_total.labels(action=..., result="allow" | "deny")` exactly once
   - on a **deny**, one `structlog` line at `info` carrying `action`, `subject_type`, `subject_id`,
     `result`, `ground`, `role_bindings_count` and `workspace_id` — the lock's log-field list — and
     **no email, no display name, no session id**
   - on an exception from the read: `check_error_total.inc()` and **re-raise unchanged**, in a
     `try/except/raise` with no `return` anywhere inside it. Comment that this is the one branch where
     a `return False` would look like the safe thing and would be the bug: a caller that received
     `False` from an unreachable database could not tell a refusal from an outage, and INT-030 gates
     `/readyz` on precisely that distinction.
4. **`may()` holds no state between calls and exposes nothing a caller could cache** — no
   `functools.lru_cache`, no module-level dict, no returned handle. A-114 and ADR-0022, quoted at the
   function, with the reason: a stale answer here is a **revoked actor**, not a late pointer.
