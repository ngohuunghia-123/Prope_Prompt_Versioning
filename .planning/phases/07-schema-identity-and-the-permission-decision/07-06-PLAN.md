## D-115 — the four-and-only-four assertion is written as *sanctioned minus not-yet-built*, and stays an equality

**Chosen.**

```python
SANCTIONED = (
    "access.list_workspaces",
    "access.lookup_api_key",
    "access.lookup_session",
    "evaluation.claim_next_run",
)

#: THIS LIST IS A PER-PHASE CONSTANT, NOT A PERMANENT FACT.
NOT_YET_BUILT = ("evaluation.claim_next_run",)

EXPECTED = tuple(name for name in SANCTIONED if name not in NOT_YET_BUILT)
```

and the test asserts `observed == EXPECTED` — a tuple equality over a sorted list read from `pg_proc`.

**The problem this solves, stated once.** `.claude/CLAUDE.md` says *"a test asserts the set is exactly
these four"*. Three of the four land in this phase; the fourth, `evaluation.claim_next_run()`, belongs
to the `evaluation` schema, which `EXPECTED_ABSENT_SCHEMAS` still declares absent and which ADR-0049
places in **Phase 16**. A test written literally against four names fails for nine phases on a true
statement, and the repairs that make it pass are all worse than the problem:
`observed <= SANCTIONED` passes when every one of them has been **deleted** — the exact state in which
the authentication bootstrap is broken and no test says so — and `len(observed) <= 4` passes for any
four functions, including four somebody added.

**The shape is borrowed rather than invented.** `EXPECTED_ABSENT_SCHEMAS` in
`tests/architecture/test_tenant_coverage.py` is the same problem solved the same way, down to the
comment: *"THIS LIST IS A PER-PHASE CONSTANT, NOT A PERMANENT FACT … the phase that creates one owns
removing it here, in the same change."* Phase 16 deletes one line from `NOT_YET_BUILT`, in the change
that creates the function, or inherits a red test it did not write.

**Rejected: creating `evaluation.claim_next_run()` early so the count is four.** It puts an
`evaluation`-schema object in access-control's migration, creates a schema declared absent, and leaves
a function with no caller for nine phases to drift from the caller that eventually arrives.

**Rejected: skipping the assertion until Phase 16.** The additions this control exists to catch happen
in Phases 7 through 15 — nine migrations, each with a locally reasonable reason to want one.

**The wording conflict is raised, not resolved.** `.claude/CLAUDE.md` and
`docs/modules/access-control.lock.yml` T-003 both say *exactly four*; this ships *exactly the
sanctioned set minus those whose module has not shipped*. That is **OQ-045**, cited in the test module's
docstring.

**Reversibility: cheap on the list** (one line per phase that lands one), **one-way on the count** —
a fifth is never the answer, and the whole value of the assertion is that it is an equality.
</objective>

**The catalogue query.** Walk **every** schema, not the eight declared ones — a definer function
planted in `public` is the same escape hatch and would be invisible to a schema-scoped walk. Exclude
only the schemas PostgreSQL itself owns (`pg_catalog`, `information_schema`, and anything matching
`pg_%`), and say at the exclusion that extensions install definer functions of their own, so the
exclusion is by owner-schema and not by name.

```sql
SELECT n.nspname || '.' || p.proname AS qualified,
       pg_get_userbyid(p.proowner)   AS owner,
       p.proconfig,
       p.prokind
FROM   pg_proc p
JOIN   pg_namespace n ON n.oid = p.pronamespace
WHERE  p.prosecdef
  AND  n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND  n.nspname NOT LIKE 'pg\_%'
ORDER  BY qualified
```

**Test 1 — the equality.** `tuple(observed) == EXPECTED`. The failure message lists **extras and
omissions separately**, in the shape plan 05-04 used for the 31-action registry, because those two
failures mean opposite things: an extra is a fifth escape hatch somebody added, an omission is a
bootstrap function somebody deleted and a product that no longer authenticates.

**Test 2 — ownership.** Every observed function is owned by `prope_migrate`. ADR-0035's owner bypass
is the mechanism the whole escape depends on: a definer function owned by `prope_app` would execute as
the role that is *subject* to the policy and would return zero rows, which is a broken bootstrap that
looks like a security feature.

**Test 3 — the empty `search_path`.** `proconfig` contains an entry whose key is `search_path` and
whose value is empty. Assert on the entry, not on the presence of the string `search_path` anywhere in

misconfiguration the requirement exists to prevent. State at the assertion why it matters: a definer
body runs as the owner, so a caller who can set `search_path` could otherwise shadow `access` with a
schema of their own and have the owner read it.

**Test 4 — `PUBLIC` cannot execute, `prope_app` can.** For each function,
`has_function_privilege('public', <oid>::regprocedure, 'EXECUTE')` is false and
`has_function_privilege('prope_app', …)` is true. Note that PostgreSQL grants `EXECUTE` to `PUBLIC` on
every new function by default, so the `REVOKE` is doing real work and its absence is silent.

**Test 5 — identifiers only, and it is a judgement made mechanical.** ADR-0051's rule is about the
*return shape*. Read each function's return type from `pg_get_function_result` and assert it against a
declared table in the test module mapping each sanctioned name to its exact expected return string —
`TABLE(user_id text, workspace_id text)`, `TABLE(workspace_id text, key_id text, key_hash text,

application, so the hash crosses the boundary and the decision does not.

### `tests/architecture/test_tenant_coverage.py` — a third category, and it is an assertion

The file's own argument is that `GLOBAL_TABLES` exists *"so an exemption is a sentence somebody signed
rather than a silent skip"* — but the implementation `continue`s past an entry, so an entry is still a
skip, just a documented one. That is fine for `history.history_action_registry`, `access."user"` and
`access.role_permission`, which genuinely have no policy. It is **wrong for `access.workspace`**, which
is the tenancy root, **has** a policy, and is only in the map because its policy is on `id` rather than
on a `workspace_id` column.

Add:

```python
#: Fully-qualified table name -> the column its tenant policy is written against.
#: NOT an exemption. These tables ARE tenant-scoped; they simply do not carry a
#: column called `workspace_id`. An entry here is ASSERTED, not skipped.
POLICIED_ON_ANOTHER_COLUMN: dict[str, str] = {
    "access.workspace": "id",
}
```

and move `access.workspace` out of `GLOBAL_TABLES` (plan 07-01 put it there so the walk stayed green
the moment the schema landed; this is the upgrade that entry was always going to get — say so in a
comment, so the two-step reads as a sequence rather than as a correction).

Change the walk so a table in `POLICIED_ON_ANOTHER_COLUMN` is **not** skipped. It must:

1. have row security enabled, and
2. have at least one policy, and
3. have a policy whose qualifier text references the declared column — read `pg_policies.qual` and
   assert the declared column name appears in it.

Assertion 3 is what makes this a declaration rather than a shrug: a policy on `access.workspace`
written against something other than `id` would satisfy 1 and 2 and isolate nothing.

Add `test_a_policied_on_another_column_entry_is_asserted_not_skipped`, whose job is to prove the
mechanism rather than the data: build the same uncovered-list computation the main walk uses, over a
**synthetic** input in which `access.workspace` is reported with `relrowsecurity = False`, and assert
the computation reports it. Factor the loop body into a small module-level function so both the real
walk and this test can call it — that refactor is the whole of what makes *"failing if the declaration
is removed"* testable, and without it the requirement can only be checked by hand-editing the file.

Also add `test_prompt_grant_is_reached_by_the_walk`: assert `access.prompt_grant` appears in the walk's
table list, carries `workspace_id`, has row security and has a policy. It is redundant with the main
walk **by construction and deliberately not by accident** — ADR-0042 added that column specifically so
the enumeration could see this table, and PITFALLS names it by name. A named test is what a reader
looking for *"is BR-01's grant table actually covered"* will find; the general walk is what would catch
it silently and report *"one of N tables"*.

Update the module docstring: it currently says *"The rule is not 'these tables need a policy'; it is
'every table needs one, and an exemption is an entry in `GLOBAL_TABLES` with a written reason'"*. Add
the third case in the same voice — *and a table whose policy is on a different column is an entry in
`POLICIED_ON_ANOTHER_COLUMN` naming that column, which is asserted rather than excused*.

### `tests/security/test_access_tenant_isolation.py` — provoke the engine

The coverage walk proves a policy **exists**. This proves it **works**, in the posture ORCHESTRATION §3
requires: assert against the live engine by provoking its refusal, with a positive control that proves
the test could have seen a row.

For each of the six policied `access` tables — `workspace`, `session`, `workspace_member`,
`role_binding`, `prompt_grant`, `api_key` — seed one row for workspace A and one for workspace B as
`prope_migrate`, then, on a `prope_app` session inside `workspace_transaction(…, B)`:

- assert the `SELECT` returns **zero** rows for A's row (the refusal), and
- assert it returns **exactly one** for B's row (the control that proves the query, the seed and the
  connection were all working)

Then the write half, which is the one ADR-0040 calls load-bearing and which a read-only test would
miss entirely: inside `workspace_transaction(…, B)`, attempt an `INSERT` stamped `workspace_id = A`
into `prompt_grant` and assert the policy's `WITH CHECK` refuses it at the engine — with the control
that the same `INSERT` stamped `B` succeeds.

And the no-context case, which is ADR-0035's whole inversion: on a plain session with **no**
`app.workspace_id` set, every one of the six returns zero rows — while `prope_migrate` reads both.
Note in the module docstring that `access."user"` and `access.role_permission` are deliberately absent
from this list because they have no policy by decision (ADR-0042's enumeration), and that they are
declared in `GLOBAL_TABLES` with the reason — so a reader who counts six tables in an eight-table
schema finds the answer here.
