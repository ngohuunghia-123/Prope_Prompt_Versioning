<objective>
Ship the membership and role commands, and make **AC-08** true: a workspace always has at least one
Admin, and the last one cannot be removed or demoted.

This is ROADMAP success criterion 3. It is also the phase's most consequential *irreversible* failure:
a workspace that reaches zero Admins is permanently frozen — nobody can add a member, transfer
ownership, rotate a credential, or release anything — and there is no cross-workspace operator surface
to repair it from, because no module has one by construction and A-012 rules out building one. The
refusal is cheap; the recovery does not exist.

## D-110 — A-117 is enforced twice: a command that refuses with a message, and a deferred constraint trigger that refuses at COMMIT

**Chosen.** Both, and each owns something the other cannot do.

**The command owns the refusal a human sees.** `remove_member` and `set_roles` count the workspace's
active Admins inside their own transaction, raise `LastAdminRefused` before writing, increment
`prope_access_control_last_admin_refused_total`, and log the workspace and the actor. A-117 requires a
refusal *"with a message saying so"* and a counter; an engine error cannot produce either without the
application mapping a constraint name back to a sentence, which is the indirection ADR-0053's
catalogue makes worse rather than better.

**The trigger owns the guarantee.** `access.assert_workspace_has_an_admin()` is a
`CONSTRAINT TRIGGER … AFTER DELETE OR UPDATE ON access.role_binding` and
`… AFTER UPDATE ON access.workspace_member`, both `DEFERRABLE INITIALLY DEFERRED`, raising if the
affected workspace has no `role_binding` with `role = 'Admin'` whose member row is `active`. Deferred,
so a legitimate multi-statement change — demote one Admin and promote another in the same transaction
— passes on the state at `COMMIT` rather than on the state mid-statement.

**Why the belt as well as the braces, when `0004` recorded a knowing exception for a cross-table rule
of the same shape.** Three differences, and they all point the same way:

1. **The failure is unrecoverable.** A-055's guard protects against a body row that should not exist;
   this one protects against a tenant that can never be administered again. `0004`'s exception is
   priced against a per-row lookup on *"the highest-volume insert path in the system"*; a membership
   change happens a handful of times per workspace per year.
2. **This project has declined an application-maintained invariant on exactly this shape five times**
   — BR-03's constraint, ADR-0025's privilege, ADR-0027's schema, ADR-0035's policy, ADR-0048's
   trigger — and ORCHESTRATION §3 states the rule as standing: *"the migration carries the guarantee."*
3. **The command is not the only writer for long.** Phase 8 mounts two routes on this rule, Phase 9
   asserts refusal shapes over it, and plan 07-05's tombstone deletes `role_binding` rows on a
   different code path. A guarantee that lives only in one function is a guarantee the second writer
   does not inherit.

**`SECURITY INVOKER`, and this is the trap.** The trigger function must be declared with the
**default** security context. A `SECURITY DEFINER` trigger function would appear in `pg_proc` with
`prosecdef` true and would be a **fifth** privilege-escalating object — failing plan 07-06's exact-set
assertion and violating a project non-negotiable, for no benefit: the invoker is `prope_app` inside a
`workspace_transaction`, so `app.workspace_id` is already set and the policy lets it count its own
workspace's rows. Write `-- SECURITY INVOKER (the default) is load-bearing` at the function.

**Rejected: a `CHECK` constraint.** It cannot see another row, let alone another table.

**Rejected: the trigger alone.** No message, no counter, and A-117 asks for both. The refusal would
reach the SPA as an unmapped `raise_exception` and render as nothing at all under ADR-0053's catalogue.

**Rejected: the command alone.** It is the option `0004` took for A-055 and it is right there and
wrong here, for the three reasons above. `0004`'s own posture is instructive: it made the absence of
the guard *asserted rather than assumed*. Here the guard exists, so what is asserted is that it fires.

**Reversibility: costly.** A landed revision is never edited, and a deferred constraint trigger that
turns out to refuse a legitimate operation is discovered by that operation failing at `COMMIT`. The
mitigation is that both directions are tested — the multi-statement demote-and-promote case is
asserted to **pass**, not only the zero-Admin case to fail.

## D-111 — removing a member ends their sessions in that workspace, in the same transaction

**Chosen.** `remove_member` issues `DELETE FROM access.session WHERE user_id = :user AND workspace_id
= :ws` alongside the status change and the role-binding deletions.

`docs/modules/access-control.lock.yml` `security_requirements` says it in one line —
*"Sessions are server-side rows; sign-out and member removal end them immediately rather than at
expiry (A-108)"* — and ADR-0022 is the whole reason sessions are rows in the first place.

**Rejected: leaving the session and relying on `may()`.** It would be *correct*: plan 07-02's
`is_active_member` check denies every action for a removed member on their very next call, with no TTL.
But it leaves a live authenticated session belonging to somebody who is no longer a member, which is a
state the lock says does not exist, and it makes the removed person's experience *"every button
fails"* rather than *"you are signed out"* — the lock's own failure-mode row calls the mid-task refusal
*"a genuinely bad experience and the correct behaviour"*, and there is no reason to keep the session
alive in order to deliver it.

**Sessions in the person's *other* workspaces are untouched.** The delete is scoped to
`(user_id, workspace_id)`. A person removed from workspace A who is still a member of workspace B keeps
working in B, and that follows from the same sentence: it is *member removal* that ends a session, and
they were removed from one membership.

**Reversibility: cheap.**

## What this plan does not do, so plan 07-05 and Phase 8 know

- **No routes.** `POST/DELETE /api/v1/workspaces/{id}/members` and
  `PUT …/members/{user_id}/roles` are INT-029's and land in Phase 8. These are the commands those
  routes call, and they take their actor as a parameter rather than reading a session.
- **No permission check inside the commands.** `may(actor, "workspace.manage_members", subject)` is
  the *route's* call, at the module's own edge (ADR-0020's *"permission is a local decision with the
  subject passed in"* cuts both ways — a command that checked its own caller's permission would be
  making a decision the caller already made). Say so at each command.
- **No `user_tombstoned` interaction.** Plan 07-05 deletes `role_binding` rows for a departing person,
  and A-151's pre-condition — *"the person must already hold no active membership"* — is what keeps
  that from meeting this trigger. The interaction is analysed in Task 1 and asserted in plan 07-05.

One revision, small, with a docstring longer than its DDL — because what has to be understood here is
not the SQL.

**`access.assert_workspace_has_an_admin()`**, `RETURNS trigger`, `LANGUAGE plpgsql`, **and no
`SECURITY DEFINER` clause of any kind.** Write the comment `-- SECURITY INVOKER (the default) is
load-bearing: a SECURITY DEFINER trigger function would be a FIFTH privilege-escalating object in a
product whose sanctioned set is exactly four, and it would fail the test that asserts it` directly
above the `CREATE FUNCTION`. It is the single most likely thing for a later reader to "fix".

Body: determine the affected workspace from `COALESCE(OLD.workspace_id, NEW.workspace_id)`, then

```sql
IF NOT EXISTS (
    SELECT 1
    FROM   access.role_binding rb
    JOIN   access.workspace_member wm
      ON   wm.workspace_id = rb.workspace_id AND wm.user_id = rb.user_id
    WHERE  rb.workspace_id = affected
      AND  rb.role = 'Admin'
      AND  wm.status = 'active'
) THEN
    RAISE EXCEPTION 'workspace % would be left with no active Admin', affected
      USING ERRCODE = 'raise_exception';
END IF;
RETURN NULL;
```

Four things the docstring must argue, because none of them is visible in the SQL:

1. **It runs under row-level security as the invoker.** `prope_app` inside a `workspace_transaction`
   has `app.workspace_id` set, so the policy permits exactly the rows it needs to count. A
   `SECURITY DEFINER` version would also work and is forbidden. A version invoked with **no** tenant
   context counts zero rows and therefore raises — which is the fail-closed direction and is worth
   naming, because it means a path that forgot `SET LOCAL` cannot silently pass this check either.
2. **`DEFERRABLE INITIALLY DEFERRED`, and the reason is a legitimate operation.** Promoting a new
   Admin and demoting the old one in one transaction passes through an intermediate state that an
   immediate trigger would refuse. Deferring makes the constraint a statement about the transaction's
   *outcome*, which is what A-117 actually says. The consequence: the refusal arrives at `COMMIT`, not
   at the statement, so the application's own pre-check (Task 2) is what produces a message a person
   can read.
3. **Two triggers, not one.** `AFTER DELETE OR UPDATE ON access.role_binding` catches removing or
   demoting; `AFTER UPDATE ON access.workspace_member` catches the other route to the same state —
   flipping the last Admin's membership to `removed` while leaving their binding in place. Both are
   `FOR EACH ROW`. There is no `INSERT` trigger: adding a row can never reduce the count.
4. **`TRUNCATE` does not fire it.** `CONSTRAINT TRIGGER` is row-level, and `TRUNCATE` fires only
   statement-level `TRUNCATE` triggers — so `tests/conftest.py`'s truncate fixture is unaffected. Say
   so; a reader who has just understood point 3 will immediately wonder about the rig.

**And the interaction with plan 07-05's tombstone, analysed here rather than discovered there.**
A-151 deletes every `role_binding` row for a departing person, which is precisely what trigger one
fires on. It cannot leave a workspace Adminless, because A-151's stated **pre-condition** is that the
person *"must already hold no active membership"* — and every route out of an active membership goes
through Task 2's refusal. So the two rules compose: you cannot remove the last Admin, therefore you
cannot tombstone them, therefore the tombstone's deletion never reduces an active Admin count below
one. Write that chain out in the revision docstring, and note that plan 07-05 asserts it directly.

### `src/prope/access_control/domain.py`

`class LastAdminRefused(Exception)` — carrying `workspace_id` and `admin_count` as attributes and a
message naming the workspace. Docstring: this is A-117's refusal, it is raised **before** anything is
written, and it exists so the refusal has a sentence and a counter that the deferred constraint
trigger cannot produce. Note that Phase 8's route maps it to a `409`-shaped `ManagementRefusal` with
its own machine code, and that inventing that code here would put a client-facing vocabulary in a
domain module.

### `src/prope/access_control/membership.py`

Four public callables. Every one of them opens **exactly one** `workspace_transaction`, and every one
takes its `actor_id` as a parameter and performs **no permission check** — the route checks
`workspace.manage_members` at the module's edge (ADR-0020), and a command that re-checked would be a
second decision that can disagree with the first. Say that once, at the top, not four times.

`async def active_admin_count(session, workspace_id) -> int` — one statement, joining `role_binding`
to `workspace_member` on `status = 'active'`, identical in shape to the trigger's `EXISTS`. Put a
`#:` note at the statement saying the two must agree and that the trigger is the authority: if they
ever diverge, the command's answer is the one that is wrong. Also used to set the `admin_count` gauge.

`async def add_member(sessionmaker, *, workspace_id, user_id, added_by, roles)` —
`INSERT … ON CONFLICT (workspace_id, user_id) DO UPDATE SET status = 'active', added_by = …,
added_at = now()`, so re-adding a previously removed person reactivates their retained row rather than
failing on the primary key. Then one `role_binding` insert per role, then `member_added` and one
`role_assigned` per role, all in the same transaction. Comment the upsert: A-151 retains removed
rows, so *insert* is not the only shape this operation can meet, and a plain `INSERT` would make
re-adding a departed colleague an error nobody would predict.

`async def remove_member(sessionmaker, *, workspace_id, user_id, actor_id)`:

1. Read `active_admin_count`; if the target holds an Admin binding and the count is 1, increment
   `last_admin_refused_total`, log at `warning` with `workspace_id`, `user_id` and `admin_count`, and
   raise `LastAdminRefused` — **before any write**.
2. `DELETE FROM access.role_binding WHERE workspace_id = :ws AND user_id = :user`
3. `UPDATE access.workspace_member SET status = 'removed'` — **never a DELETE** (A-151, and
   `prope_app` holds no `DELETE` on that table anyway).
4. `DELETE FROM access.session WHERE user_id = :user AND workspace_id = :ws` (D-111).
5. `append(member_removed)` — and a `role_revoked` per binding removed, if Phase 4's registry treats
   revocation as its own event; read the seed rather than assuming.
6. Set the `admin_count` gauge from the post-change count.

`async def set_roles(sessionmaker, *, workspace_id, user_id, actor_id, roles)` — the assign-or-revoke
route. Compute the diff against the current bindings, apply it, append one `role_assigned` per added
role and one `role_revoked` per removed role, and apply the **same** last-Admin pre-check: if `Admin`
is in the removed set and this is the only active Admin, refuse identically. Note at the function that
this is A-117's *demote* half and that AC-08 names both routes in one sentence — *"removed or their
role revoked by any route"* — so the two refusals must be the same refusal, not two lookalikes.

**The gauge.** `admin_count.labels(workspace_id=…).set(n)` after every successful membership or role
change, and **not** on the refusal path — a refusal leaves the count where it was, and AC-08's
*"admin_count stays 1"* is a statement about the gauge not having moved. Note at the call that
`workspace_id` as a label is a cardinality exception this project otherwise refuses, that it ships
because A-117 requires the gauge and `AccessControlAdminCountZero` pages on it, and that plan 07-01
recorded the same tension at the metric's definition.

### `tests/integration/test_last_admin_cannot_be_removed.py` — the lock's named path

Six assertions, and the third and fourth are the ones that make it AC-08 rather than a unit test with
a database attached.

1. **The removal route.** One workspace created through `create_workspace` (its creator is its only
   Admin). `remove_member` for that creator raises `LastAdminRefused`. Then, read through
   `migrate_engine`: the `workspace_member` row is still `active`, the `role_binding` row still
   exists, and — the clause the ROADMAP names — `prope_access_control_admin_count` for that workspace
   is still `1` and `prope_access_control_last_admin_refused_total` incremented by exactly one.
   Read the counter before and after; note in the test that it answers `None` before its first
   increment.
2. **The demotion route.** `set_roles(..., roles=[])` on the same person raises the **same**
   exception type and increments the **same** counter. AC-08's *"removed or their role revoked by any
   route"* is one sentence and this is the assertion that keeps it one behaviour.
3. **The count, not the person.** Add a second member with the Admin role. `remove_member` for the
   original creator now **succeeds**. Then `remove_member` for the second Admin is refused. This is
   the positive control that proves assertion 1 was not passing because removal is broken in general,
   and it is the assertion that would fail if somebody implemented *the creator cannot be removed*
   instead of *the last Admin cannot be removed*.
4. **The engine, bypassing the command entirely.** As `prope_app`, inside a `workspace_transaction`
   opened by hand, issue `DELETE FROM access.role_binding WHERE workspace_id = … AND role = 'Admin'`
   and assert the **commit** raises. Then read through `migrate_engine` and assert the row survived.
   This is the half that proves D-110's backstop: it never touches
   `prope.access_control.membership`, so it is a statement about the database rather than about the
   application. Include the counterpart: the same `DELETE` in a workspace that has two Admins commits
   fine.
5. **The deferred half.** In one transaction, insert an Admin binding for a second user and delete the
   first user's Admin binding. Assert it **commits**, and that the workspace has exactly one Admin
   afterwards. Without this, a stricter-than-intended trigger would pass every other assertion in this
   file and break the first real hand-over of a workspace.
6. **The other route into the same state.** `UPDATE access.workspace_member SET status = 'removed'`
   for the only Admin, by hand as `prope_app`, and assert the commit raises. This is trigger two,
   which exists because the count is over *active* members and a status flip reduces it without
   touching `role_binding` at all.

Every count and every row read is through `migrate_engine`, the owner role — an absence read under the
tenant policy is indistinguishable from an absence caused by it.
