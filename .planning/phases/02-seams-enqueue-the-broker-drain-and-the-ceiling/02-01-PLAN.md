<objective>
Give call-ledger the broker seam it will live on for the next 22 phases, proved end to end on the
thinnest real path: one call record handed to `enqueue()` in `app`, published with a confirm, consumed
by the drain, grouped by `workspace_id`, and committed to `ledger.call_record` through the Phase 1
writer.

Purpose: everything else in Phase 2 is expansion off this slice. The queue's declared arguments are a
one-way decision (RabbitMQ refuses to redeclare a queue with different arguments), so the declaration
has to be right in the phase that makes it, and asserted in the same phase it is made.

**On this plan's size — stated rather than buried.** Fifteen files and an 88,000-token estimate is the
largest slice in the phase, and both numbers are honest consequences of what a tracer is: it touches one
file per layer because its whole value is proving the layers connect, and splitting it by layer would
produce exactly the horizontal decomposition tracer-first exists to avoid. Two things follow. First,
the estimate is **uncalibrated** — `estimate-calibration` reports `sample_count: 0` for this project, so
the calibration factor is 1.0 and `tokens` equals `raw_tokens` by construction rather than by agreement
with any measured run; `confidence: low` is derived from that sample count, not self-rated. Second, most
of the fifteen files are small and single-purpose (`__init__.py` files, `topology.py`'s constants,
`envelope.py`'s one model) — the bulk of the estimate is Task 2's `drain.py` and its live-broker test.
If Task 2 overruns, split it at its own boundary — publish path in one plan, drain in another, both
still vertical — rather than reverting to layer-shaped plans.

Output: `aio-pika` pinned, a real RabbitMQ testcontainer beside the Postgres one, the single topology
definition both processes call, the publish path with its three-branch confirm classification, the
windowed drain with per-group transactions and per-group acks, and the tests that prove all of it
against a live broker.

**Stated Phase 2 gap, per D-21 and D-16 — this plan creates it deliberately and does not hide it.**
On a failed or nacked confirm, and on a full handoff buffer, `enqueue()` counts and drops. There is no
direct-write fallback in this phase (CL-01, Phase 3) and no idempotent upsert on `call_id` (CL-02,
Phase 3). `/readyz` ships its final semantics — the database alone — so for one phase there is a
window where the broker is down, readiness is green, and records genuinely are lost.
`prope_call_ledger_metadata_dropped_total` carries the lock file's `must stay 0` note and **will not
stay 0 in Phase 2**; CL-01 and CL-02 are what return it to zero. That is written at the counter, in
the plan, and in the SUMMARY.

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Queue type — classic durable, or quorum</name>
  <reversibility rating="one-way">RabbitMQ refuses to redeclare an existing queue with a different type or different arguments; changing this after any environment has run means deleting a queue with messages in it.</reversibility>
  <decision>Declare `prope.call_record` as a classic durable queue, or as a quorum queue (`x-queue-type: quorum`).</decision>
  <context>
This is the one Phase 2 decision RESEARCH surfaced that `02-CONTEXT.md` could not have anticipated, so
it is not covered by an existing D-NN. A-149 requires that overflow **dead-letters rather than drops**.
RabbitMQ's own documentation states that quorum queues *"do not support `reject-publish-dlx`
configurations"* — and `reject-publish-dlx` is the single overflow mode that both dead-letters the
overflowing message and `basic.nack`s the publisher. That nack is precisely the signal D-21 counts and
that ADR-0041's Phase 3 direct-write fallback consumes.

The undo cost is the reason this is a checkpoint rather than a planner call: a queue type and its
arguments cannot be changed in place. In any environment that has already run, changing this means
deleting the queue — with whatever is sitting in it — and redeclaring.
  </context>
  <options>
    <option id="classic-durable">
      <name>Classic durable queue (RESEARCH's recommendation)</name>
      <pros>The only shape that satisfies A-149's "overflow dead-letters rather than drops" AND nacks the publisher, so ADR-0041's Phase 3 fallback fires on overflow. Classic is RabbitMQ 4.x's default queue type. No Raft overhead, which buys nothing at the single node ADR-0033 fixes. Classic mirroring was removed in 4.0, so "classic" no longer implies "mirrored" and carries no deprecation smell.</pros>
      <cons>No `x-delivery-limit`, so poison-message dead-lettering becomes the drain's job rather than the broker's. That work is planned (Task 3) but it is code this project now owns and tests.</cons>
    </option>
    <option id="quorum">
      <name>Quorum queue</name>
      <pros>`x-delivery-limit` defaults to 20 from RabbitMQ 4.0, so poison-message dead-lettering is free and the drain's failure classification gets simpler. At-least-once dead-lettering is built in.</pros>
      <cons>Cannot use `reject-publish-dlx` at all. The only available overflow mode is `drop-head`, which dead-letters the OLDEST record and never nacks the publisher — so ADR-0041's fallback never fires on overflow, and A-149's guarantee is met only in the letter. Pays Raft replication cost for a single-node host.</cons>
    </option>
  </options>
  <resume-signal>Select: classic-durable, or quorum</resume-signal>

`src/prope/call_ledger/drain.py` — D-15's window and ADR-0040's grouping. `set_qos(prefetch_count=N)`,
`declare_topology`, then an async queue iterator with `no_ack=False`. Resolve the CONTEXT discretion
item on the numbers with the argument D-15 demands, in a `#:` comment: sustained throughput is
approximately N divided by the sum of the window time and the per-window write time, and batching adds
at most the window time to a record's lag. At 50 rps the window time dominates and N is irrelevant — a
250 ms window holds about twelve messages, so steady-state lag is the window plus the write, far inside
the 2 s target. N matters only during a backlog, where the window fills instantly and throughput is N
divided by write time; clearing 500 records per second against a 250 ms floor needs N of at least 125
before write time is counted at all, so `WINDOW_SIZE = 500` gives roughly four times headroom and
clears the 3,000-message backlog target in about six windows. `WINDOW_MS = 250`. Prefetch equals
`WINDOW_SIZE`, and the comment must record Pitfall 6 — RabbitMQ applies prefetch per consumer, not per
channel, and a prefetch of 0 means infinite, so the memory bound is N multiplied by envelope size and
holds only for a single consumer. Collect a window on size-or-time, whichever comes first; group by
`workspace_id`; and for each group open one `workspace_transaction`, call
`write_records(session, drafts, retention_window=...)`, and ack that group's delivery tags **after that
group's transaction has committed**. Write out in the docstring why the ack is per group and not per
window: the window is N transactions, one per distinct workspace, and if group three fails after
groups one and two have committed, acking the window would either ack failed work or redeliver
committed work. Do not use the cumulative `multiple=True` form; say why at the call site. The retention
window arrives through a keyword-only injected async resolver in the `ChunkObserver` idiom —
`retention_for: Callable[[str], Awaitable[timedelta]]` — defaulting to a module-level function that
returns `writer.DEFAULT_RETENTION_WINDOW`. That keeps `drain.py` a pure function of its arguments and
keeps `write_records` free of a settings query (D-11); plan 02-02 supplies the real per-workspace
resolver and plan 02-03 wires it in `worker.py`. The drain takes a `stopping: asyncio.Event` and
returns cleanly when it is set.

**The resolver takes exactly one positional argument, the `workspace_id`, and the docstring must say so
in those words.** The drain has no sessionmaker to hand it and must not acquire one — it calls
`await retention_for(workspace_id)` and nothing else. Plan 02-02's real reader is
`read_retention_window(sessionmaker, workspace_id)`, a two-argument function, so it is **not** directly
assignable here: plan 02-03 binds the sessionmaker with `functools.partial` before passing it in.
Record that at the parameter, naming `functools.partial` explicitly, because passing the bare
two-argument function type-checks under a loose annotation and then raises `TypeError` on the first
workspace group at runtime — inside a consumer, on the path whose whole purpose is not losing records.
