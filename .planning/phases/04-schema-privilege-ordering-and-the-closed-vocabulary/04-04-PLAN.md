One file. It asserts the rule the lock file states twice and that nothing else in this phase touches.

**The docstring** names what makes this module's A-046 position sharper than any other module's: the
lock forbids logging **two columns this module writes**, one of which — `reason` — is user-authored free
text in Vietnamese that may quote whatever the author was looking at, and the other of which —
`details` — is the one column in Prope with no fixed shape, written by five modules. Both are
allow-listed *into the table* (A-124) and neither is allow-listed *into a log line*. Second paragraph:
the technique and why it is the whole record rather than one field — a per-field assertion tests the
field somebody thought of, and the leak that matters is the field nobody thought of. Third paragraph:
**this file is the first thing in the project that reads `LOGGABLE_FIELDS`**, and what that does and
does not buy — exercised paths only, and the AST gate that would cover unexercised ones is routed to
Phase 6 with AC-8 (Task 1's adoption).

Two module-level markers, distinct and distinctive, in `test_publish_confirm_failures.py`'s style —
something no other string in the suite could contain, e.g. `REASON_MARKER =
"zzmarkerzz-reason-4ba17c"` and `DETAIL_MARKER = "zzmarkerzz-detail-9f21ab"`. A helper
`_every_metric_label_value()` copied in shape from the analog: every label value currently in the
default `REGISTRY`, across every metric, collected wholesale.

Four tests.

1. **`test_a_marker_in_reason_and_in_details_survives_a_successful_append_and_reaches_nothing`** —
   inside `structlog.testing.capture_logs()`, write an event through `record_event` on a
   `workspace_transaction`, with `action = 'revision_released'`, `target_type = 'revision'`,

   `reason = REASON_MARKER`. **Two vacuity guards before the loop, exactly as the analog carries them**:
   assert the row actually landed (read back through `migrate_engine`) — *the append must actually have
   happened, or this proves nothing* — and assert `captured` is non-empty — *a successful append must
   log SOMETHING, or the assertion is vacuous*. Then, for every captured record, `repr` it whole and
   assert neither marker appears; and for every value from `_every_metric_label_value()`, assert neither
   marker appears. Add the third assertion that makes the row half meaningful: read the row back and
   assert both markers **are** in the database — the rule is *stored but never logged*, and a test that
   only proved absence from the log would also pass against a module that dropped the values entirely.
2. **`test_a_marker_in_a_rejected_appends_details_reaches_nothing_and_the_key_name_does`** — the refusal

   rejected append logs the action and the offending key name"* and a test that asserted only the
   absence would pass against a module that logged nothing at all.
3. **`test_a_marker_in_reason_reaches_nothing_on_the_refusal_path`** — the same shape with

   refusal at check one has issued no SQL, and a naive implementation that logged the whole draft would
   leak there and nowhere else.
4. **`test_every_logged_key_is_in_the_allow_list`** — capture the records from both a successful append
