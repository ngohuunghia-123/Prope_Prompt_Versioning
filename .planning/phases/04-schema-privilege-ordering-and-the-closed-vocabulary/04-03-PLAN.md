<objective>
Prove the phase's second success criterion — **two events written in one transaction have a stable
order on every run, including when their timestamps are identical** — and close the one hole the
column definition that provides it leaves open.

The guarantee itself shipped in plan 04-01: `seq bigint GENERATED ALWAYS AS IDENTITY (CACHE 1)`. What
is left is threefold, and only the first is what a reader of PH-04 expects.

**One: the ordering, asserted against the case it exists for.** A-076's approve-and-release is one
request writing two rows in one transaction, and a break-glass release writes a release event and opens
a review task in the same breath. Sorted by timestamp those pairs appear in an arbitrary order on the
one screen whose job is to show the sequence of decisions — *roughly half the time, for exactly the
two-event cases that matter most*, as the lock's own failure-mode row puts it. The test therefore writes
both events with a **byte-identical** `occurred_at` and asserts `seq` orders them, with a control
proving the timestamps really are identical: a test using `datetime.now(UTC)` twice would occasionally
produce two different instants and would then be asserting the tiebreak it meant to remove.

**Two: the hole `GENERATED ALWAYS` leaves, which CONTEXT's D-53 does not cover.** PostgreSQL documents
an escape hatch: *"For an identity column defined as `GENERATED ALWAYS`, it is an error to insert an
explicit value (other than `DEFAULT`) without specifying either `OVERRIDING SYSTEM VALUE` or
`OVERRIDING USER VALUE`."* `OVERRIDING SYSTEM VALUE` then overrides the sequence, and **the
documentation attaches no privilege requirement to it** — any role holding `INSERT` may use it, and the
engine's own error message names the bypass in its `HINT`. So `GENERATED ALWAYS` refuses the statement
anyone would actually write and does not refuse the statement someone determined would write. The
correct posture is the one this repository has already taken twice: **assert the absence rather than
assume it.** Both halves are proven at the engine, and a source gate turns *nobody would do that* into a
checked property.

**Three: the two inferences nothing may make from `seq`, pinned by a test rather than by a comment.**
*"`nextval` and `setval` calls are never rolled back"* — and the mechanism has to be stated precisely,
because the loose version is false and this plan's first draft shipped it. **A rolled-back `INSERT`
consumes a sequence value and never returns it. A validation refusal consumes nothing**, because
`check_event` raises before `record_event` issues any statement — plan 04-02's own `must_haves` says so
in as many words (*"raises … before any SQL is issued"*), so a bare refused append leaves the next
event's `seq` exactly one higher and there is no gap to find. The gap PH-05 actually produces comes
from its composite shape: a valid event is written, *then* a second append is refused, and the caller's
rollback strands the value the valid `INSERT` had already taken. Both are normal, neither is a defect,
and **the test must provoke the gap through a statement that reached the engine** or it asserts a
property this implementation cannot exhibit. Nothing may infer "events were deleted" from a gap, and that matters
more here than anywhere else in Prope, because A-121 and ADR-0025 make *an event is missing* the most
serious accusation available about this table and Phase 6 ships a test literally named *events are never
deleted*. The second inference is not testable here and is stated instead: **assignment order is not
commit order.** Two concurrent transactions can take 5 and 6 and commit 6 first, so a reader between the
two commits sees 6 with no 5. Inside one transaction — the entire case PH-04 and AC-4 are about — the
order is exact. Across transactions it is not, and the hazard lands on **Phase 5's cursor pagination**:
a *what is new since `seq > N`* poll would permanently skip a row that committed after a higher `seq`
was already returned. INT-007 paginates `seq DESC`, which is the safer direction, so this is a warning
carried forward rather than a defect fixed here — but naming it now is what stops Phase 5 finding it in
a flaky test.

**No decision checkpoint is inserted.** The one open call this plan makes — whether the `OVERRIDING`
source gate is worth building at all — is cheap and reversible in both directions, and it is decided in
Task 3 with its rejected alternative written down, which is the house form for a decision that is not
one-way.
</objective>

**The docstring** opens on the failure mode that looks healthy, in `test_body_retention_delete.py`'s
voice: **two events read back in the order they were written look correct even when the order is an

owner role, which is subject to no policy. Second paragraph: the case this exists for is A-076's, and it
is named rather than abstracted — approve-and-release is one request writing two rows, and the lock's
own failure-mode row says the wrong order shows *"roughly half the time, for exactly the two-event cases
that matter most"*. Third paragraph: what this file deliberately does not assert, so the omissions read
as boundaries — no absolute `seq` values, and no ordering property across concurrent transactions.

**Use the real vocabulary.** The two events are `revision_approved` and then `revision_released`, both
with `target_type = 'revision'`, both in `WORKSPACE_A`, both `occurred_at=day(5)` — the same value
object passed twice, not two calls to a clock. State that at the fixture: `datetime.now(UTC)` called

statement anyone would write, **and it does not refuse the statement someone determined would write** —

engine refuse a caller-supplied value"*; that is true of the naive form and false of the documented one,
and this file is what turns the difference from a belief into a recorded boundary. The third paragraph
states the division of labour with Task 3: **the engine closes the accidental case, and a source gate
closes the deliberate one** — neither is sufficient alone, and each is named in the other's file.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `prope_app` -> `history_event.seq` | The application role holds `INSERT` by design, and `INSERT` is the privilege that makes a supplied `seq` reachable. The engine's `GENERATED ALWAYS` rule and the source gate are the two halves of the control; neither is sufficient alone. |
| `prope_migrate` -> `history_event.seq` | A data revision could supply `seq` values with no application code involved at all, and would do so once with no review of its effect on existing rows. This is why the source gate covers `alembic/`. |
| one transaction -> another | Inside one transaction `seq` is exact. Across concurrent transactions assignment order is not commit order, which is a **reader-side** hazard rather than a writer-side one and is Phase 5's to handle. |
