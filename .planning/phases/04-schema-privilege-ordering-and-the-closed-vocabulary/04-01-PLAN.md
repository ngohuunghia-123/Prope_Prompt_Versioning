<objective>
Ship the `history` schema with its **whole guarantee stack in one applied migration** — two tables,
four indexes, the composite vocabulary key, the tenant policy, the grant matrix and the thirty-one-row
seed — teach the Phase 1 test rig that a second schema exists, and prove the one property the module is
sold on: **`prope_app` cannot rewrite a history row, and the engine is what says so.**

This is the tracer, and its vertical path is short because the guarantee it proves has no application
layer by design. ADR-0025's whole argument is that append-only belongs in the authorisation layer, so
PH-02 is proven or disproven by two `has_table_privilege` calls and a statement the engine refuses.
`04-RESEARCH.md` states the failure mode this plan is shaped against: *"A plan that spends its weight on
the validator and treats the grant matrix as a line in a migration has inverted the phase."* The
validator is plan 04-02's; the grant matrix is this plan's, and it is the phase's first success
criterion.

**This is the first new schema since Phase 1, and that costs four test-rig edits that a reader of
revision `0004` would not expect.** `0004`'s docstring says *"NO TEST RIG EDIT IS NEEDED, AND THAT IS
THE POINT"* — true of a new **table**, false of a new **schema**, because three Phase 1 files name
`ledger` as a literal. Two of them go red (`tests/conftest.py`'s truncate filter has no history entry;
`tests/architecture/test_tenant_coverage.py` asserts the existing-schema tuple is `("ledger",)`), and
the third — `tests/integration/test_migration_chain.py` — does something worse: it stays **green while
silently not covering the new schema**, so a pristine-cluster upgrade would assert nothing about
whether `history` arrived, and the idempotency snapshot would not notice a seed applied twice. All
three are edited here. **`.planning/STATE.md`'s Phase 01 note naming Phase 7 as the first phase that
must shrink `EXPECTED_ABSENT_SCHEMAS` is now wrong; this phase is first, and the comment inside
`test_tenant_coverage.py` that says the same thing is corrected in the same change.**

**No decision checkpoint is inserted in this plan, deliberately.** Six one-way or costly decisions were
adopted in `04-DISCUSSION-LOG.md` with their reversibility ratings recorded — D-50 (the positive grant
form instead of the lock file's literal `REVOKE`), D-53 (`GENERATED ALWAYS` where the lock says
`bigserial`), D-56 (the first `GLOBAL_TABLES` entry), D-57 (a composite foreign key on a tenant-scoped
table), D-61 (the derived `target_type` set and twenty-eight empty `detail_keys`) and D-64 (the
Phase 4 / Phase 5 split). Re-opening any of them here would be re-asking a settled question, which is
the posture plan 02-04 took for D-18 and D-20. All six are carried into `deferred-items.md` and are
owed to `04-UAT.md` and `.planning/ORCHESTRATION-DECISIONS.md` as numbered adjudication items.

**Stated gap this plan leaves open, and who closes it.** After this plan the `history` schema is
complete and unwritable-by-application-code, and **nothing in `src/prope/` knows it exists.** There is
no `record_event`, no registry loader, no counter. Plan 04-02 builds the validating write path (PH-05)
and plan 04-03 proves the total order (PH-04). The tests in this plan seed events with a raw `INSERT`
through the factory module rather than through a write path that does not exist yet — which is also
what keeps PH-02's assertion independent of the code plan 04-02 writes.

**The module docstring is a deliverable, not decoration.** Match `0004`'s density. It must carry, each
as a bold-led paragraph:

1. *What this revision is*: the `history` schema and its two tables, arriving with the whole stack in one
   applied migration, which is the shape `0002`, `0003` and `0004` all use.
2. **`D-53 — THE LOCK FILE SAYS bigserial AND THIS SHIPS GENERATED ALWAYS AS IDENTITY.`** A `bigserial`
   is a `DEFAULT nextval(...)`, and a default is only consulted when the caller omits the column;
   `prope_app` holds `INSERT` by design, so a hand-written statement supplying its own `seq` would be
   accepted and the total order would stop being total with no error anywhere. The same sentence in
   `data.owns` that says `bigserial` also says *"monotonic, and the ONLY sort key"*, and
   `GENERATED ALWAYS` implements that more strictly. **State the deviation honestly and do not repeat
   the planner's original ground for withholding an OQ, which was false.** The column type is `bigint`
   either way, but the *observable behaviour differs*: under the lock's `bigserial` an `INSERT` naming
   `seq` and supplying a value succeeds silently, and under `GENERATED ALWAYS` the engine refuses it —
   which is exactly what `tests/security/test_history_seq_cannot_be_supplied.py` (plan 04-03) asserts.
   So this is a strengthening with a behavioural difference against a literal spec token, not a
   spelling difference, and it is **owed an OQ naming `docs/modules/property-history.lock.yml`
   `data.owns → history_event → seq` and `docs/adr/0024-…`'s Decision block**. Phase 4's allocated
   range `OQ-027…OQ-031` is fully consumed, so the id is escalated to the orchestrator in
   `deferred-items.md` §1 rather than taken from another phase's range. The docstring records the
   deviation, the behavioural difference, the test that proves it, and the fact that the OQ is owed and
   unallocated. Contrast item 3, which genuinely is a spelling difference with a byte-identical end
   state.
3. **`D-50 — THE LITERAL REVOKE THE LOCK FILE NAMES IS NOT ISSUED.`** `libraries_frameworks` names
   `REVOKE UPDATE, DELETE ON history.history_event FROM prope_app`. `prope_app` never holds either, so
   the statement would be a no-op that reads in a diff as protection. `grant_table`'s own docstring
   already argues the positive form — *"both end in the same state and the positive form is the one a
   reviewer can read"* — and the end state is what
   `tests/security/test_history_is_append_only_by_privilege.py` asserts, which is true under either
   spelling and false under neither.
4. **`WHAT THIS REVISION ENFORCES, AND WHAT IT DELIBERATELY DOES NOT.`** The `(action, target_type)`
   pairing is an engine fact (the composite key below). The `details` allow-list and `requires_reason`
   are **not**, and cannot be: a `CHECK` cannot reach another table, and ADR-0023 rejects triggers for
   this module **by name**, on the grounds that they *"put the audit vocabulary in migrations rather
   than in a module, where the allow-list of ADR-0024 cannot run."* Make the argument freshly rather
   than citing `0004`: only two of `0004`'s three anti-trigger reasons transfer, because the volume
   argument does not apply — `history_event` takes one row per state change, not one per gateway call,
   so a per-row registry probe would be affordable here and is refused on the other two grounds.
   Because the guarantee lives in one language and not in the engine, **the absence is asserted rather
   than assumed**: name `tests/security/test_history_validation_has_no_database_backstop.py` (plan
   04-04) as the file that proves a hand-written `INSERT` bypassing the module succeeds.
5. **`THE RIG EDITS THIS REVISION FORCES, AND WHY 0004's CLAIM DOES NOT TRANSFER.`** `0004` says no test
   rig edit is needed. That is true of a table and false of a schema; name the three files and the
   literal in each.
6. **Types.** Every `*_id` is `text` (ADR-0003 prefixed ULIDs) and every timestamp is `timestamptz`
   (A-003). `workspace_id`, `actor_id` and `target_id` are **values, not references** (A-122) — the
   property that makes ADR-0054's tombstone-and-survive cost this module nothing. The only foreign key
   in the module is intra-schema and points at the module's own second table.
7. **`WHAT GENERATED ALWAYS GUARANTEES, AND THE ESCAPE HATCH IT DOES NOT CLOSE.`** This is the
   **boundary note**, and plan 04-03 Task 2 is written against it existing — it instructs its executor
   to delete this paragraph if the boundary ever moves, so a revision without it leaves a dangling
   reference in a security test. PostgreSQL: *"For an identity column defined as `GENERATED ALWAYS`, it
   is an error to insert an explicit value (other than `DEFAULT`) without specifying either
   `OVERRIDING SYSTEM VALUE` or `OVERRIDING USER VALUE`."* The documentation attaches **no privilege
   requirement** to `OVERRIDING SYSTEM VALUE`, so any role holding `INSERT` may use it and the engine
   names the bypass in its own `HINT`. `GENERATED ALWAYS` therefore refuses the statement anyone would
   write and does not refuse the statement someone determined would write. Name the two halves that
   record it, in the register item 4 uses for the refused trigger:
   `tests/security/test_history_seq_cannot_be_supplied.py` proves both directions at the engine, and
   `tests/architecture/test_no_overriding_system_value.py` refuses the token in source under
   `src/prope/` and `alembic/`, which is the half the engine cannot close. State the operational
   consequence in one sentence and get it right, because it is the reason the boundary matters: a
   supplied `seq` **does not advance the sequence**, so the next engine-assigned value is *lower* than
   the supplied one and sorts *before* an event that was written later — the order goes silently wrong
   and stays silently wrong until the sequence climbs to the supplied value, which at *"< 500 events per
   prompt property per year"* may be years. It is not a loud break.

**`CREATE_HISTORY_ACTION_REGISTRY` — written first, because the event table's key points at it.**

- `target_type text NOT NULL`.
- `detail_keys text[] NOT NULL` — a set of identifiers, because the allow-list check is a set

**`CREATE_HISTORY_EVENT` — exactly the twelve columns ADR-0024's schema block names, and no thirteenth**

refusal as a comment at `occurred_at`. ADR-0024 marks exactly three columns nullable — `actor_id`
(and only for the system case), `scope_prompt_id`, and `reason` — so **the other nine are `NOT NULL`**,
and the comment says so as a derivation rather than leaving nullability to look arbitrary: an audit row
missing its actor type, its action, its subject or its instant is not an audit row.

id               text NOT NULL                      -- hev_-prefixed ULID, the PK
workspace_id     text NOT NULL

actor_id         text

Comments that must be present, each carrying the argument rather than restating the type:

- At `seq`: D-53's `bigserial`-is-a-default argument, and **`CACHE 1` written out although it is also
  the default**. PostgreSQL: with a cache above one *"the values might be generated out of sequence when
  all the sessions are considered"* — session A reserves 1..10 and session B reserves 11..20 and returns
  11 first. That is the one setting that destroys this column's only property, it is one
  `ALTER SEQUENCE ... CACHE 20` away, and Task 2 reads `seqcache` back. Naming it here is what makes
  that assertion read as intentional rather than as trivia.
  Also state the two properties nothing may infer, because both are live hazards and one of them is
  Phase 5's. **Monotonic is not gapless** — *"`nextval` and `setval` calls are never rolled back"*. Write
  the mechanism precisely, because the imprecise version is wrong in a way a later reader would build
  on: **a rolled-back `INSERT` consumes a sequence value and never returns it; a validation refusal in
  `check_event` raises before any statement is issued and consumes nothing.** Both are normal and
  neither is evidence an event was deleted. PH-05's criterion produces gaps by the first route and not
  the second — its own transaction test writes a valid event, *then* refuses, and the rollback strands
  the value the valid `INSERT` consumed. Nothing may infer "events were deleted" from a gap, which
  matters more here than anywhere else in Prope because AC-10 is a Phase 6 test named *events are never
  deleted*. And **assignment order is not commit order** — two
  concurrent transactions can take 5 and 6 and commit 6 first, so a reader between the two commits sees
  6 with no 5. Inside one transaction, which is the entire case PH-04 and AC-4 are about, the order is
  exact; across transactions it is not, and that lands on Phase 5's cursor pagination.
- At `id`: it is the primary key, not `seq`. `CONSTRAINT pk_history_event PRIMARY KEY (id)`. It is what
  INT-006's envelope returns, what the lock says is logged (*"the event's id is logged; its content is
  not"*), and what A-045 makes the identifier convention across all eight modules. A `bigint` surrogate
  key beside it would be two identities for one row and a per-call-site decision about which one is
  meant.
- `CONSTRAINT uq_history_event_seq UNIQUE (seq)` — **not hygiene, and the comment must resolve the
  "fifth index" tension out loud rather than leaving it to a reviewer.** D-55 says four indexes and no
  fifth; a `UNIQUE` constraint is an index. The resolution: D-55 is about **query support** — four
  indexes for four declared read shapes — while this one enforces a constraint. The identity sequence
  guarantees distinctness only while nobody restarts it, and the test rig restarts it between tests by
  design (D-48), so this is what makes "seq is a total order" a property of the *table* rather than of
  the sequence's history. Its write cost is a right-edge B-tree insert on a monotonically increasing
  bigint, which is the cheapest index maintenance PostgreSQL has.
- `CONSTRAINT ck_history_event_actor_type_values CHECK (actor_type IN ('user', 'system'))` — **never a
  native enum.** Pitfall 4 and `test_no_native_enum_type_exists_in_the_ledger_schema` (now parameterised
  over both schemas) are the standing rule: adding a value to a native enum cannot run inside a
  transaction block and removing one is impossible at any price.
- `CONSTRAINT ck_history_event_actor_id_present_unless_system CHECK (actor_id IS NOT NULL OR actor_type
  = 'system')` — the pairing rule read exactly as the lock states it: `actor_id` is null *only* in the
  system case, and a system actor **with** an id is permitted. Named so a test can say which rule
  refused rather than merely that something did.
- `CONSTRAINT ck_history_event_reason_length CHECK (reason IS NULL OR char_length(reason) <= 500)` —
  **characters, not bytes, and a CHECK, not `varchar(500)`.** ADR-0053 ships a Vietnamese-only
  interface, so a user-authored reason is multi-byte and a byte cap would silently be a ~170-character
  cap for every user the MVP has. A named CHECK is also droppable and re-addable, where a type change on
  an append-only table is a rewrite the application role cannot perform.
- At `details`: `jsonb NOT NULL DEFAULT '{}'::jsonb`, and the comment must state the inversion of
  `0003`'s call one schema over. `call_body.request_body` is `text` because *"jsonb would reject a
  malformed body, which is exactly the body worth keeping"*. Here the payload is assembled by our own
  code out of allow-listed keys and never contains provider content, so a malformed payload is a caller
  bug and refusing it at the engine is right. The two decisions look contradictory and are one rule
  applied twice. `NOT NULL DEFAULT '{}'` because `user_tombstoned`'s `detail_keys` are deliberately
  empty and NULL versus `{}` would be two spellings of "no details" — the allow-list check would then
  have two branches and one of them would eventually be the one nobody wrote. **No GIN index**: no query
  in any lock file reads a details key, and this is the one table in Prope that only ever grows (A-121).
- At `scope_prompt_id`: nullable by design, and **no constraint of any kind, stated so the absence does
  not read as an oversight.** A `CHECK` cannot express the rule — "prompt-scoped actions must carry a
  scope" needs the registry, and a CHECK cannot reach another table — and a trigger is refused by
  ADR-0023. The lock routes the enforcement to a **metric** rather than a refusal
  (`prope_property_history_null_scope_prompt_total`, alert `PropertyHistoryScopeMissing`, severity
  *ticket*, with the note *"The write succeeded and an Activity feed is quietly incomplete. This is the
  only silent-but-detectable failure here"*), and converting it to a refusal would fail a user's state
  change over a display concern. **That metric is Phase 6's.** What this phase owes Phase 6 instead is
  the derivation, so the check can be data-driven when it arrives: seven of the thirteen `target_type`
  values are prompt-scoped — `property`, `revision`, `release`, `review_task`, `eval_suite`, `eval_run`,
  `prompt_grant` — and six are not — `provider_config`, `workspace`, `member`, `role`, `api_key`,
  `user`. A-119 says the prompt-scoped set names *six*; the derivation gives seven, and that
  discrepancy is already inside `OQ-029`. **Do not add a sixth registry column** (`prompt_scoped`):
  CONTEXT fixes the registry at five, and a sixth is inventing schema the spec did not declare.
- `CONSTRAINT fk_history_event_action FOREIGN KEY (action, target_type) REFERENCES
  history.history_action_registry (action, target_type)` — **and no `ON DELETE` or `ON UPDATE` clause of
  any kind**, following `0003:216-221`'s stated rule: the registry is `SELECT`-only for `prope_app` and
  A-120's vocabulary is closed, *"so the case cannot arise, and naming a behaviour for an impossible
  case invites someone to make it possible."* The comment must also dispose of the cross-tenant
  objection rather than leaving it assumed: `test_no_foreign_key_leaves_the_ledger_schema` exists
  because referential-integrity checks *"always bypass row security"*, so a key from a tenant-scoped
  table into **another tenant-scoped table** leaks the existence of another tenant's row through the
  success or failure of the check. **This key's target is global and byte-identical for every
  workspace**, so there is nothing to infer; and the history counterpart of that test still asserts no
  key *leaves* `history`, which this one does not. Record the cost honestly, as an agent judgement and
  not a measurement: every `history_event` insert takes a `FOR KEY SHARE` lock on one of thirty-one
  registry rows, and those become multixact-generating hot rows under concurrency. `FOR KEY SHARE` locks
  are mutually compatible so they never block each other; multixacts are created only when two or more
  transactions hold a lock on the *same* row at the same instant, which is a function of concurrency
  rather than throughput. ADR-0033 runs one `app` and one `worker` on one VM, the lock's load target is
  200 appends/sec, and the appends spread over thirty-one rows with millisecond transactions. **The
  escape hatch is recorded rather than pre-emptively tuned: dropping the key is cheap at any time and
  adding it back after the pilot is a validating scan over a never-shrinking audit table.** Do not touch
  `autovacuum_multixact_freeze_max_age`; a knob turned for a problem nobody has is a second runbook
  A-012 forbids.

**No CHECK on `target_type`, anywhere**, and say so in a comment. ADR-0024 calls it a closed
enumeration; the registry's thirty-one seeded rows **are** that enumeration, and `history_event`'s

second copy of a list, and adding a fourteenth would become a `DROP`/`ADD CONSTRAINT` with a validating
scan over an append-only table — the exact cost D-57 refused one column over.

**`upgrade()` — the ordering, and one call that must run before another.**

```python
def upgrade() -> None:
    op.execute("CREATE SCHEMA history AUTHORIZATION prope_migrate")
    op.execute("GRANT USAGE ON SCHEMA history TO prope_app, prope_report")

    assume_migrate_role()

    op.execute(CREATE_HISTORY_ACTION_REGISTRY)
    op.execute(SEED_ACTION_REGISTRY)
    op.execute(CREATE_HISTORY_EVENT)
    for statement in CREATE_INDEXES:
        op.execute(statement)

    enable_tenant_rls("history", "history_event")

    grant_table("history", "history_event", app_privileges=["SELECT", "INSERT"])
    grant_table("history", "history_action_registry", app_privileges=["SELECT"])

    reset_role()
```

The two `CREATE SCHEMA` / `GRANT USAGE` lines run **before** `assume_migrate_role()`, and the comment
says why: `prope_migrate` is not guaranteed to hold `CREATE ON DATABASE`, and revision `0001` created
`ledger` as the connected superuser for exactly this reason. Everything after runs under the assumed
role so the objects are owned correctly, which is what ADR-0035's owner bypass rests on. `reset_role()`
is not optional — `assume_migrate_role`'s docstring states the consequence of forgetting it: Alembic's
own write to `public.alembic_version` is then attempted as `prope_migrate`, which holds no privilege
there. The registry is created and seeded **before** `history_event`, because the composite key points
at it. `enable_tenant_rls` is called in the revision that creates the table and never a later one
(`0004:154-157`'s comment is the register), and **`history_action_registry` gets no
`enable_tenant_rls` call at all** — with the `GLOBAL_TABLES` entry below shipping in the same change,
because ADR-0045's walk would otherwise fail it.

The two `grant_table` calls each carry a comment in `0003:252`'s register. On `history_event`:
`SELECT` and `INSERT`, no `UPDATE`, no `DELETE`, **and this is PH-02 in its entirety** — ADR-0025's
*"a log the application can rewrite is a Sheet with better indexing"*. Note that `SELECT` alongside
`INSERT` is a requirement rather than generosity: PostgreSQL requires `SELECT` privilege on every column
a statement *references*, and the tenant policy's `USING`/`WITH CHECK` predicate references
`workspace_id` — `0003:246-251` records the identical reasoning for `call_body` — and `SELECT` is also
what INT-007's `read()` needs in Phase 5. On `history_action_registry`: `SELECT` only, **derived from
ADR-0038 rather than chosen** — *"the registry table is SELECT-only for `prope_app` … there is no
user-editable path and no API that writes it, so there is no runtime event that could make the cache
stale"* — which is what makes ADR-0038's process-lifetime cache with no invalidation safe: the only
writer is `prope_migrate`, the only write is a migration, and ADR-0031 restarts the application after
migrating.

`report_select` takes its default of `True` on both, and **the argument is made rather than inherited**,
in `0004:163-168`'s shape. ADR-0037 was written *about this exact table*: *"in every other module a
stray privileged session is a risk; here it is the module whose entire product claim is that the record
cannot be quietly rewritten"* and *"with one privileged role used for two purposes, no session record
distinguishes a person reading a metric from a person editing a row."* A-126's cross-workspace Success
SQL reads `history_event` across workspaces; withhold `SELECT` from `prope_report` and that query goes
back to `prope_migrate`, which is the only role that can `DELETE` a history row and is precisely the
outcome ADR-0037 exists to prevent. **Granting is not the lenient option here; it is the one that keeps
ADR-0025's distinction intact.** State the counter-consideration honestly rather than omitting it:
`reason` is user-authored free text and `details` is a payload, so `prope_report` becomes a full-read
credential over the module's two most content-bearing columns — a posture ADR-0037 already declares,
whose control is A-124's allow-list and A-020's line, not a grant.

`downgrade()` drops in reverse dependency order — `history_event` first, then
`history_action_registry` (the key points at it), then `DROP SCHEMA IF EXISTS history CASCADE`, under

## Assumption delta — an agent judgement, not a detector result

`gsd-tools`' assumption-delta detector does not exist in this environment (ORCHESTRATION §0) and none
was run or simulated. The genuine identity-model delta this plan carries, recorded in the shape the
Phase 1–2 plans used:

- **Noun now primary:** the *history event*, which arrives with **two** candidate identities in the same
  row — `id`, an `hev_`-prefixed ULID, and `seq`, a database-assigned bigint.
- **Decision: `promote` on one and `demote` the other, rather than `add-alongside`.** `id` is promoted to
  *the* identity (primary key, the value INT-006 returns, the value logged, the convention A-045 fixes
  across eight modules). `seq` is demoted to an ordering key with a `UNIQUE` constraint and no
  identity role. The rejected shape is the one that reads as obvious — `seq` as the primary key,
  because the cursor key is the sort key — and it is refused because it would leave two identities for
  one row and a per-call-site decision about which one is meant.
- **Companion invariant:** `uq_history_event_seq` pins that `seq` is distinct **as a property of the
  table** rather than as a property of the sequence's history, which matters because the rig restarts
  the sequence between tests by design.
- **Accepted consequence:** the ordering key is not the identity, so a reader holding an `id` cannot
  infer position and a reader holding a `seq` cannot address a row across a restore. Both are correct;
  neither is a gap.
