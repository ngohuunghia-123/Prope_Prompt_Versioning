<objective>
Build the module: the vocabulary as Python values, the registry as ADR-0038's immutable process-lifetime
mapping, and **the validating write path that runs inside the caller's transaction** — then prove
PH-05, which is the phase's third success criterion and the one that cannot be tested without it.

**Why this phase builds a write path at all, stated plainly because a reader of the two ROADMAP phase
goals will expect otherwise.** Phase 5's goal names `append()`, `read()` and `registered_actions()`.
Phase 4 owns **PH-05**, whose criterion is *"an append with an unregistered action or an unregistered
`details` key raises, rolls the caller transaction back with no partial state, and increments
`append_rejected_total` with a reason"* — a raise, a rollback and a counter, none of which is observable
without a path that validates and writes. ORCHESTRATION §9 forbids the alternative: *"a red test is
never 'expected'."* So D-64 draws the line **by capability rather than by filename**: this plan ships
the registry loader, the three-way validator, the refusal type and its reason vocabulary, the rejection
counter, and an internal insert that runs on a session handed to it. **Phase 5 renames or wraps
`record_event` as INT-006's `append()`**, adds `scope_prompt_id` as a contract, `read()` with its cursor
semantics and `registered_actions()`, and wires the registry into `app` and `worker` at process start.
That is the honest cost of the split — this phase ships a function under a name no downstream spec uses
— and it is smaller than a phase whose stated criterion cannot be tested inside it.

**The transaction posture is the whole module and it is the inverse of its nearest neighbour.**
`src/prope/call_ledger/seams.py:37-48` argues D-19's own-transaction shape **by naming this module** as
the pattern it deliberately does not copy. Here the argument runs the other way: `record_event` takes an
`AsyncSession`, never an `async_sessionmaker`; it opens no transaction and closes none; and it never
calls `session.rollback()`, because ending the caller's transaction underneath them is the exact
inverse of ADR-0023's *"commits or rolls back with it"*. **The raise is the whole mechanism, and the
caller's `async with` is what performs the rollback.**

**The test that proves that is not the obvious one, and the obvious one proves nothing.** A test
asserting `SELECT count(*) FROM history.history_event` is zero after a refused append goes green
against a module that opened and rolled back *its own* transaction — which is call-ledger's shape and
the one arrangement ADR-0023 forbids. So the PH-05 test **is the caller**, and it gives the caller
something to lose: a valid event written in the same transaction *before* the poisoned one, asserted
gone afterwards through the owner role.

**Stated gaps this plan leaves open, each with the requirement that closes it.** `record_event` does not
stamp `scope_prompt_id` as a contract and does not enforce that a prompt-scoped action carries one —
that is A-119's guard, which the lock routes to a metric rather than to a refusal, and the metric is
Phase 6's. There is no `read()`, so nothing yet reads a history row back through the module. The
registry is loaded by a function its tests call; **there is no module-level global and no process-start
wiring**, deliberately, so Phase 5 introduces the global rather than inheriting a mutable one somebody
already reached for. And AC-6 — the registry equalling the union of five lock files' event lists — is
Phase 5's assertion against the seed plan 04-01 shipped.
</objective>

`{event, call_id, workspace_id, reason, queue, delivery_tag, group_size, window_size, job}`. For
call-ledger, `reason` carries closed vocabulary tokens — `unroutable | nacked | timeout`,

The `#:` block above it must say two things. **`seq` is absent from the column list — not `DEFAULT`,
not a comment, absent** — because a column that is not named cannot acquire a value by a one-word edit,
and `GENERATED ALWAYS` refuses the statement anyone would write but not the statement someone
determined would write (plan 04-03 asserts both halves). And **`CAST(:details AS jsonb)` over a
`json.dumps` string** rather than binding a `dict`: a raw `text()` statement carries no SQLAlchemy type
information, so a bound `dict` reaches the asyncpg dialect's `jsonb` encoder — `lambda str_value:
b"\x01" + str_value.encode()` — and raises `AttributeError` from inside a codec, which reads as a
driver bug rather than as a type error at the call site. The cast makes the parameter's inferred type
`text`, so a mistake produces a clear `expected str, got dict`; and serialisation becomes this module's
decision rather than a dialect's, which matters because `details` is the one column A-124 exists to
police.

`def check_event(event: HistoryEventDraft, registry: Mapping[str, RegisteredAction]) -> None` —
**D-62's single validation site.** Its docstring must say, in these words, that `record_event` calls it
and **nothing else may**, and that Phase 5's `append()` wraps `record_event` and must not call it a
second time: a second call double-counts `append_rejected_total`, and the lock's alert makes every
increment a page, so a double count is a second page for one failure. Three checks, in this order, and
**the order is a decision the docstring states rather than leaving to look incidental**:
`unknown_action` first, because without a registration the other two questions have no answer;
`unknown_detail_key` before `missing_reason`, because a payload leak is T-022 (HIGH) and a missing
reason is a policy omission, so the more serious refusal wins when a caller manages both.

```python
    registered = registry.get(event.action)
    if registered is None:
        raise HistoryAppendRejected(RejectionReason.UNKNOWN_ACTION, action=event.action)

    unregistered = frozenset(event.details) - registered.detail_keys
    if unregistered:
        raise HistoryAppendRejected(
            RejectionReason.UNKNOWN_DETAIL_KEY, action=event.action, detail_key=min(unregistered)
        )

    if registered.requires_reason and not (event.reason or "").strip():
        raise HistoryAppendRejected(RejectionReason.MISSING_REASON, action=event.action)
```

`min(unregistered)` gets a comment: it is for a **deterministic message**, not for meaning — one
unregistered key is enough to refuse, and picking the lexically first makes the failure reproducible in
a test. `(event.reason or "").strip()` gets one too: a reason of `"   "` satisfies `NOT NULL` and
satisfies the 500-character CHECK and is not a reason, so whitespace-only is refused here where the
engine cannot.

## Assumption delta — an agent judgement, not a detector result

No assumption-delta detector exists in this environment and none was run. The genuine delta:

- **Noun now primary:** the field name `reason`, which from this plan onward names **two different
  kinds of value** in one codebase — a closed-vocabulary classification token in call-ledger, and
  user-authored free text in property-history that must never leave the database.
- **Decision: `promote` the disambiguation rather than `add-alongside`.** `reason` keeps call-ledger's
  meaning exclusively; property-history's classification token is promoted to its own name,
  `rejection_reason`, and the free-text column is demoted to *not a loggable field name at all*. The
  rejected shape is the one that looks symmetric — one field name, one allow-list, a per-module
  qualifier — and it is refused because it makes A-046 a property asserted per module, which is the
  shape a module can forget to assert.
- **Companion invariant:** the user-authored `reason` has no entry in `LOGGABLE_FIELDS`, so the
  prohibition is expressed as an absence rather than as a rule somebody has to remember. Plan 04-04
  asserts it with a marker.
- **Accepted consequence:** `rejection_reason` and `reason` sit near each other in one allow-list and a
  careless reader will treat them as one field. The `#:` comments at both are the mitigation.
