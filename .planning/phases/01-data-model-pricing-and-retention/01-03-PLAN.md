## Adopted readings that bind this plan

- **Discretion §1 — money.** `numeric(20,10)` end to end; exact decimal in Python; quantise at the **column's** scale (ten decimal places, banker's rounding), never at the currency's. A representative call is a few hundred tokens at a price of order 0.00015 per 1k, which is about 0.00007 — rounded to a currency's minor units that is 0.00, the row now records a cost of zero, ROADMAP success criterion 2 forbids it in as many words, and the `cost > 0` CHECK would turn a rounding decision into a write-path outage. `numeric(20,10)` spans both a USD price of order 0.00002 per 1k and a VND price of order 1000 per 1k (A-107 keeps the currency explicit and forbids conversion). Confidence on the exact `(20,10)` is MEDIUM — flagged below.
- **Discretion §2 — effective-date boundary.** Half-open `[effective_from, next effective_from)`; predicate `effective_from <= created_at`; a call landing exactly on an `effective_from` resolves to the **new** row. "Rows exist but every `effective_from` is later than the call" is `unpriced` on exactly the same footing as "no row at all" — the distinction is invisible to the writer and should stay invisible, because it is one conditional away from someone deciding the earliest row is close enough.
- **Discretion §3 — the seam.** One async `write_records(session, records, *, retention_window)`; it **does** upsert `workspace_spend` in the same transaction (A-103, ADR-0040). `period_month` from the record's own `created_at`; `call_count` counts every written record including unpriced and unknown-usage ones; `total_cost` sums only priced costs — `call_count` answers "how much traffic", `total_cost` answers "how much money", and conflating them would let unpriced traffic look free.
- **OQ-B — the retention window is a parameter**, `retention_window: timedelta = timedelta(days=30)`, not a column. No table outside `data.owns` is touched. Phase 2 owns the storage decision when `PUT /workspaces/{id}/retention` arrives.
- **OQ-E — a `priced` call can never cost exactly zero.** Gateway's GATE-04 describes a pre-first-byte fallback recorded "with zero tokens and zero cost"; under this encoding that row is `usage_status='unknown'` / `cost_status='not_applicable'` with NULL tokens and NULL cost. This plan asserts that reading in a unit test so the Phase 19 gateway work inherits it rather than inventing a zero. Carried upstream as an open question because the two documents use different words for the same row.
- **Pattern 7 — `now` is a parameter, never a call.** Every function that compares against the present takes it as an argument. CL-03's day-5/day-12/day-20 case and CL-08's 31-days-ago case both become plain arithmetic on `datetime` values with no clock to freeze, and no test-time clock library can move the *server's* clock anyway.

## Flagged assumptions

- **A3 — `numeric(20,10)` is wide enough** for both USD-per-1k and VND-per-1k prices and for any realistic cost. Medium risk: a too-narrow scale rounds a small cost to zero, which the `cost > 0` CHECK then rejects at insert. The sub-cent test in Task 1 is the guard; widen rather than narrow if it ever trips.
- **A4 — `call_count` includes unpriced and unknown-usage records.** The repo does not state it. Medium risk: it changes what the number means. Recorded here and asserted in Task 2 so the semantics are visible rather than implied.
- **A2 — tz-aware datetimes everywhere.** `datetime.now(UTC)`, never the deprecated naive form; never a naive `datetime(...)` in a fixture. A naive value compared against a `timestamptz` column is interpreted against the *server's* time zone, so the day-5/day-12 arithmetic could pass or fail by geography.
