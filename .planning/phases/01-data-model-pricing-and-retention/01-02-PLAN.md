policies and grants — and turn every migration-carried guarantee into a live-engine assertion.

## Adopted readings that bind this plan

- **OQ-A** — `workspace_id` is `text` on all five tables; every policy predicate compares text to text with no cast. Confirmed at the `checkpoint:decision` in plan 01-01.
- **Discretion §5** — `text` + named `CHECK`, never a native PostgreSQL enum type; index list per RESEARCH.md Pattern 1.
- **Discretion §6** — `prope_report` receives its `SELECT` grants in this phase, in the same revision as the tables. ADR-0037 already records that `BYPASSRLS` plus `SELECT` on `ledger.call_body` makes this a full-read credential over raw end-user bodies and that it is handled as one. Narrowing it (granting `prope_report` `SELECT` on four tables and not on `call_body`) would need an ADR and is out of scope for this phase — recorded here so a reviewer who notices the tension finds it already answered, and so nobody invents the narrowing unilaterally.
- **Alembic layout** — one revision per slice, guarantee per helper (see plan 01-01 § "Planner decisions the repo does not state").
- **`call_body` keeps `SELECT` as well as `DELETE`.** A `DELETE … WHERE expires_at <= …` reads a column, and PostgreSQL requires `SELECT` privilege on every column a statement references. Revoking `SELECT` in the name of "no read path" would break the retention job. The no-read-path guarantee (AC-10) is a property of the **route table**, not of the grant matrix, and it lands in Phase 3.

    **`tests/security/test_append_only_privilege.py`** — D-07 / T-006, five tests, every one carrying
    a positive control. Seed a real price row as `prope_migrate`. Then, inside
    `workspace_transaction(app_sessionmaker, that_workspace)`, first assert the row **is** visible
    (`SELECT count(*)` returns 1) — without this the whole file passes against an empty table, since
    an update affecting zero rows and an update refused by the engine are both "nothing changed" from
    the test's side. Then assert an `UPDATE` on `ledger.price_table` raises with a permission-denied
    message naming `price_table`, and that a `DELETE` on it raises the same way. Privilege is checked
    before row security, so a visible row isolates the privilege rather than the policy. Add a third
    test asserting `DELETE` on `ledger.call_record` is refused with a visible row present, and a
    fourth asserting `DELETE` on `ledger.call_body` **succeeds** for a seeded body — the retention job
    is the one thing that must have it, and asserting the permission's presence is what stops a later
    "tighten the grants" pass from breaking retention silently.

    A fifth test, named so `-k teeth` selects it, is the **mutation check, written as a runnable
    test** rather than as a manual procedure — a guarantee nobody can execute is not a guarantee, and
    this plan is `autonomous: true`, so there is no actor to hand a manual step to. Its shape:
    seed a price row as `prope_migrate`; then, as `prope_migrate`, issue
    `GRANT UPDATE ON ledger.price_table TO prope_app` and commit; inside a `try`, open a **new**
    `workspace_transaction` (a fresh transaction, because privilege is re-checked per statement but
    the refusal must be observed after the grant is visible), assert the row is visible, and assert
    the `UPDATE` that tests 1 and 2 expect to be refused now **succeeds** — that is, assert
    `has_table_privilege('prope_app','ledger.price_table','UPDATE')` is now true and that no
    permission error is raised. In a `finally`, issue
    `REVOKE UPDATE ON ledger.price_table FROM prope_app` as `prope_migrate` and commit. After the
    `finally`, assert `has_table_privilege('prope_app','ledger.price_table','UPDATE')` is false again,
    so a failure inside the body cannot leave the privilege matrix loosened for every later test in
    the session. This is what proves tests 1 and 2 are asserting the engine's refusal rather than an
    empty table or a no-op update.
