<objective>
Close the two remaining phase success criteria: a price row added after the fact reprices only what
was never priced, and bodies past their retention window are gone by any query while their call
records remain.

Purpose: these are the two operations that touch already-written history, and each has a failure mode
that reads as success. Repricing that widens its filter silently rewrites figures a reviewer already
approved. A retention job that runs cleanly and deletes nothing looks healthy from the job's side —
which is why this phase verifies the deletion by direct query against the data, never through an API
that could be filtering.

Output: `reprice_unpriced`, `delete_expired_bodies`, and two integration test files that assert every
property separately against a live PostgreSQL 17.

## Adopted readings that bind this plan

- **OQ-D — one transaction per chunk.** ADR-0040 says the retention job "deletes each one's expired bodies in bounded chunks inside that workspace's transaction". Read literally, the singular puts every chunk in one transaction, which holds every row lock and the whole snapshot for the duration and therefore delivers none of the benefit chunking exists for — and the lock file's chaos plan ("run the deletion job concurrently with peak writes and assert the writer's lag stays inside its target") is only satisfiable with short transactions. **Adopted reading: each transaction covers exactly one workspace and carries its own tenant context.** Every chunk gets its own transaction; every transaction is still single-workspace, the policy's check clause still applies, and no transaction is long-lived. Raised upstream as OQ-D; the ADR is not edited.
- **OQ-C — no enumeration, no scheduler.** ADR-0051 names `access.list_workspaces()` as *the* mechanism for a cross-tenant sweep and names call-ledger's retention job directly, but the `access` schema does not exist until Phase 7 and access-control is in this module's `forbidden_dependencies`. This phase ships `delete_expired_bodies(sessionmaker, workspace_id, *, now, chunk_size, max_chunks)` — workspace-scoped, no enumerator, no timer — which fully satisfies CL-08 and AC-8, every clause of which is testable against a single seeded workspace. **A fifth `SECURITY DEFINER` function is not the answer**: a project test asserts the sanctioned set is exactly four, and that assertion only means something while the number tracks architecture. The `worker` process that would host a timer does not exist until Phase 2, and no scheduler library enters the build for a third timer.
- **Pattern 7 — `now` is a parameter.** `delete_expired_bodies` takes the cut-off instant as an argument. AC-8's "bodies written 31 days ago with a 30-day retention window" is then plain arithmetic on `datetime` values.
- **Verification is by direct query as `prope_migrate`, not through the application session.** The lock file's security test plan requires exactly this: "retention delete verified by direct query rather than through an API that could be filtering". Under row-level security, an application-session query for the wrong workspace returns zero rows whether or not the delete worked, so a test checking emptiness through `prope_app` in the wrong tenant proves nothing.

## Flagged assumptions

- **CL-08 edge probe row: UNRESOLVED, surfaced not dropped.** The deterministic edge probe classified CL-08 as `unclassified` and it is carried here as a flagged assumption rather than auto-resolved with a backstop. The two open dimensions are: **(a) A6 — chunk size.** 5,000 rows per chunk is a research judgement, not a repo decision. The stated target is one day's expired bodies removed within 10 minutes at up to 500,000 body rows in a batch; at 5,000 that is 100 chunks, which has ample headroom, but the number is tunable and unvalidated at real scale. **(b) OQ-C — cross-tenant enumeration.** CL-08's requirement text says "call bodies past their retention window are deleted" without saying *for which workspaces*; Phase 1 answers it for one workspace at a time and leaves the sweep that visits all of them unbuilt, because the mechanism ADR-0051 designates does not exist yet. Both are recorded here so the gap is visible rather than assumed closed.
- **A7 — `FOR UPDATE SKIP LOCKED` in the chunk selection** is a safety improvement (the job becomes safe to run concurrently with itself and with the writer), not a requirement. Low risk either way.
- **A8 — a chunked delete returns space to the table's free list, not to the disk.** A-132 states and accepts this, with a disk-usage alert beside the oldest-body gauge in a later phase. Do not "fix" it with a full vacuum — that takes an exclusive lock on the largest table in the system.
