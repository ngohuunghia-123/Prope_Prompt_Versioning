## Adopted readings that bind this plan

- **OQ-D — one transaction per chunk.** ADR-0040 says the retention job "deletes each one's expired bodies in bounded chunks inside that workspace's transaction". Read literally, the singular puts every chunk in one transaction, which holds every row lock and the whole snapshot for the duration and therefore delivers none of the benefit chunking exists for — and the lock file's chaos plan ("run the deletion job concurrently with peak writes and assert the writer's lag stays inside its target") is only satisfiable with short transactions. **Adopted reading: each transaction covers exactly one workspace and carries its own tenant context.** Every chunk gets its own transaction; every transaction is still single-workspace, the policy's check clause still applies, and no transaction is long-lived. **This reading is proven behaviourally, not by reading the source — and the proof has to observe an IN-FLIGHT loop, not a returned one.** `delete_expired_bodies` therefore takes an optional `on_chunk` callback (default `None`, so the production call path is unchanged) that is awaited after each chunk's transaction commits and before the next one opens. The `-k per_chunk` test's callback opens a fresh `prope_migrate` connection and records how many bodies remain: over 12 expired bodies at `chunk_size=5` the recorded sequence is 7, 2, 0 — chunk 1's deletions are already visible outside the loop while chunks 2 and 3 have not run. A loop-wide single transaction would record 12, 12, 12, because nothing it deleted becomes visible to another connection until the whole loop commits, and a plain count on that other connection does not block on the uncommitted deletes — so the broken shape fails loudly rather than hanging. **A bounded `max_chunks=1` run cannot discriminate the two shapes at all**: with exactly one chunk, both must commit before returning, so both produce the identical post-return observation. That is why the test is an unbounded multi-chunk run observed from inside. A keyword search over the implementation would be weaker still and would reject correct loop shapes. Raised upstream as OQ-D; the ADR is not edited.
- **OQ-C — no enumeration, no scheduler.** ADR-0051 names `access.list_workspaces()` as *the* mechanism for a cross-tenant sweep and names call-ledger's retention job directly, but the `access` schema does not exist until Phase 7 and access-control is in this module's `forbidden_dependencies`. This phase ships `delete_expired_bodies(sessionmaker, workspace_id, *, now, chunk_size, max_chunks, on_chunk)` — workspace-scoped, no enumerator, no timer — which fully satisfies CL-08 and AC-8, every clause of which is testable against a single seeded workspace. **A fifth `SECURITY DEFINER` function is not the answer**: a project test asserts the sanctioned set is exactly four, and that assertion only means something while the number tracks architecture. The `worker` process that would host a timer does not exist until Phase 2, and no scheduler library enters the build for a third timer.
- **Pattern 7 — `now` is a parameter.** `delete_expired_bodies` takes the cut-off instant as an argument. AC-8's "bodies written 31 days ago with a 30-day retention window" is then plain arithmetic on `datetime` values.
- **Verification is by direct query as `prope_migrate`, not through the application session.** The lock file's security test plan requires exactly this: "retention delete verified by direct query rather than through an API that could be filtering". Under row-level security, an application-session query for the wrong workspace returns zero rows whether or not the delete worked, so a test checking emptiness through `prope_app` in the wrong tenant proves nothing.

## Flagged assumptions

- **CL-08 edge probe row: UNRESOLVED, surfaced not dropped.** The deterministic edge probe classified CL-08 as `unclassified` and it is carried here as a flagged assumption rather than auto-resolved with a backstop. The two open dimensions are: **(a) A6 — chunk size.** 5,000 rows per chunk is a research judgement, not a repo decision. The stated target is one day's expired bodies removed within 10 minutes at up to 500,000 body rows in a batch; at 5,000 that is 100 chunks, which has ample headroom, but the number is tunable and unvalidated at real scale. **(b) OQ-C — cross-tenant enumeration.** CL-08's requirement text says "call bodies past their retention window are deleted" without saying *for which workspaces*; Phase 1 answers it for one workspace at a time and leaves the sweep that visits all of them unbuilt, because the mechanism ADR-0051 designates does not exist yet. Both are recorded here so the gap is visible rather than assumed closed.
- **A7 — `FOR UPDATE SKIP LOCKED` in the chunk selection** is a safety improvement (the job becomes safe to run concurrently with itself and with the writer), not a requirement. Low risk either way.
- **A8 — a chunked delete returns space to the table's free list, not to the disk.** A-132 states and accepts this, with a disk-usage alert beside the oldest-body gauge in a later phase. Do not "fix" it with a full vacuum — that takes an exclusive lock on the largest table in the system.

**One production signature carries a test-facing seam, deliberately.** `delete_expired_bodies` takes
an optional keyword-only `on_chunk` callback, defaulting to `None`. It is awaited after each chunk's
transaction commits and before the next one opens. With the default the production call path is
byte-for-byte the loop it would otherwise be — no callback, no branch taken, no cost. It exists
because OQ-D's adopted reading (one transaction per chunk) is **only** observable from inside a
running multi-chunk loop: once the call has returned, a per-chunk implementation and a loop-wide one
are indistinguishable, since both must have committed to have persisted anything. The alternative
considered was a lock-and-observe test — hold a row in chunk 2 with a second connection's row lock,
start an unbounded run in a task, observe from a third — which touches no production signature but
needs concurrency choreography and a timeout guard so a bug hangs the suite instead of failing it.
The callback is chosen because it is deterministic under `pytest-asyncio`, needs no timeout, and
fails loudly rather than hanging when the implementation is wrong.

**No new tables, columns, constraints, policies, grants, migrations, routes, env vars, or database
functions.** In particular: no scheduler, no cross-tenant enumerator, and no `SECURITY DEFINER`
function — the sanctioned project-wide set stays at four.

    locator — never the body columns — so the one statement in the MVP that touches this table cannot

    `async def delete_expired_bodies(sessionmaker, workspace_id, *, now, chunk_size=DEFAULT_CHUNK_SIZE, max_chunks=None, on_chunk=None) -> int`
    loops: each iteration opens its **own** `workspace_transaction(sessionmaker, workspace_id)`,
    executes one chunk, commits, and accumulates the affected row count. It stops when a chunk affects
    fewer rows than `chunk_size`, or when `max_chunks` iterations have run. `DEFAULT_CHUNK_SIZE` is
    5,000; add a comment recording that this is a tunable judgement against the stated target of one
    day's expired bodies — up to 500,000 rows — removed within ten minutes, which is 100 chunks at
    that size.

    One transaction per chunk is the adopted reading of ADR-0040 (OQ-D above): every transaction still
    covers exactly one workspace and carries its own tenant context, and none is long-lived. Do not
    hold one transaction across the whole loop.

    **`on_chunk` — the seam that makes the previous paragraph checkable.** It is keyword-only and
    defaults to `None`. When given, it is an async callable awaited as
    `await on_chunk(deleted_in_chunk, deleted_total)` **after** that chunk's transaction has committed
    and **before** the next one is opened — that placement is the whole point, so await it outside any
    open transaction and never inside the `workspace_transaction` block. When it is `None`, take the
    branch that skips it entirely: the production path supplies no callback and must behave exactly as
    it would without the parameter. Do not use `on_chunk` for anything in production code, do not
    default it to a logger, and do not let it swallow exceptions — a callback that raises should
    propagate, because in the test it is carrying an assertion.

    Ship **no scheduler and no workspace enumerator**. This function is called with one workspace id.
    The `worker` process that would host a timer arrives in Phase 2, and the cross-tenant enumerator
    ADR-0051 designates lives in a schema that does not exist until Phase 7 (OQ-C). Do not create a
    database function of any kind to work around it.

    Do not add a full-rewrite reclamation step. A chunked delete returns space to the table's free
    list rather than to the disk; A-132 states and accepts that, and the full-rewrite form takes an
    exclusive lock on the largest table in the system.

    **`tests/integration/test_body_retention_delete.py`** — seed through `write_records` with
    tz-aware `created_at` values so the `expires_at` stamps are produced by the real write path, then
    call `delete_expired_bodies` with an explicit cut-off. Assertions are made **through the

    **One test proves per-chunk transactionality behaviourally, and it must observe the loop while the
    loop is still running.** This is the assertion that actually establishes OQ-D's adopted reading,
    and it is the only thing in the phase that does. Get its shape right or it proves nothing:

    **Why the obvious version is worthless.** Calling with `max_chunks=1` and then checking from a
    fresh connection that 7 of 12 bodies remain does **not** discriminate the two implementations. With
    `max_chunks=1` there is exactly one chunk, and a loop-wide single transaction must also commit
    before returning or nothing would persist at all — so it leaves the same 7 rows for the same fresh
    connection to find. Any observation taken after the call has returned is blind to where the
    transaction boundaries were. Do not write the test that way.

    **The shape to write.** Seed 12 expired bodies. Define an async callback that, each time it is
    invoked, obtains a **fresh** `prope_migrate` connection — a new connection from `migrate_engine`,
    not the one used for seeding and not anything the delete loop holds — runs
    `SELECT count(*) FROM ledger.call_body` for the workspace, and appends the number to a list
    captured in the test. Then call
    `delete_expired_bodies(..., chunk_size=5, on_chunk=<that callback>)` **unbounded** — no
    `max_chunks` — and assert:
    (1) the call returns 12 and terminates on the short third chunk;
    (2) the callback fired 3 times;
    (3) the recorded list is exactly `[7, 2, 0]`.
    Element 0 is the load-bearing one: 7 survivors were visible to an outside connection at a moment
    when chunks 2 and 3 had not yet run, so chunk 1's transaction had already committed. A loop-wide
    single transaction records `[12, 12, 12]` instead — its deletions are invisible to any other
    connection until the whole loop commits — and it fails rather than hangs, because a plain count on
    that other connection takes no locks and does not wait on uncommitted deletes.
    (4) Finally, assert on a fresh connection after the call that 0 remain, so the mid-run observations
    are anchored to a real completed delete.
    Add one more test asserting the default path is unaffected: the same seed, the same unbounded
    `chunk_size=5` call with **no** `on_chunk` argument, still returns 12 and still empties the table.
    Name the discriminating test so `-k per_chunk` selects it, and this one so `-k default_path` does.
