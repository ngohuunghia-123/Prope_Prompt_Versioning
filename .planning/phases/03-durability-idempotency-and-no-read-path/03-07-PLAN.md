<objective>
Plan `03-06` executed two honest full-length load runs and **halted phase 3 on a measured finding**:
`performance_requirements`' *"writer drain throughput >= 500 records/sec sustained"* is not met.
**212 records/sec** (3,500 rows in 16.53 s) and **189 records/sec** (3,359 rows in 17.79 s) end to
end across the recovery from the 60 s stall; **494 records/sec** for `write_records` in isolation
through the same pooled sessionmaker. Re-measured on this host at the start of this plan, against
unchanged code: **469 records/sec** isolated, **1.47 ms** per `resolve_price`, and **4,013
records/sec** for the same 500 records with `usage_status = unknown` — which is the same finding
reproduced a third time and localises it exactly.

**It is an N+1 read inside the one write path in the system.** `write_records`' pass-1 loop calls
`resolve_price` once per draft whose `usage_status` is `reported`, and issues the query whether or
not a price row exists — so an unpriced workspace pays the same. Roughly **70% of a priced window's
cost is that one SELECT per record**.

**D-280 — one statement per batch, keyed on the pair and never on the instant.** `write_records`
collects the batch's distinct `(provider_config_id, upstream_model)` pairs, loads every price row for
those pairs in **one** statement, and resolves each record in Python **against that record's own
`created_at`**. `PRICE_ROWS_FOR_KEYS` joins `ledger.price_table` against
`unnest(:provider_config_ids, :upstream_models)`, which is pairwise — so M keys are M index lookups
inside **one round trip** rather than M round trips, and the access path is still
`uq_price_table_workspace_id`'s `(workspace_id, provider_config_id, upstream_model, effective_from)`.

*Rejected:* **one statement per distinct pair** (M round trips). It satisfies the same
*"a function of M and not of N"* property and is simpler to write, and it is refused because M is
unbounded — a drain window is 500 records and nothing says they share a model, so the worst case is
exactly the N+1 this plan exists to remove. *Rejected, and named because it is the obvious first
attempt:* **a memo keyed on `(pair, created_at)`**. All 30,000 drafts in the load run share the
fixture calendar's `day(5)`, so an instant-keyed cache would report a perfect number here and buy
**nothing** in production, where every record has a distinct timestamp. That is a test-passing device
and not a fix. **Reversibility: cheap** — one statement and one call site.

**D-281 — effective dating moves from SQL to Python, and the two must be provably the same rule.**
`PRICE_IN_FORCE`'s `WHERE effective_from <= :at ORDER BY effective_from DESC LIMIT 1` becomes
`bisect_right(rows, at, key=effective_from) - 1` over that pair's rows in ascending `effective_from`
order. The interval stays half-open `[effective_from, next effective_from)`, so a call landing
exactly on an `effective_from` is priced at the **new** row; ties are impossible rather than broken,
because `uq_price_table_workspace_id` refuses a second row for the same key and instant. **The
supersession range is still derived and never stored** — here by position in an ordered list, in
`api.PRICE_ROWS` by `lead(effective_from)` — because a stored `effective_to` would need the `UPDATE`
on `ledger.price_table` that A-102 and T-006 forbid. **Reversibility: cheap.**

**D-282 — the whole history is fetched per key, with no upper bound on `effective_from`.**
*Rejected:* bounding the fetch by the batch's maximum `created_at`. It is a correct optimisation and
it puts an instant back into the query, one refactor away from the memo D-280 just refused; and
`ledger.price_table` holds one row per price change, so the rows it would save are a handful.
**Reversibility: cheap.**

**D-283 — `resolve_price` and `PRICE_IN_FORCE` survive unchanged, and the drift they create is closed
by an assertion rather than by a claim.** There are now two implementations of one rule: the SQL one
(`resolve_price`, used by `repricing.reprice_unpriced` and by CL-03's own unit tests) and the Python
one (`PriceBook.price_at`, used by the writer). *Rejected:* collapsing them by making `resolve_price`
delegate to the book. It is the tidier shape and it is refused for two concrete reasons — it would
change `repricing`'s statement in a plan whose remit is the writer's N+1, and `PRICE_IN_FORCE` is
named in prose in `api.py` (twice), `schemas.py` and `test_management_routes.py` as *the* statement of
the half-open interval, so retiring it edits four files' arguments to move one function.
**What is shipped instead is stronger than "there is only one implementation": a test that runs both
resolvers over the same rows at the same instants — including one microsecond either side of an
`effective_from` — and asserts they return the same row.** Two implementations proven equal beat one
implementation assumed correct. **Reversibility: cheap**, and the collapse stays available; the
delete-together instruction is written at both sites.

**D-284 — the price book is loaded BEFORE pass 1's loop, and that is a correctness improvement as
well as a speed one.** Under `READ COMMITTED` each statement takes its own snapshot, so today a price
row committed part-way through a batch can be seen by record 400 and not by record 1 — one batch,
two views of the price table. One statement gives the whole batch **one snapshot**. The cost, stated
rather than discovered: a batch that will be refused for an `eval` record carrying a body or a
`gateway` record with no `version_id` now issues one SELECT before it raises. It is inside the
caller's transaction, it writes nothing, and it buys the snapshot property above.
**Reversibility: cheap.**

**D-285 — an empty key set issues no statement at all.** A batch in which every record has
`usage_status = unknown` — the shape the load run's body seeding uses — must still cost **zero**
price reads, which is what today's `if usage_status is UNKNOWN` branch buys by never asking. The
guard is in `load_price_book` rather than at the call site, so all three callers get it.
**Reversibility: free.**

**D-286 through D-289 are unused.** This plan's allocated range is D-280…D-289 and it consumed six.

**What this plan does not do.** It does not touch `drain.py`, `fallback.py` or `seams.py` — there is
one implementation of the write path on purpose and all three reach it through `write_records`. It
does not lower the 500 records/sec figure, weaken the assertion, or mark the test. If the batched
resolution still does not reach 500, that is reported as `OQ-085` with the measurements, and the
assertion stays red.
</objective>

**`PRICE_ROWS_FOR_KEYS`**, a plain string constant `text()` — the gate in
`tests/architecture/test_no_sql_interpolation.py` requires it and the right answer to that gate is a
statement that needs no composition:

```sql
SELECT p.provider_config_id, p.upstream_model, p.price_row_id,
       p.input_price_per_1k, p.output_price_per_1k, p.currency, p.effective_from
FROM   unnest(CAST(:provider_config_ids AS text[]), CAST(:upstream_models AS text[]))
       AS wanted(provider_config_id, upstream_model)
JOIN   ledger.price_table AS p
  ON   p.workspace_id       = :workspace_id
  AND  p.provider_config_id = wanted.provider_config_id
  AND  p.upstream_model     = wanted.upstream_model
ORDER  BY p.provider_config_id, p.upstream_model, p.effective_from
```

Its `#:` block must argue five things, in `PRICE_ROWS`' register:

- **Why `unnest` of two arrays and not `= ANY` twice.** Two independent `ANY`s are a cross product:
  they would match provider A's config with provider B's model. `unnest(a, b)` is **pairwise**, which
  is the only shape that expresses "these exact pairs". The two arrays are built together and are
  therefore the same length; unnest pads the shorter one with NULLs, which is a silent wrong answer
  and is why they are built in one place.
- **The access path, by name.** `uq_price_table_workspace_id` is
  `(workspace_id, provider_config_id, upstream_model, effective_from)` and `0003`'s own comment says
  the column order **is** the lookup order. This is a nested loop over the unnested keys with one
  index scan each: M index lookups in **one** round trip.
- **`ORDER BY ... effective_from` is load-bearing and not cosmetic.** The Python side bisects the
  per-key list and assumes it ascends. Say so, so nobody removes the clause as noise.
- **`workspace_id` is in the join alongside the tenant policy rather than instead of it** — the
  posture `PRICE_IN_FORCE` and `PRICE_ROWS` already take.
- **No upper bound on `effective_from` (D-282)**, with the reason: bounding by the batch's maximum
  `created_at` would put an instant back into the query.

**`PriceBook`**, a frozen dataclass wrapping `dict[tuple[str, str], tuple[PriceRow, ...]]` with one
method:

```python
def price_at(self, *, provider_config_id, upstream_model, at) -> PriceRow | None
```

Its docstring is where D-281 lives. It must say, in the module's voice, that this is
`PRICE_IN_FORCE`'s rule expressed over a list rather than a second rule: `bisect_right(rows, at,
key=...) - 1` selects the last row whose `effective_from` is `<= at`, which is exactly
`effective_from <= :at ORDER BY effective_from DESC LIMIT 1`. It must repeat the three properties the
module docstring already owns rather than assume them — half-open interval, ties made impossible by
`uq_price_table_workspace_id` rather than broken, and `None` meaning *unpriced* and never a zero —
and it must carry **the delete-together instruction**: this and `resolve_price` are two
implementations of one rule, `test_the_batch_resolver_and_resolve_price_agree` is what keeps them
equal, and a change to either belongs in the same commit as a change to that test.

**`load_price_book(session, *, workspace_id, keys)`** returns a `PriceBook`.

- Empty `keys` returns `PriceBook({})` **without executing anything** (D-285), with the reason at the
  guard: a batch of `usage_status = unknown` records must still cost zero price reads.
- `keys` is de-duplicated and **sorted** before the arrays are built — a duplicate pair would
  multiply the rows returned, and sorting makes the parameter order reproducible across runs.
- Rows are grouped into ascending-`effective_from` tuples per key, taking the SQL order rather than
  re-sorting.
- Nothing here reads a clock. Say it, because the module docstring's first claim is that nothing in
  it does.
