<objective>
Close CL-12 by measuring it, and be honest about which half of it runs.

CL-12's claim is *"enqueuing a call record stays off the caller's response path at p95 under 1 ms
under sustained load, with no metadata dropped"*, and the lock file's stated `condition` is **the
queue at 80% depth**. ROADMAP SC5 adds the duration: 50 rps sustained for ten minutes.

**Nothing in this repository times anything today.** There is no analog to copy, so this plan's real
content is the sampling arithmetic and the shape of the span, both written from scratch and both
argued rather than picked.

**The claim splits, and the split is the decision.** Thirty thousand records over ten minutes against
a suite that currently runs in about 151 seconds is a suite nobody runs — and a suite nobody runs is a
gate that stops gating. So:

1. **A CI-resident proxy that runs by default**, asserting the same two properties — the p95 and
   `metadata_dropped_total == 0` — at 80% handoff depth, in-process. It costs roughly 900 `enqueue()`
   calls, asks for **no broker fixture and no AMQP round trip**, and touches no database. **It does
   not, however, avoid a container**, and the plan says so rather than claiming otherwise:
   `tests/conftest.py:170-178` declares `truncate_ledger` as `autouse=True` depending on
   `migrate_engine` → `postgres_container`, unconditionally, so **every test collected under `tests/`
   starts PostgreSQL**, including anything under a new `tests/load/`. The suite has already paid that
   cost by the time this test runs. See Task 1 for what is asserted instead.
2. **The full-fat 50 rps × 10 min run, marked and skipped**, with a documented invocation, so the
   stated criterion exists as a test and is honest about when it runs.

**Why the proxy is a fair proxy, stated so the verifier can check the reasoning rather than accept
it.** `enqueue()` is deliberately **synchronous** — *"there is nothing to await, and a coroutine would
invite a caller to await something"* — so the caller's span is exactly the function call and nothing
around it. The span's cost is the same at record 1 and at record 30,000 because nothing in it scales
with elapsed time: one byte-size computation, one clock read, one `put_nowait`, two counter increments
and one histogram observation. What ten minutes of arrival adds is **buffer depth**, and the proxy
buys that directly by pre-filling to 80% — which is the lock file's own stated condition, and the only
term in the span that depth touches is `put_nowait`'s bookkeeping on a bounded `asyncio.Queue`. The
one thing the proxy cannot show is drift over time, and that is precisely what the marked run is for.
**Say that at the test**, because "the fast test proves the slow test" is a claim, and an unargued one
would be the wrong kind of shortcut.

**What the CI-resident proxy does not do.** It does not measure the drain, the fallback, or
`write_lag_seconds` — those are the *system's* lag, and folding them into a caller-span assertion would
make a failure unattributable, which is the opposite of what a performance assertion is for. CL-12's
**p95 clause** is about the caller's span only, and the proxy measures exactly that.

**But CL-12's acceptance criterion of record is AC-12, and AC-12 has three clauses, not two.** Its
text: *"Given 50 rps sustained for 10 minutes, when enqueue is measured in the caller's process, then
p95 stays under 1 ms, **write lag p95 stays under 2 s**, and no metadata is dropped."* ROADMAP SC5
omits the middle clause, and `REQUIREMENTS.md` maps CL-12 → AC-12; **AC-12 is not in PITFALLS §2's
restatement table**, so there is no exemption to claim and its text stands as written. Milestone M1
closes with this phase, so a clause not asserted here is asserted by nobody. The instrumentation
already exists — plan 03-01 chose `2.0` as a `WRITE_LAG_BUCKETS` edge *specifically* so this quantile
is computable — so what is missing is only the assertion, and **Task 2's full-fat run is where it
goes**, because that is the only test in this phase where enqueue, publish, drain and commit all run
under sustained arrival.

**Task 2 also picks up three lock-file clauses that no other plan in this phase owns**, for the same
reason — M1 closes here and an unowned clause becomes invisible the moment the phase is marked done:
`test_plan.load`'s *"writer drain >= 500/sec"* and *"stall the writer for 60 s and assert the backlog
clears rather than growing"*, and `test_plan.chaos`' fifth clause, *"run the deletion job concurrently
with peak writes and assert the writer's lag stays inside its target."* All three are provocations
**inside** the one paced run rather than three new ten-minute runs; see Task 2 for the schedule.

**Standing environment facts, and two of them are load-bearing for a timing test.**

- **Python 3.13 fixed the Windows clock.** `time.monotonic()` on Windows now uses
  `QueryPerformanceCounter` for a 1 µs resolution instead of `GetTickCount64`'s 15.6 ms, and
  `time.get_clock_info("perf_counter")` reports `resolution=1e-07` on this host. **The classic advice
  "never use a Python clock for sub-millisecond timing on Windows" is obsolete on the pinned
  interpreter.** `perf_counter_ns` is still the right call, but the reason is unambiguity rather than
  resolution, and the test should say so — otherwise the next reader either distrusts the measurement
  or copies the obsolete workaround.
- `uv run ruff format --check` fails repo-wide (Broken Window #1) and is **not** this plan's to fix;
  `uv run ruff check src/ tests/ alembic/` is the gate.
- `docker` is not on the default bash PATH. The CI-resident proxy needs no daemon at all; the
  full-fat run does.

**No new dependency.** Do not add `pytest-benchmark`, `pytest-timeout`, or any timing library: the
measurement is an order statistic over a list of integers, `statistics` is in the standard library,
and a benchmark plugin would bring its own calibration, its own warm-up and its own opinion about what
a p95 is — three things this assertion needs to own.

**The two constants, derived and argued:**

```python
#: The lock file's stated condition is "queue at 80% depth", so this is derived
#: from HANDOFF_MAXSIZE rather than written as 410 — a literal here is a number
#: that stops meaning 80% the day the bound changes.
HANDOFF_80_PERCENT = int(HANDOFF_MAXSIZE * 0.8)

#: 500, because a p95 is the (0.95N)th order statistic. At N=500 there are 25
#: observations above the p95, so one scheduling hiccup moves the estimate by a
#: rank rather than defining it. At N=100 there are five, and a single GC pause
#: is a fifth of the tail. Above ~1000 the estimate stops improving and the test
#: starts costing more than it proves.
SAMPLES = 500
```

**The measurement, and every line of it is a decision:**

1. `reset_handoff()`, then `enqueue()` `HANDOFF_80_PERCENT` drafts to reach the stated depth. No
   publisher runs, which is what makes 80% depth free to arrange and is why this test needs no broker.
2. Build **all** the timed drafts **before** the loop. A draft constructed inside the timed region
   would put `CallRecordDraft.__init__` and a ULID generation inside a span that is supposed to be
   `enqueue()` alone.
3. `start = time.perf_counter_ns()`, the bare `enqueue(draft)`, `samples.append(time.perf_counter_ns()
   - start)`. Nothing else inside the span — no assertion, no append of anything but the delta, no
   counter read. **Then, immediately after the append and therefore outside the span, one
   `handoff().get_nowait()`.** This is not optional and it is not tidiness: `HANDOFF_MAXSIZE` is 512
   and `HANDOFF_80_PERCENT` is 409, so 409 pre-filled plus `SAMPLES = 500` timed calls with nothing
   draining is **909 records into a 512-slot bounded queue**. The 103rd timed call fills it and calls
   104–500 take `enqueue()`'s `except asyncio.QueueFull` branch (`enqueue.py:120-129`), which
   increments `metadata_dropped_total` and `enqueued_total{outcome="dropped"}` — making this task's own
   zero-drop assertion **arithmetically unreachable**, while the p95 assertion still passes because the
   `QueueFull` path is cheap. The failure would arrive as a bare counter mismatch with no diagnosis
   attached, and the obvious "fix" — deleting the drop assertion — deletes half of CL-12. The
   one-line consumer holds the depth at exactly 409 for the whole run, which is what *"at 80% depth"*
   actually means. (`task_done()` is not needed: nothing joins this queue.) **The alternative —
   `SAMPLES = HANDOFF_MAXSIZE - HANDOFF_80_PERCENT` = 103 — is refused** by the order-statistic
   argument the `SAMPLES` constant already makes: at N≈100 a single GC pause is a fifth of the tail.
4. Sort, take `samples[int(0.95 * len(samples))]`, assert it is under `1_000_000` ns, and put the
   observed value in the assertion message in milliseconds so a failure reports the number rather than
   just failing.
5. Assert `metadata_dropped_total` moved by **zero** across the whole run, as a **delta** taken before
   and after — `prometheus_client`'s default `REGISTRY` is process-global and the suite shares one
   process, so an absolute value passes when the test runs alone and fails when it runs after its
   neighbour, which is the worst failure shape a suite can have. **Do not add a registry-reset
   fixture** to make absolutes work: it would hide every counter's cross-test behaviour, which is the
   one thing these counters exist to make visible.

**Add a second, separate test for the byte cap's cost**, and keep it separate on purpose:
`test_a_body_at_the_cap_still_fits_the_budget`, identical in shape — **including the
`get_nowait()`-per-sample discipline above, which every timed loop in this file obeys without
exception** — but with every timed draft carrying a request/response pair at exactly
`MAX_BODY_BYTES`. `enqueue()`'s `str.encode()` at the cap is the
largest single term in the span — tens of microseconds against a 1 ms budget — and folding it into the
first test would make a failure ambiguous between "the buffer got slower" and "the encode got
slower". Two tests, two subjects, and **a failure that names which cost moved** is the whole reason
for the split. Note in its docstring that this test is why `ENQUEUE_DURATION_BUCKETS` has edges below
100 µs at all.

**Write the honest caveats at the module, because a timing assertion in CI is a flake waiting to be
argued about:**

- It measures the machine it runs on. A loaded CI runner can fail it, and the correct response is to
  re-run once and then investigate, **not** to raise the threshold — the threshold is the lock file's
  and this test does not own it.
- `time.perf_counter_ns` is chosen for unambiguity, not for resolution: on Python 3.13 both
  `perf_counter` and `monotonic` report a 1e-07 resolution on this host via `QueryPerformanceCounter`,
  so the classic Windows objection is obsolete on the pinned interpreter. Say it, so the next reader
  neither distrusts the measurement nor reintroduces a workaround for a problem that no longer exists.
- No warm-up iterations and no discarded first sample. The first `enqueue()` in a process pays for
  lazily creating the handoff and for `structlog`'s first bind, and **both are real costs a real
  caller pays**; discarding them would measure a system that has already been running, which is not
  what the gateway's first request meets. The pre-fill loop happens to absorb them anyway, and that is
  stated rather than relied on silently.
- The proxy runs **by default and carries no marker**. It costs roughly 900 `enqueue()` calls, asks
  for no broker fixture and no database access of its own, and **SC5 proven by a test that never

  (`conftest.py:213-237`) is the fixture that opts in by fixture graph; `truncate_ledger` does not

  declares no `tests/conftest.py` edit for exactly that reason.

**Assertion one: the histogram the code publishes agrees with the list the test measured.**
`enqueue()` observes `enqueue_duration_seconds` on every call (plan 03-01), and the proxy times the
same calls independently. After the proxy's run, read the histogram's bucket counts from the registry

  span — the classic error, and one that would otherwise be invisible forever — fails here rather than
  in a dashboard nobody reads.
- It is why `0.001` is a **bucket edge** and not an interior value.
  `histogram_quantile` interpolates linearly *inside* the bucket containing the quantile, so a target
  that fell in a bucket's interior could only be answered to that bucket's width. The default buckets
  start at 5 ms — five times **above** this target — so every observation would land in the first
  bucket and the p95 would read as "somewhere under 5 ms" forever. **A metric that cannot fail its own
  target is not a measurement**, and this assertion is what proves the replacement edges can.
