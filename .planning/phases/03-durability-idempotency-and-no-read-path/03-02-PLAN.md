<objective>
Close CL-02, and close it against the thing it is actually about.

**A duplicate in `ledger.call_record` is refused by the primary key with or without this plan.**
`call_id` is the table's whole primary key, so a second row was already impossible. What a redelivery
corrupts is `ledger.workspace_spend` — the monthly aggregate maintained inside the writer's own
transaction (A-103) so that `check_spend_ceiling` reads one row instead of aggregating the largest
table in the system. That aggregate is incremented today from the rows *offered*, not from the rows
that *inserted*. **A plan that stops at `ON CONFLICT DO NOTHING` passes a "the record appears once"
test and still fails CL-02.**

So the statement moves to `INSERT … ON CONFLICT (call_id) DO NOTHING … RETURNING call_id`, and
`write_records`' control flow inverts: insert first, read the returned `call_id` set, then build the
month buckets and the body rows from that set alone. `RETURNING` over `DO NOTHING` is the only shape
that says which rows were new, and that is the whole design.

This plan also carries three consequences that fall out of the same change and belong nowhere else:

- **The two counters the `LedgerDuplicateCallIds` alert reads together.**
  `duplicate_call_id_total` from the offered/returned gap inside `write_records` — the database's own
  view — and `redelivered_total` from `AbstractIncomingMessage.redelivered` in the drain — the
  broker's own view. Deliberately not one counter, because the alert's stated method is *"duplicates
  that track redeliveries are the broker working, and duplicates that exceed them are a caller
  generating ids badly"*, and that comparison is impossible if either side is derived from the other.
- **`metadata_dropped_total` stops counting dead-letters (D-30).** After plan 03-01's fallback, that
  counter means a record exists **nowhere**, and a dead-lettered record is in
  `prope.call_record.dlq` with a 30-day TTL and an alert on any non-zero depth. Two increments in
  `drain.py` currently make it mean something else. This is a **removal**, and removals are the ones
  that get skipped.
- **`missing_version_id_total` gains the increment site it does not have.** Today a `source=gateway`
  draft with a NULL `version_id` is refused by `ck_call_record_gateway_calls_carry_version_id` as an
  `IntegrityError`, which dead-letters under a constraint name rather than under this counter's name.
  The counter's whole job is to be zero, and a counter that can never move is not a control.

**Deliberate gaps, named with the plan that closes each.** `prope_call_ledger_write_lag_seconds` is
observed on the drain's committed path here, and on the fallback's path in plan 03-01, but **nothing
scrapes either** until plan 03-04 ships `/metrics` on `app` — and `worker`'s registry is not that
process's, which is `OQ-026`'s subject and plan 03-04's to raise. The `LedgerDuplicateCallIds` alert
rule itself is plan 03-04's.

**CL-11's disposition, stated here rather than left silent.** `REQUIREMENTS.md` files CL-11 under
Phase 1 / Pending while both clauses are built and green: clause 1 (`unknown` tokens are NULL, never
zero) by `tests/unit/test_unknown_usage_never_zero.py`, clause 2 (the unknown count reported alongside
the total) by `tests/integration/test_run_totals.py`, where `seams.py:569` records that it built the
function and deliberately claimed no requirement. **This plan does not split the id and does not remap

Restructure `write_records` around a statement that reports which rows were new.

**The statement (D-33).** Replace `INSERT_CALL_RECORD`'s `text()` construct with a Core one, because
**a `text()` executemany does not return per-row results** and `models.py` already declares the table:

```python
from sqlalchemy.dialects.postgresql import insert as pg_insert
from prope.call_ledger import models

#: D-33. `sort_by_parameter_order` is DELIBERATELY ABSENT, and this comment is
#: the reason, because the absence of an argument is invisible and somebody
#: adding ordering "for determinism" would be making a reasonable-looking change
#: that fails only under load. With it, SQLAlchemy selects `call_id` as a
#: CLIENT-SIDE SENTINEL and the driver then compares the sentinel-keyed result
#: length against the batch length — which ON CONFLICT DO NOTHING guarantees will
#: differ the first time a duplicate arrives. That raises
#: `InvalidRequestError: Sentinel-keyed result set did not produce correct number
#: of rows`, which is CL-02's OWN scenario turned into an exception, on the path
#: whose whole job is to survive it.
#:
#: No ordering is needed because the returned ids are used as a SET: the month
#: buckets are built from membership, never from positional correspondence. That
#: is why D-33 says RETURNING call_id and not RETURNING an index.
UPSERT_CALL_RECORD = (
    pg_insert(models.call_record)
    .on_conflict_do_nothing(index_elements=["call_id"])
    .returning(models.call_record.c.call_id)
)
```

and the same shape for `UPSERT_CALL_BODY`, without `returning`, with its own
`on_conflict_do_nothing(index_elements=["call_id"])`.

**`DO NOTHING`, never `DO UPDATE`, and there are four independent reasons — write all four at the
statement.** (1) ADR-0019 prices once at write time and never revises; `DO UPDATE` would re-price an
existing record from a redelivered envelope, which is the one thing effective dating exists to
prevent. (2) `prope_app` holds no `UPDATE` on `ledger.call_body`, and PostgreSQL requires `UPDATE`
privilege for `ON CONFLICT DO UPDATE` — so `DO UPDATE` on one table and `DO NOTHING` on the other
would put two idempotency semantics inside one function. (3) `RETURNING` over `DO NOTHING` is the only
thing that says which rows were new, and CL-02's claim is about `workspace_spend`. (4) The pleasant
corollary, worth recording because a future tightening would break two things rather than one: the
`SELECT` grant on `call_body` that `0003_ledger_tables.py:246-252` justifies solely as *"required
alongside DELETE"* is **also** what makes `ON CONFLICT DO NOTHING` legal on that table, because all
forms of `ON CONFLICT` require `SELECT` on any column read.

**Do not copy the rowcount reading from the statement next door.** `UPSERT_WORKSPACE_SPEND`'s
`rowcount == 0` is a genuine refusal (WARN-2 / T-02-13) because its `ON CONFLICT … WHERE` makes a
conflicting row not match. Under `DO NOTHING`, a zero rowcount means *"already there"*, which is the
ordinary case. Say so at the new statement, because the neighbouring statement in the same file says
the opposite about its own rowcount and a reader will carry the reading across.

**Invert the loop (D-33, and Pitfall 2 is the trap in the inversion).** The per-draft loop currently
does two jobs — validating the batch and aggregating it — and only the second is about what inserted.
**Split them:**

- **Pass 1 stays where it is and keeps validating the WHOLE batch.** The two-workspace refusal, the
  eval-carries-a-body refusal, the zero-cost refusal, and — critically — the **mixed-currency
  refusal** all stay over every offered record. If the currency check moved with the buckets, a batch
  mixing two currencies whose second-currency records are all duplicates would be silently *accepted*
  where it is refused today, and `tests/integration/test_write_path.py:312` would either go red or,
  worse, stay green while the property quietly changed. A batch mixing currencies is a caller bug
  whether or not its rows are duplicates, and refusing it whole is this module's established posture.
  The cost of splitting is one extra iteration over a list already in memory.

  **Reproduce the check exactly, and the "exactly" is the whole instruction.** Today the refusal is
  not a separable validation — it is a side effect of the month-bucket accumulation at
  `writer.py:338-351`, so it is **keyed on `period_month(draft.created_at)` and only consults records
  that carry a cost** (`if cost is not None`). A batch holding a January USD record and a February VND
  record is **accepted today**, and a batch whose second currency arrives only on an unpriced record is
  accepted too. Pass 1 must therefore build its own `month -> currency` map for validation with the
  same keying and the same `cost is not None` guard. **The natural wrong move is a batch-wide
  `{r.currency for r in records}` set**, which silently tightens `write_records` and would fail
  nothing in the suite, because `test_a_batch_mixing_two_currencies_raises_rather_than_summing`
  (`test_write_path.py:312`) uses a single month. Write the keying in one sentence at the check.
- **Pass 2 is new.** Execute the upsert with the full `record_rows` list, collect
  `inserted = set((await session.execute(UPSERT_CALL_RECORD, record_rows)).scalars().all())`, then
  build the month buckets by iterating the per-draft results and skipping any `call_id` not in
  `inserted`. Only then run `UPSERT_WORKSPACE_SPEND`, whose statement and its `ON CONFLICT … WHERE`
  currency invariant are **completely unchanged** — only its inputs moved. The currency pre-read, the
  rowcount check and the WARN-2 race message all stay exactly as they are.

**D-34: a body follows its record.** Filter `body_rows` by the same `inserted` set before executing
`UPSERT_CALL_BODY`. The case this decides is the one ADR-0041 creates on purpose: a confirm that
**timed out** rather than being refused means the broker did get the message, plan 03-01's fallback
wrote the record without its body, and the broker later delivers the same record *with* its body.

*"`body_dropped_total` equals the number missing from `call_body`"*, because the drop was already
counted. **A counter that cannot be reconciled against the table is worse than a body that was already
declared best-effort (A-037).** Write that trade at the filter, including its cost stated plainly: a
body lost to a timed-out confirm is lost permanently, by decision.
