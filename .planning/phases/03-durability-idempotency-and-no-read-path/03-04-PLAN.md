**The finding this plan cannot solve and must not hide.** `prometheus_client`'s registry is **per
process**, and Prope runs two. `worker` serves no HTTP by D-17 — which is *derived from ADR-0028*
(*"`app` publishes and never consumes, `worker` consumes and never serves HTTP"*) rather than chosen
in discussion, and is therefore **not this phase's to reverse**. So after this plan:

- eight metrics exist only in `worker` — `written_total`, `write_lag_seconds`, `queue_depth`,
  `dlq_depth`, `redelivered_total`, `retention_deleted_total`, `oldest_body_age_seconds`, and
  `ceiling_check_total`;
- four more are incremented in **both** processes — `unpriced_total`, `unknown_usage_total`,
  `missing_version_id_total`, `duplicate_call_id_total` — so `app`'s copy is a **partial** count;
- and three of the six declared alerts — `LedgerWriteLagHigh`, `LedgerRetentionOverdue`,
  `LedgerDuplicateCallIds` — read metrics on that list.

Ship the instrumentation, ship `/metrics` on `app`, and raise **`OQ-026`** with that exact list
attached. **Do not solve it by opening a port on `worker`**: that reverses a decision derived from an
ADR, adds the surface T-02-15 registers, and `tests/integration/test_worker_jobs.py:459-478` would go
red on the import alone — which is the mechanical reason as well as the architectural one.

**And what the alert rules file is, precisely.** The deployment stack owns no milestone
(PITFALLS §4), so **no phase will ever wire this file into a running Prometheus.** That is not a
reason to leave the rules unwritten: the rules are where the thresholds and the *reasons* for them
live, and the lock file spells all six out including `LedgerRetentionOverdue`'s deliberate choice to
measure the data rather than the job. The test is what stops the file rotting — a rule referencing
`prope_call_ledger_spill_bytes` would parse fine and alert never. What the test can honestly claim is
bounded and must be stated at the test: it proves the file is well-formed YAML and that every metric
a rule names exists in the registry. It does **not** prove the file is a valid Prometheus rules file
and it does not prove a PromQL expression parses — that is `promtool check rules`, which needs a
binary this repository does not have.

Serve the registry, and serve it somewhere every assertion in the repository can see.

**A plain `APIRoute`, never `app.mount(make_asgi_app())`, and this is a decision rather than a
mounting detail.** `prometheus_client.make_asgi_app()` mounted with `app.mount(...)` produces a
Starlette `Mount`, which has neither `effective_route_contexts` nor a `dependant` — so
`assembled_routes()` skips it entirely and it appears in **neither** the route-table assertion nor
`app.openapi()`. **And nothing in the suite would notice**: the two count assertions compare a table
built *from* `assembled_routes` against `EXPECTED_ROUTES`, so a `Mount` is invisible to both, and
`test_the_router_and_the_health_routes_are_the_only_things_mounted` walks raw `app.routes` but asserts
only that `/docs`, `/redoc` and `/openapi.json` are absent. **A served path that every route
assertion in the repository is blind to is exactly the shape AC-10 exists to refuse.** Broken Window
#4 already records that a naive `app.routes` walk asserts vacuously; this is the same class of hole
one layer out — a route the *helper* cannot see rather than one the *test* cannot see. Mounting at
`/metrics` also serves `/metrics/` with a 307 in front of it, which is a second, smaller reason.

So:

```python
@application.get("/metrics", response_class=Response, include_in_schema=True)
async def metrics() -> Response:
    return Response(generate_latest(REGISTRY), media_type=CONTENT_TYPE_PLAIN_0_0_4)
```

with a docstring at `healthz`'s density carrying four things:

1. **Unversioned and sessionless, by A-045's rule and INT-030's neighbourhood.** A scraper holds no
   session, and call-ledger *cannot* check a permission — ADR-0018's forbidden edge means this module
   has nothing to authorise against. So the route sits beside `/healthz` and `/readyz`, declares no
   `ManagementAction`, and — following `readyz` — does **not** use the A-045 envelope, because a
   Prometheus exposition is not a management-API refusal.
2. **Why a route and not a mount**, in the words above, naming `assembled_routes` and the `dependant`
   check by line.
3. **`CONTENT_TYPE_PLAIN_0_0_4`, not `CONTENT_TYPE_LATEST`.** In `prometheus-client` 0.26.0
   `CONTENT_TYPE_LATEST` is `text/plain; version=1.0.0; charset=utf-8` while `generate_latest` emits
   the 0.0.4 text format — the library's own `choose_encoder` pairs this function with
   `CONTENT_TYPE_PLAIN_0_0_4` and reaches for the 1.0.0 label only when a client explicitly asked for
   it. Labelling the payload 1.0.0 would be a claim about the format the payload does not honour.
   Write this at the route so a later reader does not "modernise" the constant. Content negotiation
   via `choose_encoder` is available and is deliberately not used: negotiation is a feature nothing in
   this deployment asks for, and the one-line form is what the library itself defaults to.
4. **What is and is not readable here**, with the `OQ-026` list: eight metrics live only in `worker`,
   four more are partial, and three declared alerts read metrics on that list.

`include_in_schema=True` is load-bearing rather than incidental: excluding it would make the served
table and the OpenAPI schema disagree, which is the exact hole
`test_the_openapi_schema_agrees_with_the_route_table` says it exists to close.
