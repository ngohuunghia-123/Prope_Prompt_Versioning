<objective>
Two small, unrelated-looking changes that share one property: **each is a control that exists but
cannot currently do its job.**

**CL-07 first.** Phase 2 built the fail-open branch and said so at the code — *"the branch ships in
Phase 2; the CLAIM does not"* — and counted it on `prope_call_ledger_ceiling_failed_open_total`. That
counter is **not the declared metric.** The lock file declares
`prope_call_ledger_ceiling_check_total # labels: result = allowed | refused | failed_open`, which
counts **all three** branches, and today only one branch has an increment site at all. So the
requirement is not closed by renaming a constant: it is closed by giving `allowed` and `refused` the
increment sites they never had, which is the actual work, and by retiring the Phase 2 counter so one
number does not have two names.

Say the corollary out loud, because a verifier will read ROADMAP SC3's words *"increments the
failed-open counter"* and may reach for the Phase 2 constant: **a labelled counter is a counter.**
`ceiling_check_total{result="failed_open"}` is the failed-open counter, under the name the spec
declares.

**CR-01 second.** `schemas.py:394` declares `retention_days: int` with no upper bound, and
`api.py:720` evaluates `timedelta(days=payload.retention_days)` **before any statement exists**.
`OverflowError` subclasses `ArithmeticError`, which matches none of `classify_write_failure`'s
branches, so it takes the `PERMANENT` default and dead-letters. `02-VERIFICATION.md` raised it,
ORCHESTRATION §4 routed it here, and this is the cheap moment: the route is unreachable until Phase 7
fills the session seam, so the fix lands before its own exposure.

**This is the documented exception to "build database-first", and naming the exception is what keeps
the rule intact.** A `CHECK` cannot help with an exception raised in the client before a statement is
constructed. The lower bound stays where it is — at the engine, in
`ck_workspace_retention_window_is_positive` — and the asymmetry between the two bounds is written **at
the field**, so a later reader does not tidy one of them into the other's home.

**What this plan deliberately does not do.** It does not add an `ArithmeticError` branch to
`classify_write_failure`: that would treat a bad input as a write-classification problem two modules
away from where it was accepted, and it would soften a classifier whose `PERMANENT` default is
load-bearing (T-02-06). It does not ship a `/metrics` route — plan 03-04 owns exposition, so
`ceiling_check_total` is observable from tests and from nothing else when this plan lands, and the
`OQ-026` gap that keeps `worker`'s copy unscrapable is 03-04's to raise.
</objective>

Put the bound where the exception happens, and write down why it cannot go where every other bound in
this repository goes.

**`MAX_RETENTION_DAYS = 3650` as a module constant** beside `MAX_PAGE_LIMIT`, for the reason that
comment already gives: the tests assert the number, and a literal in a `Field` is a number a test
would have to restate. Then `retention_days: int = Field(le=MAX_RETENTION_DAYS)`.

**Argue the number, do not round it.** The bound's job is to keep an input from becoming an
unclassifiable exception, and among the values that do that, ten years is the largest that is still
recognisably a retention *policy*: longer than the pilot, longer than anything OQ-013 could plausibly
answer, and short enough that "never delete" — the one answer ADR-0018 and A-040 refuse — cannot be
spelled in this field. Write that at the constant in the tuning-constant voice, and note what the
bound does **not** do: it does not bound the stored column, so a window already longer than ten years
(there are none, and there is no path that could have created one) would be unaffected; it bounds what
a caller may set.

**Write the asymmetry at the field, immediately beside the paragraph that argues the lower bound's
absence, and do not contradict that paragraph.** `:384-390` is correct and stays: the lower bound is
`ck_workspace_retention_window_is_positive`'s at the engine, `set_retention_window` surfaces the
refusal rather than clamping, and re-checking it in pydantic would put one guarantee in two places.
The new paragraph says why the upper bound is **different in kind**: `api.py:720` evaluates
`timedelta(days=payload.retention_days)` **before any statement exists**, so there is no engine to
refuse it; `OverflowError` subclasses `ArithmeticError`, which matches none of
`classify_write_failure`'s branches and therefore takes the `PERMANENT` default and dead-letters; and
a `CHECK` cannot help with an exception raised in the client. **This is the documented exception to
"build database-first", and naming the exception is what keeps the rule intact.** End the paragraph
with the instruction that is the whole reason it is long: a later reader must not tidy one bound into
the other's home, because they are the same field's two bounds for two different reasons.

**Inherit `PageRequest`'s consequence verbatim: this is a `422`, not a clamp.** A request quietly
corrected into one the caller did not make leaves them believing it took effect. And **no new
`ErrorCode` member**: `ErrorCode` is a closed `StrEnum` and a `le=` violation renders as the existing
`VALIDATION_FAILED` through `install_error_envelope`'s `RequestValidationError` handler. Adding a
member would be a code the SPA's catalogue has never seen (ADR-0053), which renders as nothing at all
and does so silently.

**`tests/unit/test_retention_days_bound.py`** is the test that proves the bound does the job it was
added for, and it must assert the *reason* rather than only the *rule*. Three cases:

1. The boundary pair — `3650` validates, `3651` raises `ValidationError`.
2. **The property, not the number:** for the largest value the schema accepts, `timedelta(days=n)`
   constructs without raising; and for a value that would overflow (`10**9` is comfortably past
   `timedelta.max.days`), the schema raises `ValidationError` **first**, so `OverflowError` is
   unreachable through this model. Write that assertion as *"the exception this bound exists to
   prevent cannot be reached through this schema"*, because a test that only checks `le=3650` would
   still pass if somebody later changed the bound to `10**8` and reintroduced the bug.
3. The negative control that stops the test from being about pydantic: `0` and `-1` are **accepted**
   by the model, because the lower bound is the engine's. Assert that, and say in the test's docstring
   that if it ever starts failing, somebody has moved the lower bound into pydantic and the paragraph
   at the field should be deleted in the same change.

**`tests/integration/test_management_routes.py`** gets the route-level half: with the session
