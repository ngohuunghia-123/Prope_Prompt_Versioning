round-trip belongs to Phase 17 and must be located in the audit, not rebuilt here — this plan writes no
pricing code and no eleventh metric.

a route.** Plans 18-01 through 18-05 build the module's behaviour; this plan is the last thing that runs
and it either points at what they built or says, in writing, that nothing points at it yet. **The
load-bearing claim is that "asserted" never means "I read the code and it looked right" — it means a file
path and a function name that this plan or a prior one can name from the tree, checked against the tree

**`deploy/prometheus/rules/evaluation.rules.yml`** — one group named `evaluation`, six rules. Header
comment repeats the other five files': nothing in this roadmap wires this into a running Prometheus

**`EvalRunDurationHigh`** — ticket, `for: 30m`. Lock: *"run duration p95 > 120 s for 30 min; the stated
success metric is missing."* Expression:
`histogram_quantile(0.95, sum by (le) (rate(prope_evaluation_run_duration_seconds_bucket[30m]))) > 120`.
The description states, plainly, that the histogram is labelled `role, status` and the `sum by (le)`
aggregates across **both** — a candidate run and a baseline run, completed and interrupted alike, all
feed one p95 — because `docs/brainstorm/00_context.md#success` states the 120 s target per suite run
regardless of role, and A-054's concurrency-of-5 argument is about wall clock, not about which kind of
run it was. If 120 is not a declared bucket edge in `src/prope/evaluation/observability.py`, say so and
carry the interpolation caveat `RegistryResolveLatencyHigh` carries. Cross-reference D-329's own point:
`max_concurrent_runs = 2` exists partly for **measurement**, so this alert and A-063's restated purpose
are the same argument from two directions — five interleaved runs each record the whole submit's
duration and would all miss 120 s together, which is what `max_concurrent_runs` prevents.

**`EvalCaseErrorRateHigh`** — ticket, `for: 15m`. Lock: *"case error rate > 10% over 15 min; upstream or
configuration trouble."* Numerator `prope_evaluation_case_error_total` (labelled `error_code`, summed
across all values). Denominator: **verify against the real observability module** whether
`prope_evaluation_case_duration_seconds` is observed for every case regardless of outcome — including a
`regex` timeout, which D-335 records completes (with `outcome=error`) rather than hanging past its
1.0 s budget, and a dispatch failure after retries. If it is, the expression is
`sum(rate(prope_evaluation_case_error_total[15m])) / sum(rate(prope_evaluation_case_duration_seconds_count[15m])) > 0.10`
and the description states the denominator choice and why: none of the ten declared metrics is a bare
"cases attempted" counter, so the duration histogram's `_count` suffix — observed once per case whether
it passed, failed or errored — is what stands in for it. **If the tree disagrees** — the histogram is
only observed on success, say — do not force the expression; write the true denominator (which may be
`prope_evaluation_case_error_total` summed against itself over a wider window, or the true count if one
exists) and record the deviation from this plan's assumption in the SUMMARY.

**`EvalRunsInterrupted`** — ticket, `for: 0m`. Lock: *"`prope_evaluation_run_interrupted_total > 0` in
1 h"* — this is already `increase(...) > 0`-shaped in the lock's own words, unlike `RegistryUnfilteredQuery`
and `EvalModalityMismatch` below, so the expression is
`increase(prope_evaluation_run_interrupted_total[1h]) > 0` with **no deviation to declare**. The
description states why this is a ticket and not a page, the one severity decision this alert set makes
that a reader might expect to go the other way: a `worker` restart mid-run is an ordinary operational
event under ADR-0049's own words (*"if `worker` is down entirely nothing sweeps and nothing needs to"*),
the interrupted run's completed case results stay readable (AC-7), and a human re-runs with one click at
no data loss — the shape `LedgerMetadataDropped` and `LedgerRetentionOverdue` page for is *record exists
nowhere* or *policy commitment broken*, and neither is what this counter means. Cite D-325's dual-counter
equality (`prope_evaluation_run_interrupted_total` and `prope_evaluation_run_total{status="interrupted"}`
move together, from one site, after commit) as the reason a phantom increment cannot happen here without
also being visible on the lifecycle series.

**`EvalPricingStalled`** — ticket. Lock: *"completed runs with `priced_at` NULL older than 15 min."* This
is a SQL-shaped condition and none of the ten declared metrics exposes `priced_at` staleness — the same
shape `OQ-082` already named for the registry's `RegistryUnapprovedPointer`, and D-337's own text names
this as owed to the M6 audit rather than something this plan invents a metric for. Ship it the way
`OQ-082`'s "Option B, degenerate form" describes: an expression that parses and cannot fire —
`vector(0) > 1` — and a description carrying, in order: (1) the condition verbatim; (2) that ADR-0030
chose Prometheus and Grafana *and deliberately nothing else* — no `postgres_exporter`, no SQL-to-metric
bridge — so there is no honest expression; (3) that this module's `deployment_target` names exactly three
`worker` residents and none of them is a pricing-staleness sweep, so inventing an eleventh metric fed by
a fourth job is refused for the same reason `OQ-082`'s Option A was refused for the registry; (4) that
the actual mechanism a responder should trust instead is Phase 17's pricing round-trip, **named by file
and test function once Task 3 locates it — write a placeholder sentence here (`"see the M6 audit for the
located test"`) if Task 1 runs before Task 3 finds it, and fill in the real name before this plan's gate
runs**; (5) the sentence: *"raised as owed-and-unallocated per ORCHESTRATION §5 — this phase's OQ-096
through OQ-100 range is fully allocated to named decisions, and this gap is not one of them."* **Do not**
create a sixth OQ file for this — ORCHESTRATION §5 is explicit that a consumed range is not borrowed from
and an unallocated finding is recorded in the artifact's own docstring plus the SUMMARY, not given an id.

**`EvalQueueBacklog`** — ticket, `for: 15m`. Lock: *"`prope_evaluation_run_queue_depth > 10` for 15 min;
the global bound (A-063) is too tight for the number of suites in use, or a run is holding slots it never
releases."* Expression: `prope_evaluation_run_queue_depth > 10`. The description states D-328's
reinterpretation in full, the same shape `LedgerRetentionOverdue`'s description states its own two

a project-wide sum rather than a per-workspace backlog — and that this is a **correction to the plan

analogous case. State that the gauge is published by the **sweeper**, riding its own cross-tenant
