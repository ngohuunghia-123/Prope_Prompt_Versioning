<objective>
Make EVAL-06 true and prove it. **The whole plan turns on one line of Phase 17's handlers:
`refusal_for(visible=row is not None, allowed=allowed, action=...)` — where `row is not None` is
tenant visibility and nothing else, so a prompt in the actor's own workspace that they hold no grant
on is `visible=True` and answers `403`.** Phase 17 knew this and wrote it down: 17-01's Task 2 step 4
puts a `# WHY:` line at that argument naming this phase and EVAL-06, and 17-03's security module says
in its docstring that the gap is stated and not closed. This plan closes it, in the file that owns it,
and the repair is one local helper called by every route.

D-330 says the criterion is proved three ways and puts the weight on the third, because the first two
are free. A fabricated id and an id seeded in another workspace are **the same code path**: under
ADR-0045 the child read returns zero rows for both, so they are byte-identical without anyone
arranging it, and asserting them against each other proves the tenant policy Phase 16 already proves.
The third case — an id in the **same** workspace, on a private prompt with no grant — is the one where
the tenant predicate passes and a route can return `403`, return a run, or return output text. All
three are asserted equal as **serialized responses** — status, every header, and the raw body with each
body's own `request_id` masked and the three masked values proved different — never as three separate
status-code assertions, because three assertions that a status is `404` are satisfied by three
different `404` bodies and the body is where a leak lives.

The second clause of AC-6 — *"and no output text is returned"* — is D-331's sentinel scan and
deliberately **not** a field allow-list. A unique token goes into `case_result.output_content` and a
second into `eval_case.input_messages`; every route on the assembled surface is driven as the
non-grantee **and** as the grantee; and both tokens must be absent from every byte of every refusal,
from every captured log record on **both** paths, and from every metric label value — the last closing
A-046's metric clause in the same test rather than in a second one that drifts away from it. This is
Phase 15's `search_text` move one module over, chosen for the same stated reason: a field allow-list
passes the first time somebody adds a field, and `case_result.output_content` is the second copy of
provider content in Prope (T-011, A-137).

It also answers the mismatch that has been owed since 2026-08-09. `evaluation.lock.yml`'s
`security_requirements` say results are visible to *"exactly the actors who may read the prompt — same
filter, same repository-layer enforcement as the registry"*, which describes INT-002; `apis.consumes`
names only `may()`. BSP step 5 found it and recorded it as owed to step 6; step 6 did not fold it in;
Phase 17's D-311 routed it here as owed-and-unallocated. **The answer is no INT-002 consumption, and
the visibility oracle is that sentence read as a permission rather than as a filter:
`may(actor, prompt.read, prompt_subject)`.** Raised as `OQ-096` with the four consequences it ships
with, including one that is not free.

Deliberately left open, with the plan that closes each. The sweeper, its event and its counters are
**18-01's**; the executor's per-case re-check is **18-02's**; the two bounds, the two-claim-loop race
and AC-12's unset-tenant assertions on `eval_run` are **18-03's**; the regex blast radius and the
stdlib-`re` absence are **18-05's**, in this same wave and in disjoint files; the §9a clause-by-clause
walk is **18-06's**. This plan asserts nothing about the sweeper except that an `interrupted` run's
case results are as private as any other run's.

## D-330 as implemented — visibility is `may(prompt.read)`, and the lock file is what says so

**Chosen.** `src/prope/evaluation/api.py` gains one local helper, and every route calls it:

```python
async def _refusal_for_prompt(db, actor, row, action) -> ManagementRefusal | None:
    subject = _prompt_subject(row)                      # synthetic private, ownerless when row is None
    visible = await may(db, actor, PROMPT_READ, subject)
    allowed = await may(db, actor, action, subject)
    return refusal_for(visible=visible, allowed=allowed, action=action)
```

Three properties, and the third is the one a reviewer should check first:

1. **It is the lock file's own sentence.** *"Results are visible to exactly the actors who may read the
   prompt"* (`docs/modules/evaluation.lock.yml:429-430`). `may(actor, prompt.read, prompt_subject)` is
   that sentence with no interpretation added. Phase 7's D-104 makes `may()` *visibility AND
   permission*, so it already answers `False` for the private-no-grant case at `decide()`'s step 6 —
   the only thing Phase 17 got wrong was asking a different question when it built the refusal.
2. **Both calls are awaited unconditionally, in a fixed order, on every path.** Phase 9's D-131: a
   short-circuit that skips the second call when the first is `False` makes the two paths do different
   amounts of work, which is a timing oracle on exactly the distinction A-116 exists to hide. Task 3
   asserts the statement count is equal across all three refusal cases rather than trusting the shape.
3. **It costs one extra statement per request**, on the poll endpoint, which is the highest-frequency
   read in the module. That is the price and it is named rather than discovered.

**Rejected: `is_visible(...)` from `src/prope/access_control/refusals.py`.** It is the function written
for exactly this and it **cannot be called from here**. Two of its five arguments — `grant_level` and
`is_active_member` — live in `access.prompt_grant` and `access.workspace_member`, which this module's
`data.reads` forbids joining (*"through its API only (INT-001), never by joining across module
tables"*), and no seam returns them. `OQ-081` is already the record of that, raised by Phase 15 for the
registry. 14-01's D-245 rejected it for the same reason one module over.

**Rejected: pushing the three visibility disjuncts into the repository's join** — the registry's
repository-layer shape the lock's sentence alludes to. It needs `granted_ids`, which is
`visible_subject_filter`, which is D-332's refusal; and it would put a copy of BR-01's rule in a second
module's SQL, which is the drift `is_visible` exists to prevent.

**The consequence that is not free, stated here and again in `OQ-096`.** `may(prompt.read)` is
visibility **and** the `prompt.read` permission, so an actor who can see a `workspace`-level prompt but
whose role does not grant `prompt.read` now gets `404` from every eval route where prompt-registry's
detail route answers `403`. This is reachable today and not hypothetically: the seeded **Admin** role
(plan 07-01, the `ROLE_PERMISSION_SEED` block) holds thirteen actions and `prompt.read` is not one of
them. The direction is fail-closed and it is the direction non-negotiable #4 prefers, but two modules
now answer differently for one actor and that belongs in a question with an id rather than in a
reviewer's surprise.

**Reversibility: costly.** A refusal that has leaked cannot be un-leaked, and a `403` a client has
already learned to branch on is a wire promise; `/api/v1` is frozen (A-142).

## D-331 as implemented — a sentinel, both directions, and the positive control that makes absence mean something

**Chosen.** Two tokens that cannot occur by accident, one in `case_result.output_content` and one
inside the JSON of `eval_case.input_messages`, on the private prompt in workspace A. Every route on
`assembled_routes(app)` is driven twice — once as the non-grantee, once as the owner — inside
`structlog.testing.capture_logs()`. The tokens must be absent from every byte of every non-grantee
response and from every captured record and every metric label on **both** runs.

**The grantee half is not symmetry, it is the half that can fail.** The non-grantee never gets a
`200`, so the only way a token reaches them is through a refusal body — which is a short, structured
envelope. The grantee legitimately receives both tokens in a response body; the path where they leak
*further* is the log line and the metric label, and that path only exists when the value is actually in
hand. A test that scanned only the refusal path would assert the easy half twice.

**Rejected: asserting on parsed response fields, or on a list of models that may not carry content.**
A response model that gains an `output` field in Phase 23 escapes a field allow-list silently and
forever. `tests/security/test_no_body_read_path.py` (Phase 3) set this posture for a whole response and
06-03's Task 2 applied it to a whole row; this applies it to a whole surface.

**Added beyond D-331, and it narrows a gap D-333 accepted.** The route set the scan drives is not a
literal in the test file — it is read from `assembled_routes(app)` and asserted to be exactly the set
the module mounts. D-333 names the residual hole as *"a route added to this module after this phase is
caught only by Phase 23's assembled route-table assertion"*; with the coverage assertion, a route added
to this module later turns **these** tests red instead. The hole that remains is a route in **another**
module that returns evaluation content, which is genuinely Phase 23's.

**Reversibility: cheap.**

## D-332 as implemented — no INT-002, and the question gets an id

**Chosen.** This module consumes `may()` and no filter. `OQ-096` is created at the start of Task 1,
before the code it is about, in `OQ-078.md`'s frontmatter shape.

Three arguments, and the third is the one that decides it:

1. Every list this module exposes is scoped to **one prompt** — a prompt's suites, a suite's versions,
   a run's cases. `visible_subject_filter` answers *"which subjects of this type may this actor see"*,
   which is a question no route here asks.
2. A second visibility mechanism beside `may()` is a second answer that can disagree with it. The
   registry has both today and `OQ-080` is the record of what that costs: a colleague with an ordinary
   `prompt.read` role sees another person's private prompt in a **list page** while the detail route
   answers `404` for the same row.
3. So consuming INT-002 here would import a **known-open** contradiction with a ticket number attached,
   into the module whose content the lock puts in the same sensitivity class as a prompt body.

**Rejected: deferring it a fourth time.** It was owed to step 6 on 2026-08-09, step 6 did not fold it
in, Phase 17 routed it here, and this phase holds the allocated id. A fourth deferral would be the
plan noticing the same thing twice.

**Reversibility: cheap** — one call site if the answer changes.

### `src/prope/evaluation/api.py` — one helper, nine call sites, one comment removed

Add **one** module-level private coroutine, placed beside the existing refusal helper:

```python
async def _refusal_for_prompt(
    db: AsyncSession,
    actor: Actor,
    row: Mapping[str, Any] | None,
    action: str,
) -> ManagementRefusal | None:
    """The refusal, or None. Visibility is `prompt.read` on the parent prompt."""
    subject = <the module's existing prompt-subject builder>(row)
    visible = await may(db, actor, PROMPT_READ, subject)
    allowed = await may(db, actor, action, subject)
    return refusal_for(visible=visible, allowed=allowed, action=action)
```

Rules for it, each with a reason the executor must be able to state:

- **`PROMPT_READ` is `ManagementAction.PROMPT_READ.value` if that member exists, else
  `Action.PROMPT_READ.value` imported from access-control's vocabulary.** Not a string literal —
  17-01's rule that every action value is `Action.<MEMBER>.value` by reference exists so a retyped
  literal cannot drift from the seeded `role_permission` rows. **Add no member to `ManagementAction`.**
- **`subject` is built once and used for both calls.** Two subjects would be two chances to build them
  differently, and the second difference would be invisible.
- **When `row is None` the subject is the synthetic private, ownerless one the module already builds**
  (17-01 Task 2 step 4). Both `may()` calls then return `False` and the answer is `404` — which is what
  cases 1 and 2 need, and it costs the same two statements as case 3, which is the point.
- **Both `await may(...)` calls are statements, not operands of an `and`/`or`.** Write them on separate
  lines. `visible and await may(...)` short-circuits and re-opens the timing oracle Phase 9's D-131
  closed; Task 3 asserts the statement count is equal across the three cases, so a short-circuit is a
  failing test rather than a review comment.
- **One pointer comment on the helper and nowhere else:**
  `# D-330 / OQ-096: visibility is may(prompt.read) on the parent, not RLS row presence.`
  Twelve words. The argument lives in this plan and in `OQ-096`.

### The tests

1. **`test_the_three_refusals_are_byte_identical`** — parameterised over `ROUTES`. Issue the three

   - equal `code` (`"not_found"`);

     action, because naming one tells an attacker which permission was checked);

### The two sentinels

Module-level constants, each a string that could not occur by accident, each with a one-line comment
naming the column it stands for:

```python
OUTPUT_SENTINEL = "zzsentinelzz-output-<8 hex chars>"   # case_result.output_content
INPUT_SENTINEL = "zzsentinelzz-input-<8 hex chars>"     # inside eval_case.input_messages' JSON
```

`INPUT_SENTINEL` goes **inside** the JSON of `input_messages`, in a message's `content`, not as the
whole column — a scan that only ever sees top-level values would pass on a nested leak, and nesting is
how the real value is actually stored.

The fixture is Task 3's, rebuilt in this module (the two files do not share a fixture package: 18-05
shares this wave and a new shared module is a lost update waiting to happen — say so in a comment).
