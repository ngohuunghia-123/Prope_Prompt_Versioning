<objective>
Ship the whole worker-side spine of EVAL-07 in one vertical path, and close the half of ROADMAP
Phase 18 success criterion 1 that says **a run whose worker died is marked `interrupted`**. What lands:
`src/prope/evaluation/sweeper.py` with D-323's single `UPDATE … WHERE status = 'running' AND <no
progress> … RETURNING` statement as a module-level `text(...)` constant; the `eval_run_interrupted`
append inside the same transaction with `actor_type = 'system'`, a null `actor_id` and `details`
carrying `version_id` and `suite_version` from the joined suite; both declared counters moved after
commit by the number of rows the engine actually changed; the queue-depth gauge established as
project-wide, unlabelled and published by a resident that is not the claim loop; and the sweep composed
by hand under `supervise()` in `src/prope/worker.py` as its own resident, with D-339's three places
that change together moving in this one change.

**The load-bearing claim is that a pass which reaps nothing is not evidence of a healthy system, and
this plan asserts the difference rather than assuming it.** Under ADR-0045 an
`UPDATE evaluation.eval_run SET status = 'interrupted' WHERE status = 'running' …` issued by `prope_app`
with no `app.workspace_id` in the session matches **zero rows**. The job then runs, reports success,
reaps nothing, and `prope_evaluation_run_interrupted_total` stays at zero — which is byte-for-byte the
signal a correct system produces. Two things follow, and both are in this plan rather than in a review.
The cross-tenancy is done the sanctioned way — `src/prope/worker.py`'s existing `WorkspaceEnumerator`,
already bound to `access.list_workspaces()` by plan 07-03, with `SET LOCAL app.workspace_id` per
workspace and **no fifth `SECURITY DEFINER` function** (D-321). And
`tests/integration/test_sweeper_is_cross_tenant.py` asserts **both halves plus the control**: a run in a
workspace this process has never opened a transaction for **is** reaped; the same corpus with an
enumerator returning `()` reaps **exactly zero** and leaves the run `running`; and the same statement
with no tenant set reports `rowcount == 0` where the tenanted one reports `1`.

The second guarantee is the one that could destroy data rather than merely fail to save it. D-323's
single statement exists because a select-then-update leaves a window in which a run **completes**
between the two statements and is then overwritten as `interrupted` — a reviewer's finished evidence
destroyed by a liveness job. The `status = 'running'` predicate inside the `UPDATE` closes that at the
engine and, as a side effect nobody has to maintain, makes the job **idempotent by predicate rather than
by lock**: a second pass, a restarted process or a second `worker` replica reaping the same run gets
zero rows back, appends no second event and increments no counter.

**What this plan deliberately leaves open, and who closes it.** The reap is *advisory* when it lands:
ADR-0049 releases the row lock at the claim on purpose, so a slow-but-alive executor keeps dispatching
cases into a run this sweep has already reaped, spending the workspace's own key on results nobody will
read. **Plan 18-02 owns the per-case `status = 'running'` re-check (D-336, `OQ-099`) and owns AC-7's
end-to-end proof against a worker that actually died** (`tests/chaos/test_interrupted_run_sweeper.py`) —
this plan asserts the statement and the composition, never the kill. It asserts neither concurrency
bound (18-03), drives no Phase 17 route and asserts no refusal shape (18-04), measures no regex blast
radius (18-05), and writes no alert rule and no §9a audit (18-06).
</objective>

## Resolutions this plan makes

18-CONTEXT consumes D-320 through D-339 and **the range is closed**, so none of the following mints a
decision id. Each is either an item from the CONTEXT's *Claude's Discretion* block or a collision with
what Phases 16 and 17 actually put on disk. Every one of them is stated here so the executor does not
invent it and the SUMMARY can report it.

**R1 — the sweep's SQL lives in `src/prope/evaluation/sweeper.py`, as a module-level `text(...)`
constant, and not in Phase 16's run repository.** The CONTEXT leaves the home open and fixes the
constraint: `tests/architecture/test_no_sql_interpolation.py` `rglob`s `src/prope/` and requires every
`text(...)` argument to be a plain string constant, so it is a module-level constant either way. A new
module wins on two counts. `runs.py` is 16-04's, whose whole subject is that `transition()` is the
**only** writer of `eval_run.status`; putting a second, set-based writer in the same file would make
that sentence read as false to the next person who opens it, when what is actually true is narrower
(see R5). And every plan in this phase's later waves imports the sweep, so a file whose name says what
it is beats a function buried in a repository.

**R2 — the depth gauge is Phase 16's if Phase 16 shipped it, and this plan asserts it rather than
rebuilding, re-homing or retiring it.** D-328 argues the gauge should ride the sweeper's enumeration and
rejects *"a fifth resident job of its own"*. Plan 16-02 ships `src/prope/evaluation/queue_depth.py` with
`observe_queue_depth(sessionmaker, workspaces, …) -> int` over the same enumerator, and plan 16-05's R2
composes it as `JOB_EVAL_QUEUE_DEPTH` at a 15 s interval. Task 1 reads disk and takes one branch:

- **Branch A (expected).** `observe_queue_depth` exists and is composed. `sweeper.py` declares **no**
  depth function; nothing is deleted; `worker.py` gains no second call. Every correctness property
  D-328 names is already true of the shipped code — it walks the enumerator under the policy, it reduces
  to a project-wide total, it is unlabelled, it sets `0.0` rather than leaving the series unset, and it
  is published by a resident that is **not** the claim loop, which is the property D-328's rejection
  paragraph was actually protecting. D-328's remaining claim — *one enumeration serving two readers* —
  is a **cost** argument, not a correctness one, and it is worth less than a cross-phase deletion of a
  tested job. The deviation is recorded in the SUMMARY as **owed and unallocated**: this plan's only
  allocated id is `OQ-098` and it is spoken for.
- **Branch B.** `queue_depth.py` or `observe_queue_depth` is absent. Then `sweeper.py` declares
  `observe_run_queue_depth(sessionmaker, workspaces) -> None` exactly as 18-CONTEXT's signature block
  writes it, and the worker's sweep body calls it after the reap on a **second** call to the same
  enumerator — `expired_body_sweep`'s stated trade, *"cheaper than a changed signature or a side effect
  in a pure function"*, which is the CONTEXT's first discretion item resolved.

`tests/integration/test_run_queue_depth_gauge.py` is written in **both** branches, and under branch A it
carries the one assertion 16-02's unit-level gauge test cannot make: that the series moves under a
`run_worker` composition, and that the resident publishing it is not the resident it measures.

**R3 — `NO_PROGRESS_AFTER` lives in `sweeper.py`; `JOB_EVAL_INTERRUPTED_SWEEP` and
`INTERRUPTED_SWEEP_INTERVAL_SECONDS` live in `worker.py`.** The CONTEXT's signature block puts all three
under `worker.py`, and that cannot hold for the first: `sweep_interrupted_runs`' default is
`no_progress_after: timedelta = NO_PROGRESS_AFTER`, and importing it from `prope.worker` — the module
that imports `sweeper` — is a cycle at module load. The split follows `DEFAULT_CHUNK_SIZE`, which lives
in `prope.call_ledger.retention` and is imported by `worker.py:75`. The two composition constants stay
in `worker.py` beside `RETENTION_SWEEP_INTERVAL_SECONDS` and `DEPTH_GAUGE_INTERVAL_SECONDS`, which is
what makes `vars(prope.worker)`'s `JOB_`-prefix scan keep working and what D-339 binds the test name to.

**R4 — a test makes a run look abandoned by backdating through `migrate_engine`, and the injected
cut-off is used only where the boundary itself is under test.** The CONTEXT's third discretion item asks
which of three techniques proves what. Resolved: **backdating** proves the statement, because it is the
only technique that exercises the real predicate against real `case_result.created_at` values and the

**1. `REAP_INTERRUPTED_RUNS` — one `text()` constant, one statement, no interpolation.**

```python
REAP_INTERRUPTED_RUNS = text(
    """
    UPDATE evaluation.eval_run AS r
       SET status      = 'interrupted',
           finished_at = :cut_off_now
      FROM evaluation.eval_suite AS s
     WHERE s.workspace_id = r.workspace_id
       AND s.id           = r.suite_id
       AND r.status       = 'running'
       AND greatest(
             r.started_at,
             coalesce((SELECT max(cr.created_at)
                         FROM evaluation.case_result cr
                        WHERE cr.workspace_id = r.workspace_id
                          AND cr.run_id       = r.id),
                      r.started_at)
           ) < :no_progress_before
    RETURNING r.id, r.prompt_id, r.version_id, s.suite_version
    """
)
```

Six things about that statement are load-bearing and only two of them are visible:

- **`r.status = 'running'` is inside the `UPDATE`.** D-323. There is no `SELECT` first, so there is no
  window in which a run completes between two statements and is then overwritten. It is also what makes
  the job idempotent by predicate: a second pass matches nothing.
- **`greatest(started_at, max(case_result.created_at))`.** D-322. `started_at` is the **floor**, so a run
  that claimed and then died before its first case landed is reaped rather than left forever with a null
  aggregate. PostgreSQL's `greatest` ignores NULL arguments, so the `coalesce` is belt beside braces
  here; keep it, because the statement then reads correctly under a standard-following dialect too, and
  because the intent — *fall back to the start when there is no progress* — is what a reader needs.
- **The join is to `eval_suite` on `(workspace_id, id)`**, which is `fk_eval_run_suite`'s exact key, and
  it exists so `suite_version` arrives with the `RETURNING` row rather than as a second read per reaped
  run (D-324). It is an inner join and that is correct: the foreign key makes a run without a suite
  unrepresentable.
- **No `workspace_id` predicate on `r`.** The tenant policy is the enforcement; the statement runs inside
  `workspace_transaction(sessionmaker, workspace_id)` and `workspace_id` is text compared to text with no
  cast. This deliberately differs from `retention.DELETE_CHUNK`, which writes the predicate out — there
  the predicate also selects the index; here the `UPDATE` is set-based over everything visible and a
  second copy of the tenant decision is a second thing that can be wrong.
- **`:cut_off_now` and `:no_progress_before` are bound parameters**, computed once per pass by the caller
  from one `clock()` read. Never `now()` inside the statement: a cut-off that advanced mid-pass would
  make *what this pass reaped* depend on how long the pass took.
- **`finished_at` and `status` are the entire `SET` list**, and they are the only two columns in it that
  `prope_app` holds `UPDATE` on for a reason — 16-01's ten-column grant. `started_at` is absent from that
  grant, which is why `ck_eval_run_finish_needs_start` cannot be violated here: a `running` row was
  stamped by `claim_next_run()` as the owner and nothing can null it back.

| field | value | why |
|---|---|---|

| `target_id` | `row.id` | |
| `scope_prompt_id` | `row.prompt_id` | what makes the reap visible on the prompt's activity feed |
| `occurred_at` | `now` | the pass's one clock read, so every event in a pass carries the same instant |

Four properties of that body must be right and three of them are invisible:

- **`reaped += len(rows)` sits AFTER the `async with`, not inside it.** The count means *rows this pass

  indistinguishable from a working one.

  commit (D-325, R7).
