## D-174 — A refresh never touches a `manual` row, and never deletes anything

**Chosen.** Reconciliation has exactly four cases and they are enumerated in the code as four:

| the model is | in the upstream list | in the table | what happens |
|---|---|---|---|
| **new** | yes | no | INSERT, `source='discovered'`, `available=true`, `first_seen_at = last_seen_at = now` |
| **still there** | yes | yes | UPDATE `last_seen_at = now`, `available = true`, `display_name`; `first_seen_at` untouched |
| **gone** | no | yes, `source='discovered'` | UPDATE `available = false`. **No DELETE.** `last_seen_at` untouched — it is when the provider last listed it, and a row that has gone should keep saying when |
| **manual** | no | yes, `source='manual'` | **nothing at all** |

**The fourth case is the one that gets written wrong**, and it is written wrong by an implementation
that looks correct: "anything not in the list is unavailable" is the obvious rule and it marks every
manually added model unavailable on the first refresh. A-091 puts manual entry in the catalogue
*"for models the endpoint omits"* — so absence from the list is the manual row's **defining property**,
not evidence about it.

**The no-delete rule** is the lock's own, quoted at the code: *"`available: false` rather than
deletion, so a revision bound to a model the provider has retired still explains itself instead of
pointing at nothing."* A deleted row makes a released revision reference a model id with no record
anywhere, and the failure presents to a reviewer as a blank field rather than as an explanation.

**Rejected: deleting rows absent from two consecutive refreshes.** It is the tidy version and it
destroys the only evidence of what a bound revision was pointing at. Storage is not the constraint —
this table holds a few hundred rows per workspace.

**Rejected: a `retired_at` column** to distinguish "gone" from "never seen". Not declared in
`data.owns`, and `available=false` plus `last_seen_at` already carries it: the pair says *not available
now, and here is when it last was*.

**Reversibility: cheap** for the rules; **one-way** for anything deleted, which is why nothing is.

---

## D-175 — `supports_streaming` is an adapter-level claim, not a discovered fact

**Chosen.** A `discovered` row gets `supports_streaming = True`. A `manual` row takes the caller's
value, defaulting to `True`.

**The honest statement, and it goes in the column's docstring rather than being quietly implied:** an
OpenAI-compatible `GET /models` response carries no streaming field at all. The value is not
discovered; it is asserted by the adapter, and for `openai_compatible` — the MVP's only adapter
(A-094) — streaming is part of the wire contract the adapter's name claims. So `True` is a statement
about the **adapter**, and the moment a second adapter arrives (OQ-016, post-MVP) it becomes a
per-adapter answer rather than a constant.

**Rejected: `NULL` / unknown.** The column is `NOT NULL` in `data.owns` and the lock's own
`get_model_catalogue` contract returns `supports_streaming` as a fact prompt-registry's picker renders.
A tri-state would push "unknown" into a UI that has to render something, and "unknown" renders as
either yes or no anyway — with nobody having decided which.

**Rejected: probing each model for streaming support.** It is one paid completion per model per
refresh, on a table with a few hundred rows, to learn something the adapter already asserts.

**Reversibility: cheap.** One default and one adapter-keyed lookup when the second adapter lands.

### `src/prope/provider_access/catalogue.py`

Module docstring: A-091, INT-016's soft-seam rule quoted, D-174's four cases stated as four, D-175's
honest statement about `supports_streaming`, and the money prohibition — *"Holds no price and no cost
column of any kind — money is call-ledger's (A-030, A-056)"* — with the note that this is the one table
in provider-access where a price would try to appear, which is why plan 10-01 asserts its absence from
`information_schema` rather than trusting a review.

```python
CATALOGUE_REFRESH_OK = "ok"
CATALOGUE_REFRESH_FAILED = "failed"
CATALOGUE_REFRESH_RESULTS = frozenset({CATALOGUE_REFRESH_OK, CATALOGUE_REFRESH_FAILED})

@dataclass(frozen=True, slots=True)
class CatalogueEntry:
    id: str
    model_id: str
    display_name: str
    source: str
    supports_streaming: bool
    available: bool
    first_seen_at: datetime
    last_seen_at: datetime

@dataclass(frozen=True, slots=True)
class ReconciliationCounts:
    added: int
    still_present: int
    marked_unavailable: int
    manual_untouched: int
```

**`ReconciliationCounts` is not diagnostics.** It is the return value the tests assert the four cases
through, and it is what phase 11's route renders so an operator pressing *refresh* sees what changed
rather than a spinner that stops. Say that at the type.

```python
async def reconcile_catalogue(
    session, *, workspace_id, provider_config_id,
    upstream_models: Sequence[DiscoveredModel], now: datetime,
) -> ReconciliationCounts
```

Takes the caller's `AsyncSession` — ADR-0023's shape — because `verify_provider_config` calls it inside
the transaction that is also writing the verification columns, and a passing verification and its
catalogue must land together or not at all.

The body is the four cases, **each in its own block with its own comment naming it**, in this order:

1. Read every existing row for `provider_config_id` into a `{model_id: row}` mapping. One query, not
   one per model.
2. **New** → INSERT with `id = f"{CATALOGUE_ID_PREFIX}{ULID()}"`, `source=SOURCE_DISCOVERED`,
   `supports_streaming=True` (D-175, with the comment), `available=True`,
   `first_seen_at=now`, `last_seen_at=now`.
3. **Still there** → UPDATE `last_seen_at=now`, `available=True`, `display_name`. **`first_seen_at` is
   not in the SET list**, and the comment says why: it answers *when did this workspace first see this
   model*, which a re-appearance must not overwrite. `available=True` is in the SET list deliberately —
   a model that comes back is available again, and that is the case the "returning model" test exists
   for.
4. **Gone and discovered** → UPDATE `available=False`. **`last_seen_at` is not in the SET list** — it
   is when the provider last listed it, and a row that has gone should keep saying when it went.
5. **Gone and manual** → **no statement at all.** Not an UPDATE with unchanged values; no statement.
   The comment is D-174's paragraph in one sentence: absence from the list is a manual row's defining
   property, not evidence about it. Count it in `manual_untouched` so the caller can see the rule
   applied rather than infer it from nothing happening.

**A model id appearing twice in the upstream list** is deduplicated before reconciliation, keeping the
first occurrence, with a comment: the UNIQUE would refuse the second insert and take the whole
transaction — and the whole verification — with it, on a malformed third-party response Prope did not
write. **Dedupe, do not raise**, and say so.

```python
async def refresh_catalogue(
    sessionmaker, client, *, workspace_id, provider_config_id, key_ring, now,
) -> tuple[str, ReconciliationCounts | None]
```

Opens its own `workspace_transaction`, reads `base_url`, decrypts the credential the same way
`verify_provider_config` does, calls `list_upstream_models`, and reconciles. Then the property that
matters:

**A failed listing writes nothing.** The upstream call happens **before** any write, and on a non-`ok`
reason the function returns `(reason, None)` having issued no statement — not a partial reconciliation,
not a "mark everything unavailable because we could not reach the provider". Write the argument at the
early return: an unreachable provider is not evidence that its models were withdrawn, and a refresh
that emptied the catalogue on a network blip would make INT-016's soft seam hard in the worst possible
way — the picker would go blank during an outage and a reviewer would conclude the models were gone.

Increment `catalogue_refresh_total.labels(result=…)` at exactly one site.

```python
async def add_manual_model(
    session, *, workspace_id, provider_config_id, model_id, display_name,
    supports_streaming: bool = True, now,
) -> str
```

INSERT with `source=SOURCE_MANUAL`, `available=True`, both timestamps `now`. It does **not** catch the
UNIQUE violation: adding a model the provider already lists is a caller mistake that must reach the
caller, and phase 11's route turns it into a 409. Comment that decision, because swallowing it would
silently produce a duplicate-looking success.

```python
async def read_catalogue(session, *, provider_config_id) -> tuple[CatalogueEntry, ...]
```

Ordered by `model_id` — stable, alphabetical, deterministic, and the same rule the probe uses to pick
its model, so a reader meets one ordering convention in this module rather than two. It returns
**unavailable rows too**, and the docstring says why: a revision bound to a retired model must be
explicable, so the picker's job is to show the row greyed rather than to hide it. Filtering is the
caller's.

There is **no** function in this module that takes a revision, a prompt, or a released pointer, and the
docstring says so with the forbidden edge cited: prompt-registry depends on this module, never the
reverse.

### `src/prope/provider_access/configs.py`

Inside `verify_provider_config`'s **passing** branch only, after the three verification columns are
written and inside the same transaction:

```python
await reconcile_catalogue(session, workspace_id=…, provider_config_id=…,
                          upstream_models=outcome.models, now=now)
```

Three sentences at the call, because each answers a question a reader will have:

- **No second request.** `outcome.models` is what `list_upstream_models` already returned inside the
  probe, so *"probe passes → the catalogue populates"* (the lock's e2e journey) costs exactly the two
  requests the probe already made.
- **Same transaction.** A passing verification and the catalogue it discovered land together or not at
  all. A configuration that is `active` with an empty catalogue is a picker that shows nothing for a
  provider that works, and it would be an inconsistency nothing later repairs.
- **Failing branch: nothing.** A failed verification does not reconcile, even when the model list
  succeeded and only the completion failed. Write the reason: the catalogue describes a configuration
  that works, and half-populating it from a configuration that does not is how a picker comes to offer
  models nobody has ever completed against. `refresh_catalogue` is the path for a deliberate
  list-only refresh, and it is a separate call an operator makes on purpose.

## Flagged assumptions

The deterministic detectors Phase 1–2 artifacts cite do not exist here (ORCHESTRATION §0). **No
detector was run.** The boundary conditions the catalogue genuinely has are enumerated in the
acceptance criteria and are: a new model, a persisting model, a withdrawn discovered model, a withdrawn
manual model, a model that returns after being withdrawn, a duplicated id in the response, an empty
list, a list endpoint that fails while completions work, and a manual add colliding with a discovered
row. **This is an agent enumeration, labelled as one.**

The claim that an OpenAI-compatible `GET /models` response carries no display name and no streaming
field is an agent judgement from ADR-0015 and general knowledge of the wire shape, **not a surveyed
fact**; D-175 is written so that being wrong about it costs one default rather than a schema change.
