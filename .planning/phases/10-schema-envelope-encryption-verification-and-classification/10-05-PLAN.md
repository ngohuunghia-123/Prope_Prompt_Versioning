<objective>
Two operations that look similar and share almost nothing: **rotating a credential** replaces a secret
the workspace supplied, and **re-wrapping a data key** replaces the key Prope wraps it with. One
touches a plaintext; the other must never see one.

The pair is what makes ADR-0014's central claim true in practice rather than in principle. Envelope
encryption was chosen over one static key on two grounds — blast radius and **rotation** — and the
rotation argument was specific: *"rotating it … requires decrypting and re-encrypting every row in one
migration, during which the old key must still be present. Envelope encryption makes rotation a
re-wrap of a few small values."* A phase that ships the envelope and not the re-wrap has shipped the
data layout of the decision and not the property it was made for.

## D-176 — A rotation is an UPDATE in place, not a delete-and-insert

**Chosen.** `rotate_credential` UPDATEs the existing row: same `crd_` id, same `provider_config_id`,
new `ciphertext` / `nonce` / `wrapped_dek` / `kek_version` / `last_four`, and `rotated_at = now`.

**Three things make this the only workable shape and each is worth stating.**

*One: the AAD binds to the row's identity.* D-163 seals both layers against
`credential_id | workspace_id | provider_config_id`. A delete-and-insert mints a new `crd_` id, so the
new AAD differs from the old — harmless in itself, but it means the id is not a stable fact about a
configuration's credential, and phase 11's 60 s decrypted-credential cache (A-092) would then have to
key on something else or invalidate on an id it cannot see change.

*Two: the engine already refuses the alternative.* `uq_credential_provider_config` (plan 10-01) permits
exactly one row per configuration. A delete-and-insert in one transaction satisfies it, but so does an
insert-then-delete that fails halfway, and the shape that cannot fail halfway is the one that never has
two rows in flight.

*Three: the grant matrix already describes it.* Plan 10-01 granted `prope_app` column-level UPDATE on
exactly the sealed values plus `last_four` and `rotated_at` — and **not** on `provider_config_id`. So a
rotation that tried to move a credential between configurations is refused at the engine, before the
cipher's AAD would refuse it. Two independent refusals for one mistake is the posture this module takes
everywhere.

**Rejected: append a new row and mark the old one superseded.** It is how every other history in this
project works, and it is exactly what A-025 forbids here: *"replaced in place on rotation — never
appended, so no readable history of a secret accumulates."* The audit trail records **that** a rotation
happened, by whom and when; it never records what changed. This is the one table in Prope where the
project's own append-only instinct is the wrong instinct, and the code should say so where a reader
will meet it.

**Reversibility: costly.** The UNIQUE is in a landed revision and phase 11's cache is written against a
stable credential id.

## D-177 — AC-13 is asserted HERE, in phase 10, and the re-wrap is a callable rather than a route

**Chosen.** `.planning/research/PITFALLS.md` gap 1 records AC-13 as owed to *"10 or 12"*: *"KEK re-wrap
V1 → V2: every row reports `kek_version=2`, every credential still decrypts, V1 can be removed, and no
plaintext was written anywhere."* **Phase 10 takes it**, and it ships as
`rewrap_workspace_credentials(...)` — a plain async function in `src/prope/provider_access/rewrap.py`
with no route, no job and no CLI.

**Why phase 10 and not phase 12.** The whole operation is `wrapped_dek` and `kek_version` — two columns
plan 10-01 created, one crypto function plan 10-01 wrote, and one key ring plan 10-01 built. It needs no
route, no dispatch, no admission gate and no SSRF guard, which is everything phase 12 is about. And
`kek_version` shipped in the schema *"from day one"* on ADR-0014's explicit instruction; a version column
whose version can never change for two phases is a column with no exerciser, and the first thing that
exercises it is the thing that finds out whether it works.

**Why a callable and not a route.** The lock declares eight-to-ten management routes and none of them
is a re-wrap; `scope.in_scope` names *"Encrypt every credential at rest"* and *"Rotate a credential in
place"* and neither is a KEK rotation; `events` is empty both ways; `deployment_target` names no
scheduled job. **AC-13 requires a command the specification does not give a home to**, and that is
`OQ-058`.

Given no declared home, the smallest honest thing is a function the operator invokes with
`uv run python -c` on the host that already holds `.env`, and the docstring says exactly that,
including the operational sequence:

1. Add `PROPE_KEK_V2` to `.env` alongside V1. **New credentials immediately wrap under V2** — because
   `wrapping_version` is `max(versions)` (A-135) — which is intended and is also how someone rotates by
   accident.
2. Run the re-wrap. Every row moves to V2.
3. Verify `SELECT DISTINCT kek_version FROM provider.credential` returns `{2}` **in every workspace**.
4. Remove `PROPE_KEK_V1` from `.env` and restart.

**Rejected: a management route.** It would be a ninth or eleventh route on a surface the lock
enumerates exactly, exposed over HTTP, whose effect is invisible to the caller and whose failure mode is
partial. A route for an operation only the person holding `.env` can meaningfully perform is a route
whose authorisation is the wrong shape.

**Rejected: an Alembic data migration.** It would put a KEK in the migration's environment, and
migrations run as `prope_migrate` in CI-adjacent contexts — ADR-0032's *"never enters CI"* is the whole
of the KEK's protection and a migration is the most likely place to break it by accident.

**Rejected: a supervised job on an interval.** Nothing to do on any interval; a KEK rotation is a
deliberate act, and a job would need a trigger, which is a route again.

**Reversibility: cheap.** A function with one call site is promoted to a route or a CLI in an afternoon.
The **assignment** of AC-13 to this phase is what is not free, and `deferred-items.md` §2 records it so
phase 12's verifier does not go looking for it.

### `src/prope/provider_access/credentials.py`

```python
async def rotate_credential(
    sessionmaker, *, workspace_id, provider_config_id, actor_id, new_secret, key_ring, now,
) -> str
```

One `workspace_transaction(sessionmaker, workspace_id)`, and inside it:

1. `existing = await get_sealed(session, provider_config_id=provider_config_id)`. `None` → raise
   `CredentialNotFound`, a module exception. Note at the raise that under RLS a wrong workspace produces
   the same absence, which is the correct refusal shape and phase 11 renders it as a 404 (A-116).
   **The existing sealed values are read for their `credential_id` only** — the rotation never opens
   them, because replacing a secret does not require knowing the old one. Say that: a rotation that
   decrypted the old credential to replace it would put a plaintext in memory for no reason at all.
2. `sealed = seal_credential(new_secret, key_ring=key_ring, credential_id=existing_id,
   workspace_id=workspace_id, provider_config_id=provider_config_id)` — **the same `credential_id`**,
   which is what keeps D-163's AAD valid and D-176's stable id true. Comment the reuse explicitly,
   because minting a fresh id here is the natural instinct and it is wrong.
3. `UPDATE provider.credential SET ciphertext, nonce, wrapped_dek, kek_version, last_four,
   rotated_at = :now WHERE id = :existing_id` — exactly the six columns the column-level grant permits,
   and **not** `provider_config_id`, `workspace_id`, `created_by` or `created_at`. The comment names the
   grant: the engine refuses the other four, so this list is not a convention that could drift from the
   privilege.
4. `await append(session, HistoryEventDraft(...))` with `action="credential_rotated"`,
   `target_type="provider_config"`, `target_id=provider_config_id`, `actor_type="user"`,
   `actor_id=actor_id`, `scope_prompt_id=None`, `reason=None`, `details={}`, `occurred_at=now`.
   **Two sentences at this call.** First: `details` is `{}` and plan 04-01's registry seeds
   `credential_rotated` with an empty `detail_keys`, so **any key at all fails the write** — which is
   how *"the credential redacted in every event"* stops being a promise and becomes a check (ADR-0024).
   Second: the target is the **configuration**, not the credential, because `crd_` ids are not a thing
   any audit reader should be handed and because the four provider events all scope to
   `provider_config` in the registry.
5. Return the credential id, unchanged from what went in — which is the API-visible statement that this
   was a replacement and not a new credential.

**The docstring carries the three things a reader needs and would otherwise get wrong:**

- **A-025 inverts this project's own instinct.** Everywhere else, history is appended and never
  deleted; here the row is replaced and the previous ciphertext is gone. Write the reason: an
  append-only secret store is a store of every secret a workspace has ever used, and the value of that
  store to an attacker grows monotonically with time.
- **The re-probe is not here.** *"Re-probes before the new credential becomes active (A-090)"* is a
  route-level composition — `rotate_credential` then `verify_provider_config` — and it is **phase
  11's** (INT-027). State what this function alone leaves true: the new credential is stored
  immediately, and processes pick it up as their 60 s caches expire (A-092, **phase 11's cache**), so
  the ordering question — should the row be replaced before or after the probe passes? — is a real one
  and it is phase 11's to answer. Record it in `deferred-items.md` §4 rather than deciding it from
  here, because the answer depends on the route's error contract.
- **Nothing here retries, re-verifies, or dispatches.**

Also define `CredentialNotFound` beside `ProviderConfigNotFound`'s home, whichever module plan 10-03
put that in, so the two refusals are siblings.

### `tests/integration/test_credential_rotation_replaces_the_row.py`

- **One row, before and after.** Register, rotate, and assert `SELECT count(*) FROM provider.credential
  WHERE provider_config_id = …` is 1 at both points, and that `id` is unchanged.
- **The old secret is gone.** Snapshot `ciphertext`, `nonce` and `wrapped_dek` before; assert all three
  differ after; and run the whole-corpus marker scan from plan 10-01's security test over the **old**

  The new secret's `last_four` is the positive control.
- **`rotated_at` is set and `created_at` is not moved** — the pair that says the row is the original
  row carrying a new secret.
- **The event.** Exactly one `credential_rotated` row in `history.history_event` for the configuration,

  one table over.
- **The half-commit case**, which is the lock's own chaos clause. Monkeypatch
  `prope.provider_access.credentials.append` (or whatever name the module binds) to raise, attempt the
  rotation, and assert: the exception propagates; `provider.credential` still holds the **original**

### `src/prope/provider_access/rewrap.py`

Module docstring: ADR-0014's rotation argument in full, D-177's operational sequence as a numbered
list, `OQ-058` cited by name, and — first, because it constrains everything below — **the rule that no
credential plaintext is produced at any point.** There is no `open_credential` import in this module,
no logger, and no return value carrying anything but counts.

```python
@dataclass(frozen=True, slots=True)
class RewrapCounts:
    examined: int
    rewrapped: int
    already_at_target: int
```

```python
async def rewrap_workspace_credentials(
    session, *, workspace_id, key_ring, target_version: int, now: datetime,
) -> RewrapCounts
```

Takes the caller's `AsyncSession`, so a workspace's re-wrap is one transaction and either all of its
rows move or none do. Per row:

- `sealed.kek_version == target_version` → skip, count `already_at_target`. **This is what makes the
  operation idempotent**, and idempotence is the property that lets an operator re-run it after an
  interruption without thinking. Say so.
- otherwise → `rewrap_data_key(sealed, key_ring=key_ring, target_version=target_version,
  credential_id=…, workspace_id=…, provider_config_id=…)` and
  `UPDATE provider.credential SET wrapped_dek = :w, kek_version = :v WHERE id = :id`.
  **Exactly two columns in the SET list**, and the comment says what that buys: it is Task 3's
  byte-identity assertion expressed as SQL, and it is ADR-0014's *"does not touch a single ciphertext"*
  made checkable rather than believed. **`rotated_at` is not touched either** — the credential did not
  rotate, its wrapping did, and moving `rotated_at` would make an audit reader think a secret changed.

```python
async def rewrap_all_credentials(
    sessionmaker, *, key_ring, target_version, now, workspace_ids: Sequence[str],
) -> RewrapCounts
```

Opens one `workspace_transaction` **per workspace** and sums the counts. Two paragraphs at the loop:

- **One transaction per workspace, not one for everything.** ADR-0040's per-workspace batching rule and
  the RLS seam both require it — `workspace_transaction` takes exactly one workspace by construction and
  there is deliberately no method that sets a second inside an open transaction. The consequence is
  stated rather than hidden: an interruption leaves some workspaces at V2 and some at V1, **which is
  safe** because both keys are present during the whole operation (D-177 step 1) and because a re-run
  skips what is done.
- **`workspace_ids` is a parameter, not a scan.** The caller supplies them from
  `access.list_workspaces()` — the sanctioned enumerator (ADR-0051), one of the four `SECURITY DEFINER`
  functions, and the fix Broken Window #3 already routes through a parameter rather than an import. Say
  plainly why the alternative is refused: `SELECT DISTINCT workspace_id FROM provider.credential` would
  need to run outside a tenant context on the highest-liability table in the system, and would miss a
  workspace whose credential row is somehow absent — enumerating **workspaces** rather than **rows**
  is the same correction ADR-0051 made for the retention sweep. If phase 7's function is not on disk
  yet, the parameter is still the right shape and the caller is still the composition root.

**No metric is added and none of the fourteen fits**, and the docstring says so with the reason: a KEK
re-wrap is a deliberate operator action performed perhaps twice in the product's life, and a Prometheus
counter for it would be a series that is zero forever and then briefly one. The observable is the
function's returned `RewrapCounts` and the row state afterwards. **`prope_provider_access_kek_unavailable`
is touched only by the key ring** (plan 10-01) and a re-wrap against a ring missing either version fails
there, which is the correct place.

> *Given credentials wrapped under `PROPE_KEK_V1`, when V2 is added and the re-wrap command runs, then

**Setup.** Build **three** configurations across **two** workspaces, each with a distinct marked
secret, all sealed under a ring holding V1 alone. Three-across-two is deliberate and the docstring says
so: one workspace would let a per-workspace loop pass while being wrong about the second, and one
credential would let a single-row implementation pass. Snapshot, per row, `ciphertext`, `nonce`,
`wrapped_dek`, `kek_version` and `rotated_at` through `migrate_engine`.

**The operation.** Build a ring holding **both** V1 and V2 — which is the state `.env` is in during a
real rotation — and run `rewrap_all_credentials(..., target_version=2, workspace_ids=[A, B])`.

**Clause 1 — every row reports `kek_version = 2`.** Assert it per row and assert
`SELECT DISTINCT kek_version FROM provider.credential` returns exactly `{2}`, read through
`migrate_engine` so no policy can hide a row. Assert `counts.rewrapped == 3` and
`counts.already_at_target == 0`.

**Clause 2 — every credential still decrypts.** For each row, `open_credential` with a ring holding
**V2 only**, and compare `hashlib.sha256` of the result against the digest recorded at setup. Digests
rather than plaintexts, so this test's own assertion output cannot become the leak clause 4 is about.

**Clause 3 — V1 can be removed.** For each row, `open_credential` with a ring holding **V1 only** and
assert `KekUnavailable` — the version is simply not in the ring — and with a ring holding **V2 only**
and assert success. Together those two say the corpus no longer depends on V1 and does depend on V2,
which is exactly what "V1 can be removed" means operationally.

**Clause 4 — no plaintext was written anywhere.** Three assertions, because "anywhere" has three
meanings and only the first is obvious:

1. **Not to a column.** Re-run plan 10-01's corpus scan over all three markers across all three
   `provider` tables, in every encoding.
2. **Not to a log line.** Capture structlog output for the duration of the operation and assert it is
   **empty of the markers**, and additionally assert the module binds no logger at all — the source
   check from Task 2's verify, repeated here as a behavioural sibling so the property is asserted in
   the file that claims it.
3. **Not through the process.** The re-wrap never calls `open_credential`, so no plaintext exists in
   the process at any point. Assert it by monkeypatching `prope.provider_access.crypto.open_credential`
   to raise `AssertionError` for the duration, and running the whole operation again on a second
   corpus. **This is the sharpest available form of clause 4**: it does not check that the plaintext was
   not written, it checks that it was never produced.

message quotes the ADR — *"It does not touch a single ciphertext"* — and says what a failure means: an
implementation that re-encrypted the credential would pass every one of AC-13's four clauses and would
