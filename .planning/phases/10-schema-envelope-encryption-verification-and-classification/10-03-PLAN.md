<objective>
Close PA-03. Make **"a provider that does not return a usage object cannot be registered"** a fact of
the system rather than a sentence in a lock file — which is the obligation ADR-0013 left here in as
many words: *"a provider that ignores include_usage is a provider-access admission question, not a
gateway workaround."*

The chain SC2 asks for has three links and each is enforced by a different mechanism, deliberately:

1. **Verification fails, with the reason naming the missing usage object.** The probe reads the
   response, finds no `usage`, and records `no_usage_object` — a token, not a sentence, so the reason is
   a value a metric can be labelled with and a dashboard can count.
2. **The configuration is not saved active.** Not by the command remembering to leave it disabled, but
   by `ck_provider_config_active_requires_verification`, which refuses `status = 'active'` while
   `last_verified_at IS NULL`. Plan 10-01 landed it; this plan is what makes it fire.
3. **It cannot be bound to a revision.** By the composite foreign-key target
   `uq_provider_config_bindable`, over a generated column that is true only once a verification has
   passed. **Phase 13 must point `registry.revision`'s foreign key at it**, and this plan is the one
   that says so loudly enough to survive three phases of distance.

This plan also lands the seam phase 12 is built to replace, and does not build phase 12's work.
`upstream.py` is the one place an `httpx.AsyncClient` is constructed; ADR-0047's address-pinning
transport goes in there and nowhere else. **No SSRF guard is claimed here.**

## D-170 — `last_verified_at` means the last verification that PASSED

**Chosen.** `last_verified_at` is written **only** on a pass and is never written back to NULL.
`verification_status` and `verification_error` carry the latest attempt's outcome, pass or fail. The
two columns are two different clocks on purpose.

**The alternative is the obvious reading — "the last time verification ran" — and it breaks
`bindable`.** `bindable` is `GENERATED ALWAYS AS (last_verified_at IS NOT NULL)`, and phase 13's
foreign key references `(id, bindable)`. If `last_verified_at` moved on every attempt and could be
nulled on a failure, then a configuration bound by ten released revisions would have its `bindable`
flip to `false` the first time an upstream hiccup failed a routine re-verify — and PostgreSQL would
**refuse the update**, because ten rows reference the pair. The result is a system where a transient
provider blip makes it impossible to record that the provider blipped.

So the monotonic column is the one `bindable` is generated from, and the volatile columns are the ones
an operator reads. **The lock's own two rules are consistent with this and only with this**: *"An
unverified configuration cannot be bound to a revision"* is about ever having passed, while *"A
dispatch is admitted only for a configuration whose status is active and whose last verification
passed"* is a dispatch-time rule reading `verification_status` — a different column, in a different
phase (11).

**Rejected: a separate `first_verified_at` column** to carry the monotonic half, leaving
`last_verified_at` volatile. It is the more literal reading of both names and it is refused because it
adds a column the lock's `data.owns` field list does not declare, on the table this module's whole
surface reads — and the same guarantee is available from a column that is already there, given a
definition. The definition is written in a `COMMENT ON COLUMN` (plan 10-01) so it is discoverable from
`psql` and not only from this file.

**Reversibility: costly.** `bindable` is generated from it and phase 13's foreign key references
`bindable`.

## D-171 — "Cannot be bound to a revision" is a composite foreign key, and phase 13 owns the other half

**Chosen.** `provider_config` carries `bindable boolean GENERATED ALWAYS AS (last_verified_at IS NOT
NULL) STORED` and `UNIQUE (id, bindable)` (landed in plan 10-01). A revision references
`(provider_config_id, provider_config_bindable)` with a local `CHECK (provider_config_bindable)`, which
makes it structurally impossible for a revision row to exist against a configuration that never passed
verification.

**The lock declares the foreign key and not the guarantee.** `data.referenced_by` says only
*"prompt-registry: `revision.provider_config_id` -> `provider_config.id`, a foreign key"*, while AC-3
requires that an unverified configuration *"cannot be bound to a revision"*. A plain single-column
foreign key cannot express a conditional target — it accepts any `provider_config.id` at all,
including one that has never been probed. **The declared mechanism does not implement the declared
criterion**, and that gap is `OQ-057`.

**Rejected: an application-level check in prompt-registry** — read the configuration, refuse if
`verification_status != 'passed'`. Refused on ORCHESTRATION §3's standing rule that the migration
carries the guarantee, and on a second ground specific to this seam: prompt-registry checking a
provider-access invariant means the invariant lives in the module that does not own it, and a second
writer (a data fix, a backfill, a future importer) bypasses it entirely. The project already has the
precedent it needs — the Approved-only release rule *"enforced by a database constraint, not by
application code"* is one of the four non-negotiables — and this is the same shape one module over.

**Rejected: a trigger on `registry.revision`.** Same effect, more machinery, and a trigger that
enforces a cross-schema rule is a cross-schema dependency that no dependency diagram shows.

**The consequence, and it is the load-bearing sentence of this plan.** Phase 10 can build the target
and cannot build the referencing side, because `registry.revision` does not exist until phase 13.
Phase 10 therefore proves the mechanism against a **temporary table** carrying the same composite
foreign key (plan 10-01, Task 5), which proves the target works and proves nothing about whether
anybody aims at it. **`deferred-items.md` §3 routes this to phase 13 by name, `OQ-057` states it, and
the 10-01 and 10-03 SUMMARYs both have to repeat it**, because a target nobody aims at is worse than no
target: it looks like a guarantee.

**Reversibility: one-way on the column** (it is generated and referenced), **cheap on the phase-13
half** (an FK is added or it is not).

## D-172 — The probe lists models first, then completes with a named model

**Chosen.** `probe_configuration` performs, in order: `GET {base_url}/models`, then
`POST {base_url}/chat/completions` with `max_tokens=1` against a model chosen by a stated rule —
the caller's `probe_model` if supplied, otherwise the **lexicographically smallest** model id the list
returned. An empty list and no `probe_model` fails verification with `no_models_listed`.

The order is what the lock's own end-to-end journey describes: *"Register a provider from the dashboard
→ probe passes → the catalogue populates"*. Doing the list first means one probe produces both facts —
the endpoint works and the catalogue has content — and it means plan 10-04's catalogue reconciliation
consumes a value the probe already fetched rather than making a second round trip.

**Rejected: probing with a hardcoded model name** (`gpt-3.5-turbo` or similar). It is a guess about a
third party's catalogue baked into Prope, and a self-hosted OpenAI-compatible endpoint — the exact case
`base_url` exists for — serves none of them.

**Rejected: taking the first model in the order the provider returned.** Verification would then depend
on the order a third party happened to serialise a JSON array in, which makes a failed probe
irreproducible. **Lexicographically smallest is arbitrary and deterministic**, and the docstring says
exactly that: arbitrary is fine, non-deterministic is not.

**Rejected: failing when the model list is empty even though a `probe_model` was supplied.** The lock
requires *"manual entry for models the endpoint omits"*, so an endpoint with an empty or unimplemented
model list is a supported shape, and refusing it would refuse a configuration the catalogue is designed
to accommodate.

**Reversibility: cheap.**

## D-173 — The HTTP client is a parameter; `upstream.py` is the only place one is built

**Chosen.** Every function in `probe.py` takes an `httpx.AsyncClient`. `upstream.py` holds one factory,
`build_upstream_client(...)`, which is the single construction site in the module and the single place
`follow_redirects=False`, the timeout and the transport are set.

**This exists for phase 12 and the plan says so at the code.** ADR-0047 requires that a dispatch
*"connects to the ADDRESS IT VALIDATED with the hostname preserved only for TLS SNI"*, implemented as a
custom `httpx` transport. If phase 10 scatters `AsyncClient(...)` across three call sites, phase 12
must find and change three; with one factory it changes one, and every existing call site inherits the
guard without being edited. **A phase that leaves the next phase a seam it can actually reach is worth
one extra module.**

**Rejected: constructing the client inside `probe_configuration`.** It is one fewer file today and it
is the shape that makes ADR-0047 a search-and-replace later, on the module where a missed call site is
an SSRF hole.

**Rejected: a module-level singleton client.** It would be constructed at import, before settings are
read, and it would be shared between `app` and `worker` semantics that ADR-0046 deliberately separates.

**Reversibility: cheap.**

### `src/prope/provider_access/upstream.py`

The whole module is one factory and its argument, and the docstring is most of its value.

```python
UPSTREAM_TIMEOUT_SECONDS = 10.0     #: A-090's hard timeout for the probe.
UPSTREAM_USER_AGENT = "prope/0.1"

def build_upstream_client(
    *,
    timeout_seconds: float = UPSTREAM_TIMEOUT_SECONDS,
    transport: httpx.AsyncBaseTransport | None = None,
) -> httpx.AsyncClient
```

returning `httpx.AsyncClient(timeout=httpx.Timeout(timeout_seconds), follow_redirects=False,
transport=transport, headers={"user-agent": UPSTREAM_USER_AGENT})`.

The docstring carries four things, and three of them are about what this module is **for**:

1. **This is the only place in Prope an outbound HTTP client is constructed**, because this module is
   Prope's only outbound egress (INT-023). A grep for `AsyncClient(` that finds one hit is the property;
   a test asserts it.
2. **`follow_redirects=False` is written explicitly even though it is httpx's default**, and the reason
   is quoted: *"a 302 is a resolution the guard never saw"* (ADR-0047). A default is not a decision
   anybody can see in a diff, and this one has to be visible.
3. **`transport` is a parameter and is `None` today. Phase 12 fills it** with ADR-0047's
   address-pinning transport — connect to the address that was validated, preserve the hostname for TLS
   SNI and certificate verification, never re-resolve. State plainly what is **not** true yet: **there
   is no SSRF guard in phase 10**, `base_url` is not validated against loopback, link-local or private
   ranges, and a phase-10 probe against an internal address would succeed. That is PA-11 / AC-11 /

### `src/prope/provider_access/probe.py`

Module docstring: A-090 (a live probe before a configuration may be bound), A-030 and ADR-0013's
closing obligation (*"a provider that ignores include_usage is a provider-access admission question,
not a gateway workaround"*), and the A-046 declaration — this module holds a decrypted credential in a
header and the provider's response body in a local, and it writes neither anywhere.

**The closed reason vocabulary**, as module constants beside a frozenset, in
`_classify_publish_failure`'s discipline — one place a value is chosen, so a fourth cannot appear by
accident:

```python
REASON_OK = "ok"
REASON_NO_USAGE_OBJECT = "no_usage_object"
REASON_NO_MODELS_LISTED = "no_models_listed"
REASON_CREDENTIAL_REJECTED = "credential_rejected"
REASON_UNREACHABLE = "unreachable"
REASON_TIMEOUT = "timeout"
REASON_BAD_RESPONSE_SHAPE = "bad_response_shape"
REASON_REDIRECT_REFUSED = "redirect_refused"
REASON_UPSTREAM_ERROR = "upstream_error"
VERIFICATION_REASONS = frozenset({...})
```

`REASON_NO_USAGE_OBJECT` gets its own comment: **this is the reason SC2 and AC-3 require to "name the
missing usage object"**, it is the value `verification_total{result="fail", reason=...}` carries, and it
is what `ProviderUsageMissing`'s sibling alert `ProviderVerificationFailing` is read against. The lock
also names `blocked_address` as a verification reason in its SSRF failure mode — **declare it here as
`REASON_BLOCKED_ADDRESS` with no producer**, on D-40's precedent, and say in one line that phase 12
produces it. A reason set that grows in phase 12 is a set that was not closed.

```python
@dataclass(frozen=True, slots=True)
class DiscoveredModel:
    model_id: str
    display_name: str

@dataclass(frozen=True, slots=True)
class ProbeOutcome:
    passed: bool
    reason: str                       #: a member of VERIFICATION_REASONS
    upstream_status: int | None
    provider_error_code: str | None   #: allow-listed; never the provider's message
    models: tuple[DiscoveredModel, ...]
    probed_model: str | None
```

`ProbeOutcome.__post_init__` asserts `reason in VERIFICATION_REASONS`, so an invented reason is a raise
at construction rather than an unbounded metric label later.

```python
async def probe_configuration(
    client: httpx.AsyncClient,
    *,
    base_url: str,
    credential: str,
    probe_model: str | None = None,
) -> ProbeOutcome
```

The sequence, and every step's failure lands on a named reason:

1. **`GET {base_url}/models`**, with `Authorization: Bearer {credential}`. Build the URL by joining a
   `base_url` whose trailing slash is normalised once, in a module-level helper, so
   `https://x/v1` and `https://x/v1/` produce the same request — a class of bug that costs an
   afternoon and is invisible in review.
   - A 3xx → `ProbeOutcome(passed=False, reason=REASON_REDIRECT_REFUSED, ...)`. ADR-0047: *"a provider
     that redirects its completions endpoint fails verification rather than being followed at dispatch
     time."*
   - A 401/403 → `REASON_CREDENTIAL_REJECTED`. A transport failure → `classify_transport(exc)` mapped
     onto `REASON_TIMEOUT` or `REASON_UNREACHABLE`. Any other non-2xx → `REASON_UPSTREAM_ERROR`.
   - A 2xx body that is not `{"data": [ … ]}` → `REASON_BAD_RESPONSE_SHAPE`.
   - **An empty list is not itself a failure** — it becomes one only at step 2, and only if no
     `probe_model` was supplied (D-172).
2. **Choose the model.** `probe_model` if given; else `min(model_ids)` if the list is non-empty; else
   `ProbeOutcome(passed=False, reason=REASON_NO_MODELS_LISTED, ...)`. The comment at `min()` says
   arbitrary-and-deterministic beats first-in-the-provider's-order, because a failed probe that cannot
   be reproduced is a support ticket nobody can close.
3. **`POST {base_url}/chat/completions`** with a body built from module constants:
   `{"model": chosen, "messages": PROBE_MESSAGES, "max_tokens": PROBE_MAX_TOKENS, "stream": False}`.
   `PROBE_MESSAGES = ({"role": "user", "content": "ping"},)` and `PROBE_MAX_TOKENS = 1`, both named
   constants with a comment: the probe **costs the workspace money**, one token's worth, and that is
   the smallest honest amount — a probe that does not really complete does not really verify. Say that
   `max_tokens=1` may make a provider return `finish_reason="length"`, which is **not** a failure and
   must not be classified as one.
   - Same status handling as step 1, with the same reasons.
4. **The usage check, which is the point of the whole function.** Parse the 2xx body as JSON. If it is
   not a mapping, or has no `choices`, → `REASON_BAD_RESPONSE_SHAPE`. If it has no `usage` key, or
   `usage` is not a mapping, or it lacks any of `prompt_tokens` / `completion_tokens` / `total_tokens`,
   or any of the three is not an `int` → **`REASON_NO_USAGE_OBJECT`**.
   Write the paragraph at this check: A-030 is *"Only providers returning a usage object are
   supported"*, A-089 makes requesting usage unconditional rather than a caller option, and the ±2%
   token-accuracy success metric **is a parse** — so a provider returning `usage: {}` or
   `usage: {"total_tokens": null}` is exactly as unsupportable as one returning no key at all, and the
   check is on the three fields rather than on the key's presence for that reason.
   **Do not parse into a strict pydantic model.** ADR-0015 requires unknown provider fields to pass
   through untouched, and a strict model is how that promise gets broken by accident. Read the three
   fields out of the mapping and leave the mapping alone.
5. On success → `ProbeOutcome(passed=True, reason=REASON_OK, upstream_status=200, models=…,
   probed_model=chosen)`.

**Exactly one chat-completions request per call**, whatever happens. No loop, no `except` that tries
again, no second attempt on a timeout. State it in the docstring with A-090 and A-088 both cited, and
Task 4 counts requests at the stub to prove it.

**Every non-2xx path runs the status through `classify_failure` from plan 10-02** and records the
resulting `ErrorClass` in the log fields — **not** in `verification_error`. Say why the two are
different: the reason token is provider-independent and countable; the error class is the taxonomy the
gateway branches on, and verification is not a dispatch. Using one for the other would give
`verification_total` a label whose value set is the dispatch taxonomy.

**`provider_error_code`** is read from the body at `error.code` and `error.type` **only**. The
provider's `error.message` is read nowhere, is stored nowhere, and there is no field on `ProbeOutcome`
that could hold it — T-026's mitigation expressed as a type rather than as discipline.

1. **Why ASGITransport rather than a real socket**: no port, no bind, no teardown race, deterministic,
   and fast enough to be used freely. And **what it therefore cannot test** — httpx's timeout handling
   is implemented in the transport layer and `ASGITransport` does not enforce one, so **a genuine
   wall-clock timeout cannot be provoked here**. `classify_transport(httpx.ReadTimeout(...))` is
   unit-tested directly in plan 10-02, and a real-socket timeout assertion is routed to phase 11 or 12.

2. **Why it records requests**: the exactly-one-attempt property (A-088, A-090) is a **count**, and a
   count needs a counter at the far end. `requests` is that counter and `auth_headers` is how a test
   asserts the credential arrived — which is also how a test asserts it arrived **only** in a header.
3. **That it is deliberately permissive about the request** — it parses the body and records it, and
   refuses nothing — because a stub that validated would hide the case where Prope sends something a
   real provider rejects.
