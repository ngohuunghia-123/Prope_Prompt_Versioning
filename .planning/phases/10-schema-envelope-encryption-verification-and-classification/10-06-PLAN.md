## D-178 — The forbidden edge is enforced by a source gate; the grant enforces something else, and each is labelled as what it is

**Chosen.** Two mechanisms, two claims, two labels.

**What a grant can enforce.** All eight modules are Python packages in one process holding one
`prope_app` password (ADR-0027 rejected role-per-module by name: *"it means eight credentials and eight
connection pools carried by the application"*). PostgreSQL sees one role. **No grant can distinguish
provider-access's query from prompt-registry's**, and any plan claiming otherwise is claiming something
the database cannot do.

What the grant genuinely enforces is a different, real thing: **`prope_report` cannot read
`provider.credential`** (D-166). That is a privilege-level refusal, provable by provoking the engine,
with a positive control on the two sibling tables — and it is the only one of its kind this phase can
make.

**What enforces the module boundary.** A source gate: an AST walk over every module under
`src/prope/`, discovered by `rglob`, asserting that the `credential` table name, the credential model,
`prope.provider_access.crypto` and `prope.provider_access.keyring` are named **only** inside
`src/prope/provider_access/`. It is the same posture and the same file shape as
`tests/architecture/test_no_sql_interpolation.py`, whose own docstring already argues for it: *"a
runtime test can only prove that the inputs it happened to try were safe, while this proves that no
interpolated statement exists to try."* Substitute "no cross-module read exists to try".

**Its limits are stated in its own docstring rather than discovered by a reader.** It cannot see a
dynamic import, a `getattr` on a module object, or raw SQL assembled from fragments. It is a
grep-with-a-parser, and the honest claim is *"the ordinary form of this mistake is refused on the day
it is written"* — not *"this is impossible"*. **Do not overclaim in the docstring**; the whole value of
labelling the layers is lost the moment one of them is described as more than it is.

**Rejected: a database role per module.** ADR-0027 rejected it, and re-proposing it here would be
re-litigating a settled decision to buy a guarantee the source gate substantially provides.

**Rejected: no source gate, relying on the table separation alone.** ADR-0014's separation stops a
`SELECT *` on `provider_config` from returning ciphertext. It does nothing about a module deliberately
querying `provider.credential`, which is exactly what the forbidden edge names.

**Reversibility: cheap.** A test file with an `ALLOWED` escape hatch that is empty and meant to stay
that way.

One file, one property, and a docstring that is careful about what it claims.

**The docstring, in three paragraphs.**

*What the rule is.* `.claude/CLAUDE.md`'s forbidden-edge list reads *anything → credential*.
provider-access is the only module in Prope that decrypts anything, and the lock's own security
requirement is that a credential *"never crosses a module seam in either direction"*. This gate is one
of **three** layers, and it says which: ADR-0014's table separation (structural — a `SELECT *` on
`provider_config` cannot return ciphertext), D-166's grant (privilege — but it constrains
`prope_report`, **not** another module), and this walk (source).

*Why a grant cannot do this job.* All eight modules are packages in one process holding one `prope_app`
password (ADR-0027). PostgreSQL sees one role and cannot distinguish provider-access's query from
prompt-registry's. **State that plainly**, because the natural reading of "enforce it with grants" is
that the database refuses the cross-module read, and it does not.

*What this gate cannot see.* A dynamic import, a `getattr` on a module object, a table name assembled
from fragments at runtime, or a query built by an ORM whose model was imported under an alias this walk
does not recognise. **It is a grep with a parser.** The honest claim is that the ordinary form of the
mistake is refused on the day it is written, and the docstring says exactly that rather than something
stronger.

**The implementation.**

```python
SOURCE_ROOT = Path(__file__).resolve().parents[2] / "src" / "prope"
OWNING_PACKAGE = "provider_access"

#: Names that may appear only inside src/prope/provider_access/.
FORBIDDEN_ELSEWHERE = (
    "provider.credential",     # the qualified table name in any SQL string
    "prope.provider_access.crypto",
    "prope.provider_access.keyring",
)

#: Explicit, reasoned exceptions: (module path relative to src/prope, why).
#: Empty, and meant to stay that way. An entry here is a sentence somebody signed.
ALLOWED: frozenset[tuple[str, str]] = frozenset()
```

Three checks over every `.py` file `rglob`'d under `SOURCE_ROOT` whose path does **not** contain
`OWNING_PACKAGE`:

1. **String constants.** Walk the AST for `ast.Constant` nodes holding a `str`, and fail any containing
   `provider.credential` or the bare table name `credential` **as a whole word inside a SQL-shaped
   string** — match the qualified form for certainty and, for the bare word, only inside strings that
   also contain a SQL keyword (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, `FROM`, `JOIN`). Comment the
   two-part test: the bare word `credential` appears in ordinary prose all over this project's
   docstrings, and a gate that failed on a docstring would be turned off within a week. **A gate people
   turn off is worse than no gate**, and that sentence belongs in the file.
2. **Imports.** Walk `ast.Import` and `ast.ImportFrom` and fail any that names
   `prope.provider_access.crypto` or `prope.provider_access.keyring`, at any depth, including
   `from prope.provider_access import crypto`.
3. **The credential model.** Fail any import of the credential `Table` object from
   `prope.provider_access.models` by name. Import the model's actual attribute name from the module
   under test rather than hardcoding a string, so a rename in plan 10-01's `models.py` cannot silently
   defeat the gate — **a security gate written against a string constant is a gate a rename disarms.**

Then two assertions that keep the gate from passing vacuously — the failure mode
`assembled_routes()` exists to prevent, one layer over:

- **the file list is non-empty**, and specifically contains at least one module from another package

- **the gate detects a planted violation.** Parse a small SQL string and a small import statement

  that nothing happened.

Finally, the escape-hatch test, copied in spirit from `test_every_global_table_exemption_carries_a_written_reason`:
an `ALLOWED` entry with a blank reason fails. The escape hatch exists so that an exception is a sentence
a reviewer disagrees with, not a rule that quietly stopped applying.

### `tests/security/test_report_role_cannot_read_credentials.py`

**The refusal.** Through `report_engine`, `SELECT id FROM provider.credential` raises an
insufficient-privilege error. Assert on the **error class or SQLSTATE `42501`**, not on a message
substring, and assert it is **not** an undefined-table error — those are two very different bugs with
one symptom, and a test that accepted either would pass against a schema that failed to deploy.

**Two positive controls, not one.** `SELECT id FROM provider.provider_config` and
`SELECT id FROM provider.model_catalogue` both **succeed** through the same engine, cross-tenant, with
rows present in two workspaces. The pair proves three things at once: the engine works, the schema
deployed, and the withholding is specific to one table rather than a schema-wide grant that was
forgotten.

**The docstring is most of this file's value**, and it carries four things:

1. **D-166 and its ground**, quoting ADR-0014's threat model: *"a `SELECT` from an application bug, a
   backup file copied to a laptop, a read replica with looser access."* ADR-0037 describes
   `prope_report` as a full-read credential *"issued to a person rather than to a process"*, which is
   the third of those three sentences with a login attached.
2. **This does not affect the backup.** ADR-0037's own line: the dump runs as the host `postgres`
   superuser. A restored cluster carries every credential. Say it explicitly, because
   "credentials are excluded from the backup" is the conclusion a reader will otherwise reach and it
   would be a serious one to reach wrongly.
3. **It is defence in depth, not a requirement.** Plan 10-01's SC1 test says the ciphertext is useless
   without the KEK, so a `prope_report` SELECT is not itself a compromise. What changes is the answer to
   ADR-0037's own framing question — *"what could this credential do if it leaked"* — from "hand over the
   entire ciphertext corpus" to "not that". **Do not overstate it beyond that.**
4. **The tension, named**, with `OQ-059` cited: ADR-0037's Consequences say `prope_report` *"reads
   everything and changes nothing"*, and after this phase that is untrue by one table.

**And the deliberate pair.** Reference `tests/security/test_report_role_can_read_bodies.py` by path in
the docstring and state the contrast in one sentence: phase 3 **left** the reporting role's read of
`ledger.call_body` and recorded the exception; phase 10 **withholds** it for `provider.credential`. The
difference is the one ADR-0021 already draws — a stored body is data the product exists to record,
while a stored credential is a third party's secret Prope holds under a non-negotiable — and a reader
comparing the two files should find that difference argued rather than inferred.

### `tests/architecture/test_provider_schema_surface_is_closed.py`

An inventory a reviewer can read, in five assertions, all through `migrate_engine`:

1. **Exactly three tables** in `provider`, by name, as a sorted set equality against a literal — so a
   fourth table added in phase 11 or 12 is a red test in the phase that adds it rather than a
   discovery later.
2. **No `SECURITY DEFINER` function** in the `provider` schema — `pg_proc.prosecdef` false for every
   function in the namespace, including the monotonicity trigger's, which plan 10-01 declared
   `SECURITY INVOKER` explicitly. The docstring points at phase 7's project-wide four-and-only-four
   test rather than duplicating it, and says what this one adds: **the trigger function is the one
   object in this phase that could have become a fifth by inattention.**
3. **All three tables are tenant-scoped**, each with row security enabled and a policy, and **none of
   them appears in `GLOBAL_TABLES`** — the lock's own claim, *"No table in this schema appears in
   `GLOBAL_TABLES`"*, asserted directly here as well as inherited from
   `test_tenant_coverage.py`'s generic walk. Two assertions of the same property from different
   directions is deliberate: the generic walk would also pass if somebody added a `GLOBAL_TABLES`
   exemption, and this one would not.
4. **No money anywhere in the schema.** No column name matching `%price%`, `%cost%` or `%currency%`,
   and no column of type `numeric`, `real` or `double precision`, across all three tables — the
   schema-wide form of the assertion plan 10-04 makes at the type.
5. **No column outside `credential` has a `bytea` type.** The sealed values live in exactly one table,
   which is ADR-0014's separation asserted as a shape rather than as an intention: a ciphertext column
   appearing on `provider_config` would be caught here on the day it appeared, and that is the exact
   mistake the separation exists to prevent.
