## D-160 — The whole `provider` guarantee stack ships in ONE revision

**Chosen.** Three tables, three tenant policies, three grant blocks, four CHECK constraints, one
UNIQUE that makes a secret's history impossible, one generated column with its FK target, and one
trigger — all in a single Alembic revision.

**Rejected: one revision per kind** (tables / RLS / grants / constraints), which the phase-1 research
recommended in general and which `alembic/ddl.py`'s own docstring already declines. A tracer's value is
proving the stack connects **in a single applied migration**; a chain of four revisions has three
intermediate states in which `provider.credential` exists and is readable across tenants, and a deploy
interrupted between two of them leaves one of those states running. This repeats D-96's reasoning
because the reasoning is the same and rediscovering it costs a phase.

**Rejected: a second revision later in this phase** for the `bindable` column plan 10-03 needs.
Splitting a generated column away from the table that generates it means plan 10-03 owns a migration,
and a phase with two revisions in flight is a phase where `alembic heads` is read twice and wired
wrong once.

**Reversibility: costly.** A landed revision is never edited; a change is a new revision.

## D-161 — Three explicit `SecretStr` KEK slots on the ONE `Settings` class

**Chosen.** `Settings` in `src/prope/db/engine.py` gains `kek_v1`, `kek_v2` and `kek_v3`, each
`SecretStr | None = None`, mapping to `PROPE_KEK_V1`…`PROPE_KEK_V3` through the existing `PROPE_`
prefix. `build_key_ring(settings)` assembles the version → raw-bytes mapping A-135 describes.

**Rejected: a second `BaseSettings` subclass** in `src/prope/provider_access/`. That module's own
docstring already refused it, in writing, for `broker_url`: *"ADR-0032 gives the host one `.env`, and
two settings objects reading it is two places to forget a key."* The reasoning has not changed and a
KEK is the worst key to forget.

**Rejected: `extra="allow"` plus a validator that harvests every `PROPE_KEK_V<n>`.** It is the only
shape that supports an unbounded number of versions, and it is refused on a specific hazard rather than
on taste: pydantic's extra fields are plain `str`, not `SecretStr`, so a `Settings` repr — in a
traceback, a debugger frame, a `model_dump()` in an error report — would print every KEK in full. The
lock's own rule is that *"nothing reads `os.environ` wholesale into a log line, error report, or metric
label"*, and `extra="allow"` is precisely that with an extra step. `SecretStr` is what makes a repr
safe, and a declared field is what gets you `SecretStr`.

**The cost, stated rather than discovered:** three slots is a ceiling. Two live rotations can be in
flight before anyone edits code; a fourth version is one line in the one file that already holds every
other setting. **A tunable judgement, not a repo decision, recorded so that changing it is a visible
act.**

**Reversibility: cheap.** One line per slot.

## D-162 — `wrapped_dek` carries its own nonce; there is no fourth column

**Chosen.** `wrapped_dek` stores `nonce(12 bytes) || AESGCM(kek).encrypt(nonce, dek, aad_dek)` as one
`bytea`. The credential ciphertext keeps its own separate `nonce` column, which is the one the lock's
field list names.

**The conflict this resolves, and it is a real one.** `data.owns.credential.fields` lists
`ciphertext, nonce, wrapped_dek, kek_version` — **one** nonce. AES-GCM needs a fresh nonce per
encryption, and envelope encryption performs **two**: the secret under the DEK, and the DEK under the
KEK. A single KEK wraps every DEK in the system, so reusing one nonce across wraps is the catastrophic
misuse of GCM — it leaks the XOR of plaintexts and forges authentication tags. The declared field list
cannot be implemented as written.

**Rejected: adding a `dek_nonce` column.** It is the more legible shape and it is refused because it
edits a lock file's declared field list by fact rather than by conversation. Prefixing keeps the
declared list exactly true and makes `wrapped_dek` a single self-contained value with no way to pair it
with the wrong nonce.

**Rejected: a deterministic nonce derived from `credential_id`.** It is stable across a re-wrap, which
is exactly when the same DEK gets wrapped again under a new key — and a derived nonce plus a rotated
KEK is still nonce reuse the moment someone rotates back. Fresh random nonce, every wrap, no exceptions.

**Raised as `OQ-056`, not absorbed.** Either answer is defensible; a field list that cannot be
implemented is not.

**Reversibility: one-way.** These are stored bytes. Changing the layout after credentials exist is a
data migration that must decrypt every credential, which is the migration ADR-0014 exists to avoid.

## D-163 — Both encryptions are bound to the row by AAD

**Chosen.** Both AES-GCM operations take additional authenticated data derived from the row's own
immutable identity: `prope/credential/v1|<purpose>|<credential_id>|<workspace_id>|<provider_config_id>`,
with `<purpose>` being `secret` for the credential and `dek` for the wrap.

Without it, the sealed values are **portable**: an attacker with write access could move workspace A's
`(ciphertext, nonce, wrapped_dek, kek_version)` onto workspace B's credential row and Prope would
decrypt it happily and present it to workspace B's provider. GCM's authentication tag proves the bytes
were not altered; only the AAD proves they belong to *this* row. The three components are the three
that never change for the life of a row — and this is one of the two reasons rotation is an UPDATE in
place rather than a delete-and-insert (plan 10-05, D-176).

**Rejected: no AAD.** It is what the naive reading of "encrypt the credential" produces, and it makes
the confused-deputy attack a copy of four columns.

**Reversibility: one-way**, for D-162's reason.

## D-164 — All fourteen metrics are defined at import, in a per-module observability module

**Chosen.** `src/prope/provider_access/observability.py` defines every metric the lock's
`observability_requirements.metrics` block declares — all fourteen — at import, even though ten of
them have no increment site until plans 10-02 through 10-05 and phases 11 and 12.

The precedent is D-40 and the argument is unchanged: **a metric that first appears the moment it goes
non-zero has no baseline, and no alert can be written against a series that does not exist.**
`prope_provider_access_usage_missing_total` is the sharp case, because its whole job is to be zero and
`REGISTRY.get_sample_value` returns `None` — not `0.0` — for a metric nothing has touched.

The **file** follows `src/prope/property_history/observability.py`, not `src/prope/observability.py`:
the shared module holds `LOGGABLE_FIELDS` and call-ledger's eighteen, and a second module's fourteen
landing in it would make one file the metric registry for eight modules.

**Consequence for phases 11 and 12, recorded so they do not duplicate it:** they inherit these
fourteen already defined and must add increment sites, not definitions. Phase 12's spec routing names
the metrics block, which is about asserting them, not about creating them.

**Reversibility: cheap.**

## D-165 — A failed registration saves a DISABLED row; it does not save nothing

**Chosen.** `register_provider_config` always lands `status = 'disabled'`,
`verification_status = 'unverified'`, `last_verified_at = NULL`. Verification is a **second** command
(plan 10-03) that flips it. `POST /api/v1/providers` (phase 11) composes the two.

**Rejected: probe-then-insert, leaving no row when verification fails** — which is the literal reading
of `apis.exposes`' *"is probed live before the record is saved active"*. It is refused on the lock
file's own columns: `verification_status` and **`verification_error`** are declared fields on
`provider_config`, the `ProviderVerificationFailing` alert fires on *"a spike on a previously passing
configuration"*, and `prope_provider_access_verification_total{result=fail, reason}` is a declared
metric. **A column that can never be populated is a column nobody built**, and an alert about a
configuration that was never saved has nothing to fire about. "Not saved *active*" is satisfied by a
saved-and-disabled row, and only that reading makes the other three declarations true.

The consequence is real and belongs in the open: a registration with a bad credential leaves an
encrypted bad credential at rest. That is the same posture rotation has, and it is why the credential
row is replaced in place rather than appended to.

**Reversibility: costly** — it is the shape phase 11's route composes and phase 12's sweep reads.

## D-166 — `prope_report` is NOT granted SELECT on `provider.credential`

**Chosen.** `grant_table("provider", "credential", app_privileges=[...], report_select=False)`. It is
the first use of that parameter in the project, and the first table in Prope the reporting role cannot
read.

**The ground is ADR-0014's own threat model**, quoted rather than paraphrased: *"a `SELECT` from an
application bug, a backup file copied to a laptop, a read replica with looser access."* ADR-0037
describes `prope_report` as a full-read credential *"issued to a person rather than to a process"* —
which is the third of those three sentences with a login attached.

**It does not affect the backup.** ADR-0036's dump *"continues to run as the host `postgres`
superuser, because a `SELECT`-only role cannot dump schema"* (ADR-0037, Decision). A restored cluster
still carries every credential.

**It is defence in depth, not a requirement, and the plan says so.** SC1 asserts that the ciphertext
is useless without the KEK, so a `prope_report` SELECT is not itself a compromise. What it changes is
the answer to ADR-0037's own framing question — *"what could this credential do if it leaked"* — from
"hand over the entire ciphertext corpus" to "not that".

**The tension is real and is raised as `OQ-059` by plan 10-06**, because ADR-0037's Consequences say
`prope_report` *"reads everything and changes nothing"*, and this makes that sentence untrue by one
table. The reversal is `report_select=True` in a follow-up revision — one line.

**Reversibility: cheap.**

### `src/prope/provider_access/keyring.py`

```python
KEK_BYTES = 32          #: AES-256. AESGCM refuses 16/24/32 mismatches itself; this is the one we mean.

class KekUnavailable(RuntimeError): ...

@dataclass(frozen=True, slots=True)
class KeyRing:
    #: version -> 32 raw bytes. Never printed: __repr__ prints the SORTED VERSION
    #: NUMBERS and nothing else.
    _keys: Mapping[int, bytes]

    @property
    def versions(self) -> tuple[int, ...]: ...
    @property
    def wrapping_version(self) -> int: ...     # max(versions); raises KekUnavailable when empty
    def key_for(self, version: int) -> bytes: ...  # raises KekUnavailable naming the VERSION only

def build_key_ring(settings: Settings) -> KeyRing: ...
```

`build_key_ring` decodes each present slot with `base64.b64decode(value, validate=True)` and requires
exactly `KEK_BYTES` bytes, raising `KekUnavailable` naming **the version number and the reason**
(`not base64` / `wrong length`) and **never the value or its length in characters**. An empty ring is
not an error at construction — it is an error at `wrapping_version` and at `key_for`, because
`/readyz` (phase 12) needs to be able to *observe* an empty ring rather than fail to import.

`wrapping_version` is `max(versions)` and its docstring is A-135 quoted: *"the highest present wraps,
and a rotation re-wraps every `wrapped_dek` without ever touching a plaintext credential."* Say the
consequence out loud: **adding `PROPE_KEK_V2` to `.env` changes what new and re-wrapped credentials
are wrapped under, immediately, with no code change** — which is the intended mechanism and is also
the way someone rotates by accident.

Every `KekUnavailable` raise sets `kek_unavailable.set(1)` and every successful `key_for` sets it to 0
— the gauge the `ProviderKekUnavailable` page reads. Its docstring says what the gauge does **not**
mean: it is not a provider outage, and confusing the two costs *"an hour of debugging the wrong seam
at exactly the wrong moment"* (ADR-0014).

### `src/prope/provider_access/crypto.py`

Module docstring at `fallback.py`'s density, carrying ADR-0014's decision, D-162's framing with
`WRAP_NONCE_BYTES` named, D-163's AAD construction quoted as a literal template, and the A-046
declaration every module in this package carries — this one more than most, because it is the only
module in Prope that holds a plaintext credential in a local variable.

```python
DEK_BYTES = 32
NONCE_BYTES = 12          #: the credential ciphertext's nonce
WRAP_NONCE_BYTES = 12     #: the prefix inside wrapped_dek (D-162)
AAD_VERSION = "prope/credential/v1"

def _aad(purpose: str, *, credential_id, workspace_id, provider_config_id) -> bytes
def seal_credential(secret: str, *, key_ring, credential_id, workspace_id,
                    provider_config_id) -> SealedCredential
def open_credential(sealed: SealedCredential, *, key_ring, credential_id, workspace_id,
                    provider_config_id) -> str
def rewrap_data_key(sealed: SealedCredential, *, key_ring, target_version,
                    credential_id, workspace_id, provider_config_id) -> SealedCredential
```

- `_aad` builds `f"{AAD_VERSION}|{purpose}|{credential_id}|{workspace_id}|{provider_config_id}"
  .encode("utf-8")` with `purpose` one of two module constants `AAD_PURPOSE_SECRET = "secret"` /
  `AAD_PURPOSE_DEK = "dek"`. The docstring states the three components are the three that never change
  for the life of a row, and that this is the second reason rotation is an UPDATE in place.
- `seal_credential` refuses a secret shorter than `MIN_CREDENTIAL_LENGTH` with a `ValueError` whose
  message names **neither the secret nor its length** — "credential is shorter than the minimum" and
  nothing more, because an error body that reports a length is an oracle.
  It generates a fresh DEK with `AESGCM.generate_key(bit_length=256)`, a fresh `NONCE_BYTES` nonce and
  a fresh `WRAP_NONCE_BYTES` nonce with `os.urandom`, encrypts the secret's UTF-8 bytes under the DEK
  with the `secret` AAD, wraps the DEK under `key_ring.key_for(key_ring.wrapping_version)` with the
  `dek` AAD, and returns `SealedCredential(ciphertext, nonce, wrap_nonce + wrapped, wrapping_version)`.
  **It does not compute `last_four`** — that is `credentials.py`'s, and the docstring says why: this
  module's contract is that a plaintext enters and never leaves, and a function that returns a
  fragment of the plaintext is a function someone will call for the fragment.
- `open_credential` slices `wrapped_dek[:WRAP_NONCE_BYTES]` and the remainder, unwraps, decrypts,
  decodes UTF-8, and observes `credential_decrypt_seconds` with `cache="miss"` — the only label value
  this plan produces; `cache="hit"` is the 60 s cache's, which is **phase 11's (PA-08)**, and the
  docstring says so at the label rather than leaving a reader to wonder why a hit never appears.
  `InvalidTag` from either layer propagates **unchanged and uncaught**. Write the reason: an
  authentication failure means the stored bytes were altered, moved between rows, or wrapped under a
  different key, and every one of those is a security event that must not be reported as a decryption
  that returned something.
- `rewrap_data_key` unwraps with `sealed.kek_version` and re-wraps with `target_version`, returning a
  new `SealedCredential` whose `ciphertext` and `nonce` are **the same objects it was given**. Its
  docstring carries AC-13 and ADR-0014's *"It does not touch a single ciphertext"*, and states the
  invariant plan 10-05 asserts byte-for-byte. The DEK plaintext exists in a local for the duration of
  the call and in nothing else.

**No logging in this module at all.** State that as a rule in the docstring, not as an accident: there
is no `log` binding, no `structlog.get_logger()` call, and the only observability is the two metric
touches. A module holding a plaintext credential with a logger in scope is one `log.debug(locals())`
away from the incident this project is shaped to prevent.
