## D-254 — "One indexed read" is proven with `EXPLAIN` over a real corpus, never with a timing and never with a planner switch

**Chosen.** `tests/integration/test_activity_is_one_indexed_read.py` seeds a corpus large enough that a
sequential scan is a live alternative, runs `ANALYZE history.history_event` as the owner, and then runs
`EXPLAIN (FORMAT JSON)` of the **statement `read()` actually issues**, as `prope_app`, inside a
`workspace_transaction`. It asserts three things about the plan tree:

1. some node is an `Index Scan` or `Index Only Scan` **using
   `ix_history_event_workspace_id_scope_prompt_id_seq`** by name;
2. **no** node is a `Seq Scan` on `history.history_event`;
3. **no** join node of any kind appears — no `Nested Loop`, `Hash Join` or `Merge Join`.

**The third assertion is the one the criterion is actually about.** *"One indexed read"* is not a
performance claim; it is the claim that the Activity screen does **not** assemble itself by joining four
modules' tables, which is the shape A-119 was written to make unnecessary and the module graph forbids
anyway. A test that only asserted "an index was used" would pass a query that used an index and then
joined three more.

**Rejected: asserting a latency instead.** A timing over a small corpus passes with a sequential scan,
and the orchestrator's own instruction says it: *prove it with `EXPLAIN`, not with a timing.*

**Rejected: `SET LOCAL enable_seqscan = off`.** It is the obvious way to make the test deterministic on a
small table and it destroys the assertion's meaning: it proves the index is **usable**, which nobody
doubted, rather than that the planner **used** it, which is the criterion. **Instead, make the choice
real**: seed on the order of a few thousand events across several prompts and several workspaces, so the
selective predicate genuinely beats a scan, and `ANALYZE` first so the planner has statistics rather
than defaults. Write both sentences in the test's docstring — the next person to see this test flake on
a smaller corpus will reach for the switch.

**The honest caveat, stated rather than left for a reviewer to find**: a query plan is a property of the
data as much as of the schema, so this test asserts the plan **for a corpus it built**. It cannot prove
the plan at pilot scale. What it can prove — and what makes it worth having — is that the index exists,
that it is the one the criterion names, and that nothing in the query defeats it.

**A pre-flight assertion runs first**: `ix_history_event_workspace_id_scope_prompt_id_seq` exists in
`pg_indexes` with the expected column list. Phase 4 creates it and this plan verifies rather than
assumes; **if it is absent or its columns differ, stop and raise it** — the orchestrator's instruction
is explicit that this index lives on property-history's table, not on this module's, and that its
absence is an open question rather than something to build here.

**Reversibility: cheap** — it is a test.

## D-255 — The Activity response is the event as property-history stored it, with nothing denormalised and no `module` field

**Chosen.** `ActivityEvent` carries exactly what `read()` returns: `seq`, `id`, `action`, `target_type`,
`target_id`, `actor_type`, `actor_id`, `reason`, `details`, `occurred_at`. No name, no email, no display
name, no prompt title, and **no `module` field.**

**Why no `module` field**, given that ROADMAP SC3 is phrased in terms of *"all four writing modules"*:
which module wrote an event is not a column on `history_event` and does not need to be. The `action` is
from a closed thirty-one-name vocabulary (ADR-0024, A-120) and each name belongs to exactly one writer,
so *"which module"* is derivable from the action by anybody who cares and is not a fact a client should
branch on. Inventing a field for it would be denormalising a mapping that lives in the action registry,
where INT-008 already exposes it as data.

**Why nothing about the actor beyond the id.** ADR-0054 tombstones a departing person and keeps
`actor_id` as **an opaque surviving value** — that is what makes *"history rows are never deleted"* free.
A response that carried a display name would outlive the tombstone in every client cache and every
screenshot. Phase 9's AC-15 owns the rendering rule (*"the API returns the catalogue key, never a name
or email, for a tombstoned actor"*); this route stays on the right side of it by carrying no name at
all.

**`details` is passed through as an opaque object**, not modelled field by field. Its keys are
**allow-listed per action** by property-history at append time (A-124), which is what stops a prompt
body or a credential reaching the audit log through an undeclared field. Re-modelling it here would
either restate that allow-list — a second copy of a thirty-one-action mapping — or narrow it, dropping
keys a later phase registered. One sentence at the model says both halves.

**`status` and every other vocabulary value stays literal** (ADR-0053 rule 9). The client translates the
`action` through its catalogue; the API does not.

**Reversibility: cheap.**

### `src/prope/prompt_registry/activity.py` — new

A small module holding the composition, so `api.py`'s handler stays the same shape as the other nine.

Module docstring, four paragraphs:

1. **What this file is**: the Activity view, and the only place in this module that reaches
   property-history's read seam. Name INT-007 and A-044.
2. **The cycle break, stated as the reason for the ordering.** property-history checks **no** permission
   and has no way to — no actor parameter, no import of access-control. So *"may you see this subject"*
   is answered **here, before the read**, and a caller that reached `read()` without having asked would
   have leaked another workspace's decision trail. RLS is the backstop (ADR-0045), **not** the control.
   Write that sentence; it is INT-007's own.
3. **Why the events come from four modules and this file joins nothing.** `scope_prompt_id` is stamped
   at append by every writer (INT-006, A-119). That single column is what makes the Activity one read
   instead of a join across four modules' tables — a join this module's `forbidden_dependencies` would
   refuse anyway. So the filter is `scope_prompt_id` and nothing about origin, and an event's writer is
   recoverable from its `action` (D-255).
4. **Ordering is `seq`, never `occurred_at`** (A-125, A-076). Approve-and-release writes two events with
   the same timestamp inside one transaction; a timestamp sort would show the one screen whose job is
   the sequence of decisions in an arbitrary order for exactly the two-event case that matters most.
   This module does not sort at all — `read()` does — and this paragraph exists so nobody adds a
   `sorted(...)` here.
