<objective>
Serve the four routes that change something: register a prompt property, edit its mutable fields, retire
it, and create the next immutable revision. All four are **thin over phase 13's commands** — this plan
writes no `INSERT`, no `UPDATE`, and appends no history event — and all four are almost entirely about
**refusal shape**, which is where a management API earns or loses its credibility.

Seven distinct refusals ship here. Each one has to be the right status, the right machine code, and the
right amount of information: enough that a person can fix their mistake, and not so much that the
response answers a question the actor was not entitled to ask.

## D-251 — The write routes are thin over phase 13's commands, and the permission read is a separate transaction

**Chosen.** Each write route: opens one `workspace_transaction`, asks INT-002 once, reads the subject
row through the repository, calls `refuse_unless_permitted`, **closes that transaction**, and then calls
phase 13's command — which opens its own transaction, re-checks its own invariants, writes, and appends
its history event on the same session (ADR-0023).

**Two transactions, and the window between them is stated rather than hidden.** Between the permission
read and the command's write, another actor can change the row. What that costs is bounded by where the
guards live, and that is the whole reason this shape is acceptable:

- **The safety-critical guards are inside the command's transaction, not in the route.** Phase 13's
  D-232 puts the retire guard's pointer read in the same transaction as the status write *"so the check
  and the write cannot be separated by another writer"*, and phase 13's migration carries
  `ck_prompt_property_retired_has_no_release` underneath as the backstop that survives a second writer
  entirely. The route's read decides **permission**; the command's read decides **legality**.
- **ADR-0020's model is exactly this.** *"The caller passes `owner_id` and `access_level` from the row
  they already read."* A permission decision is a decision about a row somebody read a moment ago;
  making it atomic with the write would mean holding access-control's read inside every command, which
  is the coupling ADR-0020 exists to remove.

**Rejected: threading the route's session into phase 13's commands** so the check and the write share a
transaction. It would require editing four functions that ship a phase earlier, whose own guards are
already inside their transactions, and whose signatures the phase-13 tests are written against —
trading a real regression risk for a window whose worst case is a 403 that would have been a 200 a
second earlier.

**Rejected: re-checking permission inside the command.** That is the second `if` ADR-0020 refuses, and
it would put an access-control call inside a function evaluation and release-control also call.

**Reversibility: cheap** — if the window ever matters, the repair is to pass a session, and phase 13's
commands are the four places it would land.

## D-252 — One route declares ONE action and may CHECK a second; `PATCH` is where that first happens

**Chosen.** `PATCH /api/v1/prompts/{prompt_id}` declares `prompt.edit` through `declares_action` — one
member, because that is what a route table can carry and what phase 23's AC-10 asserts — and calls
`may()` a **second** time for `prompt.transfer_owner` when, and only when, the request moves `owner_id`.
A caller holding `prompt.edit` and not `prompt.transfer_owner` gets a **403 naming
`prompt.transfer_owner`**, and the owner is unchanged.

The second refusal is a **403 and not a 404**, and the asymmetry is deliberate: by the time this check
runs the actor has already been told the prompt exists — they could read it — so hiding *which*
permission is missing would make the product unusable without hiding anything. Phase 9's D-131 states
that split; this is its first multi-permission instance.

**The gap this exposes is raised as `OQ-079` and not filled here.** The lock's PATCH line covers
*"title, purpose, tags, access level, owner"*. INT-001 gives this module `prompt.change_owner` and
`prompt.change_access`; **A-115 spells the first `prompt.transfer_owner` and has no member at all for
the second**, because its `prompt.grant` is about `access.prompt_grant` rows and phase 8 has already
assigned it to access-control's grants routes. So changing a property's `access_level` — the column that
decides whether a prompt is private — rides on `prompt.edit` in this plan, which is the **narrowest
existing action that covers it** and is what phase 7's D-99 (A-115 wins) leaves available.

**Rejected: minting `prompt.change_access` as a twenty-sixth vocabulary member.** `vocabulary.Action` is
mirrored by `role_permission.action`'s `CHECK` in another module's migration; adding a member here is a
cross-module schema change taken to avoid writing down a question.

**Rejected: refusing every `access_level` change until the question is answered.** It would make a
declared, `CHECK`-constrained column unwritable and would break phase 15's own SC1 fixture, which needs
a prompt to become `workspace`.

**Reversibility: cheap on the route, costly on the vocabulary** — if `prompt.change_access` is minted
later, every workspace's role matrix has to be told about it.

## D-253 — The refusal vocabulary: 422 for the caps (not 413), 409 for the two conflicts, and INT-016 never refuses at all

**Chosen**, five refusals and one non-refusal:

| Condition | Status | Code | Carries |
|---|---|---|---|
| model name malformed (not `namespace/name`, empty part, `/` inside a part, over the length cap) | 422 | `model_name_invalid` | the two parts as submitted |
| model name already taken, case-insensitively | 422 | `model_name_taken` | `namespace` and `name` as submitted |
| body over 32 KiB in UTF-8 | 422 | `body_too_large` | the **actual byte size** and the cap |
| change summary absent, empty, or over 200 characters | 422 | `change_summary_invalid` | the actual length and the cap |
| revision-number collision surviving the command's one retry | 409 | `revision_conflict` | the prompt id and the number that collided |
| retire while a release is active | 409 | `prompt_has_active_release` | the released `version_id` and `revision_number` |
| `upstream_model` not in the catalogue, or catalogue empty/unavailable | **no refusal** | — | an advisory field on the 201 |

**The caps are 422 and the lock says 413, and that disagreement is raised as `OQ-077` rather than
absorbed.** `failure_modes` says *"detection: 413 rate on the revision endpoint"*. INT-024's failure
line says *"422 for validation with `details`"*, and A-045 says there is **one** error envelope. Three
reasons 422 wins here and the question still gets written down:

1. A 413 is about the **HTTP entity**, and the cap is on **one JSON field** — a request carrying a 40 KiB
   body and a 40 KiB fallback answer is under any plausible request-size limit and still violates A-050.
2. A-050 requires *"a message naming the actual size"*, and the envelope's `details` is where a size
   goes; a bare 413 from a server or a proxy carries none.
3. INT-024 is the interface registration for exactly these routes and it names 422.

**The two 409s are conflicts and not validation errors**, and the difference is whether retrying
unchanged could succeed. A revision-number collision **can** — somebody else got there first and the
next attempt takes the next number, which is why phase 13's command already retries once and this is
only what a second collision looks like. A retire with an active release **cannot** until a withdrawal
happens, which is INT-014 and belongs to somebody holding `release.withdraw` (A-052, ADR-0009). Both
answers say *"the world changed, look again"*, which is what 409 means; a 422 would say *"your request
is wrong"*, which is not true of either.

**INT-016 is the one soft seam in the build and this plan is where that is proven.** The interface says
it plainly: *"An unavailable or stale catalogue degrades the picker to free text; it never refuses a
save. The catalogue is discovered from the provider's own list and is allowed manual entries precisely
because provider endpoints omit models; treating it as authoritative would block a legitimate revision
on a third party's incomplete API."* So `catalogue_check.catalogue_advice(...)` returns one of three
values — `listed`, `not_listed`, `catalogue_unavailable` — the revision is saved either way, and the
value rides on the 201 response as an advisory field the editor renders as a warning.

**Rejected: refusing an unknown model.** It is the intuitive read of *"validation lookup — does this
provider configuration exist and expose this model"* and INT-016 explicitly forecloses it.

**Rejected: silently dropping the advice** when the catalogue is empty. Then *"the provider has no
models registered"* and *"your model is fine"* are the same response, and the failure-mode row whose
whole subject is a stale catalogue has no surface.

**Reversibility: cheap** on the advisory value, **costly on the status codes** — a client that learned
409 means retry-after-refresh is a client that breaks when it becomes 422.

### `schemas.py`

**`PromptPropertyCreate`** — `namespace`, `name`, `title`, `purpose`, `tags: list[str] = []`,
`access_level: str = <the private constant>`. **No `owner_id`**: A-051 makes an owner one person and the
creator is that person; an `owner_id` field would let a caller register a prompt in somebody else's
name at creation and then need `prompt.transfer_owner` to do the same thing afterwards. Say that at the
model. **No `status`**: every registration lands `Active` (phase 13's D-224/D-238).

**`PromptPropertyUpdate`** — `title`, `purpose`, `tags`, `access_level`, `owner_id`, **all optional, and
`namespace` and `name` absent entirely** (A-021, and phase 13's grant matrix holds no `UPDATE` on
either). A model with no field set is refused by a validator with the reason written out: an empty PATCH
that succeeded would either write nothing and return 200 — a lie — or write an `owner_changed` event for
no change, and phase 13's D-233 makes it one event per **changed** field.

**`RevisionCreate`** — `body`, `provider_config_id`, `upstream_model`, `parameters: dict = {}`,
`fallback_answer: str | None`, `change_summary`. **Do not put `max_length` on `body`**: A-050's cap is a
**byte** count and pydantic's `max_length` on `str` counts characters, so a Vietnamese body would be
accepted at roughly three times the cap (phase 13's D-237 makes the same argument at the `CHECK`). The
byte check belongs where phase 13 put it; this model only carries the field.

**`RevisionRead`** gains one advisory field — `catalogue_status: str` with the closed three-value set —
and a docstring line saying it is INT-016's answer, that it is **never** a refusal, and that the editor
renders it as a warning beside the model picker.
