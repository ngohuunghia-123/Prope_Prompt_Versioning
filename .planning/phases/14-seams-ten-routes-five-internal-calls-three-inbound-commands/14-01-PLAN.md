## D-240 — Permission filtering is a required ARGUMENT of every repository read, not a convention

**Chosen.** `src/prope/prompt_registry/repository.py` holds every statement this module's person-facing
read paths issue, as plain `text(...)` module constants, and **every read function takes
`visible: VisibleSubjects` as a required keyword-only argument.** There is no default, no `None`
sentinel and no `filtered=True` flag. The set is pushed into the statement as a bound parameter and the
statement's `WHERE` clause carries the disjunction; a handler never assembles a predicate.

Exactly one function does not take it: `read_without_permission_filter(session, statement, params, *,
reason: str)`. It increments `prope_registry_unfiltered_query_total`, logs at `warning`, and its
docstring says it exists so that going around the filter is **an act somebody has to write down**. The
lock file specifies precisely this mechanism:

> queries that bypass it require an explicit, named unsafe call that trips the counter.

**Rejected: filtering in the handler**, which is what INT-024 and the lock's `security_requirements`
both name as the thing that must not happen. It is not rejected because it is ugly; it is rejected
because the eleventh handler is the one that forgets, and nothing about a handler makes forgetting
visible.

**Rejected: a `Repository` class holding the session**, with the filter applied in a base method. It
reads well and it has the failure this decision exists to prevent: a subclass, or a second method on the
same class, that issues a statement without going through the base. A required argument on a free
function cannot be skipped — the call does not compile without it — while an inherited method can be
bypassed by writing one line somewhere else in the class.

**Rejected: making the filter a `session`-level thing** (a policy, a listener, a `before_execute`
hook). It would apply to the commands, to `resolve()` and to property-history's `read()` on the same
session, all of which are correctly *unfiltered* for stated reasons — see D-243 — and an over-broad
filter that silently narrows the gateway's hot read is a worse failure than the one being prevented.

**Reversibility: costly.** Ten routes, phase 15's tripwire test and phase 15's whole PR-03 claim are
written against this shape.

## D-241 — The ten routes live in one `api.py`, and the module keeps a flat package

**Chosen.** `src/prope/prompt_registry/api.py` holds one `APIRouter(prefix="/api/v1")` and all ten
routes as this phase's later plans add them, in `src/prope/call_ledger/api.py`'s and plan 11-05's
`src/prope/provider_access/api.py`'s shape. Statements live in `repository.py`, response models in
`schemas.py`, and the module stays flat — no `routes/` package.

**Rejected: a `routes/` package**, the shape plan 08-01 chose for access-control. That module mounts
**fifteen** routes across six unrelated resources (auth, workspaces, grants, keys, permissions,
tombstone) and the split earns its keep there. Ten routes over two resources do not, and a package
would put the shared dependencies, the shared refusal helper and the shared page shape either in a
fourth file or duplicated in three.

**The cost, stated because it is real and it lands on the orchestrator rather than on a reader.** Plans
14-01 through 14-04 all edit `api.py`, so they are declared in **four successive waves** and can never
fan out concurrently. Execution is serial regardless (ORCHESTRATION §7), so the cost is bookkeeping
honesty rather than wall-clock; it is written here so the wave numbers are not read as a mistake.

**Reversibility: cheap** — splitting one module into a package later is a move, not a redesign.

## D-242 — `search_text` is excluded by construction three times over, and none of the three is a review

**Chosen**, and all three ship in this plan because the first response model is where the class of
defect enters:

1. **Every response model is explicit.** `schemas.py`'s models list their fields; nothing uses
   `from_attributes` over a whole row, and no model is built from `**dict(row)`.
2. **No statement selects `search_text` by name** outside a search predicate, and **`SELECT *` appears
   nowhere in `src/prope/prompt_registry/`.** A source gate in Task 4 parses every `text(...)` constant
   in the package and fails on either.
3. **The engine already refuses to let the application write it** — phase 13's D-226 leaves
   `search_text` out of every `grant_column_update` list. That is the write half; this decision is the
   read half, and the two together are what make ADR-0048's *"maintained by a database trigger, not by
   the application"* structural on both sides.

**Rejected: a field deny-list** applied to serialised output. `prope.observability`'s `LOGGABLE_FIELDS`
already carries the argument for the opposite posture and it is exactly right here: *a deny-list fails
silently the first time a field is renamed.* An explicit response model is an allow-list.

**What this plan does NOT claim.** T-017's full assertion — a **whole-response scan across every list
and detail endpoint**, plus a known body string asserted absent — is the owed **AC-7** and belongs to
**phase 15**. This plan asserts the scan on the one endpoint it ships, so the shape exists for phase 15
to generalise rather than invent. Saying which half is here is the point of routing it.

**Reversibility: cheap.**

## D-243 — The tripwire counts the PERSON-facing read paths, and deliberately not `resolve()` or the commands

**Chosen.** `prope_registry_unfiltered_query_total` is incremented by exactly one function, in
`repository.py`, on the management read path. `resolve()`, `list_released()` and the three inbound
commands live in **their own modules** (`resolve.py`, `commands.py`, plans 14-05 and 14-06) and neither
call the repository nor touch the counter.

**This is a decision and not an omission, and getting it wrong would make phase 15's criterion
unsatisfiable on day one.** Phase 15 SC2 is *"`prope_registry_unfiltered_query_total` stays 0, with a
page attached if it moves"*. The gateway resolves a model name on every single production request. If
`resolve()` counted as an unfiltered query, the counter would leave zero the moment the product worked,
`RegistryUnfilteredQuery` would page continuously, and the only available repair would be to stop
believing the alert.

The reason the two paths are different is written at both call sites rather than assumed:

- The **management** path's actor is a **person**, and their visibility is the union of role bindings
  and per-prompt grants (A-111). `visible_subject_filter` is the only thing that knows it.
- **`resolve()`'s** actor is a **consumer key**, whose entire authority is `scope_model_names` and
  which the gateway has already scoped through `may_resolve` (INT-004, A-081) before this module is
  reached. A `visible_subject_filter` call on a key would ask access-control a question about a
  subject type it does not hold and would return `mode: none` — refusing every production request.
- The **commands'** caller is release-control, which has already checked `revision.submit`,
  `revision.approve`, `release.create`, `release.break_glass` or `release.withdraw` at its own edge
  (INT-012, INT-013, INT-014 all say *"Auth: none — release-control has checked …"*).

**Rejected: one counter over every statement the module issues**, which is the reading a later reader
will reach for because it sounds stricter. It is not stricter; it is a counter that cannot be zero, and
a tripwire that is never zero is decoration.

**Reversibility: cheap** on the mechanism, **one-way on the alert**: once `RegistryUnfilteredQuery` has
been observed firing in normal operation, nobody trusts it again.

## D-244 — The registry's `ManagementAction` members are valued from `access_control.vocabulary.Action`, and A-115's spellings win

**Chosen.** Every member this phase adds takes its value from `prope.access_control.vocabulary.Action`
— phase 7's D-98 twenty-five-member `StrEnum`, mirrored as `role_permission.action`'s `CHECK` — imported
and referenced as `Action.<MEMBER>.value`, never retyped. Phase 8's **D-118** established this and phase
7's **D-99** settles the spellings: **where A-115 and INT-001 disagree, A-115 wins.**

The registry's actions, from A-115's list rather than from INT-001's table:

| Route | Action | Note |
|---|---|---|
| `GET /prompts`, `GET /prompts/{id}`, `GET /prompts/{id}/revisions`, `GET /revisions/{id}`, `GET /prompts/{id}/diff`, `GET /prompts/{id}/activity` | `prompt.read` | six routes, one action |
| `POST /prompts` | `prompt.create` | |
| `PATCH /prompts/{id}` | `prompt.edit` | see the conflict below |
| `POST /prompts/{id}/retire` | `prompt.retire` | |
| `POST /prompts/{id}/revisions` | `revision.create` | **A-115 has it; INT-001's caller table does not list it for this module.** The table is illustrative, the vocabulary is normative |

**The conflict this exposes, raised as `OQ-079` and not absorbed.** INT-001 gives prompt-registry
`prompt.change_owner` and `prompt.change_access`. A-115 spells the first `prompt.transfer_owner` and has
**no member at all** for the second — its `prompt.grant` is about `access.prompt_grant` rows and phase 8
already assigned it to access-control's grants routes. So `PATCH /prompts/{id}`, which the lock says
edits *"title, purpose, tags, access level, owner"*, is **one route carrying three distinct
permissions**, one of which has no name. `declares_action` attaches exactly one action to a route.
Plan 14-03 owns the resolution; this plan owns the tracer's single `prompt.read` and states the finding
where the enum is edited.

**Rejected: minting a `prompt.change_access` member here.** It would be a twenty-sixth action in a
vocabulary whose closure is asserted against `role_permission`'s `CHECK` — a migration in another
module's schema, taken to avoid writing down a question.

**Reversibility: costly** — these values are permission strings the whole build is written against.

## D-245 — Visibility is decided by whether the FILTERED read returned the row, and `may()` runs either way

**Chosen.** A detail read issues **one** filtered statement. If it returns a row, `visible=True` and
`may()` is called with that row's real `owner_id` and `access_level`. If it returns nothing,
`visible=False` and `may()` is called with a **synthetic private, ownerless subject** — so both paths
issue the same number of statements and do the same work.

Then, uniformly:

```python
refusal = refusal_for(visible=row is not None, allowed=allowed, action=action)
if refusal is not None:
    raise refusal
```

**Why not `is_visible()`.** Phase 9 ships `is_visible(*, actor_id, owner_id, access_level, grant_level,
is_active_member)`, and two of its five arguments — `grant_level` and `is_active_member` — live in
`access.prompt_grant` and `access.workspace_member`. This module may not read either
(`data.reads`: *"through its API, never by joining across module tables"*), and asking access-control
for them per row is the per-row check A-118 exists to replace. **The filtered read IS the visibility
answer**, which is what INT-002's set form is for.

**Both `refusal_for` arguments are evaluated before the branch, unconditionally.** Phase 9's D-131
states the reason and it is a security property rather than a style: *"a short-circuit that skips
`may()` when the subject is invisible makes the two paths do different amounts of work, which is a
timing oracle on exactly the distinction A-116 exists to hide."* Write that sentence at this handler and
point at it from every later route in the phase.

**A consequence worth naming rather than discovering.** INT-002's own text specifies the caller's query
as `WHERE workspace_id = :ws AND (owner_id = :actor OR id = ANY(:ids))` — **two** disjuncts — while
phase 9's `is_visible` has a third clause, `access_level == "workspace" and is_active_member`. This plan
implements the **two-disjunct form INT-002 specifies**, which fails **closed**: a `workspace`-level
prompt is visible to its owner, to grantees and to any actor whose role binding produced `mode: all`,
and to nobody else. Widening it is phase 15's, whose SC1 is the private-by-default claim; the gap is
recorded in `deferred-items.md` and named in `OQ-079`'s second clause.

**Reversibility: cheap** on the mechanism, and the failure direction is the safe one.

## D-246 — The `{prompt_id}` path parameter is spelled as the LOCK spells it, and the disagreement is raised

**Chosen.** `/api/v1/prompts/{prompt_id}`, because `docs/modules/prompt-registry.lock.yml`'s
`apis.exposes` spells it that way and the lock file is authority #1 (ORCHESTRATION §1).
`docs/architecture/interfaces.md` INT-024 and `.planning/ROADMAP.md` SC3 both spell it `{id}`, and
`src/prope/call_ledger/api.py` uses `Path(alias="id")` on `/workspaces/{id}`.

**This is not cosmetic and that is why it is raised as `OQ-078`.** The registry's own
`security_requirements` block ends with a route-table rule:

> FOUR modules mount routes under `/api/v1/prompts/{prompt_id}` — this one, evaluation, release-control
> and access-control's grants — and three under `/api/v1/workspaces/{id}`. … A CI test asserts the
> assembled route table contains no duplicate (method, path) pair.

That test compares **literal path strings**. `/api/v1/prompts/{id}/activity` and
`/api/v1/prompts/{prompt_id}/activity` route identically and compare unequal, so two modules spelling
the parameter differently would make a genuine duplicate invisible to the assertion whose whole job is
to see it. One spelling has to win project-wide, and this plan takes the lock's, states it, and raises
the question rather than quietly picking the one the neighbouring module happened to use.

**Reversibility: cheap here, costly across the build** — one string in this module, four modules'
worth if the answer arrives after they have all mounted.

## D-247 — `prompt_id` and `version_id` join `LOGGABLE_FIELDS`; `namespace`, `name` and `title` do not

**Chosen.** The lock's `log_fields` block declares `actor_id, workspace_id, prompt_id, version_id,
action, outcome, duration_ms`. Whichever of those are absent from `prope.observability.LOGGABLE_FIELDS`
are added here, each with the one-line justification every existing entry carries: they are opaque
prefixed ULIDs and closed-vocabulary tokens, not content.

**The model name is deliberately NOT logged**, and the reason is worth a sentence at the allow-list: a
model name is `namespace/name` chosen by a person, it is the string other people's code calls, and it
is the most useful thing in the file for an attacker who has obtained logs — while `prompt_id` answers
every support question a name would, against a register the reader already has access to. The lock's own
never-logged line (*"prompt body, fallback answer, credentials"*) is a floor, not a ceiling.

**Reversibility: cheap.**

### `src/prope/prompt_registry/repository.py` — new

**Module docstring, five paragraphs, in `src/prope/db/session.py`'s register** (that file is the closest
precedent: a small module whose whole value is a property nobody can see at a call site):

1. **What this file is.** Every statement the person-facing management API issues, and every read
   function it issues them through. The routes in `api.py` build no SQL and assemble no predicate.
2. **The rule, stated as a rule.** *Permission filtering is an argument, not a convention.* Every read
   here takes `visible: VisibleSubjects` as a **required keyword-only** parameter. Quote A-118's
   sentence about deadline pressure. Say what the shape buys: a new read path does not compile until
   its author has decided what visibility means for it.
3. **The one way past it, named.** `read_without_permission_filter` increments
   `prope_registry_unfiltered_query_total`, which the lock file alerts on at
   `> 0, page immediately`. Say that no code in this package calls it today, that phase 15 asserts the
   counter is 0, and that the function exists so that going around the filter is an act somebody has to
   write down rather than a query somebody forgot to constrain.
4. **What this file is deliberately NOT.** It is not the gateway's read path (`resolve.py`, D-243), and
   it is not the inbound commands (`commands.py`). Both are unfiltered **by contract**, both have their
   scoping done by their callers, and both would make the tripwire non-zero in normal operation if they
   were routed through here. Name D-243.
5. **`search_text` is never selected by name outside a search predicate, and `SELECT *` appears
   nowhere.** T-017, ADR-0048: it is a second copy of the prompt body on the table every list endpoint
   reads. Name the source gate in Task 4 as the thing that enforces it.

**The visibility predicate, written ONCE.** A single module-level constant that every filtered
statement embeds by being written out in full — not by string composition, because
`test_no_sql_interpolation.py` requires each `text(...)` argument to be a plain string constant and this
repository's answer to that gate is *a statement that needs no composition, not an entry on its
allow-list* (`call_ledger/api.py`'s own words). So each statement below spells the predicate out, and a
`#:` comment above the first one is the single place the reasoning lives, with the others pointing at
it.

The predicate, in every filtered statement:

```sql
  AND (CAST(:visible_all AS boolean)
       OR p.owner_id = :actor_id
       OR p.id = ANY(CAST(:visible_ids AS text[])))
```

Its `#:` block carries five things:

- `:visible_all` is `true` exactly when `VisibleSubjects.mode is ALL`. **`mode: all` is not a tenancy
  bypass** — INT-002 and ADR-0045 — it means every prompt *in the workspace*, and the workspace
  restriction is the policy underneath plus the explicit `p.workspace_id = :workspace_id` term beside
  it.
- `p.owner_id = :actor_id` is **the caller's half of INT-002's contract**, quoted from INT-002:
  access-control may not read `prompt_property` (ADR-0020), so ownership is knowable only where the row
  is, which is here.
- `:visible_ids` is the grant-derived set. **`mode: none` renders as an empty array and NOT as an
  error and NOT as an unfiltered query** — INT-002 says so in as many words, and the empty array still
  leaves the ownership disjunct standing, which is why `none` does not mean *the actor sees nothing*.
- The `CAST`s are not decoration: with none, asyncpg has no type to infer for a parameter that may
  arrive as an empty list.
- **The third disjunct INT-002's own text does not have** — `access_level = 'workspace' AND
  <the actor is an active member>` — is deliberately absent (D-245). It fails closed, phase 15 owns
  widening it, and `OQ-079` is where the question lives. Write that at the constant so nobody adds it
  casually and nobody deletes the question.

**One helper**, because three call sites will bind these three parameters and a fourth will get it
wrong:

```python
def visibility_parameters(visible: VisibleSubjects, actor_id: str) -> dict[str, object]
```

returning `{"visible_all": ..., "visible_ids": [...], "actor_id": actor_id}`. Its docstring states the
one invariant: `visible_all` is true **only** for `mode is ALL`, and `visible_ids` is empty for every
mode but `IDS` — mirroring `VisibleSubjects`' own `__post_init__`, so a value object that somehow
carried both could not widen anything here.

**This task's one statement and one function.**

```python
SELECT_PROMPT_PROPERTY = text(
    """
    SELECT p.id, p.workspace_id, p.namespace, p.name, p.title, p.purpose,
           p.owner_id, p.access_level, p.status, p.tags,
           p.released_version_id, p.released_at, p.created_at, p.updated_at
    FROM   registry.prompt_property AS p
    WHERE  p.workspace_id = :workspace_id
      AND  p.id = :prompt_id
      AND  (CAST(:visible_all AS boolean)
            OR p.owner_id = :actor_id
            OR p.id = ANY(CAST(:visible_ids AS text[])))
    """
)
```

Fourteen columns named one by one, and `search_text` and `released_version_status` both absent. Put a
`#:` line on the absence of each: the first is T-017, the second is phase 13's `OQ-070` column that
exists only so BR-03 can be a foreign key and has no meaning to any client.

```python
async def get_prompt_property(
    session: AsyncSession, *, workspace_id: str, prompt_id: str,
    visible: VisibleSubjects, actor_id: str,
) -> Mapping[str, Any] | None
```

Returns the row mapping or `None`. Its docstring says the thing the routes depend on: **`None` means
"not visible OR not there", and the caller must not try to tell them apart** — that conflation is
A-116's not-found rule expressed in the return type, and a variant that distinguished them would be the
existence oracle the rule exists to close.

```python
async def read_without_permission_filter(
    session: AsyncSession, statement: TextClause, parameters: Mapping[str, Any], *, reason: str,
) -> Sequence[Any]
```

Increments `unfiltered_query_total` **once per call, before execution**, logs
`registry.unfiltered_query` at `warning` with `reason` (a closed token the caller passes, never a
free-form string built from request data), and executes. Docstring: the lock's mitigation sentence
verbatim, the `RegistryUnfilteredQuery` alert, and the flat statement that **nothing in this package
calls it and phase 15 asserts the counter is 0**.

**One shared refusal helper**, because the phase has ten routes and D-245's rule must be identical at
each:

```python
async def refuse_unless_permitted(
    db: AsyncSession, *, actor: Actor, action: str,
    subject_id: str, workspace_id: str,
    row: Mapping[str, Any] | None,
) -> None
```

It builds the `Subject` from `row` when there is one and from the **synthetic private, ownerless**
values when there is not, calls `may()`, calls `refusal_for`, and raises if it returns a refusal. Its
docstring is where D-245 lives at the code: why the filtered read is the visibility answer, why
`is_visible` is not used here, and why `may()` is called on both paths. **It does not wrap `may()` in a
`try`** — INT-001's raise is the mechanism and a caught raise is the bug the seam is shaped to prevent.

**The route.**

```python
@router.get(
    "/prompts/{prompt_id}",
    response_model=PromptPropertyRead,
    dependencies=[Depends(declares_action(ManagementAction.PROMPT_READ))],
)
async def get_prompt(prompt_id: str, session=Depends(require_session), sessionmaker=Depends(get_sessionmaker)) -> PromptPropertyRead
```

Body, in order, with a comment on each step naming the seam it is:

1. `async with workspace_transaction(sessionmaker, session.workspace_id) as db:`
2. `visible = await visible_subject_filter(db, actor, "prompt")` — INT-002, once per request.
3. `row = await repository.get_prompt_property(db, workspace_id=…, prompt_id=…, visible=visible,
   actor_id=session.user_id)`
4. `await refuse_unless_permitted(db, …, row=row)` — raises 404 or 403; returns None otherwise.
5. Build `PromptPropertyRead` field by field from `row`. **Never `PromptPropertyRead(**row)`** — the
   whole point of the explicit model is that adding a column to the table does not add a field to a
   response, and `**row` would undo it silently.

The `prompt_id` path parameter takes **no validation regex**. A-021 specifies the model name's shape and
not its alphabet, and a prefix check here would be a second place for ADR-0003's id format to be
written; an id that does not exist is a 404 through the ordinary path, which is the same answer a
malformed one deserves.
