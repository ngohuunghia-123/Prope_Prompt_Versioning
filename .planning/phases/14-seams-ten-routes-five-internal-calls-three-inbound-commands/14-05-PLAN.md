<objective>
Build the gateway's hot read: **`resolve(model_name, pin)` returns the released revision's full binding,
and its miss says which kind of miss it was.**

Two ROADMAP criteria live here and they pull in opposite directions, which is why they are one plan.
**SC1** is a latency claim — p95 under 10 ms over 1,000 requests — and every extra round trip spends it.
**SC2** is an information claim — *model name unknown* and *model name known, nothing released* must be
different results — and the obvious way to tell them apart is a second query. This plan's whole design
problem is answering both with **one statement**.

ADR-0009 says why SC2 matters, and it is not diagnostics:

> the gateway's resolve path must distinguish "model name unknown" from "model name known, nothing
> released" … otherwise **a withdrawal is invisible in the one metric that would show its blast
> radius.**

Phase 19's SC2 and SC3 assert the gateway half — `no_release` distinct from `unknown_model` at the wire.
**If the resolver collapses them, the gateway cannot separate them either**, and the collapse is
invisible until somebody withdraws a release in production and nothing anywhere says how much traffic
just started failing.

## D-256 — `resolve()` carries the workspace, and a pin is filtered on `Approved` in the statement

**Chosen.**

```python
async def resolve(sessionmaker, *, workspace_id: str, model_name: str, pin: str | None = None) -> ResolveResult
async def list_released(sessionmaker, *, workspace_id: str) -> tuple[ReleasedModel, ...]
```

**The workspace parameter is a declared deviation from INT-009 and is raised as `OQ-075`, not
absorbed.** INT-009's *"Request carries"* line names *"the bare model name, and an optional pin"* and no
workspace, while INT-010 beside it registers `list_released(workspace_id)`. Under ADR-0035 and ADR-0045 a
`prope_app` query issued with no `app.workspace_id` set returns **zero rows rather than an error** — so a
workspace-less `resolve()` would answer *"model name unknown"* for every model name in the product, at
p95 well under 10 ms, and nothing would fail. The gateway already holds the workspace: INT-003 returns
`{workspace_id, key_id, scope}` before this seam is reached.

This is the same shape phase 2 recorded as `OQ-020` — `get_run_totals` shipping as
`(workspace_id, run_id)` where INT-021 registers `run_id` alone — and it gets the same treatment: ship
the honest signature, raise the question, edit no spec.

**The pin filters on the stored status, and that is not a BR-03 violation.** INT-009 says *"A pin whose
revision is not `Approved` is refused"* and then explains it as *"this seam reads a pointer the
constraint has already guaranteed"* — **which is true of the released pointer and false of a pin.** A pin
names an arbitrary revision of that prompt; no constraint has said anything about it. So the pin
statement carries `AND r.status = 'Approved'` explicitly, and the sentence at the statement says why that
is a read filter rather than an application check standing in for the constraint: non-negotiable #2 is
*"only `Approved` revisions may be released **or resolved**"*, BR-03's database constraint covers the
release half, and the resolve half has no pointer to lean on. `OQ-075`'s second clause names the
interfaces sentence.

**Pin syntax**: `@<n>` where `n` is all digits is a revision number; anything else is a version id. The
gateway strips the pin before calling `may_resolve` (INT-004) and passes both here (INT-009). Parse it in
one function with the ambiguity stated: a version id is a `rev_`-prefixed ULID and can never be all
digits, so the two forms cannot collide — say that at the parser rather than leaving it to be
rediscovered.

**Reversibility: costly** — the signature is what phases 19 through 21 are written against.

## D-257 — One `LEFT JOIN` answers the hit and both miss reasons; the miss is a typed value with a third reason for a pin

**Chosen.** The bare-name path is **one statement**:

```sql
SELECT p.released_version_id,
       r.version_id, r.revision_number, r.body, r.provider_config_id,
       r.upstream_model, r.parameters, r.fallback_answer
FROM   registry.prompt_property AS p
LEFT   JOIN registry.revision AS r
  ON   r.workspace_id = p.workspace_id AND r.version_id = p.released_version_id
WHERE  p.workspace_id = :workspace_id
  AND  lower(p.namespace) = lower(:namespace)
  AND  lower(p.name) = lower(:name)
```

and the three outcomes fall out of it with **no second round trip**:

| Result | Meaning |
|---|---|
| zero rows | `unknown_model` — no prompt property has that model name in this workspace |
| one row, `released_version_id IS NULL` | `no_release` — the name is known and nothing is released |
| one row with a binding | hit |

**Rejected: two statements** — *"does this name exist?"* then *"what is released?"* It is the shape a
reader reaches for first, and it pays a second round trip **on every miss** to learn something the first
statement already knew. On a path whose whole budget is 10 ms, spending a round trip to explain a
failure is exactly backwards.

**Rejected: an inner join with a separate existence check on the miss path.** Same cost, and it makes
the *common* case (a hit) and the *interesting* case (a withdrawal) take different code paths — which is
how the two miss reasons drift apart in the first place.

**The `lower()` on both sides matches phase 13's D-225 functional unique index**
`uq_prompt_property_model_name (workspace_id, lower(namespace), lower(name))`, so the lookup is an index
scan on exactly the expression the index was built on. Getting this wrong — writing
`p.namespace = :namespace` — still returns correct answers and silently stops using the index, which is
the failure this hot path cannot see. Write that sentence at the statement.

**The miss is a typed value.** `ResolveResult` is `RevisionBinding | ResolveMiss`, both frozen and
slotted; `ResolveMiss` carries a `MissReason` `StrEnum`. **Never an exception, never `None`.** INT-009
reserves the raise for *Prope being broken* — *"raises -> the gateway returns an OpenAI-shaped 500 and
does not serve the fallback answer"* — and a withdrawal is a normal product state, not a fault. A `None`
return would be a third thing a caller can get wrong beside the two the type already has.

**`MissReason` has THREE members, and the third is a declared widening.** The lock declares
`reason = unknown_model | no_release`. A **pin** produces a miss that is neither: the model name is
known, something may well be released, and the pinned revision does not exist, belongs to another
prompt, or is not `Approved`. Rather than mislabel it as one of the two — which would corrupt the exact
signal ADR-0009 built the label for — this plan adds **`pin_unresolvable`** and records it as an
UNCONFIRMED adoption under `OQ-075`. The two declared values keep their meanings exactly, so every alert
and every phase-19 assertion written against them is unaffected; the label set is closed, fixed in
source, and three values is inside ADR-0030's cardinality rule.

**`outcome` on the duration histogram is `hit | miss | pinned`** — the lock's three — read as
**disjoint**: `pinned` is a *successful pin resolution*, `hit` is a successful bare-name resolution, and
`miss` is any miss whatever its reason. That is the only reading under which the three do not overlap,
and the reason detail lives on `resolve_miss_total` where the lock puts it. State the reading at the
metric; a later reader given `hit/miss/pinned` with no note will label a pinned hit `hit` and a pinned
miss `pinned`, and the series will mean two things.

**`RESOLVE_DURATION_BUCKETS` must contain `0.010` as an edge.** Phase 13's plan 13-01 declares the tuple;
**verify it and fix it here if it does not**, and say so in the SUMMARY. `src/prope/observability.py`
states the rule at length: `histogram_quantile` interpolates *inside* the bucket holding the quantile, so
a target that is not an edge can only be answered to that bucket's width — and
`prometheus_client`'s defaults start at **0.005**, which phase 3 already hit once. Choose the remaining
edges for resolution between 0.5 ms and 50 ms, and put `RegistryResolveLatencyHigh`'s own threshold
(p95 > 10 ms for 5 min) on the same edge, because it is the same number.

**Reversibility: costly** — the miss vocabulary is what phase 19's gateway branches on and what the
alerting is written against.

### `src/prope/prompt_registry/resolve.py` — new

**Module docstring, six paragraphs, in `call_ledger/seams.py`'s register:**

1. **What this file is**: INT-009 and INT-010, the gateway's two read seams, with **no caller in this
   repository yet** — the gateway is phases 19-21. So they are proved from this module's own tests
   against the real engine, rather than from a caller that could be shaped to agree with them. That is
   `seams.py`'s own sentence and it applies unchanged.
2. **Why this file is not `repository.py`** (D-243). The management path's actor is a person and its
   visibility is `visible_subject_filter`'s; this path's actor is a **consumer key** whose entire
   authority is `scope_model_names`, already applied by `may_resolve` at the gateway's edge (INT-004,
   A-081). Routing it through the repository would make `prope_registry_unfiltered_query_total` non-zero
   on every production request and turn phase 15's page-immediately alert into noise.
3. **The miss is a value, not an exception** — with INT-009's failure line quoted, and the sentence that
   the gateway must **not** serve the fallback answer on it (A-022, ADR-0009): the fallback covers an
   upstream provider failure, and reporting a withdrawal as one would send a consuming team to debug the
   wrong system.
4. **Nothing here is cached** (ADR-0012, ADR-0046). The 30 s TTL lives in the **gateway**, it **expires**
   and nothing invalidates it, and a cache here would exist twice — once in `app`, once in `worker`
   importing this module for evaluation's batch runs — with no invalidation between the copies.
   `deployment_target` says this in the lock file's own words; quote it.
5. **The workspace parameter and `OQ-075`** (D-256), including the zero-rows-not-an-error sentence, which
   is why the omission would have been silent.
6. **A-046**: nothing here logs a body, a fallback answer or a model name, and `workspace_id` is never a
   metric label.

**Value objects**, frozen and slotted:

```python
@dataclass(frozen=True, slots=True)
class RevisionBinding:
    version_id: str
    revision_number: int
    body: str
    provider_config_id: str
    upstream_model: str
    parameters: Mapping[str, Any]
    fallback_answer: str | None

class MissReason(StrEnum):
    UNKNOWN_MODEL = "unknown_model"
    NO_RELEASE = "no_release"
    PIN_UNRESOLVABLE = "pin_unresolvable"

@dataclass(frozen=True, slots=True)
class ResolveMiss:
    reason: MissReason

ResolveResult = RevisionBinding | ResolveMiss
```

`parameters` is wrapped in a `MappingProxyType` at construction, for the reason phase 5's `HistoryEvent`
gives: a frozen dataclass holding a mutable dict is immutable in name only, and this one escapes to the
gateway which composes a request from it.

**Two statements**, each a plain `text(...)` constant with a `#:` block:

- `RESOLVE_RELEASED` — D-257's `LEFT JOIN`, with the three-outcome table in the comment, the
  `lower()`-matches-the-index sentence, and the note that `released_version_status` is deliberately not
  selected (it exists only so BR-03 can be a foreign key).
- `RESOLVE_PINNED` — the same projection, joined on the pin instead of the pointer, with
  `AND r.status = 'Approved'` and D-256's paragraph at it. Two variants of the predicate are needed —
  `r.revision_number = :revision_number` and `r.version_id = :version_id` — and they are **two
  statements, not one with a self-switching-off pair**, because the pin is one form or the other and a
  statement that could take both would need two NULL casts on the hot path to express *"exactly one of
  these"*. Say that; it is the one place in the module where the `CAST(:x AS text) IS NULL` idiom is
  refused, and refusing an established idiom needs a reason written down.

**`resolve()`**: one `workspace_transaction`, one `execute`, one branch on the result, one
`resolve_duration_seconds.labels(outcome=…).observe(...)` around the whole call, and
`resolve_miss_total.labels(reason=…).inc()` on a miss. Time it with `perf_counter` around the
transaction, not around the statement — the transaction is what the gateway pays for.

**`list_released()`**: one statement, `INNER JOIN` (a prompt with no release is simply absent),
projecting `namespace`, `name`, `version_id`, `revision_number`, composing `model_name` in Python.
`#:` block: INT-010's *"deliberately not the same query as `GET /api/v1/prompts`"* — no cursor, no
filters, released only, and the actor is a consumer key — plus the sentence that reusing the management

argument nobody reviewed"*. It is **not** permission-filtered: the gateway applies the key's scope
afterwards (INT-010's own failure paragraph), and one sentence says so, so nobody "fixes" it by adding
`visible_subject_filter`.
