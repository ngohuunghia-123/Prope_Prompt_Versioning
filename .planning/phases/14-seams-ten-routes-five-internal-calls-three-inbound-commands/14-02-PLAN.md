Serve the four read routes that make the registry a **register** rather than a table: the list-and-search
screen somebody finds a prompt on, the revision chain they read down, the single revision they open, and
the diff a reviewer decides against. All four go through plan 14-01's repository layer and none of them

## D-248 — The keyword term is folded and escaped in one place, and `ILIKE` over `search_text` is the whole mechanism

**Chosen.** `src/prope/prompt_registry/search.py` holds one function:

```python
def prepare_search_term(raw: str) -> str
```

It does exactly two things and says so at length:

1. **Escapes the LIKE wildcards** — `\`, `%` and `_` — so a term containing them matches those
   characters literally. The statement declares `ESCAPE '\'` explicitly rather than relying on the
   default, because the default is `\` only until somebody sets `standard_conforming_strings`
   differently and a search that silently matches everything is not a failure anybody reports.
2. **Applies the same folding the trigger applies to the document.** A-150 folds diacritics and case
   **inside** `registry.compose_search_text`, so `search_text` is already folded and the query term must
   be folded identically or `tiêu đề` will not match its own row. **Read phase 13's composer and mirror
   it** — if phase 13 exposed the folding as a callable SQL function, call that from the statement
   instead of duplicating it in Python, and say in the SUMMARY which you did. Two spellings of one
   folding rule is exactly the drift ADR-0048 built a trigger to avoid.

The predicate itself:

```sql
  AND (CAST(:q AS text) IS NULL OR p.search_text ILIKE :q_pattern ESCAPE '\')
```

with `:q_pattern` bound as `'%' + prepared + '%'` **from Python**, because building it in SQL with `||`
would put the folding call in two places once the term is folded server-side.

**Rejected: `tsvector` / `plainto_tsquery` / a stemming dictionary.** ADR-0048 rejects all three on
three specifics rather than on taste — no bundled Vietnamese dictionary to name under ADR-0053, no infix
matching, and a parser that reads `namespace/name` as a file path so `refund` misses
`support/refund-classifier`, which is *the most likely query in this product*. The owed **AC-10** exists
precisely to stop a future "optimisation" back to it, and this plan asserts both of its cases at the
route.

**Rejected: `similarity()` ranking and an `ORDER BY similarity DESC`.** ADR-0048 puts it on the upgrade
ladder for later and the default ordering is `updated_at DESC` (D-249). Relevance ranking would make the
list order depend on the query, which is a different product decision than the one that has been taken.

**Reversibility: cheap** on the escaping, **costly on the folding** — a folding rule that disagrees with
the trigger's makes rows un-findable by their own text, silently, which is the failure mode ADR-0048
names as the worst available shape for a register.

## D-249 — `updated_at DESC, id DESC`, an opaque cursor resolved through the FILTERED read, and no body in a list

**Chosen**, three parts of one shape:

**The ordering** is `p.updated_at DESC, p.id DESC`, served by phase 13's
`ix_prompt_property_workspace_updated_at (workspace_id, updated_at DESC)`. ADR-0048 specifies
`updated_at DESC` and the lock states the consequence out loud — *"`updated_at` now MOVES when a revision
is saved, so a freshly edited prompt rises to the top. Desirable, and new."* `id DESC` is the tiebreak,
because `updated_at` is not unique and a keyset page over a non-unique key skips or repeats rows.

**The cursor is an opaque prompt id**, resolved to its `(updated_at, id)` position by a separate
statement — **phase 5's D-71 shape, deliberately copied.** Two things this buys that a
composite-encoded cursor does not:

- An unknown cursor is a **refusal** rather than a silent empty page. Phase 5's argument applies
  unchanged: folding the resolution into the page statement as a scalar subquery makes an unknown id
  produce `updated_at < NULL`, which returns zero rows and reads as *the list ended here*.
- **The resolution runs through the visibility predicate too**, so a cursor naming a prompt the actor
  cannot see is refused **identically** to one naming a prompt that does not exist. A cursor that
  resolved against an invisible row would be an existence oracle with a page of results attached.

**The cost, stated rather than discovered**: one extra round trip per page after the first, and a page
boundary that can move. Because `updated_at` changes when anybody saves a revision, a prompt edited
mid-scroll can cross the cursor and be seen twice or missed once. **That is inherent to ordering by a
mutable column and it is not repaired by pretending otherwise** — write it at the statement, and note
that the alternative (ordering by `id DESC`, which is creation order and stable) was rejected because
ADR-0048 chose recency and recency is what a register is scrolled for.

**No body in a list.** `RevisionSummary` carries `version_id`, `revision_number`, `change_summary`,
`author_id`, `status` and `created_at` and **has no `body` field.** A-050 caps a body at 32 KiB and the
load condition is 20 revisions per property: 640 KiB in a page somebody asked for a chain of change
summaries. `RevisionRead` — the single-revision model — carries the body, because
`GET /api/v1/revisions/{version_id}` is the route that exists to return it.

**Reversibility: costly** — the cursor's opacity is a wire contract, and a client that learned to build
one from a timestamp would break when the encoding changed.

## D-250 — `GET /api/v1/revisions/{version_id}` resolves its permission through its PARENT, in one statement

**Chosen.** The route's statement joins `registry.revision` to `registry.prompt_property` and carries the
visibility predicate **on the parent**:

```sql
FROM   registry.revision AS r
JOIN   registry.prompt_property AS p
  ON   p.workspace_id = r.workspace_id AND p.id = r.prompt_id
WHERE  r.workspace_id = :workspace_id
  AND  r.version_id = :version_id
  AND  (<the visibility predicate, on p>)
```

so an invisible parent yields **zero rows** and the ordinary not-found path answers.

**This route is the one in the ten with no prompt id in its path**, which makes it the one where a
handler is most likely to read the revision first and check afterwards. **Rejected: exactly that** — read
the revision, then call `get_prompt_property` on its `prompt_id`, then decide. It is two round trips, it
puts a decision back in the handler, and between the two reads there is a window in which the answer
changes. One statement has none of those.

`registry.revision` carries its own `workspace_id` with RLS and a policy (T-018, phase 13), so the
**tenant** half is enforced twice — by the policy and by the explicit predicate — and the **visibility**
half is enforced once, here, on the parent. Write both sentences at the statement: they are different
guarantees and a reader who conflates them will delete one.

The same statement shape serves the **diff** route with a second version id, and the pair read asserts
that *both* revisions belong to the `{prompt_id}` in the path. A `from` that belongs to another prompt is
**not-found**, not a 422: A-116's rule does not stop at the subject in the path, and confirming that a
version id exists somewhere else is the same leak by a different door.

**Reversibility: cheap.**

### `src/prope/prompt_registry/search.py` — new, small, and entirely about one function

Module docstring, three paragraphs: what the term has to survive (LIKE wildcards), what it has to agree
with (the trigger's folding, A-150), and why both live here rather than at the statement (one place,
because a second spelling of the folding rule makes rows un-findable by their own text with no error and
no failed query — ADR-0048's stated worst case).

```python
LIKE_ESCAPE = "\\"
LIKE_WILDCARDS = ("\\", "%", "_")   # order matters: the backslash first

def prepare_search_term(raw: str) -> str
```

Escape in the order given — escaping `\` after `%` double-escapes the escape — and say that in a comment,
because it is the classic way to get this wrong. Then apply the folding to match the composer. If phase
13 exposed the folding as a SQL function, **do not fold in Python**: return the escaped term and let the
statement call the function, and record that branch in the SUMMARY.

Two module constants for the caps, so the route does not invent them: a minimum term length (adopt
**1**, and say why a minimum above 1 was rejected — `q=a` over a workspace's own prompts is a legitimate
question and the corpus is 1,000 rows, not a web index) and a maximum (adopt **200**, matching A-050's
change-summary cap, and say the number is a bound rather than a product rule).

### `src/prope/prompt_registry/repository.py`

Two statements and two functions.

**`RESOLVE_LIST_CURSOR`** — the D-249 cursor resolution:

```sql
SELECT p.updated_at, p.id
FROM   registry.prompt_property AS p
WHERE  p.workspace_id = :workspace_id
  AND  p.id = :cursor

```

Its `#:` block carries D-249 in full: why it is a separate statement (phase 5's D-71), why the
visibility predicate is on it (a cursor that resolved against an invisible row is an existence oracle),
and what an unresolved cursor means (a refusal, never an empty page).

**`LIST_PROMPT_PROPERTIES`** — one statement, fourteen columns (the same projection
`SELECT_PROMPT_PROPERTY` uses; write it out rather than composing it, per the no-interpolation gate),
with:

```sql
WHERE  p.workspace_id = :workspace_id
  AND  (<the visibility predicate>)
  AND  (CAST(:q AS text) IS NULL OR p.search_text ILIKE :q_pattern ESCAPE '\')
  AND  (CAST(:owner_id AS text) IS NULL OR p.owner_id = :owner_id)
  AND  (CAST(:status AS text) IS NULL OR p.status = :status)
  AND  (CAST(:access_level AS text) IS NULL OR p.access_level = :access_level)
  AND  (CAST(:tag AS text) IS NULL OR :tag = ANY(p.tags))
  AND  (CAST(:cursor_updated_at AS timestamptz) IS NULL
        OR (p.updated_at, p.id) < (CAST(:cursor_updated_at AS timestamptz), CAST(:cursor_id AS text)))
ORDER  BY p.updated_at DESC, p.id DESC
LIMIT  :limit
```

`#:` block, five points:

- **`search_text` is named here and nowhere else in this module**, and this is the search predicate
  D-242 carves out. T-017 in one sentence: it is a second copy of the prompt body, it is in this `WHERE`
  clause and in no `SELECT` list, and the source gate in plan 14-01 Task 4 is what keeps that true.
- **The row-value comparison `(updated_at, id) < (…, …)` is the keyset**, and it is written as a row
  comparison rather than as `updated_at < :x OR (updated_at = :x AND id < :y)` because the two are the
  same predicate and only one of them can be got wrong.
- **The `CAST`s are not decoration** — asyncpg has no type to infer for a NULL parameter
  (`call_ledger/api.py`'s own words).
- **The ordering column is mutable**, and the paging consequence, from D-249.
- **Which index serves what**: the trigram GIN for the keyword term, the
  `(workspace_id, updated_at DESC)` btree for the ordering. Say that a query with **both** may use
  either and that this plan does not pin a plan — the performance row is p95 < 500 ms at 1,000
  properties, which is not a number that needs a planner hint, and a hint here would be a decision taken
