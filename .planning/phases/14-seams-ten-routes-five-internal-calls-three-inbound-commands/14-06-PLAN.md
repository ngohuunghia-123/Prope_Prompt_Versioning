## D-258 — The three commands take the CALLER's session, open no transaction, and append no event

**Chosen.**

```python
async def set_revision_status(session: AsyncSession, *, version_id: str, status: str, decision_id: str) -> None
async def set_released_revision(session: AsyncSession, *, prompt_id: str, version_id: str,
                                release_id: str, expected_current_version_id: str | None) -> None
async def clear_released_revision(session: AsyncSession, *, prompt_id: str, release_id: str) -> None
```

**A session, not a sessionmaker**, and this is the opposite of what plan 14-03's routes do with phase
13's commands (D-251). The difference is not taste — it is what all three interface registrations
require in the same words:

> Any raise aborts release-control's transaction, and with it the release row and the
> `revision_released` append. **There is no release without a trail, by transaction rather than by
> convention.** (INT-013)

A command that opened its own transaction would commit the pointer move and then let release-control's
release row roll back, leaving production serving a revision with no release record — which is precisely
the row the `RegistryUnapprovedPointer`-adjacent reconciliation query exists to find and precisely the
state ADR-0008's amendment names as the surviving gap. This is ADR-0023's shape, applied to a write
seam instead of to a read: *the callee runs on the caller's connection inside the caller's open
transaction.*

**They append no property-history event.** The lock's `outputs` block names **five** — `property_created`,
`revision_created`, `owner_changed`, `access_level_changed`, `retired` — and none of them is a status
move or a release. Release-control writes `revision_submitted`, `revision_approved`, `revision_released`
and `release_withdrawn` **in the same transaction** as the command it just issued, which is exactly what
makes the trail atomic with the change. A second append here would double the trail on the one table
A-121 keeps forever.

**`decision_id` and `release_id` are accepted, logged, and stored nowhere — because there is no column
for them.** `registry.revision` has no `decision_id` and `registry.prompt_property` has no `release_id`
in their declared field lists, and adding one would be a schema change duplicating a row release-control
already owns. ADR-0008 says *"`decision_id` names the approval or release row that authorised it, so a
status with no decision behind it is a detectable defect"*, and its own amendment says how it is
detected: **release-control's reconciliation query**, not a column here. So the commands validate the
ids' *shape* (non-empty, ADR-0003's prefixed-ULID form), log them on the success line, and store
neither. `prope.observability.LOGGABLE_FIELDS` gains `decision_id` and `release_id` with the one-line
justification the existing entries carry — both are opaque prefixed ULIDs, neither is content.

**INT-012 also requires raising on *"a `decision_id` that does not exist"*, and that is unimplementable
from here.** It would mean reading release-control's `approval` table, which is a **forbidden
dependency** — the edge whose absence is the cycle break. Raised as **`OQ-076`**, second clause, and not
absorbed.

**Reversibility: costly** — the signature is what phases 22 through 24 are written against, and the
session-versus-sessionmaker choice is the one that cannot be changed later without revisiting every
caller's transaction boundary.

## D-259 — The legal transition table is adopted here, because no authority declares one

See the checkpoint block in Task 1. **Adopted: the closed forward-and-back set**

```
Draft      -> In review     (submit)
In review  -> Approved      (approve)
In review  -> Draft         (changes requested, A-066)
```

and **nothing else** — in particular `Approved` is terminal from this command's point of view, and every
self-transition raises.

It lives in `domain.py` as data:

```python
LEGAL_STATUS_TRANSITIONS: Mapping[str, frozenset[str]]
```

one table, validated against in one place, with no `if`-chain and no second copy. Raised as **`OQ-076`**
because ADR-0008 fixes the *vocabulary* (`Draft | In review | Approved`) and A-066 fixes *one* edge
(changes-requested returns to Draft), and **nothing anywhere declares the set of legal moves** — while
INT-012 says in as many words that *"the provider validates the transition"* and *"the legal state
machine lives in one module."* A module told to validate against a table nobody wrote will invent one;
this writes the invention down instead of hiding it in a function body.

### `src/prope/prompt_registry/commands.py` — new

**Module docstring, seven paragraphs, and it is the most load-bearing docstring in the phase:**

1. **What these three are**: INT-012, INT-013 and INT-014, the only writes to `revision.status` and to
   the released pointer in the entire system, issued by release-control and by nobody else. **No caller
   exists in this repository** — release-control is phases 22-24 — so they are proved from this module's
   own tests, in `seams.py`'s stated posture.
2. **The cycle this breaks**, in A-041's and ADR-0001's words: the pointer is a registry field that only
   release-control may write, and it writes it through a command so that release-control writes no table
   it does not own (ADR-0008).
3. **The session contract** (D-258), with INT-013's *there is no release without a trail, by transaction
   rather than by convention* quoted. **This function does not commit** and the caller's context manager
   owns the boundary — `append`'s own contract line, restated because it is the same contract.
4. **No history event is appended here** and why (D-258), naming the lock's five `outputs` and
   release-control's four.
5. **The constraint decides and this module explains** — phase 13's D-221 adoption assigned exactly this
   sentence to phase 14. `set_released_revision` catches the `IntegrityError`, **branches only on the
   constraint's name**, and re-raises a domain error naming the revision. Write the distinction out: it
   reads *which* constraint fired, never the revision's status, so BR-03 stays out of Python (ADR-0001,
   INT-013, non-negotiable #2).
6. **Nothing here is idempotent**, per all three interface registrations, with the reason: the
   compare-and-set is what makes a retry **safe or loud and never quiet**.
7. **A-046**: the success line carries `prompt_id`, `version_id`, `decision_id` / `release_id`, `action`
   and `outcome`, and no body, summary or fallback answer.

**`set_revision_status`.** Two statements and one table lookup:

1. Read the current status: `SELECT status FROM registry.revision WHERE version_id = :version_id`. No
   row → raise `UnknownRevision`. (This read is about producing a legible refusal, and the docstring says
   so — the *write* is still guarded, see below.)
2. Validate against `LEGAL_STATUS_TRANSITIONS` (D-259). Illegal pair → raise
   `IllegalStatusTransition(from_status, to_status)`, whose message names both and cites `OQ-076`.
3. Write with the current status **in the WHERE clause**:
   `UPDATE registry.revision SET status = :new_status WHERE version_id = :version_id AND status =
   :expected_status`, and `rowcount == 0` → raise `ConcurrentStatusChange`. Say why the guard is there
   even though step 1 just read it: between the read and the write another transaction can move it, and
   a bare `UPDATE ... SET status` would overwrite a decision somebody else recorded. The read is for the
   message; **the WHERE clause is the correctness**.
4. **Catch the engine's foreign-key refusal by name.** Phase 13's D-221 makes an `Approved` -> anything
   move on a **currently released** revision impossible, because the status is part of the referenced
   key. Under D-259's adopted table that pair is already illegal at step 2, so this branch should be
   unreachable — **catch it anyway**, translate it to a domain error saying the release must be withdrawn
   first (INT-014), and put one sentence at the branch: it exists because the table in `domain.py` and
   the key in the migration are two statements of one rule, and a future widening of the first without
   the second must not surface as a raw `IntegrityError`.

**`set_released_revision`.** One statement, one conditional second:

```sql
UPDATE registry.prompt_property
   SET released_version_id     = :version_id,
       released_version_status = 'Approved',
       released_at             = :released_at
 WHERE id = :prompt_id
   AND released_version_id IS NOT DISTINCT FROM :expected_current_version_id
```

- **All three columns in one `SET` list**, because `ck_prompt_property_released_pointer_is_whole` refuses
  a partial move — phase 13's D-221 routed exactly this to phase 14.
- **`released_version_status = 'Approved'` is a literal, not a parameter, and not a read.** It is the
  only value the CHECK permits, and binding it from anywhere else would be this module making a claim
  about the target's status. Say that at the statement.
- **`IS NOT DISTINCT FROM`, not `=`**, so `expected_current_version_id = None` correctly matches a NULL
  pointer — a first release. A `=` would never match NULL and every first release would look like a
  conflict. This is the single most likely bug in the file; write it at the statement.
- `released_at` is a **parameter** the caller passes, not `now()` read here: this repository's standing
  convention is that a `now` is an argument, and release-control's release row must carry the same
  instant.
- `IntegrityError` → branch on `_constraint_name`: `fk_prompt_property_released_revision` →
  `RevisionNotApproved(version_id)`; `ck_prompt_property_released_status` → the same domain error with a
  different message (it means somebody bound a status other than `'Approved'`, which under this
  implementation is impossible and is therefore a programming error worth naming); anything else →
  **re-raise unchanged**.
- `rowcount == 0` with **no** exception → the compare-and-set failed **or** the prompt does not exist.
  Distinguish them with one extra read on the failure path only, and say that the extra round trip is
  paid exactly where nobody is measuring. **Order matters**: the follow-up read must not run after an
  `IntegrityError`, because the session is in a failed state — put it in the `else` of the `try`, not
  after it.
- The conflict raises `ReleasePointerConflict(expected, actual)`, which INT-013 says release-control
  surfaces as **409**: *"someone released something else while this reviewer had the screen open, and
  overwriting it silently is how a release nobody decided reaches production."* Quote it.
