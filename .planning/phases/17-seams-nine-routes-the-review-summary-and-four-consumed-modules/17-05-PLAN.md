<objective>
Prove the phase's headline criterion over the whole assembled stack, in the one shape that cannot be
faked: **drive a real 20-case run through Phase 16's claim loop and executor, against a real socket, and
read the comparison back through 17-01's submit route, 17-02's pricing and 17-04's comparison route —
never by inserting the executor's output by hand.** D-300 gives this phase no case-level code path of
its own, which means this plan's `test_run_and_compare.py` is the first test in the whole milestone that
exercises Phase 16's executor and this phase's money and comparison logic *together*. **The rig chooses
to drive the real executor against a stub HTTP provider rather than seed `case_result` rows directly —
stated here as the load-bearing decision it is**: seeding rows would prove the comparison's arithmetic
and nothing about whether a submit actually reaches a dispatch, a claim, or a price; driving the real
path proves the seam, at the cost of needing a real socket, a real admission gate and a real two-revision
fixture whose scripted answers deliberately diverge on some cases so the comparison has something to
show. That is `tests/evaluation/__init__.py`'s and `tests/prompt_registry/__init__.py`'s discretion item,
resolved in the direction the phase architect's brief already named.

This plan also lands the **route-declaration proof for all nine routes** — `assembled_routes(app)`
contains exactly the nine `(method, path)` pairs, each with `declares_session` true and exactly one
`declared_action` from the four-member vocabulary — so Phase 23's cross-module AC-10 assertion finds a
declaration to extend rather than a hole to fill, the same relationship
`tests/architecture/test_route_table.py` already has with `call-ledger`'s five routes.

**The wall-clock half of SC1 is measured twice and reported twice, never averaged, and this plan states
which run the criterion is actually ticked against.** `tests/load/test_suite_run_p95.py` measures p50,
p95 and p99 over N independent 20-case runs against the stub with an injected 3s-per-request latency,
gated behind `PROPE_RUN_LOAD=1` per ORCHESTRATION §3 and the lock's own `test_plan.load` clause — that
file is where the numeric ROADMAP SC1 claim (`<= 120s at p95`) is asserted, and it does not run in the
default gate. `test_run_and_compare.py` proves the *functional* half — the run completes, the comparison
is real, both deltas are real — against a single unthrottled run with a generous absolute ceiling stated
as a liveness bound, never as the percentile claim. This is the honest answer the phase CONTEXT's
Discretion item names as costing a decision, and it is made here rather than left for a reviewer to
discover that the default `uv run pytest -q` never touches SC1's number at all.

**Nothing here writes to `src/prope/`.** Every assertion in this plan is written against the four plans
that already shipped this wave's code — 17-01's submit route, 17-02's pricing and claim-time ceiling,
17-03's suite and run-read routes, 17-04's comparison route and review summary — plus Phase 16's schema
and executor, planned in parallel and read from disk rather than assumed. If any of the eleven `truths`
above cannot be made true because a seam is missing or shaped differently than this plan expects, **the
fix is a follow-up owned by the plan that holds that file**, and this plan's job is to say precisely
which truth failed and against which file, in the SUMMARY — a gate that quietly patches what it is
supposed to be measuring has stopped being a gate.

### `tests/evaluation/stub_provider.py` — new

A minimal, real, socket-bound HTTP/1.1 responder, in `_stub_provider.py`'s register but written fresh
for this package (see the frontmatter's prohibition against importing phase 11's copy). Module docstring
states in two sentences: why it is a real socket (AC-7's own reason, restated: a transport-level mock
counts library calls, not wire requests, and this plan needs to prove the executor really dispatched);
and that it is deliberately a second copy of the pattern rather than an import, in `tests/load/__init__.py`'s
own words about `counter_value`.

```python
@dataclass
class ScriptedProvider:
    request_count: int = 0
    latency_seconds: float = 0.0     # injected delay before every response; 0.0 by default
    _answers: dict[str, str]          # request "reply_key" -> canned assistant content
    _default_answer: str
```

Behaviour:
- `async def start(self) -> str` — binds `asyncio.start_server` on `("127.0.0.1", 0)`, returns the
  `base_url` (`http://127.0.0.1:<port>`). `async def stop(self) -> None` closes it.
- Each request: parse the JSON body (an OpenAI-chat-shaped payload — `messages`, `model`, the caller's
  generation `parameters`), increment `request_count`, sleep `latency_seconds` if set (`asyncio.sleep`,
  never a blocking `time.sleep` — a blocking sleep would serialise the whole event loop and turn a
  concurrency-5 run into a concurrency-1 run, silently invalidating Task 4's p95 measurement in Task 3
  below), then look up the **reply key** the fixture embedded in the request (see `corpus.py` below) in
  `_answers`, falling back to `_default_answer` if the key is absent.
- Respond with a minimal OpenAI-chat-completion-shaped JSON body: one choice, `message.content` set to
  the looked-up answer, and a `usage` object with small, fixed, non-zero `prompt_tokens` and
  `completion_tokens` — **non-zero and fixed**, so Task 3's token-delta assertion has a known ground
  truth to check the application's own arithmetic against, rather than trusting whatever number happens
  to come back.
- `Content-Type: application/json`, `Connection: close` — one request per connection is fine here; this
  fixture does not need `upstream.py`'s connection-cache behaviour, only its request/response contract.

**No retry simulation, no redirect, no timeout scenario.** Those are phase 11's proofs (AC-7, `origin`
classification) and this plan's fixture answers every request; a case that never reaches the provider is
out of this fixture's scope by design (OQ-094 already covers that split, in 17-02).
