## D-304a — the caller's session carries the evidence; call-ledger's totals necessarily do not

`get_review_summary` is handed an `AsyncSession` and must call
`get_run_totals(sessionmaker, workspace_id, run_id)`, which takes neither of those things: D-19 gives it
its own transaction and D-20 therefore gives it a `workspace_id` argument, and both are shipped facts in
a file this plan may not touch. Three consequences, decided here rather than at a keyboard:

**The sessionmaker is derived, not passed.** `AsyncSession.bind` is the `AsyncEngine` the session was
opened from — verified on this repository's SQLAlchemy 2.0.51 — so
`async_sessionmaker(bind=session.bind)` yields a maker on the **same engine and the same pool** with no
new configuration and no second `Settings` read. If `session.bind` is `None`, the function raises
`ReviewSummaryUnavailable`; it does not guess an engine. **Rejected: adding a `sessionmaker` parameter.**
The architect fixed the signature at `(session, prompt_id, version_id)` and Phase 23 is written against
it; a fourth argument is a change to a registered seam bought for a mechanical convenience.

**The workspace is read from the transaction's own tenant context**, with
`SELECT current_setting('app.workspace_id', true)`, never from an argument. This is D-304's *"no
`workspace_id` parameter"* honoured literally and it buys a property an argument could not: the
workspace `get_run_totals` is asked about is **the same one RLS already scoped the run rows to**, so the
two cannot disagree. A `NULL` or empty setting means the caller opened a session outside
`workspace_transaction`, every evidence read would return zero rows, and the function raises.

**The money reads are a second snapshot, and the split is the honest one.** The *evidence* — suites,
runs, counts, timestamps — is read on the caller's session, so the revision release-control is showing
and the evidence beside it are one instant. The *money* comes from another module's append-only table
through its own seam a few milliseconds later. The only thing that read can miss is a `price_run` that
lands in between, and missing it produces `unpriced_count > 0` or a `NULL` cost, which withholds the
delta — the fail-safe direction. **The totals reads are sequential**, one after another, never gathered:
each takes a second pooled connection while the caller's transaction holds one, and a `gather` over N
suites can exhaust the pool and deadlock the request against itself.

— **Reversibility:** costly — Phase 23 is written against the signature.

## D-305a — "latest completed" is the most recently SUBMITTED completed run, ordered by id

INT-017 says *"latest completed run for that revision"* and no authority says what *latest* means when a
revision has been re-run. `case_flip_total` exists because re-runs are expected, so the tie is real.

**Adopted: `ORDER BY id DESC` among completed runs**, which is submit order — `evr_` ids are ULIDs
(ADR-0003, A-045) whose lexicographic order is their mint order, and the row is minted in `submit_runs`
at the reviewer's own request. **Rejected: `finished_at DESC`.** Consider run A submitted at 10:00 and
finishing at 10:20, and re-run B submitted at 10:05 and finishing at 10:10. Under `finished_at` the
summary shows B at 10:10 and then **flips back to A** at 10:20 — the displayed evidence moves backwards
to a run the reviewer started *before* the one they were just looking at, and a reviewer refreshing the
screen watches the pass/fail column change for a reason that is neither a re-run nor sampling noise.
Under id ordering the row only ever moves forward. **Rejected: `started_at DESC`** — `started_at` is
written at the *claim*, so it orders by scheduler behaviour rather than by anything a person did.

No authority is contradicted, so **no OQ is owed**; it is an adoption, recorded in the SUMMARY's ledger
section for `ORCHESTRATION-DECISIONS.md`.

— **Reversibility:** cheap for the ordering, costly for the SQL if `id` ever stops being a ULID.

## D-305b — one row per suite the prompt CURRENTLY has, and a suite edit mid-review is fail-closed

The rows are keyed on the suites the prompt has **now**, at their current versions, with a `LEFT JOIN
LATERAL` to the latest completed candidate run **for that suite version**. Three consequences, all
stated:

1. A suite created after the run appears as a row with `has_completed_run = False`, which makes
   `requires_acknowledgement` true. Under any run-keyed alternative it would be invisible, and a
   reviewer would approve with no evidence for a yardstick that exists and no acknowledgement of it.
2. A suite **edited** during a review — version 4 becomes version 5 — flips its row to
   `has_completed_run = False` until the candidate is re-run at version 5. That is A-004's argument
   arriving where it matters: the evidence on screen was measured with a yardstick that is no longer the
   yardstick, and the fail-closed direction is the safe one.
3. `suite_id` encodes name **and** version (the lock says so), so the lateral's `r.suite_id = s.id`
   predicate is what pins the yardstick. Nothing compares suite *names* on this path.

## D-306a — one exception type, and every handler in `review.py` re-raises

`ReviewSummaryUnavailable(RuntimeError)`, declared in `domain.py` beside the types it is about. **One
type, not two.** Release-control's response to *"the prompt row was not visible"* and to *"call-ledger's
totals raised"* is identical — evidence unavailable, acknowledgement mandatory (A-070) — and a second
type is a second branch, and the second branch is the one that proceeds. It does **not** subclass
whatever refusal type the routes raise: it is not an HTTP refusal, and route 9 letting it become a `500`

release-control answers `5xx` when INT-017 raises **with the approve action still available**.

Every `except` in `review.py` re-raises, chained with `from exc`, and an AST walk in the contract test
asserts it — because the failure this forbids is not one somebody argues for, it is one somebody adds in
a hurry six months from now.

## D-308a — the fold, and the three edges the fold does not obviously cover

One fold, in this order:

| # | condition | rollup delta | why |
|---|---|---|---|
| 1 | any row's `cost_delta.withheld_reason is not None` | `CostDelta(None, None, SUITE_WITHHELD)` | D-308, SC4. The per-suite list is returned **untouched** |
| 2 | `suites` is empty | `CostDelta(None, None, NO_BASELINE)` | Nothing was measured, so there is nothing on the other side. A-060's member is the only one of the seven whose text is true here |
| 3 | the present deltas carry more than one `currency` | `CostDelta(None, None, CURRENCY_MISMATCH)` | A-107: no FX, so no total — never a converted one. Unreachable today (one candidate revision, one baseline revision, one binding each) and written anyway, because *unreachable* and *unwritten* look identical from a stack trace |
| 4 | otherwise | `CostDelta(sum(amounts), that currency, None)` | A genuine total, including `Decimal("0")` |

Rung 1 above rung 2 and rung 3 is deliberate: `suite_withheld` is the most specific true statement
available whenever it applies.

**`SuiteRow` carries `candidate_cost` and `baseline_cost`** — the two figures its delta was computed
from — with a `__post_init__` that ties them to the delta: **both present exactly when
`cost_delta.withheld_reason is None`, both `None` otherwise.** This is an addition to the CONTEXT's
sketch and it is load-bearing twice. The rollup's ratio is `sum(candidate) / sum(baseline)` and cannot
be derived from deltas alone; and a withheld side rendered as a zero cost becomes **unconstructible**
for the same reason `CostDelta.__post_init__` makes a withheld amount unconstructible. **Rejected:
carrying a per-suite `cost_delta_ratio` field instead.** Ratios do not sum, so the rollup would need the
costs anyway, and a second derived money field on the row is a second thing Phase 23 can render wrongly.

## D-309a — the threshold is configuration with a default; the ratio is one number; there is no block

**`cost_delta_ratio = candidate_total / baseline_total`, quantized to four decimal places
(`ROUND_HALF_UP`), and the SAME quantized value decides `cost_warning`.** One number for the flag and
for the screen, so they can never disagree at the fifth decimal. `cost_warning` is
`ratio is not None and ratio >= 1 + threshold` — a ratio, matching the metric's declared 1.20 bucket
edge and OQ-009's *"warn at >= +20%"*. The boundary is `>=`, asserted at exactly `1.2000`.

Two edges, decided: a **zero baseline total with a positive candidate total** has no finite ratio, so
`cost_delta_ratio` is `None` and `cost_warning` is **true** — the flag's job is to make a reviewer look,
and "it used to cost nothing" is the strongest case for looking. A **zero on both sides** gives
`cost_delta_ratio = None` and `cost_warning` false. Neither observes the histogram: there is no ratio to
observe, and a fabricated one is what the metric's `None`-not-zero rule exists to prevent.

**The threshold is configuration.** `EvaluationSettings(BaseSettings)` in `domain.py`, one field —
`eval_cost_warning_threshold: Decimal = Decimal("0.20")`, `ge=0`, `PROPE_` prefix, `.env` file, so the
operator key is `PROPE_EVAL_COST_WARNING_THRESHOLD`. This is a **second `BaseSettings` subclass**, which
`src/prope/db/engine.py`'s own docstring argues against — and the argument does not reach this case. It

## D-316a — route 9 pairs the baseline by suite id, and refuses when the same NAME sits at another version

The baseline pairing rule is `suite_id` equality (the lock: *"the most recent completed run where
`version_id` equals the prompt's current `released_version_id` and `suite_id` equals the candidate run's
`suite_id`"*), and `suite_id` encodes name and version. Applied alone it makes D-316's refusal **dead
code**: a baseline measured with an older suite version simply is not found, and the block reports
`no_baseline`. AC-4 asserts that refusal happens, so pairing alone cannot be the whole rule.

**Adopted, on route 9 only:** pair by `suite_id`; when that finds nothing, look for a completed baseline
run for the same suite **name** at a **different** `suite_version`; if one exists, refuse the whole
request with `409` and `details` carrying the suite name, the candidate's `suite_version` and the
baseline's `suite_version` — **both versions, in `details` and never in `message`** (ADR-0053). The
machine code is taken **by reference** from whichever constant 17-01 and Phase 16 left on disk
(`ErrorCode.EVAL_SUITE_VERSION_MISMATCH` / `CROSS_SUITE_VERSION_COMPARISON`); a test asserts the two
values are equal if both exist. **Rejected: refusing only that block.** A screen rendering three blocks
where one quietly says *not comparable* is the authoritative-looking meaningless comparison the lock's
failure_mode row 4 describes, and INT-025 and AC-4 both say *refused*.

**`get_review_summary` does not inherit this refusal**, and the asymmetry is the point: the summary's
job is to report per-suite state including *we could not compare this*, so it withholds that suite's
delta with `no_baseline` and returns. Route 9's job is to render two runs' cases side by side, which is
undefined across yardsticks.

## D-318a — money comes from the seam, tokens come from the run row

`RunTotals` is derived from `ledger.call_record`, and **those rows do not exist until `price_run` has
run**. So a completed-but-unpriced run yields `input_tokens = 0, output_tokens = 0, cost = None,
unpriced_count = 0` — and treating those zeros as token counts would put a fabricated token delta on the
screen of exactly the run that could not be priced.

**Tokens therefore come from `eval_run.input_tokens` / `eval_run.output_tokens`**, which the executor
writes at completion (Phase 16's D-284 lists both as updatable), and the token delta is present only
when **both** sides' columns are non-`NULL`. **Money comes only from `get_run_totals`**, never from
`eval_run.cost_amount`, because the two counts that decide the withholding exist only on the seam's
answer (D-318, INT-021). A side with no completed run passes `None` to `compute_cost_delta`, which is
its rung 1; a completed side with `priced_at IS NULL` passes its real `RunTotals` and falls to the rung
that reads `cost is None`. Both land on `NOT_PRICED_YET`, which is the state Phase 16 ships in.

```sql
WITH current_suites AS ( … the shared expression … )
SELECT s.id            AS suite_id,
       s.name          AS suite_name,
       s.suite_version AS suite_version,
       s.case_count    AS case_count,
       r.id            AS run_id,
       r.finished_at   AS finished_at,
       r.pass_count, r.fail_count, r.error_count,
       r.input_tokens, r.output_tokens
FROM   current_suites s
LEFT JOIN LATERAL (
    SELECT run.id, run.finished_at, run.pass_count, run.fail_count, run.error_count,
```
