<objective>
Ship one vertical path through the module with the most edges in Prope, and use it to fix — once, for
the whole phase — the two closed vocabularies that five later plans consume. **A reviewer's submit
becomes N queued runs plus N `eval_run_started` history events in ONE transaction, against a
`history.history_action_registry` allow-list that must already carry `version_id` and `suite_version`
or the very first append is refused with `unknown_detail_key` and rolls the whole submit back.** That
refusal is not hypothetical: Phase 4 seeded all four `eval_*` rows with an **empty** `detail_keys` on
purpose (D-61) and routed the registration to Phase 16 twelve phases in advance, and Phase 16 appends
nothing at submit time so it has no reason to notice.

This plan therefore opens with an **inventory task**, and that is the deliberate shape rather than
caution. Phase 16 is being planned and executed in parallel; its plan set lands on disk first and
**disk is the authority**. `.planning/phases/16-*/16-CONTEXT.md` D-292 draws the Phase 16 / Phase 17
line at the HTTP edge and the pull, D-280 puts the four `detail_keys` updates inside Phase 16's own
revision, and D-288 puts an `eval_run_started` append inside the **claim** transaction with
`actor_type = 'system'` — while this phase's D-319 puts `eval_run_started` at the **creation** of the
run rows, in `app`, with the reviewer as `actor_id`. Those two statements are not compatible, and Task
1 is what turns that from a discovery in review into a line in a SUMMARY. **This plan does not edit
Phase 16's claim path under any circumstance** — it is not in `files_modified`, plan 17-02 owns the
one insertion that goes there, and a phase that "fixed" another phase's append while that phase was
still executing would be the lost update ORCHESTRATION §8 exists to prevent.

What ships: D-319's verify-then-add revision (or a written statement that Phase 16 already did it);
the four `ManagementAction` members valued by reference from `access_control.vocabulary.Action`, which
is BR-10 expressed as data — **`suite.edit` is not `prompt.edit`**; evaluation's whole closed
error-code set, declared here so that 17-03 and 17-04 in later waves consume members rather than
racing each other to add them to a shared file; and INT-025 route 6,
`POST /api/v1/prompts/{prompt_id}/eval-runs`, as `202` with one run id per suite, `[]` for a prompt
with no suites, `may()` on the prompt row the handler already read, the advisory `check_spend_ceiling`
refusal that states a reason and no figure, and **no `409` for `max_concurrent_runs`** (D-314,
`OQ-091`).

Deliberately left open, with the plan that closes each. The other eight routes are 17-03's (seven) and
17-04's (the comparison). `get_review_summary`, `requires_acknowledgement`, the rollup and the
withholding fold are 17-04's. Pricing, `get_run_totals`, the three-valued cost delta and the
claim-time ceiling — including `eval_run.status = 'refused'` and
`prope_evaluation_run_total{status=refused}` — are 17-02's. The 20-case end-to-end run and the two p95
numbers are 17-05's. **The same-workspace private prompt is Phase 18's (EVAL-06), and this plan states
that gap rather than papering over it**: this module reads visibility from RLS alone, so today a
prompt in the actor's own workspace that they hold no grant on answers `403` where EVAL-06 will
require `404`. D-311 declines `visible_subject_filter` for this module and routes the gap to Phase 18;
this plan asserts the two refusal shapes that ARE decidable today and names the third.

month, every row's timestamp and every event's `occurred_at` are one instant.

Body, in order:

1. `suites = await repository.current_suites(session, prompt_id=prompt_id, names=suite_names)`.
2. If `suite_names` was supplied and any requested name is absent from the result: raise
   `ManagementRefusal(422, ErrorCode.EVAL_SUITE_NAME_UNKNOWN, details={"names": sorted(missing)})`.
   **The whole submit is refused, not the recognised subset** — D-313's argument applies with more
   force to a re-run than to a first submit: a screen showing three suites when the reviewer asked for
   four is a screen where they cannot tell which yardsticks were applied.
3. If `suites` is empty: `return []`. **Zero rows, zero events, and the caller still answers `202`**
   (D-313). A `404` here would say the prompt does not exist, which is false, and not-found is the one
   response shape in this project that carries security weight.
4. For each suite, in name order: mint `run_id = f"{RUN_ID_PREFIX}{ULID()}"`, `INSERT` one `eval_run`
   row with `status='queued'`, `role='candidate'`, `started_at = NULL`, `started_by = actor_id`,
   `suite_id`, `version_id`, `prompt_id`, `workspace_id`. **`role` is `candidate` for every row this
   function writes**; a baseline run is started by Phase 16's pairing rule (EVAL-03) and never by this
   route. Then, on the **same session**, `await append(session, HistoryEventDraft(...))` with:

   | field | value |
   |---|---|
   | `workspace_id` | the argument |
   | `actor_type` | `'user'` |
   | `actor_id` | the argument — the reviewer, because a person did this |
   | `action` | `'eval_run_started'` |
   | `target_type` | `'eval_run'` |
   | `target_id` | the minted `run_id` |
   | `scope_prompt_id` | `prompt_id` — what makes the Activity feed one indexed read (A-119) |
   | `reason` | `None` — `requires_reason` is false for this action |
   | `details` | `{"version_id": version_id, "suite_version": suite["suite_version"]}` |
   | `occurred_at` | `now` |

   **N runs, N events**, one per run, because `target_id` addresses one run and an event about three
   runs could not name its subject. A prompt with no suites produces no event at all, which is the
   correct shape: no state change, no trail.
5. Return the `StartedRun` list.

### `src/prope/evaluation/api.py` — route 6

Module docstring in `call_ledger/api.py`'s register but at §12's length, carrying five things and no
more: INT-025's nine paths as a table with the plan that adds each (so a reader of the half-built file
knows it is half-built on purpose); `{prompt_id}` and `OQ-078`; that `may()` is called once, after the
prompt row is read, with the subject supplied from that row (ADR-0020); that every handler runs inside
exactly one `workspace_transaction` and a query without it returns **zero rows rather than an error**;
and A-046's never-logged list.

```python
router = APIRouter(prefix="/api/v1")

@router.post(
    "/prompts/{prompt_id}/eval-runs",
    status_code=202,
    response_model=EvalRunSubmitRead,
    dependencies=[Depends(declares_action(ManagementAction.RUN_START))],
)
async def submit_eval_runs(
    prompt_id: str,
    body: EvalRunSubmitWrite,
    session: Annotated[Session, Depends(require_session)],
    sessionmaker: Annotated[async_sessionmaker[AsyncSession], Depends(get_sessionmaker)],
) -> EvalRunSubmitRead:
```

**The `{prompt_id}` spelling is whatever prompt-registry actually mounted** — read
`src/prope/prompt_registry/api.py` and match it byte for byte. `OQ-078` records that the authorities
spell it two ways and that the route-uniqueness assertion compares literal strings, so two modules
disagreeing would make a genuine duplicate invisible to the test whose whole job is to see it. **Add
nothing to `OQ-078`**; record the five paths this module will mount in the SUMMARY instead.

Handler body, in this order, and the order is load-bearing:

1. `now = datetime.now(UTC)` — read once, at the top, passed everywhere.
2. `async with workspace_transaction(sessionmaker, session.workspace_id) as db:`
3. `row = await repository.get_prompt_authority(db, prompt_id=prompt_id)`
4. `allowed = await may(db, actor_for(session), ManagementAction.RUN_START.value, subject)` where
   `subject` is built from `row` when there is one and from a **synthetic private, ownerless** subject
   when there is not. Then
   `refusal = refusal_for(visible=row is not None, allowed=allowed, action=…)` and raise it if it is
   not `None`. **Both arguments are evaluated unconditionally before the branch** — Phase 9's D-131:
   *a short-circuit that skips `may()` when the subject is invisible makes the two paths do different
   amounts of work, which is a timing oracle on exactly the distinction A-116 exists to hide.* Follow
   14-01's `refuse_unless_permitted` helper if it exists in the registry's api module; **do not import
   it across module packages** — copy the shape, one local helper, and say so.
   **The stated gap:** `visible` here is RLS visibility only. A prompt in the actor's own workspace
   that they hold no grant on is `visible=True`, so today it answers `403` where EVAL-06 will require
   `404`. D-311 declines `visible_subject_filter` for this module and routes that to **Phase 18**.
   Write one `# WHY:` line at the `visible=` argument naming Phase 18 and EVAL-06, and record it in
   the SUMMARY. Do not close it here and do not pretend it is closed.
5. `decision = await check_spend_ceiling(sessionmaker, session.workspace_id, now=now)` — **after** the
   permission decision, so a caller who cannot see the prompt never causes a ceiling evaluation and
   never moves `prope_call_ledger_ceiling_check_total`. It takes a **sessionmaker** and opens its own
   transaction (call-ledger's D-19) while this handler holds one open; that is a second pooled
   connection and no lock is shared, and it looks wrong enough to earn a one-line
   `# WHY: INT-020 takes a sessionmaker by D-19; this is a second connection, not a nested transaction.`
   On `not decision.allowed`, raise
   `ManagementRefusal(409, ErrorCode.MONTHLY_CEILING_EXCEEDED, message=…, details=None)`.
   **Discretion item 5, resolved: `409`, not `402`.** Three reasons, in order of weight. (a) The SPA
   branches on the machine `code`, never on the status (ADR-0053), so the status's whole job is how a
   generic HTTP client and the proxy in front of it behave — and RFC 9110 §15.5.3 leaves `402`
   *reserved for future use*, which is a poor thing to make a wire promise out of on a frozen
   `/api/v1`. (b) `409` is already in this module's declared status vocabulary (route 2's duplicate
   name, route 9's suite-version mismatch), so the client's error handling is closed at
   `403 / 404 / 409 / 422` instead of gaining a fifth branch. (c) A `402` in Caddy's access log names
   the workspace's billing position to every reader of that log, and log readers are not permission-
   checked — which is A-056's concern one layer out from the response body. The refusal is genuinely a
   conflict with the workspace's current state, so `409` is not a fudge. **`details` is `None` and the
   `message` contains no figure, no limit, no remainder, no percentage and no currency.**
   **Nothing here writes `status='refused'`** and nothing here increments
   `prope_evaluation_run_total` — the claim-time result owns both (D-302), in plan 17-02.
6. `revision = await get_revision(db, body.version_id)`. `None`, or a revision whose prompt is not
   `prompt_id`, raises `ManagementRefusal(422, ErrorCode.EVAL_VERSION_NOT_FOR_PROMPT,
   details={"version_id": body.version_id})` — a value the caller already sent, which is the only kind
   of thing `details` may carry. `422` and not `404`: the actor can see the prompt, so there is no
   existence to protect, and naming the field they got wrong is what lets them fix it. Use
   `get_revision`'s **real** signature from Task 1; if INT-011 is not wired on disk, skip this check,
   raise nothing, and record the omission in the SUMMARY rather than reaching into another module.
7. `started = await submit_runs(db, prompt_id=…, version_id=…, suite_names=body.suites,
   actor_id=session.user_id, workspace_id=session.workspace_id, now=now)`
8. Build `EvalRunSubmitRead(runs=[EvalRunStarted(run_id=r.run_id, suite_id=r.suite_id,
   suite_name=r.suite_name) for r in started])` — **field by field, never a splat.**
9. One `log.info("evaluation.run_started", …)` **per created run**, carrying only
   `workspace_id`, `actor_id`, `prompt_id`, `version_id`, `run_id`, `suite_id`, `suite_name`,
   `suite_version` — all members of `LOGGABLE_FIELDS` after Task 3, and no count field.

The transaction commits at the context manager's exit. **The atomic unit is the `eval_run` rows plus
their events**; the ceiling check is a read on its own transaction and has nothing to roll back, which
is worth the one sentence it gets in `submit_runs`' docstring.

The `prompt_id` path parameter takes **no validation regex**: an id that does not exist is a `404`
through the ordinary path, which is the same answer a malformed one deserves, and a prefix check here
would be a second place ADR-0003's id format is written.
