<objective>
Build the transaction that turns a `queued` row into a `running` one, and prove it is **one**
transaction. `claim_one` calls the fourth sanctioned `SECURITY DEFINER` function with no tenant set,
sets the tenant mid-transaction from the workspace the claim just produced, appends the
`eval_run_started` history event under that tenant, and commits — after which the row lock is gone and
the executor may take 120 s without holding anything.

**The load-bearing claim is that the status change and its event are atomic, and the only way to
demonstrate it is from the failing side.** A test that claims a run and finds an event beside it is
satisfied by two commits as easily as by one. So this plan makes `append` raise and asserts that
`status` is still `queued`, `started_at` is still NULL and `history.history_event` is empty — and,
because a negative result is worthless without attribution, it first proves through `migrate_engine`
that the queued row was there to claim and then proves that the identical call claims it once the
injection is removed. That trio is what separates *the transaction rolled back* from *there was
nothing to claim* and from *the test looked at the wrong table*.

The second half is a gauge, and it is the single most likely silent defect in this phase. A
`prope_app` `SELECT count(*) FROM evaluation.eval_run WHERE status = 'queued'` with no tenant set
returns **zero rows** — the tenant policy working exactly as designed — so the obvious implementation
reads 0 forever, `EvalQueueBacklog` never fires, and the whole thing looks healthy. This project has
been bitten by that shape twice already (`ObservedWorkspaces`' *"runs cleanly, deletes nothing, and
looks healthy"*, and `observe_oldest_body_age`'s corrected paragraph). So the depth pass walks a
`WorkspaceEnumerator` — 02-03's seam, filled since Phase 7 by ADR-0051's `access.list_workspaces()` —
and counts per workspace **under** the policy. The test asserts the gauge is non-zero for queued runs
in a workspace the reading transaction never set as its tenant, and sets the two wrong readings beside
it (0 with no tenant, one workspace's share with the wrong tenant) so that the assertion has something
to fail against.

**What this plan deliberately leaves open.** It writes no executor and dispatches nothing — plan 16-05
composes `execute_run` and the fourth `worker` job, and it is the plan that imports `claim_one` and
`observe_queue_depth`. It does not assert owed AC-13's *two concurrent claim loops, one winner*; that
lives in `tests/integration/test_claim_next_run.py`, which another plan in this phase owns, and this
plan's bound assertion is the caller-level, serially-awaited one instead. It writes no
`eval_run_completed` event: 16-04 owns the status writer and 16-06 owns completion. And it implements
D-289's bound without closing D-289's hole — under `READ COMMITTED` two claim loops can each see the
last free slot, ADR-0049's Consequences say otherwise in as many words, and that sentence is **raised
as OQ-090 rather than patched**.

**No Alembic revision, no DDL, no schema change.** Everything this plan needs at the database — the four
tables, their policies, the grant matrix, `evaluation.claim_next_run(integer)` with its `GRANT EXECUTE`,
the three `eval_run` indexes and the four `history.history_action_registry` `detail_keys` updates —
ships in plan 16-01's single revision (D-280). This plan allocates no revision number, runs
`uv run alembic heads` for no purpose, and adds no dependency: `uv.lock` must not move.

## Resolutions this plan makes

16-CONTEXT consumes D-280 through D-299 and **the range is closed**, so none of the following mints a
new decision id. Each is a resolution the CONTEXT's *Claude's Discretion* block or an ordinary gap left
to the plan, stated here so the executor does not have to invent it and the SUMMARY can report it.

**R1 — `ClaimedRun` is defined in `claim.py`, unless 16-01 already put it in `domain.py`.** The
CONTEXT's signature block places `claim_one(...) -> ClaimedRun | None` in `claim.py` and
`execute_run(sessionmaker, claimed: ClaimedRun, ...)` in `executor.py`, and names no home for the type.
It goes here, a frozen slotted dataclass of exactly ADR-0049's five identifiers, because this is the
module that produces it. **If `src/prope/evaluation/domain.py` already declares a `ClaimedRun`, import
it and do not declare a second one** — two dataclasses sharing a name across two modules is the trap
`tests/property_history/__init__.py:64-76` records for `INSERT_HISTORY_EVENT`, where a field added in a
later phase lands in whichever of the two the author had open. Report which way it went in the SUMMARY.

**R2 — the mid-transaction tenant helper reuses `prope.db.session.SET_TENANT` rather than declaring a
second copy.** D-288 requires *a named helper in this module with the reason at it, not a bare
`execute` at the call site*, and this satisfies both halves: the helper is named and local, the
statement is the project's one definition. A second `text("SELECT set_config('app.workspace_id', :ws,
true)")` in a second module is two places that must agree about the third argument — and the third
argument is the entire difference between a transaction-local setting and one that leaks into the next
transaction on a pooled connection. **Rejected: `workspace_transaction`.** It opens the transaction, and
the whole point of D-288 is that the transaction is already open with a query already run in it.

**R3 — the event's actor is `SYSTEM` carrying the run's `started_by`, and `suite_version` +
`started_by` are fetched by ONE policied read after the tenant is set.** `claim_next_run()` returns five
identifiers and neither of these is among them, and widening it is forbidden (ADR-0051). So one
statement, joined across `eval_run` and `eval_suite` on the composite key, issued **after**
`set_tenant_mid_transaction` — which is not merely acceptable but is the demonstration the lock file
asks for: *"everything after the claim runs under ordinary RLS."* `actor_type = SYSTEM` because the
claim loop performed the transition, up to a second later, in another process; `actor_id =
started_by` because `HistoryEventDraft.__post_init__` explicitly permits a system actor **with** an id
and dropping the submitter would leave an audit row that cannot say whose submit this run serves.
**Rejected: `ActorType.USER`** — the user did not perform this state change. **Rejected: `SYSTEM` with
`actor_id=None`** — *"an audit row that cannot say who acted is not one"* is the draft's own sentence,
and here we can say. 16-04's and 16-06's `eval_run_completed` should follow this shape; that is a
pointer for those plans, not a change to them.

**R4 — neither new module logs.** `LOGGABLE_FIELDS` is in `src/prope/observability.py` and D-299 has
plan 16-01 adding this module's ten field names to it. That file is not in this plan's declaration, and
a `log.info(..., run_id=...)` here would make this plan's own gate
(`tests/architecture/test_loggable_fields.py`, which walks the source and refuses an unlisted keyword)
depend on another plan's edit having landed first — a red test this plan did not write, in a wave whose
plans run concurrently. The history event is the durable record and `append` already logs
`property_history.event_appended` with `target_id`, `workspace_id`, `scope_prompt_id` and `actor_id`,
every one of which is already in the allow-list. Nothing is lost.

**R5 — `WorkspaceEnumerator` is re-declared in `queue_depth.py`, not imported from `prope.worker`.**
Structurally identical, deliberately not imported: 16-05 makes `worker.py` import this module, and an
import in the other direction is a cycle at module load. `prope.call_ledger.retention` sets the
precedent — it declares its own `ChunkObserver` alias rather than reaching into the module that
schedules it.

**R6 — the gauge is the SUM over enumerated workspaces, unlabelled, and the pass returns it.**
Unlabelled because ADR-0030's cardinality rule makes `workspace_id` never a label and a project test
asserts it; the sum because `EvalQueueBacklog` (`> 10 for 15 min`) is a whole-deployment threshold. The
`int` return is what 16-05's job body and this plan's tests read, in `sweep_expired_bodies`' shape.

**R7 — `claim_one` takes a keyword-only `clock`, defaulted.** The event's `occurred_at` is the one
clock read on this path; `worker.py:503-506` and `run_worker`'s `clock` parameter already establish the
pattern, and it lets the test assert an exact instant rather than a window. The production composition
passes nothing.

**R8 — OQ-090 is created by this plan's executor, not by the planner.** ORCHESTRATION §5 makes creating
an allocated `OQ-NNN.md` the one permitted `docs/` write; the id is allocated to D-289 by 16-CONTEXT
and to no sibling plan. `docs/adr/0049-…` is **not** edited.

1. **What ADR-0049 claims**, quoted verbatim — including *"this bound survives replication and
   ADR-0046's does not"*.
2. **Why it is false as written.** `SKIP LOCKED` guarantees that two loops never claim the *same* row,
   and that half is true and is what owed AC-13 asserts. It says nothing about two loops claiming
   *different* rows of the same workspace. The admission predicate is a correlated
   `count(*) WHERE status = 'running'`, and under `READ COMMITTED` — PostgreSQL's default and this
   project's — each statement sees a snapshot taken at statement start, in which the other
   transaction's uncommitted `UPDATE … SET status = 'running'` is invisible. Both loops can therefore
   see the same last free slot, and `max_concurrent_runs = 2` becomes 3. The row lock does not help:
   the rows are different rows, so nothing contends.
3. **What ships anyway, and why it is exact under it.** Exactly one claim loop per process, awaited
   serially — one claim per tick, the run started before the next tick claims — and **one `worker`
   replica**, which is ADR-0033's runtime and A-138's recorded scope. Under that composition there is
   only ever one uncommitted claim transaction at a time and the count is exact. This plan implements
   the bound as a parameter (`claim_one(..., max_concurrent_runs=…)`) and asserts it in the serial form
   in `tests/integration/test_claim_and_event_are_atomic.py`.
