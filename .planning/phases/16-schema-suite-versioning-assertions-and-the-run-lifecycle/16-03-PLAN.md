<objective>
Ship the two halves of *authoring*: the **assertion registry**, which decides what a case may assert
and refuses everything else where its author can fix it, and the **suite writer**, which makes
*"editing a suite creates its next version"* a statement about rows rather than about discipline.

**A suite version is an INSERT, and the row that would be edited is one `prope_app` physically cannot
touch.** Plan 16-01 shipped the grant matrix — `SELECT, INSERT` on `eval_suite` and `eval_case`, no
`UPDATE`, no `DELETE` — and this plan is where that becomes visible from the outside: version 5 is
created with a fresh `evs_` id, version 4 is byte-identical afterwards over every column of the suite
row *and* of its case rows, and the sibling suite named `accuracy` is untouched **because nothing
writes it**, which is a stronger sentence than *because the writer is careful*. That is EVAL-04's
mechanism half and ROADMAP SC3's first two clauses.

**The assertion registry is code, not a table, and the contrast with `history.history_action_registry`
is the argument rather than an inconsistency** (D-296). An action name is *data* another module's
validator compares against, so a row is enough. An assertion type is bound to an **evaluator function
that must exist**: a registry row with no evaluator is a case that can never be run, discovered at
dispatch time, on a run somebody paid for. So the registry is a module-level immutable mapping
`{Modality: {type_name: Evaluator}}`, the payload is validated against it by a pydantic v2
discriminated union **at suite-save time**, and a `required_phrase` on a `structured` suite is refused
with `ASSERTION_TYPE_NOT_VALID_FOR_MODALITY` at the moment the author saves rather than as twenty
identical failures on a run they paid for.

**What this plan deliberately leaves open, and who closes it.** SC3's third and fourth clauses — an
in-flight run still reporting against version 4, and a comparison across two versions refused naming
both — are **not** here: the run row's lifecycle is 16-04's and the comparison is 16-06's, and their
test file is `tests/integration/test_suite_version_pinning.py`, which this plan must not write. The
regex **blast-radius** half of owed AC-11 (*"other work in the same `worker` container completes
unaffected"*) is **Phase 18's**; this plan proves the timeout fires and the outcome is `error`, which
is AC-11's first half and all of it that is observable without a running container. Nothing here
dispatches, nothing here is routed, and `src/prope/app.py` is not touched.

## D-295 — two dependencies are added, `uv.lock` moves, and this frontmatter is the permission

**Chosen.** `regex` and `jsonschema`, both pinned exactly. ORCHESTRATION §3 says *"no dependency may be
added unless a plan explicitly says so"*, and the `files_modified` block above plus this section are
that saying. The reviewer of the lock diff must be able to see it was decided rather than dragged in.

`regex` is not a taste. A-005 makes the pattern **user-authored code running in `worker`**; stdlib `re`
has no timeout and holds the GIL in C without yielding; and as of ADR-0049 that container also runs
call-ledger's drain, call-ledger's retention job and provider-access's batch dispatch. One prompt
owner's `(a+)+$` is an outage in three other modules, from a field that is user-authored by design.

`jsonschema` is named because **pydantic v2 emits JSON Schema and does not validate an arbitrary
externally-authored one**, so A-005's JSON-schema assertion type had no library until the lock's step-4
pass named one.

**Rejected: stdlib `re` with a length bound only.** The bound is the second line of defence, not the
first; a catastrophic pattern beats any input length worth allowing.
**Rejected: `signal.alarm` or a thread watchdog around `re`.** `signal.alarm` is POSIX-only and the
development host is Windows (ORCHESTRATION §3), and a thread cannot interrupt a C-level regex holding
the GIL — which is the whole failure being defended against.

**Reversibility: costly.** A dependency in `uv.lock` is a supply-chain decision, and removing `regex`
means re-answering T-009.

## D-297, resolved here — nine `text` types, seven `structured` types, and no egress

Two conflicts with the specs, one decision each, both **raised as `OQ-088` and neither patched**.

*The count.* `eval_case.notes` says *"the eight types in A-005"* and then enumerates **nine** — exact,
substring, regex, JSON-schema, required phrase, forbidden phrase, max length, max latency, max cost —
and A-005's own Statement enumerates the same nine. **Adopt nine**: the enumeration is the
specification and the adjective is the typo, which is D-60's disposition of the 30-vs-31 vocabulary
count one module over.

*The egress.* A-061 registers, for `structured`, *"a URL resolving to a fetchable asset of a stated
content type"*. Fetching that URL is outbound HTTP from `worker`, and this module's `external_services`
is `[]` with the comment *"No internet egress. Every upstream call goes through provider-access"*.
**`asset_fetchable` is therefore not registered**, and the test that asserts its absence carries the
reason at the assertion so it does not read as an omission.
**Rejected: routing the fetch through `dispatch()`.** That seam is chat-completions; a general fetch on
it is a new capability on the module that owns Prope's only egress, decided in an eval phase.

## Resolved here, because D-296 and D-297 name the registry and not its contents

Every one of these was open. A plan that leaves them open makes the executor invent them.

- **The type names are snake_case machine tokens**, and they are the discriminator values of the
  pydantic union, so they are wire-visible and one-way once a suite is authored against them.
  `text`: `exact_match`, `substring`, `regex`, `json_schema`, `required_phrase`, `forbidden_phrase`,
  `max_length`, `max_latency_ms`, `max_cost`.
  `structured`: `json_schema`, `required_key`, `forbidden_key`, `value_at_path`, `asset_count`,
  `max_latency_ms`, `max_cost`.

- **`substring` and `required_phrase` are two types because A-005 lists two, and the difference is
  written down rather than left for someone to ask about.** `substring` is raw containment — exact
  characters, case-sensitive, whitespace as written. `required_phrase` is the human-language check:
  both sides are `casefold()`ed and internal whitespace runs collapsed to one space, so *"Please
  Note"* matches *"please  note"*. `forbidden_phrase` is `required_phrase` negated, with the same
  normalisation, because a forbidden phrase that can be evaded with a capital letter is not a control.

- **`AssertionOutcome` is a three-member `StrEnum` — `PASSED`, `FAILED`, `ERRORED` — and it lives in
  `assertions.py`, not in `domain.py`.** Two reasons and both matter: `domain.py` is plan 16-01's file
  in a parallel wave and this plan may not touch it (ORCHESTRATION §8), and the assertion vocabulary
  belongs to the registry rather than to the schema — no CHECK constraint mirrors it. **`ERRORED` is
  A-057's rule pushed down one level**: a timeout in the assertion machinery is not evidence about a
  prompt, exactly as a dispatch failure is not, so it can never become a `fail`.
  **This contradicts an assumption plan 16-01 recorded in passing** — its `assertion_results` note
  says the per-assertion record shape is `(type, passed, code)`, and a boolean `passed` cannot
  represent `ERRORED`. The serialisation is 16-05's to write; **this plan hands 16-05 a three-state
  `outcome` and says so in the SUMMARY**, because a boolean there would silently collapse A-057.

- **`code` is never free text.** Every code any evaluator emits is a member of `MachineCode`,
  `WithheldReason` (both 16-01's, in `domain.py`) or `AssertionCode` — this module's own two-member
  enum holding the codes that exist nowhere else: `CONTENT_NOT_JSON` and `INPUT_TOO_LONG`. A unit test
  asserts that the set of codes the module can emit is a subset of the union of those three, which is
  what stops the fourth code from being a string literal typed at a call site.

- **Unparseable content is a `FAILED`, not an `ERRORED`.** A `structured` assertion, or a `json_schema`
  assertion in either modality, against content that is not JSON records `FAILED` with
  `AssertionCode.CONTENT_NOT_JSON`. A-057 separates a failure of the *machinery or the provider* from
  *evidence about the prompt*, and a prompt that was asked for JSON and returned prose is the second
  kind. The modality gate (16-05) catches the systemic version of this before dispatch; this is the
  per-case one.

- **Paths are JSON Pointers (RFC 6901), resolved by ten lines in this module.** `required_key`,
  `forbidden_key`, `value_at_path` and `asset_count` all take a `pointer`. A dotted path invented here
  would have to answer *"what if a key contains a dot"* forever, and RFC 6901 has already answered it
  with `~0` and `~1`. No library is added for it — `jsonschema` is for schemas.

- **`max_cost` is registered even though this phase produces no cost.** D-292 ships a run whose
  `cost_amount` is NULL until Phase 17, so `evaluate(..., cost=None)` on a `max_cost` assertion records
  `ERRORED` with `code = WithheldReason.NOT_PRICED_YET` — the same enum D-294 created so that a missing
  number always states *why*. **Rejected: refusing `max_cost` at save time until pricing exists**,
  which makes A-005's ninth type unauthorable and forces re-authoring later; the entire point of
  registering it now is that a suite authored today stays valid. The stated consequence, so nobody
  meets it as a bug: **in Phase 16 a suite carrying `max_cost` produces error results for those
  assertions**, and the `case_result.error_code` vocabulary — closed at eight values by 16-01's CHECK —
  has no member for it. That gap is real, is Phase 17's to close with pricing, and is escalated as
  owed-and-unallocated (this phase's OQ range is fully consumed, ORCHESTRATION §5).

- **A JSON schema containing `pattern` or `patternProperties` is refused at save time.** This is the
  half the architecture gate cannot see and is the sharpest thing in this plan. `jsonschema` evaluates
  those two keywords with **stdlib `re`**, on a schema the prompt owner wrote — which is precisely the
  user-authored-pattern-under-`re` execution T-009 exists to prevent, arriving through a library
  instead of through an import. An AST walk over `src/prope/` can never see it. So the schema is
  walked at authoring and refused if either keyword appears anywhere in it, with the message pointing
  at the `regex` assertion type, which is the supported way to assert a pattern and is the one with a
  timeout. **Rejected: accepting it and documenting the hole**, which is the documented blind spot
  D-87 already refused one module over.

- **The refusal shapes are two, and the line between them is ADR-0053's catalogue.** The *type
  vocabulary* refusals — a type valid for the other modality, a type valid for neither — raise
  `AssertionSpecRejected` carrying a `MachineCode`, because those are the two the authoring UI must
  translate into *"this assertion type is not available for this suite's modality"*. **Everything
  else** — an invalid regex pattern, a missing field, a wrong type, an extra field, a banned schema
  keyword — is a pydantic `ValidationError` and gets no machine code, because it is an ordinary
  malformed-body refusal and Phase 17 renders it as a 422 exactly like every other one. Inventing a
  seventh machine code would mean editing `domain.py`, which is another plan's file.

- **Neither writer calls `may()`.** Permission is the edge's decision and Phase 17 owns the edge —
  the same posture 13-02 took for `create_revision`.

**The values, first.**

```python
class AssertionOutcome(StrEnum):
    PASSED = "passed"
    FAILED = "failed"
    ERRORED = "errored"     # A-057 one level down: not evidence about the prompt

class AssertionCode(StrEnum):
    CONTENT_NOT_JSON = "content_not_json"
    INPUT_TOO_LONG = "input_too_long"

@dataclass(frozen=True, slots=True)
class AssertionResult:
    type: str
    outcome: AssertionOutcome
    code: str | None = None

@dataclass(frozen=True, slots=True)
class AssertionContext:
    content: str
    latency_ms: int
    cost: Decimal | None

Evaluator = Callable[[BaseModel, AssertionContext], AssertionResult]
```

`MAX_REGEX_INPUT_CHARS = 200_000` — the lock's *"length-bounded input"* as the second line of defence.
One line at it: the figure is a tunable judgement recorded so that changing it is a visible act, chosen
above any single chat completion in practice (~50k tokens), and it is **characters** rather than bytes
for ADR-0053's reason.

**The specs, as a pydantic v2 discriminated union.** One `BaseModel` per type, every one carrying
`model_config = ConfigDict(extra="forbid", frozen=True)`. `extra="forbid"` is load-bearing and gets the
one-line comment: a mistyped field name is refused at authoring, where its author can fix it, instead of
being silently dropped and asserting nothing forever.

| type | fields | evaluates |
|---|---|---|
| `exact_match` | `value: str` | `content == value` |
| `substring` | `value: str` | `value in content` — raw, case-sensitive |
| `regex` | `pattern: str` | `compiled.search(content, timeout=…)` is not None |
| `json_schema` | `schema: dict[str, Any]` | content parses as JSON **and** validates |
| `required_phrase` | `phrase: str` | normalised phrase in normalised content |
| `forbidden_phrase` | `phrase: str` | normalised phrase **not** in normalised content |
| `max_length` | `characters: int` (`gt=0`) | `len(content) <= characters` |
| `max_latency_ms` | `milliseconds: int` (`gt=0`) | `latency_ms <= milliseconds` |
| `max_cost` | `amount: Decimal` (`gt=0`), `currency: str` | `cost is not None and cost <= amount` |
| `required_key` | `pointer: str` | the pointer resolves |
| `forbidden_key` | `pointer: str` | the pointer does not resolve |

`regex.pattern` carries a pydantic **field validator that compiles it** — `regex.compile(pattern)`, the
default V0 behaviour left alone so a pattern the author tested elsewhere behaves the same — and lets
`regex.error` surface as a `ValidationError`. That is the lock's *"compiled once at suite save time so a
syntactically invalid regex is refused at authoring"*, and one line says what "compiled at save time"
does and does not mean: the **refusal** happens at save; the evaluate path calls `regex.compile` again
and hits the library's own pattern cache, so there is no second parse and no cross-request cache to
invalidate.

`json_schema.schema` carries **two** field validators, in this order:
1. **the keyword refusal** — walk the schema recursively (dicts and lists) and reject if any mapping
   contains the key `pattern` or `patternProperties`, with a message naming the keyword and pointing at
   the `regex` assertion type as the supported way to assert a pattern. One `# WHY:` line: `jsonschema`
   evaluates those two keywords with **stdlib `re`**, on a schema the prompt owner wrote, and an AST
   walk over our source can never see it.
2. `validator_for(schema, default=Draft202012Validator).check_schema(schema)` — an unusable schema is
   refused at authoring rather than as a run-time explosion.

`max_cost.currency` gets `pattern=r"^[A-Z]{3}$"` (pydantic's own field constraint, not `re` — write the
one-line note, because a reader will reach for `re` there), matching
`ck_eval_run_cost_currency_format` one table over.

**The registry.**

**The three functions that are the module's seam.**

```python
def parse_assertions(payload, *, modality: Modality) -> tuple[BaseModel, ...]
def evaluate(assertions, *, content, latency_ms, cost) -> tuple[AssertionResult, ...]
def resolve_pointer(document, pointer: str) -> tuple[bool, Any]   # RFC 6901, ten lines
```

`parse_assertions` is the authoring gate and is called **before any INSERT**:

1. Refuse a non-list payload and a non-mapping element with a `ValidationError` from the `TypeAdapter`.
2. For each element, read its `type` field **before** validating, and decide the refusal:
   - not a string, or absent → `ValidationError` (an unshaped element is a malformed body);
   - present in `REGISTRY[modality]` → validate it through
     `TypeAdapter(list[TextAssertion])` / `TypeAdapter(list[StructuredAssertion])`;
   - present in the **other** modality's map → raise
     `AssertionSpecRejected(MachineCode.ASSERTION_TYPE_NOT_VALID_FOR_MODALITY, assertion_type=…, ordinal=…)`;
   - present in neither → the same exception with `MachineCode.UNKNOWN_ASSERTION_TYPE`.
   Doing the vocabulary check **before** handing the batch to pydantic is what makes the two codes
   distinguishable at all: pydantic's discriminated union reports one undifferentiated
   `union_tag_invalid` for both cases, and the difference between *"not available for this modality"*
   and *"no such assertion type"* is the entire authoring-UI message.
3. `AssertionSpecRejected(Exception)` — `# noqa: N818` with the same one-line justification
   `HistoryAppendRejected` carries, and the same discipline: **the message names the type and the
   ordinal and never the assertion's value.** An expected value or a pattern can quote whatever the
   author was looking at, and `HistoryAppendRejected`'s rule — *"the value is deliberately not shown,
   because it is the object that failed the allow-list"* — transfers unchanged.

`evaluate` builds one `AssertionContext` and dispatches each spec through the merged type→evaluator
mapping. It **catches the pinned `regex` timeout class and nothing broader**, returning
`AssertionResult(type, ERRORED, MachineCode.ASSERTION_TIMEOUT)`; a `regex` match against content longer
than `MAX_REGEX_INPUT_CHARS` is not attempted at all and returns
`AssertionResult(type, ERRORED, AssertionCode.INPUT_TOO_LONG)`. It **raises nothing** — a run that dies
because one assertion misbehaved is the failure the whole `ERRORED` state exists to prevent.

`max_cost` with `context.cost is None` returns `ERRORED` with `WithheldReason.NOT_PRICED_YET`.

Module docstring, short: what this module owns, the A-046 declaration (**this module handles model
output on every call and logs none of it — it has no logger at all**), and `# T-009 / D-295: regex, not
stdlib re — a pattern is user-authored code in worker`.

**Signatures.**

**Two deviations from `16-CONTEXT`'s signature block, both argued here and neither owed an OQ** — the
CONTEXT is this phase's own artifact, not a locked upstream spec, and ORCHESTRATION §5 governs `docs/`:

1. **The two writers take a `sessionmaker`, not a `session`.** The retry must open a *new* transaction
   (a PostgreSQL transaction that has raised is aborted; every subsequent statement fails with
   `25P02` until rollback), so a function handed someone else's open session cannot implement D-286's
   retry at all. This is exactly 13-02's shape and the reason is 13-02's reason.
2. **`get_suite` takes a `session`**, because it is a plain read that Phase 17's route will compose
   into a request-scoped transaction — `get_revision`'s shape, one module over.

**`create_suite`.** Version 1, and it does **not** retry: two people creating a suite with the same
name on the same prompt is not a race to be smoothed, it is a collision the second author must see, and
a retry would silently produce *version 2 of somebody else's suite* while the author believes they made
a new one. On `IntegrityError` naming `uq_eval_suite_prompt_name_version`, raise `SuiteNameTaken`.
Write that contrast at the exception — it is the one place in the module where *not* retrying is the
decision.

Body order, and the order is the decision:

1. `parse_assertions(case.assertions, modality=output_modality)` for **every** case, **before opening
   the transaction**. A bad type is refused with nothing written, and the ordinal of the offending case
   travels in the exception.
2. `workspace_transaction(sessionmaker, workspace_id)`.
3. Mint the suite id with 16-01's `new_eval_id(SUITE_ID_PREFIX)`.
