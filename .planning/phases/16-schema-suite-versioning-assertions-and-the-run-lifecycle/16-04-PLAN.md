<objective>
Build the run row's two writers and prove, at the engine, that **the run cannot be re-pointed at a
different yardstick and cannot be started by the application** — the two halves of EVAL-04's third
clause that no amount of repository discipline can deliver.

`src/prope/evaluation/runs.py` ships `create_queued_runs` — one `evr_` run per suite id, `role` in
`candidate | baseline`, `started_at` left NULL because `ck_eval_run_queued_has_no_start` says the claim
is what stamps it — and `transition(session, run_id, *, to: RunStatus, …)`, **the only writer of
`eval_run.status` in the project**. The state machine it carries is small and every edge in it is
argued: `queued → running` is refused *in code* and named as `evaluation.claim_next_run`'s, because
`started_at` is absent from the ten-column grant and an application-written `running` row would be a
run with no start time — the exact state Phase 18's sweeper reads as liveness; `running → completed`
writes the counts, the tokens, `finished_at` **and** the `eval_run_completed` history event in one
transaction; `running → refused` is the claim-time gate's terminal write; and `interrupted` is refused
here with Phase 18 named at the insertion point.

`tests/security/test_eval_run_column_grants.py` proves D-284 **against the live engine rather than by
reading the migration**. `prope_app` succeeds on the ten granted columns and is refused on `suite_id`,
`workspace_id`, `prompt_id`, `version_id`, `role`, `started_by`, `started_at` and `id` — each through a
statement whose `SET` list names only that column, **because PostgreSQL checks column-level `UPDATE`
against the `SET` list**, which is why the same test also shows that a statement *reading* `suite_id`
in its `WHERE` and setting `status` succeeds. `suite_id`'s absence is the whole of EVAL-04's third
clause: *"`suite_id` is written onto the run at start and never re-read from the prompt"* is a grant,
and the mutation check restores it, watches the re-pointing statement land, and revokes it again — so
the refusal is demonstrably the engine's. The same file asserts `eval_run` and `case_result` hold no
`DELETE` for `prope_app` (A-137's no-delete-path carried by the grant matrix rather than by the absence
of a `DELETE` statement somebody could add) and that a NULL `cost_amount` with a non-NULL
`cost_currency` — and its converse — is refused by `ck_eval_run_cost_carries_currency`.

**What this plan deliberately leaves open.** It dispatches nothing and prices nothing: a run completed
by `transition` carries pass/fail/error counts and token counts and a **NULL cost**, and that is the
expected end state of this phase, not a bug (D-292). It writes no `eval_run_started` — that rides
inside 16-02's claim transaction — and it composes nothing into `worker`, which is 16-05's. It writes
the executor's *destination* and not the executor: 16-05 calls `transition(to=COMPLETED)` at the end of
a run and `transition(to=REFUSED)` at the modality gate, and 16-06 supplies the counts through the
withholding rules. No HTTP route exists in this phase at all.
</objective>

## Resolutions this plan makes

16-CONTEXT consumes D-280 through D-299 and **the range is closed**, so none of the following mints a
decision id. Each is a gap the CONTEXT left to the plan, resolved here so the executor does not invent
it and the SUMMARY can report it.

**R1 — `transition` returns a `RunTransition` value object; the CONTEXT's `-> None` is widened.**
16-CONTEXT's signature block reads `async def transition(session, run_id, *, to: RunStatus, ...) ->
None`. It is widened here for one reason: **`transition` must not touch a metric, and something has to
carry the numbers out to the point after the commit where a metric may legitimately be recorded.**
`drain.py:340-372` states the rule in as many words — the success metrics are recorded *immediately
after the commit*, outside the `async with`, because a counter is process state and a rollback cannot
reach it. A `transition` that incremented `prope_evaluation_run_total` inside the caller's transaction
would over-count every rolled-back completion, and the rolled-back completion is precisely the event
this phase's atomicity test provokes on purpose. `RunTransition` carries `run_id`, `from_status`,
`to_status`, `role`, `started_at`, `finished_at`; `observe_run_transition(t)` is the one site that
touches the two metrics. The widening is an addition with no behavioural difference for a caller that
ignores it, and 16-CONTEXT is this phase's own document rather than a locked spec — so it is reported
as a resolution in the SUMMARY, not raised as an open question (the precedent is `append()`'s widened
return, which needed `OQ-035` because INT-006 is a locked interface and this is not).

**R2 — the state machine is a mapping from each writable target to its ONE legal predecessor.**
`ALLOWED_FROM: Mapping[RunStatus, RunStatus] = {COMPLETED: RUNNING, REFUSED: RUNNING}`, and a
`REFUSED_TARGETS: Mapping[RunStatus, str]` holding `RUNNING` and `INTERRUPTED` with the sentence each
refusal carries. `queued → refused` is deliberately **not** an edge: PITFALLS §2's restatement of AC-9
says the advisory check at `POST /eval-runs` produces a synchronous error and **only the claim-time
result writes `status=refused`**, and by claim time the row is already `running`. An edge nobody can
reach is an edge nobody tests.

**R3 — the guard is a compare-and-set, not a read-then-write.** The `UPDATE` carries
`AND status = :from_status`, and `rowcount` is what decides. Under `READ COMMITTED` an `UPDATE` that
meets a concurrently-updated row waits for the other transaction, then **re-evaluates its own `WHERE`
against the new row version** — so a sweeper that marked the run `interrupted` between this function's
read and its write makes the predicate fail rather than being silently overwritten. `repricing.py:85-90`
carries this argument for `cost_status`, one module over: *"carrying the predicate into the update's own
`WHERE` makes that row simply not match, instead of being overwritten with a second opinion."*

**R4 — a `refused` transition writes NO history event, and that is the spec rather than an omission.**
The closed vocabulary holds four `eval_*` actions — `eval_suite_updated`, `eval_run_started`,
`eval_run_completed`, `eval_run_interrupted` — and there is no `eval_run_refused`. ADR-0038 makes a
32nd action a migration plus a restart, in another module's schema, decided in an eval phase. The
refusal is recorded by the row (`status='refused'`, `finished_at`) and by
`prope_evaluation_run_total{status=refused}`, which is the detection signal `evaluation.lock.yml`'s
spend-ceiling failure mode names. **Noted in the SUMMARY's ledger** so Phase 17 and Phase 18 do not
each independently discover it and reach for a fifth action.

**R5 — `transition` does not refuse non-zero counts on a `refused` run.** The obvious rule — *a refused
run measured nothing, so its counts must be zero* — is wrong here, and the reason is D-298's named gap:
for a binding nothing has ever observed, the modality gate has no input, the run proceeds, **the first
case's response is classified and a mismatch aborts the run at `status='refused'` having billed exactly
one upstream call**. That run has one `case_result` behind it and its counts must be able to say so. The
absence of the rule is deliberate and is recorded here rather than left to look like an oversight.

**R6 — `create_queued_runs` refuses an empty `suite_ids` and refuses a repeated id.** An empty tuple
returned from a submit is the *"ran cleanly, did nothing, looked healthy"* shape this project has been
bitten by twice; what a `POST /eval-runs` against a prompt with no suites returns is Phase 17's route
decision (A-059 makes an empty *suite* legal, which is a different thing), and it must not be made by
accident in a writer. A repeated suite id in one submit is two runs of one yardstick and a doubled bill,
against the lock's *"a submit produces one run per suite"*.

**R7 — `_read_run` is a module-private helper, and it exists as a seam.** Task 3's interleave test wraps
it to commit a competing status change between the read and the `UPDATE`, which is the only way to open
the window R3's guard exists to close. One line at the definition saying so; the plan carries the rest.

### The state machine

```python
#: Each writable target and its ONE legal predecessor (R2). Phase 18 adds
#: RunStatus.INTERRUPTED: RunStatus.RUNNING here, and deletes its entry from
#: REFUSED_TARGETS below, in the change that ships the sweeper (EVAL-07).
ALLOWED_FROM: Mapping[RunStatus, RunStatus] = MappingProxyType({
    RunStatus.COMPLETED: RunStatus.RUNNING,
    RunStatus.REFUSED:   RunStatus.RUNNING,
})

REFUSED_TARGETS: Mapping[RunStatus, str] = MappingProxyType({
    RunStatus.RUNNING: "evaluation.claim_next_run() is the only writer of 'running': it stamps "
                       "started_at as the function's owner, and started_at is absent from the "
                       "UPDATE grant, so a run this function started would have no start time",

```

`RunStatus.QUEUED` appears in neither mapping, so a transition *to* `queued` falls through to the
generic refusal — there is no path back into the queue and a re-run is a new row (A-054).

Body, in order, and the order is load-bearing:

1. If `to` is in `REFUSED_TARGETS`, raise `InvalidRunTransition` with that entry's sentence. **Before
   any SQL** — the refusal is about the caller's intent, not about the row.
2. If `to` is not in `ALLOWED_FROM`, raise `InvalidRunTransition` naming `to` and the two writable
   targets.
3. `row = await _read_run(session, run_id)`. If `None`, raise `RunNotFound`.
4. If `row.status != ALLOWED_FROM[to]`, raise `InvalidRunTransition` naming the observed status, the

6. If `result.rowcount != 1`: re-read. A row with a different status ⇒ `InvalidRunTransition` naming the
   status the competing writer left; no row ⇒ `RunNotFound`. **This is R3's branch and it is the reason
   step 4 is not sufficient**: between the read and the write, Phase 18's sweeper may commit
   `interrupted` on the very same row.
7. If `to is RunStatus.COMPLETED`, `await append(session, HistoryEventDraft(...))` with:
   - `workspace_id` = the row's, `action = "eval_run_completed"`, `target_type = "eval_run"`,
     `target_id = run_id`, `scope_prompt_id` = the row's `prompt_id`;

     transition in another process, up to a second later, so the actor is not a user; the submitter's id
     is carried because `__post_init__` explicitly permits a system actor **with** an id and dropping it
     would leave an audit row that cannot say whose submit this run serves. This is 16-02's R3 shape,
     which named this plan as the one that should follow it;

     disagree about when the run ended, and the caller reads one clock;

     keys `history.history_action_registry` registers for this action** (16-01's four `detail_keys`

     transaction with it, which is the correct behaviour and is asserted.
   The append comes **after** the `UPDATE` reported `rowcount == 1`, so a transition that changed
   nothing writes no event. One `# WHY:` line, twelve words.
8. Return `RunTransition(...)`, reading `role` and `started_at` from the row.
