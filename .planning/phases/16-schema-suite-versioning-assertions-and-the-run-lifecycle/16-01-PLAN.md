> ## ⚠ COMMENT DENSITY — ORCHESTRATION §12 IS IN FORCE AND OUTRANKS THIS FILE
>
> This plan is written to §12 and carries its arguments **in the plan**, where they cost nothing at
> runtime. The source files it asks for get **pointers, not arguments**: `# ADR-00NN / D-NNN: <=12
> words`, a one-line `# WHY:` where the code looks wrong but is right, a short docstring on a public
> seam, and a note at an assertion that would otherwise look vacuous. **That is the whole budget.**
> Comments and docstrings together stay well under a third of any file, and the migration under 25% —
> a migration is mostly DDL and DDL is self-describing. Nowhere below does "say it at the constraint"
> mean a paragraph; it means one line, or the plan's own prose is the record instead.

<objective>
Ship the `evaluation` schema in **one applied revision**, and prove at the engine — not in Python — the
three properties this module's whole claim rests on: **the yardstick cannot be rewritten, the run that
used it cannot be re-pointed at another one, and the row a worker claims cannot be claimed twice.**

Suite immutability and the yardstick pin are **grants, not conventions**. `prope_app` holds `SELECT,
INSERT` on `eval_suite` and `eval_case` and holds neither `UPDATE` nor `DELETE`, so *"editing a suite
creates its next version"* is a statement about what the role can physically do (D-283). `eval_run`'s
`UPDATE` is a column list of exactly ten names and `suite_id` is not among them, so the failure-mode
row's mitigation — *"`suite_id` is written onto the run at start and never re-read from the prompt"* —
is checked by PostgreSQL against the statement's `SET` list (D-284). ADR-0025's sentence transplanted:
a log the application can rewrite is a Sheet with better indexing, and **a yardstick the application
can rewrite is worse, because a comparison measured with it still renders, authoritatively, with the
wrong number.**

This plan also lands **the fourth and last sanctioned `SECURITY DEFINER` function**, and empties
`NOT_YET_BUILT` in `tests/security/test_security_definer_set_is_exactly_sanctioned.py` in the same
change (D-281). Plan 07-06 wrote that file with the comment *"Phase 16 deletes one line from
`NOT_YET_BUILT`, in the change that creates the function, or inherits a red test it did not write."*
Three edits go with it — the tuple empties, `claim_next_run`'s `pg_get_function_result` joins the
per-name pin map, and the docstring stops describing a four-minus-one set. **`OQ-045` is thereby

Four ROADMAP success criteria are graded on this phase and **this plan closes none of them** — it makes

## D-280 — the whole `evaluation` guarantee stack in ONE revision

**Chosen.** Four tables, four tenant policies, four grant blocks including a ten-column `UPDATE` list,
every named `CHECK`, three intra-schema foreign keys, four indexes, one deferred constraint trigger,
one `SECURITY DEFINER` function and four cross-schema data `UPDATE`s — a single Alembic revision.

**Rejected: one revision per kind** (tables / RLS / grants / function), which RESEARCH Pattern 10
recommends in general and which `alembic/ddl.py`'s own docstring already declines. A chain of five
revisions has four intermediate states, and in three of them `eval_case.input_messages` and
`case_result.output_content` — which hold the same content class as a prompt body (T-011, A-046) —
exist and are readable across tenants. A deploy interrupted between two of them leaves one of those
states running.

**Rejected: a second revision for the `SECURITY DEFINER` function**, on the grounds that a
privilege-escalating object deserves its own reviewable diff. It is the opposite: the function and the
policies it escapes must land together, or there is a deploy state in which the claim loop's target
table has a policy and the escape does not exist — and the loop then returns zero rows **while looking
healthy**, which is the failure this phase's `<risks>` names three separate ways of reaching.

**Reversibility: one-way.** A landed revision is never edited; a change is a new revision.

## D-287 — one `LANGUAGE sql VOLATILE` data-modifying CTE, ordered by `id`

**Chosen.** `evaluation.claim_next_run(p_max_concurrent_runs integer)` returns
`TABLE (run_id text, workspace_id text, prompt_id text, version_id text, suite_id text)` — ADR-0049's
five identifiers, no prompt text, no case input, no output — and is emitted through 07-01's
`security_definer_function` so the empty `search_path`, the `REVOKE … FROM PUBLIC` and the
`GRANT EXECUTE … TO prope_app` cannot be assembled a line short.

Three sub-decisions, each with its rejection:

- **`LANGUAGE sql`, not `plpgsql`.** A SQL body cannot contain control flow, so it cannot contain a
  decision — ADR-0042's property, and the one that keeps these four objects *lookups* rather than
  *authorities*. The admission predicate is a `WHERE` clause, not an `if`.
- **`p_max_concurrent_runs` is a parameter, not a literal.** A-063 calls the bound *configurable*;
  baking `2` into the body makes a configuration change a migration. The value lives in `domain.py`
  beside the other tunables and is passed at every call.
- **`ORDER BY r.id`, not `ORDER BY r.created_at`.** **`eval_run` has no `created_at` column** — the
  lock's field list runs `… suite_id, role, status, started_at, finished_at, …` — while ADR-0049's SQL
  block orders by one. `id` is an `evr_`-prefixed ULID (ADR-0003, A-045) and ULIDs sort
  lexicographically by creation time, so FIFO is available with no column and no deviation from the
  declared field list. **Rejected: adding `created_at`**, which is the undeclared-column deviation
  13-01 paid for with OQ-070 and is not worth paying twice for an ordering the id already carries. The
  residual difference — two runs created in the same millisecond may order by ULID randomness rather
  than by microsecond timestamp — is escalated in the SUMMARY rather than given an OQ id, because the
  observable end state (FIFO within a workspace's submit) is the same.

**Reversibility: one-way.** Four modules' worth of tests pin the return shape, and the set of
`SECURITY DEFINER` objects is asserted by equality.

## D-285 — `case_count` is asserted by a DEFERRED constraint trigger, and the trigger is `SECURITY INVOKER`

**Chosen.** `case_count` is written once, in the transaction that creates the version. The column is
declared by the lock and cannot be dropped; it is a denormalised count on a table whose rows are
immutable, so **the only way it can lie is a later `INSERT` into `eval_case`** — which `prope_app`
**can** do, because D-283 grants `INSERT`. The guard is a `CREATE CONSTRAINT TRIGGER … AFTER INSERT ON
evaluation.eval_case DEFERRABLE INITIALLY DEFERRED FOR EACH ROW`, comparing `eval_suite.case_count`
against `count(*)`.

**`DEFERRABLE INITIALLY DEFERRED` is the whole point and it is why this is a `CONSTRAINT TRIGGER` and
not a plain `TRIGGER`.** The legitimate writer inserts the suite row and then N case rows in one
transaction; a non-deferred trigger fires after the first case and refuses a correct transaction. A
plain `CREATE TRIGGER` cannot be deferred at all — the syntax is accepted only on
`CREATE CONSTRAINT TRIGGER`. Getting that wrong produces a migration that applies cleanly and makes
every legitimate suite insert fail, which is why Task 4 asserts the refusal arrives **at `COMMIT`** and
not at the statement.

**`SECURITY INVOKER`, explicitly**, in plan 07-04's shape and for 07-04's reason: a `SECURITY DEFINER`
trigger function is a fifth privilege-escalating object and the answer is never a fifth. Its reads run
under the invoker's RLS, which is correct — it counts the tenant's own rows, and an insert with no
tenant set never reaches the trigger because the policy's `WITH CHECK` refuses it first.

**Rejected: dropping the column and computing the count on read.** It is a declared field; removing it
is the silent narrowing ORCHESTRATION §5 refuses, and `GET /eval-suites` reads it per row.
**Rejected: a maintenance trigger that recomputes `case_count`.** That makes the count always true and
therefore never falsifiable, and the failure it guards — *"18 of 20 passed"* with nothing behind it,
A-137's own sentence — is exactly the kind that must be loud.
**No `CHECK (case_count BETWEEN 10 AND 20)`.** `scope.in_scope` says *"each 10-20 cases"* and **A-059
says a prompt may have an empty eval suite**; a range constraint would make A-059 unrepresentable.
`CHECK (case_count >= 0)` is the whole of what is true.

**Reversibility: cheap** — a trigger body is a new revision.

## D-299 — ten metrics at import, and `LOGGABLE_FIELDS` gains identifiers only

**Chosen.** All ten declared metrics are defined at import in
`src/prope/evaluation/observability.py`, even though seven of them have no increment site until plans
16-04 through 16-06 and one (`prope_evaluation_run_interrupted_total`) has none until Phase 18. The
rule is D-40 / D-164 / D-228 unchanged: **a metric that first appears when it goes non-zero has no
baseline, and `REGISTRY.get_sample_value` returns `None` — not `0.0` — for a metric nothing has
touched.**

`prope_evaluation_run_queue_depth` is the sharp one and it repeats a trap this project has been bitten
by twice. A `prope_app` `SELECT count(*) FROM evaluation.eval_run WHERE status = 'queued'` issued with
no tenant set returns **zero rows**, so the gauge would read 0 forever and `EvalQueueBacklog` would be
an alert that never fires — `ObservedWorkspaces`' *"runs cleanly, deletes nothing, and looks healthy"*
wearing a different hat. **This plan defines the gauge and wires nothing to it**; plan 16-02 owns the
enumerator pass and the test that asserts it is non-zero for a queued run in a workspace the reading
transaction did not set as its tenant. Saying which half is here is the point of saying it at all.

**`LOGGABLE_FIELDS` gains ten names and refuses an eleventh.** Added, in Phase 4's adopted one-flat-list
shape: `prompt_id`, `version_id`, `suite_id`, `suite_version`, `run_id`, `case_id`, `outcome`,
`error_code`, `attempt_count`, `duration_ms`. (`workspace_id` and `actor_id` are already in the list
and are not re-added.) **`suite_name` is refused.** It is author-written display text that may be
non-English (OQ-010) and may quote whatever the author was looking at, and the allow-list's stated
discipline is *"every entry is an identifier or a closed-vocabulary token"*. The lock's `log_fields`
block names `suite_name` in as many words, so this is a deviation with an observable behavioural
difference and is **raised as `OQ-089`**; `suite_id` resolves to the name through the row it is on.

**Reversibility: cheap on the metrics, costly on `LOGGABLE_FIELDS`** — seven modules inherit the shape.

## Resolved from the CONTEXT's "Claude's Discretion", because a plan that leaves these open makes the executor guess

- **`prope_report` keeps `SELECT` on all four tables** (`grant_table`'s `report_select` default). The
  argument, made rather than defaulted: `registry.revision` already grants `prope_report` every prompt
  body in Prope (13-01 made that call explicitly), so excluding `case_result.output_content` buys
  nothing and creates an inconsistency somebody will later "fix" in the wrong direction. The single
  exclusion in this project is `provider.credential` (D-166) — a decryptable secret, not content — and
  ADR-0036's nightly dump runs as the host superuser regardless. **This is a reportable adoption**
  (one-way once a report user exists) and goes in the SUMMARY's `ORCHESTRATION-DECISIONS` block.
- **`assertion_results` is a jsonb ARRAY of per-assertion records**, not a summary object, guarded by
  `ck_case_result_assertion_results_is_array`. `GET /eval-runs/{run_id}/cases` (Phase 17) is the only
  reader and it renders per assertion; a summary would make *"which assertion failed"* unanswerable
  from stored data. The record shape (`type`, `passed`, `code`) is 16-05's to write and is not
  constrained by the engine beyond `array`.
- **`case_result.error_code` is a closed superset**: INT-015's seven `DispatchError` classes —
  `timeout`, `rate_limited`, `credential_rejected`, `upstream_5xx`, `bad_request`, `content_filtered`,
  `transport` — plus `assertion_timeout`. Eight values, a named `CHECK`, mirrored by `ErrorCode` in
  `domain.py`. It is a metric label, so it must be closed either way; the superset is required because
  a regex timeout is an `error` outcome (A-057) with no `DispatchError` behind it.
- **The `evs_` / `evc_` / `evr_` / `evcr_` id-assembly site is `domain.py`**, in
  `property_history.domain.HistoryEventDraft`'s exact shape: the prefix as a module constant and
  `field(default_factory=lambda: f"{PREFIX}{ULID()}")` on the frozen dataclass that carries the id,
  with a `__post_init__` prefix assertion. This plan ships the constants, the one-line `new_eval_id`
  helper and the `ClaimedRun` value object; the dataclasses for suites, runs and results belong to the
  plans that construct them and extend this same module.
- **`eval_run.role` gets NO partial unique index.** The pairing rule tolerates duplicate baselines
  (D-293's `get_released_revision` decides which one is current), and a unique index over `(version_id,
  suite_id) WHERE status = 'queued' AND role = 'baseline'` would make a legitimate re-run of a baseline
  fail with a constraint violation the API has no shape for. A submit storm producing two baseline runs
  costs one duplicated run and is visible in `prope_evaluation_baseline_reused_total{recomputed}`.
- **`eval_suite.name` is capped at 200 characters, in characters and not bytes.** No authority declares
  a cap; 200 is this plan's choice, recorded rather than assumed, and matched to A-050's
  `change_summary` figure because both are one-line author-written display text. Characters and not
  bytes for ADR-0053's reason: a byte cap is roughly a one-third cap in Vietnamese, the only language
  the MVP ships.
- **Test file placement follows the repository, not the lock's `test_ref` strings.** Several of those
  name `tests/integration/test_*` with no `.py` suffix and one names `tests/chaos/…`, a directory that
  does not exist and is Phase 18's. This plan writes `.py` files in the existing `tests/security/`,
  `tests/integration/` and `tests/evaluation/` trees and creates no new test directory.

#### `evaluation.eval_suite`

```

workspace_id     text        NOT NULL
prompt_id        text        NOT NULL   -- a VALUE, not a reference
name             text        NOT NULL
```

- `pk_eval_suite PRIMARY KEY (id)`

  and **the race arbiter** for D-286's retry, which plan 16-03 owns. It deliberately **does not gain

  permitting the same triple in two workspaces.
- `uq_eval_suite_workspace_id UNIQUE (workspace_id, id)` — **trivially unique, and that is the point.**

- `ck_eval_case_input_variables_is_object CHECK (jsonb_typeof(input_variables) = 'object')`

#### The deferred `case_count` trigger

```sql
CREATE FUNCTION evaluation.assert_case_count_matches() RETURNS trigger
LANGUAGE plpgsql SECURITY INVOKER SET search_path = '' AS $$
DECLARE
    declared integer;
    actual   integer;
BEGIN
    SELECT s.case_count INTO declared
    FROM   evaluation.eval_suite s
    WHERE  s.workspace_id = NEW.workspace_id AND s.id = NEW.suite_id;

    IF NOT FOUND THEN
        RETURN NULL;
    END IF;

    SELECT count(*) INTO actual
    FROM   evaluation.eval_case c
    WHERE  c.workspace_id = NEW.workspace_id AND c.suite_id = NEW.suite_id;

    IF actual <> declared THEN
        RAISE EXCEPTION
            'eval_suite_case_count_matches: suite % declares % cases and holds %',
            NEW.suite_id, declared, actual
            USING ERRCODE = '23514';
    END IF;
    RETURN NULL;
END;
$$;

CREATE CONSTRAINT TRIGGER eval_suite_case_count_matches
    AFTER INSERT ON evaluation.eval_case
    DEFERRABLE INITIALLY DEFERRED
    FOR EACH ROW EXECUTE FUNCTION evaluation.assert_case_count_matches();
```

Three one-line notes at the code and no more: **`CONSTRAINT TRIGGER`, because a plain `CREATE TRIGGER`
cannot be deferred**; **`SECURITY INVOKER` explicitly, because the sanctioned definer set is four and a
fifth is never the answer**; and the `NOT FOUND` early return, which is not laxity — an insert whose
suite is invisible has already been refused by the policy's `WITH CHECK`, so reaching here means the
owner is writing and there is nothing to compare against. `SET search_path = ''` costs nothing and
removes a shadowing vector, which is why every object above is schema-qualified.

#### The claim function

Body constant, then one `security_definer_function` call **inside** `assume_migrate_role()` so
`prope_migrate` owns it (07-06's ownership test depends on that):

```sql
WITH candidate AS (
    SELECT r.id
    FROM   evaluation.eval_run r
    WHERE  r.status = 'queued'
      AND  (SELECT count(*) FROM evaluation.eval_run r2
             WHERE r2.workspace_id = r.workspace_id AND r2.status = 'running')
           < p_max_concurrent_runs
    ORDER  BY r.id
    FOR UPDATE SKIP LOCKED
    LIMIT  1
)
UPDATE evaluation.eval_run AS u
   SET status = 'running', started_at = now()
  FROM candidate c
 WHERE u.id = c.id
RETURNING u.id, u.workspace_id, u.prompt_id, u.version_id, u.suite_id
```

Four things that will bite if they are skipped:

1. **Every object is schema-qualified** because `search_path` is empty; `pg_catalog` stays implicitly
   searched, so `now()` and `count(*)` resolve.
2. **Every body column is table-qualified** (`r.`, `r2.`, `u.`, `c.`), because the `RETURNS TABLE`
   output names are OUT parameters visible inside the body and collide with column names of the same
   spelling. **If the engine still reports ambiguity**, rename the outputs to `o_run_id`, `o_workspace_id`,
   `o_prompt_id`, `o_version_id`, `o_suite_id`, pin the new signature in the set test, and record the
   rename in the SUMMARY — **do not drop the qualification** to make it compile.
3. `VOLATILE`, not the helper's `STABLE` default. A `STABLE` data-modifying function is a lie the
   planner is entitled to act on.
4. `FOR UPDATE SKIP LOCKED` inside the CTE and the `UPDATE` outside it is the canonical queue shape and
   is what makes AC-13 true. `SKIP LOCKED` guarantees two loops never claim the *same* row; it does
   **not** serialise two loops claiming *different* rows of the same workspace, and ADR-0049's
   Consequences say otherwise. One line at the constant pointing at `OQ-090`, which **plan 16-02
   creates** — this plan does not create it, and if it is absent when this plan finishes that is
   expected.

### `tests/integration/test_claim_next_run.py` — owed AC-13, the predicate, the ordering, the trigger

`test_two_concurrent_claims_leave_exactly_one_winner`
One queued run in `WORKSPACE_A`. Open **two** `prope_app` connections, A and B, each with its own
explicit transaction. In A, call `claim_next_run(2)` and assert one row. **Without committing A**, in B

`status == 'running'`, `started_at IS NOT NULL`, and that exactly one row in the table is `running`.
**No sleeps and no timing**: the ordering is enforced by holding A's transaction open, which is the only
form of this test that cannot pass by luck. `pytest-timeout` is not installed, so a test that hangs
hangs the suite — keep both transactions inside `async with` blocks that close on failure.

`test_the_admission_predicate_honours_its_parameter`

its bound and B is not — which proves the predicate is per-workspace and is `<`, not `<=`. Then mark one

green from the first call cannot be *"there was nothing to claim"*.
