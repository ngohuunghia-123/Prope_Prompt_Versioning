<objective>
This plan makes a claimed run **execute**. It composes the fourth resident into `worker`, runs the
claim-time admission gate, turns a revision plus a case into an upstream request, dispatches it,
classifies what came back, and writes one `case_result` row per case before completing the run.

**It closes ROADMAP success criterion 4 (EVAL-09 / restated AC-9): a run whose declared suite modality
disagrees with the last observed shape of its target is written `status='refused'` before any case is
dispatched, naming both shapes, with no upstream call billed.** The restated form is the operative
one — `.planning/research/PITFALLS.md` §2 says the modality check runs twice, advisory at
`POST /eval-runs` (Phase 17) and authoritative at claim time, and **only the claim-time result writes
`status='refused'`**. That is what this plan asserts.

It deliberately leaves three things open. **Money**: no `price_usage`, no `check_spend_ceiling`, no
`get_run_totals` — a run here completes with `cost_amount`, `cost_currency` and `priced_at` all NULL,
which is D-292's stated cost and is asserted as the expected end state rather than discovered as a bug.
Phase 17 closes it and the admission tuple already has the line it inserts. **The comparison**: the
cost delta, the baseline pairing and the cross-version refusal are 16-06's, one wave later; this plan
ships the classifier that decides `error` versus `fail` and stops there. **The sweeper**: nothing here
writes `interrupted`, and a run whose executor dies stays `running` with its completed case results
readable — which is precisely the state Phase 18's EVAL-07 sweeper is written against, and it is why
each case commits its own row rather than the run committing twenty at the end.

One consequence is worth meeting here rather than in a security review. **AC-9 asks for a refusal that
"names both shapes", and `eval_run` has no column that can hold a reason.** Its field list is fixed by
the lock and carries no `refusal_code`, the four registered `eval_*` history actions carry
`detail_keys` of exactly `{version_id, suite_version}`, and this plan owns no migration. So the naming
lands in the two places that can hold it: `prope_evaluation_modality_mismatch_total{declared, observed}`
— whose entire label set exists for this, bounded at four series — and the `AdmissionRefusal` value
object that Phase 17's advisory pre-check renders synchronously. **A run refused at claim time carries
its status durably and its reason only in the metric and the log line.** That is a gap, it is named
here, it is asserted in the form that exists, and it is escalated as owed-and-unallocated in the
SUMMARY (this phase's OQ range is fully consumed and another phase's is never borrowed).

## R1 — `jobs.py` is a factory module, and the loop is one claim per tick, awaited

`build_claim_loop_job(...)` returns a **zero-argument coroutine factory** — 02-03's contract, restated
in `src/prope/supervisor.py`'s module docstring as *"a job here is a name, a zero-argument coroutine
factory, and nothing else"*. The factory body is `await interval_job(body, CLAIM_LOOP_INTERVAL_SECONDS,
stopping)`, and `interval_job` **runs the body first and waits after** (`supervisor.py:240-244`), which
is the property D-291 names: a worker starting after an outage drains the queue on its first pass
rather than one second later.

The body is `claim_and_execute(...)`: one `claim_one()`, and if it returned a run, one `execute_run()`
**awaited to completion before the tick returns**. That is D-289's adopted composition — *"exactly one
claim loop per process, awaited serially (one claim per tick, the run started before the next tick
claims), and one `worker` replica"* — under which `max_concurrent_runs` is exact.

**The honest consequence, stated rather than found later.** A serial loop never has two runs of the
same workspace `running` at once, so `MAX_CONCURRENT_RUNS = 2` is an upper bound this composition never
reaches. The bound is real and is asserted independently by 16-02's `claim_one` test (one running run,
a bound of 1, the second call returns `None`); it becomes load-bearing when a second replica arrives
(A-138). Throughput is therefore one run per `run duration + 1 s`, which at the lock's 20-case/120-second
target is the pilot's shape and not a scaling design. **Rejected: draining the queue inside one tick**
(loop until `claim_one` returns `None`) — it makes the interval meaningless and turns a slow provider
into an unbounded tick. **Rejected: firing `execute_run` as a background task** — it breaks D-289's
serialisation, and the exception would land on a task nobody awaits.

## R2 — four jobs, or five, and the executor decides from what is on disk

The objective for this plan says the three-jobs assertion becomes **four**. Plan 16-02 — wave 2, so it
lands before this one — says in its own `files_modified` comment that its `queue_depth.py` and
`claim.py` *"are composed as two different supervised jobs in 16-05"*. Both cannot be true, and the
resolution is not a preference:

**If `src/prope/evaluation/queue_depth.py` exists on disk with `observe_queue_depth`, compose it as a
second job and the count is five.** Leaving it uncomposed ships D-299's exact failure — a gauge nothing
ever sets, `REGISTRY.get_sample_value` answering `None` forever, and `EvalQueueBacklog` as a rule that
can never fire. That is `ObservedWorkspaces`' *"runs cleanly, deletes nothing, and looks healthy"*
wearing a different hat, and this phase's own `<risks>` calls it the single most likely silent defect.

**If it does not exist**, compose only the claim loop, the count is four, and the SUMMARY reports the
gauge as unwired with `queue_depth.py`'s absence as the reason. Either way the test's **name carries the
number** and the SUMMARY says which branch was taken and why.

The two intervals differ and the difference is argued: the claim loop ticks at **1.0 s** (A-054, D-291),
the depth pass at **15.0 s** — `DEPTH_GAUGE_INTERVAL_SECONDS`' matched-to-the-scrape reasoning
(`worker.py:143-166`), and because the depth pass is one indexed read **per workspace** and running it
every second is N transactions a second forever for a series Prometheus samples every fifteen.

## R3 — `dispatch` and `get_revision` arrive as parameters, bound at the composition root

`execute_run` takes both as keyword arguments; `worker.py` is the one file that imports the real ones.
This is D-13's explicit central composition and it buys three things: `prope.evaluation` acquires no
import edge to `prope.provider_access` or `prope.prompt_registry`, so the "importing this package pulls
in no FastAPI" property (14-05's rule, restated in 16-04's acceptance criteria) survives; the seam is
injectable, which is what makes SC4's *"no upstream call is billed"* assertable at all; and INT-015's
*"same function, two processes"* (A-142 §1) stays literally true, because `worker` calls the identical
`dispatch` the gateway will call in `app`.

**Rejected: importing the real `dispatch` as `jobs.py`'s default.** It puts a module-load-time edge
from `evaluation` to two other modules inside a package `worker` imports, and the first time one of them
grows a transitive `fastapi` import the failure is an import error in a container, not a test.

## R4 — the executor's per-run bound is an `asyncio.Semaphore`, resolved from 16-CONTEXT's discretion list

A-054 fixes the number at **5**; 16-CONTEXT leaves the shape open and notes it interacts with
ADR-0046's `batch_concurrency = 8` semaphore held in the same process by provider-access. Chosen: one
`asyncio.Semaphore(concurrency)` acquired around the dispatch call, with every case's coroutine created
up front and gathered.

**Because a semaphore composes with another semaphore by minimum, and a queue does not.** Two nested
bounded queues make effective parallelism a function of queue depths and hand-off timing rather than of
the two numbers anyone wrote down; two nested semaphores make it `min(5, 8)` per run and 8 across runs,
which is exactly what owed AC-10's restatement asks to be asserted independently in Phase 18.
**Rejected: `asyncio.TaskGroup` with a bounded queue** — Trap 1 in `supervisor.py`'s docstring is
decisive: the first child exception cancels every sibling, which here means one case's defect discarding
nineteen results the workspace already paid for.

## R5 — the classifier maps TEN upstream classes onto EIGHT stored codes, and its totality is a test

16-CONTEXT's discretion list asks whether `case_result.error_code`'s vocabulary is provider-access's
classes verbatim or a superset with `assertion_timeout`. Resolved: **`domain.ErrorCode`'s eight
(16-01's) is the stored and labelled vocabulary**, and `results.DISPATCH_ERROR_CODES` is a total
mapping from `provider_access.failures.ErrorClass` onto it.

The mismatch is real and is not this plan's to fix: INT-015 registers **seven** class names, ADR-0017
and plan 10-02 ship **ten** with three different spellings (`OQ-055` already records the divergence),
and `ErrorCode` carries INT-015's seven plus `assertion_timeout`. So the mapping is 10 → 8 and every
row is a judgement:

| `ErrorClass` (provider-access) | `ErrorCode` (stored) | why |
|---|---|---|
| `credential_rejected` | `credential_rejected` | same fact, same spelling |
| `rate_limited` | `rate_limited` | same |
| `timeout` | `timeout` | same |
| `content_filtered` | `content_filtered` | same |
| `invalid_request` | `bad_request` | INT-015's spelling of the same fact (D-167 / `OQ-055`) |
| `upstream_unavailable` | `upstream_5xx` | INT-015's spelling. Plan 10-02 renamed it because a connection reset is not a status code; the stored vocabulary kept the old name |

`ErrorCode.TRANSPORT` therefore has **no producer**, because provider-access folded transport failures
into `upstream_unavailable`. Record that at the mapping in one line rather than deleting the member —
plan 10-02 takes the same posture for its own two producerless classes.

The mapping is `MappingProxyType` and read through `.get(cls, ErrorCode.UPSTREAM_5XX)`, so an eleventh
upstream class is a wrong-but-survivable label rather than a `KeyError` on a run somebody paid for —
**and `tests/unit/test_dispatch_outcome_classifier.py` iterates `ErrorClass` and asserts every member is
a key**, so the default is never taken in a green tree.

## R6 — a per-case coroutine raises nothing, and each case commits its own row

Every `run_case` returns a `CaseRecord` and raises nothing: a dispatch failure is a value (INT-015 —
`DispatchError` is returned, never raised), a composition refusal is caught by type, and an assertion
that misbehaves is 16-03's `evaluate`, which *"raises nothing"* by construction. A genuine programming
error — the one case `dispatch` is documented to raise for — is caught by class at the case boundary and
recorded as `outcome='error'`, `error_code='upstream_5xx'`, because INT-015's own failure table says a
genuine raise is a **run error** for evaluation and losing nineteen paid results to it is worse.

**Each case writes its `case_result` in its own `workspace_transaction`.** A single transaction holding
twenty rows would be open across twenty upstream calls — a 120-second transaction pinning a connection
and holding a snapshot, which is exactly what ADR-0049 refused for the claim. It is also what makes
AC-7's *"its completed case results remain readable"* true for a run whose worker dies, which Phase 18
depends on and does not implement.

`uq_case_result_run_case UNIQUE (run_id, case_id)` is the engine backstop for *"no case is dispatched
twice"*. **No code path in this phase can reach it** — a `running` run is not re-claimable — and the
plan says so rather than writing a handler for a branch it cannot test.

## R7 — the composer is duplicated on purpose, and the duplication is bounded rather than closed

A-027 says the eval runner uses *the same resolution and dispatch semantics* as the gateway. `gateway`
is a **forbidden dependency** of `evaluation`, and M6 and M7 are both wave 4, so no shared module can be
planned into either. Two implementations of variable substitution and the system-prompt rule will exist.

The failure mode is the worst one this module has: **the eval measures something production does not
run, silently, and the reviewer's evidence is about a different request.** The mitigation is not a
promise. `composition.py` names ADR-0011, GATE-07 and GATE-08 in its docstring as the contract it must
match, and `tests/unit/test_eval_composition.py` is a **table** — missing variable, literal placeholder,
caller-supplied system message, unused variable, braces in the conversation — that Phase 19 must mirror
row for row rather than re-derive. The SUMMARY carries the `deferred-items.md` entry addressed to the
M7 planners under `## Ledger entries owed`; **the executor does not write that file** (ORCHESTRATION §7).

This is bounded, not closed, and the plan says so.

## R8 — `assertion_results` is a list of per-assertion records, not a summary

16-CONTEXT leaves the column's shape open and names `GET /eval-runs/{id}/cases` (Phase 17) as its only
reader. Chosen: a JSON array of `{"type": …, "outcome": …, "code": … | null}`, one element per assertion
in the case's declared order. **Rejected: a summary.** A-137's own sentence about this module's failure
shape is *"18 of 20 passed"* with nothing behind it; a per-case summary reproduces that one level down —
the reviewer sees the case failed and cannot see which assertion decided it, which is the single fact
that tells a prompt owner what to change.

## R9 — a run whose revision or suite cannot be read RAISES, and the run is left for Phase 18

INT-011's failure semantics say `get_revision` raises and *"evaluation treats it as a run error, never a
case failure"*. There is no `error` run status — the `CHECK` holds five values and none of them is one —
and there is no column to record a reason in (see the objective). So: a missing suite is a defect
(`fk_eval_run_suite` guarantees it exists) and a missing revision is unreachable through Phase 17's
route (it validates `version_id` before writing the queued row) and forbidden by A-049 afterwards
(revisions are never deleted). Both raise. The supervisor logs `supervisor.job_crashed` with the job
name and the exception **class** and restarts the loop after its backoff; the run stays `running` and is
reaped as `interrupted` by Phase 18's sweeper after five minutes.

**This does not loop**, and that is the property worth checking: the run is already `running`, so the
next tick's `claim_next_run()` cannot see it. **Rejected: refusing the run** — it needs a machine code
the schema cannot store and would make an unreachable branch the place a reader learns the vocabulary
from.

## R10 — exactly two log lines, and neither can carry content

`evaluation.run_refused` (`run_id`, `reason`) and `evaluation.run_completed` (`run_id`, `duration_ms`).
Every keyword is a `LOGGABLE_FIELDS` member after 16-01's edit; `reason` carries a `MachineCode` value,
which is a closed set fixed in source, the same discipline `supervisor.py` uses for its own `reason`.

**No per-case log line.** Twenty lines per run, every run, with `case_id` and `outcome` on each, is
noise in front of the one thing an operator acts on, and `case_result` is the durable record. **Nothing
in these five modules logs `output_content`, an `input_message`, a variable value or an assertion
value** — T-011 puts all four in the same content class as a prompt body, and `LOGGABLE_FIELDS` has no
name that could hold one.

### `src/prope/evaluation/modality.py`

```python
def classify_modality(content: str) -> Modality
LAST_OBSERVED_OUTPUT: sqlalchemy.TextClause
async def observed_modality(session: AsyncSession, version_id: str) -> Modality | None
def observe_modality_mismatch(declared: Modality, observed: Modality) -> None
```

`classify_modality` is **pure and total** — it never raises, because its caller is deciding whether to
spend money and an exception there is a run that dies for a reason nobody can act on. The rule, in
order, and the order is the specification:

1. `stripped = content.strip()`. Empty ⇒ `Modality.TEXT`. (An empty response is not a structure.)
2. If `stripped` starts with `{` or `[`, try `json.loads`. Success ⇒ `Modality.STRUCTURED`. Failure ⇒
   fall through to text — a message that begins with a brace and is not JSON is prose.
3. If `stripped` contains no whitespace and starts with `https://` or `http://` ⇒ `Modality.STRUCTURED`
   (A-061's *asset reference*). The no-whitespace test is what keeps *"see https://example.com for
   details"* text; write the one-line `# WHY:` there, because a reader will reach for `in`.
4. Otherwise `Modality.TEXT`.

**A bare JSON scalar is TEXT, deliberately.** `json.loads("4")`, `json.loads("true")` and
`json.loads('"hi"')` all succeed, and a model that answered `4` produced prose that happens to parse.
Step 2's brace test is what excludes them, and the test table asserts all three.

**No `re`, no `regex`, no URL parsing library.** `str.startswith` and `str.split` are the whole of it.

`LAST_OBSERVED_OUTPUT` — one `text()` constant, one plain string literal, every value bound:

```sql
SELECT cr.output_content
FROM   evaluation.case_result cr
JOIN   evaluation.eval_run r
  ON   r.workspace_id = cr.workspace_id AND r.id = cr.run_id
WHERE  r.version_id = :version_id
  AND  r.status = 'completed'
  AND  cr.output_content IS NOT NULL
ORDER  BY cr.created_at DESC, cr.id DESC
LIMIT  1
```

Four things about it are decisions rather than defaults. `r.status = 'completed'` is a **literal**, not
a bound parameter: it is a fixed member of a closed vocabulary the schema's own `CHECK` enumerates, and
binding it would suggest the query could be asked about another status — `queue_depth.py`'s stated rule,
one module over. `output_content IS NOT NULL` excludes errored cases, which have none and would
otherwise classify as `TEXT` forever. The join is on `(workspace_id, run_id)`, matching
`fk_case_result_run`'s composite shape. And the tie-break on `cr.id DESC` matters because `evcr_` is a
ULID and `created_at` can repeat inside one run: without it, "the most recent" is whatever the planner
returned.

**No workspace predicate is written out here**, and that is the one place in this module where the
policy is the whole enforcement rather than a backstop — the session is already tenanted by
`execute_run`'s `workspace_transaction`, and `version_id` is a value that may legitimately name a
revision the caller cannot see. Say so in one line.

`observed_modality` executes it, returns `None` when there is no row, and otherwise
`classify_modality(row)`. **It stores nothing** (A-047, D-298) and its two-line docstring says that and
the one constraint a caller must respect: the session must already be tenanted.

`observe_modality_mismatch` is the **one** increment site for
`prope_evaluation_modality_mismatch_total`, labelled `declared=str(declared), observed=str(observed)`.
Synchronous, no I/O; the caller calls it **after** the refusal transaction has committed —
`observe_run_transition`'s rule (16-04), for its reason: a rolled-back refusal must count nothing.

### `src/prope/evaluation/composition.py`

```python
SYSTEM_ROLE = "system"
PLACEHOLDER = regex.compile(r"\{\{\s*([A-Za-z_][A-Za-z0-9_]*)\s*\}\}")

class CompositionRefused(Exception)          # noqa: N818 — a refusal a caller catches
class SystemMessageRefused(CompositionRefused)
class MissingVariable(CompositionRefused)
class UnsubstitutedPlaceholder(CompositionRefused)

def substitute(body: str, variables: Mapping[str, Any]) -> str
def compose_messages(body, variables, case_messages) -> tuple[Mapping[str, str], ...]
```

**`regex`, not `re`** — 16-03's AST gate walks this package and D-295 bought the library. This is the
one place in the module where that matters and it earns a `# T-009 / D-295` pointer and no more.

`substitute` is ADR-0011's variable rule, exactly:

- every `{{name}}` whose `name` is a key of `variables` is replaced by `str(value)`;
- a `{{name}}` with **no** value raises `MissingVariable(name)` — the name, never the value, because a
  value is caller data and an exception message is the least safe object on hand (T-011,
  `HistoryAppendRejected`'s rule transferred);
- variables the body does not use are **ignored**, because the missing-variable check already catches
  the typo an unused key would otherwise hide;
- after substitution, if `"{{"` appears anywhere in the result, raise `UnsubstitutedPlaceholder`. This
  is the belt, and it is load-bearing: `PLACEHOLDER` tolerates inner whitespace but not every
  malformation an author can type, and ADR-0011's *"a request containing a literal `{{customer_name}}`
  is never dispatched upstream"* has to hold for the forms the pattern does not match.

`compose_messages`:

1. If any element of `case_messages` has `role == SYSTEM_ROLE`, raise `SystemMessageRefused` naming the
   **ordinal**, never the content. GATE-07, one module over: the revision's body is the system message,
   it is always first, and it is the only one.
2. `system = {"role": "system", "content": substitute(body, variables)}`.
3. Return `(system, *case_messages)` — the case's conversation **byte-identical**, in order.

**Substitution touches the body and nothing else.** A case message containing `{{customer_name}}` is
passed through untouched, because ADR-0011 rejected filling placeholders from the conversation on the
grounds that *"a prompt whose conversation legitimately contains braces would break in a way no error
message could explain"*. This is one row of the table and it is the row a re-implementer gets wrong.

The module docstring is **four lines and no more**: what it composes, and the sentence that makes it
checkable — `# A-027 / ADR-0011 / GATE-07 / GATE-08: must match the gateway's composer`. The argument
lives in this plan (R7); the file carries the pointer.

`admit` iterates in order and returns the **first** refusal, stopping. `None` means admitted.

**Why modality is first and the ceiling is second**, written in this plan rather than in a comment: a
modality mismatch is a permanent property of the binding and is fixed by editing the suite or
re-pointing the revision; a ceiling refusal is a transient property of the calendar month and is fixed
by waiting. When both hold, recording the permanent one is the one a person can act on, and a run
refused for a transient reason has thrown away the durable fact. Short-circuiting also means a run
refused for modality never pays for a ceiling lookup, which is a cross-module call.

insertion **one line**. A single `if` would make it a re-shaped function, a diff nobody can review
against this plan, and a second place where the order lives.

**Step 1 — read, in one short read-only transaction.** `workspace_transaction(sessionmaker,
claimed.workspace_id)`; `suite = await get_suite(session, claimed.suite_id)`; `revision = await
get_revision(session, claimed.version_id)`; `refusal = await admit(session, claimed, suite)`. A `None`
from either read raises (R9) — a `LookupError` subclass declared in this module, named so a
`supervisor.job_crashed` line says which. The transaction closes before any dispatch: it must not be
open across an upstream call.

**Step 2 — the refusal path, and it dispatches nothing.** If `refusal is not None`:

1. `now = clock()`;
2. a fresh `workspace_transaction`, `t = await transition(session, claimed.run_id,
   to=RunStatus.REFUSED, finished_at=now, pass_count=0, fail_count=0, error_count=0)`;
3. **after the commit**: `observe_run_transition(t)`, then — when the code is

4. `log.warning("evaluation.run_refused", run_id=claimed.run_id, reason=str(refusal.code))`;
5. `return`. **`dispatch` is not called, not once**, and that is SC4's whole assertion.

The ordering in 3 is the one thing here that is easy to get wrong and impossible to see later: both
observations happen **outside** the transaction block, so a rolled-back refusal moves no counter.

**Step 3 — the unobserved-binding probe (D-298's named gap).** `check_modality` returned `None` for two
different reasons — the modalities agree, or nothing has ever been observed — and the second needs
different handling. Have `admit` return `None` in both cases and re-ask cheaply: in step 1, capture
