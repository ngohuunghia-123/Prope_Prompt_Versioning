<objective>
Make the tripwire a tripwire.

ROADMAP SC2 is four words long and every one of them does work: **`prope_registry_unfiltered_query_total`
stays 0, with a page attached if it moves.** The lock file makes it the mitigation for the failure mode
its own text calls *"the top adoption barrier in the survey, and the fastest way to lose the pilot"*:

> A new list or search query path is added without the permission filter. … Filtering is a property of
> the repository, not of the handler; queries that bypass it require an explicit, named unsafe call that
> trips the counter.

Phase 14's plan 14-01 built the wire — `read_without_permission_filter(session, statement, params, *,
reason)` in `repository.py`, the only site that touches the counter (D-243) — and phase 13's plan 13-01
defined the counter at import so the series exists at zero rather than appearing the moment it goes
non-zero. **This plan proves the two facts that make those worth having:** that the counter does not move
when the product is used, and that it *would* move if somebody went around the filter.

**A counter nobody has ever seen increment is indistinguishable from a counter that is not wired.** That
is the whole reason the negative control is not optional here, and it is the same argument phase 13 made
for its drop-and-restore trigger check and phase 1 made for its drop-and-restore constraint check: an
assertion nobody has watched fail is an assertion nobody should trust.

## D-267 — The counter is asserted as a DELTA, never as an absolute zero

**Chosen.** Every assertion in this plan reads
`REGISTRY.get_sample_value("prope_registry_unfiltered_query_total")` **before** and **after** the work
under test and asserts the difference. `0` for the read sweep, `1` for the negative control.

**This is forced rather than preferred, and the reason is worth stating because an absolute assertion is
the obvious thing to write.** `prometheus_client`'s default registry is **process-global** and lives for
the whole pytest session. The negative control in Task 2 increments the counter on purpose. So an absolute
`== 0` assertion elsewhere in the suite is green when it runs first and red when it runs second, which is
the worst shape an assertion can have: it passes alone and fails in a full run, or the reverse, and
whichever way round it lands, somebody will "fix" it by deleting it.

Two consequences, both written into the test module rather than left to be rediscovered:

- **Plan 15-06's phase gate must not assert an absolute zero either.** It asserts the structural claim
  instead — one increment site, no callers under `src/` — which is the claim that survives the session.
- **The alert is still `> 0` in production**, and that is correct: a real process has no test in it. The
  divergence between the rule's expression and the test's assertion is deliberate and the rule's
  `description` says so, so nobody "aligns" them later.

**Rejected: a fresh `CollectorRegistry` per test.** The counter is a module-level object bound to the
default registry at import (phase 13's D-228, for D-40's reason). Rebinding it per test would mean
re-importing the module or monkeypatching the metric, and a test that replaces the metric it is asserting
about proves nothing about the metric that ships.

**Rejected: running the negative control in a subprocess.** It would preserve the absolute assertion at
the cost of a second process model in the test suite, a second engine, and an assertion nobody can debug.
The delta is one line.

**Reversibility: cheap** on the mechanism; the divergence between the rule and the test is permanent and
is the thing to document.

## D-268 — The negative control calls the escape hatch directly, and a source walk keeps it to one caller

**Chosen.** Task 2 imports `read_without_permission_filter` and calls it with a real statement, real
params and `reason="negative control: proving the tripwire is wired"`, then asserts the delta is exactly
1 **and** that a `warning`-level record was emitted carrying that reason. Then an AST walk over
`src/prope/prompt_registry/` asserts **no module in the package calls it** — the function exists to be
callable, and nothing production-side calls it today.

**The pairing is the point.** *The counter moves when the hatch is used* plus *nothing uses the hatch* is
a stronger claim than either alone, and it is exactly the claim SC2 makes. Asserting only the second would
leave open that the hatch does not count; asserting only the first would leave open that something already
went through it.

**Rejected: asserting the counter is zero and calling that proof.** It is the assertion the criterion
literally asks for and it is satisfied by a counter that is defined and wired to nothing. The lock file's
own detection line for this failure mode is `prope_registry_unfiltered_query_total > 0`, which is a claim
about a mechanism, and a mechanism has to be exercised once.

**Rejected: a test that adds an unfiltered query to `src/` and removes it.** It provokes the real
condition and it edits production source inside a test run, which is the shape phase 3's alert-rules test
refused for its own artifact: *"a test that edited the artifact it audits is a test that can leave the
artifact edited."*

**Reversibility: cheap.**

## D-269 — Three rules, one page, and the page is the tripwire

**Chosen.** `deploy/prometheus/rules/prompt_registry.rules.yml` — one group, `prompt_registry`, three
rules, in the shape phases 3, 6, 9 and 12 established for their modules:

| Alert | Expression | `for` | Severity |
|---|---|---|---|
| `RegistryResolveLatencyHigh` | `histogram_quantile(0.95, sum by (le) (rate(prope_registry_resolve_duration_seconds_bucket[5m]))) > 0.01` | `5m` | ticket |
| `RegistryUnfilteredQuery` | `increase(prope_registry_unfiltered_query_total[5m]) > 0` | `0m` | **page** |
| `RegistryUnapprovedPointer` | see D-270 | — | ticket |

**Exactly one pages, and which one is a decision.** Phase 3's rules file asserts its own two-page set for
the same reason, and the argument transfers: *"a page that fires on one malformed envelope is a page
people learn to close, and that would cost the only ones that are genuinely worth having."* Here the
paging rule is the one whose condition means **a private prompt may already have been shown to somebody
with no grant**, which is the one thing in this module worth waking a person for. Resolve latency is a
performance regression and is a ticket.

**`increase(...[5m]) > 0` rather than the lock's literal `> 0`.** The lock declares
`prope_registry_unfiltered_query_total > 0, page immediately`. Taken literally that fires **forever** once
the counter has ever moved — process restarts reset it, but a long-lived container would page every
evaluation interval for the life of the deployment, which is how a page becomes noise. `increase(...)`
fires on the event and clears. **The deviation is declared in the rule's own description**, naming the
lock line it departs from, rather than being silently improved.

**Reversibility: cheap on the file, one-way on the alert.** Phase 14's D-243 says it: once
`RegistryUnfilteredQuery` has been observed firing in normal operation, nobody trusts it again.

## D-270 — `RegistryUnapprovedPointer` ships as a document, and the SQL it is really about is asserted as a test

**Chosen.** The lock declares:

> `RegistryUnapprovedPointer` — the Success-metric query (released pointer whose revision status
> != Approved) returns any row

**That is a SQL query and Prometheus cannot run one.** ADR-0030 chose Prometheus and Grafana *and
deliberately nothing else*: no `postgres_exporter`, no query-exporter, nothing that turns a `SELECT` into
a series, and none of the six declared metrics exposes the condition. So the rule has no honest
expression. And phase 13's D-221 made the condition **structurally unreachable** anyway — BR-03 is a
foreign key from `(workspace_id, released_version_id, released_version_status)` to
`(workspace_id, version_id, status)` with the status column pinned to `'Approved'` by a `CHECK`, so the
engine will not accept the row the query looks for.

So the rule ships with **all three names present** (the declared set is complete, and
`test_alert_rules.py`'s equality assertion is therefore meaningful), an expression over a metric that
exists, and a `description` that carries, in order:

1. the Success-metric SQL **verbatim**, so a responder can run it;
2. the sentence that Prometheus in this stack cannot evaluate it, and why (ADR-0030);
3. the fact that D-221's foreign key makes the condition unreachable while the constraint stands, so the
   honest reading of a non-empty result is *"the constraint is gone"* rather than *"the pointer went
   bad"*;
4. the name of the check that actually runs —
   `tests/integration/test_registry_schema_ships_its_guarantees.py`'s named assertion on
   `fk_prompt_property_released_revision`, which phase 13 wrote with a message stating what its loss
   costs;
5. `OQ-082`, by id.

And **Task 3 asserts the SQL itself**, against a seeded database, so the query in the annotation is known
to run and known to return nothing. That is the closest thing to the declared alert this stack can
execute, and it runs on every commit rather than at 3 a.m.

**Rejected: a seventh metric set by a `worker` job** running the SQL on an interval. Faithful to the
intent and it puts a scheduled job in a module whose `deployment_target` says in as many words *"This
module has NO scheduled job and NO queue consumer of its own"* — the same sentence that made the Cache row
`n/a` and that ADR-0046 already had to repair once elsewhere.

**Rejected: omitting the rule.** The lock declares three alerts; shipping two is a spec deviation, and
`test_alert_rules.py`'s `DECLARED_ALERTS` equality would have to be written to expect the smaller set,
which hides the deviation inside a test constant.

**Reversibility: cheap** — the whole thing is one YAML block and one test.
