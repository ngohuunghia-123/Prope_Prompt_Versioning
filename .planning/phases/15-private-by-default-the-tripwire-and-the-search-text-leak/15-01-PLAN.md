## D-260 — `mode: all` widens PERMISSION, never VISIBILITY, and the visibility disjunction is three terms

**Chosen.** `src/prope/prompt_registry/repository.py` holds one predicate fragment, used by every
person-facing read, and it is unconditional:

```sql
(owner_id = :actor_id
 OR id = ANY(:visible_ids)
 OR access_level = :workspace_access_level)
```

`VisibleSubjects` contributes only to `:visible_ids` — `mode: ids` supplies them, `mode: none` supplies
an empty array, and **`mode: all` supplies an empty array too.** The mode is consumed, and it is
consumed as the answer to *"may this actor read prompts at all"*, never as the answer to *"which
prompts exist for this actor"*.

**Rejected: INT-002's literal reading**, which is that `mode: all` means the caller adds no id predicate
at all. It is what the interface registry says, it is what phase 8's plan 08-02 documents at the
producer, and it breaks non-negotiable #4 on the first workspace with two people in it. The worked case
is in `OQ-080`: B holds a role whose `role_permission` rows include `prompt.read` — which every
non-guest role must, or B cannot use the product — so `visible_subject_filter` answers `mode: all`,
the id predicate disappears, and A's private prompt is in B's result page while the detail route
(which asks `is_visible`) answers `404` for the same row. Listable and not openable, from two spellings
of one rule.

**Rejected: reading the mode at the handler and choosing between two statements.** It moves the decision
out of the repository, which is the exact property A-118 and the lock's `security_requirements` exist to
protect: *"Permission filtering lives in the repository layer, not in handlers, so a new query path
cannot forget it."* A branch in a handler is a thing the eleventh handler forgets.

**Rejected: asking `is_visible` per row after the query.** That is the per-row check A-118 replaced, it
needs `grant_level` and `is_active_member` per row, and it turns a page of 50 into 50 permission calls.

**The failure direction is stated, because it is the one that matters.** This predicate can return **too
few** rows — an actor with a `mode: all` role who owns nothing, holds no grant, and looks at a workspace
of private prompts sees an empty list. That is private-by-default working. It cannot return another
person's private prompt, which is the direction that costs the pilot.

**Reversibility: costly.** Ten routes, the search path and the whole of PR-03 are written against this
shape, and reversing it means reversing `OQ-080` with the user.

## D-261 — The membership term is the session, and the inference is written at the predicate rather than assumed

**Chosen.** The third disjunct is `access_level = :workspace_access_level` with **no membership column
in it**, because inside a management request the actor is an active member of the request's workspace by
construction: `authenticate_session(cookie)` returns `{user_id, workspace_id}` (INT-005) and every route
serves inside `workspace_transaction(sessionmaker, session.workspace_id)`. access-control's `is_visible`
takes `is_active_member` as a parameter and this module has no way to read it — `access.workspace_member`
is another module's table and `data.reads` forbids the join.

**This is an inference about how sessions are issued, not a contract**, and the docstring says exactly
that, cites `OQ-081`, and names the case it does not cover: a session that outlives a membership. ADR-0022
makes revocation effective on the next request for grants and keys; nothing has been read that says what
removing a member does to their session row.

**Rejected: a sixth access-control seam** (`is_active_member`). Honest, and one more round trip on every
list request, plus an `apis.exposes` line and an INT row this planner may not write.

**Rejected: defaulting the term to `False`** — i.e. shipping the two-disjunct form phase 14 already has.
It fails closed, which is why phase 14 could ship it, and it makes `access_level = 'workspace'` mean
nothing at all: the level exists so that a prompt can be shared with the workspace without a grant per
person, and a predicate that ignores it deletes the feature rather than securing it.

**Reversibility: cheap** — one bound parameter, one disjunct.

## D-262 — Byte-identity is asserted after exactly one normalisation, and the normalisation is proved to be the only difference

**Chosen.** `tests/security/_refusal_shapes.py` exposes
`assert_identical_refusals(left, right, *, expected_status, expected_code)`. It compares:

1. `status_code`;
2. the response headers, minus `content-length` — which is derived — and minus `date` if present;
3. the response **body bytes**, after replacing the value of the envelope's `request_id` with a fixed
   placeholder in both.

And it asserts, in the same function, that **the un-normalised bodies differ** — because if they did not,
`request_id` would not be varying, the envelope would be broken, and the normalisation would be hiding
that rather than allowing for it.

**Rejected: comparing parsed JSON.** Parsing is the application's own account of what it sent, and phase
12's D-205 already settled this posture for the credential sweep: *"the corpus is the bytes that actually
went out, and the two differ exactly when a serializer does something nobody read."* A key-order
difference, a `null` rendered as an absent key, an integer serialized as a string — all of them are
observable to an attacker and invisible to a parsed comparison.

**Rejected: comparing status and `code` only.** The leak AC-3 is about is *existence*, and existence
leaks through anything that varies: a `details` object present on one and absent on the other, a
`Content-Length` that differs by four bytes, a `message` that names the id on one path. Phase 9's D-131
already forbids `details` on the 404 branch for exactly this reason; this assertion is what would notice
if that ever changed.

**Rejected: normalising more than `request_id`.** Every additional normalisation is a byte range the
assertion stops looking at. One is the minimum the A-045 envelope forces, and it is proved to be
necessary rather than assumed.

**Reversibility: cheap.**

## D-263 — The refusal is asserted over a written-out route census, never over the route the test happened to pick

**Chosen.** `tests/prompt_registry/__init__.py` gains `REGISTRY_READ_ROUTES` — a literal tuple of every
registry route that reads a subject and can therefore leak its existence, each entry carrying the method,
the path template, and how to build a request for it. Written out rather than derived from the router,
in `tests/architecture/test_route_table.py`'s `EXPECTED_ROUTES` posture and for its stated reason: *"a
test that computed its expectation from the application would pass whatever the application happened to
mount."*

A test at the bottom of `test_private_by_default.py` asserts the census covers every subject-reading
route in `assembled_routes(app)` whose path starts with `/api/v1/prompts` or `/api/v1/revisions` — so a
route added in phase 16 or later without a refusal assertion is a red test on the day it is written,
rather than a gap discovered by a milestone that does not own it.

**Rejected: deriving the census from the router.** The assertion would be checking a list the router also
produced.

**Rejected: asserting the refusal on the detail route only**, which is what AC-3's literal text asks for
(*"a direct GET by its id"*). The lock's own `security_requirements` generalises it — *"A prompt the actor
may not see returns the same not-found response as a nonexistent id"*, with no route named — and the
routes that leak most cheaply are the ones nobody thinks of: `/revisions/{version_id}`, which is keyed on
a **revision** id and reaches the prompt through a join, and `/diff`, which takes two.

**Reversibility: cheap.**
