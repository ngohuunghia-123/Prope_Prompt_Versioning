<objective>
Prove ROADMAP SC4 where it is actually load-bearing: **through the read functions this module exposes**,
not only against the tables underneath them, and with the one control phase 13 could not run.

The criterion:

> A cross-workspace read of `registry.revision` is refused by RLS, and a read with no `app.workspace_id`
> set returns zero rows rather than all rows.

`registry.revision` **holds every prompt body in Prope** and carried no tenant column at all until
ADR-0045's inverted coverage walk failed on it — the fourth child-table-with-only-a-parent-FK in five
module passes, and T-018 in the lock's STRIDE register. Phase 13's plan 13-06 asserted the boundary at the
table: the wrong tenant, no tenant, a mis-stamped `INSERT`, a cross-tenant parent, and the reporting
role's four privileges. **That was the right thing to assert then and it is not the whole of SC4 now**,
because between then and this phase a module grew ten routes, two hot reads and three commands, and each
of those is a path to the same rows that phase 13 could not have driven.

**Two things this plan adds that nothing else in the milestone has.**

1. **The read paths.** Phase 13 wrote its own SQL. This plan calls `resolve()`, `list_released()`, the
   filtered repository reads, the keyword search and the activity read — the functions a bug would
   actually arrive through — under the wrong tenant and under no tenant.
2. **The negative control.** Phase 13 asserted zero rows under an unset tenant. **Zero rows is also what
   an empty table returns, what a broken query returns, and what a `WHERE 1=0` returns.** The only way to
   know it is the policy is to remove the policy and watch the rows appear. Nothing in phases 1-14 has
   done that for `registry`, and it is the same argument phase 1 made for its constraint mutation check
   and phase 13 made for its trigger one.

**This plan runs ALONE** (ORCHESTRATION §7a(b)). Task 2 drops a policy on the session-scoped Postgres
container; a concurrent test inside that window reads another tenant's prompt bodies and fails for a
reason that has nothing to do with what it was testing.

## D-271 — SC4 is asserted through the module's own read functions, and the policy is removed to prove the zero

**Chosen.** `tests/security/test_registry_read_paths_are_tenant_scoped.py` enumerates every public read
in `src/prope/prompt_registry/` — **discovered from the package rather than written down**, then compared
against a written-down expected set so both a new read and a deleted one fail — and drives each one three
times: right tenant (rows), wrong tenant (zero), no tenant (zero, no raise). Then, once, with the
`registry.revision` policy dropped, it drives the no-tenant case again and asserts **all** rows come back.

**Why through the functions rather than through SQL.** A hand-written `SELECT` proves the table's policy.
It cannot prove that `resolve()` — which A-128 carves out as **raw SQL** for latency, on the gateway's hot
path — issues a statement the policy applies to. A raw statement executed on a connection obtained
somewhere else, or through an engine built with a different role, would be invisible to a table-level
test and is exactly the shape a latency optimisation reaches for.

**Why the drop-and-restore.** *Zero rows* is the answer to a great many questions and only one of them is
the one being asked. The control converts *"the read returned nothing"* into *"the read returned nothing
**because of the policy**"*, and it is the only assertion in the milestone that distinguishes them.

**Rejected: proving it by reading the policy out of `pg_policies`.** Phase 13's coverage walk and its
constraint inventory already do that, and a policy's existence is not its effect: a policy with a
predicate that is accidentally true is present, enumerable, and useless.

**Rejected: dropping the policy on a fresh container.** A second container per test session for one
assertion, on a Windows Docker Desktop host that already runs Postgres and RabbitMQ. The `finally` plus
the re-assertion is cheaper and the hazard is declared.

**Reversibility: cheap** — a test module.

## D-272 — Nothing in the package may obtain a session except through `workspace_transaction`

**Chosen.** `tests/architecture/test_registry_session_origin.py` walks every module under
`src/prope/prompt_registry/` with `ast` and asserts that no module calls a `sessionmaker`, constructs an
`AsyncSession`, calls `engine.connect()`, `engine.begin()`, or otherwise obtains a connection by any route
other than `workspace_transaction` — or by receiving a `session` as a parameter, which is the shape every
function in the module actually uses.

**This is what keeps the unscoped case a bug rather than an idiom.** `src/prope/db/session.py` is explicit:
*"A query issued on a session obtained any other way sees zero rows, because the policy predicate compares
against a setting that was never set."* That is a **safe** failure and it is also a **silent** one: a
module that grew its own sessionmaker would return empty lists forever and look like a workspace with no
prompts. The runtime test above proves the engine's answer; this proves nobody in this package can ask the
question.

**The exemption is `worker`'s importer, and it is named.** `deployment_target` says the shared image's
`worker` imports this module *"as a reader"* for evaluation's batch runs. If a module in this package
builds a session for that path, it is a real exception and belongs on a written-out `ALLOWED` list with a
reason — **empty on the day this ships**, in the posture
`tests/architecture/test_no_sql_interpolation.py` already takes for its own escape hatch.

**Rejected: a runtime assertion that every session carries the setting.** It can only prove the sessions
the tests happened to open, and it would need a hook in production code to observe them — instrumentation
added to satisfy a test, which is the thing to refuse.

**Reversibility: cheap.**
