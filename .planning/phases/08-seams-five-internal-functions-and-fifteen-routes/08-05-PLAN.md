<objective>
Mount `POST /api/v1/users/{user_id}/tombstone` — **the only route in Prope that destroys data** — and
prove the half of ADR-0054 that makes the erasure honest: that the audit trail naming the erased
person is completely unchanged, and that one reasonless `user_tombstoned` event exists in each
workspace they belonged to.

**Why this is a separate plan and the last route in the phase.** The operation touches five tables and
writes N events in one transaction, and its correctness is a *negative* over the one table in Prope
that nothing may delete from. AC-14 is not "the tombstone works"; it is *"every event they caused is
still present with their `actor_id` unchanged, no row was deleted, and nothing was anonymised or
reassigned"* — an assertion about what did **not** happen, which is the kind that passes vacuously
unless the population it ranges over is proven non-empty first.

**Two obligations point here from other phases.** Phase 6's `deferred-items.md` routes *"AC-9's call
site — access-control writing one `user_tombstoned` event per workspace"* to Phase 8 by name. And
`.planning/REQUIREMENTS.md` puts AC-13 — the identity columns, the sessions — in **Phase 7**, so the
two halves of one operation are split across two phases on purpose: Phase 7 owns what the tombstone
*clears*, Phase 8 owns what it *records*.

---

**D-129 — the event fan-out is one `user_tombstoned` per `workspace_member` row of any status, with
empty `details` and no `reason`, and the operation is refused while an active membership exists.**

Chosen, and every clause is ADR-0054's rather than this plan's:

- **One event per workspace the person had been a member of**, read from the retained
  `workspace_member` rows **of any status**. Those rows are retained precisely because they are how
  the operation knows which workspaces to write into — delete them and the fan-out has no source.
- **`details = {}` and `reason = None`.** The Phase 4 seed registers `user_tombstoned` with empty
  `detail_keys` and `requires_reason` false, and ADR-0054 §7 gives the reason in its own words:
  *"requires_reason here would be the exact mechanism by which the erased name walks back into the one
  table nothing can be removed from."* A free-text reason on an erasure event is the erasure undoing
  itself one plausible sentence at a time.
- **Refused while the person still holds an active membership**, with a `409`. Each removal writes its
  own `member_removed` event in its own workspace, and the tombstone is the account-level act that
  follows — *"so the two facts stay separately recorded rather than collapsed into one ambiguous
  event."*
- **`user.tombstone` is its own action**, separate from `workspace.manage_members`, because A-115 says
  so and gives the reason: erasure is irreversible and account-scoped while removal is neither.

Rejected: **one event, in the workspace the actor performing it is in.** It is one row instead of N and
it records the act in a place that has nothing to do with the person: a workspace whose member
vanished would have no event explaining it, which is the exact question the trail exists to answer.
Rejected: **deriving the workspace list from `role_binding`.** Bindings are deleted by this same
operation, and a person removed from a workspace has no binding in it at all — so the list would be
short by every workspace the tombstone is most likely to be about.
Rejected: **carrying the workspace count, the removal dates or the former display name in `details`.**
Each would need a registry migration (`OQ-047`'s mechanism) and each is a name-shaped or
name-adjacent value entering the append-only table at the moment the point is to remove one.

Reversibility: **one-way, in the strongest sense in this project.** The operation is irreversible
inside Prope by design; the events it writes are permanent by privilege (ADR-0025). What *is*
reversible is the choice of fan-out shape, and only until the first tombstone runs in an environment
anybody keeps.

One command, and it is the only one in Prope that destroys anything.

**`src/prope/access_control/tombstone.py` — one public function.**

```python
async def tombstone_user(session, *, user_id: str, tombstoned_by: str) -> tuple[str, ...]
```

Returns the workspace ids it wrote an event into, so the route can report the count without the caller
re-reading anything. No `commit`, no `begin`, no `rollback` — the route owns the transaction, exactly
as `grants.py` and `members.py` do, and here the boundary is doing more work than anywhere else in the
module: **six kinds of write must be one atomic act or the person is half-erased.**

The order, and each step's reason at the step:

1. **Refuse if any `workspace_member` row for this user has an active status.** Raise this module's
   refusal, which the route renders as `409`. ADR-0054's own sentence: each removal writes its own
   `member_removed` event in its own workspace and the tombstone is the account-level act that
   follows, *"so the two facts stay separately recorded rather than collapsed into one ambiguous
   event."* The check is first because a refusal after a delete is not a refusal.
2. **Read the workspace ids from `workspace_member`, any status.** This is the fan-out's source and
   the reason those rows are retained. Read it **before** any deletion, and write at the read that a
   later reordering that deleted first would produce an empty fan-out and a green test — which is why
   the step order is argued here rather than left to the reader.
3. **Clear the identity columns** — `email`, `display_name` and `password_hash` to NULL, `status` to
   `tombstoned`, `tombstoned_at` and `tombstoned_by` set. Note at the code that `unique(email)`
   tolerates any number of tombstones because PostgreSQL permits many NULLs in a unique index, and
   that a NULL `password_hash` is a no-match that **still runs the hash comparison** so a tombstoned
   email stays timing-indistinguishable from an unknown one (A-144, ADR-0043) — the sign-in side of
   that is Phase 7's and is named here so the two halves are findable from each other.
4. **Delete every `session` row for the user.** *"A tombstone that left a live session behind is a
   tombstone the person can still authenticate through"* (ADR-0022). Effective immediately, because
   sessions are rows and nothing is cached.
5. **Delete every `role_binding`, and every `prompt_grant` naming them as grantee.** Move every
   `workspace_member` row to `status = removed` and **retain** it.
6. **Leave every `api_key` untouched**, and say so in a comment at the absence — an absence nobody
   argued for reads as an oversight. A key belongs to the workspace, not to its creator (A-113), and
   revoking one on an HR event would break a consuming product's traffic silently.
7. **Append one `user_tombstoned` per workspace id from step 2**, `target_type='user'`,
   `target_id=user_id`, `scope_prompt_id=None`, `details={}`, `reason=None`, `actor_id=tombstoned_by`,
   `workspace_id` = each id in turn. **The events are last** so every one of them describes a state
   that has already been reached in this transaction.

**The `workspace_id` problem, and it is the sharpest thing in this plan.** Every append writes a row
carrying a `workspace_id`, and the caller's transaction has **one** tenant context set by
`workspace_transaction`. Writing an event into a workspace the transaction is not scoped to will be
refused by the tenant policy's `WITH CHECK` — which is the policy working correctly. Resolve it in
whichever way Phase 7's schema actually permits, in this order of preference, and **state the choice
and its reason in the docstring and the SUMMARY**:

- (a) the route opens **one transaction per workspace**, each with its own tenant context, and the
  atomicity claim weakens from *one transaction* to *one per workspace* — **which is not acceptable
  for AC-14** and is listed only to be refused: a partial fan-out is a person erased in some
  workspaces and not others;
- (b) the whole operation runs in one transaction whose tenant context is set per statement group via
  `set_config` — i.e. `SET LOCAL app.workspace_id` is re-issued before each workspace's append, inside
  the same transaction. This keeps one commit and satisfies every policy, and it is the shape to
  prefer;
- (c) `history_event`'s policy or the append path already tolerates a multi-workspace write in one
  transaction. **Check rather than assume**; if it does, (b) is unnecessary and the docstring says so.

Whichever holds, write the argument at the code: **the tombstone is the only operation in Prope that
legitimately writes into more than one tenant in one transaction**, and that is worth a paragraph
because the next person to see it will assume it is a bug.

**One metric**, if Phase 7 left it owed: no metric in the lock file's list counts tombstones. Do
**not** invent one — the lock declares seventeen and this operation is deliberately not among them,
and adding an eighteenth here would repeat the finding phase 6 raised as `OQ-039` in the other
direction. Note the absence in the SUMMARY instead.

  <action>
One file, and its docstring is where the criterion is explained rather than restated.

**Name the failure mode that looks healthy, first.** A tombstone that also anonymised the trail would
*pass* a naive test — the person's name is gone from everywhere, which is what a reader assumes
erasure means — and it would destroy the product's central claim, which is that every call can be
traced back to the exact revision that served it and every decision to the actor who made it. AC-14 is
the assertion that keeps the erasure honest **in the direction the claim runs**, and its whole
difficulty is that it is a negative: nothing changed. A negative over an empty set is free, so
**every assertion in this file establishes its population first.**

**Building the population.** Use the seeders from `tests/access_control/__init__.py` plus the routes
this phase mounted, so the events are real ones: create three workspaces, add the person to all three,
have them grant access in one and be assigned a role in another, remove them from all three, then
tombstone. That produces a person with `member_added` ×3, `role_assigned`, `access_granted`,
`member_removed` ×3 naming them as actor or target — **assert that count is at least six before the
tombstone runs.** Say in the docstring that this is the vacuity guard and that without it the whole
file passes on a person who did nothing.

**The whole-row comparison** is the strongest available form of *"nothing was anonymised or
reassigned"*. Select every column of every event naming the actor into a stable ordered structure
before the tombstone, do the same after, and compare — rather than asserting field by field, which
tests the fields somebody thought of. Phase 6's `06-03` established the whole-row posture for this
table; reuse it. Read both snapshots through `migrate_engine`.

**The api_key assertion has two halves and both matter**: the rows are unchanged (structural), and a
key the person created **still authenticates** (behavioural). The second is the one that would catch a
tombstone that revoked keys by a path the row comparison did not cover.

**The degenerate zero-workspace case is asserted deliberately.** A person who belonged to no workspace
produces no events, and that must be a success and not a refusal — otherwise an account created and
never added anywhere can never be erased, which is the case an erasure request is most likely to
arrive for.

**`tests/integration/test_tombstone_clears_identity_and_sessions.py`** — AC-13's file, Phase 7's
requirement. **Only touch it if it exists.** If it does, add nothing that duplicates this file; add
only the assertions this plan's transaction changed — that the `workspace_member` rows are retained
and that the bindings and grants are gone — and say in the SUMMARY exactly what was added. **If it
does not exist, do not create it, and report the absence**: AC-13 is Phase 7's and a missing test for
another phase's requirement is a gap the phase gate should surface rather than a gap this plan should
fill.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin → `POST /users/{id}/tombstone` | The only request in Prope that destroys data, and it is irreversible. |
| `tombstone_user` → `history.history_event` | Writes into **more than one tenant in one transaction** — the only operation in the system that legitimately does. |
| `tombstone_user` → `access.user` | Removes the only two directly identifying columns in Prope (A-146). |
| the running system → the nightly dump | The one path by which an erased name comes back, and it is outside every module. |
