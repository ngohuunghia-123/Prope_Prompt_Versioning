resolves it to a `(user_id, workspace_id)` from a live row, `may()` decides, one `access.prompt_grant`

**D-116 — the shared A-045 surface moves out of `prope.call_ledger.schemas` into
`src/prope/management_api.py`.**
Chosen: one neutral module, outside every module's package, holding `SESSION_REQUIRED`, `ErrorCode`,
`ManagementRefusal`, `ApiError`, `ErrorEnvelope`, `REQUEST_ID_PREFIX`, `_envelope`,
`install_error_envelope`, `DEFAULT_PAGE_LIMIT`, `MAX_PAGE_LIMIT` and `PageRequest`. `session_auth.py`
and `management_api.py` then sit beside each other as the two shared-infrastructure files, and
`session_auth` imports from `management_api` in one direction only.
Rejected: **access-control importing `prope.call_ledger.schemas`.** `access-control.lock.yml`'s
`forbidden_dependencies` names call-ledger with its own reason, and release-control's owed AC-14 is an
import-linter layering contract that *"fails the build on a cross-module model import"* — so the edge
would be built now and refused later, by a test in another milestone. Rejected: **a second envelope
for access-control.** A-045 says there is one error shape and `install_error_envelope`'s docstring
says a second is the thing a client would have to parse two of. Rejected: **leaving it where it is and
re-exporting.** Two public homes for one closed `StrEnum` is two places for the vocabulary to drift,
and phase 5's D-66 refused the same shape for the same reason.
**This move was written down in advance by the code itself.** `install_error_envelope`'s docstring
says: *"when a second module mounts routes, this function and `prope.session_auth.ManagementRefusal`
move together to wherever OQ-021's answer puts the shared surface."* Phase 8 is that second module.
OQ-021 is still unresolved and is **not** resolved here — the file is placed where session_auth.py
already is, on session_auth.py's own stated reasoning, and OQ-021 is cited at the top of the new
module.
Reversibility: **cheap** — a move plus six import sites, with no behaviour on either side of it.

**D-117 — access-control's sixteen routes live in five modules under
`src/prope/access_control/routes/`, assembled into one `APIRouter`.**
Chosen: `routes/__init__.py` owns the router and imports each resource module; `routes/grants.py`,
`routes/keys.py`, `routes/auth.py`, `routes/workspaces.py`, `routes/users.py` own their handlers.
`prope.app` includes **one** router from this module.
Rejected: **one `api.py`**, call-ledger's precedent. That file is ~700 lines for five routes; sixteen
would be ~2,000, and — the operative reason — every plan in this phase would edit the same file, which
is also what would make the phase's waves collide.
Rejected: **five `include_router` calls in `prope.app`.** D-13's composition is *"the list is the
import block"*, and five entries for one module makes the list longer without making it more explicit;
it also multiplies the number of places a prefix can be typed wrong.
**The route count is sixteen, not fifteen**, and the discrepancy is raised as `OQ-049` rather than
absorbed: INT-029's row says *"15 routes"* beside a Routes line enumerating sixteen operations, and
the lock file's `libraries_frameworks` says nineteen beside an `apis.exposes` block enumerating
eighteen. The enumeration is authoritative; the counts are summaries. **No new health route is
mounted** — `/healthz` and `/readyz` are one pair per process and `app` already serves them with the
semantics INT-030 gives access-control.
Reversibility: **cheap.**

**D-118 — `ManagementAction` gains access-control's members, and they carry NO module prefix.**
Chosen: every new member's **value is taken from `prope.access_control.vocabulary.Action`**, the
twenty-five-member `StrEnum` Phase 7's D-98 creates and its migration mirrors as the
`role_permission.action` `CHECK` — imported and referenced as `Action.<MEMBER>.value`, never retyped.
call-ledger's five keep their `call_ledger.` prefix.
Rejected: **prefixing access-control's members `access_control.`** to match the neighbours. It would
give every permission two spellings — one on the route, one in the database — and the bridge between
them would be a mapping table nobody maintains.
Rejected: **not extending `ManagementAction` at all**, which is what Phase 7's D-98 chose *for Phase
7* and is right there: it declined to add twenty-five permission names that no route declares, because
`test_every_registered_action_is_declared_exactly_once` asserts an exact set equality. Phase 8 adds
**only members that have routes**, which is the other half of that same argument — and Task 4 replaces
the exact-equality assertion with a both-directions membership assertion precisely so the two halves
compose.
**Phase 7 raised the identical conflict independently as `OQ-041`, and the name disagreement as
`OQ-042`.** Both are cited beside the block; `OQ-046` is this phase's form of the first and adds the
bridge test. Where A-115 and INT-001 spell an action differently, **A-115 wins** (Phase 7's D-99), so
this phase's grants routes declare **`prompt.grant`** and not INT-001's `prompt.change_access`.
The consequence is stated rather than hidden: `tests/architecture/test_route_table.py:363-374`
currently asserts *every* member starts with `call_ledger.`, and this plan **rewrites** that assertion
to the rule that survives — lowercase dotted ASCII everywhere, and a module prefix exactly on the
members belonging to a module that makes no INT-001 call. Plan 08-06 turns the other half into the
bridge test. Raised as **`OQ-046`**: two closed sets are both called "the vocabulary", and AC-10 reads
differently against each.
Reversibility: **costly** — the values are permission strings five modules will be written against.

**D-119 — INT-005's wiring is Phase 7's (D-101) and this plan does not rebuild it; what it adds is the
one finding Phase 7's version leaves open.**

**Read this before Task 2.** Phase 7 plan 07-01 ships `src/prope/access_control/sessions.py` with
`authenticate_session(sessionmaker, session_id)`, and its **D-101** gives `require_session` a
`Request` parameter, has it read `request.app.state.sessionmaker` directly, and call
`authenticate_session`. That decision was taken while this phase was being planned in parallel, it
executes first, and **it wins.** Phase 8 verifies it and builds on it.

What this plan therefore does **not** do: it does not write `sessions.py`, does not add
`install_session_authenticator`, and does not change `require_session`'s body.

What it does instead — and this is the substance of D-119: **record the finding Phase 7's D-101 does
not address.** D-101 argues correctly that `session_auth.py` must not import
`prope.call_ledger.api.get_sessionmaker`, because that would make the shared session boundary depend
on one module's error vocabulary. The same argument runs in the other direction and D-101 does not
make it: `require_session` calling `authenticate_session` means **`session_auth` imports
`prope.access_control`**, and `prope.call_ledger.api` imports `session_auth` — so call-ledger
transitively depends on access-control, which is the edge ADR-0018 says it does not have and cites as
the reason call-ledger needs no permission check. It is also the edge release-control's owed AC-14
import-linter contract would fail the build on, in Phase 24.

**Adopted: leave Phase 7's wiring exactly as it shipped, and record the edge.** Rejected: **replacing
it with a composition-root-installed authenticator** (`install_session_authenticator` in
`install_registry`'s shape, ADR-0038) — which is what this plan originally specified and which does
close the edge. It is refused **not** because it is worse but because rewriting a working boundary one
phase after it shipped, in a phase that owns four other requirements, trades a real regression risk on
Prope's authentication path for an import-graph property that no test asserts until Phase 24. The
executor must **check how Phase 7 actually wired it** and, if `session_auth.py` does import
`prope.access_control`, report it in the SUMMARY and in `deferred-items.md` §8 as an open edge with
Phase 24 named. D-116's `management_api.py` move already removes the *other* half of the same problem,
which is why that half is done here and this half is only recorded.
Reversibility: **cheap** — the installed-authenticator shape remains available to whichever phase
takes the import-linter contract.

**D-120 — the grant events carry the grantee in `target_id` and the level in a newly registered
detail key.**
Chosen: `target_type='prompt_grant'`, `target_id=<grantee usr_ id>`, `scope_prompt_id=<prompt_id>`,
`actor_id=<granter>`; `access_granted` carries `details={"level": ...}` and `access_revoked` carries
`{}`. One additive migration registers `{level}` on `access_granted` only, mirroring
`role_assigned` / `role_revoked` exactly.
Rejected: **reading the level back from `access.prompt_grant`.** Revocation *deletes* the row, so
after a revoke the level access was held at exists nowhere — on the one table in Prope that is never
deleted from, which is the fact most worth having.
Rejected: **putting the level in `reason`.** Free text on an append-only table is what ADR-0054
argues against at length, and `requires_reason` is false for both actions.
Rejected: **a surrogate `id` on `prompt_grant`** so `target_id` could name the row. The lock's field
list has none, the row's identity is the triple, and adding one to make an event field natural is a
schema change to serve a payload.
Consequence, stated: `tests/integration/test_history_schema_ships_its_guarantees.py` asserts *"every
other action's `detail_keys` is empty"* and goes from two declared key sets to three **in this plan**,
so the suite does not go red in another module's file. Raised as **`OQ-047`**.
Reversibility: **costly** — a registered detail key is data five modules read through
`registered_actions()`, and un-registering one after events carry it makes those events unwritable.

The same decision fixes **where the write lives**: `grant_access(session, ...)` and
`revoke_access(session, ...)` are service functions in `src/prope/access_control/grants.py`, each
writing its row and calling `append(session, event)`, with no `commit`, no `begin` and no `rollback`
anywhere in the module; the route owns `workspace_transaction(sessionmaker, workspace_id)`. Rejected:
**the handler doing both inline** — five more write routes follow in plans 08-03 to 08-05 and each
would re-derive the ordering, and the ordering *is* the requirement.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `app` (session cookie) | The cookie is the whole of a person's authority (ADR-0029). It arrives unauthenticated, decides `workspace_id` for the entire request, and therefore decides which tenant's rows the transaction may touch. |
| SPA → `POST /prompts/{id}/grants` | The caller supplies the subject's `owner_id` and `access_level` (ADR-0020). Access-control cannot verify them and is forbidden from reading the table that would. |
| `app` → `access.lookup_session` | A `SECURITY DEFINER` function running with no tenant context — one of four sanctioned bypasses of RLS in the whole system. |
| access-control → `history.history_event` | An append on the caller's connection. Anything it carries is permanent (A-121, ADR-0025). |
