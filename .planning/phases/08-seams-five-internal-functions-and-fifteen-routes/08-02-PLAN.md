<objective>
Ship INT-002 — the **set** form that sits beside `may()` so a list endpoint filters in SQL rather than
per row — and prove it against the assertion the lock file itself names: the id list compared
row-for-row against calling `may()` on every prompt in a 1,000-prompt workspace.

**Why the set form is the interface and not an optimisation.** A-118 and INT-002 both say it, and the
reason is a prediction about people rather than about performance: without it, *"permission filtering
lives in the repository layer"* cannot be satisfied without a cross-module join the registry forbids
itself, and **the version that ships under deadline pressure is the query with no filter at all.** The
shape exists to make the correct implementation the easy one. PITFALLS names the resulting failure —
a private prompt appearing to someone with no grant — as the top adoption barrier in the survey and
the one most likely to end a pilot, *"because it is discovered by the person whose prompt leaked."*

---

**D-121 — the returned set is the grant-derived contribution; ownership stays the caller's own
predicate.**
Chosen: `visible_subject_filter` answers from `access.role_binding`, `access.role_permission` and
`access.prompt_grant` only. `mode: all` when a role binding confers the subject type's read action at
workspace scope. `mode: ids` with exactly the `prompt_grant` ids otherwise. `mode: none` when neither
confers anything. **The caller ORs its own `owner_id = :actor` predicate**, and the contract says so in
those words.
Rejected: **returning "everything the actor may see", ownership included.** It is what AC-9 literally
asks for and access-control cannot produce it: `prompt_property.owner_id` is the only record of
ownership and `data.reads` is `[]` — *"which is why `may()` takes the subject's `owner_id` and
`access_level` as parameters (ADR-0020). This is the module's central design constraint and the reason
its dependency list has one entry."* Reading it would break the forbidden edge, the constraint and the
ADR in one move.
Rejected: **an `owned_ids` parameter** the caller passes in. It is ADR-0020's shape and it is the wrong
shape here: a list endpoint has not read any rows yet, so the caller would run an ownership query
purely to feed it back in — two round trips to build one `WHERE` clause.
Consequence, stated: **AC-9's `then` clause is literally false as written** and is raised as
**`OQ-048`**, severity high, rather than absorbed. AC-9's `given` clause is *"an actor whose visibility
comes entirely from grants"* — an actor who owns nothing — which is exactly the case that makes the
impossible half vacuous, and Phase 8 asserts that case plus the row-for-row agreement that is stronger
than it.
Reversibility: **costly** — prompt-registry's repository layer is written against this from Phase 15.

The same decision settles the `ids` branch's shape: **it is one statement over `prompt_grant` with no
`IN`-list ceiling.** Return every granted id, unbounded, and expose the size as
`prope_access_control_visible_filter_ids_size` — the histogram A-118's own revisit condition is
watching. Rejected: **capping the list and falling back to `mode: all` above the cap** — a cap that
silently widens visibility turns a performance problem into a disclosure. Rejected: **paginating the
filter** — the consumer pushes this into a `WHERE`, and a paginated filter is not a filter. The honest
bound is written at the metric: at 1,000 prompts an actor granted all of them produces a
1,000-element `ANY(:ids)`, which PostgreSQL handles, and the revisit trigger is the histogram rather
than a number guessed now.

**D-122 — `mode: none` means "no grant-derived visibility", not "sees nothing", and the docstring is
where that is prevented from being misread.**
Chosen: three modes, closed, with `none` documented at the constant as *the caller still ORs its own
ownership predicate*.
Rejected: **collapsing `none` into `ids` with an empty tuple.** It is the same value and a different
statement, and INT-002 declares three modes; more to the point, a caller that treated an empty `ids`
as "return nothing" would hide a person's own prompts from them — which is the single most alarming
possible bug in this product and the one nobody would report as a permissions problem.
Reversibility: **cheap.**

One function, one value object, two metrics.

**`src/prope/access_control/domain.py` — the return type.**

```python
@dataclass(frozen=True, slots=True)
class VisibleSubjects:
    mode: VisibilityMode          # StrEnum: ALL = "all", IDS = "ids", NONE = "none"
    ids: tuple[str, ...] = ()
```

`VisibilityMode` is a `StrEnum` for `domain.py`'s stated reason: a value that is stored, transmitted
or compared is a fact and stays literal ASCII wherever it travels — and these three strings are
INT-002's declared vocabulary, so they are also the `mode` label's closed value set on the histogram
below. Frozen and slotted, and `ids` is a **tuple** rather than a list: a caller that could append to
the set it was handed is a caller that could widen its own visibility, and the type is the cheapest
place to refuse that. `__post_init__` asserts the one invariant worth asserting — `ids` is empty
unless `mode is IDS` — because a non-empty `ids` beside `mode: all` is ambiguous in exactly the
direction that widens.

**`src/prope/access_control/visibility.py` — new.**

```python
async def visible_subject_filter(session, actor: Actor, subject_type: str) -> VisibleSubjects
```

Match whatever Phase 7's `may()` takes as its first argument. `subject_type` is `"prompt"` today;
an unrecognised type returns `mode: none` and never raises, for A-115's reason applied one level up —
a typo that silently widened would be the failure the closure exists to prevent, and here the safe
failure is also the silent one, so it increments the same `unknown_*` counter family Phase 7 built if
one exists.

**The module docstring is the deliverable and it carries five paragraphs:**

1. **What the three modes mean, and specifically what `none` does not mean.** `all` — a role binding
   confers the subject type's read action at workspace scope, so the caller adds no id predicate.
   `ids` — visibility comes from grants, and these are exactly the granted ids. `none` — **no
   grant-derived visibility**, which is not the same statement as *the actor sees nothing*: the caller
   still ORs its own ownership predicate. Write that sentence out; it is the one a later reader is
   most likely to misread, and misreading it hides a person's own prompts from them.
2. **The caller's half of the contract, in the caller's own words.** The registry's query is
   `WHERE workspace_id = :ws AND (owner_id = :actor OR id = ANY(:ids))`, and this function supplies
   only the second disjunct. Cite ADR-0020: this module may not read `prompt_property`, so ownership
   is knowable only where the row is, which is the caller. Cite **`OQ-048`** by id, because AC-9's
   literal text says otherwise and a reader who notices must land on the question rather than on a
   surprise.
3. **`mode: all` is not a tenancy bypass** (INT-002, ADR-0045). It means every subject of that type
   *in the workspace*, and RLS enforces the workspace underneath regardless. A caller that dropped its
   own `workspace_id` predicate on seeing `all` would still get zero rows from another tenant, which
   is the inversion ADR-0035 is built on.
4. **Nothing is cached, by this module or by its caller** (A-114, ADR-0022). A revoked grant is
   refused on the next request; a cache is the mechanism that would make that false. This is a
   deliberate divergence from the 30-second resolution cache sitting beside it at INT-009, and the
   reason is what a stale answer costs: a stale pointer serves a previously approved revision one TTL
   late, a stale permission serves a revoked actor.
5. **Failure semantics: it raises, and no caller catches it.** A list endpoint returning 5xx is
   correct; a list endpoint returning everything is not. There is no `except` in this module in which
   an unfiltered query could be manufactured.

**The statements.** Two, at most, and each as a module-level `text(...)` constant with a `#:` block in

- `ROLE_CONFERS_ACTION` — does this actor hold any role binding in this workspace whose role has a

- `GRANTED_PROMPT_IDS` — `SELECT prompt_id FROM access.prompt_grant WHERE grantee_user_id = :actor`,

This is the lock file's own `test_ref` and the most valuable test in the plan. Its module docstring
names the failure mode that looks healthy: **two implementations of one rule.** `may()` unions role
bindings and grants per row; `visible_subject_filter` computes the same union as a set. Nothing forces
them to agree, they are written months apart in this project's timeline, and the way they diverge in
practice is that one of them is updated when a rule changes. A test that only checked the filter's
output against a fixture would pass through the divergence.

**Building the 1,000-subject population, and why it is synthetic.** `prompt_property` does not exist
until Phase 13, and `prompt_grant.prompt_id` is a **value and not a foreign key** — the lock says so
and gives the reason (a foreign key would point this module's schema at prompt-registry's table, in
the forbidden direction). So the population is 1,000 generated `prm_`-shaped ids held only by the
test, of which:

- 40 carry a `prompt_grant` row for the actor,
- a declared handful carry `owner_id = actor` in the **subject the test constructs**, standing in for
  the row a real caller would have read (ADR-0020),
- the rest are owned by somebody else and granted to nobody.

Say all of that in the docstring, including the sentence that makes it honest: **the ids are synthetic
because access-control cannot see a prompt, and that is the same reason `may()` takes the subject's
attributes as parameters.** This is not a weaker test than the real one; it is the same test with the
registry's half supplied by the caller, which is exactly the seam ADR-0020 defines.

Seed through `migrate_engine` — the owner role, subject to no policy — so a later refusal is
attributable to the code under test. Read back through `migrate_engine` too, never through the
function under test.

Six tests, matching `<behavior>` one for one. Two rules for all of them:

1. **Every set assertion is a two-directional equality that names the difference.** `assert
   set(result.ids) == expected` is not enough on 1,000 elements: use symmetric difference in the
   failure message so a red run says *which* ids, and put a positive control in each test (assert the
   expected set is non-empty before comparing) so an empty-vs-empty pass is impossible.
2. **The `may()` loop is 1,000 real calls, not a mocked one.** If that is slow enough to matter, say
   the number in the docstring rather than reducing it — the population size is AC-9's, and a test
   that quietly ran 50 would be asserting a different criterion.

**The performance smoke bound, and what it is not.** Time the `ids` branch on the 1,000-prompt
population and assert it completes under a **generous** ceiling — 1 second, not 20 milliseconds — with
a `#:` comment saying exactly why: the lock's requirement is a p95 at 50 requests/second and this is
one call on a cold container with a session-scoped PostgreSQL under a test harness, so asserting 20 ms
here would be asserting the harness. **This bound catches an accidental N+1 or a missing index and
nothing finer**, and the real measurement is routed to Phase 9's `test_plan.load` sweep. Do not let it
read as the requirement.
