<objective>
Mount the nine remaining INT-029 routes that are not grants, keys or the tombstone: the three `/auth`
routes, workspace creation, the member collection, the role assignment, and the permission matrix —
each write appending its history event in the same transaction as the change.

**Five of the module's ten events land in this plan** — `workspace_created`, `member_added`,
`member_removed`, `role_assigned`, `role_revoked` — which is half the module's output surface and the
half that makes a workspace mean anything. Every one uses the shape plan 08-01 set for
`access_granted`: the command writes its row and appends on the same session, the route owns the
transaction, and neither can exist without the other.

**This plan mounts Prope's only unauthenticated route and its only three action-free routes**, and the
mechanism that keeps those four from being an accident is a literal list, not a skipped assertion.

---

**D-126 — the three `/auth` routes declare no action, and the exemption is a literal three-entry list
asserted for exact equality.**
Chosen: `POST /auth/login`, `POST /auth/logout` and `POST /auth/password` declare no
`ManagementAction`; `tests/architecture/test_route_table.py` names them in an `ACTION_FREE_ROUTES`
constant (declared empty by plan 08-01, filled here) with the reason written beside each, and asserts
the set of action-free versioned routes is **exactly** that list. `UNAUTHENTICATED_ROUTES` gets one
entry, `POST /auth/login`, on the same terms.
Rejected: **inventing `auth.login`, `auth.logout` and `auth.password_change` vocabulary members that
every role holds.** A permission check that can never deny is theatre, and it would put three rows per
role in `role_permission` that `GET /permissions` then renders as if they were policy — on the one
endpoint whose whole purpose is that the running matrix can be compared against OQ-006's answer.
Rejected: **leaving them undeclared with no list.** That is exactly the default AC-10 forbids:
*"a route declaring none fails the test rather than defaulting to unauthenticated."* An enumerated
exemption with a written reason is not a default; a `continue` in a loop is.
The precedent is in the file already: `test_the_health_routes_are_unversioned_and_declare_nothing`
does the identical thing for `/healthz` and `/readyz` and asserts the count.
Reversibility: **cheap.**

**D-127 — `POST /workspaces` is permission-checked against the actor's current workspace, and the
bootstrap gap that leaves is stated rather than closed here.**
Chosen: `may(actor, "workspace.create", subject={type: "workspace", ...})` evaluated against the
workspace the actor's session is in, so an Admin somewhere may create another workspace and a Viewer
may not. The new workspace's id is generated by the application before the transaction opens, so the
create transaction sets its own tenant context — which is the reason the lock file gives for workspace
creation needing no `SECURITY DEFINER` function.
Rejected: **no check at all** — every authenticated person may create a workspace. Defensible, and it
declares no action, which puts a fourth route in D-126's exemption list for a route that is a *write*.
Rejected: **checking against the workspace being created.** The actor holds no binding in a workspace
that does not exist yet, so the check would be evaluated against an empty binding set and would deny
every time.
**The gap this leaves, stated out loud: the FIRST workspace and the FIRST user cannot be created
through any route in Prope.** There is no self-service sign-up (A-108, A-110), no invitation (A-071),
and this route requires a session that requires a user that requires a workspace. Phase 7 owns
identity and may already ship a bootstrap path; if it does not, **nobody owns it** and the deployment
work that owns no milestone (PITFALLS §4) is where it would land. This plan does not invent one —
inventing an unauthenticated bootstrap route would be adding Prope's second unauthenticated path
under deadline pressure — and `deferred-items.md` records it as an inherited gap with no owner.
Reversibility: **cheap** for the check; the bootstrap decision is not this plan's to make.

**D-128 — the login route ships in Phase 8 with no rate limiter, and the gap is counted rather than
hidden.**
Chosen: mount `POST /auth/login` now, calling Phase 7's sign-in. The A-144 limiter — 5 per email, 20
per source address, rolling 15 minutes, consulted **before** the user row is read and **before** any
hash is computed — is Phase 9's, and its placement rule is the whole of ADR-0043.
Rejected: **holding the route back to Phase 9.** Every other route in this phase needs a session, and
a session needs a login; the alternative is a phase whose routes can only be exercised through a test
seam, which is exactly the posture Phase 2 was stuck in and which plan 08-01 exists to end.
Rejected: **building a partial limiter here.** ADR-0043's value is *where* the limiter sits; a limiter
built after the hash is a limiter that does not bound the resource it exists to bound (46 MiB and a
core per attempt on a 4 vCPU host), and Phase 9 would move it rather than extend it.
**The consequence, written at the route and repeated in the SUMMARY:** for one phase
`POST /api/v1/auth/login` is unauthenticated and unthrottled. Same posture Phase 2 took for the
call-ledger loss window — declared, stated at the code, and closed by a named later requirement.
Reversibility: **cheap** — Phase 9 inserts a call before the first statement.

**D-128's companion clause — `PUT .../roles` is a full replacement of the actor's role set, and it emits one
`role_assigned` per added role and one `role_revoked` per removed role.**
Chosen: the body carries the complete desired role list; the command diffs it against the current
bindings and appends one event per change, all inside one transaction. No event is written for a role
that was already held.
Rejected: **a `POST`/`DELETE` pair per role.** INT-029 declares one route, `PUT`, and *"assign or
revoke; same refusal"* — one route with two verbs' worth of behaviour is what the spec describes.
Rejected: **one event per request carrying the whole new set.** `role_assigned`'s registered detail
keys are exactly `{role, grantee_user_id}` — singular — and a set-shaped payload would need an
unregistered key, which aborts the transaction (ADR-0024). The seed decides this and it decided it in
Phase 4.
Reversibility: **cheap.**

Three routes. One of them is the most security-sensitive path in the product.

**`ErrorCode` gains one member**, in `src/prope/management_api.py`:
`AUTHENTICATION_FAILED = "authentication_failed"`. Its comment is the whole of A-144 in three lines:
this **one** code answers an unknown email, a wrong password and — from Phase 9 — a rate-limited
attempt, and the response carrying it must be identical in status, body, headers and timing across all
three. A second code for any of them is the account-enumeration oracle this module closes everywhere
else.

**`POST /api/v1/auth/login`** — no session dependency, no `declares_action`. Body: `email`, `password`.
On success: call Phase 7's sign-in, set the `prope_session` cookie **HttpOnly, Secure, SameSite=Lax,
same-origin, path `/`** (ADR-0043, ADR-0052 — and note at the code that this route is the one place
those attributes are set, which is why `session_auth.SESSION_COOKIE`'s docstring says the flags are
not enforceable there), and return the session's `user_id`, `workspace_id` and
`must_change_password`. On any failure: `401` with `AUTHENTICATION_FAILED` and a fixed message.

Four things at the code, and all four are the route's reason for existing rather than commentary:

- **No branch may vary the response by cause.** Write it as a single failure path with one return, not
  as two `if`s that happen to return the same thing today.
- **A tombstoned email must be indistinguishable from one that never existed** — the lock file says
  the NULL `password_hash` case *"STILL RUNS THE HASH COMPARISON"*, so this route must not short-circuit
  on a missing user before Phase 7's service has done its work. If Phase 7's service already handles
  it, say so at the call site rather than adding a second guard.
- **The one-phase gap, at the route**: there is no rate limiter until Phase 9 (A-144, ADR-0043), so
  this endpoint is unauthenticated and unthrottled for one phase, and ADR-0043's own argument about
  46 MiB and a core per attempt on a 4 vCPU host is why that is a real exposure rather than a
  theoretical one. Name Phase 9 and A-144. Same posture Phase 2 took for its loss window: declared at
  the code, in the plan, and in the SUMMARY.
- **Nothing here is logged beyond the outcome.** No email, no password, no hash, no cookie value
  (A-046). `prope_access_control_login_total{result}` is Phase 7's or Phase 9's depending on where the
  service lives; increment whatever exists and do not create a parallel counter.

**`POST /api/v1/auth/logout`** — session required, no action declared. Deletes the session row and
clears the cookie. Its docstring carries ADR-0022 in one sentence: sessions are rows precisely so that
sign-out is effective **at once** rather than at expiry, and a self-contained token would make this
route a lie for the rest of the token's lifetime. **No history event** — the lock file is explicit that
sign-in successes and failures are not events, *"putting them here would turn the audit trail into an
access log"*, and the same argument covers sign-out.

**`POST /api/v1/auth/password`** — session required, no action declared. Body: `current_password`,
`new_password`. Changes the **caller's own** password and clears `must_change_password`. **There is no
user id anywhere in the path or the body**, and the docstring says that is the mechanism rather than
the convention: an id parameter is how this route would become a way to set somebody else's password,
and the actor comes from the session row. Requires the current password even though the session
already proves identity — say why: a session left open on a shared machine is the case this defends,
and it costs one field. No history event, same reason as logout. Refuse a wrong current password with
`AUTHENTICATION_FAILED`, the same code and shape as login, so the two paths cannot be used to
distinguish anything.

**`src/prope/session_auth.py`** — no new `ManagementAction` members in this task. Add one sentence to

`tests/architecture/test_route_table.py`'s `ACTION_FREE_ROUTES` is where they are enumerated, so a
reader of the enum finds the exemption rather than concluding the enum is incomplete.

**`src/prope/access_control/routes/__init__.py`** imports `auth` so its handlers register.
