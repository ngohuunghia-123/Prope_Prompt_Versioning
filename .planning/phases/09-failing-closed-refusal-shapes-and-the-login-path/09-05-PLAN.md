<objective>
Make *an unavailable access-control takes the whole system down safely rather than open* a fact that has
been observed, not a property everybody assumes.

The lock file states the failure mode without softening it: *"Every module fails closed, so the entire
product refuses every request, including the gateway … this is a full outage of every consuming
product's AI feature"*, and then, in the mitigation, *"the honest statement is that this module has no
degraded mode by design, because **the degraded mode of a permission oracle is called an allow.**"*
That sentence is the whole of AC-11, and the only way to hold it is to prove there is no path from an
exception to a `True`.

**D-142 — Fail-closed is a raise. A caught exception returning `False` is refused, and the ban is
symmetric.**

INT-001 says *"Fails closed by raising"*, and plan 08-06 asserted structurally that no `except` under
`src/prope/access_control/` returns something meaning allow. This plan makes the rule explicit and
widens it, and adds the half nobody states:

Chosen: on any error a check cannot evaluate, the seam increments
`prope_access_control_check_error_total`, writes one log line, and **re-raises the original exception
unchanged**. No `except` anywhere converts it to `True`, and **no `except` converts it to `False`
either**.

Rejected: **`except Exception: return False`** — the shape that looks like fail-closed and is not. It
produces the right *answer* and destroys the *signal*: `AccessControlCheckErrors` never fires, the
`check_error_total` counter the lock declares becomes unreachable, `/readyz` stays green, and a total
outage of the product presents to support as "some people say their permissions are wrong." The lock
declares `check_error_total` as *"a check that could not be evaluated"* — a counter that exists
precisely because the safe failure would otherwise be a silent one, which is the identical argument
A-115 makes for `unknown_action_total`.

Rejected: **a caller-side `try/except` that renders a 403.** A 403 says *you may not*; a database
outage means *nobody could tell*. Rendering the first for the second is a lie that survives in a
screenshot.

The consequence is deliberate and is the behaviour AC-11 asserts: an unevaluable check becomes a **5xx**
through the A-045 envelope's existing handler, and a 5xx is a refusal. Every module refuses; none
allows; the product is down; and it is visible.

Reversibility: **cheap** in code, **one-way** in incident history — an allow manufactured during an
outage has already been served.

---

**D-143 — Two provocations, because a closed port and a mid-request loss are different failures.**

The lock's `test_plan.chaos` clause 1 is *"Take the database away **mid-request**"*, and
`tests/integration/test_health_and_readiness.py` already establishes the other shape — settings pointed
at a closed port, `UNREACHABLE_DATABASE_URL`.

Chosen: both.

- **Provocation A — never reachable.** Build the application with its engine pointed at a closed port,
  in the existing `unreachable_database_app` posture. Cheap, deterministic, and it exercises the connect
  path.
- **Provocation B — taken away mid-request.** With a real request in flight, terminate its backend from
  a second connection (`pg_terminate_backend` against the session's own pid). The request is executing
  when the connection dies, which is the path a connect-time failure never reaches: a half-consumed
  result set, an `asyncpg` `ConnectionDoesNotExistError` rather than an `OSError`, and a SQLAlchemy
  engine holding a pool entry it does not yet know is dead.

Rejected: **pausing or stopping the container.** It is the most faithful provocation and the most
expensive to undo: the session-scoped `postgres_container` is shared by every test in the run, a stop
loses the schema, and a pause that outlives its `finally` hangs the rest of the suite rather than
failing it.

Rejected: **revoking `CONNECT` from `prope_app`.** Tempting because it is one statement, and it is the
mechanism plan 06-05 considered for a different provocation. Rejected here because it changes a
privilege — the exact class of state whose leak `tests/security/test_append_only_privilege.py` depends
on — and a `finally` that fails to re-grant reddens every later test in the session in a way that reads
as a privilege bug rather than as a fixture leak.

**Every provocation is reversed in a `finally`, and the reversal is asserted afterwards** with a real
query, not assumed. Say so at each one.

Reversibility: **cheap.**

Make the rule explicit in the five seams, then assert its absence across the whole project.

**The five seams — `may`, `visible_subject_filter`, `authenticate_api_key`, `may_resolve`,
`authenticate_session`.** For each, the failure path is exactly three statements and then a re-raise:

```python
except Exception:
    check_error_total.inc()           # or the seam's own error counter, see below
    logger.warning("access_control.check_failed", action=..., result="error")
    raise
```

Four rules at these sites, and each needs its sentence written once in `permissions.py` and pointed at
from the other four:

1. **`raise`, bare, not `raise SomeWrappedError(...) from e`.** A wrapped exception loses the driver's
   type, and the type is what a later reader needs to tell a connection loss from a programming error.
2. **The `except` catches `Exception`, not `BaseException`.** `CancelledError` is a `BaseException` in
   Python 3.8+ and a cancelled request is not a check error; counting it would make
   `AccessControlCheckErrors` fire on every client disconnect.
3. **The counter increments before the re-raise, not in a `finally`.** A `finally` also runs on the
   success path.
4. **`result="error"` is a log field and NOT a third value on `check_total`'s `result` label.** The lock
   declares that label as `allow | deny` — two values — and `check_error_total` is the separate counter
   the lock declares for exactly this case. Do not widen the label.

Which counter each seam uses: `may` and `visible_subject_filter` use
`prope_access_control_check_error_total` (the lock's *"a check that could not be evaluated"*).
`authenticate_api_key` already has `key_auth_total{result}` whose set is closed at three — **do not add
a fourth value**; increment `check_error_total` and say at the code why the closed set was not widened.
`authenticate_session` likewise. Write that reasoning once.

**Also assert the negative that D-142 adds**: no seam has an `except` that returns `False`. Where Phase
7 or Phase 8 left one, **fix it** and record it in the SUMMARY as a change to another phase's code with
the reason — the silent-deny argument — because an executor that finds one will otherwise leave it,
reasoning that it is already safe.

**`tests/security/test_no_except_manufactures_an_allow.py` — the project-wide walk.**

`ast`-parse every `.py` under `src/prope/` — discovery, not a list, with a vacuity guard — and for every
`ExceptHandler` node, walk its body and flag:

- a `Return` whose value is `True`, or a constant that is truthy;
- a `Return` whose value is a call to something in a small `ALLOW_SHAPED` set: anything constructing a
  `VisibleSubjects`-equivalent with `mode="all"`, and anything constructing the module's identity value
  objects (`KeyIdentity`, `Session`) — because returning an identity from an `except` is manufacturing
  an authenticated principal, which is the same failure wearing a different type;
- a `Return` whose value is `False` **inside a handler in a module under `src/prope/access_control/`** —
  D-142's second half. This one is reported as a **separate finding class** with its own message, so a
  failure says *silent deny* rather than *manufactured allow*; they are different bugs with different
  fixes and a single message would send somebody to the wrong one;
- a `pass` as the sole statement of a handler in any module under `src/prope/access_control/`.

Two exemptions, each a row in an `ALLOWED_HANDLERS` mapping with a written reason, and each asserted to
exist on disk:

- `src/prope/access_control/rate_limit.py`, if any handler there returns a bool — the limiter can only
  produce a denial and cannot produce an allow (ADR-0043, plan 09-02's module docstring).
- `src/prope/access_control/keys.py`'s `parse_presented_key`, which returns `None` — never raises — for
  a malformed presentation by plan 08-03's D-123. `None` is not an allow and the walk should not flag
  it, but the exemption is written down so a reader knows the walk considered it.

**The mutation control.** In `tmp_path`, write three synthetic modules — one whose handler returns
`True`, one whose handler returns a `Session(...)`, one whose handler returns `False` — run the checker
against each, and assert each is reported with the **right finding class**. Then a clean module that
re-raises, asserted to report nothing. Without this, the walk's silence is unfalsifiable.
