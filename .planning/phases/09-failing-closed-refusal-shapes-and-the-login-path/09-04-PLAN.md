Two criteria, one question: **what is a response allowed to contain?**

AC-7 asks it about a credential — the plaintext key appears in its creation response and nowhere else,
ever, and the stored row cannot rebuild it. AC-15 asks it about a person — no surface renders a name or
an email for someone who has been tombstoned, and the absence is rendered through a catalogue key rather
than a stored string. They are the same discipline pointed at two different values, they are both
asserted by walking the whole surface rather than by checking the model somebody remembered, and they
are both in this plan for that reason.

**AC-7's scope changes here, and that is the plan's main content.** Plan 08-03 asserted the secret's
single appearance *over the two modules that existed*, and Phase 8's `deferred-items.md` §5 routed
*"AC-7's whole-system enumeration — the secret in no other response in the system"* to this phase. The
enumeration is still bounded by which modules exist — two of eight — and the honest form is: **every
response model in the assembled OpenAPI schema, every log record, every metric label, every
`history_event` row, every column of every `access` row, and a real `pg_dump`.** That last one is the
lock file's own words in `test_plan.security` and has never been run.

---

**D-140 — A tombstoned actor renders as `null` plus a catalogue key, produced by the projection.**

Chosen: every response model that can carry an actor gains an optional `display_key: str | None`. When
the underlying `access."user"` row is tombstoned — `display_name` and `email` are NULL and `status` is
`tombstoned` — the projection sets `display_name=None`, `email=None`, `display_key=TOMBSTONED_ACTOR_KEY`.
When it is not, `display_key` is `None` and the two real fields are populated. **The rule is applied
where the row becomes a response model** — in `members.py`'s projection — and not at each route, so a
route added later inherits it.

Rejected: **returning a Vietnamese or English string like "Người dùng đã bị xoá".** ADR-0053 §1 is
explicit: *"No literal display text in a component, including error text, empty states, button labels,
and validation messages"*, and §5 puts the API on the machine-`code` side of that line — *"The client
renders the `code`, not the `message`."* A display string returned by the API is a display string in the
API, and a second locale then costs a backend deploy.

Rejected: **omitting the fields entirely and letting the client infer.** An inference is a rule in the
client, and the client is the artifact that does not exist (PITFALLS §3). `null` plus a key is a fact
the API states.

Rejected: **rendering the user id.** It is already there as `user_id`. A `display_name` falling back to
the id is a display string that happens to be an identifier, and it is exactly the shape that makes an
opaque id look resolvable.

Consequence, stated: **ADR-0053 §3 requires a CI check failing the build on a key present in the code
and absent from the `vi` catalogue.** There is no catalogue and no CI check, because the i18n layer has
no owner — PITFALLS §5 records it and Phase 8 recorded five `ErrorCode` members with the same problem,
now seven with plan 09-01's `password_change_required` and this key. **Raised as `OQ-052`**, not
absorbed, and this plan ships the key rather than the catalogue.

Reversibility: **costly** — six modules' actor renderers will be written against the field, and the SPA
(whenever it exists) keys on the value.

---

**D-141 — The catalogue key is one constant in `management_api.py`.**

Chosen: `TOMBSTONED_ACTOR_KEY = "actor.tombstoned"` beside `ErrorCode`, in the module plan 08-01 created
as *the one A-045 surface every module's routes share*.

Rejected: **a member of `ErrorCode`.** It is not an error. A refusal vocabulary that contains a
rendering hint is a vocabulary whose closure means less.

Rejected: **a constant in `access_control`.** Five other modules render actors — a prompt's owner, an
approval's reviewer, a release's releaser, an eval run's starter, a history event's actor — and each
importing it from access-control would be five modules importing a sixth for a string. `management_api`
is already the shared home and already has no module dependencies.

Rejected: **a literal at each renderer.** Six spellings, one of which will be `"actor.tombstoned "` with
a trailing space, and the catalogue check that would have caught it does not exist.

The dotted form matches ADR-0053 §3's *"The keys are English, and they are identifiers, not fallbacks"*
and §7's derivation of one key per registered history action. Reversibility: **cheap** for the location,
**costly** for the value once a catalogue exists.

**`src/prope/management_api.py` — one constant (D-141).**

```python
#: The catalogue key every actor renderer in every module returns in place of a
#: tombstoned person's name (AC-15, ADR-0053, ADR-0054).
TOMBSTONED_ACTOR_KEY = "actor.tombstoned"
```

Its comment carries four things: what it is for; that ADR-0053 §1 forbids literal display text so the
API returns a key and never a rendered string; that ADR-0053 §3 requires a CI check failing the build on
a key the `vi` catalogue does not hold, **and that no catalogue and no check exist** — PITFALLS §5, and
`OQ-052`; and that it lives here rather than in access-control because six modules render actors and
none of them should import a fifth for a string.

**The projection — in `members.py` if the read projection lives there, otherwise in
`routes/workspaces.py`.**

One function, `render_actor(row) -> ActorRead`-shaped, applied wherever a `user` row becomes a response
model:

- tombstoned (`status == "tombstoned"`, or `display_name is None and email is None` — use whichever the
  tombstone actually produces, and say which at the code): `display_name=None`, `email=None`,
  `display_key=TOMBSTONED_ACTOR_KEY`.
- otherwise: the real values, `display_key=None`.

Write at the function:

1. **It never consults history for the old value.** ADR-0054's whole claim is that inside a running
   Prope no path leads from a tombstoned `actor_id` back to a name. A projection that fell back to the
   last `member_added` event's details would be that path, and it would be added by somebody being
   helpful.
2. **The branch is on the row it was given.** No second query, no join to `history`, no lookup by id.
3. **`display_key` is `None` for a live actor rather than a key meaning "present".** A key that is
   always set is a key that stops meaning anything; the field's presence *is* the signal.
