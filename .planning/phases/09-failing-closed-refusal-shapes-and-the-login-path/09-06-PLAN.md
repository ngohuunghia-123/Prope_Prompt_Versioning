**D-144 — The two unbounded label sets get opposite answers, and both are decisions rather than
oversights.**

The lock file declares `prope_access_control_admin_count` as a gauge labelled `workspace_id` and
`prope_access_control_key_scope_refusal_total` as a counter labelled `key_id`. ADR-0030 bounds metric
label cardinality by construction, `src/prope/observability.py`'s own docstring says `workspace_id` is
*"deliberately never a label"*, and `tests/broker/test_publish_confirm_failures.py` asserts that
project-wide over the whole registry. Phase 7 shipped both as declared and stated the tension at each
metric; Phase 8 hit the same wall for `key_id` and routed the decision here rather than raising a
second open question.

**`admin_count` keeps `workspace_id`.** `AccessControlAdminCountZero` pages on
*"`prope_access_control_admin_count == 0` **for any workspace**"*, and that alert is the proof that
A-117's refusal works — the lock says so in those words: *"the gauge exists to prove the refusal is
working rather than to catch a state anyone plans to recover from."* An unlabelled gauge cannot express
*for any workspace*: a sum over workspaces is non-zero while one workspace is frozen, which is exactly
the state the alert exists for. The cardinality is bounded by the number of workspaces in a pilot-scale
single-VM deployment, and the bound is stated rather than assumed.

Consequence: `tests/broker/test_publish_confirm_failures.py`'s project-wide walk gains **one declared
exemption**, as a mapping from metric name to reason, with the alert named in the reason and the metric
asserted to exist. **The walk is not narrowed** — an exemption that is asserted is a decision; a walk
that skips a pattern is a walk somebody has stopped believing.

**`key_scope_refusal_total` drops `key_id`.** The opposite answer, for three reasons that do not apply
to `admin_count`. There is no alert on it. `key_id` is a `key_`-prefixed ULID, so the label set grows
without bound with key creations and never shrinks — worse than workspace count by the ratio of keys to
workspaces. And the per-key signal it was for is **already available**: `key_id` is in
`LOGGABLE_FIELDS` (plan 08-03 put it there with a written justification) and the lock file names it
loggable in the same sentence that names the secret as not, so *which key is being refused* is a log
query rather than a missing series. This is OQ-030's outcome applied a second time — Phase 6 dropped
`workspace_id` from `prope_property_history_rows_total` for the same reasons.

Both are raised as **`OQ-053`** against `docs/modules/access-control.lock.yml`'s
`observability_requirements.metrics` block, naming the two exact comment lines and ADR-0030. **The lock
file is not edited.**

Reversibility: **cheap** to add a label back; **costly** to remove one that has been scraped, because
the historical series does not merge.

**D-145 — The load clause runs as a bounded proxy by default and as the full ten minutes behind Phase
3's `load` marker.**

`test_plan.load` is *"50 rps of gateway authentication plus 50 management requests/sec for 10 minutes,
with no cache anywhere; assert the combined `authenticate_api_key` + `may_resolve` p95 stays under
5 ms."* Ten minutes at 100 rps is 60,000 operations and it cannot live in a suite that already costs
150 seconds.

Chosen: one file, two tests. A **default** test running a bounded operation count — enough samples for
a stable p95, sized so it finishes in a few seconds — and a **`@pytest.mark.load`** test running the
full ten minutes, selected with `-m load` and deselected otherwise. Phase 3 registered that marker in
`[tool.pytest.ini_options]` and added no `addopts`, so both are collected by default and only the
marked one is skipped by an explicit `-m "not load"`; **this plan reuses the marker and registers
nothing.**

Rejected: **only the ten-minute form.** It would be run once, by its author, and never again.

Rejected: **only the bounded form**, with the real number in a comment. `test_plan.load` is a clause
ORCHESTRATION §9a requires this phase to assert or route, and a comment is neither.

Rejected: **mocking the database to hit the throughput.** The performance requirement's condition is
*"50 rps sustained, cold — no cache exists by decision"*, and the whole number is about a real indexed
read plus a real `compare_digest`. A mocked timing measures the mock.

**What is measured, exactly:** the two seams **together**, because the lock's
`performance_requirements` row says *"authenticate_api_key + may_resolve, measured together"* — this is
one span from the raw presented key to the boolean, which is what the gateway's 50 ms budget actually
contains. Measuring them separately and adding the p95s would overstate it, and measuring only one
would understate it.

**What is not measured, and is routed:** the second half of the clause — *"the gateway's own added
latency p95 stays inside 50 ms with this module's share included rather than excluded"* — needs a
gateway. **Phase 20.** Plan 08-02 already routed the rest of `test_plan.load` here and this is where the
remainder goes on.

Reversibility: **cheap.**
