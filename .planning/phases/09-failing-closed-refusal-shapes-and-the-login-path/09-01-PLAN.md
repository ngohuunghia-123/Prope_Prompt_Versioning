<objective>
Give Prope one refusal vocabulary, decided in one function, and prove it on the thinnest real path that
exists today: the three `/prompts/{prompt_id}/grants` routes, whose subject is a prompt the module is
forbidden to read and whose visibility therefore arrives as a parameter.

**A-116's two shapes are the whole of SC1, and the difference between them carries security weight.**
Not-found when the actor cannot see the subject — which is what stops a private prompt being confirmed
to exist, and is BR-01's whole point. Forbidden **naming the missing permission** when they can — which
is what makes the product usable once someone can already see it. Phase 8 shipped the *branch* at the
grants routes (08-01, T-08-07) and said in writing that it ships the branch rather than the proof. This
plan makes it one mechanism and proves it.

---

**D-131 — The refusal is a value returned by one function, not a raise scattered across handlers.**

Chosen: `src/prope/access_control/refusals.py` exposes `refusal_for(*, visible: bool, allowed: bool,
action: str) -> ManagementRefusal | None`, and every handler in every module writes
`if (refusal := refusal_for(...)) is not None: raise refusal`. One function chooses between `404
NOT_FOUND` and `403 FORBIDDEN`, and it is the only place in `src/prope/` where either status code is
chosen for a permission outcome.

Rejected: **each handler raising its own `ManagementRefusal`.** That is what Phase 8 shipped, and it is
correct for one plan and wrong for fifteen routes across six modules. A-116's rule is a *property of
every refusal in Prope*, and a property enforced at fifteen call sites is a property that holds until
the sixteenth. The failure is not hypothetical: the natural way to write the sixteenth route is to copy
the fifteenth, and the natural mistake when the subject is *not* a prompt is to reach for 403 because
403 is the one that says something useful.

Rejected: **a FastAPI dependency that performs the check.** It would have to read the subject to know
its `owner_id` and `access_level`, which is exactly the read ADR-0020 forbids — the caller has already
read the row and passes the attributes in. A dependency would either re-read (forbidden) or take the
attributes as arguments (which a dependency cannot do without the handler supplying them, at which
point it is a function call with extra machinery).

Consequence, stated: `refusal_for` is imported by `src/prope/call_ledger/api.py`. That is
call-ledger importing an access-control symbol, and ADR-0018 says call-ledger *"exposes nothing that
needs a permission check, which is exactly why it can have no dependency on access-control."* **So it
does not import it** — call-ledger's five routes have no permission outcome to render and this plan
changes only their session dependency. Written here because the import is the tempting move and the
prohibition is easy to lose.

Reversibility: **cheap.**

---

**D-132 — When visibility is unknown, the answer is not-found. The fail-closed direction is toward
silence, not toward information.**

Chosen: `refusal_for` takes `visible` as a required keyword with no default, and every call site
supplies it from the row it read. Where a caller genuinely cannot determine visibility — the subject
was not read, or the read failed — it passes `visible=False` and gets not-found.

Rejected: **defaulting `visible=True`**, which reads as "be helpful". It inverts the non-negotiable:
the failure mode of a wrong `True` is a 403 naming a permission on a prompt the actor was never allowed
to know exists, and it is silent, because a 403 looks like the system working.

Rejected: **a third `unknown` state.** ORCHESTRATION §3 says *never zero and no fourth state* — a
refusal names what is missing rather than substituting a value — and here the honest name for
"visibility could not be determined" is already `False`. A third state would need a third response
shape, and a third response shape is a third thing an attacker can distinguish.

Reversibility: **one-way in practice.** Once a caller has shipped a `403` for an invisible subject, the
information has been disclosed and cannot be recalled.

---

**D-133 — `Session` gains `must_change_password`, and the forced-change gate is a second declared
dependency rather than a path list.**

A-110 requires a forced password change at first sign-in. Phase 8 shipped the flag's *clearing* and the
login response carrying it, and routed *"refusing every other route while it is set"* here
(`08/deferred-items.md` §5).

Chosen: `session_auth.Session` gains `must_change_password: bool`, and `session_auth` gains
`require_usable_session`, a dependency that depends on `require_session` and raises
`ManagementRefusal(403, ErrorCode.PASSWORD_CHANGE_REQUIRED)` when the flag is set. **Every management
route in every mounted module declares `require_usable_session`**; exactly two declare the bare
`require_session` — `POST /api/v1/auth/password` and `POST /api/v1/auth/logout` — and
`tests/architecture/test_route_table.py` asserts that set for exact equality in both directions.

Rejected: **a path allow-list inside `require_session`.** A route exempt because of how its path is
spelled is a route nobody can enumerate from the route table, which is the exact property AC-10 exists
to give and the exact failure ADR-0018's *"a route that appears because a file was named a certain
way"* argument names.

Rejected: **leaving `Session` at two fields and re-reading the user row in the gate.** `Session`'s
docstring argues against a field *"carrying authority"* — and `must_change_password` carries none; it
*withholds* it, which is the opposite direction and is why it is admissible where a role or a
permission set would not be. Re-reading would put a second read of `access."user"` on every management
request, on the module the lock file calls the highest read volume in the system.

Rejected: **enforcing it in the SPA.** The SPA does not exist (PITFALLS §3), and a control that lives
only in a client is not a control.

Reversibility: **cheap** for the gate; **costly** for the `Session` field, because six modules'
handlers take `Session` as a parameter and a field removed later is a signature change in all of them.

---

**D-134 — Visibility is a value the caller computes, and this module ships the rule rather than the
lookup.**

`refusals.py` also exposes `is_visible(*, actor_id: str, owner_id: str | None, access_level: str,
grant_level: str | None) -> bool` — the one place the private-by-default rule is written down: an actor
sees a subject if they own it, or hold any grant on it, or the subject's `access_level` is `workspace`
and they are an active member. Every input is a parameter. Nothing is read.

Rejected: **inlining the rule at each caller.** Six modules would each hold a copy of BR-01, and the
first one to get it wrong gets it wrong invisibly.

Rejected: **folding it into `may()`.** Phase 7's D-104 already made `may()` *visibility AND permission*
— so `may()` answers `False` for both causes and **cannot tell them apart**, which is precisely the
distinction A-116 needs. `is_visible` is the second half of that same answer, exposed separately so a
caller can ask which kind of no it received. Say that at both functions; a reader who finds only one of
them will assume the other is redundant.

`access_level`'s value set is `private | workspace` per Phase 7's D-104 / OQ-043, and an unrecognised
value behaves as `private`. This plan does not re-decide it; it cites it and fails closed the same way.

Reversibility: **cheap.**

**`src/prope/access_control/refusals.py` — new. Two functions, no I/O, no session parameter.**

```python
def is_visible(*, actor_id: str, owner_id: str | None, access_level: str,
               grant_level: str | None, is_active_member: bool) -> bool
def refusal_for(*, visible: bool, allowed: bool, action: str) -> ManagementRefusal | None
```

`is_visible` is D-134's rule, written once: `True` when `actor_id == owner_id`, or `grant_level is not
None`, or (`access_level == "workspace"` and `is_active_member`). Everything else is `False`, and an
`access_level` outside the declared set falls to `False` **by construction rather than by an `else`** —
write the comparison as an equality against the `workspace` constant, so an unrecognised value is
private without anybody having to remember to handle it. Cite Phase 7's D-104 and `OQ-043` at the
constant: the value set is declared in no document, Phase 7 adopted `private | workspace`, and this
function inherits that adoption rather than making a second one.

`refusal_for` is D-131's decision and is four lines of body and thirty of docstring, deliberately:

- `allowed` → `None`. There is no refusal.
- `not visible` → `ManagementRefusal(404, ErrorCode.NOT_FOUND, …, details=None)`.
- `visible and not allowed` → `ManagementRefusal(403, ErrorCode.FORBIDDEN, …, details={"action":
  action})`.

The docstring must say, in this order and in these words:

1. **What the not-found branch is defending.** BR-01 is one of the four non-negotiables: prompts are
   private by default, enforced as not-found and never as forbidden. A 403 on an invisible subject
   confirms it exists, and confirming existence is the whole of the leak — the survey's top adoption
   barrier is *the person whose prompt leaked finds out*, not an attacker.
2. **What the forbidden branch is buying**, because otherwise a later reader will make both branches
   not-found and think they have hardened it. Once the actor can already see the subject, hiding the
   *reason* they cannot act on it makes the product unusable and teaches people that Prope is broken.
   The lock file says exactly this: *"the second is what makes the product usable once someone can
   already see it."*
3. **The `details` asymmetry is deliberate and is the only asymmetry permitted.** `details={"action":
   …}` on the 403; `details=None` on the 404 — because a 404 that named an action would tell an
   attacker which permission was being checked, which is a smaller version of the same leak.
4. **`message` is never displayed** (ADR-0053) and is English on purpose. It may name the action on the
   403 path and must **not** name the subject id on either path.
5. **No branch here performs I/O**, and that is ADR-0020's property applied to the shape as well as to
   the decision: the caller has already read the row, so it already knows everything both branches need.

`__all__` on `src/prope/access_control/__init__.py` gains `refusal_for` and `is_visible`, beside the
five seams.

**`src/prope/access_control/routes/grants.py` — three handlers, one shape.**

Replace the two inline branches plan 08-01 wrote with the call. Each handler:

```python
refusal = refusal_for(visible=is_visible(...), allowed=await may(...), action=ManagementAction.PROMPT_CHANGE_ACCESS)
if refusal is not None:
    raise refusal
```

**Both arguments are evaluated before the branch**, unconditionally, and that is a requirement rather
than a style: a short-circuit that skips `may()` when the subject is invisible makes the two paths do
different amounts of work, which is a timing oracle on exactly the distinction A-116 exists to hide.
Write that sentence at the call site of the first handler and point at it from the other two.

The subject's `owner_id`, `access_level` and `grant_level` arrive as they do today — from the request,
per ADR-0020. Where plan 08-01 left a route with no subject attributes to pass (the module cannot read
`prompt_property`), pass what it passes today and do not invent a read. If the SPA supplies them, the
schema already says so; if the route currently treats every prompt as visible, **that is a finding**,

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an unauthenticated or under-privileged caller -> a management route | The refusal is the only thing the caller learns. Its status, its code, its `details`, its headers and its timing are all channels. |
| `Session` -> every handler in six modules | A field on `Session` is a field every handler can branch on. `must_change_password` is admissible because branching on it can only refuse. |
| a refusal path -> stdout / the metric registry | A log line that distinguishes the two refusals is the artifact a later debugging session turns into a response field. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-09-01 | Information disclosure | a 403 rendered for a subject the actor cannot see | **critical** | mitigate | D-131's single decision function, D-132's fail-closed default, and the byte-identity assertion against an id that names no row.
