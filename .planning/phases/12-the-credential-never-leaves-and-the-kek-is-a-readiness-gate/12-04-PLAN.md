**D-212 — The declared metric set is read out of the lock file, not retyped into the test.**

Chosen: `tests/architecture/test_provider_metric_surface.py` parses
`docs/modules/provider-access.lock.yml` with `yaml.safe_load`, takes
`observability_requirements.metrics`, and asserts set equality against every `prope_provider_access_*`
name in the live registry — **in both directions.** A metric the lock declares and the code does not
define fails; a metric the code defines and the lock does not declare fails too.

The file parses as YAML: the step-6 sweep normalised 31 prose scalars for exactly this reason, and
recorded that *"every earlier step's claim about this file rested on reading it rather than on loading
it."* This test is the first thing in the build to take that at its word.

Rejected: **a written-out list in the test**, which is `EXPECTED_ROUTES`' posture and is right for routes.
Routes have no second machine-readable source; metrics do. Where a real second source exists, retyping it
is how two lists come to disagree — which this project has already paid for once.

One mechanical wrinkle, written at the code: `prometheus_client` strips a trailing `_total` from a
Counter's name in `REGISTRY.collect()`, and renders a Histogram as `_bucket` / `_sum` / `_count`.
Normalise before comparing and say so, because a test that "fixes" this by loosening to a substring match
stops being an equality assertion.

Reversibility: **cheap.**

**D-213 — Three declared identifier labels, three separate answers.**

`OQ-053` is where phase 9 raised this shape and it was resolved per metric. Same method here.

| Metric | Declared labels | Decision | Reason |
|---|---|---|---|
| `credential_rejected_total` | `provider_config_id` | **Keep**, under a declared exemption | `ProviderCredentialRejected` alerts *"> 0 **for one configuration**"*. Without the label the alert cannot name the configuration, and the lock says of it: *"Without this alert the symptom is a rising fallback rate and no cause."* The cardinality is bounded by configurations, which are a handful per workspace, and it is a Counter rather than a Histogram |
| `upstream_duration_seconds` | `provider_config_id`, `upstream_model` | **Drop both** | It is a **Histogram**. Two identifier labels multiplied by the bucket count is the worst cardinality shape in the file — models alone are bounded at 200 per configuration by the lock's own performance row. No alert reads it. The two facts go on the dispatch log line, where they already belong per `log_fields` |
| `model_unavailable_total` | `provider_config_id`, `upstream_model` | **Drop both** | `ProviderModelUnavailable` alerts on `> 0` with no per-model clause, so the alert fires without them. The operator needs to know *which* model, and the lock's own `log_fields` already lists `upstream_model` — the per-model signal lives on the log line, exactly as phase 9 put the per-key signal on the log line for `key_scope_refusal_total` |

Rejected: **keeping all three because the lock declares them.** The lock declares them in a comment and
ADR-0030 bounds cardinality in a decision; where a comment and a decision disagree the decision wins, and
the per-metric reasoning is what makes that a judgement rather than a preference.

Rejected: **dropping all three for consistency.** Consistency would silence the one alert whose whole
value is naming the configuration. The lock file argues that alert harder than any other in the block.

Reversibility: **cheap now, costly after a series has been scraped** — adding a label later splits every
existing series and breaks every dashboard query written against it.

**D-214 — The cardinality walk forbids a class of name, not one name.**

`tests/broker/test_publish_confirm_failures.py::test_workspace_id_is_never_a_metric_label` walks every
metric in the registry and forbids exactly one label name. That was right when `workspace_id` was the only
identifier in the system. It is now the third phase to add a metric with an identifier-shaped label, and a
walk that forbids one name is a walk that passes for every name nobody thought of.

Chosen: replace the single name with `IDENTIFIER_LABELS`, a written-out frozenset —
`workspace_id`, `provider_config_id`, `upstream_model`, `user_id`, `api_key_id`, `prompt_id`,
`revision_id` — and a written-out `EXEMPTIONS` mapping `(metric_name, label)` to a **reason string that
names the alert requiring it**. Assert three things: no metric carries an identifier label outside the
exemptions; every exemption's metric actually exists (so an exemption cannot outlive its metric); and
every exemption's reason is non-empty. That third assertion is `GLOBAL_TABLES`' blank-reason check applied
to a different escape hatch, and it is the reason that mechanism has held.

Rejected: **a new test file.** The existing walk is where a reader looks, and two walks is two places to
add the next exemption.

Reversibility: **cheap**, and it will redden any earlier phase that added an identifier label without an
exemption — which is the point. If it does, that is a **finding**, and the fix belongs to the phase that
owns that metric, reported in the SUMMARY rather than patched here.

**D-215 — Seven alerts, each with its reason, and the two that cannot fire said out loud.**

`deploy/prometheus/rules/provider_access.rules.yml`, in `call_ledger.rules.yml`'s exact voice: a header
saying what the file is (a reviewable record of what pages a human at 3 a.m. and why), what it is not
(nothing loads it — PITFALLS §4, the deployment stack owns no milestone), what keeps it honest
(`tests/architecture/test_alert_rules.py`), and what its severity vocabulary means.

Then the seven, each with a `for`, a `severity`, and a description carrying the lock file's own argument.
And then the part this module needs that call-ledger's did not: **two of the seven cannot currently
fire, and the file says so at the rule rather than in a footnote.**

- `ProviderBatchStarved` reads `shed_total{priority="batch"}`, which is incremented **only in `worker`**
  (ADR-0046 makes the processes the priority classes), and `worker` serves no HTTP (`OQ-026`). No scraper
  reaches the series.
- `ProviderVerificationFailing` is declared as *"a spike on a **previously passing configuration**"*, and
  `verification_total`'s declared labels are `result` and `reason` — there is no configuration dimension
  to group by. The rule is written in the form that **is** expressible (a rate of
  `verification_total{result="fail"}`) with a comment saying what it cannot distinguish and citing
  `OQ-065` clause 3.

Writing a rule that cannot fire, with a comment saying it cannot fire, is better than not writing it: the
alternative is prose in a lock file where nobody notices that three of seven read series that do not
exist. That is the argument `call_ledger.rules.yml` already makes and it holds harder here.

Reversibility: **cheap.**
