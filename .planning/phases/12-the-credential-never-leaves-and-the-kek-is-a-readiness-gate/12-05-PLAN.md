**D-216 — The correctness halves gate. The timing halves are measured, reported, and gated only under the
marker.**

Chosen, following phase 9's D-145 and phase 3's D-45.2: each load clause ships as **one file with two
tests**. The default test runs a bounded version — fewer requests, shorter duration — and asserts every
**correctness** claim: the cache hit ratio, that only batch is shed, that no chunk is lost or reordered,
that interactive is not blocked. It **measures** p50, p95 and p99 and prints them, and gates on none of
them. The second test carries `@pytest.mark.load`, is skipped unless `PROPE_RUN_LOAD` is set, runs the
lock file's literal condition, and asserts the three thresholds: dispatch overhead p95 < 10 ms, cache hit
ratio > 99%, per-chunk overhead p95 < 1 ms.

Rejected: **gating the default suite on p95 < 10 ms.** The measurement here is a Windows developer host,
a testcontainer PostgreSQL over a Docker network, and a stub on loopback in the same interpreter. A
threshold that fails for the machine it ran on is a threshold somebody deletes, and a deleted threshold

Rejected: **not writing the timing assertion at all.** The lock file states three numbers and the audit in
plan 12-06 has to say something about each. A marked test that a human can run with `make load` is a
statement about the number; silence is not.

**D-217 — A deadline consumed inside Prope is `dispatch_deadline_exceeded`, `origin = prope`. `OQ-067`.**

The lock file's fifth chaos clause is *"hold the database connection open but unresponsive during a
decrypt-cache miss and assert the deadline is honoured rather than the dispatch hanging."* Honouring the
deadline is the easy half. The half worth writing down is what class comes back.

`timeout` exists in ADR-0017's set and it carries `origin = provider`, because ADR-0017's eight classes are
all descriptions of what **the provider** did. Returning `timeout` here would put a Prope-side stalled
database into `error_total{origin="provider"}`, which is the metric an operator reads to decide whether
the provider is broken — and every downstream signal (`GatewayFallbackRateHigh`, the provider alert block)
would then point at the wrong seam. **That is the same defect SC3 forbids for the KEK, one seam over**, and
the reason `origin` is a label at all.

Chosen: `dispatch_deadline_exceeded`, `origin = prope`, `fallback_eligible = True` (the caller's prompt
still needs an answer and nothing the caller did caused this), `retryable = True` (a stalled database is
transient in a way a refused address is not, so evaluation's transport-only retry is *correct* to fire).
Note that `retryable` differs from `address_refused`'s — which is exactly why the lock file keeps
`fallback_eligible` and `retryable` as separate facts rather than one bit.

Rejected: **reusing `timeout` with a second origin.** Phase 10's table maps each class to exactly one row
with one origin, and its own closure test asserts every member appears exactly once. A class carrying two
origins breaks that, and a table where one name means two things is the table the gateway branches on.

Rejected: **raising instead of returning.** D-182: `dispatch()` returns a value for every condition that is
not a caller contract violation, and a stalled database is not the caller's bug.

Consequence: the `origin = prope` count moves from **three to four** — `kek_unavailable`,
`admission_shed`, `address_refused`, `dispatch_deadline_exceeded` — and the closure assertion moves with
it, in this change, naming all four. `OQ-067` is where the underlying gap is raised: the declared closed
set has no `origin = prope` member and Prope has now needed four.

Reversibility: **costly.** Two consumer modules branch on the taxonomy.

**One measurement decision worth stating, because it is the difference between a number and a guess.**
The cache hit ratio is computed from `credential_decrypt_seconds{cache="hit"}` and `{cache="miss"}`'s own
**sample counts**, read off the registry — not from a counter the test increments. That is the number the
operator's dashboard would show, so it is the number under assertion. A test that counts its own hits
proves the test can count.

**Clause 3 — the 429 storm.** The lock's failure mode is a five-suite eval submission colliding with live
gateway traffic on one shared key, and the mitigation under ADR-0046 is the two per-process caps.

Set up **two gates in one interpreter** — an interactive one sized 4 and a batch one sized 2, standing for
`app` and `worker` — exactly as phase 11's D-192 established, with no shared object between them. Script
the stub to answer `429` with a `Retry-After` for a sustained window while continuing to accept
connections. Offer far more batch dispatches than the batch cap and a steady trickle of interactive ones.

Assert, and each of these is a claim an average could not make:

- `shed_total{priority="batch"}` moves;
- `shed_total{priority="interactive"}` stays at **zero** — every interactive dispatch that arrived was
  admitted, because ADR-0046 makes the two structurally non-contending and there is no path by which a
  batch dispatch can hold an interactive slot;
- every interactive dispatch that was admitted returned a `rate_limited` `DispatchError` with
  `origin = provider` and a `retry_after_ms` parsed from the header — the provider's 429 is the provider's,
  and it must not be confused with Prope's own shedding, which is `origin = prope`;
- `error_total{class="rate_limited", origin="provider"}` and `shed_total{priority="batch"}` are **two
  different numbers** that both moved. The failure this asserts against is an implementation that counts
  a shed as a rate-limit or the reverse, which would make the `ProviderBatchStarved` and
  `ProviderInteractiveShed` alerts read each other's signal;
- after the storm, both gates are **fully available again** — every slot released. A gate that leaks a
  slot under load is a gate that degrades permanently and the symptom appears three tests later.

Cite `OQ-064` in the docstring: SC2, INT-015 and ADR-0046 point three ways about what shedding batch
means, phase 11 adopted *interactive fails fast, batch waits to its own deadline and is shed on expiry*
(D-191), and this test asserts that adopted shape rather than re-litigating it.

**Clause 5 — the database that accepts and never answers, during a decrypt-cache miss.**

Build a second engine whose connections **accept and then stall** — the simplest honest mechanism is a
`SQLAlchemy` event hook, or a wrapper session whose `execute` awaits an `asyncio.Event` that is never set
(`loop.add_signal_handler` is unimplemented on Windows, so every stop path in this repository is a
settable `asyncio.Event` and this is the same idiom used the other way round). Say in the docstring which
mechanism you used and why it is a stall rather than a refusal: a refused connection is a different
failure with a different class, and the clause is specifically about a connection that **is** open.

Ensure the cache is **cold** for the configuration under test, so the dispatch takes the miss path and
therefore reaches the database. Dispatch with `deadline_ms` set to something small and measurable — 250 ms
— and assert:

- the call **returns** within `deadline_ms` plus a stated margin, measured on `time.perf_counter`. Write
  the margin as a named constant with its reasoning, and make it generous: this is asserting *not a hang*,
