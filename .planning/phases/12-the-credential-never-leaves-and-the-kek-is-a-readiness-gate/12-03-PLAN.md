<objective>
Make losing the key unmistakable.

The lock file's first failure mode is the module's worst one and it says exactly what the mitigation is:
*"Fail loudly and specifically rather than degrading into what looks like a provider outage — a distinct
gauge, a distinct page, and /readyz withheld so an orchestrator does not route traffic to a process that
cannot serve any of it."* AC-12 turns that into four clauses, and SC3 restates them: **readiness is
withheld, the KEK gauge reads 1, the dispatch failure class is distinct from every provider-origin class,
and no log line suggests a provider outage.**

The fourth clause is the one that needs work before it can be a test at all. *"No log line suggests a
provider outage"* is a statement about a **resemblance**, and a resemblance is not assertable. D-210 turns
it into four mechanical claims.

---

**D-208 — `/readyz` gains the KEK check, and this reverses a docstring that says it is final.**

`src/prope/app.py`'s `readyz` opens with *"The database alone. **This is its final form** (D-16,
INT-030)."* That sentence was true of phases 2 and 3, and it is not true of M4.
`docs/modules/provider-access.lock.yml` `apis.exposes` says *"`GET /readyz` — ready only when the
key-encryption key is available and the database is reachable"*, and `deployment_target` says
*"`/readyz` remains gated on KEK availability as well as the database — **the one readiness check in
Prope that is not purely about PostgreSQL**."* The lock file is authority 1 (ORCHESTRATION §1) and
`app.py`'s docstring is code. So the check is added and **the docstring is amended to name the reversal**
rather than quietly losing the word "final" — a reader who remembers the old sentence must find out here
why it changed, and the reason is a lock file line rather than a preference.

This is not an OQ: there is no conflict between two authorities, only between an authority and a
docstring written before the authority's module was built.

Chosen shape: `checks: ["database", "kek"]` on the 200, and `failed_check: "database"` **or**
`failed_check: "kek"` on the 503 — the existing single-name field, not a list, because the existing body
shape is INT-030's and a client reading `failed_check` should not have to learn a new type. The database
is checked first; if it fails, that is the named check and the key ring is not consulted, because a
process that cannot reach PostgreSQL is unready for a reason the operator can act on immediately.

**A provider being unreachable changes nothing here.** The lock says it twice, and the reason is blast
radius: readiness that cascades converts one module's outage into every module's on a host with no HA.

Reversibility: **costly.** A compose healthcheck and an orchestrator read this endpoint, and a readiness
answer that gets stricter can take a working deployment out of service.

---

**D-209 — A process with no usable KEK boots, sets the gauge, and withholds readiness. It does not exit.**

Chosen: the lifespan evaluates the ring once at startup, sets
`prope_provider_access_kek_unavailable` to 0 or 1, logs one record at `error` level naming the missing
version, and **carries on**. `worker` does the same in its own startup path, because it dispatches too
and has no `/readyz` to speak through.

Rejected: **refusing to start.** It is the instinct — a process that cannot decrypt anything is useless,
so fail fast — and it is wrong here for a specific reason. `ProviderKekUnavailable` pages on the **gauge**,
and a gauge that is never exported because the process died at import is a page that never fires. The
operator's first signal becomes a restart loop in `docker ps`, which is the same symptom as a bad image,
a bad database URL, or an OOM. The whole point of this failure mode is that it must not be confused with
something else. A booted process that answers `/healthz` 200, `/readyz` 503 with `failed_check: "kek"`,
and exports `kek_unavailable = 1` says exactly one thing and says it three ways.

Rejected: **checking lazily at first dispatch only.** The lock's own analysis says the realistic trigger
is *"a deploy that loses or truncates `.env`"*, and a deploy whose breakage is invisible until the first
customer request is a deploy that looks successful.

Reversibility: **cheap.** One branch in each lifespan.

---

**D-210 — "No log line suggests a provider outage" becomes four mechanical claims.**

Chosen, asserted together on a KEK-unavailable dispatch:

1. **`prope_provider_access_error_total{origin="provider"}` does not move**, and
   `{class="kek_unavailable", origin="prope"}` moves by exactly one. This is the machine-readable form of
   the claim and it is the one an operator's dashboard actually reads.
2. **Zero captured log records carry `origin="provider"`**, and zero carry any of the upstream fields —
   `upstream_status`, `upstream_duration_ms`, `error_class` with a provider-origin value.
3. **Zero captured records contain any word from a closed provider-outage vocabulary**, fixed in the test
   as a literal tuple: `upstream`, `provider_error`, `unavailable`, `unreachable`, `timeout`, `502`,
   `503`, `gateway`. Written out rather than derived, in `EXPECTED_ROUTES`' posture, so a new word that
   should be on the list is a deliberate addition.
4. **The stub's request counter is zero.** No provider was contacted, so any sentence about a provider is
   a sentence about something that did not happen. This is the clause that makes the other three more
   than stylistic.

Rejected: **asserting the log message string equals a fixed value.** It couples the test to prose and
passes the moment somebody rewrites the message, which is the opposite of what the clause protects.

Reversibility: **cheap.**

---

**D-211 — The gauge is restorable, and the cache window is stated rather than closed.**

Two properties that only look like details until somebody debugs an incident.

**The gauge goes back down.** A gauge that latches at 1 is a gauge that pages forever after a five-minute
outage, and a gauge that pages forever gets silenced. The chaos test restores the key and asserts the
gauge returns to 0 and `/readyz` returns to 200, with no restart.

**A credential already decrypted keeps working for up to 60 s after the key is removed, and that is
correct.** A-092 and ADR-0012's shape make the cache *expire*, never be invalidated; nothing tells it
anything. So the observable sequence after a KEK is pulled is: readiness withheld **immediately**, and
dispatches continuing to succeed for the remainder of each entry's TTL before failing with
`kek_unavailable`. That is graceful degradation with the orchestrator already told to stop sending work,
and it is written down here because otherwise it is discovered as an intermittent test.

The consequence for the chaos test is that the dispatch half must run against a **cold** cache — a
configuration not yet dispatched, or an entry whose TTL the injected clock has advanced past — and the
test says which it used and why.

Reversibility: **cheap** for the gauge; the cache behaviour is A-092 and is not this plan's to change.

---

**Two things this plan finds and routes rather than absorbs — `OQ-068`.**

1. **`worker` cannot withhold readiness.** It serves no HTTP (D-17, from ADR-0028) and it dispatches batch
   traffic. A `worker` with no KEK keeps claiming eval runs it cannot serve, fails every case, and the
   only signal is a gauge in a registry nothing scrapes (`OQ-026`). The lock's mitigation — *"/readyz
   withheld so an orchestrator does not route traffic to a process that cannot serve any of it"* — is
   therefore true of half the deployment.
2. **The lock says both KEK triggers fail at start-up. One of them cannot.** *"a `kek_version` in a row
   with no matching entry present (A-135) — both of which fail at start-up rather than at first dispatch,
   because the KEK is read once when settings load."* A missing `.env` entry does fail at start-up. A
   **row** naming a version the ring does not hold is a property of a row, and nothing at start-up reads
   rows — discovering it would mean scanning every credential in every workspace at boot. So it fails at
   first use, which this plan implements and asserts, and the prose is inaccurate rather than the code
   being wrong.

Give the ring a question that costs nothing to ask, and ask it in both processes at startup.

**`keyring.py` — `def wrapping_key_available(self) -> bool`.**

It answers one thing: *can this ring produce the key that would wrap a new data key right now?* Under
A-135 that is the **highest present** `PROPE_KEK_V<n>` slot, so the implementation is: find the highest
declared slot that is populated, decode it, check it is the right length for AES-256 (32 bytes), and
return `True`. Any failure — no slot populated, a slot that is not valid base64, a slot of the wrong
length — returns `False`.

Three properties written at the function, because each is a way this goes wrong:

- **It never raises.** `/readyz` is polled; a readiness check that raises is a 500 where a 503 was meant,
  and the compose healthcheck reads the status code.
- **It never touches the database and never decrypts.** It is asked on every poll. A check that decrypts
  costs a KEK operation per poll and can fail for a reason other than the one it names, which turns a
  precise signal into a vague one.
- **It never logs, returns, or renders the key material.** It returns a bool. ADR-0032's line about
  nothing reading the environment wholesale into a log line belongs at this function, because this is the
  function most likely to want to be helpful about *which* slot is wrong. It may name the **version
  number**; it may never name a byte.

Add a companion `def missing_wrapping_version(self) -> int | None` returning the version number that
**would** have wrapped, for the one startup log record — a number, never a value.

**The gauge, at startup, in both processes.** In `app.py`'s `lifespan` and in `worker.py`'s startup path:
build the ring (or read the installed one), call `wrapping_key_available()`, set
`prope_provider_access_kek_unavailable` to `0` or `1`, and on `1` emit exactly one `log.error` record —
event name `provider_access.kek_unavailable`, carrying the missing version number and nothing else. Then
**continue** (D-209). Write at the branch the sentence: *a process that exits here cannot export the gauge
the page reads, so the operator's first signal becomes a restart loop that looks like four other faults.*

Put the constructed ring on `app.state` in `app.py` so `/readyz` reads the ring the process is actually
using rather than constructing a second one from the same settings — two rings is two answers.

**`tests/unit/test_key_ring_availability.py`** — the question as a table, no container needed:

- every slot empty → `False`, and `missing_wrapping_version()` returns the highest declared version;
- only V1 populated → `True`, and the wrapping version is 1;
- V1 and V2 populated → `True`, wrapping version 2 (A-135's highest-present rule, asserted as behaviour
  rather than read from a comment);
- the highest slot populated with a value that is not valid base64 → `False`;
- the highest slot populated with a 16-byte key → `False`, because AES-256 needs 32 and a short key is a
  silent downgrade rather than an error;
- `wrapping_key_available()` **never raises**, asserted by driving every one of the above through a
  `try/except Exception` that fails the test if anything is caught;
- the KEK's own bytes appear in **zero** log records emitted during any of the above, asserted with plan
  12-02's `forbidden_renderings`.
