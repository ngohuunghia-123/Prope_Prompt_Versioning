# Interim report: improvement-agent-scope-and-differentiation

**Locus question:** If auto-improvement agents are already shipping in funded competitors and generic optimization measurably overfits or harms specific applications, what should this platform's agent actually do?
**Flavor:** dialectical

## What the corpus already said

The referent problem statement (`research/runs/prompt-asset-register-solution-4fbe59/query.md`) mandates an agent that "tự đề xuất cải tiến" (automatically proposes improvements) and "chạy eval so sánh phiên bản mới với cũ trước khi phát hành" (runs comparison evals before release), under a hard HITL-approval constraint. The product's own committed positioning, recorded in the same file, explicitly anti-positions against leading with "an AI agent that suggests prompt improvements," naming it "already commoditized by Braintrust Loop, PromptLayer, Bedrock." The positioning instead leads with three pillars: (1) ingest-and-map the existing chaos (code/Sheets/Notion/Drive/chat exports → clustered near-duplicates → state-of-the-world map), (2) cost as a binding promotion gate, (3) a two-minute evidence card for the HITL approver. This locus exists precisely because the problem statement and the positioning are in tension, and my job is to find the agent scope that satisfies the mandate's letter without competing on the commodity feature.

## What the new sources say

**`251213598` — Textual Gradients are a Flawed Metaphor for Automatic Prompt Optimization.** Only the arXiv abstract page was available in the corpus (no full-text HTML or PDF extraction was fetched for this locus investigation — an audited absence; the argument below is necessarily abstract-level). The abstract states the paper investigates "textual gradient methods" — the dominant self-reflection/critique-and-rewrite paradigm behind most LLM-driven auto-prompt-optimizers — "through a series of experiments and case studies," and finds: "While such methods often result in a performance improvement, our experiments suggest that the gradient analogy does not accurately explain their behavior." The load-bearing claim for this locus is narrow but important: these methods often *do* improve scores, but the causal story usually attached to them ("the model computed a gradient-like correction from the failure") is not what is actually happening mechanically. This matters for agent design because it means the "reasoning" an auto-improve agent attaches to a proposed edit is not a trustworthy explanation of why the edit works — it is a post-hoc narrative, not a derivation. [[251213598-textual-gradients-are-a-flawed-metaphor-for-automatic-prompt-optimizat]]

**`260122025` / full-text `when-better-prompts-hurt...` — When Generic Prompt Improvements Hurt.** This is the load-bearing quantitative source. The abstract (v2, expanded 30-case suites) reports: "generic prompt additions do not produce monotonic improvements: stronger output-contract prompts improve strict extraction for both models, while RAG citation/content-compliance declines under some generic-rule conditions. The largest observed decline occurs for Qwen 2.5 on RAG when generic rules are appended to the user prompt, from 26/30 to 9/30" — an absolute drop from 86.7% to 30% pass rate, a **56.7 percentage-point collapse**, from adding generic "be helpful, be comprehensive" rules to an otherwise-working RAG prompt.

The fuller v1 experimental account (15–20 cases/suite) gives the mechanism in detail. Baseline (task-specific) vs. "improved" (generic wrapper + generic rules) pass rates: Extraction 100%→90% (Llama 3), RAG 93.3%→80% (Llama 3, −13.3pp) and 93.3%→86.7% (Qwen 2.5, −6.7pp); Instruction-following *improved*, +13.3pp (Llama 3) and +6.7pp (Qwen 2.5). A four-condition ablation (baseline / +wrapper / +rules-in-user-prompt / full-improved) isolates the mechanism precisely: "adding the system wrapper alone (A→B) has no effect — all metrics remain identical. Adding generic rules to the user prompt (B→C) causes extraction degradation in Llama 3 (100%→90%)... RAG performance degrades across both models when the full improved prompt is used, confirming that generic 'helpfulness' pressures conflict with grounding requirements." The failure mode is concrete: "The improved prompt's instruction to 'be helpful' and 'provide comprehensive answers' encouraged the models to hallucinate information not present in the source documents, failing the 'correct but unsupported' check." The paper's own limitations section flags this as "existence proofs (generic prompts *can* hurt) rather than universal quantitative claims" — small synthetic suites (15–30 cases), two local 7–8B quantized models, deterministic decoding only — so the exact percentages should not be treated as universal constants, but the qualitative mechanism (generic instruction-conflict degrading task-specific constraints) is architecture-agnostic reasoning, not a model-specific artifact. [[260122025-when-generic-prompt-improvements-hurt-evaluation-driven-iteration-for]] [[when-better-prompts-hurt-evaluation-driven-iteration-for-llm-applications-a-fram]]

**`loop-agent-braintrust` — the closest shipped competitor capability, mechanism only.** Loop's prompt-optimization path is explicitly annotation-triggered, not raw-production-traffic-gradient-triggered: "After adding thumbs up/down reactions or free text annotations to playground outputs, select Optimize to open Loop with your annotations as context. Loop receives your annotations alongside the playground outputs and can suggest prompt improvements to address issues you've flagged." Loop *can* pull from production logs as context ("Create a dataset from logs with errors," "Build a dataset from high-scoring examples," "Find similar traces") — so it is not blind to real traffic — but the optimize step itself fires on human-curated annotations of selected outputs, not an unsupervised sweep of the full production distribution. Consequential actions are additionally confirmation-gated: "Tagging an environment affects every consumer that loads the dataset by environment, including production evals and automations, so Loop asks for confirmation before applying a tag unless auto-accept is enabled." **Answer to the critical question:** Loop grounds optimization in human-annotated *samples* of real outputs (playground annotations, optionally log-derived datasets), not in a static synthetic benchmark — this partially blunts the overfitting critique (it's not memorizing an arbitrary benchmark) but does not fully blunt it either, because the annotated sample is a human-curated subset, not systematic coverage of the traffic distribution, and there is no documented automatic regression-suite gate before a suggestion reaches the user. [[loop-agent-braintrust]]

**`how-we-built-open-source-automated-prompt-optimization` (Evidently) — implementer's honest account.** Evidently's overfitting mitigation is a classic ML train/val/test split, stated as design intent rather than measured generalization gap: "we apply a classic machine learning approach, where the labeled dataset is split into train, validation, and test subsets (by default, 40% train, 40% validation, and 20% test — all configurable). Prompts are optimized on the training set and evaluated on the validation set. The best-performing prompt is selected based on validation performance, and the final score is reported on a held-out test set. This ensures that even if a prompt overfits the training examples, it will fail on validation and be discarded — giving much higher confidence in the final optimized prompt." Separately, overfitting is fought at the generation step itself, baked directly into the optimizer's own prompt template: *"Please update my prompt to improve LLM quality. Generalize examples to not overfit on them."* Two audited absences worth flagging explicitly: (1) despite the brief mentioning a "5–20% train/test accuracy gap" as an expected finding, **this piece reports no such number** — it asserts the split *prevents* overfitting by construction but never quantifies a residual gap on real deployments; (2) the claim "often just 5-10 examples are enough" is asserted, not benchmarked against the split sizes described a paragraph earlier. Both read as an implementer's confidence in a design pattern, not an empirically verified generalization result. [[how-we-built-open-source-automated-prompt-optimization]]

**`rubber-stamp-reviews-minware` — reviewer-overload mechanism (transferred from code review, not prompt-specific).** Root causes: "Incentives to approve quickly rather than thoroughly," "PRs too large or unclear to reasonably review in one sitting," "Lack of team norms around what a good review looks like." Warning signs: "PRs approved within minutes of being opened," "Repetitive 'LGTM' or 'Looks good' comments with no substance," "Reviewers frequently approving code they have not read." The prevention playbook is directly transferable: "Break down large PRs to make review manageable," "Use checklists or rubrics to guide reviewers," and track leading indicators ("Thorough Review Rate," "Review Latency" — "Very short latency combined with fast approvals may indicate reviews are not happening at all"). [[rubber-stamp-reviews-minware]]

## Evidence synthesis

The dominant self-reflection/"textual gradient" paradigm behind most auto-prompt-optimization tooling (a) often improves scores but for reasons the "gradient" story does not actually explain (`251213598`), and (b) when applied generically rather than task-specifically, can produce large, silent regressions on the exact dimensions an enterprise prompt registry is supposed to protect — citation/grounding compliance dropped 56.7 points in one condition, and 13.3 points in the more conservative reproducible experiment, purely from adding conventional-wisdom "be helpful and comprehensive" language (`260122025`). Crucially, the same paper shows the harm is *not* uniform across dimensions: the identical generic edit that wrecks RAG grounding *improves* instruction-following by 6.7–13.3 points. There is no single scalar "better prompt" — improvement is dimension- and task-specific, which is exactly why a generic proposal engine cannot be trusted to self-certify its own suggestions; only a task-specific eval suite run against the *specific* production application can.

Both shipped/documented competitor mechanisms studied here already build in some form of this discipline, which undercuts the idea that "proposes improvements" is a differentiator worth competing on directly. Braintrust Loop requires a human annotation step before it will generate a suggestion, and confirmation before consequential promotion. Evidently gates prompt *selection* (not raw training performance) behind a held-out validation split, and additionally instructs the generating LLM to explicitly avoid overfitting language in its own optimization prompt. Neither source reports what happens if a team skips these gates — but both treat the gate as load-bearing, not optional, which itself is evidence that the raw "auto-propose" capability is considered risky enough by its own implementers to require wrapping, not a capability that can be shipped bare.

The reviewer-overload evidence, while sourced from general code-review practice rather than prompt review specifically, maps cleanly onto the problem statement's mandatory-HITL constraint. The same root causes ("PRs too large or unclear to reasonably review in one sitting," fast approval as a red flag for un-reviewed changes) apply directly to a queue of LLM-generated prompt-edit proposals: if an agent proposes edits at any meaningful cadence without a strict per-item evidence discipline, the "mandatory HITL approval to promote a version to production" constraint from the original problem statement degrades from a real control into exactly the rubber-stamp failure mode the corpus documents — fast, low-information approvals that provide no actual quality guarantee. This is the strongest argument in this locus: the problem statement's own hard constraint (HITL, RBAC, regression eval, cost alerts) is *self-undermining* if the improvement agent is not rate- and evidence-disciplined, independent of any competitive-differentiation argument.

### Position A: the agent should still generatively propose prompt rewrites (satisfy the literal mandate; treat commoditization as a reason to match, not avoid, the feature)

The strongest case for this reading is that the problem statement is explicit and specific — "agent hỗ trợ tạo/sửa/versioning prompt, tự đề xuất cải tiến" is not vague, and users evaluating the platform (VinUni AI20K judges, or eventual internal buyers) may simply check for the feature's presence. Loop and Evidently both demonstrate the capability is buildable with known-good discipline (annotation-gating, train/val/test splitting) — the corpus does not show the feature is impossible to do responsibly, only that it is risky *when ungated*. If competitors already ship it, omitting it entirely creates a checkbox gap regardless of how well-reasoned the anti-positioning is.

### Position B: the agent should not generatively propose edits at all; it should ingest/map and synthesize evidence, leaving edit authorship to humans

The strongest case here is the quantitative harm evidence itself: `260122025`'s ablation shows that even a *conservative*, well-intentioned generic improvement (not an adversarial or careless one) collapsed RAG grounding by double digits to over 50 points depending on suite size, and the harm is dimension-specific in a way that makes "propose an improvement" underspecified as a request — improved *relative to what objective*? Combined with `251213598`'s finding that the causal story attached to auto-generated edits ("gradient-based correction") is not reliable, an agent that proposes edits is asking a human approver to trust both an unreliable causal narrative and an unvalidated generic quality judgment, which is precisely the setup that produces rubber-stamping under `rubber-stamp-reviews-minware`'s documented root causes ("PRs too large or unclear to reasonably review," fast approval as a red flag). The product's own anti-positioning already concedes this feature is commoditized — competing head-on with better-funded Loop/PromptLayer/Bedrock on generative quality is a losing allocation of a small hackathon team's build time regardless of the risk argument.

## Committed position

The agent's defensible job is a **rate-limited, eval-gated exception reporter**, not a generative rewriter — and the literal mandate ("tự đề xuất cải tiến") should be satisfied by narrowing what "propose" means rather than by dropping the capability, because dropping it fails the problem statement outright while shipping it unguarded fails the evidence. Concretely: (1) the primary, differentiating agent capability is ingestion and state-of-the-world mapping — scanning code/Sheets/Notion/Drive/chat exports, extracting and clustering near-duplicate prompts into a map — because no source in this locus shows any competitor (Loop, Evidently, PromptLayer, Bedrock) doing this, and it is the actual bottleneck named first in the original Vietnamese problem statement ("Prompt... nằm rải rác trong code, Google Sheet, Notion"). (2) The improvement-proposal function should be demoted to a narrow trigger condition: it fires only for a prompt that already has a task-specific regression-eval suite (bootstrapped from that prompt's own production traffic, per the product's supporting USP — not a generic benchmark), only when a failure cluster or cost/latency signal crosses a defined threshold, and every candidate it generates must be pre-validated against a held-out slice of that same task-specific suite (mirroring Evidently's train/val/test discipline, not just training-set accuracy) before a human ever sees it. (3) What the human actually reviews is not a raw diff with an LLM's self-narrated rationale — the textual-gradient evidence says that narrative is not reliable — but the evidence card: consequence-language diff, task-specific eval delta (not a generic quality score), cost/token delta, blast radius, and a recommendation. This is simultaneously the mechanism that satisfies the problem statement's "eval hồi quy để đảm bảo không giảm chất lượng" and "cảnh báo thay đổi làm tăng token/chi phí" constraints and the mechanism that keeps the mandatory HITL gate from decaying into the rubber-stamp failure mode. (4) Rate discipline should be explicit and enforced, not aspirational: cap proposals per prompt per review cycle (e.g., at most one active candidate per prompt awaiting a decision at a time — never a batch of variants), and never admit a candidate to the approval queue unless it already cleared the machine-side regression gate on the task-specific suite; this is the direct transfer of the rubber-stamp literature's core prescription ("break down large PRs to make review manageable," "use checklists or rubrics") into prompt-change review.

- **Position:** The agent should not ship as a free-running "suggest improvements" generator; it should ship as (a) an ingestion/mapping agent as the lead differentiator and (b) a rate-capped, eval-pre-validated exception-report generator whose sole output to a human is an evidence card, not a raw candidate edit with a self-narrated rationale — this satisfies the problem statement's literal requirement while avoiding both the commodity-feature trap and the demonstrated overfitting/regression risk.
- **Confidence:** medium-high. The harm-of-generic-optimization evidence is quantified and mechanistically explained via a clean ablation (`260122025`), but is drawn from one paper, two small local 7–8B models, and synthetic suites of 15–30 cases per condition — the paper itself calls its findings "existence proofs... rather than universal quantitative claims." The competitor-mechanism evidence (Loop, Evidently) is vendor documentation, appropriately used here for mechanism only, not comparative superiority. The textual-gradients critique is abstract-only (full text not fetched in this pass), so its argument is taken at the level the abstract states it, not verified against the paper's actual experiments.
- **Boundary conditions:** This position holds most strongly for tasks with a clear, checkable task-specific contract (structured extraction, RAG grounding/citation, agentic tool-use) — exactly the domains `260122025` tested and where generic instruction-conflict was shown to bite. It is weaker evidence for purely open-ended/creative prompt tasks where "generic improvement" may not conflict with any hard constraint, and the paper explicitly scopes itself to "text-in, text-out... single-model systems," not complex multi-agent orchestrations. Outside these conditions — e.g., a low-stakes, cosmetic formatting fix to a prompt with no existing eval suite — the case for this much gating is weaker, and a lighter-weight, still-logged suggestion flow may be acceptable.
- **What would change this position:** A large-N, multi-model, production-scale study showing that generic/self-reflection-based auto-improvement loops reliably hold or improve task-specific eval metrics without task-specific gating (e.g., >90% of the time across varied application types) would undercut the case for this much restriction. Separately, direct evidence (not currently in this corpus) that Braintrust Loop or a comparable competitor performs *unsupervised* optimization against raw production traffic with automatic regression-gated promotion — rather than the annotation-triggered, confirmation-gated flow documented here — would mean the commoditized feature is more capable than assumed, and the differentiation argument (though not the overfitting-risk argument) would need revisiting.
- **Evidence weight:** 1 empirical ablation study with a clear causal mechanism and concrete effect sizes supports restricting/gating generic proposals (`260122025`, both v1 detailed and v2 abstract); 1 abstract-level theoretical critique supports distrust of auto-generated rationales for edits (`251213598`, not independently verified against its own experiments in this pass); 2 vendor/implementer sources describe gating patterns consistent with this position but do not themselves argue for it (`loop-agent-braintrust`, `how-we-built-open-source-automated-prompt-optimization` — both report design intent, not measured outcomes); 1 adjacent-domain source supports the reviewer-overload mechanism by analogy, not direct prompt-registry data (`rubber-stamp-reviews-minware`). No source in this set directly contradicts the position; the main risk to calibration is that all quantitative harm evidence comes from a single paper.

## Open questions

- The full text of `251213598` (Textual Gradients are a Flawed Metaphor) was not available in the corpus beyond the arXiv abstract page — its actual case studies and experiments (which the abstract references but does not summarize) could meaningfully sharpen or complicate the "unreliable rationale" argument. Worth a follow-up fetch of the PDF/HTML if this locus gets more budget.
- No source in this locus reports what happens when Loop's or Evidently's gating is *bypassed* or fails (e.g., a documented incident of a Loop-suggested prompt regressing in production) — this would be strong corroborating or disconfirming evidence and does not appear to exist in the corpus as currently fetched.
- The 5–20% train/test accuracy gap the task brief expected from the Evidently piece was not found; it may exist in a different Evidently source (e.g., their LLM judge optimization case study, referenced but not fetched here) or may simply not be a number Evidently has published — this is an audited absence worth flagging to the orchestrator rather than treating as resolved.
- No source here quantifies an appropriate numeric rate cap (e.g., "no more than N proposals per prompt per week") — the "at most one active candidate per prompt at a time" recommendation above is inferred from the rubber-stamp literature's general "break down large batches" principle, not from a prompt-registry-specific study, and should be treated as a reasoned default rather than an evidence-backed number.
