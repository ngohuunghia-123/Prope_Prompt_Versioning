# Interim report: registry-decay-design-lessons

**Locus question:** Which specific schema and workflow choices separate a prompt register that stays current from one that repeats the CMDB / data-catalog / feature-store decay pattern — and does the founding premise of scattered, duplicated prompts actually hold when measured?

**Flavor:** dialectical

## What the corpus already said

The width corpus already assembled the vendor-side skeleton for a prompt register (owner, version, approval, RBAC, retirement) via sources like `centralized-prompt-management-for-enterprise-2026-framework`, `prompt-governance-is-the-new-data-governance-cio`, and `enterprise-ai-prompt-management-protect-organizational-ai-knowledge`, but — per the loci brief — none of these specify *how* the register avoids going stale operationally. The adjacent-domain sources named as this locus's priority reading (MLflow, CMDB, data catalogs, feature stores, IAS 38) were fetched but not yet synthesized into concrete rules before this investigation. This note reads those five bodies in full and one additional accounting source to close that gap.

## What the new sources say

**1. MLflow's RFC on deprecating model registry stages** [rfc-deprecating-model-registry-stages-issue-10336-mlflowmlflow-github]. MLflow's original registry enforced four fixed lifecycle stages: "Users can transition model versions through four fixed stages (from none, to staging, to production, and then to archived)." The RFC states plainly: "Over the years, we've received extensive feedback on the inflexibility of model registry stages." The replacement is not a richer enum — it is a decomposition into three orthogonal mechanisms: (a) **tags**, free-key/value annotations for status ("apply a tag of key validation_status and value pending... then update the tag value to passed"); (b) **aliases**, reassignable named pointers where "more than one alias can be applied to any given model version" and reassignment happens "via the UI and client API alike, thereby decoupling model deployment from the production system code"; and (c) **separate registered models per environment** for ACL/environment separation ("create separate registered models... dev.ml_team.revenue_forecasting, staging.ml_team.revenue_forecasting, and prod.ml_team.revenue_forecasting"). The load-bearing design lesson: a single global fixed-stage enum cannot express every team's actual lifecycle, so MLflow split "what environment is this in" (ACL/separate object), "is this the one currently serving traffic" (alias, mutated by an explicit promote/copy action), and "what is its review status" (freeform tag, informational only, never gates routing) into three separate fields with three separate staleness tolerances.

**2. CMDB vs. Asset Management (Cloudaware)** [cmdb-vs-asset-management-differences-and-why-you-need-both]. This is vendor content (a CMDB company) but its central mechanism claim is specific and reusable: two systems (or two fields) that both claim to own the same attribute will rot. "When teams try to fold one into the other, two things tend to happen: ITAM fields go stale because no one updates them inside an operational tool, or CMDB relationships go stale because no one re-maps them inside an asset register." Their own audit finding: "the single most common finding is exactly this: two systems exist, but neither one is being trusted, because they disagree on the basics — and no one has decided which one wins on which field. The fix is rarely a new tool. It's a one-page 'who owns which column' agreement between IT operations, finance and procurement." A second, more concrete decay-timeline claim (also vendor-sourced, treat as directional not measured): pairing a CMDB with a live discovery source is necessary "or your CIs will be stale within two release cycles" — the only quantified staleness window in the corpus for this mechanism, and it should be flagged as vendor assertion, not a study finding.

**3–5. Data catalog failure sources** [why-do-data-catalogue-projects-fail], [data-catalogs-are-dead-long-live-data-discovery], [3-data-catalog-pitfalls-to-avoid-for-successful-governance]. These converge on the **entry-ticket / expert-dependency mechanism**, but split on the fix. The failure diagnosis is consistent: "the 'entry ticket' remains too high... current systems still require understanding data vocabulary, navigating complex interfaces, or knowing the technical organisation of data. This friction creates a well-known phenomenon in large companies: expert dependency... these experts become bottlenecks. In some groups, teams spend several hours a week simply answering comprehension questions or manually validating metadata" [why-do-data-catalogue-projects-fail]. Monte Carlo's "data discovery" framing pushes toward full automation as the fix: "Traditional data catalogs... rely on data teams to do the heavy lifting of manual data entry, holding them responsible for updating the catalog as data assets evolve. This approach is not only time-intensive, but requires significant manual toil that could otherwise be automated" — and projects that "the next generation catalogs will have the capabilities to learn, understand, and infer the data" [data-catalogs-are-dead-long-live-data-discovery]. OvalEdge's pitfalls piece explicitly contradicts the pure-automation fix: "relying solely on automation in data curation is a major pitfall—while it extracts and classifies metadata, it cannot provide the business context necessary for making informed decisions... Automation cannot determine whether it contains only active customers, historical data, or prospects... Without proper contextualization, even the most advanced automation can result in an underutilized, confusing data catalog" [3-data-catalog-pitfalls-to-avoid-for-successful-governance]. Its prescribed fix is not "automate everything" but "automation + contextualization": prompt business users with structured, low-friction questions at point of use rather than expecting standalone stewardship effort.

**6. "You Still Don't Need A Feature Store"** [you-still-dont-need-a-feature-store-xebia]. Sceptical-case source, explicit about the corpus's vendor-bias risk: "Other content on feature stores is often written by feature store providers. This content focuses on the respective feature store implementation." Its four canonical reasons to adopt a feature store — prevent repeated feature dev, prevent repeated computation, fetch features not provided by consumer, solve train-serve skew — only partially map onto a prompt register: "prevent repeated dev work" (discoverability/dedup) maps directly; "prevent repeated computation" and "train-serve skew" do not apply to prompts at all (prompts aren't recomputed or subject to distribution skew the way features are). This is useful as a scope check: much of the abstract "asset registry" skeleton pattern-matches from feature-store vendor marketing, and only a subset of that literature's justifications actually transfer to prompts — a caution for the final report not to over-borrow feature-store architecture wholesale.

**7. The GitHub prompt-management study, full text** [understanding-prompt-management-in-github-repositories-a-call-for-best-practices] (the HTML full-text note at `arxiv.org/html/2509.12421v2`; the companion note `250912421-...` is the arXiv abstract page only and does not contain the body). Verified numbers against the actual paper text, with corrections to the brief's cited figures:

- Corpus: **24,800 prompts across 92 repositories** — confirmed exactly: "we perform an empirical analysis of 24,800 open-source prompts from 92 GitHub repositories."
- Exact duplication: **10.1% (2,507 out of 24,800) prompts are exact duplicates** — confirmed exactly as quoted in the brief.
- Semantic duplication threshold: confirmed — "we assess semantic duplication via sentence embeddings (using 'all-mpnet-base-v2') with a cosine similarity threshold of >0.95." Semantic duplicates: **38.5% (9,553 out of 24,800)** of all prompts — this figure was not in the brief but is directly relevant and should be added to the final report.
- **Correction required**: the brief's figure of "prompt duplication affecting 23.9% of repositories" does **not** appear anywhere in the paper body. The actual repository-level figures reported are four distinct numbers, split by internal/external and exact/semantic: "internal exact duplication occurs in 13.0% (12 out of 92) of repositories, whereas internal semantic duplication occurs in 30.4% (28 out of 92) repositories... external exact duplication occurs in 16.3% (15 out of 92) of repositories, while external semantic duplication occurs in 34.8% (32 out of 92) of repositories." None of these is 23.9%, nor is any simple average of them (their unweighted mean is 23.6%, close but not identical, and there is no stated basis in the paper for averaging these categories). **The final report should replace "23.9% of repositories" with the four correct figures above** and specify which one (internal vs. external, exact vs. semantic) is being cited, since they mean different things.
- Repository composition is highly skewed toward one type: "72.8% (67 out of 92) of the repositories store a large set of prompts that allow developers to reuse the prompts without reinventing the wheel... without explicit authorship attribution or categorization," and "the top eight repositories accounting for 90.8% of the collected data," with "the six largest repositories are all categorized as prompt collections."
- The paper's own scope limits: "our focus on GitHub may not fully capture practices in other ecosystems, such as Hugging Face or private commercial prompt stores" — the authors explicitly exclude enterprise/internal settings from their claims.

**8. IAS 38 recognition of intangible assets** [recognition-and-cost-of-intangible-assets-ias-38-ifrs-community]. Provides the honesty caveat requested by the brief. IAS 38 recognition requires four criteria jointly: "Identifiability... Probability of future economic benefits... Control over the future economic benefits... Reliable cost measurement." Notably, IAS 38.69 requires that "Training activities," "Start-up activities," and "internally generated goodwill, brands, customer lists and similar items" be expensed, not capitalized, "because such expenditure cannot be distinguished from expenditure to develop the business as a whole" — and control over economic benefits "typically can't be recognised as assets due to insufficient control" for know-how-like items. A corporate prompt library resembles this excluded category (know-how, not a separable identifiable asset with reliable cost measurement) more than it resembles software or a licence. This does not undermine the product's positioning — "asset register" is a defensible organizational/ledger metaphor (a system of record with owner, cost, lifecycle) — but the final report should not imply the register performs formal IAS 38 balance-sheet capitalization; that would overclaim what the mechanism does.

## Evidence synthesis

Three independent adjacent-domain sources — MLflow (lifecycle), Cloudaware (shared fields), and the data-catalog trio (curation entry-ticket) — converge on a two-tier schema logic even though none of them state it explicitly as such. Tier 1 (operational/routing fields: current-production pointer, owner-of-record, cost/usage) decays when it is treated as a manually-maintained status flag, independent of the action that actually changes reality (MLflow's stage enum; CMDB's unowned column). Tier 2 (semantic/business-context fields: what this thing is for, whether it's still the right one) decays for a different reason — not because nobody "owns" the field mechanically, but because supplying it costs effort disproportionate to the asker's actual task (the data-catalog entry-ticket problem), and pure automation cannot substitute for it (OvalEdge's counter-evidence to Monte Carlo's "infer everything" claim).

Where the three domains disagree is on how far automation can go. The data-discovery camp (Monte Carlo) argues rich inference and automated telemetry can eventually replace manual stewardship almost entirely. The data-catalog-pitfalls camp (OvalEdge) argues this fails specifically for meaning/context fields, because "what does this data actually mean" and "is this still active" are not observable from access logs alone — they require a person who knows the current business intent. Both camps agree, however, that when a field's currency depends on someone doing a *dedicated* stewardship task (log in, browse to the record, edit a field, save — divorced from any other workflow), that field decays; the disagreement is only about whether the alternative is full automation or a *reduced-friction* human touchpoint.

The GitHub prompt-management study, read in full, gives a materially different — and more nuanced — picture than the brief's summary suggested. Duplication is real and substantial at the prompt level (10.1% exact, 38.5% semantic, using a >0.95 cosine similarity threshold on all-mpnet-base-v2 embeddings), but at the repository level the study reports four distinct, non-equivalent figures rather than one "23.9%" number, and the population is dominated by public prompt-collection repositories (72.8% of repos, 88.8%+ of prompts) whose entire purpose is aggregating other people's popular prompts for reuse — a structurally different phenomenon from one corporate group's internal, product-specific prompt sprawl.

## Committed position

### Position A: the register should auto-derive every field it can (data-discovery / "action-derivation" reading)

Strongest case: MLflow's fix for lifecycle rot was precisely to stop treating "current production version" as a manually maintained flag and instead derive it from the promote action itself (alias reassignment via `copy_model_version()` / `set_registered_model_alias()`, triggered by the same click that already performs the promotion). CMDB rot is explicitly diagnosed as a *field-ownership* problem, not a curation-effort problem — the fix Cloudaware prescribes is not "hire more stewards," it's "assign exactly one writer per column" and automate discovery of that column where possible. Monte Carlo's thesis is that manual entry is the root failure mode across the board: "This approach is not only time-intensive, but requires significant manual toil that could otherwise be automated." Applied to the prompt register, this reading says: owner-of-record, current-production pointer, version history, usage count, cost/token delta, and last-used timestamp should *all* be zero-touch, derived respectively from who clicked promote, the promote action itself, the version-control log, SDK fetch calls, eval/trace pipelines, and fetch telemetry — never free-text fields anyone can leave blank or forget to update.

### Position B: some fields cannot be derived and will decay unless curation is designed for near-zero effort at the point of an existing action (data-catalog-pitfalls reading)

Strongest case: OvalEdge's direct rebuttal to automation-only curation is concrete and specific — automated lineage/tagging can tell you a table's schema and access pattern but "cannot determine whether it contains only active customers, historical data, or prospects," and "without proper contextualization, even the most advanced automation can result in an underutilized, confusing data catalog." The GitHub prompt-management paper independently corroborates that automatable static-quality metrics (readability, spelling, length) do not touch the harder problem the authors flag as unresolved: "prompt duplication... risks maintenance inefficiencies, error propagation, and ambiguity in prompts' original authorship or modification histories" — i.e., knowing *which* duplicate is canonical, or whether apparent duplicates reflect legitimate use-case divergence, is a judgment call no embedding-similarity script resolves. Applied to a prompt register: a field like "one-line business purpose of this prompt" or "is this near-duplicate cluster actually the same prompt or a deliberate variant" cannot be pulled from SDK telemetry, no matter how instrumented the runtime is.

### Adjudication

The orchestrator's working hypothesis — every field must be derivable from an action someone was already going to take, or it goes stale within two quarters — is correct for the operational/routing tier and incomplete for the semantic/context tier, and the corpus gives a specific way to close that gap rather than abandon the hypothesis. Position A's mechanism (derive from an existing action) generalizes cleanly to Tier 1 fields (owner-of-record, current-production pointer, usage, cost, last-used) — these should be built as non-editable, automatically computed fields exactly as the hypothesis proposes, using MLflow's alias-reassignment pattern for "current production version" specifically (not a manually-set stage flag). Position B is correct that Tier 2 fields (purpose, canonicalization judgment, deprecation rationale) cannot be computed this way — but the fix is not to add a separate stewardship task (which is exactly the entry-ticket failure mode the data-catalog sources document); it is to *widen the definition* of "an action someone was already going to take" to include a two-click confirm/edit of an AI-drafted field inside the HITL promote-approval moment the product already requires by hard constraint. That single design choice — collapsing Tier 2 data capture into the mandatory approval step, rather than a standalone metadata form — is what prevents both decay mechanisms simultaneously: it satisfies Position A's "no dedicated maintenance task" requirement while satisfying Position B's "genuine human judgment is required" requirement, because the human is judging anyway (they're approving a production promotion) and the register is capturing that judgment as a byproduct rather than demanding it separately.

- **Position:** The register's operational fields (owner, current-production pointer, usage, cost, last-used) must be 100% auto-derived from existing actions (promote clicks, SDK fetch calls, eval traces) to avoid MLflow/CMDB-style decay; its semantic fields (purpose, canonicalization) cannot be auto-derived and will decay under a separate-stewardship-task model, but survive if their capture is collapsed into the mandatory HITL promote-approval step already required by the product's hard constraints.
- **Confidence:** medium-high on the schema/workflow recommendation (three independent adjacent-domain sources — MLflow, CMDB, data-catalog-pitfalls — converge on the same two-tier logic without citing each other); medium on the specific "collapse into the promote step" resolution (this is this investigator's synthesis of the sources, not a claim any single source makes explicitly for prompt registers).
- **Boundary conditions:** this holds for a register whose promote-approval action is genuinely mandatory and genuinely touches every version that matters (per the product's own HITL constraint) — if a meaningful share of prompts never go through a promote gate (e.g., prompts imported in bulk during the initial migration sweep of existing Sheets/Notion content), Tier 2 fields for *those* records have no natural capture moment and will need either a one-time bulk-tagging pass or will start stale, which the report should flag as a known gap in the migration-sweep USP rather than assume away.
- **What would change this position:** evidence that a real-world registry sustained accurate Tier-2 (semantic/context) fields over multiple years with zero human-in-the-loop capture (would support pure Position A); or evidence that even promote-time confirm/edit prompts get rubber-stamped/ignored in practice the way approval gates often do elsewhere in this corpus (see `rubber-stamp-reviews-minware`, not read in full for this locus but flagged in the width corpus) — if approval-time confirmation is empirically as neglected as a standalone stewardship task, the "collapse into the promote step" fix does not actually solve the entry-ticket problem, it just relocates it, and the report should say so with less confidence.
- **Evidence weight:** 3 adjacent-domain mechanism sources (MLflow RFC, CMDB vendor analysis, data-catalog-pitfalls) converge on two-tier field logic; 1 counter-source (data-catalogs-are-dead / Monte Carlo) argues for near-total automation and is in tension with the data-catalog-pitfalls source, both are practitioner/vendor blogs rather than controlled studies; 1 empirical paper (GitHub prompt-management study) supports the existence of unresolved duplication/attribution problems that automation alone doesn't solve, corroborating Position B, but studies public GitHub repos, not internal registries.

### On the premise (scattered/duplicated prompts)

The founding premise — that this specific conglomerate's prompts are scattered and duplicated across code/Sheets/Notion/Drive/chat in a way that causes real organizational cost — is **asserted, not measured**, and the GitHub study cannot close that gap; it measures a different population under different tooling. The paper's own stated external-validity limit says so directly: "our focus on GitHub may not fully capture practices in other ecosystems... or private commercial prompt stores." Cross-repository ("external") duplication in the paper — 16.3% of repos exact, 34.8% semantic — is measured across 92 *unrelated* public repositories, most of which (72.8%) are prompt-collection dumps whose purpose is aggregating popular, widely-circulated prompts (marketing copy templates, SEO prompts) for public reuse. That is closer to convergent copying of well-known patterns than to organizational waste, and the report should not cite it as evidence of the target group's internal redundancy. The more relevant number is *internal* duplication — within a single repository/unit: 13.0% of repos have internal exact duplicates, 30.4% have internal semantic duplicates. This is structurally closer to "one team's scattered prompt collection has near-duplicates nobody noticed," but it is still a GitHub population (with file paths, READMEs, and occasional review, however thin), not a Sheets/Notion/Drive/chat population, which has none of even that minimal structure. If the internal-duplication rate transfers at all, the more defensible inference is that a Sheets/Notion/Drive/chat substrate likely has *equal or higher* undetected duplication than 30.4%-of-units, because it lacks git's baseline discoverability — not that the 30.4% figure itself applies.

- **Position:** the report should state the scattered/duplicated-prompts premise as *plausible and mechanistically well-supported* (Sheets/Notion/Drive/chat have no built-in de-dup, versioning, or discoverability tooling, so prompts accumulating there should be expected to duplicate and drift at least as much as prompts in messy git repos) but explicitly **not** claim it is measured for this org, and should not cite the GitHub paper's headline duplication percentages as if they describe the target company's own prompt store. Use the paper only for the qualitative mechanism (duplication risk rises with unmanaged decentralized authorship) and the internal (not external) duplication figures as the closest — still imperfect — quantitative analogy, with the caveat stated explicitly.
- **Confidence:** medium. The direction of the inference (worse tooling → equal-or-more duplication) is a reasonable a fortiori argument, not a measurement.
- **What would change this position:** a direct internal audit or survey of the target conglomerate's actual Notion/Sheets/Drive prompt count and near-duplicate rate (even a rough one, e.g., from the product's own planned "state-of-the-world map" scan deliverable) would immediately upgrade this from asserted-plausible to measured, and should be treated as a first-class deliverable to validate the whole opening thesis of the product pitch.

## Open questions

- No source in this locus's read set (or, as far as searched, the wider corpus) reports an internal-organization prompt-duplication or staleness rate measured outside GitHub — this is a genuine literature gap; the "audited absence" here is that private/enterprise prompt-store duplication appears nowhere in the accessible literature, which is itself informative (it means the product's own migration-sweep scan would be a novel data point, not a redundant one).
- Whether approval-time confirm/edit fields actually get filled in with real judgment versus rubber-stamped is not tested in this locus's sources; `rubber-stamp-reviews-minware` appears in the corpus index and looks directly relevant to whether the "collapse Tier 2 capture into the promote step" fix actually works in practice — worth a follow-up read by whichever locus covers HITL approval quality.
- The CMDB "stale within two release cycles" figure is a single vendor claim with no methodology given; no independently-measured field-staleness half-life was found for any adjacent domain (CMDB, data catalog, feature store, or model registry) in this read set.
