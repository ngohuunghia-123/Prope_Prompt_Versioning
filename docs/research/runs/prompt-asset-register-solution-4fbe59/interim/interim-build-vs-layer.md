# Interim report: build-vs-layer-minimum-defensible-surface

**Locus question:** What is the smallest surface that must actually be built, given that single-cloud vendors ship versioning primitives free but are each scoped to one provider's project?

**Flavor:** dialectical

## What the corpus already said

The width sweep did not produce a dedicated note synthesizing this question; the closest prior artifact is the loci-analyst framing itself. Analyst B's reframing (recorded in the run's `loci.json`) is the operative prior: this is not "build vs buy" but "what is structurally unavailable from any single vendor?" — Bedrock and Vertex prompt management are each scoped to their own project/account, so a group running several products across several providers has no purchasable single ledger, while storage, version numbering, label assignment, and playground UI are commodity. A sibling locus (`promote-gate-efficacy-and-the-missing-approval-object`) independently found, by reading Langfuse's docs directly, that "protected prompt labels" are role-gated *write access to a label*, not an approval workflow — no pending-review state, no evidence record, no rejection path. That finding is load-bearing for this locus too: it means the approval-decision object belongs on the "must build" side regardless of which versioning substrate is chosen.

## What the new sources say

**Amazon Bedrock Prompt Management** (`create-a-prompt-using-prompt-management-amazon-bedrock`, `view-information-about-versions-of-a-prompt-in-prompt-management-amazon-bedrock`) is created and addressed entirely within a single AWS surface: prompts are created via a `CreatePrompt` request against an "Agents for Amazon Bedrock build-time endpoint," and the console flow requires "an IAM identity that has permissions to use the Amazon Bedrock console." Versioning is a flat, numbered sequence: "The response creates a `DRAFT` version and returns an ID and ARN that you can use as a prompt identifier for other prompt-related API requests," and version retrieval is done with `GetPrompt` where "In the `promptVersion` field, specify the version number." Nothing in either page describes cross-account sharing, aggregation, or a registry view spanning multiple AWS accounts — the unit of scope throughout is the single account/console session in which the prompt was created.

**Vertex / Gemini Enterprise Agent Platform prompt management** (`prompt-management-gemini-enterprise-agent-platform-google-cloud-documentation`) is explicit about its scope in a way Bedrock's docs only imply: "This page introduces a unified set of capabilities to define, save, retrieve, and manage prompts **within your Google Cloud project**." The client is instantiated with `client = vertexai.Client(project='my-project', location='my-location')`, and every subsequent method — `create`, `create_version`, `get`, `get_version`, `list`, `list_versions`, `delete`, `restore_version` — operates against that one project. `list()` "retrieve[s] a `PromptRef` for all saved prompts **in the current project**." There is a version-history and `restore_version()` mechanism, but no label/alias concept comparable to Langfuse's environment labels, and no documented cross-project aggregation.

**Langfuse's own versioning model** (`version-control-langfuse`) is the clearest description in the corpus of what "label-based" (prompt-as-content) versioning actually is, and its limits: "Each prompt version is automatically assigned a version ID. Additionally, you can assign labels to follow your own versioning scheme. Labels can be used to assign prompts to environments (staging, production), tenants... or experiments." Deployment is a pointer move: "To 'deploy' a prompt version, you have to assign the label `production`... to that prompt version," and rollback is the same operation in reverse: "You can quickly rollback to a previous version by setting the `production` label to that previous version." Crucially, Langfuse's own docs concede environments don't compose automatically even within one vendor: "Prompts are scoped to a project — if you use separate projects for different environments, see how to sync prompts between them" — i.e., even the vendor that ships the richest label model treats cross-environment sync as a bolt-on, not a native capability.

**Caching and Guaranteed Availability** (`caching-langfuse`, `guaranteed-availability-langfuse`) establish the reliability bar a prompt-serving layer has to clear to be safe to sit in a request path. The default behavior: "Langfuse prompts are cached client-side in the SDKs, so there's no latency impact after the first use and no availability risk," with stale-while-revalidate semantics ("stale prompts are served immediately while it revalidates in the background") and a layered backend cache ("The API caches prompts in a Redis cache... if Redis is unavailable, the database serves as backup"). But the guaranteed-availability page is explicit about the failure mode that remains even with all of this: `get_prompt()` "will throw an exception if: No local (fresh or stale) cached prompt is available... **and** network request fails... after retries." The two named mitigations are pre-fetch-and-exit-on-failure at startup, or a hardcoded fallback prompt compiled into the client and used "when both the local cache is empty and the Langfuse API is unavailable."

**The OpenTelemetry GenAI semantic conventions** (`gen-ai-opentelemetry`) supply exactly the vendor-neutral return channel the adapter architecture needs, and they draw the privacy line precisely where the product needs it drawn. Token usage is standardized (`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_creation.input_tokens`, `gen_ai.usage.cache_read.input_tokens`) and model/provider identity is standardized (`gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.provider.name`, with documented enum values `aws.bedrock`, `gcp.vertex_ai`, `openai`, `anthropic`, etc. — the exact set the register needs to know which runtime a trace came from). There is even a purpose-built binding key: `gen_ai.prompt.name` — "The name of the prompt that uniquely identifies it" (example given: `analyze-code`) — which is the join key a ledger would use to attribute a trace's cost/usage back to a specific named prompt asset without touching content. Content-bearing attributes are explicitly deprecated and gated: "`gen_ai.prompt` — Removed, no replacement at this time... Deprecated, use Event API to report prompt contents" and "`gen_ai.completion` — Removed, no replacement at this time," replaced by structured `gen_ai.input.messages` / `gen_ai.output.messages`, each of which carries an explicit warning: "This attribute is likely to contain sensitive information including user/PII data." Instrumentations are told they "MAY provide a way for users to filter or truncate" these fields — i.e., content capture is opt-in, not default.

**Build vs buy framing** (`build-vs-buy-a-guide-for-internal-tools-retool-blog`) supplies the 7Cs decision framework and, honestly applied, cuts both ways. On **Complexity** ("Do existing solutions fit your needs or are your requirements bespoke?"): version storage, numbering, draft states, and playground/variant-compare UI are *not* bespoke — Bedrock ships "Compare variants," Vertex/Gemini Enterprise ships Agent Studio, Langfuse ships all of it self-hosted — so per the framework's own test, buying/reusing wins there. On **Core Capability** ("Would you be building something that forms part of your company's product or service offering?"): the cross-account, cross-provider aggregation with an owner/lifecycle/cost schema is not sold by anyone as a SKU because it requires reading from N different vendor accounts and normalizing into one schema — that is the one piece where the framework's answer flips toward build. The piece is also blunt about the failure modes of building past the bespoke core: "It's straightforward enough to get a version of whatever you're building working on one person's computer. What next? Where is the app going to live?... Who's going to take responsibility for updating libraries, or maintaining test cases?" — a direct warning against scope creep into rebuilding storage/serving infrastructure a small team cannot operate long-term.

**Tech debt economics** (`paying-down-tech-debt-by-gergely-orosz-and-lou-franco`) reinforces the same caution from the maintenance side rather than the build side. Lou Franco's operating heuristic — "by reducing a specific tech debt, can I increase developer productivity and deliver business value right now? If I can't, then I don't pay it down" — is a discipline for an already-built system, but its precondition (every built surface becomes a standing maintenance liability someone must staff) argues for keeping the built surface as small as the "structurally unavailable" test allows, since a hackathon-origin tool that becomes real infrastructure ("used more than Google Sheet inside this specific conglomerate" as the stated win condition) inherits exactly the multi-year maintenance burden this piece describes, without the multi-year team the piece assumes.

## Evidence synthesis

Two things converge cleanly. First, both Bedrock's and Vertex's prompt management surfaces are documented as account/project-scoped resources with no cross-account or cross-provider aggregation shown anywhere in either doc set: Bedrock requires an IAM identity "with permissions to use the Amazon Bedrock console" and returns per-console version ARNs; Vertex is explicit that its client is instantiated against a single `project` and every list/get call is scoped to "the current project." Neither page mentions a mechanism for viewing, let alone governing, prompts across accounts, let alone across providers. That is direct, positive evidence for Analyst B's claim: there is no purchasable SKU that gives a Vietnamese conglomerate with products on Bedrock, Vertex, and self-hosted runtimes one ledger. This is a structural absence, not a pricing gap — buying a bigger Bedrock or Vertex plan does not create a Vertex-side view of a Bedrock prompt.

Second, everything downstream of "store a prompt and let me roll back" is commodity at a standard the vendors + Langfuse already exceed what a small hackathon team could build and, more importantly, *operate*. The caching/guaranteed-availability docs describe a specific, non-trivial reliability engineering pattern — TTL-bound client cache, stale-while-revalidate background refresh, Redis-backed server cache with DB fallback, startup prefetch, and a hardcoded fallback value — that exists precisely because "get me the current production prompt" is a request that must never become an outage. Reproducing that from scratch, on a Python/FastAPI/Docker stack, on a short timeline, is exactly the "underestimating the time and complexity of building" trap the Retool piece names. The right posture is not to compete with this pattern but to *inherit* it: every adapter the register builds needs to implement the same shape (cache + TTL + async refresh + fallback), because the register is now sitting where Langfuse's SDK sits — in the hot path of every downstream product's inference call, if the push architecture routes serving through it, or safely out of the hot path if it only pushes into each vendor's own store and lets that vendor's serving path (or Langfuse-grade tooling) handle runtime reads. That distinction is the actual architecture decision, not "build vs buy" in the abstract.

The OTel evidence resolves a concrete implementation question the query poses directly: can the ledger populate cost/usage fields from traces without capturing prompt content? Yes, and the spec draws that line for you. `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`, `gen_ai.provider.name`, `gen_ai.request.model` / `gen_ai.response.model`, and `gen_ai.prompt.name` are all standard, non-content attributes sufficient to attribute cost and identify which prompt/version/provider a call used. The content-carrying attributes (`gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`) are separately gated, explicitly flagged as privacy-sensitive, and off by default — meaning the register's cost-gate and usage dashboard (a stated hard constraint: "alert when a change increases token/cost") can be built entirely on the non-content telemetry surface, with content capture left as an opt-in the register never needs to require.

Where the evidence pulls the other way, and must be stated honestly: neither vendor doc I read rules out cross-account sharing definitively — I did not chase AWS Resource Access Manager / cross-account IAM roles for Bedrock, nor Vertex's organization-level resource hierarchy, either of which could partially blunt the "structurally unavailable" claim *within a single cloud, multiple accounts* (though not across Bedrock and Vertex simultaneously, which is the harder case a multi-product conglomerate on mixed providers actually faces). This is an absence-of-evidence-in-what-I-read gap, not a confirmed absence-of-capability, and it should be flagged rather than overclaimed.

### Position A: build a thin governance/ledger layer with per-runtime adapters

This is the position the mechanism evidence directly supports. The ledger owns exactly the fields no vendor store models — owner, lifecycle state, approval-decision object, cost/eval deltas, cross-provider identity — and pushes promoted content down into each product's *existing* runtime (Bedrock's `CreatePrompt`/`CreateVersion`, Vertex's `client.prompts.create`/`create_version`, or a lightweight store for self-hosted runtimes), while pulling usage/cost telemetry back via OTel's `gen_ai.*` attributes. The vendor stores remain the runtime source of truth for serving; the ledger is the control plane and the record of who-approved-what-and-why. This preserves cohesion with each product team's existing stack (no forced migration off Bedrock/Vertex), minimizes the built-and-therefore-maintained surface (no reimplementation of caching, storage, playground UI), and concentrates engineering effort on the one piece that is genuinely bespoke and genuinely absent from the market: the cross-account, cross-provider aggregation with an asset-register schema.

### Position B: build a store that replaces vendor prompt stores

The countervailing case, steelmanned: a single canonical store simplifies the mental model (one place prompts live, not N vendor stores plus a ledger pointing at them), avoids building and maintaining N adapters each with their own auth, rate limits, and API drift risk, and avoids the "two sources of truth can disagree" failure mode inherent to any push/sync architecture (the ledger says v5 is production; the vendor store, if edited directly by someone with console access, might disagree). It also sidesteps the reliability question above entirely for products with no existing prompt-management surface (a raw self-hosted LangGraph app with prompts as Python string literals) — for those, *something* has to be the store, and it might as well be the register itself rather than a third thing.

Position B is weaker on the evidence actually gathered, for three concrete reasons. It requires migrating existing product teams off tooling they already use and that the vendor already operates at a reliability standard (Redis-backed cache, DB fallback, documented SLA-adjacent monitoring) this project cannot match on a short timeline — directly contradicting the Retool piece's warning about underestimating build complexity and the hidden devops cost of "who's going to take responsibility for updating libraries, or maintaining test cases." It throws away free, already-built commodity functionality (Bedrock's variant-compare, Vertex's Agent Studio, both vendors' encryption/IAM integration) that the 7Cs Complexity test says should be reused, not rebuilt. And it does not actually solve the structural problem better than Position A does — a replacement store is still one system a Vietnamese conglomerate would have to convince every product team, including ones already committed to Bedrock or Vertex, to route production traffic through, which is a much larger adoption ask than "sync your promoted version into the store you already use."

## Committed position

Build a thin governance/ledger layer with per-runtime adapters (push) and an OTel-based telemetry return path (pull); do not build a store that replaces vendor prompt stores. The mechanism evidence is unambiguous that the one thing missing from the market is cross-account, cross-provider aggregation with an owner/lifecycle/cost schema — Bedrock and Vertex are each scoped to their own console/project with no aggregation primitive documented in either — while everything else requested (storage, numbered versions, label-as-pointer deployment, diff view, playground) is already built, in both vendor products and in third-party tools like Langfuse, to an operational standard (TTL caching, stale-while-revalidate, Redis+DB fallback, startup prefetch, hardcoded fallback) this team cannot match on a short timeline. The register should therefore own exactly four bespoke surfaces — the cross-provider asset schema, the approval-decision object (not a label write), the per-runtime push adapters, and the OTel telemetry ingestion mapped to non-content `gen_ai.usage.*`/`gen_ai.provider.name`/`gen_ai.prompt.name` attributes — and should explicitly decline to rebuild prompt storage, prompt editing UI, or a distributed caching layer at the vendor's own layer. The unavoidable cost of this design is git's absent branching/merge semantics: label-based versioning (confirmed by Langfuse's own docs, and structurally implied by Bedrock's flat numbered versions and Vertex's `restore_version` model) gives you a linear version history with movable environment pointers, not divergent branches with reconciliation — two editors who diverge on the same prompt produce either colliding linear versions or, more likely, a new "asset" under a different name, which only the register's dedup/near-duplicate clustering (not any versioning primitive) can catch after the fact. That is a real, uncompensated capability gap relative to git-based workflows for teams that need true parallel multi-environment experimentation, and it should be named as a deliberate trade for non-developer accessibility, not treated as free.

- **Position:** the register should be a thin governance/ledger layer with per-runtime push adapters and OTel-based pull telemetry, not a store that replaces Bedrock/Vertex/self-hosted prompt stores; the built surface should be limited to the cross-provider asset schema, the approval object, the adapters, and non-content-capture telemetry ingestion.
- **Confidence:** high on "don't rebuild vendor-commodity storage/versioning/UI" (directly supported by both vendor doc reads plus the Retool 7Cs framework applied honestly); medium on "adapters must match Langfuse-grade caching/fallback reliability" (strongly implied by the guaranteed-availability docs but I did not verify this precise bar is achievable within the stated hackathon timeline — it is a requirement, not a confirmed feasibility).
- **Boundary conditions:** this holds for a multi-product, multi-provider conglomerate where at least some products already run on Bedrock and/or Vertex prompt management or an OTel-instrumented self-hosted runtime. It weakens if the group standardizes on a single cloud vendor for all products (in which case that vendor's own cross-account sharing primitives, unverified here, might close more of the gap than assumed) or if no product team has any existing prompt-management tooling to adapt into (in which case the register may need to be the primary store for those specific products, a partial concession toward Position B for the self-hosted-only case).
- **What would change this position:** documented evidence that AWS Resource Access Manager / cross-account IAM roles let Bedrock Prompt Management resources be aggregated and governed across accounts within one AWS Organization, or that Vertex's project/org resource hierarchy supports the same for prompt resources — either would shrink (though not eliminate, since it would still not span both providers) the size of the "structurally unavailable" gap this position rests on. Evidence that client-side caching/fallback at Langfuse's documented reliability standard is infeasible for this team within the stated timeline would also force a fallback to a simpler, higher-risk single-point-of-failure design and should be surfaced honestly rather than hidden.
- **Evidence weight:** 2 vendor mechanism docs (Bedrock, Vertex) directly support "no cross-account/cross-provider aggregation documented"; 1 OTel spec doc directly supports "non-content telemetry return path is standardized and content capture is opt-in"; 2 Langfuse mechanism docs (caching, guaranteed-availability) support "the reliability bar for a prompt-serving layer is non-trivial and must be inherited by any adapter"; 1 Langfuse mechanism doc (version-control) supports "label-based versioning has no branch/merge semantics"; 1 build-vs-buy framework doc supports the reuse-commodity / build-bespoke split when applied honestly; 1 tech-debt economics doc supports minimizing built surface on maintenance-cost grounds. No source in this read set argues for Position B directly — Position B was constructed as the strongest available counter-case, not found pre-articulated in the corpus, and should be weighted accordingly as a steelman rather than an independently evidenced alternative.

## Open questions

- Does AWS Resource Access Manager, or any documented Bedrock cross-account sharing mechanism, allow Prompt Management resources to be viewed/governed across multiple AWS accounts within one Organization? Not checked — would partially affect the "structurally unavailable" claim for single-cloud, multi-account groups.
- Does Vertex AI's organization/folder resource hierarchy support any cross-project aggregation of prompt resources? Not checked.
- Does Bedrock Prompt Management have any label/alias-equivalent to Langfuse's movable environment labels, beyond flat numbered versions? The docs I read show only numbered versions and did not surface one — if one exists elsewhere in AWS's docs, it changes how much environment-pointer logic the register needs to own versus delegate.
- What is the actual engineering effort (person-weeks) to implement Langfuse-grade client caching + fallback in each per-runtime adapter, on the stated Python/LangGraph/FastAPI/Docker stack, within the hackathon timeline? Not quantified in this read set — Retool's piece gives one comparable anecdote (a password manager: "4-6 person months" vs. a subscription) but nothing calibrated to this specific integration surface.
- No source in this read set discusses concrete OSS options for a minimal per-runtime store for products with no existing prompt-management tooling (e.g., self-hosted Langfuse as that store) — worth a follow-up check against the corpus's existing Langfuse notes (`prompt-cicd-version-gate-and-roll-out-prompts-like-code-langfuse`, `langfuse-prompt-management-how-it-works-a-flexible-alternative-to-consider-miras`) if not already covered by another locus.
