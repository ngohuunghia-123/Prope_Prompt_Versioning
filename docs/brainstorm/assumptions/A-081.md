# A-081 — Consumer API keys belong to access-control, and a key is default-deny

**Statement**: The `api_key` table — a workspace-scoped, named, revocable secret used by a consuming
product to call the gateway — is owned by **access-control**, which already "authenticates actors and
answers every may-this-actor-do-this question". The gateway holds no key material and no key table; it
calls `authenticate_api_key(secret)` and `may_resolve(key_id, model_name)`. A key is **default-deny**:
it carries the explicit list of model names it may resolve, and a key with an empty scope resolves
nothing. A refusal returns the same not-found shape as a model name that does not exist, so a key
cannot be used to enumerate the registry.

**Rationale**: The module map's gateway → access-control seam already says the gateway "authenticates
the consumer's API key", but no module owned the table, and an unowned table is how two writers appear
later. Default-deny follows BR-01's private-by-default rule applied to a machine principal: the blast
radius of a leaked key should be what someone deliberately put on it, not the workspace. The narrow
option is chosen deliberately so OQ-006's eventual answer can only loosen it — a key scope is one
column to widen and a migration to narrow.

**Impact if wrong**: Widening to workspace-wide scope is a default on the key record. The cost of the
narrow choice is real and should be watched in the pilot: releasing a *new* prompt does not
automatically make it callable, and a consumer who was never granted it sees a not-found with no
explanation. The dashboard's key screen has to make the scope obvious for that to be a five-second
fix rather than an afternoon.
