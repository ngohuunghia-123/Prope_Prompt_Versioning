# A-124 — The `details` payload is a JSON object validated at append time against a per-action key allow-list

**Statement**: `history_event.details` is a JSON object. Each of the 31 registered actions declares the
exact set of keys it may carry — `revision_released` carries `version_id`, `previous_version_id`, and
`break_glass`; `role_assigned` carries `role` and `grantee_user_id`; and so on. At append time the keys
are checked against the registration: an unregistered key raises and the transaction fails. No value in
`details` may be a prompt body, a fallback answer, a request or response body, a credential in any form,
a password or its hash, an eval output, or a value from `prope.variables` (A-046).

**Rationale**: One schema (A-044) and 31 heterogeneous events force a payload, and a free-form JSON
column in an audit table is the single most likely place in Prope for a prompt body to end up — it is
the one column with no declared shape, written by five modules, and "just put the whole object in for
debugging" is a one-line change that no reviewer would flag. The allow-list makes the leak a build
failure at the moment it is written rather than a discovery during a security review. It also keeps the
Success-metric queries writable: a key that is registered is a key that can be indexed and relied on.

Rejected: strongly-typed columns per event (30 events, mostly-null columns, a migration per new fact);
free JSON with a redaction pass on the way in (a deny-list, and A-046 already established that
allow-lists are the rule here — the pass cannot know about a field nobody told it about); and no payload
at all, which loses `previous_version_id` and makes the restore metric unanswerable.

**Impact if wrong**: Adding a key is a registry entry and a test. The expensive direction is the one this
prevents.
