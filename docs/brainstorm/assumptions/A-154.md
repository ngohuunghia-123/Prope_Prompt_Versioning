# A-154 — The fingerprint is over the normalised system message, and variable slots are proposed rather than applied

**Statement**: an observation's grouping key is a hash of the caller's **system message** after
normalisation: leading and trailing whitespace stripped, internal runs of whitespace collapsed, and
every span that looks like an interpolated value masked before hashing. Messages with roles other than
`system` are not part of the key — they are the conversation, not the prompt. A message set with no
system message is observed under a group keyed on the first user message, and flagged as such.

Variable slots are then inferred by **diffing the members of one group**: spans that differ between
sightings of the same fingerprint are candidate variables; spans identical across every sighting are
prompt text. The result is a proposal, rendered as `{{name}}` in the form prompt-registry already
accepts (A-011, A-078). **It is never applied.** No revision is written, no placeholder is substituted
into anything live, and a person sees the proposed body against the observed one before anything
happens.

**Rationale**: the fingerprint is the one genuinely uncertain thing in the module and the product's
credibility rests on it. Too loose and two unrelated prompts merge into one row; too tight and one
prompt becomes four hundred rows and the inbox is unreadable. There is no correct answer available in
advance, only a defensible starting one, so the rule is chosen to make the failure **visible rather
than silent** — a person opening the inbox can see immediately that it grouped badly, which is why the
inbox ships before anything acts on the grouping.

Keying on the system message alone follows ADR-0011's own decomposition: the revision's body *is* the
system message, and the caller supplies the conversation. A prompt whose identity varied with the
user's turn would not be a prompt.

Proposing rather than applying is not caution, it is the same rule prompt-conversion already ships
under — *"the agent proposes; a human releases"*, and *"conversion never saves a revision"*. The
inference here is weaker than that one, being a diff rather than a model, so it earns no more
authority.

The mechanism stays in the standard library. `difflib` is enough for this shape, and anything fuzzier
— embeddings, a similarity index — is refused by A-012's debuggable-by-one-person clause and by the
fact that a wrong inference is shown to a person before it does anything. Precision buys less here
than legibility does.

**Impact if wrong**: the grouping rule is a pure function over stored bodies, so a changed rule is a
re-hash of the table rather than a lost inventory. That is the property worth protecting and it is why
the raw body is stored beside the fingerprint rather than in place of it. The one failure that is not
cheap is a caller whose prompt is genuinely unique per request — no stable span at all — which
produces one group per call; the failure mode is recorded in the module's lock rather than assumed
away.
