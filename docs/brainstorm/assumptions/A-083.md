# A-083 — The gateway forces usage reporting upstream; missing usage is recorded as unknown, never estimated

**Statement**: ~~The gateway sets `stream_options.include_usage` on the **upstream** request~~
**provider-access always requests usage on the upstream request** (*amended 2026-08-08 while locking
provider-access — see A-089; the gateway does not compose the upstream request, so it could not set
the flag*), regardless of what the caller asked for, and **the gateway** strips the resulting
usage-only chunk from the caller's stream if the caller did not request it. If a usage object still
does not arrive, the call record's token count
and cost are `unknown` and `prope_gateway_usage_missing_total` increments, which pages. They are never
estimated from length.

**Rationale**: OpenAI-compatible providers omit usage from a streamed response unless asked. Leaving
that to the caller would make an accountability guarantee depend on a flag in someone else's code:
"reported token counts match the provider within ±2%" and the cost figures behind every release
decision would quietly apply only to the consumers who happened to opt in. Stripping the extra chunk
keeps wire compatibility — an SDK that did not request `include_usage` does not expect a final chunk
with an empty `choices` array, and the constraints table says a near-miss breaks every client SDK.
Refusing to estimate is a non-negotiable constraint (BR-07): a plausible wrong number never pages, and
an honest gap does.

**Impact if wrong**: A request-mutation step and a stream filter. A provider that ignores the flag
fails A-030's admission rule and is provider-access's problem, not a gateway workaround — and as of
2026-08-08 that is no longer a forward reference: A-090 makes the verification probe refuse such a
provider before it can be saved.
