# A-097 — Generation parameters pass through verbatim; a parameter the provider rejects is a revision defect, not an upstream failure

**Statement**: provider-access sends the revision's generation parameters to the provider exactly as
stored. It injects no defaults, drops no unknown keys, and rewrites nothing. A parameter the provider
rejects returns `class: invalid_request` with `fallback_eligible: false`, so the call fails outright
and the error names the parameter.

**Rationale**: A-024 puts the parameters on the revision and forbids the caller from overriding them,
precisely so the approval record describes what ran. A module that quietly adjusts them breaks that
in the one direction nobody checks — the reviewed revision and the dispatched request stop being the
same thing, and no diff would show it.

Refusing to serve a fallback here follows from what the fallback is for. It covers an upstream
*failure*, and a bad parameter is not one: the binding has never worked and never will. Masking it
would let a revision in production look healthy while every call fails, which is worse than an outage
because nobody looks for it. The eval run is where this is meant to be caught — the same argument the
product makes to its own users, applied to itself.

**Impact if wrong**: A validation or normalisation step against the model catalogue's capability
flags, which would be additive and would fail earlier rather than differently.
