# A-033 — A fallback is served as HTTP 200 in the OpenAI shape, but explicitly marked

**Statement**: A fallback response returns `200` with a valid OpenAI chat-completion body so client
SDKs keep working, and carries three markers: the response header `x-prope-fallback: true`, a
`prope` object in the response body with `fallback: true` and the version ID, and `outcome =
fallback` on the call record. Token counts and cost for a fallback are zero and are excluded from
cost-delta comparisons. The prompt's owner is notified.

**Rationale**: Returning an error makes the fallback pointless — the consumer never gets the answer
the feature exists to provide. Returning an unmarked 200 is worse: the consuming product ships a
canned answer to a real user believing it came from the model, and nobody ever finds out. Marking
it in all three places means SDKs that ignore unknown fields still work, while a team that wants to
detect fallbacks can, at the transport layer or in the body.

**Impact if wrong**: Switching to an error status is a one-line change in the gateway plus a note to
every consumer. Excluding fallbacks from cost figures is the part that must not be relaxed — counting
a zero-token fallback as a cheap success would make a broken provider look like a cost improvement.
