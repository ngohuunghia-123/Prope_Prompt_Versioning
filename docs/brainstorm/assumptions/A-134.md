# A-134 — The two concurrency caps are 24 and 8, and both numbers are placeholders

**Statement**: `provider_config.interactive_concurrency` defaults to **24** and `batch_concurrency` to
**8** (ADR-0046). Their sum is 32, which is ADR-0016's original `max_concurrency` default, so the total
pressure on a provider key is unchanged by the split — only its distribution is new. The 3:1 ratio is
chosen so live traffic keeps the larger share, matching ADR-0016's priority order.

**Neither number is derived from anything.** No provider has published a rate limit to Prope, no
workspace has configured a real key yet, and OQ-012 has not supplied a request-rate figure — the
gateway's own `p95 < 50 ms` is itself an agent-decided placeholder (A-031) against an RPS nobody has
stated. ADR-0016's original 32 was in the same position and inherited the same silence.

**Rationale**: The caps have to be *some* number before the first deployment, and a wrong number here
fails in a visible, instrumented, and cheap-to-correct way — which is not true of most placeholders in
this project. Both directions are already alerted: `ProviderInteractiveShed` pages if the interactive
cap is too low, and `ProviderBatchStarved` warns if the batch cap is. Both are columns on
`provider_config`, so correcting either is an UPDATE rather than a deploy.

What the numbers must satisfy is a *sum*, not two independent values: the provider sees one key and
does not know which container issued a request. Raising one without lowering the other raises the total
pressure, and that is the mistake this assumption exists to make visible. The right first evidence is
the load test the lock already specifies — 50 rps interactive against a stubbed upstream with a 100-case
batch submitted concurrently — but a stub cannot rate-limit, so the real number arrives only from a real
provider.

**Impact if wrong**: Too low on interactive and the gateway serves fallback answers because of a limit
Prope set — the failure ADR-0016 says is *"worse than the one it fixes if it goes unnoticed"*, which is
why it pages. Too low on batch and eval runs crawl, which is the designed direction of the trade and
warns rather than pages. Too high in sum and the provider rate-limits the shared key, appearing in
metrics as `origin=provider` — the one case where the label points away from the actual cause, and the
reason the caps must be tuned as a pair.
