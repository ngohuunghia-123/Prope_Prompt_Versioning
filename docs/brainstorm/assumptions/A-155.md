# A-155 — An observation is written directly, off the response path, best-effort and counted — and no second queue is added

**Statement**: the observation is written in the same post-flush `BackgroundTask` that already hands
the call record to call-ledger, as one direct transaction under the workspace's row-level security. It
is not published to a broker. A failure increments `observation_write_failed_total` and is abandoned;
it is never retried on the caller's behalf and never reaches the caller, whose response was flushed
before this ran.

**Rationale**: the obvious symmetry — *the call record goes through the broker, so this should too* —
does not survive asking what a loss actually costs.

A lost **call record** loses money. It moves a workspace's spend total and every later cost delta,
which is why ADR-0041 gives it a broker with publisher confirms and a direct-write fallback, and why
A-099 gives it an idempotent upsert so a redelivery cannot double-count.

A lost **observation** loses one occurrence of a fingerprint that has already been seen and will be
seen again on the next request. The inventory is a rollup over a stream; dropping a sample from a
stream costs a counter, not a fact. The one number it perturbs is a sighting count nobody makes a
decision on to four significant figures.

Different durability requirements are what license different mechanisms, and the alternative has been
settled twice already. ADR-0028 declares **one** queue, `prope.call_record`, and its DLQ. A second
queue has been proposed and rejected on merit twice; adding one here for data that does not need
durability would be the third proposal and the weakest of the three. Piggybacking on the existing
queue is worse still — it changes a contract that has consumers, to carry a message with different
semantics, for a feature that does not need the delivery guarantee it would be buying.

**Impact if wrong**: if observations turn out to need durability, the change is `enqueue()`-shaped and
call-ledger's own pattern is sitting there to copy — ADR-0041's broker-first-with-a-direct-fallback,
against a second queue that would at that point have an argument behind it. Nothing about the direct
write forecloses that; the row and its idempotency key are the same either way.
