# A-114 — Nothing in access-control is cached, by this module or by its callers; revocation is immediate

**Statement**: Authentication results, permission decisions, key scopes, role bindings, and sessions are
read live on every check. Callers may not cache them either. Revoking a key, removing a member, or
changing a role takes effect on the next request. Full reasoning and rejected alternatives in ADR-0022.

**Rationale**: Prope's other two caches were justified by what a stale answer costs. A stale released
pointer serves a previously approved revision one TTL late (ADR-0012); a stale decrypted credential
delays a planned rotation by a minute (A-092). A stale permission serves a **revoked** credential, and
revoking a leaked key is incident response, where "immediately" and "within 30 seconds" are different
promises.

The cache would also buy little. Authentication is one primary-key read plus one hash (A-113), and a
permission check is two indexed reads over small tables — nothing like the join the gateway's resolution
cache avoids.

**Impact if wrong**: If the reads turn out to be the constraint, the ordered fallback is a database-level
optimisation first, then a cache keyed on an explicit revocation epoch — never a plain TTL, which
reintroduces the exact window this removes.
