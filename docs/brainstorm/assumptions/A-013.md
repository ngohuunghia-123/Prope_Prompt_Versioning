# A-013 — Search in the MVP is keyword and filter, not semantic

**Statement**: Registry search matches substrings in title, body, and tags, combined with filters on
owner, status, and access. No embeddings, no vector store, no similarity ranking.

**Rationale**: `prope_source_of_truth.md` §16 excludes advanced semantic clustering from the MVP and
S8 (similar-prompt check) is P2, "defer and validate". At the pilot's expected scale a keyword search
plus filters is what the ≤30-second find target actually requires.

**Impact if wrong**: Semantic search is additive — the same records, a second index.

> **Implemented 2026-08-09 by ADR-0048**, and the word *"substrings"* above turned out to be
> load-bearing rather than loose. It is now literal: `pg_trgm` GIN over a trigger-maintained
> `prompt_property.search_text`, queried with `ILIKE '%term%'`. `tsvector` would have given word
> matching instead, which is a different product — and it loses on three specifics here: it needs a
> stemming dictionary named while **OQ-010 is open**, it cannot match infixes, and its parser reads
> `namespace/name` as a file path, so `refund` would miss `support/refund-classifier`.
>
> Two clauses of this assumption are now sharper than they were. **"body"** means the **latest
> revision's** body only — bounded at 1,000 rows rather than 20,000 — plus **every** revision's change
> summary, which A-050 caps at 200 characters. And **"no vector store"** was re-tested during that pass
> when the user asked whether an LLM keyword-extractor on save, or embeddings, should be added; both
> were rejected for the MVP and ADR-0048 carries the full argument plus an ordered upgrade ladder.
>
> **The "additive" claim above survives, and is now the reason the ladder works**: `simple`-dictionary
> `tsvector` first (no language commitment, so OQ-010 stays out of it), then `pg_trgm`'s
> `similarity()` operators for typo tolerance — already installed — then `pgvector` with embeddings
> computed in `worker` on a schedule, never on the save path. The revisit trigger in this file's
> frontmatter is unchanged and is the gate on step 3.
