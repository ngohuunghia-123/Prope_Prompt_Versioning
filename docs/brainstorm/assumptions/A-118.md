# A-118 — Access-control exposes a set form beside `may()`, so list endpoints filter in SQL

**Statement**: `visible_subject_filter(actor, subject_type) -> {mode: all | none | ids, ids?: [...]}`.
A caller pushes the result into its own `WHERE` clause. `all` is returned when a role binding grants
workspace-wide read, `ids` when visibility comes from per-prompt grants and ownership, `none` when the
actor has neither. The singular `may()` stays for single-subject actions.

**Rationale**: prompt-registry's lock states that "permission filtering lives in the repository layer,
not in handlers, so a new query path cannot forget it", and its data section forbids joining across
module tables. Those two lines cannot both be satisfied with only a per-row `may()` — the filter has to
be expressible in the caller's query, and the only way to get it there without a join is to hand it over
as data.

The alternative in practice is not fifty permission calls; it is a developer under deadline pressure
writing the list query without the filter and adding the check "later", which is exactly the failure
prompt-registry names as its own worst case: a private prompt appearing to someone with no grant, the
top adoption barrier in the survey.

Returning `all` rather than every id is what keeps the common case cheap, and it is honest — a member
with workspace-wide read genuinely has no id list.

**Impact if wrong**: At a scale where the id list is too large, the mode set grows a fourth member that
expresses the predicate rather than the result, and callers already switch on mode.
