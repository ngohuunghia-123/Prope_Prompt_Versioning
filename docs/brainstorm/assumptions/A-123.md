# A-123 — property-history mounts no HTTP route; its read API takes an already-authorised scope

**Statement**: property-history exposes no endpoint. Not `/api/v1/history`, not `/healthz`, not
`/readyz`. Its entire surface is two in-process functions: `append(event)` and `read(scope)`, where
`scope` is a `(workspace_id, scope_prompt_id | target)` the caller has already permission-checked. The
read function performs no permission check of its own and does not know how to. That every module's route
table is free of a history endpoint is asserted by a test, not by intention.

**Rationale**: A-044 broke the access-control ↔ property-history cycle by giving history no screen, and
therefore no permission check, and therefore no dependency on access-control. That break is load-bearing
— it is the reason access-control's dependency list has one entry. A single mounted route reintroduces
the cycle, because a route needs an actor, an actor needs a check, and a check needs access-control,
which writes its grants through here. The route would be added by someone reasonable who wants an audit
screen, so the guard has to be a test rather than a convention.

The `/healthz` and `/readyz` omission is a separate consequence of ADR-0023: this module has no process
of its own to report on. A-045's convention applies to management APIs, and this is not one.

**Impact if wrong**: An audit view is a screen in whichever module owns the subject, which is what A-044
already prescribes. A genuinely cross-module audit view is the case A-044 names as its own revisit
trigger, and it needs a permission answer that does not come from this module — the owning-module pattern
scaled up, or a read-only admin surface in access-control, which may depend on history without a cycle.
