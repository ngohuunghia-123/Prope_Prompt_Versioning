# A-139 — A gateway process killed between flush and publish loses that call record, and nothing counts it

**Statement**: A-087 hands the call record to call-ledger **after the response is flushed**, and
ADR-0041 keeps that ordering deliberately so the write path stays outside the p95 span by construction.
If the `app` process dies in the interval between the flush and the publish, that record is lost — and
`prope_call_ledger_metadata_dropped_total` does **not** increment, because nothing ran to count it. The
window is the enqueue span, budgeted at p95 < 1 ms. It is accepted, not mitigated.

**Why it is worth writing down**: `00_context.md#success` states *"100% of calls record a version ID"*,
and the lock calls that *"an accountability claim, not a performance one"*, with
`GatewayMissingVersionId` paging immediately on the first occurrence. This is the one gap in that claim
that the instrumentation cannot see. Every other gap is counted:
`prope_call_ledger_metadata_dropped_total` covers a publish that failed *and* a fallback direct write
that failed, and ADR-0041 restored that counter's right to stay at zero and stay a page. This one
produces no signal at all — the only trace is a discrepancy between gateway request counts and ledger
row counts, which nothing currently reconciles.

**This is exactly what the spill file used to cover.** ADR-0041 deleted it, on grounds this assumption
does not reopen: three durability layers holding the same record, only one of them with its own
disk-full failure mode, its own replay correctness and its own readiness check; and *"the mechanism most
likely to be wrong is the one exercised least — a spill path that only runs during an incident is a path
nobody has watched work."* Both remain true. What changed is that the deletion's residue was never
stated, and the gateway lock kept four sentences describing a mechanism that no longer exists — this
assumption is written in the pass that removed them.

**Why nothing is rebuilt for it**: an outbox row would put a database write back inside the p95 span,
which is the precise thing A-087 exists to prevent and which ADR-0041 already rejected for the same
reason. Publishing *before* the flush would put the broker on the response path. Holding the record in
memory across a restart is not a thing a killed process can do. Every available mitigation costs the
constraint the module was built around — *"Persisting call records must not sit on the response path"*
(`00_context.md#constraints`, non-negotiable).

**Bounding the exposure honestly**: a `kill -9` of `app` also drops every in-flight request outright,
and those calls produce neither a response nor a record, so they are not a *silent* accounting error —
the consumer saw the failure. The loss described here is narrower and stranger: calls the consumer
received a **correct answer** for, in roughly the last millisecond before the process died, which Prope
has no record of. A graceful stop (`docker compose stop`, SIGTERM, uvicorn's shutdown) drains in-flight
work and does not hit this at all, so ADR-0031's ordinary deploy is not the exposure. A hard kill, an
OOM, or a host failure is.

**Impact if wrong** — that is, if the loss is ever more than a rounding error: the fix is a reconcilable
counter rather than a durability layer. Increment a gateway-side counter at flush and compare it against
ledger rows over a window, so the gap becomes visible rather than theoretical. That is one metric and a
query, and it can be added without touching the write path.

Related: [[A-087]] sets the ordering; ADR-0041 removed the mechanism; [[A-137]] and [[A-136]] record the
other two places where a deliberate deletion left a stated cost rather than a hidden one.
