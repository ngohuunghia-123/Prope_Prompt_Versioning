# A-031 — Gateway resolution: 30-second cache, fallback on upstream failure, error on caller failure

**Statement**: The gateway resolves the released revision from a short-lived in-process cache
(30 seconds). ~~invalidated immediately on release or restore~~ — **amended 2026-08-08 while locking
gateway: nothing invalidates the cache; it expires.** No mechanism for immediate invalidation exists,
and building one would reverse a forbidden edge or add a broker A-012 rules out. See ADR-0012 and
A-080. ~~which also add a bounded stale-if-error window~~ — **amended again 2026-08-09 (step 4,
release-control's pass): there is no stale-if-error window. It was deleted during the gateway's stack
pass and this sentence was left behind; an expired entry is never served.** The 30-second TTL and
everything below stand unchanged, and the TTL is now the *only* staleness in any read path in Prope.
On an upstream provider failure it
serves the fallback answer if one exists (A-032 to A-035); on a caller failure — unknown model,
unapproved pin, no access, missing credential — it returns an OpenAI-shaped error and never a
fallback. Gateway-added latency, excluding the upstream call and excluding logging, targets a p95
under 50 ms.

**Rationale**: A 30-second cache keeps the ≤5-minute restore target reachable while removing a
database read from every request — which, as ADR-0012 later observed, is exactly why no invalidation
scheme that reintroduces a per-request read could be accepted. The split between upstream and caller failures is A-034's
reasoning applied at the resolver. The 50 ms figure is a placeholder chosen so step 2 can decide
whether the cache is its own module; the user's answer to OQ-012 gave a strategy, not a budget.

**Impact if wrong**: Cache TTL and the latency target are configuration and a benchmark
respectively. Neither changes the module boundaries.
