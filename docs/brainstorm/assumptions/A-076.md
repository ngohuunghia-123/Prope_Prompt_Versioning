# A-076 — Approve-and-release is one request that writes two rows; it is never a third kind of decision

**Statement**: `POST /revisions/{version_id}/approve-and-release` performs both acts in one transaction
for an actor holding **both** the approve and the release permission. It writes one `approval` row and
one `release` row with their own ids, timestamps, and `approval_id` linking them — exactly what the two
separate calls write. Every rule survives unchanged: the acknowledgement reason when
`requires_acknowledgement` is set (A-058), `self_approved` when the actor authored the revision (A-008),
the evidence digest (A-074), the compare-and-set on the released pointer (A-072), and both the
`revision_approved` and `revision_released` history events *(renamed from the bare verbs by A-120; corrected here 2026-08-09, step 6 pass 1)*. An actor missing either permission is refused with the missing
one named — the combined action grants nothing.

**Rationale**: The friction the two-step flow creates is a UI problem, not a modelling problem, and it
should be solved where it lives. Collapsing `approval` and `release` into one object would instead
destroy the thing they exist to support: the headline success metric is a join between them (releases
with a NULL approval and `break_glass = false` must be zero), and merging makes that query a tautology
that returns 100% whether or not anyone reviewed anything. Restore-without-re-approval (A-028) and
break-glass (A-009) both depend on the same separability.

**This is not auto-release.** The anti-goal is a prompt reaching production without a recorded human
decision. Here a human deliberately performs both decisions and both are recorded; what is saved is one
page load.

**Impact if wrong**: Delete one endpoint. The two underlying actions are untouched, which is the whole
reason this shape was chosen over merging the tables.
