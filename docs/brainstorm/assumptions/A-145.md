# A-145 — Retention is declared for all 27 tables, and four of them grow without bound rather than one

**Statement**: Written by the step-6 sweep, pass 2. Every owned table needs a retention value; two had
one and twenty-five did not. The default, recorded here rather than left implicit, is **retained for the
life of the system**. Only the exceptions are interesting:

| Table | Retention | Mechanism |
|---|---|---|
| `ledger.call_body` | **30 days**, per-workspace setting ([[A-040]], [[A-106]]) | `expires_at` stamped at write; batched bounded-chunk `DELETE` from day one ([[A-132]]); excluded from the dump (ADR-0039) so a restore cannot silently double the window |
| `access.session` | `expires_at`; sign-out deletes the row | Excluded from the dump (ADR-0044) — a restore signs everybody out |
| `history.history_event` | **Never deleted, by design** ([[A-121]]) | Append-only at the *privilege* level (ADR-0025). Carries a stated growth expectation: < 500 events per prompt property per year |
| `evaluation.case_result` | **None, and no delete path** ([[A-137]]) | Inherits OQ-013. Included in the dump with no exclusion — the counts live on the parent and the evidence lives here, so an emptied child renders *"18 of 20 passed"* with nothing behind it |
| `ledger.call_record` | **Indefinite** ([[A-040]]: *"metadata indefinite"*) | No delete path. This is the accountability record NFR-02 depends on, so indefinite is correct — but it is unbounded and was not counted as such |
| Everything else (22 tables) | Life of the system | Bounded by the number of workspaces, prompts, revisions, suites, configurations and decisions — all human-created, all small |

## The correction this pass forced

ADR-0033 states: *"Disk growth has exactly one unbounded term: `call_body`."* [[A-137]] already
corrected that to two. **It is four**, and it is worth having the list in one place because each behaves
differently:

1. `ledger.call_body` — unbounded in principle, **has a delete path**, alerted on the age of the oldest
   surviving row rather than on the job's exit code. The only one actually under control.
2. `ledger.call_record` — unbounded, **no delete path**, ~1 KB/row against `call_body`'s ~10 KB, so it
   is an order of magnitude slower and reaches the same place.
3. `evaluation.case_result` — unbounded, **no delete path**, and it stores `output_content`, so it grows
   with model verbosity rather than with anything Prope controls.
4. `history.history_event` — unbounded **by decision**, small, and the only one of the four with a
   written expectation to be wrong about.

At ADR-0033's sizing (10k calls/day, 80 GB SSD) `call_body` is the term that matters within the pilot
and the retention job is what holds it. The other three matter on a horizon nobody has costed, which is
the honest reason to write them down now rather than to act on them.

**Rationale**: a retention value that nobody wrote down is a retention value nobody can be wrong about.
The two that were declared were declared because a delete job existed; the twenty-five that were not are
not oversights so much as a default nobody stated — and the sweep's job is to notice that "obvious" and
"recorded" are different.

**Impact if wrong**: the pilot's disk fills. Detected before it matters by the disk-usage alert beside
`oldest_body_age_seconds` (ADR-0033), and the remedy for three of the four tables is a retention
setting that does not exist yet — new work, not a migration, because every one of them already carries
`workspace_id` and `created_at`.
