# A-151 — What a tombstone actually does, field by field

**Statement**: ADR-0054 decided that a departing person is tombstoned rather than deleted. These are
the parameters, decided by the sweep because each of them is mechanical once the decision is made.

## The operation

`POST /api/v1/users/{user_id}/tombstone`, permission-gated on the action `user.tombstone`, held by
Admin in [[A-007]]'s placeholder seed. One transaction:

| Column on `access.user` | After |
|---|---|
| `id` | **unchanged** — the row survives so the identifier stays reserved |
| `email` | `NULL`. The column is `unique`, and PostgreSQL permits many NULLs in a unique index, so any number of people may be tombstoned |
| `display_name` | `NULL`. The UI renders a catalogue key, not a stored string — ADR-0053's i18n layer already forbids literal display text, so the "removed user" label is a translation rather than a value written into the database |
| `password_hash` | `NULL`. The login path treats a NULL hash as no-match **without skipping the hash comparison**, so a tombstoned email and an unknown email stay timing-indistinguishable ([[A-144]], ADR-0043) |
| `must_change_password` | `false` |
| `status` | `tombstoned` |
| `tombstoned_at`, `tombstoned_by` | **new columns**, set. `tombstoned_by` is an actor id, and it is the whole of the operation's accountability — see ADR-0054 §7 on why there is no reason string |
| `last_login_at` | unchanged. A timestamp is not identifying, and zeroing it would destroy the only signal that an account was ever used |

Alongside, in the same transaction:

- **Every `session` row for the user is deleted.** Sessions are server-side rows precisely so that
  removal is effective at once rather than at expiry (ADR-0022, [[A-108]]), and a tombstone that left a
  live session behind would be a tombstone the person could still authenticate through.
- **Every `role_binding` row for the user is deleted**, and every `workspace_member` row moves to
  `status = removed` if it is not already. The membership rows are **retained**, not deleted: they are
  how the tombstone knows which workspaces to write its event into, and they are how a workspace's own
  trail stays complete.
- **`prompt_grant` rows where the person is the grantee are deleted.** A grant to an account that can
  never authenticate is a permission with no holder, and BR-01's private-by-default posture says the
  narrower state is the correct one.
- **Consumer API keys are untouched.** A key belongs to the workspace, not to the person who created
  it ([[A-113]], ADR-0021); `created_by` is a value like every other actor id. Revoking a departing
  person's keys is a separate, deliberate act, and folding it into the tombstone would silently break
  a consuming product's traffic on an HR event.
- **One `user_tombstoned` history event per workspace** in the person's `workspace_member` rows, any
  status. `target_type = user`, `target_id` = the tombstoned id, `actor_id` = the admin performing it,
  `details` = `{}` — **no registered detail keys at all** ([[A-124]]), because every candidate key here
  is a fact about the person being erased.

## Pre-condition

The person must already hold no active membership — each removal writes its own `member_removed` event
in its own workspace, which is the trail of departure. The tombstone is the account-level act that
follows, and refusing it while a membership is active keeps the two facts separately recorded rather
than collapsed into one ambiguous event.

## The recovery-runbook step

ADR-0036 keeps nightly `pg_dump` archives for 30 days. **A restore from a dump taken before a tombstone
brings the name back into the running system**, and no alert would show it — `oldest_body_age_seconds`
watches bodies, not people. The runbook therefore carries a step: after any restore, re-apply every
tombstone recorded after the dump's timestamp, read from the `user_tombstoned` events, which survive in
the restored history precisely because history is never deleted. This is [[A-133]]'s rule in a second
place: **a restore is not the running system**, and the things a restore un-does are the things nothing
in the running system was watching for.

**Impact if wrong**: every line above is an `UPDATE`, a `DELETE` or a column, in one module, on tables
one module owns. The expensive direction — touching `history_event` — is the one ADR-0054 refuses.
