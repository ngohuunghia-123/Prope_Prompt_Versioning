# A-079 — Every response identifies what served it, in both the headers and the body

**Statement**: Every gateway response carries the identity of the revision that produced it, in two
places. Headers: `x-prope-version-id`, `x-prope-model`, `x-prope-revision`, `x-prope-pinned`, and
`x-prope-fallback` when it applies (A-033). Body: a `prope` object with `version_id`,
`revision_number`, `pinned`, `fallback`, `upstream_model`, and `stale_resolution` when it applies
(A-080). The response's own `model` field echoes the **Prope** model name the caller asked for, not
the upstream model — clients compare that field, and the upstream model is visible in
`prope.upstream_model` instead. On a streaming response the identity rides in the headers and on the
first chunk, so a caller can record it even if the stream is later truncated.

**Rationale**: "100% of gateway calls record a version ID" is a success metric measured inside Prope,
which means the consuming team has to take it on faith. Putting the same identity on the wire makes it
checkable by the person who most needs it — the developer who currently "cannot say which text is
running in production". Headers rather than body alone, because on a streaming call the headers are
the only place metadata can arrive before content.

**Impact if wrong**: Adding or renaming a field. SDKs ignore unknown headers and unknown body keys, so
nothing breaks on the consumer's side.
