# A-141 — The SPA is Prope's first long-lived client of its own API, and a deploy does not reload it

**Statement**: Under ADR-0052 the browser holds a JavaScript bundle for as long as the tab stays open.
An ADR-0031 deploy replaces `prope-app` and `prope-web` on the host, but **an already-open tab keeps
running the previous build's bundle against the new API** until someone reloads. No mechanism forces that
reload, and none is added in this pass.

**Why this is new rather than inherited**: ADR-0034's server rendering made it impossible by
construction. Every navigation fetched fresh markup from the process that had just been replaced, so the
client and the server could not disagree about a field name — there was no client. That property was
never written down as a benefit, because nothing had cost it yet. This is what it cost.

**What the exposure actually is**, bounded honestly:

| | |
|---|---|
| Window | From the deploy until the user reloads — realistically minutes to a working day |
| Trigger | Only a *breaking* API change. A field added, an endpoint added, a new optional parameter: no effect |
| Symptom | A screen that renders wrong or errors, and that a refresh fixes |
| Who is exposed | Authenticated humans in `app`'s UI. **Not** consumer products — the gateway is a wire API (ADR-0050) and holds no client code |

**Rationale for accepting it**: the mitigations all cost more than the failure. A version-negotiation
header that hard-fails the SPA on mismatch converts a cosmetic glitch into a forced logout during every
deploy. A service worker that self-updates adds a caching layer with its own well-known failure mode —
a stale worker serving a stale bundle — to a system whose standing answer on caching is *four caches,
none invalidated*. And Prope deploys to **one host with one environment** (ADR-0033, A-023): there is no
rolling window, no blue/green, and no fleet in which two bundle versions coexist by design. The mismatch
requires a human to have left a tab open across the exact deploy that broke a field they use.

**The cheap half is worth doing and is recorded as owed**: the build stamps a short version string into
the bundle and `app` returns the same string on a response header. The SPA compares them and shows a
non-blocking *"a new version is available — reload"* banner. That is a banner, not a mechanism: it does
not block, does not log anyone out, and does not need a cache layer. It turns an unexplained glitch into
a self-service fix, which is the whole of what this needs.

**Impact if wrong**: a reviewer sees a broken screen mid-decision and, worse than the glitch, may not
trust what it showed them — on a module whose entire product claim is that the record is accurate
([[A-074]] stores the evidence digest precisely because a screen's contents are testimony). The remedy is
the banner above, roughly an afternoon, with no schema change and no new service.
