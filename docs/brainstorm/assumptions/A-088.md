# A-088 — A dispatch is exactly one attempt; the retry policy belongs to the caller

**Statement**: `dispatch()` issues exactly one upstream request and returns its outcome. It never
retries, on any error class, regardless of `retry_after_ms`. A caller that wants a second attempt
calls again.

**Rationale**: The two callers have opposite policies and both are already decided. The gateway sets
one deadline and never retries (A-084), because inside a latency-critical path a retry doubles the
worst case to buy an outcome the fallback already covers. The eval runner retries transport errors up
to twice (A-053), because it has no latency budget and a spurious case error corrupts a comparison.
A retry inside provider-access would have to be either a policy parameter — in which case the logic
is in the callers anyway, just expressed as configuration — or a single behaviour, in which case one
of the two decided policies gets overridden by the module underneath it.

Exactly one attempt also makes the observability honest: `attempt` is always 1 in this module's logs,
so upstream call volume and dispatch count are the same number, and a retry storm shows up in the
caller that caused it.

**Impact if wrong**: Moving a retry loop down one layer and adding a policy parameter. Cheap, but it
would require re-deciding A-084 and A-053 together rather than separately, which is the thing this
assumption exists to avoid.
