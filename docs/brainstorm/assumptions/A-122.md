# A-122 — The target is `(target_type, target_id)` with no foreign key

**Statement**: `history_event` identifies its subject with a closed `target_type` enumeration and an
opaque `target_id` string. There is no foreign key to `prompt_property`, `revision`, `release`,
`eval_suite`, `provider_config`, `workspace`, `prompt_grant`, or `api_key`, and none of those tables is
ever joined to from here. A `target_id` naming a row that has been renumbered or never existed produces
an event that renders with an id and no title, which is the correct outcome.

**Rationale**: Three reasons, in order of strength. A foreign key would have to point at eight tables
owned by five modules, which is not expressible. It would point in the forbidden direction — this module
depends on nothing, and that is what makes it safe for access-control to depend on it (A-044). And an FK
would make an event's survival contingent on its subject's, which is exactly backwards for an audit
trail: the row recording that something was retired must outlive whatever it recorded.

This is the same call as `prompt_grant.prompt_id` (access-control) and the opposite of A-096's provider
case, where the constraint ran the same way the dependency already did and was therefore free. Here it
runs against it.

**Impact if wrong**: Nothing to undo. Adding a constraint later would be the change, and it would require
the dependency to change first.
