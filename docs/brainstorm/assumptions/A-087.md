# A-087 — The gateway enqueues after the response is flushed; the buffer belongs to call-ledger

**Statement**: The gateway hands a completed call record to call-ledger **after** the response has
been flushed to the caller — after the stream closes, for a streaming call (A-038). It never awaits a
write. The bounded queue, the drain, the local spill file, and the drop counters described in A-037
belong to **call-ledger**, on its ingest surface; the gateway's only measurement is
`prope_gateway_enqueue_duration_seconds`, a span that starts after the flush and is therefore excluded
from the added-latency figure by construction rather than by subtraction.

**Rationale**: A-037 describes the mechanism but not who owns it, and "an in-process background
writer" could plausibly have been read as gateway machinery. Putting it behind call-ledger's
`enqueue()` keeps the ledger a sink with one ingest path — the eval runner's usage submissions arrive
the same way — and it keeps the gateway free of durable state, which is what lets a second gateway
process be nothing but a second process. Measuring the enqueue span separately is what makes "logging
never sits on the response path" an assertion a test can fail rather than a claim in a document.

**Impact if wrong**: Moving a queue across a module boundary, plus re-pointing one metric. The
post-flush ordering is the part that must not be relaxed — it is a non-negotiable constraint.
