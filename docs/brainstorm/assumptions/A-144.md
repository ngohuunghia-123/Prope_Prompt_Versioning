# A-144 — The login limiter is 5 failures per email and 20 per source address in a rolling 15 minutes

**Statement**: `POST /api/v1/auth/login` refuses after **5 failed attempts for one email address** or
**20 failed attempts from one source address**, each counted in a rolling 15-minute window. A successful
sign-in clears the email bucket. A refused attempt returns **the identical response** an unknown email
and a wrong password already share, with no distinguishing status, body, header, or timing, and
increments `prope_access_control_login_rate_limited_total` while `login_total` does not.

**What this fills**: `access-control.lock.yml` committed twice to a limiter — *"Rate-limited per email
and per source address"* — and named no number anywhere in the repository. The mechanism, its position
in the request, and its security properties were all decided; only the two integers were blank, and a
blank integer on a security control is filled by whoever implements it.

**Why the response must stay identical**: ADR-0043 put the limiter **before** the user row is read and
**before** any argon2id hash is computed, precisely so a rate-limited attempt cannot be distinguished
from an ordinary failure by timing. A visibly different rate-limit response would hand that back — an
attacker who can tell "this email is being throttled" from "this email is wrong" has the account
enumeration channel [[A-116]] and ADR-0043 closed between them. The counter is where the operator sees
it; the caller never does.

**Why these numbers**: 5 per email is the standard ceiling and sits well above ordinary human error,
which matters more here than in most products — there is no password-reset email in the MVP ([[A-071]]),
so a lockout means finding an Admin to hand over a new password out of band ([[A-110]]). Fifteen minutes
is short enough that a real person waits it out rather than escalating. 20 per source address is
deliberately looser than 5 × 4, because a pilot team behind one office NAT shares a source address and
a per-address bucket that trips on four colleagues' typos is a limiter that gets turned off.

**What it actually protects**: argon2id at `memory_cost=47104` (46 MiB), `time_cost=1`, `parallelism=1`
(ADR-0043) on ADR-0033's 4 vCPU / 8 GB host. Unthrottled login is the one public endpoint that will
allocate 46 MiB and burn a core on demand, which is why the limiter is consulted before the hash rather
than after — it is a denial-of-service control as much as a credential-guessing one, and both jobs are
done by the same two integers.

**The limit, unchanged from where the lock already recorded it**: the limiter is a **bounded in-process
structure**, so it counts per process. [[A-130]]'s gateway split would silently admit twice as many
attempts, and — as the lock's own risk row notes — this is *not* detectable from
`login_rate_limited_total`, which keeps counting normally against a threshold that is no longer the real
one. Same shape as [[A-143]]'s cap, recorded in both places rather than in neither.

**Impact if wrong**: too tight and pilot users are locked out of a product with no self-service
recovery, which is a support call and a bad first impression; too loose and a slow credential-stuffing
run gets more attempts than it should. Both are one integer in one settings file. The window and the
counts carry no schema and no migration.

Related: ADR-0043 for the hash parameters and the limiter's position · [[A-130]] for the per-process
caveat · [[A-116]] for the enumeration rule the identical response preserves · [[A-142]] §8.
