# A-025 — Provider credentials are workspace-scoped, encrypted at rest, and never readable back

**Statement**: A credential is entered once from the provider dashboard, encrypted at rest with a
key held outside the database, and thereafter only decryptable by ~~the gateway and the eval
runner~~ **provider-access, and by no other module** (*amended 2026-08-08 while locking
provider-access*). No API returns it, no UI displays it beyond a last-four suffix, and it is redacted
in logs, error bodies, and the property history. Rotation replaces the record; it never appends a
readable copy.

**Amendment — 2026-08-08.** The original wording predates A-043 and contradicts three things written
after it: the module map's `anything → credential` forbidden edge ("Provider Access returns responses
and usage, never the secret"), gateway.lock.yml ("the credential never enters this process"), and
evaluation.lock.yml ("the provider credential is never seen by this module"). The gateway and the
eval runner do not decrypt anything — they pass a `provider_config_id` and receive a response plus a
usage object. The encryption scheme itself is now ADR-0014, and the decrypted-credential cache is
A-092.

**Rationale**: The BYOK answer to OQ-004 makes Prope a holder of third-party secrets, which it was
not before. NFR-03 requires encryption and handling policy, and "security and data concerns" is the
#2 adoption barrier in the survey — a leaked corporate provider key would end the pilot outright.

**Impact if wrong**: Tightening is always possible; loosening is not the direction anyone will ask
for. The moderate rating is for the key-management choice, which step 4 will revisit.
