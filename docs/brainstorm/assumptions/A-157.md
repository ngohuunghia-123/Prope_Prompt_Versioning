# A-157 — A namespace grant names a string, not a folder row, and an ungranted namespace denies

**Statement**: `access.namespace_grant` holds `(workspace_id, namespace, grantee_user_id, level,
granted_by, granted_at)` with **no foreign key** to `registry.folder`. The `namespace` column is a
value, exactly as `prompt_grant.prompt_id` and `history_event.actor_id` are values. A namespace with no
`folder` row can be granted; deleting a `folder` row revokes nothing; and a namespace nobody has
granted confers nothing — there is no fallback to workspace-visible.

**Rationale**: migration 0016 already refuses the foreign key from `prompt_property`, at length, and its
reasons carry one table further out: a label must not become load-bearing, and a workspace must be able
to hold a prompt in a namespace nobody has named. `list_folders` returns *the union of declared rows and
namespaces observed on prompts*, so **most namespaces in a live workspace have no row** — a permission
model that only worked on declared ones would work on the minority.

Under this decision a foreign key would be worse than redundant: it would make **deleting a folder a
permission change**, so renaming a drawer becomes a security event and a cascade becomes the mechanism
by which everyone silently loses access to everything in it.

The deny direction is the sharp part and it is chosen rather than inherited. A prompt created with a
typo in its namespace lands in a namespace nobody has granted, and it is therefore visible to its owner
and to nobody else. That is annoying and correctable. The alternative — treat an ungranted namespace as
open, so a typo cannot lose your prompt — makes a typo *publish* it, which is silent, uncorrectable
after the fact, and the exact disclosure BR-01 is one of four non-negotiables to prevent.

Two things this buys that were not the reason for it. A prompt cannot move between namespaces (A-021
makes the model name immutable, `uq_prompt_property_namespace` enforces it), so **a prompt's access
container never changes** — the *"somebody moved a file and changed who could see it"* incident is
unavailable in this design. And because the grant is on a string the caller already holds, ADR-0020 is
untouched: `Subject` gains `namespace` from the row prompt-registry has already read.

**Impact if wrong**: if an ungranted namespace should be workspace-visible instead, that is one line in
`_has_permission` and no schema change — but it is a widening, so it should be a decision somebody
makes rather than a default that was never noticed. If folders must nest, this assumption does not
survive: see ADR-0061's rejection, where flat is a constraint with a reason.
