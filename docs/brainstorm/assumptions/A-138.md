# A-138 — Nothing bounds `worker` across workspaces, and that is accepted for the pilot

**Statement**: Every concurrency bound in Prope is scoped to a workspace or to a provider config. There
is **no process-level cap on `worker`**. Three workspaces running evals simultaneously would put
3 × `batch_concurrency` = 24 dispatches in flight from one container on ADR-0033's 4 vCPU, plus their
response parsing and assertion evaluation. No cap is added in this pass.

**The full bound stack, and where it stops**:

| Bound | Scope | Value |
|---|---|---|
| per-run dispatch concurrency (A-054) | one run | 5 |
| `max_concurrent_runs` (A-063, ADR-0049) | one workspace | 2 |
| `batch_concurrency` (ADR-0046, A-134) | one provider config, in `worker` | 8 |
| — | **the `worker` process** | **none** |

**Rationale**: the pilot is eleven people (`00_context.md#problem`), and A-020 bars real corporate
prompts until the security baseline is signed off, so simultaneous multi-workspace eval load is not a
state the pilot reaches. Adding a fourth bound now means a fourth number with no measurement behind it —
A-134 already records that the third has none: *"no real provider rate-limit figure exists, and OQ-012
has not supplied a load number either."* Naming the gap is worth more than guessing at it, and the gap
is visible in the metrics that already exist rather than needing new ones.

**What makes this cheap to fix, and one asymmetry worth knowing**: ADR-0049's `max_concurrent_runs` is a
predicate inside the claim transaction, so it is a **database** bound and stays correct if `worker` is
ever replicated. ADR-0046's `batch_concurrency` is a process-local `asyncio.Semaphore` and does not —
two `worker` replicas double it against one provider key, which is precisely how ADR-0028 broke
ADR-0016. So a process-level cap and a `worker` replica are the same conversation, and the order matters:
**replicating `worker` before that conversation happens reintroduces the defect ADR-0046 was written to
remove.**

**Impact if wrong**: `worker` saturates and every eval run slows together, visible as
`prope_evaluation_run_duration_seconds` rising across all workspaces at once while
`prope_provider_*` shows no upstream trouble — a signature that distinguishes it from a slow provider.
The remedy is a global semaphore in `worker`, one number, no migration and no schema change.

Related: [[A-134]] holds the numbers this one bounds from above; [[A-063]] and [[A-054]] hold the two
below it.
