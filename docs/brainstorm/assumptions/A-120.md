# A-120 — Event action names are `<target_type>_<past participle>`, and the vocabulary is closed

**Statement**: Every `history_event.action` value is `<target_type>_<past participle>` and comes from one
closed list of 31 names registered in property-history — 30 until 2026-08-09, when ADR-0054 added
`user_tombstoned`. An action outside the list is a programming
error and the append raises, rather than writing an unrecognised row.

Five names in `release-control.lock.yml` were bare verbs and are renamed here: `submitted` →
`revision_submitted`, `approved` → `revision_approved`, `changes_requested` →
`revision_changes_requested`, `released` → `revision_released`, `restored` → `revision_restored`.
`break_glass_released` → `revision_break_glass_released`. `release_withdrawn` and `review_task_closed`
already conform.

**Rationale**: All 30 values live in one column of one table and are read together in one feed. Two
naming schemes in one enumeration — `approved` beside `provider_configured` — is the kind of thing that
is free to fix now and a migration plus a rendering-layer lookup table later. The subject-first form also
makes the value self-describing in a log line, which matters because the audit trail's whole job is to be
readable by someone who was not there.

Rejecting the alternative for the record: keeping the bare verbs and letting `target_type` carry the
subject reads fine in a table with columns and badly in a log line, an alert, or a metric label, where
the action arrives alone.

**Impact if wrong**: A rename before any data exists. After data exists it is an `UPDATE` on an
append-only table, which A-121 and ADR-0025 make deliberately hard — which is the argument for settling
it now.
