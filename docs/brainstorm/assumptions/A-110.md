# A-110 — A person joins a workspace by an Admin creating the account; there are no invitations

**Statement**: An Admin adds a member by entering an email address and a name; the system creates the
`user` row and an initial password that the Admin hands over out of band, and the person is required to
change it at first sign-in. There is no invitation link, no pending-member state, and no self-service
sign-up.

**Rationale**: An invitation is an email, and A-071 decided no email ships in the MVP. Building an
invitation flow with no channel to deliver it means building a token, an expiry, a redemption page, and
a pending state that nothing can ever leave — a state machine whose only trigger does not exist.
Self-service sign-up is worse: it lets anyone who reaches the URL create an account, in a product whose
top adoption barrier is reluctance to put prompts where others can see them (BR-01).

Handing over a first password out of band is unglamorous and is what a pilot inside one group actually
does. The forced change at first sign-in is what keeps the Admin from knowing a password the member
keeps.

**Impact if wrong**: An invitation flow is additive and lands the day A-071 does. No data model changes
— a pending member is a `workspace_member` row with a status column.

## Superseded in part, 2026-08-17 — ADR-0056 and ADR-0057

Three of this assumption's clauses no longer hold, and the last paragraph above turned out to be
exactly right about what it would cost.

1. **Self-service sign-up exists** and predates this change (`POST /api/v1/auth/register`, ADR-0052):
   without it an install with no accounts could be deployed and then not signed into, because every
   other door was behind a door. What that route does *not* do any more is create a workspace
   (ADR-0056).
2. **Invitations exist** (ADR-0057), and the objection this assumption raised is answered rather than
   overridden: there is still **no email**, and A-071 is untouched. An invitation is a six-character
   code somebody reads out, or a seat reserved against an address and claimed when that address next
   signs in. Nothing is delivered.
3. **A pending state exists and can be left**, which is the specific thing this assumption said could
   not be built. Its trigger is an administrator pressing Approve — a person, not a channel — and it
   is exactly the shape predicted here: *"a `workspace_member` row with a status column"*.

**What survives unchanged**: an Admin adding a member by creating the account with a handed-over
initial password, the forced change at first sign-in, and `must_change_password` enforced at the
session boundary. That flow is still the only one that creates an account for somebody else, and it
sits beside the invitation rather than being replaced by it.
