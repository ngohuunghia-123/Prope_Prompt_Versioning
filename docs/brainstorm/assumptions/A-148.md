# A-148 — Request bodies are capped at the ingress, because the gateway's inbound size was the one input nothing bounded

**Statement**: Written by the step-6 sweep, pass 3 (STRIDE — denial of service). Caddy refuses a
request body over **1 MiB** on every route; the gateway additionally refuses a composed upstream
message set over **256 KiB** with an OpenAI-shaped `400`, counted by
`prope_gateway_oversize_request_total`.

## What was actually missing

Prope caps almost everything it stores and nothing it receives:

| Already bounded | Where |
|---|---|
| Prompt body ≤ 32 KiB, change summary ≤ 200 chars | [[A-050]], enforced at the edge |
| Stored call body | per-body cap; oversize is **dropped and counted**, never truncated into a log line |
| Eval case input | length-bounded before the `regex` assertion runs |
| Concurrent gateway calls per key | 20 ([[A-143]]) |
| Login attempts | 5 / 20 per 15 min ([[A-144]]) |

**The caller's `messages` array on `POST /v1/chat/completions` was bounded by nothing at all.** It is
the one field on the one internet-facing route that an unauthenticated-until-checked caller controls the
size of, on a host with **8 GB of RAM and no HA** (ADR-0033), and it is held in memory *twice* on the
way through — once by the gateway composing the upstream call, once by call-ledger's record on the way
out. The stored-body cap fires at the end of that path, which is after the memory has been spent.

A single 500 MB POST is a cheaper outage than anything else in the threat model, and
`00_context.md#constraints` records that *a Prope outage is a full outage* for every consuming product.

## Why two limits rather than one

- **Caddy's 1 MiB** is the blunt one and it protects the process before any Python object exists. It
  applies to `/api/*` too, where a revision body is capped at 32 KiB anyway, so the ceiling is far above
  anything legitimate.
- **The gateway's 256 KiB** on the *composed* message set is the one that means something. It is
  roughly 64k tokens of conversation — well past any prompt a reviewer would approve, and it is the
  number that keeps the ledger's stored body in the range `call_body`'s sizing assumed (~10 KB average,
  ADR-0033).

Both are configuration, not code.

## What this deliberately does not do

It does not rate-limit by bytes per second, does not queue, and does not truncate. A refusal is an
OpenAI-shaped `400` the caller's SDK already understands — the same posture as [[A-143]]'s 429 and for
the same reason: **on the hot path a queue is just a slower error**, and a silently truncated
conversation is a wrong answer rather than a refused one.

**Impact if wrong**: set too low, a legitimate long-context consumer is refused — visible immediately in
`prope_gateway_oversize_request_total`, fixed by one number in the Caddyfile and one in settings. Set
too high, it protects less than it should. Neither carries a schema.
