# A-080 — The resolution cache is a bounded TTL-only LRU

**Statement** (amended 2026-08-09): The gateway's resolution cache is an in-process LRU of at most 5,000
entries, keyed by `(workspace_id, model_name, pin)`, with a 30-second TTL. **Nothing invalidates it** —
a release, a restore, and a withdrawal all become visible when the entry expires, within 30 seconds,
with no coordination between processes. An expired entry is never served. The cache is never persisted
and is correct to rebuild empty.

> **The 5-minute stale-if-error window is DELETED, 2026-08-09 (step 4, gateway's stack pass).** Its
> trigger was *"when prompt-registry is unreachable"* — a state ADR-0026 and ADR-0033 removed, because
> prompt-registry is an in-process function call in the same container. "Unreachable" resolves to *the
> database is unreachable*, and A-114 puts two **uncacheable** access-control reads ahead of the registry
> read on every request, so authentication fails on that same database first and the stale entry is
> never consulted.
>
> Deleted with it: `prope_gateway_stale_resolution_total`, the `GatewayStaleResolution` page, the
> `cache = stale` label, the `prope.stale_resolution: true` response marker, one failure mode, one risk
> row, and a chaos test that cannot be performed. ADR-0012 carries the full amendment and the reason
> the TTL itself survives.
>
> The rationale paragraph below is left as written, and **two of its sentences are now wrong**: the
> stale-if-error justification, and the claim that failing closed on a registry blip would be the
> alternative. There is no registry blip distinct from a database blip. They are kept rather than
> edited because what this assumption got wrong is the useful part of the record.

**Rationale**: A-031 said the cache is "invalidated immediately on release or restore", and no
mechanism for that exists: the write happens in prompt-registry, the cache lives in the gateway's
memory, prompt-registry → gateway is a forbidden edge, and A-012 rules out a broker. The TTL is the
only honest answer, and the budget affords it — 30 seconds inside a 5-minute restore target is roughly
10× headroom. The safety property that makes it acceptable: a stale entry can only serve a revision
that was released, and the released pointer can only ever have been Approved (a database constraint,
BR-03), so staleness delays a change and cannot put unapproved text into production. Stale-if-error
exists because Prope is an accepted hard dependency of other products' request paths; failing closed
on a registry blip would turn it into a full outage of every consuming product. Full reasoning and the
six rejected mechanisms in ADR-0012.

**Impact if wrong**: The TTL and the stale window are configuration. Adding a push-invalidation later
would be a new seam and a reversal of a forbidden edge, which is why the reasoning is in an ADR rather
than only here.
