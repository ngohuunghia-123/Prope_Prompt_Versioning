# A-048 — Revision numbers are allocated inside the creating transaction, arbitrated by a unique constraint

**Statement**: `revision_number` is a per-prompt counter allocated inside the transaction that creates
the revision, with `unique(prompt_id, revision_number)` as the arbiter. Numbers are gapless and a failed
create allocates nothing. On collision the loser retries once; a second collision returns "someone else
saved first" with the author's text preserved client-side.

**Rationale**: Users read "revision 7" and reason about it; a sequence that burns numbers on failed
attempts produces gaps that look like deleted history in a product whose entire pitch is that history is
intact (ADR-0002). The unique constraint rather than an application check is what makes the guarantee
survive a second process. Two people editing one prompt at once is the normal case in a team that today
keeps prompts in a shared chat, so this is a first-week scenario, not a scale concern.

**Impact if wrong**: Swapping to a sequence or an advisory lock is a change inside one repository
function.
