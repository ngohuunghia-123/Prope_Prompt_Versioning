# A-095 — Every upstream failure carries a class, an origin, fallback_eligible, and retryable as four separate facts

**Statement**: A failed dispatch returns `class` (one of `credential_rejected`, `rate_limited`,
`upstream_unavailable`, `timeout`, `model_not_available`, `content_filtered`, `invalid_request`,
`provider_contract_violation`), `origin` (`provider` or `prope`), `fallback_eligible`, and `retryable`
with `retry_after_ms` when known. provider-access sets all four; the gateway reads
`fallback_eligible`, evaluation reads `retryable`. `content_filtered` and `invalid_request` are
**not** fallback-eligible. Full reasoning and rejected alternatives in ADR-0017.

**Rationale**: The distinction the gateway's whole fallback branch rests on (A-034) and the one
evaluation's `error`-versus-`fail` rule rests on (A-057) are the same underlying judgement, and making
it requires provider knowledge that only lives in this module's adapters. Deciding it once, here,
prevents two provider matrices that will drift invisibly — both modules would keep working, they would
just disagree about what happened.

Four facts rather than one bit because they genuinely vary independently: a rate limit is retryable
and fallback-eligible, a rejected credential is fallback-eligible and not retryable, a content filter
is neither, and `origin` is what keeps "the provider throttled us" separate from "Prope's own
admission gate shed us" (ADR-0016).

**Impact if wrong**: Adding a class is additive. Changing what `fallback_eligible` means for an
existing class changes production behaviour in a module that cannot see the decision, which is why the
table is unit-tested as a table and the class is written into every call record.
