# A-094 — The MVP ships one adapter kind, OpenAI-compatible with a configurable base URL

**Statement**: `provider_config.adapter` has one value in the MVP: `openai_compatible`, taking a base
URL and a bearer credential. A workspace points it at OpenAI, Azure OpenAI, Groq, Together, Fireworks,
OpenRouter, or a self-hosted vLLM or Ollama endpoint, and no translation is needed because the wire
shape is already the one ADR-0015 makes canonical. Anthropic's Messages API and Google's Gemini API
are named as the first two additive adapters and are out of the MVP.

**Rationale**: The whole system is already OpenAI-shaped by a non-negotiable constraint, so the
zero-translation adapter is the first one to build under every possible answer to OQ-016. One adapter
kind reaches most of the market for the cost of an HTTP client; a second reaches one vendor for the
cost of a translation layer, a streaming reframe, a usage-object parse, and its own share of
ADR-0017's classification table.

**Confirmed by the user 2026-08-08** (OQ-016): "OpenAI compatible first, I'll build a distinguish SDK
after MVP." A second adapter is post-MVP work with a named owner, not a schedule risk inside this
build.

**Impact if wrong**: An adapter, not a rewrite — the `adapter` column and ADR-0015's normalisation
boundary exist so a second one is additive. The cost is schedule, and it is real: a non-OpenAI adapter
is the kind of work that looks small until the streaming path.
