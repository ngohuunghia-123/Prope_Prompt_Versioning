# A-152 — Observation is off by default, enabled per consumer key by one nullable column, and that column also names who pays

**Statement**: `access.api_key` gains `observe_provider_config_id text NULL`. NULL — the default and
the value every existing row already carries — means the key behaves exactly as it does today: an
unresolvable model name is a 404 and nothing is forwarded. A non-NULL value both enables ADR-0059's
forwarding mode for that key and names the `provider_config` whose credential pays for a forwarded
call. Setting it to a configuration that does not verify is refused at the moment it is set, not at the
moment traffic arrives.

**Rationale**: three questions collapse into one column, and each of the three has a bad answer
available.

*Is it on?* A per-workspace switch is the obvious shape and the wrong one. Observation is how a team
tries Prope against production traffic; the blast radius of getting it wrong should be one integration,
revocable in one row, and visible on the screen that already lists what a key may resolve (A-081). A
workspace-level flag turns one team's experiment into every team's.

*Who pays?* The bearer slot is already occupied by the Prope key, so the caller cannot present a
provider credential even if A-025 permitted it — and A-025 does not. Something has to choose among a
workspace's provider configurations, and the alternatives are worse: a workspace default is another
setting, and inferring it from the caller's model name means Prope guessing which account a customer
wants billed.

*Default-deny.* The column defaults to NULL for the reason `scope_model_names` defaults to `'{}'`:
a capability that arrives by upgrade rather than by decision is the one nobody audits.

**Impact if wrong**: If observation turns out to belong at the workspace level, the column moves and
the key-level value becomes an override — additive, one migration, no behaviour lost. If a workspace
needs a forwarded call to bill differently per model, this becomes a small table instead of a column,
which is the same shape `scope_model_names` would take under the same pressure.
