# A-037 — Logging is off the response path: metadata durable, bodies best-effort

**Statement**: The gateway forwards and responds first, then hands the call record to an in-process
background writer through a bounded queue. No external message broker. The record is split: the
**metadata** part (prompt, version ID, consumer, timestamp, tokens, cost, outcome) is durable — under
pressure the writer applies backpressure to a local spill file rather than dropping it. The **bodies**
are best-effort and are dropped first when the queue is full, incrementing a visible counter.

**Amended 2026-08-09 (step 4).** The **"No external message broker"** sentence is superseded by
ADR-0028: the call record is published to RabbitMQ and written by the `worker` service. Everything else
in this assumption stands and most of it matters more, not less:

- The **split** between durable metadata and best-effort bodies is unchanged, as is the drop counter.
- **Enqueue still happens after the response is flushed** (A-087), so this path remains outside the p95
  span by construction — the broker changes the destination, not the ordering.
- **A-099's caller-generated `call_id` and the upsert become load-bearing rather than merely prudent.**
  RabbitMQ delivers at least once, so a redelivery would double-count workspace spend and move every
  later cost delta. What was a crash-recovery safeguard is now protection against routine broker
  behaviour.
- ~~A publish failure on this path is counted and dropped, never raised — the same rule this assumption
  already set for body drops, for the same reason.~~ **Corrected 2026-08-09 by ADR-0041, later the same
  day.** That clause contradicted call-ledger's own lock, which says metadata drops must stay 0 and
  page, and `00_context.md#success`, which states the metric as 100%. A failed publisher confirm now
  falls back to a **direct inline PostgreSQL write of the metadata**, counted as
  `fallback_direct_write_total`. Bodies are still dropped in that path — the original rule was right
  about them and wrong about metadata.
- **The spill file, its replay, and the `/readyz` spill-directory clause are removed** (ADR-0041). The
  broker holds what the in-process queue held, and PostgreSQL — already a harder dependency than
  RabbitMQ, since nothing in Prope works without it — holds what the spill held. Metadata is dropped
  only when both are unavailable.

**Rationale**: "Redirect trước, lưu logs sau" is the user's instruction and this is its mechanism.
The split exists because two success metrics depend on different halves: "100% of gateway calls
record a version ID" is an accountability claim that cannot tolerate loss, while bodies exist for
later improvement and can. A-012 rules out a broker, so the buffer has to live in-process. A dropped
body that is silently dropped would make the traceability claim false, hence the counter.

**Impact if wrong**: Moving to a real queue later changes the writer, not the gateway. Discovering
after the fact that metadata was being dropped would invalidate the audit trail, which is why the
two halves are separated now rather than later.
