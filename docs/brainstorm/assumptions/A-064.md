# A-064 — Release-control changes revision status by command; prompt-registry performs the write

**Statement**: Release-control writes only `approval`, `release`, and `review_task`. A revision's status
moves when release-control calls `set_revision_status(version_id, status, decision_id)` on
prompt-registry, which validates the transition and performs the write. `decision_id` names the approval
or release row that authorised it.

**Rationale**: `prompt-registry.lock.yml` originally stated that `revision.status` is "written only by
release-control's approval flow", which puts a second writer on a table prompt-registry owns. The system
already solved the identical problem for the released pointer (A-041, ADR-0001) and nothing about status
is different in kind. It also matters for the strongest guarantee in the product: BR-03's Approved-only
rule is a database constraint, and a module that can write the value the constraint reads can defeat it.

**Impact if wrong**: One function call becomes one UPDATE. Cheap in either direction. See ADR-0008.
