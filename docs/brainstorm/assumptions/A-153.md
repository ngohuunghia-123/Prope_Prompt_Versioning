> **⚠️ SUPERSEDED BY [[A-156]] on the day it was written, and its premise was wrong rather than
> narrow.** The rule below keys on `MissReason.UNKNOWN_MODEL`, and **no real unmanaged model name
> produces that value**: a bare name like `gpt-4o` fails `ModelName.parse` and is refused before
> `resolve_binding` runs at all, and a slash-carrying name like `openai/gpt-4o` is refused by
> `may_resolve` as `NOT_PERMITTED` before resolution runs, because a key's scope is a list of prompt
> names and a provider's model is not one. ADR-0059's forwarding mode, as specified under this
> assumption, could not fire. ADR-0062 records the trace and A-156 replaces the rule with a
> namespace-shaped one.
>
> **What survives is the reasoning below, not the rule.** Every argument in the Rationale — the
> enumeration oracle, the governed prompt un-governing itself — is why A-156 decides at the namespace
> rather than at the name. This file is kept rather than deleted so the argument stays readable and so
> the mistake stays visible; a superseded assumption that reads like a narrowing is how the original
> error stays quotable.

# A-153 — Only an `UNKNOWN_MODEL` miss may be forwarded; the other four refusals are unchanged *(superseded)*

**Statement**: ADR-0059's forwarding mode is reachable from exactly one of `MissReason`'s five values.
`UNKNOWN_MODEL` on an observe-enabled key is forwarded upstream and observed. `NOT_PERMITTED`,
`NO_RELEASE`, `PIN_NOT_FOUND` and `PIN_NOT_APPROVED` return the same OpenAI-shaped 404 they return
today, for observe-enabled and observe-disabled keys alike, and write no observation.

**Rationale**: the mode is a hole in a refusal surface, and the shape of the hole is the whole security
argument. Two of the four excluded reasons are excluded for reasons that outrank the feature.

**`NOT_PERMITTED` is an enumeration oracle the moment it diverges.** A-116 makes a scope refusal
byte-identical to an unknown model name precisely so a leaked key cannot discover what a workspace has
registered. If an observe-enabled key got a forwarded response for a name it is not scoped for and a
404 for a name that does not exist, the difference *is* the oracle — and it is a worse one than the
original, because the distinguishing response costs the workspace money at a provider.

**`NO_RELEASE` would let a governed prompt quietly un-govern itself.** That name belongs to a prompt
somebody registered. Forwarding it means the caller goes on serving their own inline copy while Prope
files the traffic as unmanaged. Every other refusal in this product fails toward *less* is served;
this one would fail toward *something else* is served, which is the direction nothing here fails in.

The mechanism costs nothing, which is worth recording: `resolve_binding` already computes the reason
and already labels `resolve_miss_total` with it. The distinction being relied on exists in the code
before the feature does.

**Impact if wrong**: If forwarding a registered-but-unreleased name turns out to be wanted — the
plausible request, phrased as *"let it keep working until we release"* — it is a third mode and needs
its own decision, because it means Prope knowingly serving an unapproved body. It is not a widening of
this one.
