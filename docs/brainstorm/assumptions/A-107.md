# A-107 — A price row carries an explicit currency; a workspace uses one currency and there is no conversion

**Statement**: Every `price_table` row states its currency, and every stored cost carries the currency
it was priced in. A workspace's price rows must all share one currency, and figures are displayed in
it. There is no FX rate and no conversion anywhere in the MVP.

**Rationale**: Providers bill in their own currency — usually USD — and this group is Vietnamese, so
displaying VND is the obvious ask. It is also a second effective-dated table: an FX rate has a date,
a source, and the same "does editing it rewrite history" problem ADR-0019 just solved for prices, and
getting it wrong makes every stored figure depend on a rate nobody reviewed.

Storing the currency explicitly rather than assuming one costs a column and keeps every option open.
A workspace that pays in USD and wants VND on screen can have it later by adding rates; a system that
stored bare numbers could not, because nobody would know what the old ones meant.

**This is worth the user's attention** even though it did not pass the decide-or-ask test: a
Vietnamese team may reasonably expect VND on a cost-delta screen from day one, and this decision means
they will see USD unless they enter their price rows in VND themselves. Overturn it by saying so; the
column is already there.

**Impact if wrong**: An FX rate table and a display layer, both additive. Nothing stored has to change,
because the currency is on every row.
