# A-135 — `.env` may hold several KEKs, and `kek_version` selects among them

**Statement**: `credential.kek_version` has existed since the module was locked and ADR-0032 never gave
it a meaning — it settled *where* the key-encryption key lives (a single `.env` on the VM, `0600`,
git-ignored, loaded as a `pydantic-settings` `SecretStr`) but treated it as one value. A column named
for a version implies more than one.

The convention: `.env` holds one or more `PROPE_KEK_V<n>` entries. **The highest `n` present is the
wrapping key** — every new or rotated credential's data key is wrapped with it and the row records that
`n`. Older entries stay only as long as rows still reference them, and unwrapping selects by the row's
own `kek_version`. A KEK rotation is therefore three steps and no schema change:

1. Add `PROPE_KEK_V2` to `.env` and restart. New credentials wrap with V2; existing rows still unwrap
   with V1.
2. Run a one-off re-wrap command that reads every `credential` row, unwraps its data key with its
   recorded version, re-wraps with V2, and updates `wrapped_dek` and `kek_version`. **The plaintext
   credential is never touched** — only the wrapped data key is, which is the property envelope
   encryption was chosen for (ADR-0014).
3. Remove `PROPE_KEK_V1` once no row references it, verified by a query rather than by assumption.

**Rationale**: The alternative is a single unversioned key, which makes rotation an all-or-nothing
rewrite performed with the system down — and makes the existing column a lie. Recording the convention
now costs a naming rule and a command that step 6 will scope; discovering it during an actual key
compromise costs the design decision under the worst possible conditions.

Step 2 is the only genuinely new work, and it is small precisely because ADR-0014 chose envelope
encryption: the re-wrap touches `wrapped_dek` and nothing else, so it needs no provider access, no
network, and no downtime. Without envelope encryption it would be a decrypt-and-re-encrypt of every
secret in the system.

**Impact if wrong**: If a rotation is never needed, this costs one naming convention and an unwritten
command. If the KEK is ever compromised and this is not in place, the recovery is to re-enter every
provider credential by hand from every workspace — which is the same recovery ADR-0032 already names for
*losing* the key, except here it would be avoidable. The re-wrap command is not built during step 4;
this assumption is the record that it is owed, and ADR-0032's cloud-KMS upgrade path would supersede
the whole mechanism rather than extend it.
