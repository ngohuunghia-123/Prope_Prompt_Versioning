# A-146 — Personal data is classified per column, and encryption at rest stays disk-level rather than column-level

**Statement**: Written by the step-6 sweep, pass 2. Prope's 27 tables were classified column by column
rather than by asking which ones "feel sensitive".

## Directly identifying — one table

| Column | Class |
|---|---|
| `access.user.email` | **PII.** Unique index, so it is also the login identifier |
| `access.user.display_name` | **PII** |

That is the whole list. Everything else that identifies a person is an opaque `usr_` ULID.

## Pseudonymous — an id that identifies a person only via `access.user`

`history_event.actor_id` · `call_record.actor_id` · `session.user_id` · `revision.author_id` ·
`approval.reviewer_id` · `release.released_by` · `prompt_property.owner_id` ·
`prompt_grant.grantee_user_id` · every `created_by` / `granted_by` / `closed_by` / `updated_by`.

**These are borderline by construction and the decision is deliberate**: they are values, not foreign
keys ([[A-122]]), so they survive the deletion of the row they point at. That is what makes OQ-017's
cheapest option free, and it is why the classification is written down rather than assumed.

`session.user_agent_hash` is hashed at write and is pseudonymous at worst.

## Content that may contain anything, including personal data

`revision.body` · `prompt_property.search_text` (**a second copy of the body**) · `revision.fallback_answer` ·
`call_body.request_body` · `call_body.response_body` · `eval_case.input_messages` ·
`eval_case.input_variables` · `case_result.output_content` · `approval.comment` · `approval.acknowledgement_reason` ·
`release.reason` · `review_task.closed_note` · `history_event.reason`.

**Prope cannot classify these** — they hold whatever a workspace put in them, which is precisely
**OQ-013**, and **A-020** holds the line meanwhile: no real corporate prompts until the baseline is
signed off. The free-text human sentences at the end of that list carry a rule the build already
enforces: stored and rendered in the property history, **never in a log line or a metric label**
([[A-046]]), because they can name a customer or an incident.

## Secrets — not PII, and handled by their own decisions

`credential.ciphertext` / `wrapped_dek` (envelope-encrypted, ADR-0014) · `user.password_hash`
(argon2id, ADR-0043) · `api_key.key_hash` (HMAC-comparable digest, ADR-0021). **Same word, three
storage classes, and the reason each differs is the direction of use** — a credential is *presented*, a
password and an API key are only ever *verified*.

## Encryption at rest: the posture, stated rather than assumed

**No column-level encryption is added for PII. `credential` remains the sole exception.**

This is a deliberate departure from the reflex answer, and the reasoning is the project's own:

- **The user already decided the harder case.** Prompt bodies — the asset the whole product exists to
  protect, and a strictly larger exposure than two name-and-email columns — were raised as a
  candidate for encryption at rest in an earlier pass and dropped. Encrypting `email` while
  `revision.body` sits in plaintext beside it would be security theatre with a maintenance cost.
- **ADR-0014's envelope encryption defeats one specific threat**: a stolen dump or a stray `SELECT`
  yielding a *usable third-party secret*. An encrypted `email` column defeats nothing comparable —
  the application must read it on every login, so the key must be as available as the data.
- **The dominant threat is host compromise**, and ADR-0032 already names cloud KMS as the upgrade path
  triggered by A-020's sign-off. That is the lever that would move this, and it moves everything at
  once rather than two columns.

What holds instead: RLS deny-by-default on every table (ADR-0045), the `credential` envelope, the
`.env` backed up separately from and never alongside the `pg_dump` (ADR-0032, ADR-0036), and
[[A-046]]'s never-logged list.

**The gap this leaves, named:** a stolen disk image or an unencrypted backup medium yields every
prompt body and every email address in plaintext. ADR-0032 says so about the KEK's threat model
already; this records that the same sentence is true of the data.

**Impact if wrong**: adding column encryption later is a migration plus a key-management story, which
is why this is `reversibility: moderate` rather than cheap. The classification itself costs nothing and
is what OQ-017 needed in order to be askable.
