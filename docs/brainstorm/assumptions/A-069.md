# A-069 — Withdraw release clears the pointer by command, needs its own permission and a reason

**Statement**: Withdrawing a release is a `release` row with `kind = withdraw`, `version_id` NULL, and
`previous_version_id` naming what was removed. It requires a permission distinct from release, a
mandatory reason, and a confirmation naming the model name. The pointer is cleared through a new
prompt-registry command, `clear_released_revision(prompt_id, release_id)` — a separate command rather
than a NULL argument to `set_released_revision`, so the Approved-only database constraint gains no NULL
carve-out. Afterwards the gateway returns model-not-found; it never serves the previous revision and
never serves the fallback answer.

**Rationale**: A-052 named this action while locking prompt-registry and deferred its specification to
this module. `00_context.md#constraints` accepts Prope as a hard dependency of other products' request
paths, so a withdrawal is an outage in someone else's system — it earns its own permission and its own
recorded reason. Reusing the release log rather than adding a fourth entity keeps one query answering
"what has been in production, and when" (ADR-0007).

**Impact if wrong**: The command and the permission would have to be unpicked from the registry's API
and the role matrix. Moderate because prompt-registry's contract changes with it. See ADR-0009.
