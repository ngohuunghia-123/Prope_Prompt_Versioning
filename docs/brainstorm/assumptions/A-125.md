# A-125 — Event order is a monotonic sequence, not a timestamp

**Statement**: `history_event` carries a database-assigned monotonic `seq` in addition to its RFC 3339
`occurred_at` (A-003). Every ordering — the Activity feed, the release trail, cursor pagination — is by
`seq`. The timestamp is displayed and is used for durations; it is never used to sort.

**Rationale**: Two events routinely share a timestamp. Approve-and-release is one request that writes two
rows in one transaction (A-076), and a break-glass release writes a release event and opens a review task
in the same breath. Sorted by timestamp, "approved" and "released" appear in whichever order the database
returns them, and the one screen whose job is to show the sequence of decisions shows them in an
arbitrary order roughly half the time. Cursor pagination (A-045) needs a total order for the same reason
and gets a wrong or repeating page without one.

**Impact if wrong**: None foreseen while one database holds every module (A-012, ADR-0023). If that
changes, a shared sequence is no longer available and ordering within a transaction has to be carried
explicitly — which is worth knowing before the split, not after.
