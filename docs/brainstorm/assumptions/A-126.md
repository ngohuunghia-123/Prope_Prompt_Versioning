# A-126 — The two audit-event Success metrics are computed by SQL during the pilot, not by a product surface

**Statement**: Two rows in `00_context.md#success` are measured from audit events — restore time
(decision → the gateway serving the restored revision) and median review turnaround (submitted →
decided). Both are hand-run SQL against the database during the pilot review. Neither becomes an
endpoint, a dashboard, or a scheduled job.

Median review turnaround is answerable from `history_event` alone: `revision_submitted` →
`revision_approved | revision_changes_requested`, matched on `target_id`. Restore time is **not** — its
second half is the first `call_record` carrying the restored `version_id`, and `call_record` belongs to
call-ledger, which is a sink no module may read from.

**Rationale**: The measurement column in the Success table describes how a metric is verified, not a
feature. Building a surface for the restore metric would mean an edge into call-ledger — the one edge the
map forbids outright — for a number read once at the end of a pilot. Writing that down is the point:
without it, "the context file says we measure this" is a plausible argument for adding the edge, and the
argument would be made by someone who had not read the forbidden-edges list.

Note also that `00_context.md` names the restore event as `restore_requested`, which no module writes.
The event is `revision_restored` (A-120), stamped when the release commits — which is the moment the
metric means by "decision" anyway.

**Impact if wrong**: A reporting job reading two tables outside the request path, which is a different
thing from a module-to-module edge and does not create one.
