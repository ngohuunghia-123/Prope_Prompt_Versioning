# A-054 — Eval runs are claimed and executed by `worker` at concurrency 5; the client polls; a sweeper reaps interrupted runs

**Statement** (rewritten 2026-08-09 by ADR-0049): `POST /eval-runs` validates, writes one `queued` run
row per suite in the `app` container, and returns 202 with one run id each in under 200 ms. Execution
happens in the **`worker` container**, which polls at 1 s and claims a `queued` row with
`SELECT … FOR UPDATE SKIP LOCKED`, checking A-063's `max_concurrent_runs` as a predicate inside the same
transaction that sets `status = 'running'`. The row lock is released at the claim; the run then
dispatches at most **5** cases concurrently. The client polls `GET /eval-runs/{id}`. A sweeper in
`worker` — on startup and on a 60 s timer — marks any `running` run whose case results have not advanced
for 5 minutes as `interrupted`, leaving its completed case results readable.

> **Rewritten 2026-08-09 (step 4, evaluation's pass) by ADR-0049, resolving the flag this file carried
> since Stage 1.** ADR-0028 introduced RabbitMQ and a `worker` service, which removed the premise the
> rationale below opens with. The executor moved to `worker` and the sweeper's *"this process"* now means
> that container.
>
> **The prediction in "Impact if wrong" is what actually happened**, and it is worth recording that it
> held: *"the run's state lives in the database rather than in the worker."* Because it did, the move
> cost a claim query and nothing else. The 202-and-poll contract, the per-run concurrency of 5, the
> `interrupted` state and the 5-minute no-progress rule all survive verbatim. Only *where the loop runs*
> changed.
>
> **What did not happen is the obvious thing.** The broker was bought and then declined: `eval_run.status`
> is already a queue, and RabbitMQ redelivery of an unacked message would re-dispatch every case on a
> crash — spending the workspace's own key on a run nobody asked for, against AC-7 and against this
> file's own *"Re-running is one click and costs a new run."* ADR-0049 carries the full argument.
>
> A-063's per-workspace bound was restated in the same pass and is now the `max_concurrent_runs`
> predicate quoted above; its old dispatch clause is superseded by ADR-0046.

**Rationale**: A-012 forbids a broker and a separate worker fleet: one `docker-compose up` has to bring
the whole system up for a team with no ops. A 120 s p95 run (`00_context.md#success`) is far too long to
hold an HTTP request open, so the work has to be detached even without a queue. Concurrency of 5 gives
four waves for a 20-case suite and holds the 120 s budget up to roughly 30 s of mean upstream latency,
while staying polite enough not to trip a provider's rate limit on a workspace's own key. Polling is
chosen over server-sent events because the review screen already re-renders on a decision, and one
transport is one thing to debug at 3am.

**Impact if wrong**: The seam is a job interface with one implementation. Moving to a real queue later
means replacing the background task and the sweeper, not the run model — which is why the run's state
lives in the database rather than in the worker.

**Still true after the rewrite.** The claim loop is the second implementation of that seam and it cost
exactly what this paragraph predicted. A third — a broker consumer, if one is ever wanted — replaces the
claim query and nothing above it.
