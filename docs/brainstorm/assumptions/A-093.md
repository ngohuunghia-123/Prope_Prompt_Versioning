# A-093 — A dispatch carries a priority class, and batch yields to interactive at the provider seam

**Statement**: `dispatch()` takes `priority: interactive | batch`. The gateway passes `interactive`,
evaluation passes `batch`. Each `provider_config` carries `max_concurrency` (default 32) and
`reserved_interactive` (default `max(4, 25%)`). Batch dispatches occupy at most
`max_concurrency - reserved_interactive` slots; interactive dispatches never queue behind batch and
fail fast rather than waiting. On a provider 429, batch admission halves for a cooldown and
interactive is untouched. Full reasoning and rejected alternatives in ADR-0016.

**Rationale**: One credential serves both classes because OQ-004's answer was one dashboard, and a
provider's rate limit applies to the account rather than to the caller's intent. ADR-0006's named
suites mean one submit can launch five runs of 10–20 cases at once, so the collision is not
hypothetical. Without a priority order, a reviewer clicking Submit degrades a consuming product's
request path — the precise incident `positioning.md` §11 identifies as the developer veto.

Evaluation's own global bound (A-063) stays and sits above this: it caps what one workspace's runs may
ask for, while this decides who gets admitted when both classes ask at once.

**Impact if wrong**: The numbers are per-configuration columns, so tuning is a settings change. What
is moderate rather than cheap is `priority` itself — it is on an interface two modules build against,
and adding it later means changing that interface after both have been written.
