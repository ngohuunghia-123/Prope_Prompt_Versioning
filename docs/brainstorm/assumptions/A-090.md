# A-090 — A provider configuration is verified by a live probe before it can be bound to a revision

**Statement**: Creating a configuration, rotating its credential, or pressing Verify runs a live
probe against the provider — a model-list call plus one minimal completion — with a 10-second
timeout and one attempt. The result is stored as `last_verified_at`, `verification_status`, and
`verification_error`. A configuration that has not passed cannot be bound to a revision, and dispatch
refuses it. The probe is also where A-030's admission rule is enforced: a provider whose response
carries no usage object fails verification and is never saved active.

**Rationale**: Without a probe, the first test of a credential is a production call, and its failure
arrives as a fallback answer served to a customer with `credential_rejected` buried in a call record.
Checking at the moment someone is looking at the screen they just filled in is the cheapest possible
place to fail.

The admission half discharges an obligation ADR-0013 left open in writing: "a provider that ignores
`include_usage` fails A-030's admission rule and is a provider-access admission question, not a
gateway workaround." This is the admission question, answered.

**Impact if wrong**: The probe becomes advisory rather than blocking — a warning on the dashboard
instead of a refusal. That is a smaller change than it sounds, but it moves the discovery of a bad
credential back onto live traffic, which is what this exists to prevent.
