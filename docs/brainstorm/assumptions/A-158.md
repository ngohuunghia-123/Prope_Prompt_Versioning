# A-158 — A key is scoped by namespace and by name, and the union is the answer

**Statement**: `access.api_key` carries both `scope_model_names text[]` and
`scope_namespaces text[] NOT NULL DEFAULT '{}'`. INT-004 resolves a model name when it appears in
`scope_model_names` **or** its namespace appears in `scope_namespaces`. Both default empty.

**Rationale**: the problem is real and the arithmetic is the argument. A key for a product calling a
thousand prompts needs a thousand entries under A-081, and every new release is a second administrative
act — `access-control.lock.yml` already calls that *"a cost worth watching in the pilot"*. One namespace
entry replaces the thousand, and the gateway pays nothing for it: `ModelName.parse` splits
`namespace/name` at the edge of every request already, so the namespace is a value in memory and the
check is the same single indexed read it was.

**Additive rather than a replacement**, which is the part worth defending because a replacement was
what was asked for.

*Default-deny survives byte for byte.* Both arrays empty resolves nothing, by the same `= ANY(...)`
being false for every input, with no branch anybody could forget to write. That property is A-081's and
it is not weakened by adding a second array to the same `OR`.

*Every existing key keeps working*, so this is a migration with no data step and no coordination.

*The two express different things.* `scope_namespaces` says *this product owns this folder* — the
thousand-prompt case, and the reason for the change. `scope_model_names` says *this integration may
call this one prompt in a folder it does not own* — which a namespace-only scope cannot express at all,
and which is the shape of every key that is granted access rather than given a drawer. Dropping the
name array later is one migration; adding it back after an integration needed it is a migration plus an
incident.

**Impact if wrong**: if nobody ever uses `scope_model_names`, it is dropped in one migration and this
assumption is retired having cost one column and one `OR`. If the union turns out to be confusing to
administer — two lists, one answer — the fix is in the UI, which should show the effective set rather
than the two inputs.
