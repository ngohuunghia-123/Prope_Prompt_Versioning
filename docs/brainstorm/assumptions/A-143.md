# A-143 — The gateway admits at most 20 concurrent calls per consumer key, and refuses the rest in the OpenAI 429 shape

**Statement**: `POST /v1/chat/completions` holds a per-`key_id` in-flight cap, default **20**, applied
after authentication ([[A-081]]) and before dispatch. A request arriving at the cap is refused
immediately with an OpenAI-shaped `429` carrying `Retry-After` — never queued, never delayed, never
retried on the caller's behalf ([[A-084]]). The cap is configurable per key and stored beside the key's
scope, so a legitimately parallel consumer is a settings change rather than a deploy.

**What this amends**: `gateway.lock.yml` non-goal *"Rate limiting or spend enforcement. Ceilings refuse
eval runs, never gateway traffic (A-029)"*. That line settled two different things in one clause. The
**spend** half is unchanged and stays absolute — no gateway call is ever refused because a workspace has
spent money, and [[A-029]] is the argument for it. The **admission** half was never argued anywhere; it
was carried along by the sentence it shared. This assumption separates them and decides only the second.

**Why in-flight and not requests-per-minute**: the gateway's own work is small — resolve, compose,
dispatch, stream back — and it spends nearly all of a request's life waiting on an upstream provider.
What exhausts ADR-0033's 4 vCPU / 8 GB host is therefore the number of requests *open at once*, not the
number that started in the last minute. 600 slow streaming calls and 600 fast ones cost the box wildly
different amounts, so an RPS number that protects the host cannot be derived and would be set by guess.
An in-flight count is the quantity that actually runs out, and it needs no clock.

**Why it is worth having at all**, given the build has declined ten other guards: `00_context.md#constraints`
records that *"Prope is an accepted hard dependency of consuming products' request paths | No
consumer-side fallback is assumed; a Prope outage is a full outage"*, and ADR-0033 runs that on one VM
with no HA and no rolling restart. Without a cap, one consuming product's retry loop is indistinguishable
from a Prope fault and takes every other consumer down with it. With one, the misbehaving key is refused,
the counter names it, and everyone else is served. This is the cheapest control in the product that
converts a shared outage into a labelled refusal.

**Cost**: a semaphore keyed on `key_id`, one counter, and one alert input. No new component, no new
dependency, no state outside the process — which is also its limit.

**The limit, stated rather than discovered later**: the cap is **per process**. If [[A-130]]'s gateway
split ever happens, two processes each admit 20 and the effective cap is 40. That is the same footnote
the login limiter already carries ([[A-144]], ADR-0043), and for the same reason: a bounded in-process
structure is the right size for this system and the wrong shape for two of them. It is recorded here so
the split is a decision that costs something known.

**Metrics**: `prope_gateway_admission_refused_total{key_id_bucket}` — bucketed, never the raw key id
(ADR-0030 forbids a `consumer_key` label), plus `prope_gateway_inflight` as a gauge. A refusal is an
`outcome` on the call record like any other authenticated-but-refused call ([[A-086]]).

**Impact if wrong**: too low and a legitimate batch consumer sees 429s it did not earn — visible
immediately, fixed by raising one number on one key. Too high and it protects nothing, which is where
the system stands today. Both are cheap; that asymmetry is why a default was worth setting rather than
deferring to a measurement nobody has yet.

Related: [[A-029]] for the spend half this deliberately leaves alone · [[A-084]] for why the gateway
never retries · [[A-130]] for the per-process caveat · [[A-142]] §8 for the seam's auth.
