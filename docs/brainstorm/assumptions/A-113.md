# A-113 — A consumer API key is `prope_<key_id>_<secret>`, stored as a fast hash, shown once

**Statement**: A consumer key's presented form embeds its own row id, so authentication is one indexed
read plus one constant-time SHA-256 comparison rather than a scan. The secret is 256 bits from a CSPRNG.
The plaintext appears in exactly one response — the creation one — and is never recoverable; the row
keeps `last_four` for display and `last_used_at` for finding dead keys. **Human passwords in the same
module use argon2id instead**, deliberately slow. Full reasoning and rejected alternatives in ADR-0021.

**Rationale**: A fast hash is correct for a machine-generated high-entropy secret — the slow-KDF argument
exists to make guessing a human-chosen password expensive, and there is nothing to guess. A slow KDF here
would also put tens of milliseconds on the gateway's 50 ms budget on every request, and a salted hash
cannot be indexed at all, which is what the embedded id solves.

Hashing rather than encrypting is the whole point of the contrast with ADR-0014: a provider credential
must be *presented* to somebody else, so it must be decryptable; a consumer key is only ever *verified*,
so a decryptable copy is a liability with no use.

**Impact if wrong**: Changing the wire format after keys are issued means every consumer re-keys, which
is why it carries an ADR. Changing the hash is a column and a re-issue.
