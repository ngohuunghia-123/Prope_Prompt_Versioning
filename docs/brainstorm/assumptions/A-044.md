# A-044 — Property History has one writer, one event schema, and no standalone UI

**Statement**: Every module writes state-change events through one `property-history` writer into one
append-only table with one event schema (actor, action, target type, target ID, timestamp, reason).
`property-history` exposes a read API but no screen of its own: the module that owns the subject checks
permission and then renders the events — the registry renders a property's Activity, release-control
renders a release trail. `property-history` therefore depends on nothing.

**Rationale**: Giving history its own screen means giving it a permission check, which makes it depend
on access-control, which must log grants through it — a cycle. Pushing the check up to the owning
module removes it, because the owning module has already answered "may you see this subject" before it
asks what happened to it. One schema is what makes the Success metrics computable: restore ≤ 5 min and
median review turnaround are both queries across events written by two different modules
(`00_context.md` Success), and they cannot be run over per-module log shapes.

**Impact if wrong**: A read API and a screen. The part that would be expensive is per-module event
tables, which this assumption prevents.
