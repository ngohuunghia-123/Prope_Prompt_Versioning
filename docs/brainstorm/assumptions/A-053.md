# A-053 — An eval run uses the revision's own parameters verbatim; one attempt per case; retries only on transport error

**Statement**: Each eval case is dispatched with the candidate revision's provider configuration,
upstream model, and generation parameters exactly as stored — the runner never overrides temperature,
top-p, or any other parameter. Each case is attempted once. A **transport** failure (429, 5xx, timeout,
socket drop) is retried up to twice with exponential backoff and the retries are counted in the run's
cost; an **assertion** failure is never retried. A case that passed before and fails now is labelled
`changed` and shown with both outputs, never re-rolled until it passes.

**Rationale**: A-024 puts the parameters on the revision precisely so that the caller cannot change what
runs. The eval runner is a caller. Forcing temperature to 0 would produce a clean pass/fail for a
configuration production does not use, which is a more expensive lie than a flaky column. Retrying an
assertion failure is the same lie by a different route — it converts "this prompt is unreliable" into
"this prompt passes", and unreliability is exactly what a reviewer is being asked to judge. Retrying a
429 is not the same thing: nothing about the prompt was measured.

**Impact if wrong**: A retry predicate and a loop bound. If flakiness turns out to make the suite
unusable, the additive fix is n-of-m runs with the flip rate displayed, not a silent re-roll.
