# A-119 — Every history event carries a nullable `scope_prompt_id`, so a property's Activity is one read

**Statement**: `history_event` carries `scope_prompt_id` alongside `target_type` and `target_id`. Every
event whose subject belongs to a prompt property — the property itself, one of its revisions, one of its
eval suites, one of its releases, one of its grants — stamps the owning prompt's id into that column at
append time. Events with no prompt scope (`workspace_created`, `member_added`, `role_assigned`,
`api_key_created`, `provider_configured`, …) leave it null. `GET /api/v1/prompts/{id}/activity` is
`WHERE workspace_id = ? AND scope_prompt_id = ? ORDER BY seq DESC`.

**Rationale**: The Activity view a user wants is "everything that happened to this prompt" — created,
revised, submitted, approved, released, restored, suite edited, access granted. Those events name six
different `target_type`s owned by four different modules. Without a scope column the query is either a
five-way join across tables property-history is forbidden to join to, or an `IN` list the caller has to
assemble by asking four modules for their ids first. The first is impossible and the second turns one
screen into four round trips. The column is denormalised on purpose: the appending module already knows
which prompt it is acting on, so the fact is free at write time and expensive at read time.

**Impact if wrong**: If the scope turns out to need more than one dimension, this is a second nullable
column and a backfill, not a reshape — the events are already immutable rows with a stable id.
