# A-121 — History events are never deleted and never expire; there is no retention setting

**Statement**: `history_event` rows are kept for the life of the workspace. There is no retention period,
no expiry job, and no per-workspace setting — deliberately unlike `call_body`, which has all three
(A-106). Retiring a prompt, removing a member, revoking a key, and disabling a provider configuration all
leave their events in place.

**Rationale**: The events are the product claim. "Who changed this, when, and why" stops being answerable
the moment the answer has an expiry date, and every Success metric that reads audit events measures
across the whole pilot. The reason call bodies need a retention policy does not apply here: bodies carry
customer content and are the reason OQ-013 exists, while an event carries an actor id, an action name, a
target id, and a reason string, and A-046 keeps content out of it by allow-list (ADR-0024). Storage is
not the constraint either — one row per state change is a rounding error next to one row per gateway
call.

**Impact if wrong**: If a deletion obligation is established, this becomes a job and a setting, which is
work already built once for `call_body`. What would be expensive is the opposite mistake — discovering
mid-pilot that the trail was pruned.
