# A-147 — Threats found by the step-6 STRIDE pass and accepted without mitigation, with the reason for each

**Statement**: Written by the step-6 sweep, pass 3. Every module's `security_requirements` ended with
*"STRIDE pass deferred to the step-6 sweep."* It has now run over the eight trust boundaries below.
Findings scoring **critical** or **high** became `security_requirements` rows and `test_plan.security`
entries in the owning module. The findings scoring **medium** or **low** are accepted, and the skill
requires the acceptance to be a written record rather than a silence — this is it.

## The boundaries the pass enumerated

| # | Boundary | Kind |
|---|---|---|
| B1 | internet → Caddy → gateway `/v1/*` | network, and the only anonymous-until-authenticated surface |
| B2 | internet → Caddy → management `/api/*` | network, session-authenticated |
| B3 | provider-access → the workspace's upstream provider | network, **the only egress** |
| B4 | workspace ↔ workspace | tenancy — RLS deny-by-default, four `SECURITY DEFINER` bypasses |
| B5 | `prope_app` / `prope_migrate` / `prope_report` | identity |
| B6 | `app` ↔ `worker` | process — **explicitly not a security boundary** |
| B7 | the host: `.env`, the `pg_dump`, the deploy account | host |
| B8 | `app` → RabbitMQ → `worker` | process, and it carries bodies |

## Accepted: medium

**T-M1 — a forged call record (B8, spoofing/tampering).** Anything holding the broker credentials can
publish a message that moves a workspace's spend total and lands a row in the accountability record.
*Accepted*: the credentials live in one `.env` at `0600` read by `app` and `worker` (ADR-0032), and
RabbitMQ publishes no port to the host ([[A-129]]). An attacker who can publish already has the file
that also holds the KEK, at which point this is the least of it. Mitigating it would mean signing
messages with a key stored beside the one being protected.

**T-M2 — `app`/`worker` are one identity (B6).** Same image, same `prope_app` role, same `.env`. A
compromise of the gateway is a compromise of the eval executor and the ledger drain. *Accepted, and
already written down* — `gateway.lock.yml` states it in its own words: *"the process boundary is doing
no security work here."* The structural separation the design actually relies on is ADR-0050's
sub-application, not the container. Changing this means per-module database roles, which ADR-0008 has
already established are blocked by ADR-0023's shared-transaction requirement: **a transaction lives on
one connection under one role.**

**T-M3 — the management API has no rate limit (B2).** Every route except `/auth/login` is unbounded.
*Accepted*: an abuser is by definition an authenticated member of a workspace, so the exposure is one
tenant's own person degrading one small host, and it is attributable in the logs by `actor_id`. The two
surfaces where the caller is *not* already trusted — the gateway and the login form — are both bounded
([[A-143]], [[A-144]], [[A-148]]).

**T-M4 — `prompt_grant.prompt_id` and every `actor_id` are values, not foreign keys (B4).** Nothing at
the database level stops a grant referencing a prompt in another workspace. *Accepted*: RLS makes the
grant unreadable from the other workspace, prompts are never deleted (ADR-0002), and the alternative is
a foreign key pointing in a forbidden direction ([[A-122]], [[A-096]]'s mirror case). This is a
deliberate trade re-checked rather than re-opened.

## Accepted: low

**T-L1 — Grafana, Prometheus and the RabbitMQ management UI have no authentication.** *Accepted and
already answered*: none of them publishes a port ([[A-129]]), so all three are reachable only over an
SSH tunnel by whoever already holds the deploy account. The sweep checked this expecting a finding and
found a decision.

**T-L2 — timing disclosure on `may()`.** A denied check may be measurably faster than an allowed one.
*Accepted*: the caller is already authenticated, the subject's existence is separately protected by
not-found-never-forbidden ([[A-116]]), and constant-time authorisation is not a thing anyone builds.

**T-L3 — `last_used_at` on `api_key` is a weak signal.** ADR-0021 already says so in those words.

**T-L4 — repudiation of a sign-in.** Sign-ins are deliberately not history events — they are metrics
and logs, because one event per authentication turns the audit log into an access log. *Accepted*: the
product's repudiation claim is about **state changes**, which is what property-history exists for, and
every state change carries its actor inside the same transaction.

## Two things the pass expected to find and did not

- **`prope_migrate` reachable from the running process.** ADR-0031 runs migrations *"as `prope_migrate`
  in a separate step"* of the deploy script. The credential is a deployment credential, exactly as
  ADR-0027 intended. It was **not** written down that it must therefore stay out of the `env_file` the
  `app` and `worker` services read — that is now a security requirement in access-control's lock, because
  it is the single line on which ADR-0025's append-only guarantee actually rests.
- **A cross-module transaction.** There is none. `append()` runs *inside* the caller's transaction on
  the caller's connection (ADR-0023) — one transaction, one connection, one database. No saga, no
  two-phase commit, and no distributed write anywhere in the build. Pass 4 checked for the pack's
  highest-risk shape and the answer is that ADR-0023 made it impossible.

**Impact if wrong**: each accepted item is accepted against a stated condition, and the `revisit_when`
above names the three events that change one — leaving the group, splitting the gateway, or a second
holder of the deploy account.
