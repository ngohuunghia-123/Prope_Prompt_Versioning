# A-063 — The concurrency bound is a run-admission bound, global per workspace

**Statement** (restated 2026-08-09 by ADR-0049): At most **2 runs per workspace** are in `status =
'running'` at any moment — `max_concurrent_runs`, a configuration value, checked as a predicate inside
the `FOR UPDATE SKIP LOCKED` claim transaction in `worker`. Runs beyond it stay `queued` and start as
slots free. The per-run dispatch concurrency of 5 is unchanged and belongs to A-054.

> **The dispatch clause of this assumption is deleted.** It read *"at most 10 across all runs of one
> workspace at any moment"* and is superseded by ADR-0046's `batch_concurrency` (8 per provider config,
> A-134), which as of ADR-0049 holds a semaphore in the **same process** as the eval executor. For a
> workspace with one provider config, 8 binds before 10 ever does — so the outer bound was dead code in
> the common case, and two dispatch-level semaphores in one process is the ADR-0016 defect rebuilt on
> purpose.
>
> **What survives, and why it survives, is not what this file originally argued.** The rationale below
> justifies the bound as *protection for the workspace's key* — and that job now belongs entirely to
> ADR-0046, which does it better and one layer closer to the resource. The surviving reason is
> **measurement**. Total wall-clock is identical with or without run-admission: the same dispatches
> through the same 8-slot bottleneck. But `00_context.md#success` states the 120 s target **per suite**
> and `prope_evaluation_run_duration_seconds` is labelled per run, so five interleaved runs each record
> the whole submit's duration and miss the stated metric on all five, where two-at-a-time makes two hit
> it and the rest queue visibly. That is what the lock's derived row already promised —
> *"120 s × ceil(N_suites / 2)"* — and what `prope_evaluation_run_queue_depth` counts.
>
> One property gained by accident: because the bound is now a **database predicate inside the claim
> transaction** rather than a process-local semaphore, it stays correct if `worker` is ever replicated.
> ADR-0046's cap does not. [[A-138]] records that asymmetry and the unbounded case above both of them.

**Rationale**: A-054 set a per-run bound of 5 when a prompt had one suite. Under A-062 a single submit
starts one run per suite, so five suites would put 25 simultaneous calls on the workspace's own
bring-your-own key — the exact shape of the accident A-029 exists to limit, arriving by a route A-029
does not watch (it caps spend, not concurrency). A per-run bound is not a bound at all once runs
multiply.

10 is chosen to stay under the free-tier rate limits of the providers this pilot is likely to use while
still giving a two-suite submit full parallelism. It is a number to replace after the first real run, not
a derived constant.

**Impact if wrong**: one configuration value. The visible consequence of setting it too low is
wall-clock: the 120 s p95 target is stated per suite (`00_context.md#success`), and a submit with N
suites takes roughly ceil(N ÷ `max_concurrent_runs`) suite-times — ceil(N ÷ 2) at the default, which is
the number the lock's derived performance row already states. That is a queue, not a failure, and the
run rows show it. Setting it too **high** does not increase throughput, because ADR-0046's
`batch_concurrency` is the real bottleneck; it only smears every run's duration across the whole submit
and costs the per-suite metric. Both directions are one number in configuration, no migration.
