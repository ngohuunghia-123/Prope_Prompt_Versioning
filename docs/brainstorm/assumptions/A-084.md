# A-084 — The gateway does not retry upstream; it sets one deadline

> Superseded on 2026-08-27 by ADR-0069. The replacement keeps every word of the rationale and
> changes the scope of one of them: the gateway still never re-issues a call it has already sent,
> and still never sends the same request to the same provider twice. What it may now do is try the
> NEXT provider on a revision's frozen route. The deadline stays one deadline — it became the budget
> for the whole request rather than for one attempt, which is what keeps the worst case unchanged at
> 60 s however many entries a route holds, and therefore what answers this assumption's own
> "doubles the worst case" objection rather than waiving it. A-088 is untouched: provider-access
> still performs exactly one attempt per dispatch, and the loop lives in its caller.

**Statement**: One per-request deadline, no retry. Exhausting the deadline is an upstream failure and
is therefore fallback-eligible under A-034 and A-085. Connection-level retry policy, if any, belongs
to provider-access, which owns the dispatch (A-043); the gateway does not re-issue a call it has
already sent.

**Rationale**: A retry inside the path carrying the strictest latency budget in the system doubles the
worst case to buy an outcome the fallback answer already delivers in milliseconds, and it multiplies
load against a provider that is by hypothesis already failing or rate-limiting. The eval runner
retries on transport error (A-053) because it has no latency budget; the gateway's situation is the
opposite one.

**Impact if wrong**: Adding a bounded retry is a configuration and one branch. The deadline itself is
a number that OQ-012's latency answer will inform.
