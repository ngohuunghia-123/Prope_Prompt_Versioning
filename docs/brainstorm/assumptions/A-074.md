# A-074 — An approval stores the evidence digest as it stood at decision time; it is testimony, not a cache

**Statement**: An `approval` row stores an `evidence_digest`: the eval run ids, the per-suite
pass/fail/error counts, the cost delta, the baseline run ids and their timestamps, and whether
`requires_acknowledgement` was set. It stores counts, ids, and money — never model outputs, never case
inputs, never prompt text.

**This is not a violation of A-047** ("derived comparisons are computed on demand and never stored").
A-047 forbids caching a view that can be recomputed to the same answer. This digest cannot: the baseline
may have moved, a suite may have been edited to a new version (A-004), and a re-run at non-zero
temperature can flip a case (A-053). Recomputing later answers a different question — *what is true now*
— when the audit question is *what did the reviewer see*.

**Rationale**: An approval that does not record its evidence is unreviewable afterwards, which defeats
the point of recording approvals at all. It is also what makes ADR-0005's watch signal measurable: to
know whether acknowledgement is being rubber-stamped, you need the failures that were acknowledged, as
they stood.

**Impact if wrong**: A column to drop, plus the loss of every historical digest — the data cannot be
reconstructed, which is why this is `moderate` and why it is decided now rather than added later.
