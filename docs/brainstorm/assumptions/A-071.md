# A-071 — Notification is an in-app review queue only; no email, Slack, or webhook

**Statement**: A reviewer learns there is something to review by opening the product and looking at
`GET /api/v1/review-tasks` — the open queue, with overdue break-glass follow-ups flagged. No outbound
channel ships in the MVP. `external_services` stays empty for every module in the map.

**Rationale**: User decision, 2026-08-08 (OQ-015) — no email or Slack is being built for the MVP.

An outbound channel is the first external service in the whole system. It means a vendor,
a credential to store next to the provider credentials whose policy is already open (OQ-006), a
deliverability failure mode, and a decision about what a notification is allowed to contain — a prompt
title can itself be sensitive. None of that follows from the context file, and all of it is a commitment
the user makes, not one I make for them. The in-app queue is buildable now and is what any channel would
notify *about*, so it is not throwaway work.

**Impact if wrong**: The queue stays; a channel is added alongside it. Adding is cheap.

**One consequence to hold on to.** The success metric "median review turnaround < 1 business day" now
measures a human noticing as much as a human deciding. `review_task.created_at` → `approval.decided_at`
is the whole interval and cannot separate the two on its own, so the pilot should record when a reviewer
first opened the queue. If the metric is missed, that is the difference between "reviewers are slow" and
"reviewers were never told" — and only the second is fixed by building a channel.
