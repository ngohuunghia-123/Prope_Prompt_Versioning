# A-043 — Upstream dispatch lives in provider-access; both the gateway and the eval runner call it

**Statement**: The code that takes a provider configuration, a model, generation parameters, and
messages, calls the upstream provider, and returns the response plus its usage object belongs to
`provider-access`. `gateway` and `evaluation` both depend on it. `evaluation` does not depend on
`gateway`. This clarifies A-027: the eval runner shares the *resolution and dispatch semantics*, not
the gateway module.

**Rationale**: Provider Access already owns the credential and the model catalogue, so dispatch is its
job by data ownership. The alternative puts dispatch inside the gateway and makes a batch path depend
on the module carrying the strictest latency budget in the system — every change to the eval runner
would then be a change inside the hot path. Sharing dispatch is also what keeps the ±2% token-accuracy
metric honest: one usage-parsing implementation, not two.

**Impact if wrong**: Moving a dispatch function and re-pointing two callers. Moderate rather than cheap
because fallback (A-033/034) and streaming accumulation (A-038) sit just above this seam and would move
with it.
