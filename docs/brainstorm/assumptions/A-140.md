# A-140 — The cross-tenant sweep is N+1 transactions per pass, unbounded in workspace count

**Statement**: ADR-0051's sweep runs one `access.list_workspaces()` call followed by **one short
transaction per workspace** — `SET LOCAL app.workspace_id`, then the tenant-scoped queries. Gauges refresh
every 60 s; the reconciliation anti-join runs at startup and hourly. **Nothing bounds the number of
workspaces**, nothing batches the per-tenant transactions, and no target exists that either number was
chosen against.

| Pass | Interval | Transactions | Reads per transaction |
|---|---|---|---|
| review-task gauges | 60 s | 1 + N | two counts over `release.review_task` |
| pointer reconciliation | startup, then 1 h | 1 + N | one anti-join, `registry.prompt_property` × `release.release` |

**Rationale**: the alternative is a cross-tenant query that reads rows with the policy off, and ADR-0051
rejected that on the shape rule — *a function that returns tenant identifiers keeps every subsequent data
read under RLS; a function that returns rows does not*. Paying N transactions is the price of keeping the
reads policied, and at the pilot's shape it is not a price at all: `00_context.md#problem` describes
eleven people, A-020 bars real corporate prompts until the security baseline is signed off, and both
queries are indexed counts over tables that grow at human decision rate — a handful of rows per prompt per
week. Sixty transactions a minute against PostgreSQL on ADR-0033's 4 vCPU is not a load; it is a
heartbeat.

The numbers themselves are inherited rather than derived. **60 s** matches evaluation's sweeper, so
`worker` has one timer cadence rather than three. **Hourly** is what the lock file already said, written
when the reconciliation query covered a distributed-transaction gap that ADR-0026 and ADR-0027 have since
closed — its job is now residual-risk detection for ADR-0008's amended convention, which is a slower kind
of question and does not argue for a shorter interval.

**What would make this wrong**: the sweep taking longer than its own interval, which at 60 s means roughly
N > a few hundred workspaces or a missing index — either of which shows up as overlapping passes rather
than as a wrong number, because the job is a single task and a slow pass simply delays the next one.
The remedy is the ordinary one: a single grouped query per pass with `workspace_id` in the `GROUP BY`,
run inside one transaction per batch of tenants rather than per tenant. That is a rewrite of one function
with no schema change, no migration, and no change to the bypass set.

**The gap that is not about scale**: a stale gauge and a healthy gauge look identical. If the sweep task
dies, the last values persist in the Prometheus client registry and `BreakGlassTaskOverdue` neither fires
nor breaks. ADR-0051 records a sweep-heartbeat counter as owed for exactly this. That is the more likely
failure of the two, and it is not fixed by any of the scaling remedies above.

**Impact if wrong**: `worker` spends measurable time on bookkeeping that competes with evaluation's run
executor and call-ledger's drain in the same process, where [[A-138]] already records that **nothing
bounds `worker` across workspaces**. This assumption is the fourth term in that stack and the only one
that grows with tenant count rather than with activity.

Related: [[A-138]] for the missing process-level cap this sits inside · [[A-009]] and [[A-073]] for the
follow-up task these gauges measure · [[A-072]] for the compare-and-set the reconciliation query checks
after the fact.
