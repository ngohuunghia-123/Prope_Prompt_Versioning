# A-078 — Variables arrive in a `prope.variables` object; an unfilled placeholder is a caller error

**Statement**: `{{variable}}` placeholders in the revision body (A-011) are filled from an optional
top-level `prope` object on the request — `{"prope": {"variables": {"customer_name": "..."}}}` —
reached through a client SDK's `extra_body` affordance and symmetric with the `prope` object A-033
puts on the response. A placeholder with no value returns an OpenAI-shaped `400` naming the missing
variable, and a request containing a literal `{{customer_name}}` is never dispatched upstream.
Variables the template does not use are ignored. Variable **values** are caller data: never in a log
line, never in a metric label (A-046); their names may be logged.

**Rationale**: The OpenAI request shape has no field for server-side template variables, so one had to
be chosen; a body extension is ignorable by older clients and keeps caller data in one place for
redaction, which a header would not. Refusing an unfilled placeholder rather than passing it through
is the important half: a model given text that looks like a template answers plausibly anyway, and the
consumer ships a response naming `{{customer_name}}` or a hallucinated substitute. It is the caller's
bug and it should surface as the caller's error, before any money is spent upstream.

**Impact if wrong**: The field name and the substitution syntax are a parser change. Structured values
would need a serialization rule, which is additive.
