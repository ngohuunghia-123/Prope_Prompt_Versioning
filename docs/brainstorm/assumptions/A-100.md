# A-100 — Cost is priced once at write time and stored with the price row that produced it

**Statement**: The writer computes cost when it persists a record, selecting the price row in force at
the **call's own `created_at`** rather than at wall-clock write time, and stores `cost`, `currency`,
and `price_row_id` on the record. Repricing later fills only rows that were unpriced; a row that
already has a cost is never recomputed. Full reasoning and rejected alternatives in ADR-0019.

**Rationale**: A cost delta is shown to a reviewer before an approve decision, and the approval record
is testimony about what they saw (A-074). Computing at read time means a later price edit silently
changes what that record describes, which A-030 identifies by name as the thing effective dating
exists to prevent. Pricing by the call's own timestamp rather than the writer's makes a spill replay,
a backlog, and a normal write produce the same number.

`price_row_id` is on the row because the question that actually gets asked six months later is "why
did this cost that", and answering it without provenance means guessing which row was in force.

**Impact if wrong**: Adding `price_row_id` after data exists leaves every existing row unexplainable,
which is the migration this assumption avoids rather than one it creates.
