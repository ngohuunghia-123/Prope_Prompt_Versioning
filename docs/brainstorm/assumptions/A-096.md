# A-096 — A provider configuration is disabled, never silently deleted; deletion is refused while a revision binds it

**Statement**: `provider_config.status` is `active | disabled`. Disabling refuses new dispatches while
leaving the configuration and its catalogue readable, so a revision bound to it still explains
itself. `DELETE` is refused while any revision references the configuration — the same shape A-052
uses for retiring a prompt that still has an active release.

**The refusal is enforced by a foreign key**, `revision.provider_config_id → provider_config.id`, not
by provider-access asking prompt-registry anything. provider-access → prompt-registry is a forbidden
direction (module_map.md), so the constraint is the only mechanism available — and it is the better
one, for the same reason BR-03's Approved-only constraint is: it cannot be bypassed by a code path
that forgot to check. The consequence is that provider-access can say *that* the configuration is
still bound and how many revisions bind it, but not *which* — naming them would require the read it is
not allowed to make. The dashboard links to the registry's own filter instead.

**Rationale**: A revision is immutable and carries its provider binding (A-024, BR-06). Deleting the
configuration underneath it would turn an approved, auditable revision into one that points at
nothing, and every stored cost figure attached to it becomes unexplainable. Refusing the delete and
naming what blocks it turns a silent corruption into a two-step task.

Disabled-versus-deleted also gives a workspace the operation it actually wants when a key is
compromised: stop the calls now, decide about the configuration later.

**Impact if wrong**: A cascade or a soft-delete flag. Cheap while the refusal is the default, because
loosening a refusal is always easier than recovering a reference that was already dropped.
