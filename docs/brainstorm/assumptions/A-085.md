# A-085 — A fallback is only reachable before the first byte; after that a failure truncates honestly

**Statement**: The fallback answer is served only when the upstream failure occurs **before** the
first byte has reached the caller — which is every non-streaming call, and the pre-first-byte portion
of a streaming one. Once a chunk has been relayed, the status line is `200` and the caller holds
partial content, so the fallback is unreachable: the stream terminates with an OpenAI-shaped error
chunk, no canned text is appended, and the call record is written with `outcome = truncated` and the
partial body (A-038). `prope_gateway_upstream_error_total` is labelled
`stage = pre_first_byte | mid_stream` so the two are never one number.

**Rationale**: A-033 to A-035 settle whether a fallback is served and are silent about when, and
streaming is where the silence becomes a bug. Splicing canned text onto a half-finished answer
produces a response that is half model output and half stored text, joined at an arbitrary token
boundary — outside everything the approval record describes, and impossible to mark honestly, because
it is not a fallback but a hybrid. Buffering the whole stream to keep the recovery path open would
delete streaming itself, which A-038 forbids and OpenAI compatibility exists to provide. Full
reasoning in ADR-0013.

**Impact if wrong**: The gate is one state check, but `outcome = truncated` reaches call-ledger's
pricing and any later reporting, which is why this is moderate rather than cheap.
