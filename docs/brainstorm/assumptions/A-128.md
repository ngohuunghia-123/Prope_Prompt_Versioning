# A-128 — SQLAlchemy 2.0 async with Alembic and asyncpg is the data-access baseline, and two paths use raw SQL

**Statement**: All eight modules use SQLAlchemy 2.0 in async mode over asyncpg, with Alembic for
migrations. Two paths are written as raw SQL rather than ORM query construction: the gateway's
model-name resolution read, and A-118's `visible_subject_filter` set form.

**Rationale**: Alembic is chosen because three accepted decisions ship *as migrations* rather than as
application code — ADR-0025's `INSERT`/`SELECT`-only grant on `history.history_event`, BR-03's
released-pointer constraint, and ADR-0035's row-level security policies. A migration tool is therefore
load-bearing infrastructure here, not a convenience, and Alembic is the only mature option in Python.
asyncpg follows from FastAPI's async handlers (ADR-0026); a sync driver would block the event loop the
gateway's p95 budget depends on.

The two raw-SQL carve-outs are named now so they are deliberate rather than discovered. The resolve read
is the single hottest query in the system and sits inside a stated p95 (`00_context.md#success`), where
ORM statement construction is measurable overhead against a query that never changes shape. A-118's set
form exists specifically *"so list endpoints filter in SQL rather than per row"* — expressing it through
the ORM would either lose that property or produce a query nobody can read, and it is the mechanism by
which prompt-registry keeps its own promise that permission filtering lives in the repository layer.

**Impact if wrong**: Swapping the ORM later touches every module's repository layer, which is why this
is `moderate` rather than `cheap`. The two raw-SQL paths are unaffected by that swap, which is a small
argument in their favour beyond the performance one.
