# OQ-044 — Three columns in the `access` schema are named with a status and enumerated with one value

**Raised by Phase 7 planning, 2026-08-11.** `blocks_build: false` — Phase 7 adopts a set for each and
records them here. Raised because each of the three becomes a database `CHECK` in a migration, and a
`CHECK` is one of the objects this project deliberately makes expensive to change.

## The three

**`access.user.status`.** The lock names exactly one value: *"`status` set to `tombstoned`"*
(`data.owns`, and A-151's table). Nothing names the other state, and there must be one, because a
person who has not been tombstoned has a status too. ADR-0054 §8 makes the transition one-way —
*"Nothing un-tombstones a row"* — so the set is at least `{?, tombstoned}` with a one-way edge.
There is a second candidate value hiding in `must_change_password`: A-110 forces a password change at
first sign-in, and that is carried on its own boolean column rather than on `status`, which is
evidence that `status` is not a lifecycle field.

**`access.workspace_member.status`.** A-151 names `removed`. The lock says *"There is no pending
state, because there is no invitation to be pending on (A-110)"* — which rules a value **out** and
still names none in. A-151 also requires that removed rows are **retained**, so the tombstone can find
the workspaces to write its event into; that makes the distinction between "active" and "removed"
load-bearing for AC-08's admin count as well as for AC-14's event fan-out.

**`access.api_key.scope_model_names`.** A-081 makes it *"explicit and default-deny"* and the lock says
*"An empty scope resolves nothing"*, which fixes the semantics of the empty case and not the storage.
`text[]` and `jsonb` behave differently under `= ANY`, under a GIN index and under an empty literal,
and Phase 8's `may_resolve` sits on the gateway's 5 ms budget.

## What Phase 7 adopts

- `user.status` — `active | tombstoned`, CHECK-constrained, default `active`, with a companion
  constraint (`ck_user_tombstone_is_complete`) asserting that `tombstoned` implies `email`,
  `display_name` and `password_hash` are all NULL and `tombstoned_at` and `tombstoned_by` are both
  set.
- `workspace_member.status` — `active | removed`, CHECK-constrained, default `active`. AC-08's admin
  count and A-151's event fan-out both read it, in opposite directions: the count is over `active`
  rows, the fan-out is over rows of **any** status.
- `api_key.scope_model_names` — `text[] NOT NULL DEFAULT '{}'`, because default-deny is then the
  column default rather than a value the application has to remember to write, and `= ANY(...)` is one
  operator rather than a JSON containment expression.

## What is being asked

Whether those three sets are right, and in particular whether `user.status` carries a third value —
`disabled` or `suspended` — which A-110's out-of-band account creation makes plausible and which no
document requests. Adding one later is a `CHECK` change; removing one after rows exist is a migration.

## What is affected either way

- One migration's three `CHECK` constraints and one column type
- `src/prope/access_control/domain.py` — three `StrEnum`s
- AC-08's admin count query and A-151's tombstone fan-out, which read `workspace_member.status`
- Phase 8's `may_resolve`, which reads `scope_model_names` on the gateway's hot path
