# OQ-028 — Four of the 31 action names do not follow A-120's naming rule. Which gives way?

**Raised by Phase 4 planning (04-CONTEXT.md, D-61), 2026-08-10.** `blocks_build: false` — the
migration seeds the names the lock files actually contain, and this records why they were not
"tidied" on the way in.

## The conflict, stated exactly

A-120 is unconditional: *"Every `history_event.action` value is `<target_type>_<past participle>`."*
It then lists the renames it performed, and every one of them is in `release-control.lock.yml`. No
other module's names were examined.

Four names outside release-control do not satisfy the rule against their **actual** target:

| Action | Written by | Its real target | Reads as |
|---|---|---|---|
| `retired` | prompt-registry | the prompt property | a bare past participle with **no target type at all** — the exact shape A-120 renamed six release-control verbs to remove |
| `owner_changed` | prompt-registry | the prompt property | `<field>_<past participle>`. The owner is a column on the property, not a subject with an id |
| `access_level_changed` | prompt-registry | the prompt property | same — a field on the property |
| `access_granted` / `access_revoked` | access-control | the `prompt_grant` row | `access` is not a target type; the subject is the grant. Counted as one row because the pair is one decision |

`retired` is the one that matters. A-120's stated rationale is that *"a bare verb reads badly in a log
line, an alert, or a metric label, where the action arrives without its columns"* — and `retired`
arriving alone in a `PropertyHistoryAppendRejected` page is precisely that sentence's own example.

## Why it cannot simply be fixed in the registry

Because two things assert against each other and only one of them is a test.

- **AC-6 (PH-06, Phase 5)** asserts the registry equals *the union of the five lock files' event
  lists*, "no extras and no omissions". Seeding `property_retired` makes AC-6 **red**, because
  `prompt-registry.lock.yml` `outputs` and `property-history.lock.yml` `inputs` both say `retired`.
- **A-120** is prose in an assumption file. Nothing executes it.

So the build must seed `retired` to stay green, and A-120 is then false for one of 31 names — quietly,
in a file nobody re-reads. Phase 4 seeds the lock files' literal names for exactly that reason and
raises this instead of choosing silently.

## Why it is worth deciding before data exists

A-120's own *Impact if wrong* line: *"A rename before any data exists. After data exists it is an
`UPDATE` on an append-only table, which A-121 and ADR-0025 make deliberately hard — which is the
argument for settling it now."* `history_event` will hold no rows until Phase 5's first append and no
production rows until the pilot. **The window in which this is a one-line edit closes at the pilot,
and after it closes there is no supported path at all** — `prope_app` holds neither `UPDATE` nor
`DELETE` on the table, by design (ADR-0025), so the correction would be a `prope_migrate` deployment
action against the audit log, which is the operation the whole module exists to make impossible.

## What a resolver has to choose between

1. **Rename `retired` to `property_retired`** in `prompt-registry.lock.yml` `outputs` and
   `property-history.lock.yml` `inputs`, and leave `owner_changed`, `access_level_changed`,
   `access_granted` and `access_revoked` as they are. Fixes the one name A-120's own rationale
   indicts and leaves three that are readable in a log line regardless. Costs two lock-file edits
   before any code names the string.
2. **Rename all four groups** to `property_retired`, `property_owner_changed`,
   `property_access_level_changed`, `prompt_grant_granted` / `prompt_grant_revoked`. Internally
   consistent, and the last pair is ugly enough to be an argument against the rule rather than for it.
3. **Amend A-120 to state the rule as a convention with named exceptions**, and list these four. The
   rule then describes the vocabulary instead of contradicting it, and `registered_actions()` still
   returns `target_type` per action so nothing downstream has to parse a name to learn its subject.

Option 3 is the cheapest and the only one that costs nothing in the build; option 1 is the only one
that acts on A-120's own stated reason for existing. Both are defensible and it is not the planner's
call.
