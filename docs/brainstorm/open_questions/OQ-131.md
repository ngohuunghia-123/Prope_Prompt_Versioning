# OQ-131 — `seq` ships as `GENERATED ALWAYS AS IDENTITY`, where the lock file says `bigserial`

**Raised by plan 04-01, 2026-08-11.** `blocks_build: false` — the column shipped, the deviation is
recorded in the revision docstring, and a test asserts the stricter behaviour.

**Id allocated by the orchestrator, outside every phase range.** Phase 4's allocation `OQ-027…OQ-031`
was fully consumed during planning, and plan 04-01 correctly refused to borrow from another phase's
range, escalating instead. Phases 16–24 hold `OQ-086…OQ-130`, so orchestrator-allocated ids start at
`OQ-131`.

## The deviation

| | Lock file / ADR-0024 | What shipped |
|---|---|---|
| Spelling | `bigserial` | `bigint GENERATED ALWAYS AS IDENTITY (CACHE 1)` |
| Column type | `bigint` | `bigint` — identical |
| An `INSERT` that names `seq` and supplies a value | **succeeds silently** | **refused by the engine** |

**This is not a spelling difference and it is not being reported as one.** A `bigserial` is sugar for
`DEFAULT nextval(...)`, and a default is consulted only when the caller omits the column. `prope_app`
holds `INSERT` on `history.history_event` by design, so under the lock file's literal spelling a
hand-written statement supplying its own `seq` would be accepted and the total order would stop being
total with no error raised anywhere. Under `GENERATED ALWAYS` the engine refuses it.

## Why it was shipped this way

The same sentence in `data.owns` that says `bigserial` also says **"monotonic, and the ONLY sort
key"**. `GENERATED ALWAYS` implements that sentence more strictly than `bigserial` does. PH-04 —
*"two events written in one transaction have a stable order on every run"* — is the phase's second
success criterion, and it is only a guarantee if the sequence is the sole author of the value.

## The escape hatch this does **not** close, recorded so it is not later mistaken for one

PostgreSQL: *"For an identity column defined as `GENERATED ALWAYS`, it is an error to insert an
explicit value (other than `DEFAULT`) without specifying either `OVERRIDING SYSTEM VALUE` or
`OVERRIDING USER VALUE`."* The documentation attaches **no privilege requirement** to `OVERRIDING
SYSTEM VALUE`, and the engine names the bypass in its own `HINT`. So `GENERATED ALWAYS` refuses the
statement anyone would write by accident and does not refuse the statement someone determined would
write. Two halves record this: a security test proves both directions at the engine, and an
architecture test refuses the token in source under `src/prope/` and `alembic/`.

The operational consequence, which is the reason the boundary matters: a supplied `seq` **does not
advance the sequence**, so the next engine-assigned value is *lower* than the supplied one and sorts
*before* an event written later. The order goes silently wrong and stays wrong until the sequence
climbs past the supplied value — at the lock file's stated *"< 500 events per prompt property per
year"*, potentially for years. It is not a loud break.

## What is being asked

1. **Confirm the strengthening**, in which case `docs/modules/property-history.lock.yml`
   `data.owns → history_event → seq` and ADR-0024's Decision block should be amended upstream to say
   `GENERATED ALWAYS AS IDENTITY`, so the spec and the database agree.
2. **Or reverse it** to the literal `bigserial`, which would mean deleting the test that asserts a
   supplied `seq` is refused, and accepting that any holder of `INSERT` can author the sort key of an
   append-only audit log.

Reversal cost: **one-way once rows exist.** Changing the sort key of an append-only table means
rewriting rows that `prope_app` cannot rewrite by design. Cheap today, expensive after the pilot.

## What is affected either way

- `alembic/versions/0005_history_schema_and_vocabulary.py` — the column definition and its docstring
- `tests/security/test_history_seq_cannot_be_supplied.py` — asserts the refusal (plan 04-03)
- `tests/architecture/test_no_overriding_system_value.py` — refuses the bypass token in source
- `docs/modules/property-history.lock.yml` and `docs/adr/0024-*` — **not edited**, per ORCHESTRATION §5
