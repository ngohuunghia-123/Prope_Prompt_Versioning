# OQ-023 — A declared metric carries a per-workspace identifier, and the registry is now served unauthenticated

**Raised by Phase 3 plan 03-04 while mounting `GET /metrics`, 2026-08-10.** The code ships either
way — `blocks_build: false` — and the deviation is recorded here rather than absorbed into the spec,
per `.planning/BSP-LINK.md` and `.planning/ORCHESTRATION.md` §5.

## The conflict, stated exactly

`observability_requirements.metrics` declares:

```
- prope_call_ledger_unpriced_total
  # labels: provider_config_id, upstream_model
```

**A `provider_config_id` resolves to exactly one workspace.** It is provider-access's identifier for
one workspace's configured provider credential, and call-ledger records it as a value (A-025). So the
declared label set carries a per-workspace identifier under a different name.

`src/prope/observability.py`'s module docstring states the opposing rule flatly:

> every label declared here has a CLOSED set of values fixed in source, and `workspace_id` — the
> highest-cardinality identifier in the system and the one most tempting to add — is deliberately
> never a label.

and `tests/broker/test_publish_confirm_failures.py::test_workspace_id_is_never_a_metric_label` walks
the whole registry to enforce it. That test passes: the label is not *named* `workspace_id`. The
identifier is there anyway.

## What made this concrete rather than theoretical

Until this plan the registry was observable from tests and from nothing else. Plan 03-04 serves it on
`GET /metrics` — **unversioned, sessionless, and reachable from every container on the compose
network behind Caddy's single ingress** (ADR-0033, ADR-0052).

**Both halves of the honest position, because neither is fixable inside this module:**

- **The labels ship because the lock declares them.** Dropping a declared label to avoid raising a
  question is editing the build to make the spec comfortable, which is the inverse of the rule.
- **The route is unauthenticated because a scraper holds no session**, and because call-ledger has
  nothing to authorise against — ADR-0018 forbids it an outbound edge to access-control, so there is
  no permission this module could check even if it wanted to.

So **the exposure is the metric contents, not the port.** T-02-15 registered the same class of
concern for a port on `worker`; this is that concern on `app`, which is already the ingress target.
What a reader of `/metrics` learns is: which provider configurations exist, which upstream models
they call, and which of those produced calls with no price row. That is a shape-of-the-business
disclosure rather than a tenant-data one — no body, no prompt, no cost figure, no `workspace_id`
string — but it is per-tenant and it is readable by anything that can reach the port.

## A fact that changes what a cheap answer looks like

**ADR-0030's own text is more permissive than this repository's module docstring.** The ADR permits
`model_name` and `workspace_id` *"at pilot scale, reviewed if either grows past hundreds"*; the
module docstring says `workspace_id` is *"deliberately never a label"*. So one available answer is
to **correct the module's stricter rule** rather than the lock's declared labels — which would also
resolve `OQ-022` clause 4, where `LedgerRetentionOverdue`'s per-workspace threshold has to read an
unlabelled series.

## The shape of the possible answers

1. **Accept it.** Record in the lock file that `unpriced_total`'s labels are per-workspace by
   construction, and that `/metrics` is an operator surface on a single VM behind one ingress. Costs
   nothing and is what ships today.
2. **Restrict the surface at the ingress** — a Caddy matcher that answers `/metrics` only for the
   scraper. A deployment change, in a stack that owns no milestone (PITFALLS §4), so no phase in this
   roadmap would make it.
3. **Drop `provider_config_id` from the label set** and keep `upstream_model` alone. Loses the
   worklist's routing key — the alert exists to send somebody to a specific provider configuration's
   missing price row — so it trades the metric's usefulness for the exposure.
4. **Reconcile the two rules in the other direction**: correct `observability.py`'s docstring to
   ADR-0030's wording and stop pretending the stricter rule is the project's. Changes no code and
   makes the labelled gauge of `OQ-022` clause 4 available.

## Why this does not block the build

`blocks_build: false`. Every declared label ships, the registry walk that enforces the
`workspace_id` rule still passes, no body or figure reaches any label, and the route declares no
session because there is no session for it to declare. What the answer settles is whether a declared
per-workspace label may be served on an unauthenticated surface, and which of the two conflicting
cardinality rules this project actually holds.
