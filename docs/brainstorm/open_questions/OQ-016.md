# OQ-016 — Which provider will the pilot workspace actually point Prope at?

## Resolution — 2026-08-08 (user)

> "OpenAI compatible first, I'll build a distinguish SDK after MVP"

**OpenAI-compatible is the whole MVP.** A second adapter for a provider with its own wire shape —
Anthropic's Messages API, Google's Gemini API — is post-MVP work the user will take on themselves.

**Consequences applied**
- A-094 promoted from a proposed default to a decided one (`decided_by: human`). It is no longer
  waiting on anything.
- `provider_access.lock.yml`'s Estimable caveat is removed: the module's one unknown is closed, and
  the INVEST row in `module_map.md` returns to all-`yes`.
- ADR-0015's normalisation boundary and the `provider_config.adapter` column stay exactly as they are.
  They were designed so a second adapter is additive rather than a rewrite, and that is now a
  post-MVP feature with a named owner instead of a schedule risk.
- The MVP's provider surface is one HTTP client against a configurable base URL. No adapter matrix,
  no per-provider streaming reframe, and ADR-0017's classification table has one column to fill.

## Question

On day one of the pilot, whose API key gets pasted into the provider dashboard — OpenAI, Azure
OpenAI, Anthropic, Google Gemini, a Vietnamese or regional provider, or something self-hosted? And is
it one, or several at once?

## Why it matters

The MVP ships **one adapter kind**: OpenAI-compatible, with a configurable base URL (A-094). That is
not a narrow choice — it covers OpenAI, Azure OpenAI, Groq, Together, Fireworks, OpenRouter, and any
self-hosted vLLM or Ollama endpoint, all with zero translation, because ADR-0015 makes the OpenAI
chat-completions shape the internal contract and the constraints table already mandates it at the
edge.

It does **not** cover Anthropic's Messages API or Google's Gemini API. Those are different wire
shapes, and an adapter for either is real work: request translation, a streaming reframe, a usage-
object parse the ±2% success metric depends on, and its own column in ADR-0017's failure-
classification table. If the pilot workspace is an Anthropic or Gemini shop, that adapter is on the
critical path and nothing in the plan accounts for it.

This is a fact only you hold. Nothing in `00_context.md`, `BRIEF.md`, `positioning.md`, or
`prope_source_of_truth.md` names a provider.

## What we know already

- OQ-004 settled that the workspace brings its own key and picks its own provider and model per
  prompt. It did not say which.
- A-030 restricts support to providers that return a usage object, which every major provider does.
- The `provider_config.adapter` column and ADR-0015's normalisation boundary exist so a second adapter
  is additive rather than a rewrite. The cost is schedule, not architecture.

## Options

1. **OpenAI-compatible only** — A-094 stands, nothing changes.
2. **Add an Anthropic adapter** to the MVP.
3. **Add a Gemini adapter** to the MVP.
4. Something else, or more than one.

## Recommendation

Answer with the name of the provider whose key you will actually paste in on day one — that single
name settles it. Option 1 is right under every answer for the *first* adapter, so this does not block
the build; it decides whether a second one is scheduled before the pilot or after it.
