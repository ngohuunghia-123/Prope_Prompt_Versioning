# OQ-031 — ADR-0045 already wrote this phase's `GLOBAL_TABLES` entry, and the line carries two problems: a stale count, and an assertion the implemented walk does not perform.

**Raised by Phase 4 planning (plan 04-01, Task 1), 2026-08-10.** `blocks_build: false` — Phase 4 ships
either way. The entry is written with a deliberately different reason string and the divergence is
recorded here rather than absorbed, per `.planning/BSP-LINK.md`: *a spec that disagrees with the code is
information; raise an `OQ-NNN` naming the exact field and the conflict, and do not patch the spec to
agree.*

## The conflict, stated exactly

`docs/adr/0045-every-table-is-tenant-scoped-unless-declared-global.md` contains, verbatim, in its
Decision block:

```python
GLOBAL_TABLES = {
    'access.user':                     "a person is not a tenant's property; unique(email) is global",
    'access.role_permission':          "the (role, action) matrix is one table for the whole install",
    'history.history_action_registry': "30 seeded actions, immutable, ADR-0024 and ADR-0038",
    'access.workspace':                "IS the tenancy root — policied on id, not on workspace_id",
}

for table in all_tables_in_module_schemas():
    if table in GLOBAL_TABLES:
        assert rls_state_matches_declaration(table)
        continue
    assert has_workspace_id(table) and rls_enabled(table) and has_policy(table)
```

Two separate things are wrong with the third entry and the four lines under it.

### 1. It is a **seventh** stale-count site, and the only one whose text was about to be copied into a security-relevant file

`OQ-027` lists six places where the vocabulary count reads 30 against the eleven that read 31. It does
**not** list this one. This line matters more than the other six for a specific reason: **it is a
proposed literal for `tests/architecture/test_tenant_coverage.py`**, which is the file a reviewer opens
to find every table in Prope that is not tenant-scoped. Copying the ADR's string would have moved
`OQ-027`'s stale count out of prose and into a security file, where resolving it later means editing a
test.

Phase 4 therefore writes a reason string that **contains no number at all**:

```python
"history.history_action_registry": (
    "the action vocabulary is closed install-wide, not per workspace (A-120, ADR-0024); "
    "tenant-scoping it would return zero rows to registered_actions()'s only consumer — a CI "
    "test with no tenant context — and AC-6 would compare two empty sets and pass forever. "
    "Seeded by migration, SELECT-only for prope_app, never written at runtime (ADR-0038). "
    "Declared global by ADR-0045, which names this table."
)
```

That is a deliberate divergence from the ADR's wording. It states the same rule, adds the failure mode
of the alternative, cites the authority — and leaves the count where `OQ-027` can move it without
touching `tests/`.

**The question:** when `OQ-027` resolves, does ADR-0045's entry get the corrected count, or does it
adopt the numberless form for the same reason?

### 2. The ADR asserts something on an exemption; the implemented walk asserts nothing

The ADR's pseudocode is:

```python
    if table in GLOBAL_TABLES:
        assert rls_state_matches_declaration(table)
        continue
```

`tests/architecture/test_tenant_coverage.py:118-121` is:

```python
    for schema, table, row_security in tables:
        qualified = f"{schema}.{table}"
        if qualified in GLOBAL_TABLES:
            continue
```

So a `GLOBAL_TABLES` entry currently buys **no check whatsoever** — not that the table lacks
`workspace_id`, not that row security is off, not that its grants are what the declaration implies. The
exemption is a hole with a sentence in front of it. That was invisible while the dict was empty, which
it has been since Phase 1; Phase 4 puts the first real entry in it.

**Phase 4 closes the hole from the other side rather than changing the walk.** Plan 04-01's
`tests/integration/test_history_schema_ships_its_guarantees.py` asserts positively that a `prope_app`
session **with no tenant context** reads all thirty-one registry rows and **zero** history events —
which proves the table is genuinely global, proves the seed landed, and is exactly the read ADR-0038's
process-start cache performs, so it fails for the real reason if the exemption is ever reversed. That is
stronger than `rls_state_matches_declaration` for this one table and weaker for the general case,
because it is per-table rather than part of the walk.

**The question:** should `test_tenant_coverage.py`'s walk adopt the ADR's `assert` — checking that an
exempted table really does lack `workspace_id` and really does have row security disabled — so that the
next three exemptions (`access.user`, `access.role_permission`, `access.workspace`, all Phase 7's)
inherit a checked exemption rather than a skipped one?

## Why it is not resolved here

Both halves are edits to files Phase 4 may not touch: an ADR, and — for the second half — a Phase 1
architecture test whose scope is the whole project rather than this module. Phase 4's own need is met by
a positive per-table assertion. **Phase 7 is the natural resolver**, because it adds three more
`GLOBAL_TABLES` entries at once and is the first phase for which a skipped exemption would be a pattern
rather than an instance.

## What is affected either way

- `tests/architecture/test_tenant_coverage.py` — the walk, and the first `GLOBAL_TABLES` entry
- `tests/integration/test_history_schema_ships_its_guarantees.py` — the per-table positive assertion
  Phase 4 wrote instead
- Phase 7's three further exemptions, which will be written against whichever answer stands
- `OQ-027`, whose resolution would otherwise have to reach into a security-relevant test file
