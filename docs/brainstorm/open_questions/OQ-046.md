# OQ-046 — "the vocabulary" names two different closed sets, and AC-10 asserts against whichever one the reader had in mind.

**Raised by Phase 8 planning, 2026-08-11.** Phase 8 is the second module to mount management routes
and the first to mount routes that are *also* permission-checked, so it is the phase where the two
sets stop being the same thing by accident.

## The conflict, stated exactly

There are two closed sets of action strings in this project, and every authority calls both of them
"the vocabulary".

**Set 1 — the permission vocabulary.** `role_permission.action` is *"constrained to the closed
vocabulary (A-115)"*, `may(actor, action, subject)` decides over it, and INT-001 enumerates it as a
table of four callers and nineteen actions: `prompt.read`, `prompt.edit`, `prompt.create`,
`prompt.retire`, `prompt.change_owner`, `prompt.change_access`; `revision.submit`,
`revision.approve`, `release.create`, `release.break_glass`, `release.withdraw`; `suite.read`,
`suite.edit`, `run.start`, `run.read`; `provider.configure`, `provider.rotate_credential`,
`provider.disable`, `catalogue.read`. A-115 adds a twentieth, `user.tombstone`, on 2026-08-09.
**None of these carries a module prefix.**

**Set 2 — the route-declaration vocabulary.** `src/prope/session_auth.py`'s `ManagementAction` is a
`StrEnum` every management route attaches through `declares_action(...)`, and its own docstring says
it exists so that *"Phase 23's cross-module route-table assertion (AC-10 — 'every route declares an
action from the vocabulary')"* has something to read. Its five members are
`call_ledger.price.create`, `call_ledger.price.read`, `call_ledger.unpriced_worklist.read`,
`call_ledger.spend_ceiling.set`, `call_ledger.retention.set`, and the prefix is deliberate: *"seven
more modules add their own members to this enum, and `price.read` unqualified would collide the first
time two modules both have prices."*

**The two sets are disjoint today and cannot be reconciled by naming alone.** call-ledger performs no
permission check at all (ADR-0018), so its five members can never be rows in `role_permission` — a
`may()` call for `call_ledger.price.create` would be an action outside Set 1 and A-115 says an action
outside the vocabulary is **denied**. Meanwhile `prompt.read` is a Set 1 member with no route in
call-ledger to declare it.

## Why this is not a naming quibble

AC-10 is a requirement (`AC-10` in `.planning/REQUIREMENTS.md`) and its operative clause is *"a route
declaring none fails the test rather than defaulting to unauthenticated"*. That clause is
unambiguous. The clause before it — *"each declares an action from the vocabulary"* — is not, and the
two readings produce different tests:

- **Read as Set 1**, the test asserts every route's declared action is a `role_permission.action`
  row. Under that reading **the five call-ledger routes that ship today are already failing**, and
  making them pass means either seeding five permission rows for a module that checks no permission,
  or exempting call-ledger by name inside the assertion that exists to have no exemptions.
- **Read as Set 2**, the test asserts every route's declared action is a `ManagementAction` member —
  which is already true by construction, because `declares_action` refuses a non-member at import.
  Under that reading AC-10 asserts almost nothing beyond *a route declared something*.

Neither reading is wrong and neither is free, so it should be decided rather than resolved by
whichever implementer writes the phase-23 test.

## What Phase 8 adopted, and why

Phase 8 adopts **both sets, named separately, with a bridge asserted between them** (D-118):

1. `ManagementAction` remains the route-declaration vocabulary and gains access-control's members.
2. Access-control's members take the **unprefixed Set 1 strings** — `workspace.create`,
   `workspace.manage_members`, `prompt.change_access`, `user.tombstone` and so on — because those
   values are what `may()` is called with and a second spelling is a second thing to keep in step.
3. A test asserts that **every `ManagementAction` member whose value carries no module prefix is a
   `role_permission.action` row**, and that the prefixed members are exactly call-ledger's five, with
   ADR-0018 cited at the exemption. That is the strongest available form of AC-10's first clause and
   it is checkable today rather than at phase 23.

The cost is stated: `tests/architecture/test_route_table.py:363-374` currently asserts that **every**
member starts with `call_ledger.`, and Phase 8 must rewrite that assertion. It is rewritten to the
rule above rather than deleted.

## The shape of the possible answers

1. **Two vocabularies, one bridge** — what Phase 8 adopted. The prefix becomes a marker meaning *this
   route is declared but not permission-checked*, which is exactly ADR-0018's position for
   call-ledger, and the bridge test is what stops a third meaning appearing.
2. **One vocabulary, prefixed everywhere.** `role_permission.action` is re-seeded with
   `prompt_registry.prompt.read` and friends. Costs a re-seed and makes INT-001's table wrong in four
   rows; buys collision-proof names for every module at once.
3. **One vocabulary, unprefixed everywhere.** call-ledger's five members lose their prefix and are
   seeded into `role_permission` as actions no role holds. Costs five rows that `GET /permissions`
   renders as if they were policy, and re-opens the collision the prefix was added to prevent.

**A recommendation:** option 1. It is the only one that keeps ADR-0018's *"call-ledger has no
dependency on access-control"* true while giving AC-10 a test that can fail.
