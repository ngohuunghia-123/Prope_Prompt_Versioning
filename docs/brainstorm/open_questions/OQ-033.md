# OQ-033 — AC-3 says ten events over a lifecycle that enumerates nine, and neither file names the tenth.

**Raised by Phase 5 planning (plan 05-03), 2026-08-11.** `blocks_build: false` — the phase ships either
way, and being wrong costs one `append()` call in one test file. Raised rather than absorbed because
PH-03's entire content is that a prompt's Activity is **complete**, and *complete* is the number.

Phase 4 found this and handed it forward without resolving it (`04-…/deferred-items.md` §5: *"AC-3's
arithmetic does not close — the lock and Phase 5's SC1 both say 'all ten events' over a lifecycle that
enumerates nine ... Phase 5 may find the tenth event by reading its own scope"*). This is that reading,
written down.

## The conflict, stated exactly

`docs/modules/property-history.lock.yml`, `acceptance_criteria` → `AC-3`:

> Given a prompt property with a full lifecycle — created, revised twice, submitted, approved,
> released, its suite edited, access granted, restored — when its Activity is read, then **all ten
> events** are returned in one query in submission order, and no event belonging to another prompt or
> another workspace appears.

Counting the verbs: created (1), revised twice (2, 3), submitted (4), approved (5), released (6), suite
edited (7), access granted (8), restored (9). **Nine.**

`.planning/ROADMAP.md`'s Phase 5 success criterion 1 repeats the number without adding a name:

> A prompt with a full lifecycle returns **all ten** of its events in one query in submission order,
> with nothing from another prompt or another workspace.

## The reading adopted, and what it is derived from

**Registering a prompt property writes two events, not one** — `property_created` for the property and
`revision_created` for the revision it is registered with. So *created* is events 1 and 2, *revised
twice* is 3 and 4, and the enumeration closes at ten:

| # | action | target_type | writing module |
|---|---|---|---|
| 1 | `property_created` | `property` | prompt-registry |
| 2 | `revision_created` | `revision` | prompt-registry — **the tenth event** |
| 3 | `revision_created` | `revision` | prompt-registry |
| 4 | `revision_created` | `revision` | prompt-registry |
| 5 | `revision_submitted` | `revision` | release-control |
| 6 | `revision_approved` | `revision` | release-control |
| 7 | `revision_released` | `revision` | release-control |
| 8 | `eval_suite_updated` | `eval_suite` | evaluation |
| 9 | `access_granted` | `prompt_grant` | access-control |
| 10 | `revision_restored` | `revision` | release-control |

**This is a derivation and not a reading of any sentence.** Nothing in `docs/` states that registering a
property writes a `revision_created`. Three pieces of text support it and none of them says it:

1. `docs/modules/prompt-registry.lock.yml` `apis.exposes` names `POST /api/v1/prompts` as *"register a
   prompt property"* and `POST /api/v1/prompts/{prompt_id}/revisions` as *"creates the **next**
   immutable revision"*. *Next* presumes a first, and the first cannot come from the route that makes
   the next one.
2. The same file's `revision` table carries `unique(prompt_id, revision_number)`, *"allocated inside the
   creating transaction (A-048)"* — allocation exists from the first revision onward, not from the
   second.
3. A property with no revision has no body, so nothing could be submitted, approved or released, and
   `revision_submitted` at step 5 must have something to name.

## The two readings rejected

- **"Revised twice" means three revisions.** It reads the same missing event into a phrase that plainly
  means two, and it leaves `property_created` as the only event a registration writes — which would
  make a prompt's first Activity entry a property with no revision.
- **Counting the release as two events** (an approve-and-release writing `revision_approved` and
  `revision_released` in one transaction, A-076). AC-3 already lists *approved* and *released*
  separately, so this double-counts the same pair; and A-076's two-in-one-transaction case is AC-4's,
  which Phase 4 already asserts.

## What is being asked

Confirm the tenth event, or name the one that replaces it.

If registration writes only `property_created`, then AC-3's text and ROADMAP SC1's number are both
wrong by one, and the fix is deleting event 2 from
`tests/integration/test_activity_spans_four_modules_in_one_query.py` — one line, one file, which is why
this is `blocks_build: false`.

## What is affected either way

- `tests/integration/test_activity_spans_four_modules_in_one_query.py` — the ten events it writes
- `docs/modules/property-history.lock.yml` AC-3 — either the number or the enumeration
- `.planning/ROADMAP.md` Phase 5 SC1 — the same number, restated
- **Phase 13** (prompt-registry), which builds `POST /api/v1/prompts` and is where the answer becomes a
  behaviour rather than a test fixture. If registration is built to write one event and this question
  resolved the other way, the two disagree and the Activity is short by one from the first prompt
  onward
