# OQ-051 — A-110 requires a forced password change and nothing says what the other routes do while it is pending

**Raised by Phase 9 planning, 2026-08-11.** `blocks_build: false` — Phase 9 chooses a status, a code and
an exemption set, ships them, and records the choice here. Raised because three separate values were
invented by an implementing agent for a security-relevant refusal, and none of them appears in any
authority.

## The problem, stated once

Three artifacts commit to a forced password change and none of them says what *forced* means:

- `docs/modules/access-control.lock.yml` `apis.exposes`: *"POST /api/v1/auth/password — change own
  password; **required at first sign-in** (A-110)."*
- `data.owns` for `user` lists a `must_change_password` column, so the state is modelled.
- A-110 records that an Admin creates the account with *"an initial password handed over out of band"*,
  which is precisely why the change has to be forced: the initial password has travelled through a chat
  message or a spoken sentence.

What is missing is the enforcement:

1. **No acceptance criterion covers it.** There is no AC in the lock file whose `given` is a person who
   has not yet changed their initial password, so no requirement id points at it and no phase was
   assigned it. Phase 8 noticed and routed it forward — `08/deferred-items.md` §5, *"`must_change_password`
   enforced on every other route (A-110) … belongs with the rest of the refusal vocabulary"* — which is
   how it reached Phase 9.
2. **No status code is declared.** `interfaces.md` INT-029's failure-semantics line enumerates
   *"`401` identical for unknown email, wrong password and rate-limited · `409` on the zero-Admin refusal
   · `404` never-forbidden for a subject the actor cannot see · `5xx` on database failure"* and stops.
3. **No `ErrorCode` member exists**, so ADR-0053's client catalogue has nothing to translate. This is the
   seventh such member in the same position — Phase 8 recorded five (`forbidden`,
   `authentication_failed`, `last_admin`, `email_taken`, `membership_active`) and PITFALLS §5 records
   that the i18n catalogue has no owner at all.
4. **No exemption set is declared.** A gate on every route including `POST /auth/password` makes the
   state unescapable; a gate that also blocks `POST /auth/logout` leaves a person holding a session they
   cannot end.

## What Phase 9 ships (D-133, plan 09-01)

- `ErrorCode.PASSWORD_CHANGE_REQUIRED = "password_change_required"`, added to
  `src/prope/management_api.py`.
- `session_auth.Session` gains `must_change_password: bool`, and `session_auth.require_usable_session`
  raises `ManagementRefusal(403, PASSWORD_CHANGE_REQUIRED)` when it is set.
- **Every** management route in every mounted module declares `require_usable_session`. Exactly two
  declare the bare `require_session`: `POST /api/v1/auth/password` (the route that clears the flag) and
  `POST /api/v1/auth/logout` (so a person who cannot act can still end their session).
  `PASSWORD_CHANGE_EXEMPT_ROUTES` holds those two and
  `tests/architecture/test_route_table.py` asserts the set for **exact** equality in both directions,
  with a mutation control proving the assertion can fail.
- `POST /api/v1/auth/login` declares neither, unchanged — it is Prope's only unauthenticated route.

The three invented values are `403`, `"password_change_required"`, and the two-route exemption set.

## What is being asked

1. **Is `403` right, or should it be `409`?** `403` says *you may not act*, which is true and is the
   same status the permission refusals use. `409` says *the resource is in a conflicting state*, which is
   arguably closer — the account, not the request, is what is wrong — and is what the zero-Admin refusal
   already uses for a state-conflict. A third option, `428 Precondition Required`, is the literal HTTP
   answer and appears nowhere in this project's vocabulary.
2. **Is the exemption set exactly those two routes?** A case can be made for also exempting
   `GET /api/v1/permissions` (so a client can render something) and for **not** exempting logout (on the
   grounds that a person who cannot change their password should contact an Admin, not disappear).
3. **Who owns the catalogue key?** ADR-0053 §3 requires *"a CI check fails the build on any key present
   in the code and absent from `vi`"*. There is no catalogue, no `vi` file and no CI check. This is the
   seventh key in that position and PITFALLS §5 has no owner for the layer. See also `OQ-052`, which
   raises the same gap for `actor.tombstoned`.
4. **Should the lock file gain an acceptance criterion for this?** It is the only A-110 obligation with
   no assertion of its own, and Phase 9's test
   (`tests/integration/test_first_sign_in_forces_a_password_change.py`) is currently attached to no
   requirement id.

## What is affected either way

- `src/prope/management_api.py` — the `ErrorCode` member
- `src/prope/session_auth.py` — `Session.must_change_password`, `require_usable_session`,
  `PASSWORD_CHANGE_EXEMPT_ROUTES`, `declares_usable_session`
- Every route in `src/prope/access_control/routes/` and `src/prope/call_ledger/api.py` — the dependency
  they declare
- `tests/architecture/test_route_table.py` and
  `tests/integration/test_first_sign_in_forces_a_password_change.py`
- `docs/modules/access-control.lock.yml` `apis.exposes` and `acceptance_criteria`, and
  `docs/architecture/interfaces.md` INT-029's failure-semantics line — **none edited by Phase 9**
