# OQ-018 — call-ledger owns a sixth table. Does `data.owns` change, or does the table?

**Raised by Phase 2 plan 02-02 while implementing D-09, 2026-08-10.** The code ships either way —
`blocks_build: false` — and the deviation is recorded here rather than absorbed into the spec, per
`.planning/BSP-LINK.md`: *a spec that disagrees with the code is information; raise an `OQ-NNN`
naming the exact field and the conflict; do not patch the spec to agree.*

## The conflict, stated exactly

`docs/modules/call-ledger.lock.yml` `data.owns` names **five** tables:

| | |
|---|---|
| `call_record` | the metadata of every call |
| `call_body` | the raw request and response payloads |
| `price_table` | the effective-dated prices, append-only by privilege |
| `workspace_spend` | the monthly aggregate, one row per `(workspace_id, period_month)` |
| `spend_ceiling` | one row per workspace: the limits, the currency, the on/off flag |

Migration `0004` creates a **sixth**: `ledger.workspace_retention` — `workspace_id` as the primary
key, `retention_window interval NOT NULL` with a strictly-positive CHECK, `updated_by`, `updated_at`.
It carries the tenant policy and the grant matrix in the same revision as every other table in the
schema, and ADR-0045's coverage walk picked it up without being told its name.

So `data.owns` is now one row short of what the module actually owns. Nothing is broken by that; the
field is simply no longer a complete list.

## Why the table exists at all

The phase needs `PUT /api/v1/workspaces/{id}/retention` to persist a per-workspace window, and D-11
needs the drain to read it — *"a `PUT` that persists a window the writer never reads would be a route
that lies for a phase"*. That much is settled. What was open was **where the window lives**, and D-09
put it in its own table for a reason that survives restating:

**A spend ceiling and a retention window are two policies with different owners and different
lifecycles.** Folding the window onto `spend_ceiling` puts them in one row, and
`PUT /api/v1/workspaces/{id}/spend-ceiling` writes that row. A finance-side change to a monthly limit
would then be one careless full-row write away from silently resetting a retention policy nobody in
that request mentioned — a data-lifetime setting changed by an endpoint whose name says nothing about
data lifetime.

The third candidate, a generic key/value settings table, is worse than either: it cannot carry
`ck_workspace_retention_window_is_positive`, because a CHECK over a text value column would have to
know which key it was looking at. A zero-day window makes every body written after it expire at the
instant it was written, and that is a guarantee this project puts in the engine rather than in a
validator.

## What a resolver has to choose between

1. **Amend `data.owns` to six tables.** The cheapest, and it is what the build already does. It costs
   one line in the lock file and concedes that a module's owned-table list is something the build can
   extend when a decision like D-09 lands.
2. **Fold the window back onto `spend_ceiling` and keep the list at five.** Then `data.owns` is
   correct as written, and the cost is accepted rather than avoided: a full-row `PUT /spend-ceiling`
   can clobber a retention window, and the two policies share a row and an `updated_by`. If this is
   chosen, the mitigation is a partial-update discipline on that route — which is application code
   guarding a property the schema could have made impossible, and this project's standing preference
   runs the other way.

There is no third option in which both the current table layout and the current `data.owns` are
right.

## Why this does not block the build

`blocks_build: false`, on the same footing as the other spec deviations this project has recorded.
The answer changes no seam and no interface: `read_retention_window` and `set_retention_window` have
the same signatures under either option, `write_records` reads neither, and the drain's
`retention_for` resolver is unaffected. Option 1 is a one-line edit to a document. Option 2 is a
migration that moves a column and a route that has to be careful — real work, but work that is
entirely inside call-ledger and touches nothing another module can see.

What it does affect is whether `data.owns` can be trusted as a complete list, which matters to the
step-6 sweep's data-ownership pass more than it matters to the running system.
