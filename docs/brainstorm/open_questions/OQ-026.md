# OQ-026 — Twelve of the eighteen metrics are unreadable or partial, and the path that serves the other six is undeclared

**Raised by Phase 3 plan 03-04 while mounting `GET /metrics`, 2026-08-10.** The code ships either
way — `blocks_build: false` — and the deviations are recorded here rather than absorbed into the
spec, per `.planning/BSP-LINK.md` and `.planning/ORCHESTRATION.md` §5.

**Rated `high` — higher than this phase's other open questions — not because the code is wrong but
because three of the seven declared alerts cannot fire against what is actually scrapable.** An
alert rule that is true on paper is the failure this file exists to name.

Two clauses. A resolver can accept either without accepting the other.

---

## Clause 1 — `prometheus_client`'s registry is per process, and Prope runs two

`prometheus_client`'s default `REGISTRY` is a **process-global** object. Prope runs two processes
(ADR-0033: `app` and `worker`, one image, one host), and **`worker` serves no HTTP by D-17** — which
is *derived from* ADR-0028's *"`app` publishes and never consumes, `worker` consumes and never serves
HTTP"* rather than chosen in discussion, and is therefore not a phase's to reverse.

So `GET /metrics` on `app` serves `app`'s registry, and that registry is missing most of the module.

### Absent entirely — incremented only in `worker`

| Metric | Where its only increment site is |
|---|---|
| `prope_call_ledger_written_total` | `writer.write_records`, called by the drain |
| `prope_call_ledger_write_lag_seconds` | the drain, on the durable moment |
| `prope_call_ledger_queue_depth` | the depth-gauge job (D-42) |
| `prope_call_ledger_dlq_depth` | the depth-gauge job (D-42) |
| `prope_call_ledger_redelivered_total` | the drain, from `message.redelivered` |
| `prope_call_ledger_retention_deleted_total` | the retention sweep |
| `prope_call_ledger_oldest_body_age_seconds` | the retention sweep (D-43) |
| `prope_call_ledger_ceiling_check_total` | `seams.check_spend_ceiling`, called from `worker`'s side |

### Partial — incremented in **both** processes, so `app`'s copy under-counts

`prope_call_ledger_unpriced_total`, `prope_call_ledger_unknown_usage_total`,
`prope_call_ledger_missing_version_id_total`, `prope_call_ledger_duplicate_call_id_total`. All four
are incremented inside `write_records`, which has three callers — the drain (in `worker`), the
direct-write fallback (in `app`), and `price_usage`. **What `/metrics` serves for these is the
fallback's share alone**, which in a healthy system is zero.

### The alerts that read that list

- **`LedgerWriteLagHigh`** — `write_lag_seconds` p95, absent.
- **`LedgerRetentionOverdue`** — `oldest_body_age_seconds`, absent. This one pages.
- **`LedgerDuplicateCallIds`** — `duplicate_call_id_total` against `redelivered_total`: one partial,
  one absent.

### The four answers, with their costs

1. **A metrics port on `worker`.** Reverses a decision *derived from an ADR* rather than chosen; adds
   the surface T-02-15 registers (a port reachable from every container on the compose network); and
   it is refused mechanically as well as architecturally —
   `tests/integration/test_worker_jobs.py::test_worker_imports_no_web_framework` goes red on the
   import alone, before a single line of the server is written.
2. **A Pushgateway.** `worker` pushes, Prometheus scrapes the gateway. ADR-0033 fixes the runtime at
   **seven services and two images**, and this is an eighth service. It also inverts the collection
   model for a system whose whole observability argument is *debuggable by one person* (A-012).
3. **`prometheus_client`'s multiprocess mode over a shared volume.** Genuinely viable: one image, one
   host, one compose file, and the library supports it out of the box. The costs are real and three:
   it needs a **writable volume shared between two containers** (`PROMETHEUS_MULTIPROC_DIR`), it
   **degrades gauges to a chosen reduction mode** — `min`/`max`/`sum`/`livesum` across processes,
   which is a semantics decision per gauge and `queue_depth` and `oldest_body_age_seconds` would want
   different ones — and it is a change to a **deployment stack that owns no milestone**
   (`.planning/research/PITFALLS.md` §4), so no phase in this roadmap would make it.
4. **Ship no exposition at all.** Consistent with Phase 2, which shipped none. But **this is the last
   phase of milestone M1**, so "later" has no owner: no phase would ever ship it, and seven alert
   rules would be true on paper forever.

**What this phase did:** shipped the instrumentation, shipped `/metrics` on `app` as a plain route
(D-39), and wrote the rules file with the reasons attached — with this question raised and the exact
list above in it. Answer 3 is the one to take if the deployment stack ever gets an owner.

## Clause 2 — the eighth path is served against an `apis.exposes` block that does not declare it

`docs/modules/call-ledger.lock.yml` `apis.exposes` lists five `/api/v1` routes plus `GET /healthz`
and `GET /readyz`. **`/metrics` is absent.** `.planning/ORCHESTRATION.md` §5 forbids exposing an API
outside `apis.exposes[]` and prescribes exactly this remedy: name the field, raise the question, ship
the deviation declared.

**The authority already agrees the line is owed.** `docs/architecture/interfaces.md:1236-1239` says
in as many words:

> `/metrics` is declared in no lock file's `apis` block, so registering it would be inventing a seam
> into existence. It is a real surface … and it **should gain an `exposes` line during step 6**
> rather than an INT invented here.

**Step 6 ran** — the lock file carries `ready_for_build: true` — **and did not add the line.**

Meanwhile ADR-0052's Caddyfile already routes the path (`handle /metrics { reverse_proxy app:8000 }`),
so the deployment authority assumes a surface the module authority does not declare. This is a
**declaration** defect and not a design defect: the route itself is right, it is unversioned under
A-045, it declares no session because a scraper has none, and it declares no `ManagementAction`
because ADR-0018 leaves this module nothing to authorise against. Shipping it with the other clause
raised and this one unraised would be absorbing a known spec gap silently.

**No new question id is claimed for this**, because none is available — `OQ-022`…`OQ-026` are fully
consumed and `OQ-027` may belong to a phase being planned in parallel. It is a clause on the
metrics-exposition question that plan 03-04 already owns.

### One input another phase should inherit rather than discover

Serving `/metrics` grew `tests/architecture/test_route_table.py`'s `UNVERSIONED` set **from two paths
to three**, and that set is the list of routes asserted to declare **no** `ManagementAction`.
Access-control's **AC-10** — *"every route in every module declares an action from the vocabulary; a
route declaring none fails the test rather than defaulting to unauthenticated"* — is a Phase 7/9
requirement, and it will meet this exemption set. Enlarging an exemption set is a decision, so it is
written here and at the set itself rather than found by the phase that has to reconcile it.

## Why this does not block the build

`blocks_build: false`. All eighteen metrics exist and are incremented at their declared sites; the
six that live in `app` are readable; the rules file records every threshold and the reason for it;
and `tests/architecture/test_alert_rules.py` fails the day a rule names a metric that is not real.
What the answer settles is whether Prope's two processes ever share one scrape target, and whose lock
file records that `/metrics` is a surface this system serves.
