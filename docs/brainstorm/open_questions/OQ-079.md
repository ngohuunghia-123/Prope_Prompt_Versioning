# OQ-079 — `access_level` has no permission that changes it and no disjunct that reads it

**Raised by Phase 14 planning, 2026-08-11.** `blocks_build: false` — plans 14-01 and 14-03 adopt answers
to both halves and record them as UNCONFIRMED. Two findings about one column, raised together because
they are the same column and the same answer probably settles both.

`prompt_property.access_level` is the field that decides whether a prompt is private. Non-negotiable #4
is *"prompts are private by default, enforced as not-found, never forbidden, and by RLS underneath."*

## 1. No action in the vocabulary changes it

INT-001's caller table gives prompt-registry six actions, two of which do not exist under those names:

| INT-001 | A-115 (the normative vocabulary) |
|---|---|
| `prompt.change_owner` | `prompt.transfer_owner` |
| `prompt.change_access` | **absent** |

Phase 7's **D-99** settles which wins: *where A-115 and INT-001 spell an action differently, **A-115
wins***, because `role_permission.action`'s `CHECK` mirrors A-115's list. Phase 7 raised the
disagreement as `OQ-041` and `OQ-042`; phase 8 raised its own form as `OQ-046` and assigned **`prompt.grant`**
— A-115's nearest name — to **access-control's** grants routes, which write `access.prompt_grant` rows.

So the `PATCH` route the lock describes as covering *"title, purpose, tags, **access level**, owner"*
carries **three distinct permissions**, one of which has no name:

- `prompt.edit` — title, purpose, tags;
- `prompt.transfer_owner` — owner;
- **nothing** — access level.

`declares_action` attaches exactly **one** action to a route, which is what phase 23's AC-10 asserts
about the assembled table.

**Plans 14-01 and 14-03 ship**: the route declares `prompt.edit`; a request that moves `owner_id` gets a
**second** `may()` call for `prompt.transfer_owner` and a `403` naming it if denied; and an
`access_level` change rides on `prompt.edit`, as the narrowest existing action that covers it.

**Minting `prompt.change_access` as a twenty-sixth member was rejected** here: `vocabulary.Action` is
mirrored by a `CHECK` constraint in **access-control's** migration, so adding a member from
prompt-registry's phase is a cross-module schema change taken to avoid writing down a question. So is
refusing every `access_level` change until the question is answered — it would make a declared,
`CHECK`-constrained column unwritable and break phase 15's own private-by-default fixtures, which need a
prompt to become `workspace`.

## 2. No disjunct in INT-002's declared caller query reads it

INT-002 returns `{mode: all | none | ids}` and plan 08-02's contract states the caller's half in the
caller's own words:

> The registry's query is `WHERE workspace_id = :ws AND (owner_id = :actor OR id = ANY(:ids))`, and this
> function supplies only the second disjunct.

**Two disjuncts.** Phase 9's `is_visible` — the row-level counterpart, used by access-control's own
routes — has **three**:

> `True` when `actor_id == owner_id`, or `grant_level is not None`, or (`access_level == "workspace"` and
> `is_active_member`).

Under the two-disjunct form, a prompt whose `access_level` is `workspace` is visible to its owner, to
grantees, and to any actor whose role binding produced `mode: all` — and **to nobody else**. A colleague
who is an active member with no role binding conferring `prompt.read` and no grant cannot see it. That
makes `workspace` and `private` behave identically for that person, which is not obviously what a column
with two values is for.

**Plan 14-01 ships the two-disjunct form INT-002 specifies**, because it **fails closed** and because the
alternative — a third disjunct — needs `is_active_member`, which lives in `access.workspace_member`, a
table `prompt-registry.lock.yml`'s `data.reads` forbids joining to (*"through its API, never by joining
across module tables"*). Asking access-control per row is the exact thing A-118's set form exists to
replace.

## What the answer changes

- **If `access_level` deserves its own permission**, `vocabulary.Action` and `role_permission`'s `CHECK`
  both grow by one member, every workspace's role matrix has to be told about it, and the `PATCH` handler
  gains a third `may()` call. Cheapest **now**, while no workspace holds a real matrix (A-020).
- **If it does not**, INT-001's caller table should drop `prompt.change_access`, because it names a
  permission that cannot be granted.
- **If `workspace` access level should be visible to plain members**, either `visible_subject_filter`
  returns `mode: all` for that case — which folds the third disjunct into access-control, where the
  membership row is, and is the only answer that does not create a cross-module join — or INT-002's
  declared caller query grows a third disjunct and prompt-registry needs a way to know membership that
  does not exist today.
- **If it should not**, `is_visible`'s third clause is dead for this module and `access_level` is
  effectively a two-value column with one reachable value, which is worth saying out loud.
- **Phase 15 owns PR-03** (*a private prompt is absent from another person's search results*) and is the
  phase this answer lands in. It is raised here because phase 14 is where the query and the route are
  written, and phase 15 will otherwise inherit the choice without seeing it made.
