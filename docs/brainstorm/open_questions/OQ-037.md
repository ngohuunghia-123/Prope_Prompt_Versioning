# OQ-037 — `prope_property_history_rows_total` is declared as a gauge that no database role available to the running process can compute.

**Raised by Phase 6 planning, 2026-08-11.** It is a second, independent problem with the same metric
OQ-030 is about, and it survives whichever way OQ-030 is answered. OQ-030 asks *should the gauge carry
a `workspace_id` label*. This one asks *can anything set it at all*.

## The conflict, stated exactly

`docs/modules/property-history.lock.yml`, `observability_requirements.metrics`, declares:

```yaml
    - prope_property_history_rows_total
      # gauge, labels: workspace_id
```

A gauge must be set by something. There are exactly two shapes it could take, and both are blocked by a
decision that is already made.

**Unlabelled — a single global row count.** Computing it needs one query across every workspace's rows.
`history.history_event` is tenant-scoped under ADR-0045, and ADR-0035's policy predicate is
`workspace_id = current_setting('app.workspace_id', true)`. A `prope_app` query issued with no workspace
set therefore **matches nothing and returns zero rows** — the policy working exactly as designed. The
gauge would read `0` forever, and a metric that is permanently zero is indistinguishable from a healthy
one.

This is not a hypothetical. `src/prope/worker.py`'s `ObservedWorkspaces` docstring already makes the
identical argument for call-ledger's retention sweep, in the repository, today:

> A cross-tenant sweep needs a list of tenants, and under ADR-0045 there is no way for `prope_app` to
> produce one from the ledger … A `SELECT DISTINCT workspace_id` written here would therefore return an
> empty list forever, and the sweep built on it would run cleanly, delete nothing, and look healthy —
> which is the one failure mode this whole job is shaped against.

The second instance of a failure is what shows it is structural rather than a local oversight.

**Labelled by `workspace_id` — one series per tenant.** Computing it needs the list of tenants, which is
the same problem. ADR-0051 answers it for the general case with `access.list_workspaces()`, a sanctioned
`SECURITY DEFINER` function returning identifiers and nothing else — and that function arrives with the
`access` schema in **Phase 7**. property-history is planned in Phases 4–6.

**The two obvious workarounds are both closed.**

- **`prope_report`** (ADR-0037) holds `BYPASSRLS` and can read across workspaces. It is a hand-run
  reporting credential, deliberately not held by `app` or `worker`; handing it to a process to set a
  gauge would put a full-read credential in the runtime environment to answer an operational
  convenience question.
- **A fifth `SECURITY DEFINER` function** is refused outright. Exactly four are sanctioned
  (`access.lookup_session`, `access.lookup_api_key`, `evaluation.claim_next_run()`,
  `access.list_workspaces()`), a test asserts the set is exactly those four, and *a fifth is never the
  answer*.

## Why this is a real conflict and not a scheduling detail

Because the metric is declared in a block a phase is required to ship, and the phase that ships it
(Phase 6) has no way to give it a value. The available outcomes are: ship a gauge that is permanently
and misleadingly zero; ship nothing and leave a declared metric absent; or ship the declaration, leave
it unset, and say so. Only the third is honest, and it is only defensible if it is written down — which
is what this file is.

There is also a real operational question underneath. `history_event` is the one table in Prope that
**only ever grows** — A-121 keeps events forever, there is no retention setting and no expiry job — and
`performance_requirements` records an explicit expectation to be wrong about (*"< 500 events per prompt
property per year at pilot volume"*). A row-count gauge is exactly how you would find out that
expectation was wrong. It deserves an answer rather than a shrug.

## The shape of the possible answers

1. **Declare it now, set it in Phase 8, behind `access.list_workspaces()`.** The gauge exists from
   Phase 6 so a baseline and an alert can be written against it (`REGISTRY.get_sample_value` answers
   `None`, not `0.0`, for a metric nothing has touched, so a lazily-defined metric is
   indistinguishable from one that was never wired — the argument `src/prope/observability.py` already
   makes at length for call-ledger's eighteen). Phase 8 adds a supervised sweep in `worker` that
   enumerates workspaces and sets it. **This is what Phase 6 implemented**, and the recommendation.
2. **Set it per workspace, opportunistically, inside an existing `workspace_transaction`.** Cheap, and
   it requires the `workspace_id` label — so it cannot be chosen without reversing OQ-030's answer. It
   also reports each workspace's count only as often as that workspace writes, so a quiet tenant's
   series goes stale rather than absent, which is the worse of the two.
3. **Drop the metric and route the question to A-126's hand-run Success SQL** under `prope_report`,
   which already reads across workspaces by design and is not a metric. Answers the question at pilot
   review rather than continuously, which may be the honest cadence for a table that grows slowly.

**A recommendation:** option 1. It keeps the declaration where an alert can be written against it,
puts the setter in the phase that first has the tool for it, and takes no position on OQ-030 that
OQ-030 has not already taken.

## What Phase 6 shipped

`prope_property_history_rows_total`, **unlabelled** (per OQ-030's resolution, adopted UNCONFIRMED as
D-91), registered at import in `src/prope/property_history/observability.py`, **with no setter**, and
with this file and OQ-030 both named at the declaration together with Phase 8 as the owner of the
setter. No lock file and no ADR was edited.
