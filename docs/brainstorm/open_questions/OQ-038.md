# OQ-038 — a failure mode's mitigation depends on a registry field the schema does not declare.

**Raised by Phase 6 planning, 2026-08-11.** Two fields of one lock file disagree with each other, and
the disagreement decides whether the module's only silent-by-nature failure is detectable.

## The conflict, stated exactly

`data.owns` declares the registry's fields:

```yaml
    - table: history_action_registry
      fields: action, target_type, detail_keys, requires_reason, writing_module
```

Five. `failure_modes` row 3 — the prompt-scoped event appended with a null `scope_prompt_id` — states
its mitigation as:

> The registry records which actions are prompt-scoped, so the check is data-driven rather than a list
> in code; the counter labels by action so the offending event type names itself.

The registry does not record it. There is no sixth field, and none of the five carries the information:
`target_type` is the nearest, but it is a different fact and, per **OQ-029**, it is declared a closed
enumeration and is enumerated nowhere in `docs/` — so deriving prompt-scoped-ness from it would rest on
a set that is itself underspecified.

## Why this matters more than a missing column usually would

Because of what it guards. The lock is explicit that this is **the only failure mode in this module
that is silent by nature**:

> The write succeeds and the event is simply absent from that prompt's Activity feed. This is the only
> silent-but-detectable failure here, and it is silent in the direction that matters — a screen that
> looks complete and is not.

`prope_property_history_null_scope_prompt_total` and the `PropertyHistoryScopeMissing` alert exist for
exactly this, and both need to know which actions are prompt-scoped. Without the field, the check has
to be a list in code — which the mitigation rejects by name, and for a good reason: the vocabulary is
already maintained in five lock files and one migration, and AC-6 exists to stop it being maintained in
a seventh place by hand.

There is a related fact worth putting in front of a resolver. **A-119 states the rule in prose**:

> Null for workspace, member, role, key, and provider events, which have no prompt.

That is a derivation rule, stated once, in an assumption file — not data, and not checkable. It is
correct as far as it goes, and it is the source Phase 6 used for the seed values.

## The seam consequence, so it is not discovered later

`docs/architecture/interfaces.md` INT-008 declares `registered_actions()`'s return as
`[{action, target_type, detail_keys, requires_reason}]` — **four keys**. Adding a column, and returning
it, is a **widening of a registered seam**. It is the second widening this module has taken: Phase 4
recorded the first (`HistoryEventDraft` carries an `id` that INT-006's ten-field envelope does not
name). Neither is a violation of anything; both are things a spec should say and does not.

## The shape of the possible answers

1. **Add `prompt_scoped boolean NOT NULL` to `history_action_registry`**, seed it per action, and drop
   the column default so a thirty-second action must state its intent. Makes the mitigation's own words
   true. **This is what Phase 6 implemented.** Costs one additive migration and one field on
   `RegisteredAction`; widens INT-008's declared return if `registered_actions()` returns it.
2. **Derive it in Python from `target_type`.** No schema change, and it is precisely *"a list in code"*.
   It would also need OQ-029 answered first, since the `target_type` vocabulary it would switch on is
   declared closed and enumerated nowhere.
3. **Drop `null_scope_prompt_total` and `PropertyHistoryScopeMissing`.** Consistent, and it gives up
   detection of the module's only silent failure. Should not be chosen by default; if it is chosen, it
   should be chosen deliberately.

**A recommendation:** option 1, on the mitigation's own words — *data-driven rather than a list in
code* — and because the per-action values are a judgement worth reviewing once, in a migration with a
comment per action, rather than a rule somebody reimplements in each of the four writing modules.

## What Phase 6 shipped

An additive migration adding `prompt_scoped boolean NOT NULL`, seeded **true** for nineteen actions
(prompt-registry's five, release-control's eight, evaluation's four, and access-control's
`access_granted` / `access_revoked`) and **false** for twelve (access-control's other eight and
provider-access's four), with the column's default dropped afterwards; `RegisteredAction` gains the
field; and `prope_property_history_null_scope_prompt_total` is driven by it. The nineteen / twelve split
is asserted in the migration's own acceptance test, so a drift from the seeded vocabulary fails rather
than passing quietly. No lock file, ADR or interfaces row was edited.
