# OQ-039 — the third declared alert reads a series the metrics block does not declare.

**Raised by Phase 6 planning, 2026-08-11.** This is the second instance in Prope of one lock file's
`alerts` block requiring a metric its own `metrics` block does not list. The first was **OQ-022**
(call-ledger's T-005 required a dead-letter-queue depth gauge that the seventeen-name metrics block did
not carry). A pattern with two instances is worth naming as a pattern.

## The conflict, stated exactly

`observability_requirements.alerts` declares three alerts. The third:

> **PropertyHistoryWriteFailure** — append errors excluding rejections, over 5 min, page. In a shared
> database (ADR-0023) this means the database is failing, and it will already be visible elsewhere; the
> alert exists so that "the audit log stopped" is never inferred late from an empty screen.

`observability_requirements.metrics` declares seven names:

```
prope_property_history_append_total
prope_property_history_append_duration_seconds
prope_property_history_append_rejected_total
prope_property_history_read_duration_seconds
prope_property_history_events_returned
prope_property_history_rows_total
prope_property_history_null_scope_prompt_total
```

None of them counts an append error. `append_rejected_total` counts **exactly what the alert
excludes** — its declared `reason` label is `unknown_action | unknown_detail_key | missing_reason`, the
three caller-bug refusals, and the lock says of it that it *"must stay 0 in a correct build — every
increment is a caller bug that has just failed a user's transaction."* A database failure is not a
caller bug and must not be counted on that series; a fourth `reason` value would also break the closed
three-member set the lock declares and a test asserts.

`append_duration_seconds` observes durations regardless of outcome, so a rate on it moves under failure
and under load alike. `PropertyHistoryWriteFailure` has nothing to read.

## Why this is a real conflict and not a wording quibble

Because the alert is the module's answer to a specific, stated failure: *"the audit log stopped" is
never inferred late from an empty screen.* On the module whose product claim is that the record exists,
the alert that fires when the record cannot be written is not decoration. An alert that cannot be
written is a mitigation nobody built — which is exactly the sentence
`src/prope/observability.py` already carries about OQ-022's gauge:

> its `security_requirements` T-005 requires a gauge on the dead-letter queue's depth and alerts on any
> non-zero value, and that eighteenth name appears nowhere in the metrics block. That omission is raised
> as `docs/brainstorm/open_questions/OQ-022.md` rather than absorbed, and the gauge ships here because a
> mitigation that is declared in one section and absent from the other is a mitigation nobody built.

## The count consequence, stated so a later reader does not read it as a mistake

`.planning/ROADMAP.md`'s Phase 6 Spec line says *"7 metrics"*, and the module now registers **eight**.
The eighth is `prope_property_history_append_failed_total`. Anyone auditing the metric count against
the ROADMAP will find a discrepancy; this file is why.

## The shape of the possible answers

1. **Declare an eighth metric, `prope_property_history_append_failed_total`** — unlabelled, incremented
   in an `except` clause that re-raises the exception unchanged, excluding `HistoryAppendRejected` —
   and write the alert against it. **This is what Phase 6 implemented**, and it is the same resolution
   Phase 2 gave OQ-022's gauge. Cost: one counter and a `try/except/raise` on the append path, which is
   inside a p95 < 3 ms budget and is two comparisons in the healthy case.
2. **Drop the alert.** Consistent with the metrics block, and it gives up the only signal that says the
   audit log has stopped. The lock's own sentence argues against it.
3. **Reword the alert against a series that exists** — for example a fall in
   `rate(append_total)` against a baseline. Needs no new metric and is much weaker: an audit log that
   has stopped because nothing is happening looks identical to one that has stopped because every write
   is failing, and the two need opposite responses.

**A recommendation:** option 1, on OQ-022's precedent. The two cases are the same shape and answering
them differently would be the arbitrary choice.

## One thing a resolver should decide alongside it

Whether `append_failed_total` should carry a label. Phase 6 shipped it **unlabelled**, on
`src/prope/observability.py`'s stated reason for `metadata_dropped_total` — *every such failure is the
same kind of event regardless of whose it was*, and the obvious label (`workspace_id`) is the one
ADR-0030 forbids. An exception-class label was considered and not taken: the class names are asyncpg's
and SQLAlchemy's, which is an open set fixed by a dependency rather than by this project.

## What Phase 6 shipped

`prope_property_history_append_failed_total`, unlabelled, incremented at the single append site inside
`except Exception:` followed by a bare `raise`, after an `except HistoryAppendRejected: raise` clause
that ensures a rejection is never counted as a failure. Nothing is swallowed; INT-006's contract that
*the raise is the mechanism* is unchanged. `deploy/prometheus/rules/property_history.rules.yml` carries
`PropertyHistoryWriteFailure` written against it, with a YAML comment naming this file. No lock file,
ADR or ROADMAP line was edited.
