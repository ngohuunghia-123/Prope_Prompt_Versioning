# OQ-084 — The search load condition names no workspace count, no filter set and no permission shape, and search has no acceptance criterion to settle any of them

**Raised by Phase 15 planning, 2026-08-11.** `blocks_build: false` — plan 15-05 adopts one reading, states
it, and measures it. Raised because three different readings of the same condition produce three different
tests, and PITFALLS gap 5 already records that nothing else in the specification adjudicates:

> **Search and filter has no acceptance criterion.** It is a named `in_scope` capability of
> prompt-registry with a stated p95 < 500 ms performance requirement and a `test_plan.load` entry, but the
> only ACs that would cover its semantics are the owed AC-10 and AC-11.

## The problem, stated once

*"1,000 prompt properties × 20 revisions; single keyword + two filters"* under-determines the test in
four ways, and each one moves the number.

1. **How many workspaces?** The trigram index is over `prompt_property.search_text` for the whole table
   and the tenant policy narrows the scan. 1,000 properties in **one** workspace is the worst case for the
   index and the honest reading of *"a workspace with 1,000 prompts"*; 1,000 spread over ten workspaces
   makes the policy do most of the work and measures something easier. The condition names neither.

2. **Which two filters?** `scope.in_scope` lists six filterable fields — title, body, owner, status,
   access level, tag. `tags` is an array column, `status` and `access_level` are low-cardinality CHECK
   sets, and `owner_id` is high-cardinality. `owner + tag` and `status + access_level` have different
   plans and different selectivities, and a filter pair that selects two rows measures nothing about a
   1,000-row corpus.

3. **Whose permission?** A-118 puts the permission filter in the same statement, and it is the disjunct
   whose cost varies most: an actor with `mode: all` contributes nothing, an actor with 500 grants
   contributes a 500-element `ANY(:ids)`, and an actor with none contributes a predicate that eliminates
   almost everything before the trigram index is consulted. The fastest and the slowest actor differ by
   more than the target.

4. **Measured where?** Through HTTP (which includes session lookup, `visible_subject_filter`, response
   serialisation and pagination) or at the repository call (which is the only span
   `prope_registry_search_duration_seconds` covers, per phase 13's plan 13-04). The metric's buckets were
   chosen with `0.5` as an edge because *"p95 < 500 ms is the target"*, which implies the metric's own
   span — but the target is written under `performance_requirements` beside three others that are plainly
   end-to-end.

## The candidates

**A — the pessimistic single-workspace reading** (adopted by plan 15-05): 1,000 properties × 20 revisions
in **one** workspace, `owner + tag` as the two filters, an actor whose visibility comes from a **grant
list** rather than from `mode: all`, and the p95 measured at the repository call — the span
`search_duration_seconds` observes and the one a later regression would be attributed to. Cost: it is
harder than any reading the words require, so a pass proves more than was asked and a failure may be
about a condition nobody specified.

**B — the literal minimum**: 1,000 properties across whatever workspaces are convenient, any two filters,
`mode: all`. Cheap, fast, and it would pass on a sequential scan, which is what makes it useless as the
guard on ADR-0048's index.

**C — write the missing acceptance criterion first.** Search has no AC; give it one, in the shape AC-10
and AC-11 already have, and let the load condition follow from it. This is the right answer and it is a
lock-file edit, which is why it is a question rather than a decision.

## What phase 15 shipped

**Option A**, with every one of the four choices written out in the test module's docstring and this
question cited by id, so that a later reader can see which reading was measured rather than inferring it
from the fixture. Plan 15-05 also records the observed p95 in its SUMMARY, so the headroom is a number
rather than a pass.

**One consequence stated rather than discovered:** under Option A the corpus is 1,000 properties and
20,000 revisions, and the `search_text` trigger fires on every revision insert. Building that corpus
through `create_revision` would run the composer 20,000 times. Plan 15-05 builds it with bulk SQL and
measures the trigger's per-insert cost separately, which is a second small number the milestone does not
otherwise have.

## What the answer changes

Option A: `performance_requirements`' condition line gains a workspace count, a named filter pair, a
permission shape and a measurement point. Option B: plan 15-05's corpus fixture shrinks and its
assertion stops guarding the index. Option C: one new `acceptance_criteria` row with a `test_ref`, and
`REQUIREMENTS.md` gains a `PR-07` — which is a renumbering-adjacent change to a file ORCHESTRATION §1
freezes, so it needs the user rather than an agent.
