# OQ-142 — A-143's cap has metrics and a threat row, and no alert

**Raised by the gateway build, 2026-08-12.** `blocks_build: false` — the alert ships. This asks
whether the lock's alert list should gain the seventh entry it already implies.

## The contradiction

`A-143` declares its own metrics in as many words:

> **Metrics**: `prope_gateway_admission_refused_total{key_id_bucket}` — bucketed, never the raw key
> id (ADR-0030 forbids a `consumer_key` label), plus `prope_gateway_inflight` as a gauge.

and closes with *"Metrics, alerts and an AC for the cap are owed to step 6"* (recorded again in
`gateway.lock.yml`'s change log for 2026-08-09). Step 6 ran. It wrote `T-013` — HIGH, mitigated by
A-143 — into `security_requirements`, and it wrote the cap's assertions into `test_plan.security`.
It did **not** add either metric to `observability_requirements.metrics`, and it did not add an alert
to `observability_requirements.alerts`.

So the cap is declared, threatened, tested, and unwatched.

## Why it shipped anyway

The same precedent call-ledger's eighteenth metric set, and for the same reason recorded there: **a
mitigation that is declared in one section and absent from the other is a mitigation nobody built.**
An in-flight cap with no alert is a control whose only symptom is 429s arriving in somebody else's
product — Prope would be the last to know, and the number A-143 chose is explicitly a default set
without a measurement:

> **Impact if wrong**: too low and a legitimate batch consumer sees 429s it did not earn — visible
> immediately, fixed by raising one number on one key.

*Visible immediately* is only true if something is watching.

## What shipped

`deploy/prometheus/rules/gateway.rules.yml` carries seven alerts where the lock declares six. The
seventh is:

```yaml
- alert: GatewayAdmissionRefusedSpike
  expr: sum(increase(prope_gateway_admission_refused_total[5m])) > 0
  for: 5m
  labels: {severity: ticket}
```

A **ticket** rather than a page: a refusal at the cap is the control working as designed, and the
question it raises — *is 20 the right number for this consumer* — is a settings change on one key
rather than an incident. `for: 5m` is what separates a sustained condition from a burst.

Three metrics ship that the lock's metrics block does not name, all three named by A-143 or by the
threat it mitigates: `prope_gateway_admission_refused_total`, `prope_gateway_inflight`, and
`prope_gateway_oversize_request_total` — the last named by A-148 and by `T-012`, in the same shape:
declared in the security section, absent from the observability one.

## What is being asked

One of two:

1. **Add the three metrics and the alert to `gateway.lock.yml`.** This is what ships today, and it
   is what A-143's own closing sentence asked step 6 to do.
2. **Say the cap should be unwatched**, and delete the alert. Nobody has argued this and it is hard
   to argue: the counter is the only place the cap is visible from inside Prope.

Reversal cost: low. Deleting a rule is deleting a rule.

## What is affected either way

- `deploy/prometheus/rules/gateway.rules.yml` — the seventh rule
- `tests/architecture/test_gateway_alert_rules.py` — `DECLARED_ALERTS`, which carries the reason
- `src/prope/gateway/observability.py` — the three declarations
- `docs/modules/gateway.lock.yml` — **not edited**
