# OQ-030 — property-history declares a metric labelled by `workspace_id`, and a Phase 2 test already asserts no `prope_*` metric may carry one.

**Raised by Phase 4 planning (04-PATTERNS.md), 2026-08-10.** `blocks_build: false` for Phase 4 —
this phase ships one metric, `prope_property_history_append_rejected_total`, whose only label is
`reason` from a closed three-member set. **It blocks Phase 6**, which owns the other six metrics in
`observability_requirements`, and the test that will fail there was written in Phase 2 and is green
today.

This is the fourth conflict Phase 4 raises. It is its own file because it blocks a different upstream
field from OQ-027 (the vocabulary count), OQ-028 (the naming rule) and OQ-029 (the undeclared
enumerations), and a resolver can accept any one without accepting the others.

## The conflict, stated exactly

`docs/modules/property-history.lock.yml`, `observability_requirements.metrics`, declares:

```yaml
    - prope_property_history_rows_total
      # gauge, labels: workspace_id
```

`src/prope/observability.py:1-33` states the project rule, at length, in the module every metric in
Prope is declared in:

> Metric label cardinality is bounded by construction: every label declared here has a CLOSED set of
> values fixed in source, and `workspace_id` — the highest-cardinality identifier in the system and
> the one most tempting to add — is deliberately never a label.

`tests/broker/test_publish_confirm_failures.py:239-250` turns that sentence into an assertion over
the live registry, scoped to **every** `prope_*` metric rather than to call-ledger's five:

```python
async def test_workspace_id_is_never_a_metric_label() -> None:
    """ADR-0030's bounded cardinality, asserted rather than intended.

    ``workspace_id`` is the highest-cardinality identifier in the system and the
    most tempting label to add. Its absence is the control that keeps the metric
    set bounded as seven more modules land.
    """
    for metric in REGISTRY.collect():
        if not metric.name.startswith("prope_"):
            continue
        for sample in metric.samples:
            assert "workspace_id" not in sample.labels, metric.name
```

The docstring's last sentence — *"as seven more modules land"* — is the test declaring its own scope.
property-history is one of the seven, and it is the first to land a metric.

## Why this is a real conflict and not a naming quibble

The clash is not between two documents. It is between a lock file and **executable code that already
exists**, and the failure has a date: the first time Phase 6 registers
`prope_property_history_rows_total` with a `workspace_id` label and the whole suite runs, that test
goes red — in a file belonging to another module, in another package, asserting a rule nobody in
Phase 6 was editing. `.planning/ORCHESTRATION.md` §9 forbids a red test nobody predicted; this file
is the prediction.

The cardinality argument is also real rather than procedural. A gauge labelled by workspace produces
one time series per workspace, forever, and a Prometheus series is never reclaimed while the process
lives. At pilot scale that is small; the rule exists because the number is unbounded in principle and
`workspace_id` is a `wsp_`-prefixed ULID rather than a member of any closed set. ADR-0030 chose
"bounded by construction" over "bounded in practice" precisely so nobody has to make that judgement
per metric.

## What the lock file wants, and why it is not unreasonable

`prope_property_history_rows_total` answers "how big is the audit log per tenant", which is a real
operational question on the one table in Prope that only ever grows (A-121) and has no retention job.
Without a label it answers only "how big is the audit log", which does not tell an operator which
workspace to look at.

So this is a genuine trade rather than an oversight in the lock file, and it should be decided rather
than silently resolved in whichever direction the first implementer notices.

## The shape of the possible answers

1. **Drop the label. Amend the lock file to `prope_property_history_rows_total` unlabelled.**
   Matches ADR-0030, matches `observability.py`'s stated rule, matches the existing test, changes no
   code. The per-workspace question moves to the place it already belongs: A-126's hand-run Success
   SQL under `prope_report` (ADR-0037), which reads across workspaces by design and is not a metric.
2. **Keep the label and narrow the test to call-ledger's metrics.** Buys the per-tenant gauge at the
   cost of removing the only control that keeps the metric set bounded as seven modules land — which
   is the exact property that test's docstring says it exists to protect. If this is chosen, the
   narrowing must be a stated amendment to ADR-0030, not an edit to a test's `if` clause.
3. **Keep the label and bound it another way** — a gauge over the top *N* workspaces, or a histogram
   of per-workspace row counts with no identifying label. Answers the operational question without an
   unbounded series set. More machinery than the question has yet earned.

**A recommendation:** option 1, with the per-workspace question routed to A-126's hand-run SQL. The
gauge's value to an operator is "is the audit log growing faster than expected", which the unlabelled
series answers; "whose" is a question asked once, at pilot review, by somebody who already has
`prope_report`.

## Why this does not block Phase 4

Phase 4 ships exactly one metric. ROADMAP success criterion 3 names
`prope_property_history_append_rejected_total` by name, its declared labels are
`reason = unknown_action | unknown_detail_key | missing_reason` — a closed set of three fixed in
source — and it carries no `workspace_id`. The remaining six metrics and all three alerts are
Phase 6's (`04-CONTEXT.md`, "Fixed out of scope by ROADMAP"). Nothing in Phase 4 touches the
conflicting declaration, and no spec file is edited to agree with anything.
