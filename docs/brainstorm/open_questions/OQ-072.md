# OQ-072 — `prompt_property.status` has no declared vocabulary, and the five literal statuses do not supply one

**Raised by Phase 13 planning, 2026-08-11.** `blocks_build: false` — plan 13-01 adopts a two-value set
and records it as UNCONFIRMED.

## The problem, stated once

`data.owns` lists `status` as a field of `prompt_property`. **No authority in the repository says what
may be stored in it.** The nearest statements are:

- `data.owns.revision.notes`: *"Stored values are `Draft` | `In review` | `Approved`. 'In use' is derived
  from `prompt_property.released_version_id` and is never stored here (A-065); **'Retired' is a
  prompt_property status** (A-049)."* — one value, by exclusion.
- A-049: *"A property reaches the end of its life as `Retired`."* — the same one value.
- ADR-0053 rule 9 and `00_context.md`: the five literal statuses are `Draft`, `In review`, `Approved`,
  `In use`, `Retired`.

Four of those five are accounted for elsewhere: three are `revision.status` values and `In use` is
explicitly derived and never stored. So the five-status vocabulary contributes exactly one value to this
column and is silent about what a prompt property is **before** it is retired.

This is not a naming quibble. The column takes a `NOT NULL` CHECK constraint in the migration, the
retire command compares against it, `GET /api/v1/prompts` filters on it (INT-024), and the SPA's i18n
catalogue needs a key per value. A phase that guesses silently makes four downstream surfaces agree with
a guess.

## The candidates

**A — `Active` | `Retired`.** Two values, the second one declared. Reads correctly in a filter
(*"status: Active"*), needs one new i18n key, and matches how A-052's refusal is phrased
(*"refused while a release is active"*).

**B — `Draft` | `Retired`,** reusing a literal from the five. Rejected on collision: `Draft` is already a
`revision.status` value, and a UI showing *"Draft"* against a prompt that has an approved-and-released
revision is wrong in the one place the product exists to be right.

**C — no `status` column at all**, deriving *retired* from a `retired_at timestamptz` being non-NULL.
Honest, and it is how several other columns in this project work. Rejected because the lock declares
`status` as a field and INT-024's list endpoint filters by it; deleting a declared column is a larger
deviation than choosing values for it.

## What phase 13 shipped

**Option A**, as `CHECK (status IN ('Active', 'Retired'))`, with `'Active'` the value every registration
lands. Recorded at the constraint and in the migration docstring, with this question named.

Two consequences stated rather than left to be discovered:

1. **`Active` becomes a sixth literal status**, so ADR-0053 rule 9's *"five statuses"* is false by one
   the moment this ships, and the `vi` catalogue needs a key for it. That is the strongest argument for
   answering this question rather than leaving it adopted.
2. **`Retired` is terminal and the engine says so**: `ck_prompt_property_retired_has_no_release` refuses
   a row that is `Retired` while `released_version_id` is not NULL, which is A-052 carried by the
   database as well as by the refusal message SC3 requires.

## What the answer changes

One `CHECK` constraint in one migration, one Python constant, and one i18n key. **Cheap now, and it stops
being cheap the moment a workspace holds prompts** — a value set that changes after rows exist is a data
migration over the column every list endpoint filters on.
