# OQ-067 — `origin = prope` is a declared label value with no member in the closed error set

**Raised by Phase 12 planning, 2026-08-11.** `blocks_build: false` — Phase 10 already added two such
members and Phase 12 adds two more, each with its four facts written at the row. Raised because this is a
**closed vocabulary that two consumer modules branch on and every call record stores a member of**, and
because it is now the fourth time a phase has had to widen it by inference rather than by reading it.

**This is not `OQ-055` or `OQ-060`.** Those two are about the *same* set being written twice with
different names and a different count (eight in ADR-0017, seven in INT-015, three renamed, one missing).
This one is about the set having no member of a **kind** its own metric's label declares. A resolver could
answer both of those and leave this untouched, which is why it is a separate file.

## The problem, stated once

`prope_provider_access_error_total`'s declared labels are:

```
class, origin = prope | provider, fallback_eligible, retryable
```

`origin` is a **declared two-valued label**, and the lock file argues for it explicitly in the
admission-ceiling failure mode: *"`origin = prope | provider` is a label on every error precisely so the
two are never one number (A-095)."*

But both authoritative lists of `class` values contain only descriptions of what the **provider** did:

| Authority | Classes |
|---|---|
| ADR-0017 | `credential_rejected`, `rate_limited`, `upstream_unavailable`, `timeout`, `model_not_available`, `content_filtered`, `invalid_request`, `provider_contract_violation` |
| INT-015 | `timeout`, `rate_limited`, `credential_rejected`, `upstream_5xx`, `bad_request`, `content_filtered`, `transport` |

So `origin = prope` is a label value **no declared class can carry**. Any Prope-origin failure has to
either take a provider-shaped class — which puts Prope's own faults into the counter an operator reads to
decide whether the provider is broken — or introduce a class neither authority names.

## The four Prope-origin conditions the lock file itself describes

Each is a failure mode or a chaos clause in `docs/modules/provider-access.lock.yml`, and none has a class:

| Condition | Where the lock file describes it | Class adopted | fallback_eligible | retryable | Added by |
|---|---|---|---|---|---|
| The KEK is unavailable | `failure_modes` row 1; AC-12 requires *"a class distinct from every provider-origin class"* | `kek_unavailable` | true | false | Phase 10, plan 10-02 |
| Prope's own admission ceiling sheds a dispatch | `failure_modes` row 4; the `ProviderInteractiveShed` alert | `admission_shed` | true | true | Phase 10, plan 10-02 |
| `base_url` resolves into a blocked range | `failure_modes` row 9; `security_requirements` T-025; AC-11 | `address_refused` | true | **false** | Phase 12, plan 12-01 (D-203) |
| `deadline_ms` is consumed before any upstream request — e.g. a database that accepts and never answers during a decrypt-cache miss | `test_plan.chaos` clause 5 | `dispatch_deadline_exceeded` | true | **true** | Phase 12, plan 12-05 (D-217) |

Note that the last two differ on `retryable` and agree on `fallback_eligible`, which is the clearest
available demonstration of why the lock file keeps them as separate facts rather than one bit: a blocked
address is deterministic until somebody edits a configuration, and a stalled database is transient.

## Why the alternative is worse

The tempting shape is to reuse `timeout` for the fourth row and `invalid_request` for the third, because
both already exist. Both carry `origin = provider` in ADR-0017's table, and Phase 10's table maps each
class to exactly one row with one origin — its own closure test asserts every member appears exactly once.
So reusing them means either:

- **putting Prope-origin failures into `error_total{origin="provider"}`**, which makes
  `GatewayFallbackRateHigh`, `ProviderCredentialRejected` and the whole provider alert block point at the
  wrong seam. This is precisely the defect AC-12 forbids for the KEK — *"no log line suggests a provider
  outage"* — applied to the other three; or
- **giving one class two origins**, which breaks the table's own uniqueness invariant and makes the
  taxonomy the gateway branches on ambiguous at exactly the point it is being read.

## What is being asked

1. **Should ADR-0017's Decision table be widened to a documented `origin = prope` group**, with the four
   members above, so the next phase does not add a fifth by inference?
2. **Should `INT-015`'s list be reconciled at the same time?** It is the seam registry entry two consumer
   modules build against, and it is already the outlier on the naming question (`OQ-060`).
3. **Is `fallback_eligible = true` right for all four?** It is what Phase 10 and Phase 12 both adopted, on
   the ground that the caller's prompt still needs an answer and nothing the caller did caused any of them.
   A reader could argue that `address_refused` should be `false` — the configuration is broken and serving
   a canned answer hides it — which is the argument `invalid_request` already won for a bad generation
   parameter (A-097).
4. **Should the count of `origin = prope` classes be an asserted invariant at all?**
   `tests/architecture/test_error_taxonomy_is_closed.py` asserts it and each phase has had to move the
   number. Phases 10, 12 and 12 again have each edited it. A number three phases have moved is either the
   wrong invariant or exactly the right one; both readings are defensible and the choice should be made
   once.

## What is affected either way

- `src/prope/provider_access/failures.py` (or `errors.py`) — `CLASSIFICATION` and `ErrorClass`
- `tests/architecture/test_error_taxonomy_is_closed.py` — the `origin = prope` membership assertion, moved
  from two to three to four across Phases 10 and 12
- `src/prope/provider_access/observability.py` — `error_total`'s `class` label's closed value set
- Phases 19-21 (gateway) — it branches on `fallback_eligible`; four Prope-origin classes are four new
  values its fallback path must handle
- Phases 16-18 (evaluation) — it branches on `retryable`; `address_refused` must not be retried and
  `dispatch_deadline_exceeded` should be
- `docs/adr/0017`, `docs/architecture/interfaces.md`, `docs/modules/provider-access.lock.yml` — **none
  edited by Phase 12**
