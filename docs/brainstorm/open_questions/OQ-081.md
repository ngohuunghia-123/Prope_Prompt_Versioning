# OQ-081 — `is_visible` needs `is_active_member` and no seam returns it

**Raised by Phase 15 planning, 2026-08-11.** `blocks_build: false` — plan 15-01 adopts the session as
the membership witness and says so at the call site. Raised because the adoption rests on an inference
rather than on a stated contract, and the inference is load-bearing for one third of the
private-by-default rule.

## The problem, stated once

The private-by-default rule has three terms (access-control D-134): **owner**, **grant**, and
**`access_level = 'workspace'` AND the actor is an active member**. The registry has to evaluate all
three inside one `WHERE` clause, because A-118 puts permission filtering in the repository layer.

- The first term is a column on the row: `prompt_property.owner_id`.
- The second arrives from `visible_subject_filter` as a set of ids (INT-002).
- **The third has no producer.** `access.workspace_member` is access-control's table and
  `prompt-registry.lock.yml`'s `data.reads` forbids joining to it — *"through its API, never by joining
  across module tables"* — and none of access-control's five declared internal functions returns
  membership. `is_visible` takes `is_active_member` as a **parameter**, which is correct for its own
  design (it reads nothing) and leaves the question of who supplies it unanswered for this caller.

INT-002's own worked example makes the gap concrete: the predicate it specifies for the registry is

> `WHERE workspace_id = :ws AND (owner_id = :actor OR id = ANY(:ids))`

— two disjuncts. Implemented literally, **a `workspace`-level prompt is invisible to every member of the
workspace except its owner and its grantees**, which deletes the entire point of having a second access
level. Phase 14's D-245 shipped exactly that literal form, noted that it fails closed, and routed the
widening to phase 15.

## The candidates

**A — the session is the membership witness** (adopted by plan 15-01). `authenticate_session(cookie)`
returns `{user_id, workspace_id}` and every management request is served inside
`workspace_transaction(sessionmaker, session.workspace_id)`. A session for workspace W is issued by
access-control to a member of W, so inside a request the actor is an active member of the request's
workspace **by construction**, and the third disjunct reduces to `access_level = 'workspace'` with no
extra read. Cost: it is an inference about how sessions are issued, not a contract — if a session ever
outlives membership (a person removed from a workspace while holding a live cookie), the disjunct is
wrong in the widening direction for as long as the session row survives. ADR-0022's *"revocation takes
effect on the next request"* is the rule that would have to cover it, and it is written about grants and
keys rather than about membership.

**B — a sixth access-control seam**, `is_active_member(actor, workspace_id) -> bool`, called once per
request beside `visible_subject_filter`. Honest, and one more round trip on every list request. Cost: a
new entry in `apis.exposes`, a new INT-NNN, and a second thing to keep in step with `may()` — which is
the shape A-118 already argued against for the per-row case.

**C — `visible_subject_filter` returns the membership fact** as a fourth field on `VisibleSubjects`
(`is_active_member: bool`). No extra round trip, and it puts the answer in the object whose entire job is
*"what may this actor see"*. Cost: it changes a value object three modules are written against, and it
mixes a fact about the **actor** into a set of **subjects**.

## What phase 15 shipped

**Option A**, with the inference written out at the predicate in
`src/prope/prompt_registry/repository.py` and named as an inference rather than as a contract, and with
this question cited by id there. Plan 15-01's test asserts the behaviour that follows from it — a
`workspace`-level prompt owned by A is visible to B in the same workspace and invisible to C in another
workspace — so if the inference is ever wrong, the assertion is where it surfaces.

**The membership-outlives-removal case is deliberately not asserted**, because nothing in phases 7-9 has
been read to establish whether removing a member deletes their sessions. That is the real question under
this one and it belongs to whoever answers this.

## What the answer changes

Option A: one sentence in `access-control.lock.yml` recording that a live session implies active
membership, and one in ADR-0022 or a successor saying what removal does to a session row. Option B: one
new function, one new INT row, one new call site per list route, and phase 8's cross-check test extended.
Option C: a field on `VisibleSubjects`, its `__post_init__` invariant, and every consumer re-read.
