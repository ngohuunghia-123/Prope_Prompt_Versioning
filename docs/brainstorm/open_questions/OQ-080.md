# OQ-080 — `mode: all` and private-by-default are two different answers to the same question, and the registry's list query has to pick one

**Raised by Phase 15 planning, 2026-08-11.** `blocks_build: false` — plan 15-01 adopts the fail-closed
reading and asserts it. Raised because the two authorities say different things about the same row, and
the difference is visible to a user on the first day the product has two people in one workspace.

## The problem, stated once

Two rules describe when a person may see a prompt, and they were written in different passes.

**INT-002 (`visible_subject_filter`)** returns one of three modes, and says of the first:

> `mode: all` means the actor may see every subject of that type in the workspace — it is not a bypass
> of tenancy, which RLS enforces underneath regardless (ADR-0045).

Phase 8's plan 08-02 makes the producer concrete: `mode: all` is returned when *"a role binding confers
the subject type's read action at workspace scope, so the caller adds no id predicate."*

**`is_visible` (access-control, D-134, phase 9)** writes the private-by-default rule down once:

> an actor sees a subject if they own it, or hold any grant on it, or the subject's `access_level` is
> `workspace` and they are an active member.

A role binding is not in that list.

**So take an ordinary workspace with two people.** B holds a role whose `role_permission` rows include
`prompt.read` — which every non-guest role must, or B cannot use the product at all. A registers a prompt
and leaves it at the default `access_level = private`. Ask the two rules:

- `visible_subject_filter(B, "prompt")` → `mode: all`. The registry's list query adds **no** id predicate,
  and A's private prompt is in B's result page.
- `is_visible(actor_id=B, owner_id=A, access_level="private", grant_level=None, is_active_member=True)`
  → `False`. The detail route refuses with `404`.

The same prompt is listed and then not-found. **The listing half is a breach of non-negotiable #4**
(`.claude/CLAUDE.md`: *prompts are private by default, enforced as not-found, never forbidden*) and of
`prompt-registry.lock.yml`'s AC-3 in its exact words: *"when B holds no grant and searches its exact
title, then it does not appear in the results."*

**This is not a bug in either function.** `may()` is *visibility AND permission* (phase 7's D-104), so it
already answers `False` here; the defect is only in what the **set** form means, and the set form is the
one thing that reaches a `WHERE` clause. A-118 predicted the general shape of this — *"the version that
ships under deadline pressure is the query with no filter at all"* — and `mode: all` is that query with a
name on it.

## The candidates

**A — `mode: all` widens PERMISSION, never VISIBILITY** (adopted by plan 15-01). The registry's read
predicate is always three disjuncts and `mode: all` changes none of them:

```sql
WHERE (owner_id = :actor
       OR id = ANY(:granted_ids)
       OR (access_level = 'workspace' AND :actor_is_active_member))
```

`mode: all` then means *"you may read any prompt you can see"*, which is what a role binding is actually
about, and `mode: ids` contributes its ids to the second disjunct. Fails closed. Cost: the mode's name is
now misleading at the one call site that consumes it, and INT-002's sentence has to be rewritten by
somebody who owns it.

**B — keep INT-002's reading and accept that a role binding overrides `private`.** Defensible as a
product decision — "your workspace's admins can see everything" is how many tools work — but it is a
decision that deletes the *default* half of private-by-default, and the survey's top adoption barrier is
the person whose prompt leaked finding out. It would also make `is_visible` and the list query disagree
permanently, so a prompt would be listable and not openable or the reverse, depending on which rule a
route happened to use.

**C — split the mode.** `all` keeps INT-002's meaning and a fourth value (`granted_and_own`, or a
`respects_access_level: bool` on `VisibleSubjects`) carries A's meaning. Cost: a fourth member in a closed
three-member vocabulary that access-control's own tests assert the closure of, and a second producer
decision in a module that may not read the subject it is describing.

## What phase 15 shipped

**Option A**, in `src/prope/prompt_registry/repository.py`, with the reasoning written at the predicate
and this question named there by id. It is the only option that satisfies AC-3 as written, and it is the
one whose failure direction is *too few rows* rather than *somebody else's prompt*.

Phase 14's plan 14-01 (D-245) had already shipped the **two**-disjunct form INT-002 specifies literally
— owner and granted ids, with no `access_level` clause — and routed the widening here. Plan 15-01 adds
the third disjunct and pins the `mode: all` composition; both halves are asserted in
`tests/security/test_private_by_default.py`.

## What the answer changes

Option A: one sentence in `interfaces.md` INT-002 and one in `access-control.lock.yml`'s `apis.exposes`,
and nothing in code — it is already what ships. Option B: plan 15-01's predicate loses its third disjunct
and its `mode: all` branch, `is_visible` gains a role-binding term, AC-3 has to be rewritten, and
non-negotiable #4 has to be renegotiated with the user before any of it. Option C: a fourth
`VisibilityMode` member, a migration to nothing, and a new cross-check in phase 8's
`tests/integration/test_visible_filter_matches_per_row_checks.py`.
