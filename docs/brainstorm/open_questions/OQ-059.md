# OQ-059 — `prope_report` no longer reads everything, and three metric labels are the closest thing in this module to unbounded

**Raised by Phase 10 planning, 2026-08-11.** `blocks_build: false`. Two clauses; the second is a
hand-off to phase 12 rather than a question phase 10 can answer, and is labelled as one.

## Clause 1 — the reporting role is refused on one table, for the first time in the project

Phase 10 passes `report_select=False` to `grant_table` for `provider.credential` — the first use of that
parameter, and the first table in Prope the reporting role cannot read.

**The ground** is ADR-0014's own threat model, quoted: *"a `SELECT` from an application bug, a backup
file copied to a laptop, a read replica with looser access."* ADR-0037 describes `prope_report` as a
full-read credential *"issued to a person rather than to a process"*, which is the third of those three
sentences with a login attached. Its own framing question is *"what could this credential do if it
leaked"*, and withholding this one grant changes the answer from "hand over the entire ciphertext corpus
for every workspace" to "not that".

**What it does not affect.** ADR-0036's nightly dump *"continues to run as the host `postgres`
superuser, because a `SELECT`-only role cannot dump schema"* (ADR-0037, Decision). A restored cluster
carries every credential. This is **not** an ADR-0039-style exclusion from the backup, and it must not be
read as one.

**It is defence in depth, not a requirement.** Phase 10's SC1 test proves the ciphertext is useless
without the KEK, so a `prope_report` SELECT is not itself a compromise. The claim is bounded at that and
should not be restated as more.

**The tension.** ADR-0037's Consequences say `prope_report` *"reads everything and changes nothing"*.
After phase 10 that is untrue by one table.

**Reversal cost:** one line — `report_select=True` — in a follow-up revision.

### The question

Should ADR-0037's Consequences bullet be amended to *"reads everything except `provider.credential`"*,
or should the grant be restored?

## Clause 2 — metric label cardinality, handed to phase 12

Three declared provider-access metrics carry the closest thing in this module to unbounded labels:

| Metric | Labels |
|---|---|
| `prope_provider_access_upstream_duration_seconds` | `provider_config_id`, `upstream_model` |
| `prope_provider_access_credential_rejected_total` | `provider_config_id` |
| `prope_provider_access_model_unavailable_total` | `provider_config_id`, `upstream_model` |

ADR-0030 bounds metric label cardinality, and `src/prope/observability.py`'s standing rule is that
`workspace_id` — *"the highest-cardinality identifier in the system and the one most tempting to add"* —
is deliberately never a label. **A `provider_config_id` resolves to exactly one workspace**, which is
the same exposure by a different name, and it matters the moment a `/metrics` route serves this
registry.

**Phase 10 ships the labels exactly as declared**, following the standing rule established when
call-ledger met the same question: *do not drop a declared label to avoid raising a question.*

**This is a hand-off, not a claim on an id.** Phase 12 owns `observability_requirements` per the
ROADMAP's spec routing and should raise this from its own OQ range if it agrees. It is recorded here so
the finding is not lost in the gap between two phases planned by different agents.
