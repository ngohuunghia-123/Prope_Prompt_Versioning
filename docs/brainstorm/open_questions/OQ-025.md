# OQ-025 — A stored body rests where no bound and no assertion in this repository reaches

**Raised by Phase 3 plan 03-01 while introducing the per-body byte cap, 2026-08-10.** The code ships
either way — `blocks_build: false` — and the residue is recorded here rather than absorbed into the
spec, per `.planning/BSP-LINK.md` and `.planning/ORCHESTRATION.md` §5.

**Clause 2 was appended by plan 03-05 while closing CL-10, 2026-08-11.** Both clauses are the same
question asked at two layers — *a stored body rests somewhere no bound and no assertion in this
repository reaches* — and one is on the broker while the other is on a database role. The title above
was widened in that change to say so.

## Clause 1 — the broker is a second body store, and nothing bounds its bytes

T-005's own text says the broker is a second resting place for raw end-user text, and its mitigation
is the queue argument set A-149 fixes: `x-message-ttl` 24 h, `x-max-length` 1,000,000,
`x-overflow: reject-publish-dlx`, and the DLQ's own 30 days / 100,000.

**Every one of those bounds a message COUNT or an AGE. None bounds bytes.** `x-max-length-bytes` was
never declared, and it **cannot be added now** without D-23's delete-and-redeclare in every environment
that has run: the arguments are one-way, and a redeclare whose arguments differ answers
`PRECONDITION_FAILED` (406).

So on paper the queue's byte ceiling is `x-max-length` × the size of one message, and the size of one
message was unbounded at every layer: `CallBodyDraft.byte_size` is caller-supplied and `int | None`,
the handoff bounds records rather than payload, and PostgreSQL's `text` columns bound nothing a caller
would notice.

### Clause 1 — what this phase built, and exactly what it does and does not bind

`MAX_BODY_BYTES = 256 * 1024` in `src/prope/call_ledger/enqueue.py`, enforced **inside `enqueue()`,
before the `put_nowait`**, over the request and response pair together, computed from bytes that module
encodes itself — and it **overwrites** the caller-supplied `byte_size`, because a cap enforced from a
figure the capped party supplies is not a cap. Over the cap the body is dropped and counted on
`body_dropped_total{reason="oversize"}` and **the record continues with `body=None`**: metadata is
never dropped for a body's sake (D-29).

The number is argued at the constant: ADR-0033 sizes the host against *"roughly 10 KB per call"*, so
256 KiB is twenty-six times the stated average and about 64k tokens of UTF-8 — above the context window
of the models a pilot will use, which makes a body above it an asset or a base64 blob rather than a
conversation. 24 hours of the ADR's stated 10k calls/day at the cap is at most 2.5 GB, inside an 80 GB
host that already carries `call_body` at roughly 3 GB/month.

**It bounds one message. It does not bound the queue.** That is the residue, and it is what this
question is about: **a queue of a million capped messages is still 256 GB on paper**, bounded in
practice only by the 24-hour TTL and by an arrival rate nobody has measured at real scale. A producer
cap is the only layer left that can be changed without a redeclare, and it is therefore the whole of
the byte bound this system has.

### Clause 1 — the shape of the possible answers

1. **Accept the producer cap as the bound**, and record in T-005 that the byte ceiling is a property of
   the producer and the TTL rather than of the queue. Costs nothing and is what ships today.
2. **Declare `x-max-length-bytes`** and pay D-23's delete-and-redeclare in every environment that has
   run, once, before there is production data to lose. Cheapest now and never cheaper.
3. **Stop putting bodies on the broker at all** — publish metadata and write bodies on the producer's
   side. A much larger change, and it reverses ADR-0041's shape rather than extending it.

### Clause 1 — why this does not block the build

`blocks_build: false`. The path has exactly one byte bound, it is enforced before the buffer, it is
computed from bytes this module encoded, and it is counted on the counter whose subject is the body.
What the answer settles is whether the queue itself is ever given a byte bound, and where T-005's
mitigation is recorded as actually living.

## Clause 2 — the reporting credential reads every stored body in every workspace

CL-10's no-read-path sweep is three layers deep — the assembled route table, the module's internal
Python surface, and the enumeration of every statement in `src/` that names `ledger.call_body`. **All
three are about this application.** The database has a fourth reader that none of them touches.

Three verified facts, each read off the tree on 2026-08-11:

1. `CREATE ROLE prope_report LOGIN BYPASSRLS` — `alembic/versions/0001_roles_and_schemas.py:47`. The
   tenant policy is created `FOR ALL TO prope_app` and the role attribute makes it inapplicable
   anyway, so `prope_report` is outside ADR-0035 twice over.
2. `grant_table(..., report_select: bool = True)` and `GRANT SELECT ON {schema}.{table} TO
   prope_report` — `alembic/ddl.py:103, 122-123`. The default is `True` for **every table in the
   system**.
3. `grant_table("ledger", "call_body", app_privileges=["SELECT", "INSERT", "DELETE"])` —
   `alembic/versions/0003_ledger_tables.py:252`, taking that default.

So `SELECT request_body, response_body FROM ledger.call_body` on the `prope_report` credential returns
**every stored body in every workspace**. One statement, no tenant context, no application code
involved. `tests/conftest.py:162-167` has built that engine as a session fixture since Phase 1.

### Clause 2 — both readings, because either is defensible and silence is not

**In scope.** The lock file's first `security_requirements` clause is *"Bodies have no read path in
the MVP — no endpoint, **no export**, no admin viewer, and no join from another module's query"*, and
T-005's own reasoning is that *"a body's lifecycle is a property of every place it can rest, not of
the table it is meant to live in"*. That is precisely the argument ADR-0039 used to exclude
`call_body` from the nightly dump. This is the same argument one layer down — a reporting credential
is how an export gets written.

**Out of scope.** AC-10's text is *"no route, parameter, or function that returns a request or
response body"*, and a database role is none of the three. ADR-0037 records `prope_report` as a
deliberate full-read reporting credential, and ADR-0036's restore rehearsal checks the role exists in
the target cluster.

### Clause 2 — what Phase 3 did, and what it deliberately did not do

**The grant is left in place and the exposure is asserted.**
`tests/security/test_report_role_can_read_bodies.py` seeds a body in each of two workspaces through
the real write path and reads both back on the `prope_report` credential with no `app.workspace_id`
set, with `prope_app` reading exactly one row as the negative control and the role attribute and the
grant asserted separately at `pg_roles` and `has_table_privilege`. Its docstring records that this is
a **recorded exception and not an oversight** and names this file as where the question lives.

Plan 03-05 adopted that option with status **UNCONFIRMED**, on three grounds: ROADMAP SC4 is about
routes, parameters and functions, so the phase closes what it was given and hands the excess upstream
(`.planning/ORCHESTRATION.md` §5); a `REVOKE` on one table fixes one table and leaves the default that
produced it in place; and leaving the grant costs one migration later, while revoking it now against
an unbuilt restore rehearsal and an ADR that records the opposite costs a claim every later module
inherits.

The third option — do nothing and mention it nowhere — was refused outright. A year from now, *"we
looked and decided not to"* and *"nobody looked"* must not be the same artifact.

### Clause 2 — the shape of the possible answers

1. **Leave it, as shipped.** `prope_report` stays a full-read credential and the exposure is a
   recorded exception with a test on it. Costs nothing; the exposure is real and dated from Phase 1.
2. **`REVOKE SELECT ON ledger.call_body FROM prope_report`** in a migration, with a live-engine
   refusal test and a positive control on another `ledger` table proving the credential still reads.
   Makes ADR-0037's *full-read* into *full-read except the one table declared to have no reader*,
   which has to be written into the ADR rather than left implicit.
3. **The class-level answer, which is the one that actually matters: should `grant_table`'s
   `report_select` default be `False` for a table declared to have no reader?** Option 2 fixes one
   table; this fixes the pattern, and it is the decision no phase should take on evidence it turned
   up while writing a test. Every future body-bearing column inherits whichever way this goes.

### Clause 2 — why this does not block the build

`blocks_build: false`. Nothing in the MVP reads the reporting credential: there is no report, no
export job, and no scheduler to run one. The credential exists in `.env` and in the test rig, which is
exactly the point — the exposure is a standing capability rather than an active path, and the answer
changes a grant rather than a design.

**OQ-013's answer changes how long this lasts.** `call_body`'s retention window is what bounds the
volume of bodies that exist to be read at any moment, and OQ-013 is what sets it. A shorter window
shrinks clause 2's exposure without answering it; a "never delete" answer — which ADR-0018 and A-040
already refuse — would make it permanent.
