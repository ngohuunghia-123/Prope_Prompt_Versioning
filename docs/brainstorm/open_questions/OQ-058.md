# OQ-058 — AC-13 requires a re-wrap command the specification gives no home to

**Raised by Phase 10 planning, 2026-08-11.** `blocks_build: false` — plan 10-05 adopts a home and
records it as UNCONFIRMED. Raised because AC-13 refers to *"the re-wrap command"* as though one had been
specified, and none has.

## Clause 1 — the command exists in one sentence and nowhere else

AC-13 is written as a **comment** inside the lock's `acceptance_criteria` block rather than as a
numbered criterion; `.planning/research/PITFALLS.md` gap 1 records it as owed, never written as a row,
and assigned to *"10 or 12"*. Its text refers to *"the re-wrap command"*, and:

- `apis.exposes` enumerates the management routes and none of them is a re-wrap;
- `scope.in_scope` names *"Encrypt every credential at rest"* and *"Rotate a credential in place"* — a
  KEK rotation is neither;
- `events.publishes` and `events.subscribes` are both empty;
- `deployment_target` names no scheduled job.

## Clause 2 — what phase 10 shipped, and the three rejections

A plain async function, `rewrap_all_credentials(...)` in `src/prope/provider_access/rewrap.py`, with no
route, no job and no CLI, invoked by the operator on the host that already holds `.env`. The operational
sequence, which exists nowhere else in the project:

1. Add `PROPE_KEK_V2` to `.env` alongside V1. **New credentials immediately wrap under V2**, because
   `wrapping_version` is `max(versions)` (A-135) — intended, and also how someone rotates by accident.
2. Run the re-wrap. Every row moves to V2.
3. Verify `SELECT DISTINCT kek_version FROM provider.credential` returns `{2}` **in every workspace**.
4. Remove `PROPE_KEK_V1` from `.env` and restart.

**Rejected: a management route.** It would be an additional route on a surface the lock enumerates
exactly, exposed over HTTP, whose effect is invisible to the caller and whose failure mode is partial. A
route for an operation only the `.env` holder can meaningfully perform has authorisation of the wrong
shape.

**Rejected: an Alembic data migration.** It would put a KEK in a migration's environment, and migrations
run in CI-adjacent contexts. ADR-0032's *"never enters CI"* is the whole of the KEK's protection.

**Rejected: a supervised job on an interval.** There is nothing to do on any interval; a KEK rotation is
a deliberate act, and a job would need a trigger, which is a route again.

## Clause 3 — AC-13 is assigned to phase 10

PITFALLS says *"10 or 12"*. Phase 10 takes it, because the entire operation is two columns, one crypto
function and one key ring — all created in phase 10 — and needs no route, no dispatch, no admission gate
and no SSRF guard, which is everything phase 12 is about. `kek_version` shipped in the schema *"from day
one"* on ADR-0014's explicit instruction, and a version column whose version can never change for two
phases is a column with no exerciser.

**Phase 12's verifier should not go looking for AC-13.**

## Clause 4 — an unfinished re-wrap is invisible, and that is the trade

`kek_version` is per row and A-135's *"the highest present wraps"* is per process, so a **mixed corpus
works indefinitely**. That is what makes the operation safely resumable — an interruption leaves some
workspaces at V2 and some at V1, and every credential in both still decrypts while both keys are
present — and it is also what makes an unfinished re-wrap unnoticeable.

The closing check is step 3 above, performed by hand. **Should that instead be a readiness condition or
an alert?** Both `/readyz` and `observability_requirements.metrics` are routed to **phase 12** by the
ROADMAP's spec lines, so if the answer is yes, phase 12 owns it.

## The questions

1. Is a plain function invoked with `uv run python -c` on the host the right home for the re-wrap, or
   should it be a route, a CLI, or a job?
2. Should AC-13 be promoted from a comment to a numbered acceptance criterion?
3. Should a corpus not fully at the highest KEK version be surfaced as a readiness or alerting concern
   in phase 12?
