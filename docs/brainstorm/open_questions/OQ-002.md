# OQ-002 — Does approval attach to the revision, the release, or both? Does restore bypass it?

## Resolution — 2026-08-09 (user)

**Option 1. A restore to a previously released revision is exempt.** The sweep's inflation check named
this question as one the pack could already answer, and the user confirmed it.

The reasoning is the one [[A-028]] already carried: the organisation approved the revision, and
approved releasing that same revision at least once. A restore makes no new judgment — it returns to a
state already accepted. So it proceeds on a one-line mandatory reason and appends a release event with
`kind = restore`, which is what meets H-05's five-minute target at 3am with the reviewer asleep.

**The exemption is narrow, and the narrowness is the decision.** A restore to an Approved revision that
has **never** been released is an ordinary release and does require the release decision. A release of
a revision that is not `Approved` is refused by a database constraint (BR-03), restore or not. What is
exempt is the *repetition* of a decision, never the decision itself.

**Consequences applied**: [[A-028]] flips from an agent default to a user decision. No lock file
changes — release-control already implements exactly this, and ADR-0009 already separates withdraw as
its own explicit decision.


## Resolution of the first half — 2026-08-08 (user)

> "Cả 2."

Option 3 selected. Approval attaches to **both**. A revision is approved once, which makes it
eligible; each release of an eligible revision is a second, separately recorded decision.

**Consequences applied**
- `00_context.md#constraints` — recorded as a non-negotiable row.
- Release is an entity with its own approval record, not a pointer write.
- Two decision objects exist: `revision_approval` and `release_approval`. Both are append-only.

## What is still open

Restore. With approval on both, a restore is a release, and a release needs a decision — which
collides directly with the ≤5-minute restore target in H-05, since a restore happens during an
incident when the reviewer may be asleep.

**The narrowed question:** does a restore to a revision that was already approved *and* already
released once require a fresh release approval, or is it exempt?

## Why the remainder still matters
`business-analysis.md` §4.2 marks restore approval as **[Giả định]** explicitly reserved for the
product owner, and §11 rates the emergency-restore rule as severity High. It is one rule, but it is
the rule that decides whether the incident path works at 3am.

## Options
1. **Exempt.** Restoring to a previously released revision needs no new approval; it is logged with
   a mandatory reason. Meets the 5-minute target.
2. **Not exempt, but break-glass covers it.** A restore without approval is a break-glass release
   (A-009) — flagged, reasoned, and reviewed within 24 hours.
3. **Never exempt.** A reviewer must approve every restore. Honest, and slow.

## Recommendation
A-028 records option 1 as the working default: the target revision was approved, and the same
revision was already released once under an approval, so no new judgment is being made — only a
reversal to a state the organisation already accepted.
