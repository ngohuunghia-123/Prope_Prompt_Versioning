# OQ-017 — When a person leaves, what happens to their personal data, and what happens to the audit trail that names them?

## Resolution — 2026-08-09 (user)

> "tombstone the user row, keep actor_id"

**Option 1, and the stronger half of it.** Written up as **ADR-0054**, with the parameters in
[[A-151]]. The audit trail is exempt; the account is not.

`access.user` keeps its row and loses its person: `email`, `display_name` and `password_hash` become
NULL, `status` becomes `tombstoned`, and two new columns record when and by whom. **The row is kept
rather than deleted, and that is the part of the answer doing the work** — a deleted row frees an id
that a later import or a restore could re-issue, which would make a historical `actor_id` *ambiguous*
rather than merely unresolvable, and ambiguity in an audit trail is worse than absence.

`history_event` is not touched. No row deleted, no `actor_id` nulled, blanked, re-pointed or
anonymised. A-121 stands unqualified, ADR-0025's privilege is not spent, and property-history's
security requirement — *"an event's actor is recorded as it was at the time"* — was written before this
question was asked and survives it word for word.

**Three things the answer settled that the question did not raise:**

1. **The tombstone carries no reason string.** `requires_reason` is how this pack normally makes a
   rare, consequential action accountable, and it would have been the exact mechanism by which the
   erased name walked back into the one table nothing can be removed from — *"John Smith left the
   company"* is a sentence no reviewer would flag. Accountability comes from `tombstoned_by`, an id.
   `user_tombstoned` is the 31st registered action and the only one that is both detail-key-empty and
   reason-free by design.
2. **The tombstone does not reach the backups.** ADR-0036 keeps nightly dumps for 30 days, so the name
   survives in every dump taken before the tombstone, and a restore from one brings it back into the
   running system with nothing watching for it. Erasure is complete only after the retention window
   passes, and the recovery runbook now re-applies every tombstone recorded after the dump's timestamp
   — read from the `user_tombstoned` events, which survive in the restored history precisely because
   history is never deleted. This is [[A-133]] in a second place: **a restore is not the running
   system.**
3. **Consumer API keys are untouched, and memberships are retained.** A key belongs to the workspace
   rather than to whoever created it ([[A-113]]), so folding revocation into the tombstone would break
   a consuming product's traffic on an HR event. `workspace_member` rows stay, with `status = removed`,
   because they are how the operation knows which workspaces to write its event into.

**Consequences applied**: ADR-0054 and [[A-151]] written · `access.user` gains `tombstoned_at` and
`tombstoned_by` · `POST /api/v1/users/{user_id}/tombstone` added (INT-029, 14 routes -> 15) ·
`user_tombstoned` added to the vocabulary (30 -> 31, propagated to ADR-0024, ADR-0038, ADR-0053,
A-120, A-124, tech_stack.md and interfaces.md) · access-control gains AC-13/14/15 and a security
requirement · **both access-control and property-history flip to `ready_for_build: true`**.


**Raised by the step-6 sweep, pass 2 (ownership / PII classification), 2026-08-09.** This is the one

## What the build currently does, stated plainly

Two tables hold personal data, and they have opposite lifecycles:

| | |
|---|---|
| `access.user` | `email`, `display_name` — directly identifying. Deletable in principle: it is an ordinary table with an ordinary role holding `DELETE`. |
| `history.history_event` | `actor_id` on every one of the ~30 action types, forever. **Not deletable by the application at all.** ADR-0025 grants `prope_app` `INSERT` and `SELECT` and withholds `UPDATE` and `DELETE` *at the database privilege level*; `prope_migrate` is the only role that can remove a row, and it is a deployment credential that never enters the running process. |

A-121 states the rule without qualification: *"History rows are never deleted, including on prompt
retirement, member removal, key revocation, or provider disablement."* And property-history's own
security requirements already anticipated this question without asking it:

> *"An event's actor is recorded as it was at the time. A person removed from the workspace still
> appears in every event they caused; nothing is anonymised, redacted, or reassigned after the fact."*
>
> *"If a deletion obligation is later established, it lands in OQ-006's data-classification half and is
> new work, not a setting nobody enabled."*

That is the pack pointing at a question it never actually put to you. This file puts it.

## Why it is a real question and not a formality

The append-only guarantee is **the product's central claim against a spreadsheet** — that the record
cannot be quietly rewritten. It is deliberately enforced by the engine rather than by application code,
for the same reason BR-03 is a database constraint. Any erasure mechanism weakens exactly the thing the
product sells.

The tension is genuine on both sides, which is why the answer is yours:

- **Erasure obligations exist** for employee personal data in most jurisdictions, and Prope will hold a
  subsidiary's staff records the moment it holds a subsidiary's prompts.
- **Audit trails are the standard exemption.** Retaining a record of who approved a production change
  is ordinarily defensible as legitimate interest or as necessary for establishing and defending legal
  claims — and an approval trail with people removed from it is not an approval trail.

Prope has taken no position, and the absence is not visible anywhere except here.

## The shape of the possible answers

1. **The audit trail is exempt; `access.user` is not.** Delete or tombstone the `user` row on
   departure; `history_event.actor_id` survives as an opaque identifier that no longer resolves to a
   name. Cheapest, and it is what the schema already does by accident — `actor_id` is a **value, not a
   foreign key** (A-122), so removing the user row does not cascade and does not break a single query.
   The residual question is whether an unresolvable id counts as erased, which depends on whether
   anything else can re-link it.
2. **Pseudonymise at the boundary.** Keep the `user` row but blank `email` and `display_name`,
   retaining the id and the role history. Reversible by nothing inside Prope.
3. **Erase from the history too.** Requires a documented `prope_migrate` procedure — deliberate,
   visible, outside the application, which is exactly the shape ADR-0027 designed for a *"genuine
   correction"*. It spends the append-only guarantee on every use, so it needs a written trigger.
4. **No erasure path; record the position.** Defensible for an internal pilot under A-020, and it
   must then be a *stated* position rather than an unexamined default.

**A recommendation, offered because the pack owes you one:** option 1, with the tombstone written as a
history event of its own. It costs nothing structurally, it keeps the trail intact, and it is the only
option whose implementation is already true of the schema.

## Why this does not block the build

It is scored the way OQ-006 and OQ-013 are already scored throughout the eight locks —
`blocks_build: false`, `blocks_pilot: true` — and for the same reason: **the answer changes no schema
and no seam.** Option 1 is a delete the schema already supports, option 2 is an `UPDATE`, option 3 is a
runbook, option 4 is a sentence. None of them changes a table, an interface, or a module boundary, so an
implementing agent is not blocked on it.

What it does block is holding real personal data, which is precisely the line **A-020** already draws:
*no real corporate prompts until the security baseline is signed off.* This question is now part of that
baseline.
