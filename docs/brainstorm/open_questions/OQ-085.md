# OQ-085 — Is the 500 records/sec drain figure right, or is the architecture?

**Raised by plan 03-07, 2026-08-11.** `blocks_build: false` — the code ships, the assertion stays red,
and the number was not lowered. Raised because two measurements of the same requirement now disagree
with each other, and the requirement does not say which one it means.

## What the requirement says

`performance_requirements`, verbatim:

> **metric:** writer drain throughput
> **target:** `>= 500 records/sec sustained`
> **condition:** batched inserts, bodies included, single writer
> **source:** Ten times the gateway's 50 rps load-test figure. The margin is the point — a writer that
> merely keeps up has no capacity to clear a backlog after a stall, so every stall becomes permanent
> pressure.

## What has been measured, three times, on one developer host

Plan 03-06 found the figure unmet and localised the cause: `write_records` issued one `resolve_price`
round trip per record, which was roughly 70% of the cost of a priced 500-record window. Plan 03-07
removed that N+1 — one statement per batch, keyed on the distinct
`(provider_config_id, upstream_model)` pairs, resolved per record in Python against each record's own
`created_at` (ADR-0019 preserved exactly).

| Measurement | Before 03-07 | After 03-07 | Against |
|---|---|---|---|
| `write_records(500 priced, bodies attached)`, pooled sessionmaker — **the lock file's own stated condition** | **469** records/sec (03-06 measured 494) | **1,984–2,004** records/sec | 500 |
| End-to-end recovery from the 60 s stall in the paced ten-minute run | **189 / 212** records/sec | **450** records/sec | 500 |
| Recovery wall time for the same ~3,360-row backlog | 16.53 s / 17.79 s | **7.48 s** | — |

**The two rows disagree about whether the requirement is met, and the disagreement is the question.**
Measured under the condition the lock file actually states — *batched inserts, bodies included, single
writer* — the writer now exceeds the target by **four times**. Measured end to end across the load
run's recovery leg, it reads **450**, and the assertion is red.

## Why the end-to-end figure is lower, stated as facts rather than as an excuse

None of these makes 450 into 500. They are what a human needs in order to decide which number the
requirement is about.

1. **The recovery leg is not only the writer.** It contains the broker delivery, the drain's
   `WINDOW_MS = 250` collection floor per window (~7 windows for a 3,360-record backlog, so ~1.75 s of
   the 7.48 s is collection the writer is not doing), the second drain's consumer setup, and the
   producer continuing to arrive at 50 rps throughout.
2. **The run drives the publisher and the drain on ONE event loop.** The deployment shape (ADR-0033,
   D-17) is two processes on one host. The run is built that way on purpose — it is what makes AC-12's
   write-lag clause readable at all, because `prometheus_client`'s registry is per process (OQ-026) —
   so the end-to-end figure necessarily understates what the drain achieves with a loop to itself.
3. **The measurement's own polling shares that loop.** `_wait_for_rows` issues a `count(*)` against
   `ledger.call_record` every 100 ms through the `NullPool` `migrate_engine`, so a 7.48 s recovery
   contains roughly 75 fresh connections and 75 sequential scans of a table holding up to 35,000 rows,
   on the same loop as the drain. At 189 records/sec that overhead was noise; at 450 it is not.
4. **Docker Desktop on Windows, not a Linux VM.** ADR-0033's deployment shape puts `app`, `worker` and
   `postgres` on one docker network on one Linux VM, where a round trip is roughly an order of
   magnitude cheaper. **That is an inference and this file does not record it as a measurement.**

## What was tried

- **The N+1 was removed** — the fix plan 03-06 named. Confirmed by counting statements rather than
  timing them: a batch of N records over M distinct keys issues exactly **one** statement against
  `ledger.price_table` for N=200/M=1, N=200/M=4 and N=20/M=4, with the counting instrument calibrated
  in its own test against the old shape (`tests/integration/test_price_resolution_is_batched.py`).
- **The obvious cheaper move was refused**: memoising on the resolved `created_at` instant. Every one
  of the load run's 30,000 drafts shares the fixture calendar's day 5, so it would have reported a
  perfect number in this very test and bought nothing in production.
- **The number was not lowered, the assertion was not weakened, marked, or moved**, and no threshold
  in `tests/load/test_fifty_rps_for_ten_minutes.py` changed. The only edits to that file are two
  comments describing behaviour this change made stale.

## What is being asked

1. **Which measurement is `performance_requirements` about?** Its `condition` — *batched inserts,
   bodies included, single writer* — describes `write_records`, which now measures 1,984–2,004
   records/sec. Its `source` — *the margin is the point, a writer that merely keeps up has no capacity
   to clear a backlog after a stall* — describes the recovery leg, which measures 450. If the answer is
   the first, the requirement is met and `test_plan.load`'s restatement needs an isolated benchmark
   beside the paced run rather than a figure derived from it.
2. **If it is the end-to-end figure, is 500 the right number for a single-host developer machine
   running both processes on one event loop?** Or does the requirement belong to the deployment stack,
   re-measured on the real VM — which PITFALLS §4 notes owns no milestone, so there is currently
   nowhere for that answer to be implemented?
3. **Should the load test stop charging its own instrumentation to the drain?** Reading the backlog
   through a pooled engine, or on a longer poll, or deriving the figure from
   `prope_call_ledger_written_total` instead of a `count(*)`, would each move the number without
   touching the writer. **None of them was done here**, because changing the instrument in the same
   change as the thing it measures is how a measurement stops being one.
4. **Who owns re-measuring it?** M1 closes at phase 3 and no later phase owns `writer.py`. Plan 03-06
   already routed this to *"whoever eventually owns the deployment stack"*; that owner does not exist
   yet.
