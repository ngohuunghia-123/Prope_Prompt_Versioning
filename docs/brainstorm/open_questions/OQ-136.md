# OQ-136 — `api_key.last_used_at` stays NULL between phase 8 and phase 19

**Raised by the access-control build, 2026-08-11.** `blocks_build: false` — the column, the
statement and the batched function all ship; nothing calls the function yet.

## The gap

INT-003 says the `last_used_at` update *"is not part of the contract and must never be on the
request's critical path"*. The only way to honour that literally is for `authenticate_api_key` not to
issue it — so `bootstrap.record_key_use` exists as a separate, batched, best-effort call and the
authentication path does not make it.

Its caller is the gateway, in **phase 19**: that module already owns a post-response hook which never
raises (`enqueue()`, A-037/A-087), and wiring it there rather than inventing a second background job
here is what keeps access-control's `deployment_target` line true — *"no process of its own and
nothing in `worker`"*.

Until then the column is NULL for every key, and `GET /api/v1/workspaces/{id}/keys` returns it as
`null`. ADR-0021 already calls the column *"the only signal available for spotting a key that is being
used from somewhere it should not be"* and calls it weak; between phase 8 and phase 19 it is absent.

## What is being asked

Confirm that phase 19 owns the wiring, or name an earlier caller. If the pilot starts before phase 19,
the key list should render the absence as *"not recorded yet"* rather than as *"never used"* — those
are different facts and the SPA cannot tell them apart from a NULL.

Reversal cost: none. Wiring it later costs one call site.

## What is affected either way

- `src/prope/access_control/bootstrap.py` — `record_key_use`, `TOUCH_API_KEY`
- `src/prope/access_control/schemas.py` — `KeyRead.last_used_at`
