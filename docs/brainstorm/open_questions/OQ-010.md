# OQ-010 — What language is the product interface in?

## Resolution — 2026-08-09 (user)

**Multiple languages through i18n; only Vietnamese implemented for the MVP.** Written up as
**ADR-0053**.

This is option 1's shipped surface with option 3's structure underneath. One catalogue ships, `vi`,
and it is the default and only locale — no switcher, no `Accept-Language` negotiation, no per-user
setting. What is built now is the layer: every user-facing string comes from a keyed catalogue, no
literal display text in any component, keys are English identifiers rather than fallbacks, and CI fails
on a key used in code and missing from `vi`.

**The five statuses stay literal** — `Draft`, `In review`, `Approved`, `In use`, `Retired` — in storage
and in the API, translated only at the point of display, which preserves `prope_source_of_truth.md` §18
rule 9. **The API stays English**: ADR-0003's envelope already carries a stable machine `code` beside a
human `message`, and the client renders the code. **Human-authored content is never translated** —
approval comments, release reasons, prompt bodies and fallback answers render exactly as written
([[A-046]]), because a translation layer over an audit record falsifies it.

**One consequence the answer created and the question did not anticipate**: ADR-0048 chose a trigram
index over a trigger-maintained search column before anything established what language the indexed
text would be in. A Vietnamese product means Vietnamese diacritics, and `tieu de` does not trigram-match
`tiêu đề`. [[A-150]] folds diacritics inside the existing trigger — not in the index expression, because
`unaccent()` is STABLE and cannot honestly go there.

**Consequences applied**: [[A-018]] flips from an agent default to a user decision and gains the i18n
half; ADR-0053 written; [[A-150]] written; ADR-0052's frontend row cites both.


## Question
Is the user-facing UI in Vietnamese, in English, or bilingual? And do the system status labels
(Draft, In review, Approved, In use, Retired) stay in English even in a Vietnamese UI?

## Why it matters
It is user-visible naming, so it is yours. It also interacts with a fixed constraint: the language
system in `prope_source_of_truth.md` §8 and §18 is specified in English terms and requires statuses
to stay literal. Translating them would break rule 9; leaving them in English inside a Vietnamese UI
is a deliberate choice someone has to make and defend on stage.

## What we know already
- `BRIEF.md`, `positioning.md`, and `business-analysis.md` are in Vietnamese; the source of truth is
  in English.

## Options
1. Vietnamese UI, English status labels and API vocabulary.
2. Fully English UI.
3. Bilingual toggle.

## Recommendation
A-018 records option 1 as the working default: it matches the audience and preserves rule 9.
