# OQ-061 — Two closed vocabularies owned by other modules do not cover provider-access's declared surface

**Raised by Phase 11 planning, 2026-08-11.** `blocks_build: false` — Phase 11 adopts a mapping for each
instance and writes the reasoning at the route (plan 11-05, D-193 and D-195). Raised as one question
rather than two because it is one shape: **this module's declared operations exceed a closed vocabulary
that a different module owns, and ORCHESTRATION §5 forbids provider-access extending either.**

## Instance one — there is no `provider.read`, and six of ten operations have to borrow

INT-027 declares ten operations across six paths. The permission vocabulary declares four actions:
`provider.configure`, `provider.rotate_credential`, `provider.disable`, `catalogue.read` — stated
identically in the lock file's `apis.consumes`, in `interfaces.md`'s per-module table, and in
access-control's 25-row `role_permission` seed.

Two of the ten are obvious (`POST /credential` → `provider.rotate_credential`; `GET .../models` →
`catalogue.read`). **The remaining eight have no name of their own**, and three of those are pure reads:

| Operation | Has no action of its own |
|---|---|
| `GET /providers` | reading the configuration list |
| `GET /providers/{id}` | reading one configuration |
| `PATCH /providers/{id}` | editing display name / base URL |
| `DELETE /providers/{id}` | deleting the configuration |
| `POST /providers/{id}/verify` | re-running the probe |
| `POST .../models/refresh` | re-discovering the catalogue |
| `POST .../models` | adding a model manually |

The tempting answer for the three reads is `catalogue.read`, because it is the only non-credential-bearing
action in the set. **It is wrong**, and the reason is in access-control's own seed: `catalogue.read` is
held by **Owner, Reviewer and Viewer** as well as Admin. A configuration read returns `base_url`,
`status`, `verification_status` and **the credential's last four characters**, and INT-027 names its
consumer as *"the web SPA — Workspace Admin"*. Mapping the reads to `catalogue.read` widens a
credential-adjacent surface to three more roles to avoid raising this question.

**Phase 11 adopts `provider.configure` for all eight**, including the three reads and the delete, with
`provider.disable` checked **additionally** on the `PATCH` branch that sets `status = disabled`. The
consequence is that reading a provider configuration requires the permission to create one — coarser
than A-007's *"credential-bearing actions are their own permission"* intent, in the safe direction.

## Instance two — deleting a configuration has no history action, and A-014 says every state change has one

ADR-0024's registry is a **closed** vocabulary (30 names in its own Context table, 31 as actually
derived — see `OQ` history around the vocabulary count) and provider-access's four are:

```
provider_configured, provider_updated, provider_disabled, credential_rotated
```

There is **no deletion action**, while A-014 says *"every state change writes an append-only
property-history event"* and `apis.exposes` declares `DELETE /api/v1/providers/{id}` as a real
operation. The same gap covers the catalogue: a refresh and a manual model addition are both writes with
no registered action.

**Phase 11 adopts: the delete appends nothing**, and says so at the route. The alternative considered and
rejected was appending `provider_disabled` for a deletion — the nearest registered action — which would
put a **false statement in an append-only audit log that cannot be corrected**, at the database
privilege level. What survives a deletion is the configuration's earlier events, which are never deleted
and whose `target_id` is a value rather than a foreign key (ADR-0054), so the story is complete except
for its last chapter.

## What is being asked

1. **Should `provider.read` be added to the action vocabulary?** It is one row in access-control's seed
   and one member in the shared `ManagementAction` enum. If yes, the three read operations move to it and
   the question is which roles hold it — which is really the question of whether `last_four` on a
   dashboard is Admin-only information.
2. **Is `provider.configure` on `DELETE` right**, or should deleting a configuration have its own action?
   Phase 11's argument is that deleting is stronger than disabling, so mapping it to the softer
   permission would let someone who may only disable also delete.
3. **Should `provider_deleted` join the history vocabulary?** It is one seed row in property-history's
   registry, owned by Phase 4/5. Until it exists, a configuration's deletion is the one state change in
   this module that leaves no record.
4. **Do the catalogue writes need events at all?** A refresh is discovered data rather than a decision,
   which is a defensible reason for silence — but a manual model addition is a person's act and is
   currently unrecorded.
