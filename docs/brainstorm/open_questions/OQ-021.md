# OQ-021 — Which module owns the shared session dependency's file?

**Raised by Phase 2 plan 02-05 while building the interim `require_session`, 2026-08-10.** The code
ships either way — `blocks_build: false` — and the deviation is recorded here rather than absorbed
into the spec, per `.planning/BSP-LINK.md`.

Fourth of this phase's declared deviations, and its own file for the same reason the other three have
theirs: it blocks a different upstream field from OQ-018 (`call-ledger.lock.yml` `data.owns`),
OQ-019 (`call-ledger.lock.yml` `apis.exposes`) and OQ-020 (`interfaces.md` INT-021's signature). A
resolver can accept any one without accepting the others.

## The question, stated exactly

`docs/architecture/interfaces.md` INT-005 registers `authenticate_session(cookie)` with:

> **Provider**: access-control
> **Consumers**: the shared session dependency in `app`, used by every management route in
> prompt-registry, evaluation, release-control, provider-access, call-ledger and access-control
> itself

and its own consumer note says this is *"the one seam whose consumer is a shared dependency rather
than a module"*.

So the dependency is **shared infrastructure with six consumers**, and:

- No module's lock file lists `src/prope/session_auth.py` — or any equivalent — as an artifact it
  owns. access-control's does not, and it is the module that would be the obvious candidate.
- `.planning/BSP-LINK.md` forbids editing a spec into agreement with the build, and the upstream
  planning root is read-only.

**The question is therefore: which module owns the file, and does access-control's artifact list need
to name it?**

## What this phase implemented, and why there

`src/prope/session_auth.py` — outside every module's package, a sibling of `prope/db/` and
`prope/broker/`.

That is the only placement consistent with six modules importing it while none of them imports
another module's internals. Placing it in `src/prope/access_control/` would mean call-ledger,
prompt-registry, evaluation, release-control and provider-access all import from access-control's
package — which is a real import edge in five directions, and the module graph's whole shape is that
**access-control depends on nothing but property-history**. Placing a copy in each module would be
six copies of an authentication boundary.

The file carries three things, and they travel together because all three are the same kind of
shared declaration:

| Symbol | What it is |
|---|---|
| `require_session` | the boundary — refuses with `401` / `session_required` until Phase 7 |
| `ManagementAction` / `MANAGEMENT_ACTIONS` | the closed action vocabulary AC-10 asserts against |
| `declares_action`, `declared_action`, `declares_session` | how a route declares, and how the route-table test reads what was declared |

`ManagementRefusal` — the exception every management route raises and `prope.app` renders as the
A-045 envelope — lives here too, for the same reason: it is shared by every module's routes and
belongs to none of them.

## The signature Phase 7 must preserve if the answer is unchanged

```python
async def require_session(
    session_cookie: Annotated[str | None, Cookie(alias=SESSION_COOKIE)] = None,
) -> Session:  # Session is frozen: (user_id: str, workspace_id: str)
```

The cookie parameter is declared **now**, unused, precisely so that Phase 7 replaces a function body
and touches no call site. `Session`'s two fields are INT-005's registered return (`{user_id,
workspace_id}`) and nothing else — no role, no permission set, no access level, because ADR-0020's
rule is that callers supply the subject and a field carrying authority is a field call-ledger could
be tempted to decide with.

## What a different answer costs

**An import-path rewrite at five declaration sites and one architecture test, and no behaviour.**

- `src/prope/call_ledger/api.py` — five routes, each declaring `require_session` and one
  `ManagementAction`.
- `tests/architecture/test_route_table.py` — the assembled-route-table assertions.
- `src/prope/call_ledger/schemas.py` — one import, for the `session_required` literal
  `ErrorCode.SESSION_REQUIRED` takes its value from.
- `src/prope/app.py` — one import, for the exception handler.

No signature changes, no behaviour changes, no migration. This is the cheapest of the four deviations
this phase raises to reverse, and it is raised anyway because placement of a shared authentication
boundary is not a thing a phase should settle silently.

## The shape of the possible answers

1. **Name `src/prope/session_auth.py` in access-control's lock file as an artifact it owns, sited
   outside its package.** Matches the build, matches INT-005's "shared dependency, not a module"
   note, and records an owner for a file that currently has none. Changes no code.
2. **Give the file to access-control's package** (`src/prope/access_control/session_auth.py`).
   Requires accepting five inbound import edges into access-control from modules the graph says
   depend on it only through INT-001 to INT-005 — which are in-process *calls*, not package imports
   of its internals.
3. **Register a new "platform" or "shared" pseudo-module** to own `session_auth.py`, `supervisor.py`,
   `app.py`, `worker.py`, `observability.py`, `db/` and `broker/` — the files that already exist
   outside every module's package. Larger than this question, and it would change the module map's
   "eight modules, eight bounded contexts" count, which is a decision well above this phase.
4. **Leave it unowned.** Honest about today's state and costs nothing until somebody asks which
   module's tests cover the authentication boundary.

**A recommendation:** option 1, with option 3 noted as the question it is really a small piece of.
Six files now live outside every module's package and none of them is named by a lock file; this is
the first one where the absence has a security surface attached.

## Why this does not block the build

`blocks_build: false`. The dependency exists, is declared at all five routes, refuses, and is
asserted over the assembled route table. What the answer settles is which file Phase 7 opens and
whose lock file records that a shared authentication boundary exists.
