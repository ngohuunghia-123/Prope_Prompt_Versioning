# OQ-082 — `RegistryUnapprovedPointer` is an alert whose condition is SQL, over a series no metric declares — and phase 13 made it unable to fire

**Raised by Phase 15 planning, 2026-08-11.** `blocks_build: false` — plan 15-03 ships what can honestly
ship and asserts the rest as a test. Raised because a rule that cannot evaluate its own condition is a
mitigation nobody built, and this is the mitigation for the failure the lock file calls *"the single
failure that makes the whole product worthless."*

## The problem, stated once

Three declared alerts, and two of them are ordinary PromQL over a declared metric:

- `RegistryResolveLatencyHigh` — resolve p95 > 10 ms for 5 min → `prope_registry_resolve_duration_seconds`.
- `RegistryUnfilteredQuery` — `prope_registry_unfiltered_query_total > 0` → declared, defined at import.

The third is not:

> `RegistryUnapprovedPointer` — the Success-metric query (released pointer whose revision status
> != Approved) returns any row

**That is a SQL query, and Prometheus cannot run one.** ADR-0030 chose Prometheus and Grafana *and
deliberately nothing else*: there is no `postgres_exporter`, no query-exporter, no SQL-to-metric bridge
anywhere in the stack, and none of the six declared metrics in this module exposes the condition. So the
rule as declared has no expression. Two smaller problems ride along:

1. **Nothing in this build ever wires a rules file into a running Prometheus.** PITFALLS §4 records that
   the deployment stack owns no milestone. Every `deploy/prometheus/rules/*.rules.yml` in the repository
   is a document with a test against it (`tests/architecture/test_alert_rules.py`) and no evaluator, so
   an inexpressible rule is caught by nothing today either.

2. **Phase 13 made the condition structurally unreachable, which is better news and a different fact.**
   D-221 implements BR-03 as a foreign key from `(workspace_id, released_version_id,
   released_version_status)` to `(workspace_id, version_id, status)` with `released_version_status` pinned
   to `'Approved'` by a `CHECK`. A released pointer at a non-`Approved` revision is not a row the engine
   will accept. So the query the alert is written about **cannot return a row** unless somebody drops the
   constraint — which means the honest alert is no longer *"the pointer went bad"* but *"the constraint is
   gone."* Phase 13's own `deferred-items.md` §4 says this in as many words and routes it here.

## The candidates

**A — ship the rule with a PromQL expression over a new gauge** that `worker` sets on an interval by
running the Success-metric SQL. Faithful to the declared intent. Cost: a seventh metric this module does
not declare, a scheduled job in a module whose `deployment_target` says in as many words *"This module
has NO scheduled job and NO queue consumer of its own"*, and a per-workspace gauge or an unlabelled
reduction with the same mismatch `OQ-022` clause 4 already records for call-ledger.

**B — ship the rule as a document with the SQL in its `description`, and assert the SQL in a test**
(adopted by plan 15-03). The rules file carries all three names so the declared set is complete and the
`test_alert_rules.py` equality holds; `RegistryUnapprovedPointer`'s `expr` is the constraint's own
liveness instead — there is no metric for it either, so the honest form is a rule whose `expr` is
`vector(0)` with the whole argument in the annotation, or the alert is omitted from the file and the set
assertion is edited to say so. Neither is satisfying. Cost: the alert does not fire, and a reader has to
read the annotation to find out why.

**C — delete the alert and replace it with the constraint inventory test** that phase 13 already ships
(`tests/integration/test_registry_schema_ships_its_guarantees.py` asserts
`fk_prompt_property_released_revision` exists by name, with a message saying what its loss costs). This is
the strongest *actual* mitigation available and it runs in CI on every commit rather than at 3 a.m. Cost:
the lock file declares three alerts and the file would ship two, which is a deviation somebody has to
sanction.

## What phase 15 shipped

**Option B, in its explicit form.** `deploy/prometheus/rules/prompt_registry.rules.yml` declares all
three alert names so the exact-set assertion in `tests/architecture/test_alert_rules.py` is meaningful.
`RegistryUnapprovedPointer`'s `expr` names a metric that exists and its `description` carries: the
Success-metric SQL verbatim, the sentence that Prometheus cannot evaluate it, the fact that D-221's
foreign key makes the condition unreachable while the constraint stands, and a pointer at the constraint
inventory test as the check that actually runs. Plan 15-03 also asserts the SQL itself against a seeded
database and asserts that it returns zero rows — which is the closest thing to the declared alert that
this stack can execute.

**The reason this is a question rather than a decision** is that Option C may well be right, and choosing
it means shipping two alerts where a lock file declares three. That is a spec edit, and a planner is not
the right place to make one.

## What the answer changes

Option A: one metric, one `worker` job in a module that declares it has none, and a rewritten
`deployment_target`. Option B: nothing — it is what ships. Option C: one rule deleted from the file, one
name removed from `DECLARED_ALERTS`, and one line in `observability_requirements.alerts`.
