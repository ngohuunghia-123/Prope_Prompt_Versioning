# OQ-075 — `resolve()`'s registered contract is under-specified in two ways, and both fail silently

**Raised by Phase 14 planning, 2026-08-11.** `blocks_build: false` — plan 14-05 adopts an answer for both
halves and records each as UNCONFIRMED. Both are cases where the specification as written produces a
**wrong answer with no error**, which is why they are raised together rather than absorbed.

## 1. `resolve()` has no workspace, and a workspace-less read returns zero rows rather than failing

INT-009's *Request carries* line names *"the bare model name, and an optional pin"* and no workspace.
INT-010, registered on the line below it, is `list_released(workspace_id)`.

Under ADR-0035 and ADR-0045 a `prope_app` query issued with **no `app.workspace_id` set returns zero
rows** — not an error, an empty result. That inversion is deliberate and is the project's central tenancy
guarantee. Applied to a workspace-less `resolve()`, it means:

- every model name in the product resolves to **zero rows**;
- zero rows is, correctly, *"model name unknown"*;
- so `resolve()` would answer `unknown_model` for everything, at p95 comfortably under 10 ms, and
  **nothing anywhere would fail.**

The gateway already holds the workspace. INT-003 (`authenticate_api_key`) returns
`{workspace_id, key_id, scope}` before this seam is reached, and INT-004 scopes the key against the model
name. There is no state in which the caller does not know it.

**Plan 14-05 ships** `resolve(sessionmaker, *, workspace_id, model_name, pin=None)`.

This is the same shape phase 2 recorded as **`OQ-020`** — `get_run_totals` shipping as
`(workspace_id, run_id)` where INT-021 registers `run_id` alone — and it gets the same treatment: ship
the honest signature, raise the question, edit no spec.

## 2. A pin's miss is neither of the two declared miss reasons, and the stated justification for the pin rule does not hold

INT-009 requires the miss to distinguish exactly two cases, and
`observability_requirements.metrics` declares exactly two label values:

> `reason = unknown_model | no_release`. The two must be separable or a withdrawal is invisible in the
> one metric that shows its blast radius (ADR-0009).

**A pin produces a third case.** `resolve("support/refund-classifier", pin="@2")` where revision 2 is
`Draft`, or does not exist, or belongs to another prompt: the model name is **known**, something may well
be **released**, and the pinned revision cannot be served. Labelling that as either declared value
corrupts the exact signal ADR-0009 built the label for — `no_release` would show a withdrawal that did
not happen, `unknown_model` would show a typo that did not happen.

**Plan 14-05 ships a third value, `pin_unresolvable`**, leaving both declared values with exactly their
declared meanings so every alert and every phase-19 assertion written against them is unaffected.

**Separately, INT-009's stated reason for the pin rule is false for the pin path.** It says:

> A pin whose revision is not `Approved` is refused — BR-03 is enforced by a **database constraint**, not
> by application code, and this seam reads a pointer the constraint has already guaranteed.

The constraint guarantees the **released pointer**. A pin names an arbitrary revision of that prompt and
no constraint has said anything about it. So the refusal has to be a predicate in the pin statement —
`AND r.status = 'Approved'` — which is an application-side **read filter**, not an application-side
enforcement of BR-03. Non-negotiable #2 covers *"released **or resolved**"*, so the filter is required;
only the sentence explaining it is wrong.

## What the answer changes

- **If the workspace parameter is accepted**, INT-009's *Request carries* line gains it and the lock's
  `apis.exposes` string becomes `resolve(workspace_id, model_name, pin)`. Nothing in the code moves.
- **If it is not**, some other mechanism has to supply the tenant to a read that is subject to a
  deny-by-default policy, and there is no such mechanism today short of a process-global — which would be
  wrong in `worker`, where the same module is imported for evaluation's batch runs.
- **If `pin_unresolvable` is accepted**, the metrics block gains a third label value. Phase 19 and phase
  20 should be told, because the gateway renders both misses as the same OpenAI-shaped 404 and only the
  metric separates them.
- **If it is not**, name which of the two declared values a bad pin should be counted as, knowing that
  either choice makes one of them mean two things.
- **INT-009's pin sentence should be corrected either way**, because a future reader will otherwise
  conclude the status predicate is redundant and delete it — which would put unapproved prompt text into
  production through the pin path while BR-03's constraint watched the pointer.
