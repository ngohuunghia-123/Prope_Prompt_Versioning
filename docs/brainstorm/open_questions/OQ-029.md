# OQ-029 — `target_type` is a closed enumeration and nothing enumerates it. Nor are `detail_keys` declared per action.

**Raised by Phase 4 planning (04-CONTEXT.md, D-61), 2026-08-10.** `blocks_build: false` — Phase 4
seeds a derived set and records the derivation so it is reviewable rather than buried, but the
derivation is **an agent judgement, not a reading of a spec**, and that is the whole reason this
file exists.

## The conflict, stated exactly

Three of `history_action_registry`'s five columns have no declared values anywhere in `docs/`:

**`target_type`.** ADR-0024's schema block says `target_type   closed enumeration`. A-122 says the
event *"identifies its subject with a closed `target_type` enumeration"*. A-120 makes it the first
half of every action name. **No file lists its members.** The only member stated anywhere is
`target_type = user`, in `A-151` / ADR-0054, for `user_tombstoned`. A-122 names eight *tables* a
target might have pointed at had there been a foreign key — `prompt_property`, `revision`, `release`,
`eval_suite`, `provider_config`, `workspace`, `prompt_grant`, `api_key` — but a table list is not a
`target_type` list, and it omits at least `review_task`, `eval_run`, `member`, `role` and `user`.

**`detail_keys`.** A-124 declares the mechanism and gives two examples — `revision_released` carries
`version_id`, `previous_version_id`, `break_glass`; `role_assigned` carries `role`, `grantee_user_id`
— *"and so on"*. `release-control.lock.yml` repeats the first. `access-control.lock.yml` states that
`user_tombstoned`'s set is **empty**, deliberately. That is 3 of 31 actions. The other 28 have no
declared keys, and this is the column whose entire purpose is that a prompt body cannot reach the
audit log through a field nobody declared (T-022, HIGH).

**`requires_reason`.** The only column of the three that *is* fully determined: exactly three actions
carry it — `revision_break_glass_released`, `release_withdrawn`, `revision_changes_requested` —
stated identically in the lock file, in `release-control.lock.yml` and in INT-006. Recorded here so
the resolver knows the gap is two columns, not three.

**A count that does not reconcile.** A-119 says the prompt-scoped events *"name six different
`target_type`s owned by four different modules"*. Deriving `target_type` per action from the five
lock files' event lists gives **seven** prompt-scoped types — `property`, `revision`, `release`,
`review_task`, `eval_suite`, `eval_run`, `prompt_grant`. Either one of those is not prompt-scoped, or
A-119's six is one short. It is not decidable from the documents.

## Why the two gaps are not the same size

`target_type` is **derivable with confidence** from the action names plus A-120's rule, and its cost
of being wrong is bounded: nothing joins on it (A-122 forbids the foreign key), no acceptance
criterion asserts its values, and `read()`'s subject-trail scope takes whatever the caller passes.
AC-6 asserts the **action names** only. Phase 4 therefore derives it, seeds it, and constrains
`history_event` against the registry so an event cannot pair an action with an unregistered target
type — the pairing becomes a database fact even though the vocabulary itself is a judgement.

`detail_keys` is **not derivable**. Each writing module knows which facts its own events must carry,
and four of those five modules have not been built yet — prompt-registry is Phase 13, evaluation
Phase 16, provider-access Phase 10, release-control Phase 22. A key invented now for
`eval_run_completed` is a guess that the module writing it will discover is wrong at exactly the
moment its transaction fails. **Phase 4 therefore seeds only the keys that are actually declared**
(`revision_released`, `role_assigned`, `user_tombstoned`'s empty set) and leaves the remaining 28
actions with an empty `detail_keys`, which is the strictest possible position: an append carrying any
key at all for those actions is refused. That is loud, correct under A-124's allow-list posture, and
guarantees that each writing module's own phase must add its keys deliberately — which is A-124's
stated friction *"by design at the exact point where A-046's rule is broken"*.

## What a resolver has to choose between

1. **Accept the derivation, and record `target_type`'s members in ADR-0024 or A-122** so the closed
   set is closed somewhere a reader can find it. Cheapest, and it makes the next module's author read
   a list instead of inferring one.
2. **Declare `target_type` per action in each writing module's lock file**, beside its event list,
   the way `release-control.lock.yml` already declares `revision_released`'s detail keys. Most
   consistent with where the knowledge lives; costs five lock-file edits.
3. **Leave `detail_keys` empty-until-needed, per module phase** (what Phase 4 does) versus
   **populating all 31 now**. The second is the option that looks like completeness and is not: it
   fabricates the contents of four unbuilt modules' payloads, and a wrong allow-listed key is worse
   than an absent one because it will be used.

The `detail_keys` half also needs a home for the answer. It cannot be Phase 4's, and no phase
currently owns "each writing module registers its own keys" — that obligation lands in Phases 10,
13, 16 and 22 and is named in no requirement.
