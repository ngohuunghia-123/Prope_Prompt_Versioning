# OQ-149 — What counts as the same prompt, and does reading the inbox deserve its own permission?

**Raised 2026-08-18 while locking prompt-observation.** `blocks_build: false` — A-154 and SR-1 carry
working answers and both are deliberately the narrow option, so an answer can only loosen them. Two
findings raised together because both are about how much authority a heuristic module gets.

## 1. The normalisation rule is a product decision wearing a technical costume

A-154 keys the fingerprint on the system message, normalised: whitespace collapsed, interpolated-looking
spans masked. Everything downstream is a consequence of that one line — how many rows the inbox has,
whether "this prompt changed on Tuesday" is true, and which spans get proposed as variables.

The rule cannot be validated in advance because the input is other people's code. What can be said is
what each direction costs:

- **Too loose** — two genuinely different prompts share a fingerprint. The inbox says one prompt where
  there are two, the drift view shows them flapping between bodies, and a person adopting either gets a
  proposal built from both. Silently wrong.
- **Too tight** — one prompt becomes hundreds of rows, one per interpolation. The inbox is unusable but
  the failure is obvious in the first screenshot, which is why A-154 leans this way.

**The specific unknown is what "interpolated-looking" means**, and there is no general answer. A date, a
number, a name, and a customer's pasted document are all interpolations; a JSON schema in a system
message and a JSON payload interpolated into one are the same bytes with different meanings.

**What would settle it**: fifty real system messages from one product. Not research — traffic. This is
therefore the one question here that OQ-147's answer partly answers by making the data available.

## 2. ~~`prompt.create` is a borrowing, and it may be the wrong one~~ — **ANSWERED 2026-08-18, ADR-0061**

> **This half is closed.** It asked whether reading the discovery inbox deserved its own action or
> could keep borrowing `prompt.create`. The answer turned out to be neither: **ADR-0061 makes the
> namespace the unit of authorisation**, so an observation has a container, and the ordinary
> `prompt.read` check against its namespace is the whole rule. prompt-observation needs no action of
> its own and borrows nothing.
>
> The inversion identified below is what made the borrowing wrong, and it is worth keeping visible
> because the analysis was right and the fix came from somewhere else: `prompt.create` is a
> low-privilege action a Prompt Owner holds on their first day, and it was being made to grant the
> **widest read in the product**. A-160 records the related decision that a *namespace grant* does get
> a new action, `namespace.grant`, for the mirror-image reason — whoever may share one prompt must not
> thereby be able to hand over a folder of a thousand.
>
> The surviving half of this question is §1, the fingerprint rule.

### The original text, kept for the reasoning

SR-1 checks `prompt.create` on every route. The reasoning is sound and worth repeating: A-115's
vocabulary is closed and mirrored by a `CHECK` constraint in **access-control's** migration, so adding
a member from this module is a cross-module schema change taken to avoid writing down a question —
exactly what OQ-079 rejected, twice, for `prompt.change_access`.

It is also a genuine fit rather than a convenient one: the inbox exists in order to be adopted, and a
person who may not create a prompt can do nothing with what it shows them.

**Where it might be wrong.** `prompt.create` is a low-privilege action — it is what a Prompt Owner does
on their first day. The inbox shows every ungoverned prompt in the workspace, which is a wider view than
any single prompt's owner has, and BR-01's private-by-default rule does not reach it (SR-2) because an
observation has no owner. So the narrowest permission in the module grants the widest read in the
product, and that inversion is worth somebody looking at deliberately rather than inheriting.

**If it deserves its own action**, the cost is known and small **now** — `vocabulary.Action` and
`role_permission`'s `CHECK` each grow by one member, and every workspace's matrix has to be told about
it, which under A-020 is no workspaces at all. That price rises the moment a real matrix exists, which
is the argument for answering this before the pilot rather than after.

## What the answers change

- **A looser fingerprint** changes a pure function over stored bodies, so it is a re-hash rather than a
  lost inventory (A-154 stores the raw body beside the key precisely for this). Cheap either way.
- **A new action** is one migration in access-control, one seed row per role, and one line in SR-1. It
  is cheap today and not cheap later.
- **If observed bodies are classified as more sensitive than drafted prompts** (OQ-148's third
  sub-question), then the borrowing is definitely wrong and this stops being a naming question.
