# OQ-019 — `apis.exposes` omits `price_usage`. Does the list change, or does the seam?

**Raised by Phase 2 plan 02-04 while implementing D-18, 2026-08-10.** The code ships either way —
`blocks_build: false` — and the deviation is recorded here rather than absorbed into the spec, per
`.planning/BSP-LINK.md`: *a spec that disagrees with the code is information; raise an `OQ-NNN`
naming the exact field and the conflict; do not patch the spec to agree.*

This is one of three deviations this phase raises, and it gets its own file for the reason the other
two do: each blocks a different upstream field, and a resolver can accept one without accepting the
others. OQ-018 (plan 02-02) blocks `data.owns`; OQ-020 (this plan) blocks INT-021's signature.

## The conflict, stated exactly

`docs/modules/call-ledger.lock.yml` `apis.exposes` lists **three** internal seams. `price_usage` is
not among them.

`docs/architecture/interfaces.md` registers it as **INT-019** — provider call-ledger, consumer
evaluation, in-process and explicitly *not* the broker, request carrying a `run_id` and one usage row
per eval case, returning void, with failure semantics of *"raises -> evaluation records a run error,
not a case failure"*.

And the lock file's own `inputs` block **cites INT-019** as evaluation's contract with this module.
So the same file both names the interface and omits the function the interface registers.

`src/prope/call_ledger/seams.py` ships `price_usage`. The lock's list is treated as an omission
rather than as the authority.

## Why the function cannot simply be folded into `enqueue`

The obvious repair — one `write_call_records(source=...)` covering both callers, leaving
`apis.exposes` correct — is refused on merit, and the reason is the whole of D-18.

**The two failure contracts are opposite:**

| | on failure |
|---|---|
| `enqueue` (INT-018) | **Never raises into the caller. Ever.** It is on the gateway's response path, and A-139 makes the p95 budget a property of the seam. It counts and drops. |
| `price_usage` (INT-019) | **Raises.** Evaluation must be able to record a **run error**, because a run whose usage could not be priced must not report a cost delta — and INT-021's counts are how the review screen says so. |

One function with a `source` flag would have to pick one of those and quietly break the other caller.
Worse, the breakage is invisible in both directions: "returned normally" and "raised" are both
plausible-looking behaviour from the outside, and the gateway would discover its choice as a failed
user request while evaluation would discover its choice as a cost delta nobody can explain.

## Why this does not block the build

`blocks_build: false`. The function exists, is tested against the real engine
(`tests/integration/test_eval_usage_priced_without_body.py`), and evaluation is not built until
Phase 16/17. Nothing is waiting on the answer. What the answer settles is which document is right,
which matters when Phase 17 is written against one of them.

## The shape of the possible answers

1. **Add `price_usage` to `apis.exposes`.** The list becomes four internal seams. This is what the
   build already assumes and what INT-019 already says. Cheapest, and it changes no code.
2. **Remove INT-019 and fold eval usage into INT-018.** Requires deciding which failure contract
   survives, and accepting that the other caller gets the wrong one. The argument above is why this
   is not recommended.
3. **Keep both documents as they are and record the omission as known.** Leaves a lock file that
   contradicts its own `inputs` block, which is the state that produced this question.

**A recommendation, offered because the pack owes you one:** option 1. It is the only one that leaves
every document saying the same thing as every other document and as the code.
