# OQ-141 — `prope_registry_revision_created_total` is asked for a label the project forbids

**Raised by the prompt-registry build, 2026-08-12.** `blocks_build: false` — the counter ships,
increments, and is scrapable. It ships with no labels.

## The contradiction

`prompt-registry.lock.yml`'s `observability_requirements.metrics` block writes:

```
- prope_registry_revision_created_total
  # labels: workspace
```

`src/prope/observability.py` states the project-wide rule that refuses it, and states it about this
exact identifier:

> Metric label cardinality is bounded by construction: every label declared here has a CLOSED set of
> values fixed in source, and `workspace_id` — the highest-cardinality identifier in the system and
> the one most tempting to add — is deliberately never a label.

That rule is ADR-0030's bounded-cardinality requirement applied, and five modules have shipped under
it. A workspace id is unbounded by design: workspaces are created by `POST /api/v1/workspaces` at
runtime, so the series count of this counter would grow with the customer list.

## Why a substitute label was not shipped instead

Three were considered and each is worse than none.

1. **A constant token** (`workspace="tenant"`). Reads in Grafana as a real dimension and answers
   nothing. A label that is always the same value is a lie with a legend attached.
2. **A bucket of the workspace's size or age.** Bounded, and meaningless — nobody asks "how many
   revisions were written by medium-sized workspaces".
3. **A hash prefix of the workspace id.** Bounded by construction and still an identifier: it
   correlates one workspace's activity across every panel it appears on, which is the property
   ADR-0030's rule exists to deny.

## What shipped

```python
revision_created_total = Counter(
    "prope_registry_revision_created_total",
    "Revisions written. Unlabelled: see this module's docstring and OQ-141.",
)
```

The question the label was reaching for — *which workspace wrote which revision, and when* — is
already answered, better, by `history.history_event`: every revision write appends a
`revision_created` row carrying `workspace_id`, `actor_id`, `scope_prompt_id` and `occurred_at`, and
`ix_history_event_workspace_id_action_seq` is the index for exactly that query. A metric is the wrong
instrument for a per-tenant question that an append-only audit table already answers precisely.

## What is being asked

One of two:

1. **Drop `labels: workspace` from the lock file.** The metric is a rate indicator; the audit trail is
   the per-tenant record. This is what ships today.
2. **Name a bounded label worth having.** If one exists it should be written down; none was found.

Reversal cost: low. Adding a label to a counter is a one-line change and the alert
(`RegistryUnapprovedPointer` and friends) reads none of it.

## What is affected either way

- `src/prope/prompt_registry/observability.py` — the declaration and its docstring
- `src/prope/prompt_registry/commands.py` — the one increment site
- `tests/architecture/test_prompt_registry_alert_rules.py` — reads metric families, not labels
- `docs/modules/prompt-registry.lock.yml` — **not edited**
