# OQ-139 — the grant routes take the prompt's owner and access level from the browser

**Raised by the access-control build, 2026-08-11.** `blocks_build: false` — the routes ship and the
bound is argued at `api._prompt_subject`.

## The situation

ADR-0020 says access-control may not read any subject it authorises: callers pass `owner_id` and
`access_level` from the row they already read. Every **in-process** caller is a module that read the
row a moment earlier under the tenant policy, so the parameter is a fact it already holds.

INT-029 puts `GET|POST /api/v1/prompts/{prompt_id}/grants` and `DELETE .../grants/{user_id}` on
**access-control**, which means the caller is the SPA. The SPA is in the same position — it rendered
the prompt's screen a moment ago — but it is a browser, so *"a caller that would forge it could have
skipped the check"* stops being the whole defence.

## What forging buys, and what it does not

- Forging `owner_id = me` grants the actions in `permissions.OWNER_ACTIONS`: read, edit, retire,
  grant, create a revision, edit the suite, start a run. Every one of those is already available to
  the Owner role workspace-wide.
- Forging `access_level = workspace` grants read, which is what an owner opting a prompt to the
  workspace grants anyway.
- Neither reaches `revision.submit`, `revision.approve`, `release.create`, `release.break_glass`,
  `release.withdraw`, or any provider action. No grant and no ownership confers those (A-112), so the
  four non-negotiables hold.

So the exposure is: **a workspace member can grant themselves, or somebody else, read or edit access
to a private prompt they should not have been able to see.** That is BR-01's core promise, and BR-01
is the failure most likely to end a pilot because it is discovered by the person whose prompt leaked.

## What is being asked

The honest fix is for **prompt-registry to proxy the two write routes**: the registry reads the
prompt, calls `may()` in process with the row it holds, and calls into access-control's command layer.
That contradicts INT-029's own placement of them, which is why it is a question rather than a change.

Alternatives, both weaker: sign the two attributes into a short-lived token the registry issues (a
second credential format, for one field pair), or have access-control read `prompt_property` (the
forbidden edge, and six cycles).

Reversal cost: **moving a route after the SPA ships is a coordinated frontend change.** Cheapest now.

## What is affected either way

- `src/prope/access_control/api.py` — `_prompt_subject`, `list_grants`, `create_grant`, `revoke_grant`
- `tests/architecture/test_route_table.py` — `EXPECTED_ROUTES`, if the paths move
- `docs/architecture/interfaces.md` — **not edited**
