# OQ-034 — Three authorities describe `registered_actions()` three different ways, and one of them makes the declared signature unimplementable.

**Raised by Phase 5 planning (plan 05-04), 2026-08-11.** `blocks_build: false` — the phase ships a
superset of both declared return shapes, which breaks no consumer of either. Raised because the
disagreement is **between the authorities themselves**, not between a spec and a preference, and
because a seam that ships wider than two documents describe should be a written question rather than a
silent choice.

## The conflict, stated exactly

**One.** `docs/modules/property-history.lock.yml`, `apis.exposes`:

> `internal: registered_actions() -> [{action, target_type, detail_keys}]` — the vocabulary as data, so
> a route-table test can assert every state-changing endpoint names a registered action, and so the
> rename in A-120 can be checked rather than trusted.

**Three fields. No parameter.**

**Two.** `docs/architecture/interfaces.md`, INT-008:

> **Returns**: `[{action, target_type, detail_keys, requires_reason}]` — the vocabulary as data.

**Four fields. No parameter.** The two documents disagree with each other about `requires_reason`.

**Three.** `docs/adr/0038-the-action-registry-is-cached-for-the-process-lifetime.md`, Consequences:

> `registered_actions()` **continues to read the table rather than the cache**. It exists so a
> route-table test and a CI schema check can assert the vocabulary (AC-6), and a test that checks the
> cache against the lock files instead of the database would assert nothing about what `append()` will
> accept after the next migration.

A table read needs a connection. `docs/adr/0023-property-history-is-a-library-in-the-callers-transaction.md`
forbids this module opening one of its own — the whole module runs on the caller's session — and there
is no ambient session in a Python library. **So a function reading the table with no parameter is not
expressible**, and the two declared signatures cannot both be literal and correct.

The table itself has **five** columns: `action`, `target_type`, `detail_keys`, `requires_reason`,
`writing_module`. `RegisteredAction` in `src/prope/property_history/domain.py` carries all five, and has
since Phase 4.

## What ships

```python
async def registered_actions(session: AsyncSession) -> tuple[RegisteredAction, ...]
```

Reads the table (ADR-0038), takes the session ADR-0023 forces, returns all five fields sorted by
`action`.

**Why the superset rather than three fields or four.** Narrowing to either declared shape would pick a
winner between two specs by omission. And `writing_module` is load-bearing for the very test INT-008
exists to make possible: `tests/contract/test_event_vocabulary_matches_the_locks.py` asserts not only
that the registry and the five lock files hold the same 31 names, but that **each action is attributed
to the module that declared it**. Without `writing_module` on the seam, an action filed under the wrong
writer leaves the union correct and the attribution wrong — which is precisely one of the three
disagreements property-history's own step-3 reconciliation found (*"five action names, one misfiled
event, and a Success metric naming an event nobody writes"*), and `module_map.md` really did list
`access_granted` under prompt-registry.

## What is being asked

Either:

1. **Adopt the shipped shape** and let the two interface documents carry the session parameter and the
   five-field return; or
2. **Narrow the seam**, naming which of the two declared return shapes wins — and, if the no-parameter
   signature is to stand literally, saying what supplies the connection, because ADR-0023 rules out the
   only mechanism a parameterless version could use.

Option 2's second half is the reason this is a question rather than a note: there is no answer to it
that does not change either ADR-0023 or ADR-0038.

## What is affected either way

- `src/prope/property_history/registry.py` — the function
- `tests/contract/test_event_vocabulary_matches_the_locks.py` — the only consumer inside this
  repository today
- **Phase 23**, whose assembled-route-table assertion is INT-008's declared second consumer
  (*"a route-table test can assert every state-changing endpoint names a registered action"*) and which
  will be written against whichever shape stands
- `docs/architecture/interfaces.md` INT-008 and `docs/modules/property-history.lock.yml`
  `apis.exposes` — neither of which is edited by Phase 5
