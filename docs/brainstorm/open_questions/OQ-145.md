# OQ-145 — seven places the shipped `evaluation` module differs from its own spec

**Raised by the evaluation build, 2026-08-12.** `blocks_build: false` — the module ships, its
thirteen acceptance criteria have tests, and the migration applies cleanly. Every item below is a
sentence in a locked document that the code could not satisfy as written; each is recorded here
rather than resolved by editing the document, per the project's standing rule.

Ordered by how much a reader would be surprised.

---

## 1. AC-9 says "before any case is dispatched". One case is dispatched.

**Where:** `evaluation.lock.yml`, AC-9 — *"then it is refused before any case is dispatched, naming
both the declared modality and the returned shape, and no upstream call is billed."*

**Why it cannot hold literally.** The returned *shape* is not knowable without a call. Nothing in a
revision declares it: `registry.revision` carries a `provider_config_id`, an `upstream_model` and a
body, and none of the three says whether the target answers prose, JSON, or an asset URL. The
provider catalogue does not say either — `provider.model_catalogue` records `supports_streaming` and
availability, not response modality. There is no source for the check that is not a call.

**What shipped.** `execute_run` dispatches case 1 as a **probe**, classifies what came back with
`assertions.returned_shape`, and refuses the run before anything else happens: no case results are
written, `price_usage` is never reached, and the remaining cases are never dispatched.
`tests/integration/test_modality_mismatch_refused.py` asserts exactly one dispatch and a pricer that
was never called.

**What is actually preserved.** Both properties AC-9 is protecting: the reviewer is not shown a wall
of failed assertions that reads as a bad prompt, and the workspace is not billed for a suite's worth
of calls. What is lost is one call, on one case — the minimum the check costs.

**What is being asked.** Restate AC-9 as *"refused after at most one probe dispatch, before any case
result is recorded and before any usage is priced"*, or name a source for the modality that does not
require a call.

---

## 2. `max_cost` is registered as an assertion type and is not evaluable per case.

**Where:** `evaluation.lock.yml`'s assertion registry lists `max_cost` for both modalities.

**Why it cannot hold.** Cost is call-ledger's, and INT-021 (`get_run_totals`) prices **per run**, not
per case. There is no per-case read on the ledger at all, and `ledger.call_record` is a sink —
`evaluation → call-ledger` may write usage and read run totals, and nothing else. So at the moment a
case's assertions run, the per-case cost does not exist anywhere the module may look.

**What shipped.** `_max_cost` raises `AssertionUnevaluable`, which the executor records as
`outcome=error` with `error_code=assertion_unevaluable`. **Loud, never a silent pass.** A `max_cost`
assertion in a suite therefore errors every case it is attached to, visibly, with a code that says
why. `tests/evaluation/test_assertion_registry.py` asserts that shape rather than a passing one.

**What is being asked.** One of three: drop `max_cost` from the registry; register a per-case read on
call-ledger (a new interface, and a hole in a module that is deliberately a sink); or redefine it as a
*run-level* assertion evaluated after pricing, which is a different mechanism from the eleven that
exist today.

## 3. `eval_run` ships a column `data.owns` does not list.

**Where:** `evaluation.lock.yml`, `data.owns.eval_run`.

**What shipped.** `refused_reason text`, with
`ck_eval_run_refused_reason_belongs_to_refused CHECK (refused_reason IS NULL OR status = 'refused')`.

**Why.** `status='refused'` has two causes that a reviewer must be able to tell apart — the spend
ceiling was reached (A-029), and the modality mismatched (AC-9) — and one of them means "ask an admin
about the budget" while the other means "your suite is wrong". Encoding the difference in the log line
alone would put it somewhere the review screen cannot read.

The column holds a value from a closed vocabulary (`RefusalReason`), not a sentence, so ADR-0053's
rule survives: the API returns the machine code and the client translates it.

**What is being asked.** Add `refused_reason` to `data.owns.eval_run`, or name where else the
distinction should live.

---

## 4. ADR-0049's illustrative claim SQL orders by a column that does not exist.

**Where:** ADR-0049 §1's SQL sketch reads `ORDER BY created_at`.

**Why it cannot hold.** `data.owns.eval_run` lists no `created_at`. It carries `started_at`, which is
NULL until the claim itself sets it — ordering a queue by a column the claim writes would leave the
ordering undefined for every row in that queue.

**What shipped.** `ORDER BY r.id`. Run ids are ULIDs (ADR-0003) and a ULID is lexicographically
ordered by its own timestamp prefix, so this is creation order, exactly — without adding an
undeclared column to the table.

**What is being asked.** Correct the sketch, or add `created_at` to `data.owns.eval_run` and use it.
The behaviour is identical either way; this is about the document, not the queue.

---

## 5. INT-011 registers three reads. Four shipped.

**Where:** `docs/architecture/interfaces.md`, INT-011 — `get_revision`, `get_released_revision`,
`get_diff`.

**What shipped.** A fourth, `prompt_registry.seams.get_prompt`, and this module is its first caller.

**Why.** ADR-0020 makes a permission decision take the subject's `owner_id` and `access_level` **from
the row the caller already read**, and access-control may not read `registry.prompt_property` itself.
So every module that authorises an action against a prompt needs a way to read one. prompt-registry's
own routes call `repository.load_prompt` directly; evaluation cannot, because reaching past a
module's `seams.py` is what the import allow-lists exist to refuse
(`tests/architecture/test_evaluation_depends_on_five_modules.py`).

The alternative was for evaluation to import `prompt_registry.repository`, which would make INT-011's
registered surface a description of nothing.

**What is being asked.** Register `get_prompt` on INT-011. It is already annotated as a widening in
`src/prope/prompt_registry/seams.py`, pointing here. Release-control will need it in wave 5 for the
same reason.

## 6. `visible_subject_filter` is named in `security_requirements` and is not used.

**Where:** `evaluation.lock.yml`'s `security_requirements` describe INT-002's
`visible_subject_filter`, while `apis.consumes` names only `may()`. The step-5 interfaces pass
flagged the disagreement as "owed to step 6" and it is still open.

**What shipped.** `may()` alone. The reason is structural rather than a shortcut: **every route this
module mounts is scoped to one prompt.** There is no "list every eval run in the workspace" endpoint —
suites are listed under `/prompts/{prompt_id}/eval-suites`, runs and case results are read by id and
resolve to their prompt, and the comparison is per prompt. So every list is already narrowed to a
single subject whose visibility is decided by `_visible_prompt`, and a filter that returns the set of
visible prompt ids has nothing left to narrow.

If a workspace-wide "recent eval runs" view is ever added, it needs the filter and this stops being
true.

**What is being asked.** Drop the `visible_subject_filter` sentence from `security_requirements`, or
name the endpoint it was written for.

---

## 7. An eleventh metric ships beside the ten declared.

**Where:** `evaluation.lock.yml`'s `observability_requirements.metrics` lists ten.

**What shipped.** Eleven. The extra is
`prope_evaluation_unpriced_run_total{reason}` — `ledger_unavailable`, `unknown_usage`, `no_price_row`.

**Why.** The declared alert `EvalPricingStalled` has no series to read without it. Pricing is a soft
dependency: a ledger failure leaves the run `completed` with the money column NULL, which is the right
behaviour and is indistinguishable from a run nobody has priced yet unless something counts it. The
label set is closed and fixed in source, so ADR-0030's cardinality rule holds.

**What is being asked.** Add it to the declared list. `tests/architecture/test_evaluation_alert_rules.py`
already asserts that every metric an alert names is one this module declares, which is what made the
gap visible.

## Reversal cost

Low for items 3, 4, 5, 6 and 7 — each is a document edit or a one-line code change with a test that
already pins the behaviour. **Medium for items 1 and 2**, because both are about what the product
promises a reviewer: item 1 changes what "refused" costs, and item 2 changes whether a suite author
can write a cost assertion at all.
