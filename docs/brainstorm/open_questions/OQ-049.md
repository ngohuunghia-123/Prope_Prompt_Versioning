# OQ-049 — access-control's route count is written as 15, as 19, and as an enumeration of 16.

**Raised by Phase 8 planning, 2026-08-11.** This is the phase that mounts them, and
`tests/architecture/test_route_table.py` asserts the assembled table against a literal set in both
directions — so a count that is off by one is a red test rather than a documentation nit.

## The three numbers

**INT-029's seam-table row says "15 routes".** Its own Routes line enumerates, with `GET|POST`
written as one entry:

`POST /auth/login` · `POST /auth/logout` · `POST /auth/password` · `POST /workspaces` ·
`GET|POST /workspaces/{id}/members` · `DELETE /workspaces/{id}/members/{user_id}` ·
`PUT .../members/{user_id}/roles` · `GET|POST /prompts/{id}/grants` ·
`DELETE /prompts/{id}/grants/{user_id}` · `GET|POST /workspaces/{id}/keys` ·
`DELETE /workspaces/{id}/keys/{key_id}` · `GET /permissions` · `POST /users/{user_id}/tombstone`

That is **13 bullet entries and 16 operations** across **13 distinct paths**. None of the three is 15.

**`access-control.lock.yml`'s `apis.exposes` enumerates 18** — the same 16, plus `GET /healthz` and
`GET /readyz` — while `libraries_frameworks` in the same file says **"19 routes, including Prope's
only unauthenticated path"**.

**`provenance.change_log` records the arithmetic that produced 15**: *"INT-029 goes from 14 routes to
15"* when the tombstone was added on 2026-08-09. So 14 was the pre-tombstone number, and the
pre-tombstone enumeration is 15 operations.

## Why the counting convention matters, and why it is already settled elsewhere

The identical ambiguity was met and resolved one module earlier, and the resolution is written into a
test that ships today. `tests/architecture/test_route_table.py:42-50`:

> `POST|GET /api/v1/prices` is one line in `interfaces.md` and two paths; INT-028's own text settles
> the count by saying *"5 routes"* beside four bullet lines. **Every count in this file is a path
> count** — meaning an operation count, `(method, path)`.

Under that convention INT-028's "5 routes" is right and INT-029's "15 routes" is one short of its own
enumeration. Under a bullet-line convention INT-028's would have been 4.

## What Phase 8 adopted

**The enumeration is authoritative and the counts are summaries** (D-117). Phase 8 mounts the
**sixteen** operations INT-029's Routes line and the lock file's `apis.exposes` both list, adds them
to `EXPECTED_ROUTES` as sixteen `(method, path)` pairs, and mounts **no new health route** — `/healthz`
and `/readyz` are one pair per *process*, not one per module, and `app` already serves them with the
semantics INT-030's table gives access-control (*"the database is reachable"*), which is byte-identical
to call-ledger's.

That makes the assembled `/api/v1` table 5 + 16 = **21 operations** after this phase, and the whole
table 23 including the two unversioned health routes. The ROADMAP phase title keeps the word
"fifteen"; the ROADMAP is not edited, and this file is the record of why the number in the title and
the number in the test differ by one.

## The shape of the possible answers

1. **Enumeration wins; correct "15" to 16 and "19" to 18 at the next spec revision.** What Phase 8
   adopted. Nothing in the build changes.
2. **"15" wins and one route is dropped.** Requires naming which — and every one of the sixteen is
   named individually in `apis.exposes` with its own reasoning, so there is no candidate.
3. **The counts are bullet-line counts** and INT-028's test convention is wrong. Costs a rewrite of a
   green test whose docstring already argues the other way.

**A recommendation:** option 1, folded into whichever revision next touches INT-029 — with the
counting convention stated once, in `interfaces.md`'s preamble rather than per row, so the third
instance does not have to be found by an implementer.
