# OQ-052 — AC-15 requires a catalogue key, ADR-0053 requires a catalogue and a CI check, and neither exists nor has an owner

**Raised by Phase 9 planning, 2026-08-11.** `blocks_build: false` — Phase 9 ships the key and asserts the
API half of AC-15. Raised because AC-15 is the **only** acceptance criterion in the whole project that
touches the i18n layer, PITFALLS §5 already records that the layer has no owner, and Phase 9 is the phase
where that gap stops being theoretical.

## The problem, stated once

AC-15's second clause is *"and each renders the absence through a catalogue key rather than a stored
string (ADR-0053)."* Rendering is a client act. ADR-0053 places the machinery on the client side
explicitly:

- §1 — *"Every user-facing string in the SPA comes from a message catalogue, keyed by a stable
  identifier. No literal display text in a component."*
- §3 — *"The keys are English, and they are identifiers, not fallbacks. A missing key renders the key,
  visibly, and **a CI check fails the build on any key present in the code and absent from `vi`**."*
- §5 — *"The API stays English and stays machine-readable … **The client renders the `code`, not the
  `message`.**"*

So the criterion is split across a seam:

- **The API side** — return a key rather than a name — is buildable and Phase 9 builds it.
- **The client side** — a `vi` catalogue containing that key, and a CI check that fails without it — has
  no module, no milestone and no phase. PITFALLS §3 records that the React SPA owns no milestone at all;
  §5 records the i18n layer specifically.

The gap is now measurable rather than abstract. **Seven catalogue keys exist in code and none exists in
any catalogue**, because there is no catalogue:

| Key | Introduced by |
|---|---|
| `forbidden` | Phase 8, plan 08-01 |
| `authentication_failed`, `last_admin`, `email_taken` | Phase 8, plan 08-04 |
| `membership_active` | Phase 8, plan 08-05 |
| `password_change_required` | Phase 9, plan 09-01 (`OQ-051`) |
| `actor.tombstoned` | Phase 9, plan 09-04 |

ADR-0053 §7 adds a further **31** — *"Every registered history action gets a catalogue key … derived from
`property-history.registered_actions()` (INT-008) rather than hand-listed"* — plus the existing
`ErrorCode` members from Phases 1-3. The real count is somewhere near fifty and none of them is checked
by anything.

## What Phase 9 ships (D-140, D-141, plan 09-04)

- `TOMBSTONED_ACTOR_KEY = "actor.tombstoned"`, defined **once**, in `src/prope/management_api.py` —
  beside `ErrorCode`, in the module Phase 8 created as the one A-045 surface every module's routes share.
  Six modules will render actors and none of them should import access-control for a string.
- Every response model that can carry an actor gains `display_key: str | None`. For a tombstoned person
  the projection returns `display_name=None`, `email=None`, `display_key=TOMBSTONED_ACTOR_KEY`; for a
  live one it returns the real values and `display_key=None`.
- `tests/integration/test_no_surface_resolves_a_tombstoned_actor.py` asserts, over every surface that
  exists at Phase 9, that the person's name and email appear in **zero** response bodies, log records and
  metric labels — with a negative control proving they were visible before the tombstone.

What Phase 9 does **not** ship: a catalogue, a `vi` file, or a CI check. Inventing one would put a
product-copy artifact in a phase that owns access control, and would create the first half of a layer
with no owner for the second.

## What is being asked

1. **Who owns the catalogue?** The candidates are a ninth milestone for the SPA (PITFALLS §3's
   suggestion, and a user decision rather than something a handoff can invent), the deployment work
   (PITFALLS §4, which also owns no milestone), or a per-milestone UI phase.
2. **Is `actor.tombstoned` the right key value?** It is a dotted identifier per ADR-0053 §3 and it is
   deliberately not in `ErrorCode` — it is not an error. If the eventual catalogue namespaces keys
   differently (`ui.actor.tombstoned`, `common.actor.tombstoned`), changing it later means changing a
   field six modules return.
3. **Is `display_key` the right field name and shape?** The alternatives considered and rejected in
   planning: returning a rendered Vietnamese string (ADR-0053 §1 forbids it and §5 puts translation on
   the client), omitting the fields entirely and letting the client infer (an inference is a rule in a
   client that does not exist), and falling back to the user id (a display string that happens to be an
   identifier, which is exactly what makes an opaque id look resolvable).
4. **Where does the CI check live?** ADR-0053 §3 makes it a build failure. With no SPA build in CI there
   is nothing to hang it on, and the nearest available shape — a Python test asserting every key in
   `src/prope/` exists in a checked-in `vi.json` — would be a backend test asserting a frontend artifact,
   which is a coupling nobody has agreed to.

## What is affected either way

- `src/prope/management_api.py` — `TOMBSTONED_ACTOR_KEY` and every `ErrorCode` member
- `src/prope/access_control/schemas.py` and the actor projection — the `display_key` field
- `tests/integration/test_no_surface_resolves_a_tombstoned_actor.py`
- Every later module that renders an actor: prompt-registry (**13**), release-control (**23**, **24**),
  evaluation (**17**) — each of which will import the same constant
- `docs/adr/0053-…` §3's CI check, and `.planning/research/PITFALLS.md` §3 and §5 — **none edited by
  Phase 9**
