# OQ-140 — the delete refusal is asked to name a count it may not read

**Raised by the provider-access build, 2026-08-11.** `blocks_build: false` — the refusal ships with
its shape, its status code and its machine `code`, and without the count.

## The contradiction

`apis.exposes` says both of these about `DELETE /api/v1/providers/{id}`:

> The refusal comes from the foreign key `revision.provider_config_id`, **NOT** from asking
> prompt-registry: that direction is forbidden (module_map.md)

> the response says **how many revisions bind the configuration** and links to the registry's filter
> rather than naming them

The two cannot both hold. A count of bound revisions is a `SELECT count(*) FROM registry.revision`,
which is the forbidden read whichever module issues it — and the foreign key violation PostgreSQL
raises carries the constraint name and the offending row, never a count. There is no third source.

`AC-10` asserts the strong form: *"the delete is refused by the foreign key with a count of bound
revisions and no query against prompt-registry's tables"*.

## What shipped

The refusal shape, minus the number. `409` with `code = provider_bound_by_revisions` and
`details.provider_config_id`, raised from the `IntegrityError` the foreign key produces. Disabling is
offered in the message, because disabling is the operation that is always available (A-096).

The foreign key now exists. Migration `0008_registry_schema.py` creates
`fk_revision_provider_config_id` on `registry.revision` with no `ON DELETE` clause, so the
`except IntegrityError` branch in `delete_provider` is live and a bound configuration is refused by
the engine. It is the module's one sanctioned cross-schema foreign key and it is declared as such in
`tests/architecture/test_schema_invariants.py`. Nothing in provider-access changed to make that
happen, which is the direction rule paying for itself.

The count is still missing, and the question below is unchanged by it. What did become available is
option (1)'s other half: `prompt_registry.repository.count_revisions_binding_provider` answers the
number from **prompt-registry's** side of the boundary, so a client that wants it has a read that
does not require this module to look into a schema it may not.

## What is being asked

One of three:

1. **Drop the count.** The client already has the registry's filter; the SPA can fetch the count from
   prompt-registry itself, where the read is ordinary rather than forbidden. Cheapest, and it is what
   ships today.
2. **Denormalise a counter** onto `provider.provider_config`, written by prompt-registry. That is a
   write to a table this module owns, by a module that must not have one — a worse trade than the
   count buys.
3. **Let the SPA compose it.** Prope answers `409` and the client asks prompt-registry for the number
   before rendering the message. Same as (1) with the sentence moved into the interface contract.

Reversal cost: low either way. The `details` object gains a key; no schema and no constraint moves.

## What is affected either way

- `src/prope/provider_access/commands.py` — `delete_provider`'s refusal
- `src/prope/errors.py` — `PROVIDER_BOUND_BY_REVISIONS`
- `tests/integration/test_config_delete_refused_while_bound.py` — which asserted the half that was
  testable before wave 3 and said so; the foreign-key half is now reachable
- `docs/modules/provider-access.lock.yml` — **not edited**
