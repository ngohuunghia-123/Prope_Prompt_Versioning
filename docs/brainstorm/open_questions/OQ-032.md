# OQ-032 — the spec names `bigserial`; the build ships `GENERATED ALWAYS AS IDENTITY`, which refuses a caller-supplied `seq`

**Raised by the orchestrator on Phase 4's escalation, 2026-08-10.** `blocks_build: false` — the build
ships either way, and the decision taken is the better of the two. What is owed is the *record* that
lets a person say **no, keep `bigserial` and enforce the rule in the writer instead.**

**Why the orchestrator raised it rather than Phase 4.** Phase 4's allocated range `OQ-027 … OQ-031` was
fully consumed and `OQ-022 … OQ-026` belong to Phase 3. Taking an id from another phase's range is
exactly the collision the range allocation exists to prevent, so the id is allocated here, outside both.
See `.planning/phases/04-schema-privilege-ordering-and-the-closed-vocabulary/deferred-items.md` §1.

## The conflict, stated exactly

Two authorities name the column type, and both name `bigserial`:

- `docs/modules/property-history.lock.yml`, `data.owns` → `history_event`:
  *"`seq` — **bigserial**, monotonic, and the ONLY sort key"*
- `docs/adr/0024-one-event-schema-with-a-registered-payload.md`, Decision block:
  `seq  bigserial, monotonic — the ONLY sort key (A-125)`

Phase 4 plan `04-01` ships `bigint GENERATED ALWAYS AS IDENTITY (CACHE 1)` instead (decision D-53).

## Why this is a behavioural difference and not a spelling difference

This is the part Phase 4's `04-CONTEXT.md` originally got wrong, and the reason the OQ is owed at all.
D-53's first draft withheld the open question on the ground that the deviation *"changes neither the
column type (`bigint` either way) nor the observable behaviour."* **The second half is false.**

`bigserial` is a `DEFAULT` drawing from a sequence. A default is consulted **only when the caller omits
the column** — and `prope_app` holds `INSERT` on `history_event` by design, because appending is the
whole point of the table. So under `bigserial`:

```sql
-- as prope_app, under bigserial: SUCCEEDS SILENTLY, and the row lands with a caller-chosen sort key
INSERT INTO history.history_event (seq, workspace_id, action, ...) VALUES (1, ...);
```

Under `GENERATED ALWAYS AS IDENTITY` the engine raises (SQLSTATE `428C9`), and the only way past it is
`OVERRIDING SYSTEM VALUE` — which PostgreSQL attaches **no privilege requirement** to, which is why
Phase 4 also ships a source gate (`tests/architecture/test_no_overriding_system_value.py`) rather than
resting on the column type alone.

`seq` is the total order PH-04 exists to guarantee and, per A-125, *the only sort key.* A caller able to
choose it can place an event anywhere in the history's order. That is the property the strengthening
protects, and it is observable — asserted by
`tests/security/test_history_seq_cannot_be_supplied.py` (plan `04-03`, Task 2, test 1).

## What a resolver is actually being asked

Not *"is `GENERATED ALWAYS` better?"* — it is, and the build already ships it. The question is which of
these the spec should say:

1. **Amend the two authorities to `GENERATED ALWAYS AS IDENTITY`.** The code and the spec agree; the
   guarantee lives in the engine, which is where this project puts guarantees
   (`.planning/ORCHESTRATION.md` §3, *build database-first*).
2. **Keep `bigserial` and revert the build**, enforcing "no caller-supplied `seq`" in the writer
   instead. Costs a guarantee that currently holds at the privilege level and moves it into
   application code — the trade ADR-0025 and T-006 were both written against.

**Reversibility: one-way once rows exist.** Changing an identity column's generation mode after the
table carries history is a migration against a table `prope_app` cannot `UPDATE`, on a table whose
whole product claim is that it cannot be quietly rewritten.
