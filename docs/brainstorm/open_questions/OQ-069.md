# OQ-069 — The SSRF guard's rejection policy is injectable, and no authority sanctions the seam

**Raised by Phase 12 planning, 2026-08-11.** `blocks_build: false` — the guard ships with the seam and with
a source walk that constrains it. Raised because the seam is a **deliberate, documented bypass of a
CRITICAL mitigation**, it exists for a reason no specification acknowledges, and nothing above the code
level says what is and is not allowed to use it.

## The problem, stated once

The lock file, ADR-0047 and INT-023 all require the same thing, unconditionally: a `base_url` that
resolves into a loopback, link-local or private range is **refused**, at save time and again at dispatch
time, and the dispatch connects to the address that was validated.

Every test of this module drives a stub provider on **`127.0.0.1`**, which is loopback. So does every test
of the dispatch path, the streaming path, the admission gate, the catalogue, the management routes and the
load and chaos suites. The guard is correct and it refuses all of them.

Something has to give, and there are only three shapes:

| Shape | Why it was rejected or chosen |
|---|---|
| **A loopback exemption compiled into `src/`** | Rejected by Phase 11 (D-181): *"an exemption compiled into production code is a bypass that ships."* It is one deleted `if` from being the whole vulnerability |
| **An environment variable that widens the policy** | Rejected by Phase 12 (plan 12-01 Task 4): an operator can set it, nobody reviews it, and it is exactly the shape of every "temporarily disable SSL verification" incident |
| **An injected policy object with a production default** | **Chosen** by Phase 11 (D-181) and tightened by Phase 12 (D-200, D-201). `resolve_and_pin(base_url, *, policy=PRODUCTION_POLICY, resolve=resolve_with_getaddrinfo)`, where `PRODUCTION_POLICY` is `https`-only plus the non-global-range refusal, and the test suite passes a permissive object defined in the test tree |

The chosen shape is the best of the three and it is still a parameter that turns off a CRITICAL
mitigation, present in production code, callable from anywhere in the process.

## Why the resolver is injected too, which widens the seam

Phase 12 additionally injects the **resolver** (D-201), because `.planning/research/PITFALLS.md` gap 2
restates AC-11 as requiring *"a resolver answering public on validation and private immediately after,
then asserting the connection went to the first"* — and that test is unwritable against a real
`getaddrinfo`. So the guard now has two overridable halves rather than one.

This is not a net loss: the alternative was monkeypatching `socket.getaddrinfo` for the whole interpreter,
which would apply to PostgreSQL's connections and the stub server's as well and would prove something
about the interpreter rather than about the guard. But it doubles the surface a specification is silent
about.

## What Phase 12 does about it, which is a compensating control and not an answer

Plan 12-01 Task 4 adds `tests/unit/test_address_policy.py` source assertions over **every** file under
`src/prope/`, discovered by `rglob`:

- no string constant contains `127.0.0.1`, `::1`, `localhost` or `0.0.0.0`;
- `address.py` references neither `os.environ` nor `os.getenv`;
- **no call to `resolve_and_pin` under `src/prope/` passes a `policy=` argument** — production code takes
  the default, and the only overrides in the repository are under `tests/`;
- `PRODUCTION_POLICY.allowed_schemes == frozenset({"https"})`, asserted as a value rather than exercised
  only through an override.

The third is the one that matters, and the file says so: a permissive **default** is caught by asserting
the value, but a permissive **argument at one call site** is not, and one call site is all a server-side
request forgery needs.

The limits are also written into the file. An AST walk sees source, not behaviour. A policy passed through
three layers of indirection, or read from a settings object, or selected by a factory, would defeat it. It
is the third line of defence, behind the behavioural tests and the production default.

## What is being asked

1. **Should the exemption seam be acknowledged in the lock file or in ADR-0047**, with a written rule for
   what may use it? Today the rule exists only as an assertion in a test file, which means the next person
   to need a permissive policy will find the seam before they find the rule.
2. **Is `PRODUCTION_POLICY` the right granularity?** It bundles the scheme allow-list and the address
   predicate into one object precisely so a caller cannot override half and keep the other's default
   (D-201). An alternative is two constants and two parameters, which is more flexible and is the shape
   the argument rejects.
3. **Should the tests use something other than loopback?** A stub reachable on a non-loopback address would
   remove the need for the seam entirely, but it needs a second interface or a container network on a
   Windows developer host and in CI, and it would make every provider-access test depend on that setup.
   Recorded because it is the only shape that closes the question rather than constraining it.
4. **Does `https`-only survive?** Phase 12 adopted it (D-200, `adopted: UNCONFIRMED`) on the ground that
   the private-range refusal already blocks every private `http` target, so the only thing `http` still
   buys is a bearer credential in cleartext on the public internet. If a pilot workspace turns out to need
   a plaintext endpoint, this is the decision to revisit — and revisiting it means telling somebody their
   working configuration is no longer accepted, which is why it was taken before the pilot rather than
   after.

## What is affected either way

- `src/prope/provider_access/address.py` — `AddressPolicy`, `PRODUCTION_POLICY`, `Resolver`,
  `resolve_and_pin`'s signature
- `tests/unit/test_address_policy.py` — the source walk that is the compensating control
- `tests/security/test_base_url_ssrf_guard.py` — the behavioural proof, including the mutating resolver
- The stub-provider module — `PERMISSIVE_POLICY`, the single object every test in the suite installs
- `docs/modules/provider-access.lock.yml`, `docs/adr/0047`, `docs/architecture/interfaces.md` — **none
  edited by Phase 12**
