# OQ-060 — The upstream error-class vocabulary is written twice, with different names and a different count

**Raised by Phase 11 planning, 2026-08-11.** `blocks_build: false` — Phase 11 adopts one of the two sets
with the reasoning written at the code (plan 11-01, D-183). Raised because the two authorities disagree
in a closed vocabulary that two other modules branch on, and because the disagreement removes a name
Phase 11 needs.

## The problem, stated once

`docs/adr/0017-…`'s Decision table declares **eight** classes:

```
credential_rejected, rate_limited, upstream_unavailable, timeout,
model_not_available, content_filtered, invalid_request, provider_contract_violation
```

`docs/architecture/interfaces.md`'s INT-015 declares **seven**:

```
timeout, rate_limited, credential_rejected, upstream_5xx, bad_request, content_filtered, transport
```

Set against set: four names agree. Three are renames — `upstream_unavailable` versus `upstream_5xx`,
`invalid_request` versus `bad_request`, and a `transport` class that ADR-0017 folds into
`upstream_unavailable`. Two ADR-0017 names are **absent** from INT-015 entirely:
`model_not_available` and `provider_contract_violation`.

**The absence matters rather than being cosmetic.** ADR-0017 is the authority the gateway's whole
fallback branch and evaluation's `error`-versus-`fail` rule both hang on, and it is explicit that two of
its classes are *"the ones a reasonable person gets wrong"* — `content_filtered` and `invalid_request`,
neither of which is fallback-eligible. Under INT-015's naming, `invalid_request` is spelled
`bad_request`, and a module built from INT-015 alone would produce a class name the other side's table
has never heard of.

`provider_contract_violation` is the sharper loss. `docs/modules/provider-access.lock.yml`'s
`external_services.admission_rule` and its `alerts` block make *"a registered provider that stops
returning a usage object"* a first-class outcome with its own alert (`ProviderUsageMissing`, *"the alert
ADR-0013 asked this module to own"*), and INT-015's list has **nowhere to put it**. The nearest
alternatives are all lies about what happened: it is not a `timeout`, not a `upstream_5xx`, and not
`bad_request`.

## What Phase 11 adopts (D-183, plan 11-01)

**ADR-0017's eight.** The tiebreak is *not* the precedence order in `.planning/ORCHESTRATION.md` §1,
which puts `interfaces.md` above ADRs. It is that **the lock file — authority 1 — uses ADR-0017's names
throughout its own prose**:

- `failure_modes`, mid-stream row: `error_total{class=upstream_unavailable, streaming=true}`
- `failure_modes`, bad-parameter row: `error_total{class=invalid_request, fallback_eligible=false}`
- `failure_modes`, retired-model row: `prope_provider_access_model_unavailable_total`
- `risks`: `ProviderContractViolation`
- `failure_modes`, revoked-key row: `credential_rejected`

Every one of those is ADR-0017's vocabulary. INT-015's list is the outlier, and it reads like an early
paraphrase written from HTTP statuses — which is precisely the framing ADR-0017 rejected under *"the
gateway classifies from the HTTP status."*

**Phase 10 owns the classification table** (PA-05, AC-5), so Phase 11 consumes whatever Phase 10
shipped and reports a difference as drift rather than widening it at the consumer.

## What is being asked

1. **Which list is the contract?** If it is INT-015's, `provider_contract_violation` needs a home and
   `ProviderUsageMissing` needs a class to fire against. If it is ADR-0017's, INT-015's paragraph is
   wrong in three names and short by two.
2. **Should `transport` survive as its own class?** ADR-0017 folds transport-level failure into
   `upstream_unavailable`, which loses the distinction between *the provider answered badly* and *there
   was no answer at all*. Evaluation's A-053 retries *transport errors only*, so this is the one rename
   that changes a consumer's behaviour rather than only its vocabulary — `retryable` carries the
   decision today, and whether that is sufficient is a real question.
3. **Is `model_not_available` a class or a sub-case of `invalid_request`?** It is fallback-eligible and
   `invalid_request` is not, so they cannot be merged without changing what the gateway does.
4. **Should `interfaces.md`'s INT-015 paragraph be corrected** when this is answered? Phase 11 does not
   edit it. Until it is, the next module built against INT-015 alone will produce class names nothing
   branches on.

## What is affected either way

- `src/prope/provider_access/errors.py` (or wherever Phase 10 put the table) — the enum and the mapping
- `src/prope/provider_access/dispatch.py` — the class chosen for a missing usage object and for a 3xx
- `tests/unit/test_failure_classification_table.py` — AC-5's declared test, Phase 10's
- `tests/contract/test_dispatch_seam_from_both_callers.py` — Phase 11's calling-side assertions
- Phases 16-18 (evaluation) and 19-21 (gateway) — both branch on this taxonomy
- `docs/architecture/interfaces.md` INT-015 — **not edited by Phase 11**
