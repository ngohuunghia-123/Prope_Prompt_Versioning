# OQ-146 — five places the shipped `release-control` module differs from its own spec

**Raised by the release-control build, 2026-08-12.** `blocks_build: false` — the module ships, its
thirteen acceptance criteria have tests, and migration `0010` applies cleanly. Every item below is a
sentence in a locked document that the code could not satisfy as written, or a thing the code ships
that no document lists; each is recorded here rather than resolved by editing the document, per the
project's standing rule.

Ordered by how much a reader would be surprised.

---

## 1. The submit route says "refused". AC-9 says "superseded". Both are in the same lock file.

**Where:** `release-control.lock.yml`, `apis.exposes` — *"POST …/submit — opens a review task;
**refused** if another revision of this prompt is already In review (A-067)"* — against AC-9 —
*"Given revision 5 of a prompt is In review, when the owner submits revision 6 of the same prompt,
then revision 5's review task is marked **superseded**, exactly one open review task remains for that
prompt, and no approval already recorded against revision 5 is altered."*

A build that refuses cannot satisfy AC-9. A build that always supersedes contradicts the API line and
makes the partial unique index unreachable through the front door, which would be a guard nobody could
demonstrate.

**What shipped.** `revision_number` is the discriminator, and both sentences hold on their own terms:

- submitting a **newer** revision supersedes the open task, returns the incumbent to `Draft` with the
  superseding task's id as its `decision_id`, and leaves any approval already recorded against the
  incumbent untouched — AC-9, exactly;
- submitting the **same or an older** revision raises `ReviewAlreadyOpen` →
  `release_review_already_open`, 409 — the API line's refusal.

The reading that makes both true is that A-067's *"a newer submission supersedes"* is the whole rule
and the API line is its abbreviation, written before the criterion was.
`tests/integration/test_one_review_at_a_time.py` asserts both directions.

**What is being asked.** Restate the API line as *"opens a review task; a newer revision supersedes an
open one, an older or equal revision is refused (A-067)"*, or say which of the two sentences loses.

---

## 2. INT-011 registers three reads. Five shipped, and this is the second module to widen it.

**Where:** `docs/architecture/interfaces.md`, INT-011 — `get_revision`, `get_released_revision`,
`get_diff`.

**What shipped.** `prompt_registry.seams.get_prompt` (raised as OQ-145 item 5 by the evaluation build,
and release-control is now its second caller, exactly as that item predicted) and a fifth,
`prompt_registry.seams.list_revision_chain`.

**Why the fifth.** Two screens this module owns cannot be rendered from `get_revision`:

- the **review screen** must diff a candidate against the revision that immediately precedes it when
  nothing is released — there is no released pointer to diff against, and `get_diff` needs two version
  ids, so something must name the predecessor;
- the **release screen** must state how many revisions have been created since an approval was
  recorded (the `failure_modes` approved-then-superseded scenario).

Neither is answerable without reading the chain. The alternative was importing
`prompt_registry.repository`, which is the reach past a module's `seams.py` that
`tests/architecture/test_release_control_depends_on_four_modules.py` exists to refuse — and which
would make INT-011's registered surface a description of nothing.

**What is being asked.** Register `get_prompt` and `list_revision_chain` on INT-011. Both are
annotated as widenings in `src/prope/prompt_registry/seams.py`, pointing here and at OQ-145.

## 3. Fifteen metrics ship beside the eleven declared. One of the four is the lock's own owed counter.

**Where:** `release-control.lock.yml`'s `observability_requirements.metrics` lists eleven, and its
amendment note ends *"A sweep-heartbeat counter is OWED — see the second-to-last risk row."*

**What shipped.** Fifteen. The four:

| Metric | Why |
|---|---|
| `prope_release_sweep_pass_total{pass}` | The owed heartbeat. Two closed label values, fixed in source. Without it, "the sweep ran and found nothing" and "the sweep did not run" are the same graph — which is the failure ADR-0051 exists to prevent, one level up. |
| `prope_release_without_approval_rows` | `ReleaseWithoutApproval` **pages**, and its declared condition is a SQL query, not a series. There was nothing for it to read. |
| `prope_release_unapproved_revision_rows` | Same, for the second Success-metric query. |
| `prope_release_orphaned_pointer_rows` | A released pointer whose revision no longer resolves. Found while writing the reconciliation and kept, because it is the one state that breaks *"every call can be traced back to the exact revision that served it"* without breaking any constraint. |

All three gauges are produced by the same cross-workspace sweep as the two declared ones, carry no
labels, and follow the precedent `prope_evaluation_unpriced_run_total` set in OQ-145 item 7 and
`prope_registry_unapproved_pointer_rows` set before it: **an alert whose condition is a query needs a
series, or it is an alert that can never fire.**

**What is being asked.** Add the four to the declared list.
`tests/architecture/test_release_control_alert_rules.py` already asserts that every metric an alert
names is one this module declares, which is what made the gap visible.

---

## 4. `ck_release_approval_absent_only_for_break_glass` carries a carve-out the Success metric does not mention.

**Where:** the four non-negotiables and `success_metrics` — *a release carries an approval, or it is
break-glass.*

**Why it cannot be written that way.** `release.release` also records **withdrawals**, which move the
pointer to nothing. A withdrawal has no `version_id`, no approval, and is not break-glass — it is the
act of *removing* a release, and requiring an approval on it would mean a prompt could not be pulled
from production without a review cycle, which inverts the control.

**What shipped.**

```sql
CHECK (approval_id IS NOT NULL OR break_glass OR version_id IS NULL)
```

The third disjunct is withdrawals only, and it is not free-floating: `ck_release_withdraw_has_no_target`
asserts `(kind = 'withdraw') = (version_id IS NULL)` in both directions, so no *pointer-moving* row can
reach the carve-out. A release and a restore must still carry an approval or declare break-glass, at
the engine, for owners too —
`tests/integration/test_review_sweep_sees_every_workspace.py` asserts that even `prope_migrate` cannot
`UPDATE break_glass = false` its way into the forbidden state, which is why
`ReleaseWithoutApproval` firing means the constraint itself is gone.

**What is being asked.** State the carve-out in `success_metrics` — *"every release and restore carries
an approval or is break-glass; a withdrawal carries neither and moves the pointer to nothing"* — so a
reader of the constraint does not have to reconstruct why the third disjunct is there.

## 5. A restore and a break-glass release each write two history events, and the log carries a field the lock does not list.

**Where:** `dependencies.to property-history` lists eight actions; `observability_requirements.log_fields`
lists thirteen.

**What shipped, on the events.** The eight, and no ninth — but they are not mutually exclusive. A
restore writes `revision_released` **and** `revision_restored`; a break-glass release writes
`revision_released` **and** `revision_break_glass_released`. The lock reads as a list of eight kinds of
act without saying whether one act may produce two rows.

**Why.** `revision_released` is what makes the trail answer *"what is running, and since when"* for
every pointer move uniformly — a reader who has to know that a restore is spelled differently will
miss one. `revision_restored` and `revision_break_glass_released` are the ones that carry the *reason*
the act was exceptional (`requires_reason` enforces it on the second). Collapsing them would either
lose the uniform pointer trail or lose the mandatory reason.

**What shipped, on the log fields.** Thirteen declared, and `self_approved` is logged beside them —
the boolean ADR-0010 requires be **recorded, never refused**, already a declared metric
(`prope_release_self_approval_total`) and a stored column. Plus the reconciliation sweep's three
counts (`orphaned`, `unapproved`, `without_approval`), which are numbers from a query and the only
thing that sweep's log line says.

All four are in `prope.observability.LOGGABLE_FIELDS`, which is project-wide and is the list the
architecture gate actually enforces. **The free text is still absent, deliberately**: no `comment`, no
reviewer-authored `reason`, no `acknowledgement_reason`. `acknowledged` is the boolean that a reason
was recorded, never the reason — the same distinction `detail_key` draws for property-history.

**What is being asked.** Say in the property-history dependency that a pointer move writes
`revision_released` plus, where applicable, one of the two qualifying events; and add `self_approved`
and the three sweep counts to `log_fields`.

## Reversal cost

Low for items 2, 3 and 5 — each is a document edit against behaviour a test already pins.
**Medium for item 1**, because it is the only one where the two documents disagree with each other
rather than with the code, and the resolution decides whether a second submission is an error a prompt
owner sees or a thing that quietly happens. **Medium for item 4**, because the carve-out is on the
constraint that carries the product's central claim, and a reader who trims it would remove the only
way to unpublish a prompt.
