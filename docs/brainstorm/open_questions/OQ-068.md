# OQ-068 — The KEK readiness mitigation covers `app` and cannot cover `worker`, and one of its two triggers cannot fail at start-up

**Raised by Phase 12 planning, 2026-08-11.** `blocks_build: false` — plan 12-03 implements what is
buildable and writes both gaps at the code. Raised because the lock file's first failure mode is the
module's worst one, its mitigation is stated as a general property of the module, and both halves of that
statement are true of only part of it.

## Clause 1 — `worker` has nothing to withhold

The mitigation reads:

> Fail loudly and specifically rather than degrading into what looks like a provider outage — a distinct
> gauge, a distinct page, and **/readyz withheld so an orchestrator does not route traffic to a process
> that cannot serve any of it.**

That is exactly right for `app`. Plan 12-03 implements it: `/readyz` asks the installed key ring on every
poll, answers `503` with `failed_check: "kek"`, and the compose healthcheck removes the container from the
healthy set.

`worker` runs **batch dispatch** (ADR-0028, ADR-0046) and therefore decrypts credentials, so it has the
same hard dependency on the KEK. It **serves no HTTP** (D-17, derived from ADR-0028), so it has no
`/readyz` and no way to withhold anything.

And the asymmetry is not merely that nobody is told. `worker` does not *receive* routed traffic — it
**pulls** work, through `evaluation.claim_next_run()`. A `worker` with no usable key therefore:

- keeps claiming eval runs;
- fails every case in each of them, each with `kek_unavailable`;
- sets `prope_provider_access_kek_unavailable = 1` in a registry no scraper reaches (`OQ-026`,
  `OQ-065` clause 2);
- and — because `A-057` distinguishes a run **error** from a run **failure** — turns what is really one
  operational fault into a queue of runs that each report errors.

Withholding readiness is the wrong shape for a pulling process anyway. The mechanism that would work is
the claim loop declining to claim, which is a behaviour change to **evaluation's** claim path, owned by
Phase 16 and by a decision nobody has taken. Phase 12 does not invent one: plan 12-03 Task 4 writes the
asymmetry into `src/prope/worker.py` with its consequence and cites this file.

## Clause 2 — a `kek_version` a row names cannot be detected at start-up

The same failure mode's RESOLVED paragraph says:

> The realistic trigger is now a deploy that loses or truncates `.env`, or **a `kek_version` in a row with
> no matching entry present (A-135)** — **both of which fail at start-up rather than at first dispatch,
> because the KEK is read once when settings load.**

The first trigger does fail at start-up: the settings load, the slot is empty, and the ring cannot produce
a wrapping key. Plan 12-03 evaluates exactly that in both lifespans.

The second cannot. `kek_version` is a **column on `provider.credential`**, and A-135's rule is that
`kek_version` *selects* which key unwraps that row's data key. A row wrapped under V3 in a deployment whose
`.env` now carries only V1 and V2 is discoverable **only by reading rows** — and reading them at start-up
would mean scanning every credential in every workspace at boot, across the RLS boundary, in a process
that has not finished starting. Nothing in the lock file, in ADR-0014 or in ADR-0032 asks for that, and it
would be a poor thing to ask for.

So the second trigger fails at **first use of the affected row**: plan 12-03 asserts that startup is clean,
`/readyz` answers `200`, and the dispatch for that particular configuration fails with `kek_unavailable`.
The code is right and the prose is inaccurate.

The practical consequence is worth stating: **a partial KEK loss is invisible to readiness.** A deployment
that rolls back `.env` from three keys to two is fully ready, pages nobody, and fails exactly those
configurations whose credentials were re-wrapped under the key that went away — which, after an AC-13
re-wrap (PITFALLS gap 1), is all of them.

## What is being asked

1. **Should `worker` gain a readiness surface**, or should the claim loop check the key ring before
   claiming? The second is cheaper and belongs to Phase 16; the first is an HTTP server in `worker`, which
   D-17 currently forbids and which `OQ-026` would also be answered by.
2. **Should the failure mode's prose be corrected** so that the second trigger is described as failing at
   first use? It is a one-sentence edit to a lock file that no sub-agent in this orchestration may make.
3. **Should readiness cover the stored rows at all** — for example, by having the re-wrap operation (AC-13)
   record the lowest `kek_version` still in use, so `/readyz` can compare one number against the ring
   without scanning anything? That is a small schema or settings addition and it would make clause 2's
   partial-loss case visible.
4. **What should `/readyz` say when the ring is usable but rows are not?** Today, `200`. Under question 3
   it could be `503` with a third `failed_check`. Either is defensible; the current answer is the one that
   requires no scan.

## What is affected either way

- `src/prope/app.py` — `readyz`, which plan 12-03 already changed from *the database alone* to *database
  plus KEK* (D-208)
- `src/prope/worker.py` — the startup evaluation and the written asymmetry
- `src/prope/provider_access/keyring.py` — `wrapping_key_available()`, and anything question 3 would add
- Phases 16-18 (evaluation) — the claim loop, if question 1 is answered that way
- `deploy/prometheus/rules/provider_access.rules.yml` — `ProviderKekUnavailable`'s coverage note
- `docs/modules/provider-access.lock.yml` — `failure_modes` row 1, **not edited by Phase 12**
