# OQ-083 — `search_text` never leaves through the API, and nothing says anything about the two doors it does leave through

**Raised by Phase 15 planning, 2026-08-11.** `blocks_build: false` — plan 15-02 asserts the API claim in
full and states its own boundary. Raised because the claim is written as though it were about the column
and it is only about one of the column's three exits.

## The problem, stated once

`prompt-registry.lock.yml` makes two statements about `search_text` and they are not the same size:

> `prompt_property.search_text` is a SECOND COPY OF THE PROMPT BODY and must never appear in an **API
> response**.

> `search_text` **inherits every rule the body already carries.** A-046's never-logged rule and OQ-006's
> classification question now apply to two columns, not one.

The first is a scoped, checkable claim and phase 15 discharges it (owed AC-7: a whole-response scan over
every list and detail endpoint). The second is the larger one, and taken literally it reaches two places
nothing in the specification addresses:

1. **`prope_report` reads it.** ADR-0037 issues a `BYPASSRLS` full-read role to a person for reporting.
   Phase 13's plan 13-06 asserts that role can `SELECT` from both `registry` tables across every
   workspace — correctly, because `provider.credential` is the only table in Prope it may not read
   (phase 12's D-166). So the one column that concatenates **every prompt's latest body plus every
   change summary into a single greppable document, per property** is available to that credential in one
   `SELECT`. Reading the bodies themselves requires a join and knowing which revision is latest; reading
   `search_text` requires neither. That is a meaningful difference in how easy the asset is to take,
   and no authority weighs it.

2. **The nightly dump carries it twice.** ADR-0036 takes a logical `pg_dump` with exactly two table-data
   exclusions — `ledger.call_body` (ADR-0039) and `access.session` (ADR-0044). `registry.revision` and
   `registry.prompt_property` are both in the dump, which is correct and deliberate: A-136 exists because
   *"a prompt body is not derivable, not re-issuable, and held nowhere else."* The consequence nobody
   wrote down is that the dump therefore carries **every latest body twice** — once in
   `revision.body`, once folded into `prompt_property.search_text` — and the copy is diacritic- and
   case-folded (A-150), which makes it *easier* to grep than the original, on a file ADR-0036 copies to a
   second machine that A-131 says may not exist yet.

Neither is a defect in the design. Both are consequences of two correct decisions meeting, and the
sentence *"inherits every rule the body already carries"* reads as though it had already covered them.

## The candidates

**A — say the claim is API-scoped, and record the other two exits as accepted** (adopted by plan 15-02's
docstring). `search_text` is derived data with a trigger that rebuilds it; it is in the dump because
excluding it would produce a restored database whose search index is empty until somebody backfills, and
it is readable by `prope_report` because that role reads bodies anyway. Cost: nothing changes, and the
sentence in the lock file keeps promising slightly more than it delivers.

**B — exclude `registry.prompt_property.search_text` from the dump.** `pg_dump` has no column-level
exclusion, so this means `--exclude-table-data=registry.prompt_property` (which loses the whole property
row — unacceptable) or a post-restore `UPDATE … SET search_text = registry.compose_search_text(...)`
backfill as a documented restore step. Cost: a restore procedure gains a step that, if skipped, produces a
register that is silently un-searchable — the exact failure shape ADR-0048's trigger exists to prevent,
reintroduced at the one moment nobody is watching.

**C — revoke `SELECT (search_text)` from `prope_report`.** Column-level revoke is available and phase
13's grant matrix already works at column granularity for `UPDATE`. Cost: `SELECT *` as `prope_report`
starts failing, which is the ergonomics the role exists for; and the role can still reconstruct the same
text from `revision.body` with one join, so it buys inconvenience rather than confidentiality.

## What phase 15 shipped

**Option A.** Plan 15-02's module docstring states the boundary of what the scan proves — *every response
body of every registry read route, over serialized bytes* — and names the two exits it does not cover,
with this question cited by id. Plan 15-04 re-asserts phase 13's finding that `prope_report` holds no
write privilege on either table, which is the only half of that door this milestone can close.

**Why it is worth a question rather than a comment:** OQ-006 is the open question that governs prompt
bodies, it *blocks the pilot*, and its answer will be a data-classification baseline. When that answer
arrives, this is the column it has to be re-read against — and if it is not written down now, the
re-reading will be done against `revision.body` alone, which is the copy that is harder to take.

## What the answer changes

Option A: one clause in `security_requirements` scoping the *"must never appear"* sentence to the API and
naming the two other exits. Option B: a documented restore step and a backfill statement, plus a
`test_plan` clause asserting the restore leaves search working. Option C: one `REVOKE` in a migration and
a re-read of ADR-0037's *"full-read"* wording.
