# OQ-065 — Two of provider-access's seven alerts cannot fire against what is actually scrapable

**Raised by Phase 12 planning, 2026-08-11.** `blocks_build: false` — the metrics and the rules file ship
either way, and plan 12-04 writes both unfireable rules **with a comment at the rule saying it cannot
fire**, which is the same posture `deploy/prometheus/rules/call_ledger.rules.yml` already takes for three
of its own. Raised because an alert that is true on paper is the failure `OQ-026` exists to name, and
because this module's alerts are the ones that page.

This is the **same shape as `OQ-026`, one module later**, plus one new clause that is not about process
topology at all. It is a separate file rather than an edit to `OQ-026` because `docs/` is read-only under
`.planning/ORCHESTRATION.md` §1 with exactly one exception — **creating** an `OQ`.

## Clause 1 — `ProviderBatchStarved` reads a series no scraper can reach

`prometheus_client`'s registry is per process. Prope runs two, and `worker` serves no HTTP (D-17, derived
from ADR-0028). ADR-0046 then made **the processes the priority classes**: interactive dispatch runs in
`app`, batch dispatch runs in `worker`.

So every batch-side series exists only in `worker`:

- `prope_provider_access_shed_total{priority="batch"}`
- `prope_provider_access_admission_wait_seconds{priority="batch"}`
- `prope_provider_access_dispatch_total{priority="batch"}` and
  `dispatch_duration_seconds{priority="batch"}` and `dispatch_overhead_seconds` for batch
- every `error_total` produced by a batch dispatch

`ProviderBatchStarved` — *"shed_total{priority=batch} sustained for 30 min"* — reads the first of those.
A Prometheus pointed at `app:8000/metrics` sees none of them, so the alert cannot fire, and the workspace
whose reviews never finish does not find out why. The lock file's own justification for the alert is
exactly that: *"a workspace whose reviews never finish deserves to know why."*

## Clause 2 — `ProviderKekUnavailable` covers half the deployment

`prope_provider_access_kek_unavailable` is set in **both** processes: plan 12-03 evaluates the key ring at
startup in `app` and in `worker`, because both decrypt credentials. Only `app`'s value is scrapable.

The consequence is narrower than clause 1's and worse in kind. A `worker` that lost the key keeps claiming
eval runs through `evaluation.claim_next_run()` and fails every case in each, while `app` — which still has
the key, because the two read the same `.env` and a partial loss is unusual but a rolled-back deploy or a
mismatched `env_file:` is not — answers `/readyz` 200 and pages nobody. See `OQ-068` clause 1 for the
readiness half of the same asymmetry.

## Clause 3 — `ProviderVerificationFailing` cannot be expressed against its own metric's labels

Not a topology problem. The alert is declared as:

> ProviderVerificationFailing — `verification_total{result=fail}` **spike on a previously passing
> configuration**.

`prope_provider_access_verification_total`'s declared labels, in the same block of the same file, are
`result = pass | fail` and `reason`. There is **no configuration dimension to group by**, so no PromQL
expression over this metric can distinguish:

- a configuration that passed yesterday and fails today — the case the alert is for; from
- an admin registering a new provider and getting the base URL wrong twice — an ordinary event that
  should page nobody.

Plan 12-04 writes the rule in the form that **is** expressible (a rate of `verification_total{result="fail"}`
over a window) with a comment at the rule saying what it cannot distinguish. That is a real alert with a
false-positive mode rather than a fictional one, but it is not what the lock file declares.

Note that the fix — adding `provider_config_id` to `verification_total` — collides with ADR-0030's
bounded-cardinality rule and with plan 12-04's D-213, which grants exactly one identifier-label exemption
in this module (`credential_rejected_total`, because `ProviderCredentialRejected` alerts *"for one
configuration"*). A second exemption is defensible on the same grounds; it is a decision, not an omission.

## What is being asked

1. **Should `worker` expose `/metrics`?** `OQ-026` lists four candidate answers for call-ledger's twelve
   metrics and none was chosen. The answer is the same answer for both modules, and provider-access raises
   the stakes: two of its alerts page.
2. **If not, should `ProviderBatchStarved` and the `worker` half of `ProviderKekUnavailable` be withdrawn
   from the lock file** rather than shipped as rules that cannot fire? Writing them with a comment is
   Phase 12's choice and it is the least-bad of the available ones, not a resolution.
3. **Should `verification_total` gain a `provider_config_id` label under a second declared exemption**, so
   `ProviderVerificationFailing` can be written as declared? Or should the alert be restated to what a
   two-label metric can express?
4. **Is a per-configuration verification signal better served by the log line?** `log_fields` already
   carries `provider_config_id`, and phase 9 made exactly this call for `key_scope_refusal_total`.

## What is affected either way

- `deploy/prometheus/rules/provider_access.rules.yml` — two rules carry a cannot-fire comment (Phase 12,
  plan 12-04)
- `src/prope/provider_access/observability.py` — `verification_total`'s label set
- `tests/broker/test_publish_confirm_failures.py` — `LABEL_EXEMPTIONS`, if a second exemption is granted
- `src/prope/worker.py` — if `worker` gains an HTTP surface, this is where it lands, and it is a decision
  ADR-0028 and D-17 currently forbid
- Phases 16-18 (evaluation) — clause 2's consequence is theirs: a keyless `worker` claiming runs
- `docs/modules/provider-access.lock.yml`, `docs/adr/0030`, `docs/adr/0046` — **none edited by Phase 12**
