# OQ-143 — A-086 wants a call record for every authenticated refusal; the database refuses half of them

**Raised by the gateway build, 2026-08-12.** `blocks_build: false` — the build honours the
constraint and counts what it cannot record. This asks which of the two should move.

## The contradiction

`A-086` is unambiguous about the list:

> Once a consumer key has been authenticated, every call writes a call record — **including the
> refusals: unknown model name, no release, key not permitted, pin not Approved**, caller-supplied
> system message, missing variable. Their `outcome` is `caller_error` and their token count and cost
> are zero.

`alembic/versions/0002_call_record.py` is equally unambiguous, and its comment names the success
metric it is protecting:

```sql
-- "a database constraint here, not a hope" (call-ledger.lock.yml:162-164).
-- The "100% of gateway calls record a version ID" success metric.
CONSTRAINT ck_call_record_gateway_calls_carry_version_id
    CHECK (source <> 'gateway' OR version_id IS NOT NULL),
```

The first four refusals A-086 lists happen **before or during resolution**, so there is no revision
to name. The last two happen **after** it, so there is. The two rules agree on half the list and
contradict each other on the other half.

## What shipped, and why this way round

The constraint wins, and the refusals split:

| Refusal | Record | Counted as |
|---|---|---|
| caller-supplied system message | **yes**, `caller_error` | `prope_gateway_rejected_system_message_total` |
| missing `{{variable}}` | **yes**, `caller_error` | — |
| composed message set over 256 KiB | **yes**, `caller_error` | `prope_gateway_oversize_request_total` |
| unknown model name | no | `resolve_miss_total{reason="unknown_model"}` |
| no release | no | `resolve_miss_total{reason="no_release"}` |
| key not permitted | no | `resolve_miss_total{reason="not_permitted"}` |
| pin not Approved | no | `resolve_miss_total{reason="pin_not_approved"}` |
| at the in-flight cap (A-143) | no | `admission_refused_total{key_id_bucket}` |
| failed authentication | no, **by A-086 itself** | `auth_failure_total` |

Three reasons for this direction rather than the other:

1. **A record the writer must reject is worse than no record.** `enqueue` accepts it, the publisher
   publishes it, the drain fails the insert, and it dead-letters — so the outcome is the same
   absence plus a DLQ entry and an alert (`LedgerDeadLetters` is non-zero-is-an-alert). Nothing is
   gained and something is broken.
2. **`ck_call_record_gateway_calls_carry_version_id` is the success metric.** It is one of the
   constraints this project deliberately put in the database rather than in application code, and
   weakening it to admit refusals would make *"100% of calls record a version ID"* a statement about
   a column that is sometimes NULL.
3. **A-086's own reasoning already excludes one case on exactly these grounds.** It excludes
   authentication failures because *"there is no authenticated workspace to attribute the record
   to"*. A refusal before resolution has an attributable workspace and **no attributable revision**,
   which is the same shape of argument one field over.

## What is lost

A-086's stated benefit, for four refusal kinds:

> *"A refused call is the one a developer needs to see, and 'my requests are not arriving' with an
> empty record is the hardest support conversation there is."*

That is a real cost and it is not mitigated by the metrics: `resolve_miss_total` carries a reason and
**no key id and no model name** (ADR-0030 bounds label cardinality), so an operator can see *four
scope refusals happened this hour* and cannot see *whose* or *for what*. The support conversation
A-086 is about therefore gets harder rather than easier, for precisely the cases a newly-integrating
consumer hits most.

## What is being asked

Three options, in increasing cost:

1. **Amend A-086** to say that a refusal with no resolved revision writes no record, and that
   `resolve_miss_total` is the trace. Cheapest, and it makes the built behaviour the intended one.
2. **Make the constraint conditional on the outcome** — `source <> 'gateway' OR outcome =
   'caller_error' OR version_id IS NOT NULL`. Keeps every served call covered and admits refusals.
   Costs a migration and, more importantly, weakens a constraint the project chose to state
   absolutely; *"100% of calls"* would need re-reading as *"100% of served calls"* everywhere it
   appears.
3. **A separate refusal record** — a `gateway_refusal` table, or `source = 'gateway_refused'` with
   its own constraints. Answers the support question fully and adds a table to a module whose whole
   design is one table, one price path, one spend total (A-098).

Reversal cost of what shipped: low for option 1, one migration for option 2.

## What is affected either way

- `src/prope/gateway/routes.py` — where the refusals are raised
- `src/prope/gateway/records.py` — `record_call` refuses a draft with no `version_id` and counts it
- `tests/security/test_gateway_key_scope.py` — asserts the absence, with this OQ named
- `docs/brainstorm/assumptions/A-086.md` — **not edited**
