# OQ-024 — Two `test_plan` entries describe test machinery ADR-0041 deleted

**Raised by Phase 3 plan 03-01 while writing the broker-outage chaos tests, 2026-08-10.** The code
ships either way — `blocks_build: false` — and the substitution is declared here rather than absorbed
into the spec, per `.planning/BSP-LINK.md` and `.planning/ORCHESTRATION.md` §5.

`.planning/research/PITFALLS.md` §2 already records that call-ledger's AC-1 and AC-2 are stated
against an in-process queue and a spill file *"neither of which exists"*, and instructs planning
against the restated ROADMAP form. **The same amendment did not reach `test_plan`**, and two of its
entries are still written against the deleted machinery.

## Clause 1 — the chaos entry asks for a spill volume that does not exist

`test_plan.chaos`, clause 2:

> fill the spill volume and assert the page fires and readiness is withheld before any metadata is
> dropped

There is no spill volume. ADR-0041 replaced the spill file with an inline direct write to PostgreSQL,
and the ADR's own rejection of the spill file is the argument D-27 reuses: *the mechanism most likely
to be wrong is the one exercised least, and this one only ever runs during an incident.*

**And the sharper half: this clause contradicts the amended `/readyz` clause in the same file.** D-16
makes readiness **the database alone**, and `interfaces.md` INT-030 states that a broker-side failure
is **degraded-and-counted, never un-readiness**. So "readiness is withheld" is not a behaviour any
implementation of the amended design may have — a phase that satisfied this clause literally would
have to break the readiness rule to do it.

**What this phase built instead:** two provocations in
`tests/broker/test_broker_unreachable_fallback.py`, neither of which touches the session-scoped
`rabbitmq_container`.

1. **A closed channel under a running publisher** — 1,000 records handed to `enqueue()`, all 1,000
   asserted in `ledger.call_record` through `migrate_engine`, every one carrying a non-null
   `version_id`, zero `ledger.call_body` rows, `body_dropped_total{reason="fallback"}` and
   `fallback_direct_write_total` each moved by exactly 1,000, and `metadata_dropped_total` moved by
   **zero**.
2. **A closed port at the composition root** — `_start_publisher` pointed at a port nothing is
   listening on, which is the broker-was-never-there case and the one that would fail if the
   composition returned with no task.

The page that clause 2 wanted still exists and still fires on the event that matters:
`LedgerMetadataDropped` on `metadata_dropped_total > 0`, which after ADR-0041 means **both** stores
were unavailable. The chaos test that provokes it is the fallback-refused case, asserted in
`tests/broker/test_publish_confirm_failures.py`.

## Clause 2 — the unit entry asks for queue accounting and a two-lane drop order

`test_plan.unit` names *"queue accounting and the two-lane drop order"*. Both belonged to the
in-process `metadata` / `body` lanes. There is one buffer now (`HANDOFF_MAXSIZE`, 512 records, whole
records) and one broker queue, and a body is dropped by a **byte cap in the producer** or by the
**fallback being metadata-only** — neither of which is an ordering between two lanes.

**What this phase built instead:** the cap's boundary asserted from both sides (one byte over drops
and counts; exactly at the cap keeps the body and stores the size this module computed), the record
asserted to survive its body in every case, and the buffer's own bound asserted unchanged in
`tests/broker/test_enqueue_reaches_a_committed_row.py`.

## Why this does not block the build

`blocks_build: false`. Both clauses are replaced by tests that assert the amended design's real
properties, and every substitution is named above. What the answer settles is whether `test_plan`
should be re-amended to match the ADR the metric block was already amended for — and, for clause 1,
which of the two contradictory statements in the same file about readiness is the one that stands.
