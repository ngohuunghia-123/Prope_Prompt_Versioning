# OQ-064 — Batch dispatches must be counted when shed, and must never be failed by production load

**Raised by Phase 11 planning, 2026-08-11.** `blocks_build: false` — Phase 11 adopts a shape under which
all three authorities hold, and writes the reasoning at the gate (plan 11-04, D-191). Raised because the
three read as a contradiction at first pass, and because the resolution changes what an alert means.

## The problem, stated once

Three statements about the same counter:

- **ROADMAP Phase 11, SC2**: *"With batch dispatches saturating a configuration, an arriving interactive
  dispatch is admitted without waiting, and **every unadmitted batch dispatch is counted in
  `shed_total{priority=batch}`**."* — batch must be refusable, and refusals must be counted.
- **INT-015, Admission**: *"batch yields to interactive on the shared credential, bounded at
  `batch_concurrency = 8` per provider config. **A run can be slowed — never failed — by production
  load.**"* — batch must not be refused because production is busy.
- **ADR-0046**: `app` holds only interactive dispatch and `worker` only batch, so *"the processes are now
  the priority classes"* — batch and interactive **cannot contend at all**, and *"batch yields to
  interactive"* stops being something a mechanism enforces.

Read together: SC2 describes batch losing slots to interactive, which ADR-0046 made impossible. If batch
simply waits on its own semaphore, `shed_total{priority=batch}` is permanently zero and SC2's second
clause is unassertable. If batch fails fast the way interactive does, INT-015's promise to evaluation
breaks and A-057 turns every shed into a run **error** rather than a slower result.

`.planning/research/PITFALLS.md` gap 2 already restates AC-6 for the columns ADR-0046 deleted — *"each
cap holds within its own process, their sum is never exceeded upstream, and a saturated `worker` does not
affect `app`'s admission latency"* — but it does not say what shedding means afterwards.

## What Phase 11 adopts (D-191, plan 11-04)

**Two behaviours, selected by the gate's fixed priority class.**

- **Interactive fails fast.** A non-blocking acquire; no slot means an immediate `DispatchError`
  (`rate_limited`, `origin=prope`, `fallback_eligible=true`, `retryable=true`) and
  `shed_total{priority="interactive", reason="no_slot"}`. This is ADR-0016's own sentence: *"on a path
  with a 50 ms budget, a queue is a slower error, and the gateway has a fallback answer to serve."*
- **Batch waits, bounded by its own `deadline_ms`.** Admitted within the deadline means the run was
  **slowed**, which is INT-015's promise kept. Not admitted by the deadline means
  `shed_total{priority="batch", reason="deadline"}` and the same `rate_limited{origin=prope}` value, with
  `retryable=true` so evaluation's own loop (A-053) decides.

Under that shape all three statements hold: batch is **never shed because of production load** — there is
no interactive dispatch in `worker` to lose a slot to — only because of **its own cap relative to its own
deadline**, which is exactly what ADR-0046's Consequences say the alert now means:
*"`ProviderBatchStarved` correspondingly means the batch cap is too low, and nothing else."*

## What is being asked

1. **Is the deadline the right shed trigger for batch?** It makes `shed_total{priority=batch}` a function
   of the caller's `deadline_ms` as much as of the cap, so evaluation's choice of deadline moves an alert
   that is nominally about provider-access's configuration.
2. **Should `ProviderBatchStarved`'s wording change?** The lock file describes it as *"Eval runs are being
   held back by live traffic. This is the designed direction of the trade (ADR-0016)"* — which is the
   pre-ADR-0046 meaning. Under per-process caps, live traffic cannot hold back an eval run at all, and
   the alert now means only that `batch_concurrency` is too low for the offered batch load.
3. **Should SC2's first clause be restated in the ROADMAP?** *"With batch dispatches saturating a
   configuration, an arriving interactive dispatch is admitted without waiting"* describes a scenario that
   cannot occur in one process. It is true, structurally, and a verifier reading it literally will look
   for a mechanism that does not exist.
4. **What should a batch shed's `fallback_eligible` be?** Phase 11 sets it `true` for consistency with
   the interactive shed, and A-034 means evaluation ignores it. A `false` would be equally defensible and
   would make the field mean *"a caller could truthfully serve a fallback for this"* rather than *"this
   class is fallback-eligible in general."*

- `src/prope/provider_access/dispatch.py` — the `DispatchError` constructed from a shed
- `tests/load/test_batch_yields_to_interactive.py` — AC-6's restated form, including *offered = completed
