# OQ-043 — `access_level` is a parameter of every permission decision in Prope and its value set is declared nowhere

**Raised by Phase 7 planning, 2026-08-11.** `blocks_build: false` — Phase 7 adopts a two-value set and
records it here. Raised because this is the field that decides BR-01, the non-negotiable
*prompts are private by default*, and it is the only input to `may()` whose vocabulary no document
states.

## What is written, and what is not

`access_level` appears in five places and is enumerated in none of them:

- ADR-0020's signature — `subject = {type, id, workspace_id, owner_id?, access_level?}`
- `docs/modules/prompt-registry.lock.yml` `prompt_property.fields` — the column, in a list of column
  names with no types
- the same file's event list — `access_level_changed`, so the value **moves**, so there are at least two
- `docs/modules/access-control.lock.yml` `apis.exposes` — the signature again
- `00_context.md` constraints — *"Prompts are private by default; no auto-publish, auto-share, or
  auto-release"*, which fixes the **default** and says nothing about what else exists

By contrast every other value vocabulary this decision touches **is** enumerated: `prompt_grant.level`
is `viewer | editor` (A-112), the role set is `Owner, Reviewer, Viewer, Admin` (A-007), and the action
list is A-115's twenty-five.

## Why access-control cannot resolve it by reading

ADR-0020 forbids this module from reading `prompt_property` at all — that forbidden edge is the whole
reason `access_level` is a *parameter*. So access-control must **interpret** a value it can never
observe, and the interpretation is what turns a private prompt into a visible one. Getting it wrong in
the permissive direction is the failure mode `docs/modules/prompt-registry.lock.yml` calls the top
adoption barrier in the survey.

## What Phase 7 adopts

`AccessLevel` is a two-member `StrEnum` in `prope.access_control.domain`:

- **`private`** — the default. Visibility comes only from ownership (`subject.owner_id == actor.id`)
  or from a `prompt_grant` row naming the actor.
- **`workspace`** — every active member of the subject's workspace holds the *viewer* action set on it.

and, load-bearing, **an `access_level` value outside that set is treated as `private`** rather than
raised on, so an unrecognised level fails in the closed direction. That mirrors A-115's rule for an
unrecognised action one level up, and it is asserted rather than intended.

## What is being asked

Whether `private | workspace` is the set, and specifically:

1. Is there a third level — `public`, or a per-namespace one — that the pilot needs?
2. Does `workspace` confer the **viewer** set (read the prompt, its revisions, its diff, its activity
   and its eval runs — A-112's wording) or something narrower or wider?
3. Does an unrecognised value belong in the closed direction (Phase 7's adoption) or should it raise,
   which under INT-001's *"raises, and no caller catches it"* rule is a 5xx on every request naming
   that prompt?

## What is affected either way

- `src/prope/access_control/domain.py` and `permissions.py` (one enum, one predicate)
- Phase 13's `prompt_property.access_level` column — its type, its CHECK and its default
- Phase 8's `visible_subject_filter`, whose `mode: all` branch is exactly the `workspace` case
- `docs/modules/prompt-registry.lock.yml`, `docs/adr/0020-…` — neither edited by Phase 7
