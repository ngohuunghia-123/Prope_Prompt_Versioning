# OQ-048 — `visible_subject_filter` is required to return the prompts an actor owns, and is forbidden from reading the only table that records ownership.

**Raised by Phase 8 planning, 2026-08-11.** Phase 8 owns AC-09 and ROADMAP SC1, so this is the phase
that has to produce the function and the test.

## The conflict, stated exactly

AC-9 (`access-control.lock.yml`):

> Given an actor whose visibility comes entirely from grants in a workspace of 1,000 prompts, when
> `visible_subject_filter` is called, then it returns **mode=ids listing exactly the granted and owned
> prompts**, and prompt-registry's list endpoint returns exactly that set.

`data.reads` in the same file:

> `[]` — Nothing outside its own tables. It cannot read `prompt_property`, `revision`, `release`,
> `eval_suite`, or `provider_config` — **which is why `may()` takes the subject's `owner_id` and
> `access_level` as parameters (ADR-0020). This is the module's central design constraint and the
> reason its dependency list has one entry.**

`prompt_property.owner_id` is the only record of who owns a prompt. Access-control owns
`prompt_grant`, which records grantees and not owners. INT-002's request carries *"the actor, and a
subject type"* and nothing else — no owned-id list, no ownership predicate. So the function is asked
for a set it has no input capable of producing, by the same document that forbids it the input.

**AC-9's own wording shows the seam being worked around rather than closed.** The scenario is
carefully specified as an actor *"whose visibility comes entirely from grants"* — i.e. one who owns
nothing — which is precisely the case in which the impossible half of the requirement is vacuous. The
`then` clause was not updated to match.

## Why this is a real conflict and not an implementation detail

It decides the shape of a seam **five modules and two later phases are written against**. If the
returned `ids` mean *everything the actor may see*, prompt-registry's list query is
`WHERE id = ANY(:ids)` and access-control must somehow learn ownership. If they mean *the
grant-derived contribution*, the query is `WHERE owner_id = :actor OR id = ANY(:ids)` and the
registry keeps a predicate that access-control never sees — which is ADR-0020's shape exactly, one
level up from `may()`.

The failure mode of guessing wrong is the one PITFALLS names as the top adoption barrier: *"a new
list, search, or export query path added without the visibility filter — a private prompt appears to
someone with no grant."* A filter whose contract is ambiguous is a filter two implementers combine
differently.

## What Phase 8 adopted, and why

Phase 8 adopts (D-122): **the returned set is the grant-derived contribution, and ownership stays the
caller's own predicate**, stated in the function's contract in those words.

- `mode: all` — the actor holds a role binding conferring the subject type's read action at workspace
  scope. Everything in the workspace is visible; the caller adds nothing.
- `mode: ids` — visibility comes from `prompt_grant` rows; `ids` are exactly those `prompt_id`
  values. **The caller ORs its own `owner_id = :actor` predicate**, because it has already read or is
  about to read the column that answers it, which is ADR-0020's rule applied to a set instead of to a
  row.
- `mode: none` — no role and no grant confers visibility. **This is not "the actor sees nothing"**:
  they still see what they own. The docstring says so at the constant, because `none` reading as
  *empty list* is the misinterpretation that would hide a person's own prompts from them.

**How Phase 8 tests it without a prompt table.** `prompt_registry` does not exist until Phase 13, so
AC-9's second clause — *"prompt-registry's list endpoint returns exactly that set"* — cannot run here
and is routed to Phase 15 (PR-03, permission filtering in the repository layer). What Phase 8 asserts
is the lock file's own `test_plan.integration` clause, which is the stronger half and is available
today: **`visible_subject_filter`'s id list compared row-for-row against calling `may()` on every one
of 1,000 synthetic subjects**, with the subjects' `owner_id` and `access_level` supplied by the test
in the shape ADR-0020 requires of a real caller. If the set form and the per-row form disagree on any
of the 1,000, the test fails and names the id.

## The shape of the possible answers

1. **Grant-derived contribution, ownership stays the caller's** — what Phase 8 adopted. Keeps
   `data.reads: []` true and keeps the dependency list at one entry. Costs: AC-9's `then` clause is
   literally false as written and must be amended; two callers could combine the predicate
   differently, which is what PR-03's repository-layer rule and its `unfiltered_query_total` tripwire
   exist to catch.
2. **Add an ownership input to the signature** — `visible_subject_filter(actor, subject_type, *,
   owned_ids)`. Literal-AC-9-compliant and ADR-0020-consistent, but a list endpoint has not read any
   rows yet, so the caller would have to run an ownership query first purely to feed it back in — two
   round trips to produce one `WHERE` clause.
3. **Let access-control read `prompt_property.owner_id`.** Satisfies AC-9 exactly and breaks the
   module's central design constraint, the forbidden edge, and ADR-0020 in one move. Recorded for
   completeness; it should not be chosen.

**A recommendation:** option 1, with AC-9's `then` clause amended to name the grant-derived set and
the caller's ownership predicate separately.
