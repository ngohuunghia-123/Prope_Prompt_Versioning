# OQ-047 — AC-12 requires the grant events to carry a `level`, and the seeded registry forbids them any `details` key at all.

**Raised by Phase 8 planning, 2026-08-11.** Phase 8 owns AC-12 and its ROADMAP restatement (*"a grant
and its `access_granted` event cannot exist without each other; the same holds for revocation"*), so
this is the phase where the event's payload has to be decided rather than assumed.

## The conflict, stated exactly

`access-control.lock.yml` AC-12:

> Given a grant is created and then revoked, when property history is read for that prompt, then an
> `access_granted` and an `access_revoked` event exist with **actor, grantee, level, and timestamp**,
> and neither can be written without its transaction having committed the grant row.

`history.history_event`'s columns give three of those four for free — `actor_id` is the actor,
`occurred_at` is the timestamp, `scope_prompt_id` is the prompt. **Neither `grantee` nor `level` is a
column.** Both would have to be `details` keys, and ADR-0024 makes `details` an allow-list held per
action in `history.history_action_registry.detail_keys`: a key outside it raises `unknown_detail_key`
and aborts the caller's transaction.

Phase 4's seed gives `access_granted` and `access_revoked` **empty** `detail_keys` — and
`tests/integration/test_history_schema_ships_its_guarantees.py` asserts that every action except
`revision_released` (three keys) and `role_assigned` (two) carries an empty array. So as seeded, an
`access_granted` event carrying `{"level": "viewer"}` is refused, in the same transaction as the
grant, at the moment BR-01's private-by-default grant is written.

## Why the obvious workarounds do not work

**"Put the grantee in `target_id` and read the level from `prompt_grant`."** `target_id` can carry the
grantee — but the level cannot be recovered from the table, because **revocation deletes the grant
row** (`DELETE /api/v1/prompts/{id}/grants/{user_id}`, and the tombstone deletes *"every prompt_grant
naming them as grantee"*). After a revoke, the level at which access was held exists nowhere. On the
one table in Prope that is never deleted from, that is the fact most worth having and the one this
design loses.

**"Use `target_id` for the grant row's id."** `prompt_grant`'s declared fields are `workspace_id`,
`prompt_id`, `grantee_user_id`, `level`, `granted_by`, `granted_at`. **There is no `id` column**, so
there is no single identifier to put there; the row's identity is the triple.

**"Put it in `reason`."** `reason` is free text, `requires_reason` is false for both actions, and
ADR-0054 argues at length that free text on an append-only table is how information nobody registered
walks into the one table nothing can be removed from.

**Note the asymmetry that makes this look like an oversight rather than a decision.**
`role_assigned` — the sibling operation one table over, with the same shape and the same pair of
events — *is* seeded with `{role, grantee_user_id}`. The grant pair got neither.

## What Phase 8 adopted, and why

Phase 8 adopts (D-120):

- `target_type` = `prompt_grant` (as seeded), `target_id` = **the grantee's `usr_` id**,
  `scope_prompt_id` = the prompt, `actor_id` = the granter. Grantee and prompt are then columns, not
  payload, and the Activity read finds the events by the index A-119 already ships.
- **One additive migration registers `{level}` on `access_granted` and nothing on `access_revoked`**,
  mirroring `role_assigned` / `role_revoked` exactly: the granting event records what was conferred,
  the revoking event records that it ended. `access_revoked` needs no key, because the level it ended
  is the level its `access_granted` recorded.
- `tests/integration/test_history_schema_ships_its_guarantees.py`'s "every other action is empty"
  assertion is **updated to three declared key sets rather than two**, in the same change, so the
  suite does not go red in a file belonging to another module.

The registry migration is the mechanism Phase 4 already named for exactly this: *"the thirty-second
action is a new revision plus a restart"*, and ADR-0038's process-start cache makes a restart the
deploy step ADR-0031 already performs.

## The shape of the possible answers

1. **Register `{level}` on `access_granted`** — what Phase 8 adopted. Costs one additive data
   migration and one assertion edit in another module's test file. Makes AC-12 literally true.
2. **Amend AC-12 to drop `level`**, and accept that the audit trail records *that* access was granted
   and to whom, but not at what level. Cheapest; loses the fact a reviewer would most want.
3. **Give `prompt_grant` a surrogate id and stop deleting on revoke** (a `revoked_at` column
   instead). Makes the level recoverable by join and makes `target_id` natural — but it changes a
   lock-file field list, contradicts *"revoke; effective on the next request"* only in spelling, and
   is a much larger change than the criterion needs.

**A recommendation:** option 1. It is additive, it is symmetric with `role_assigned`, and it is the
only one that leaves AC-12 assertable as written.
