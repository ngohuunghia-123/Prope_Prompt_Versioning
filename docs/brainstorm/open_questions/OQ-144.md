# OQ-144 — `resolve_miss_total` declares five reasons and the registry can only supply four

**Raised by the gateway build, 2026-08-12.** `blocks_build: false` — the counter ships with the four
reachable values. `pin_not_found` is declared and nothing increments it.

## The contradiction

`gateway.lock.yml` declares:

```
- prope_gateway_resolve_miss_total
  # labels: reason = unknown_model | no_release | not_permitted | pin_not_found | pin_not_approved
```

INT-009 answers with two values and **deliberately collapses the two pin cases into one of them**.
`tests/contract/test_registry_seams.py` locks that collapse with its reason written out:

> It renders as a `no_release` miss rather than as a third reason, because the caller must not be
> able to tell *that revision exists but you may not have it* from *nothing is released*.

So when the gateway asks for `name@8` and the registry answers `NO_RELEASE`, three different facts
are behind that one answer: the prompt has no release at all, revision 8 does not exist, or revision
8 exists and is not `Approved`. The gateway holds the pin, so it can separate the first from the
other two. It cannot separate the other two from each other.

## What shipped

Four values increment. A pinned miss counts as `pin_not_approved`; `pin_not_found` is unreachable.

That labelling is the right way round for the case that matters. AC-2's scenario — *revision 7 is
Approved, revision 8 is Draft, `name@8` is refused* — is the one a real consumer meets, because a pin
is normally typed from a revision the person is looking at on screen. A pin to a revision number that
was never allocated is a typo, and it is rare in a way a pin to an unapproved revision is not.

## Why the gateway does not resolve it by reading again

Three routes were considered:

1. **Read the revision through INT-011 `get_revision`.** Works for `@rev_01J…` and not for `@8`,
   which is the form AC-2 uses and the form a person types. It also puts a second registry read on a
   path this module's `consumes` block lists as two seams (INT-009, INT-010), and
   `tests/architecture/test_gateway_depends_on_four_modules.py` asserts that set is exactly two.
2. **Widen `ResolveMiss` with the two pin members.** The registry is the module that holds the row
   and knows the answer, so this is where the information actually lives. It is refused here because
   the collapse is a *decided* property with a contract test standing on it, and widening the enum
   changes `prope_registry_resolve_miss_total`'s label set as well — a second module's declared
   metric, changed to serve a first module's label.
3. **Query `registry.revision` directly.** Refused outright. `data.reads` says the registry is
   reached *"only through resolve() and list_released(), never by querying the tables"*, because a
   direct read would be a second, weaker enforcement point beside the Approved-only constraint.

## What is being asked

One of two:

1. **Drop `pin_not_found` from the lock's label list.** Four values, all reachable. This is what
   ships, and it costs nothing: the caller cannot tell the two apart either, which is the property
   A-116 is protecting.
2. **Widen INT-009's miss vocabulary** to `unknown_model | no_release | pin_not_found |
   pin_not_approved`, keeping the caller-facing 404 identical. This is option 2 above, and it is
   defensible — the two new values are operator-facing only, exactly like `no_release` already is.
   It costs an amendment to `tests/contract/test_registry_seams.py`, whose current assertion is the
   thing that would have to move.

Reversal cost: low either way. A label value nothing increments emits no series, so option 1 is the
absence of work rather than work.

## What is affected either way

- `src/prope/gateway/resolution.py` — `_reason_for`, the one place a reason is chosen
- `src/prope/gateway/domain.py` — `MissReason`, which carries all five members today
- `tests/security/test_gateway_pin_must_be_approved.py` — asserts `pin_not_approved`, with this OQ named
- `docs/modules/gateway.lock.yml` — **not edited**
