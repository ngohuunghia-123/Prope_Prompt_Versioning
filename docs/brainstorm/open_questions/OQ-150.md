# OQ-150 — Does `prompt_grant` survive `namespace_grant`, or is one table the answer?

**Raised 2026-08-18 by ADR-0061.** `blocks_build: false`, `blocks_pilot: false`. Both tables ship; this
asks whether that is permanent. It is recorded because *"we kept both"* is the kind of decision that
stops being a decision if nobody writes down that it was one.

## What shipped and why

ADR-0061 adds `access.namespace_grant` and **keeps** `access.prompt_grant`. `may()`'s union has five
sources instead of four, and both grant tables answer through the same `GRANT_ACTIONS` policy map, so
there is one statement of what a level confers and two statements of what it applies to.

The case for keeping both is that they are different instruments. A namespace grant is *this team owns
this drawer* — the thousand-prompt case, and the reason the change was made. A prompt grant is *look at
this one prompt*, which is the thing people actually do to each other in a working week, and a
namespace-only model cannot express it without inventing a namespace per shared prompt.

## The case for collapsing to one

**Two tables is two places to look** when somebody asks *"why can this person see that"*, and the
answer screen has to render both. Prope has been careful elsewhere about exactly this — two
implementations of *who may see this* is the failure the module map avoids three times over — and while
these are two *rows* rather than two *rules*, the distinction is thinner than it sounds when a support
question arrives.

**`prompt_grant` may simply go unused.** If a workspace's real behaviour is to organise by folder and
grant by folder, the per-prompt table becomes an unused code path with a foreign key, a level check, a
history action pair, and a tombstone interaction (ADR-0054 deletes *"every `prompt_grant` naming them
as grantee"*) — all maintained for a case nobody exercises.

**A per-prompt grant is now the only place where authority and address disagree.** Everything else in
Prope is addressed and authorised by `namespace/name`: the model name, the key scope, the visible
filter, the observation folder. A prompt grant is the one grant whose scope you cannot read off the
address.

## What would settle it

Not research. **Usage.** Count `prompt_grant` rows against `namespace_grant` rows after one real
workspace has run for a month. If per-prompt grants are a rounding error, retiring the table is a
migration and a simplification; if they are a third of the grants, the question is answered the other
way and this file closes.

## What the answers change

- **Keep both** — nothing changes. This file closes as *decided by use*.
- **Retire `prompt_grant`** — one migration to move existing rows (there is no automatic translation: a
  prompt grant does not imply its namespace should be granted, so this is a conversation per row, not a
  script), plus the removal of one `may()` source, one `GRANT_ACTIONS` application, `access_granted`'s
  `target_type`, and the tombstone clause. Cheap only while row counts are small, which is another
  reason to look early rather than late.
- **Retire `namespace_grant`** — not a real option; A-118's `ids` ceiling comes back with it, and the
  thousand-prompt key problem returns.
