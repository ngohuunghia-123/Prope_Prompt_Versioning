# OQ-063 — PA-10 is mapped to Phase 11, and the foreign key that is its declared mechanism is created in Phase 13

**Raised by Phase 11 planning, 2026-08-11.** `blocks_build: false` — Phase 11 asserts the mechanism
against a real foreign key a test creates and routes the live assertion to Phase 13 by name (plan 11-05,
D-196). Raised because it is a traceability conflict between two `.planning/` authorities, and because
a criterion routed forward without a named owner is a criterion dropped.

## The problem, stated once

`.planning/REQUIREMENTS.md` maps **PA-10** — *"Deleting a provider configuration bound by a revision is
refused with a count and no query into the registry's tables, while disabling it stops dispatch and keeps
the configuration and catalogue readable"* — to **Phase 11**, and the ROADMAP repeats it as Phase 11's
sixth success criterion.

The refusal's declared mechanism is a foreign key on **`registry.revision`**:

> *"prompt-registry: `revision.provider_config_id -> provider_config.id`, a foreign key. It is what
> refuses the delete of a bound configuration (A-096), and it exists precisely because provider-access
> may not read prompt-registry to find out."*

`registry.revision` is prompt-registry's `data.owns` and is created in **Phase 13**. At Phase 11 the
table does not exist, the constraint does not exist, and nothing can bind a configuration. Provider-access
**may not create it** — ORCHESTRATION §5 forbids writing to a table outside the module's own
`data.owns[]`, and the module map's forbidden edge is the reason the foreign key exists at all.

So the criterion's first clause is, at Phase 11, unassertable against the thing it names.

## What Phase 11 adopts (D-196, plan 11-05)

**Split the criterion at the seam between the mechanism and the constraint.**

- **Phase 11 builds and asserts everything provider-access owns**: issuing the delete and letting the
  engine refuse it; catching the foreign-key violation; discovering the referencing table from
  `pg_constraint` rather than naming it; deriving the count; rendering the `409` with the count and the
  registry filter path; and the second clause in full — disable stops dispatch, and the configuration and
  catalogue stay readable.
- The assertion runs against a **real foreign key created by the test** in a scratch schema outside the
  eight declared ones, with `prope_app` granted `SELECT` and the schema dropped in a `finally`. The
  production code path is exercised **unchanged**, which is the property that makes the stand-in worth
  something: when Phase 13 creates `registry.revision` with this foreign key, the same code counts it
  with no edit.
- **Phase 13 owns the live assertion** — a revision bound to a configuration, a delete attempted, a `409`
  with a count of 1 — because Phase 13 is the phase that creates the constraint, and an assertion belongs
  with the thing it asserts about.

Rejected: creating `registry.revision` or its foreign key from Phase 11 (another module's `data.owns`).
Rejected: deferring the whole criterion to Phase 13 (it would hand another module a criterion it does not
own, and the rendering, the count derivation and the no-registry-name property are all buildable now).
Rejected: a mock (the claim is that a database refuses; a mock asserts that a handler catches an
exception).

## What is being asked

1. **Is the split acceptable**, or should PA-10's traceability row move to Phase 13 in
   `.planning/REQUIREMENTS.md`? If it moves, Phase 11 still builds the code and Phase 12's milestone
   audit inherits a requirement it cannot tick.
2. **Should PA-10 be ticked at the end of Phase 11**, with a recorded note that its first clause is
   asserted against a stand-in constraint? Phase 1 set the precedent for an explicitly-not-ticked
   requirement with a written reason (CL-08, CL-11).
3. **Does Phase 13's plan set actually carry the live assertion?** Phase 13 was planned concurrently with
   Phase 11 and cannot have known this routing existed. Somebody has to put it in Phase 13's plans or its
   verification, and this question is where that lands.
4. **Is the same shape true anywhere else?** A requirement whose mechanism is created by a later phase is
   a class, not an instance. `data.referenced_by` blocks across the eight lock files are where the others
   would be.

## What is affected either way

- `tests/integration/test_config_delete_refused_while_bound.py` — the stand-in and its teardown
- `src/prope/provider_access/references.py` — unchanged by the answer; it is written to be
  constraint-agnostic
- Phase 13's plans or verification — the live assertion
- `.planning/REQUIREMENTS.md` — PA-10's row and its tick state
- `.planning/ROADMAP.md` — Phase 11 SC6 and Phase 13's success criteria — **not edited by Phase 11**
