# OQ-078 — The prompt path parameter is spelled two ways, and the test that would catch a real duplicate compares literal strings

**Raised by Phase 14 planning, 2026-08-11.** `blocks_build: false` — plan 14-01 adopts the lock file's
spelling and records it as UNCONFIRMED. This would be cosmetic except that a specific assertion depends
on one spelling being used project-wide.

## The disagreement

| Authority | Spelling |
|---|---|
| `prompt-registry.lock.yml` `apis.exposes` | `/api/v1/prompts/{prompt_id}` — all ten strings |
| `interfaces.md` INT-024 *Routes* | `/api/v1/prompts/{id}` |
| `interfaces.md` INT-025 (evaluation) | `/api/v1/prompts/{id}/eval-suites` |
| `.planning/ROADMAP.md` phase 14 SC3 | `/api/v1/prompts/{id}/activity` |
| shipped code — `src/prope/call_ledger/api.py` | `/api/v1/workspaces/{id}` with `Path(alias="id")` |

The lock file is authority #1 under ORCHESTRATION §1, so plan 14-01 ships **`{prompt_id}`**.

## Why it is not cosmetic

`prompt-registry.lock.yml`'s own `security_requirements` block ends with a rule whose whole subject is a
shared namespace:

> **ROUTE-TABLE UNIQUENESS.** FOUR modules mount routes under `/api/v1/prompts/{prompt_id}` — this one,
> evaluation, release-control and access-control's grants — and three under `/api/v1/workspaces/{id}`. No
> module owns either prefix and no collision exists today. **A CI test asserts the assembled route table
> contains no duplicate (method, path) pair.**

That test compares **literal path strings** — it is the only thing it can compare, because that is what
`assembled_routes()` yields. `/api/v1/prompts/{id}/activity` and `/api/v1/prompts/{prompt_id}/activity`
**route identically** and **compare unequal**. So if two of the four modules spell the parameter
differently, a genuine duplicate registration is invisible to the assertion whose entire purpose is to
see it — and the failure it exists to catch (two modules quietly serving the same path, with resolution
depending on router registration order, which ADR-0050 established this build does not rely on) returns
without a detector.

Note the same rule already applies at `/api/v1/workspaces/{id}`, where call-ledger has shipped `{id}` and
access-control's INT-029 mounts `/workspaces/…` too.

## What the answer changes

- **If `{prompt_id}` is right**, INT-024's *Routes* line, INT-025's, INT-026's and the ROADMAP's SC3 all
  spell it wrongly today, and phases 17 and 23 will mount their `/api/v1/prompts/…` routes from those
  documents.
- **If `{id}` is right**, the lock's ten `apis.exposes` strings are wrong and plan 14-01's ten routes plus
  the `EXPECTED_ROUTES` literal have to move — one file, cheaply, **while only one of the four modules is
  mounted.**
- **Either way, one spelling has to be chosen project-wide before phase 17**, because after that there
  are three modules' worth of routes to change instead of one, and the uniqueness test cannot tell anyone
  it is looking at the wrong strings.
- A cheap belt-and-braces answer, if the divergence is tolerated: make the uniqueness test compare paths
  with every `{…}` segment normalised to a placeholder. That catches a real duplicate under either
  spelling and costs three lines — but it hides the inconsistency rather than resolving it, so it is
  offered as a mitigation and not as the answer.
