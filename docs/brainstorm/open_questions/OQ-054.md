# OQ-054 — `active_sessions` is a gauge the module has no mechanism to keep true

**Raised by Phase 9 planning, 2026-08-11.** `blocks_build: false` — Phase 9 sets the gauge where sign-in
and sign-out already run, asserts those two movements, and records here that the value drifts. Raised
because a gauge that is wrong is worse than one that is absent: absent reads as *not wired* and wrong
reads as *the truth*.

## The problem, stated once

Two clauses of the same lock file cannot both be satisfied by any mechanism this module is permitted to
have.

**The metrics block requires the gauge:**

```yaml
- prope_access_control_active_sessions
  # gauge
```

**`deployment_target` forbids the only thing that could keep it true:**

> *"It has no scheduled job either — session expiry is enforced on read inside `access.lookup_session`
> (`expires_at > now()`, ADR-0042) rather than by a sweeper, so an expired row is never returned even if
> it is still present. A periodic delete of expired rows is housekeeping for disk, not for correctness,
> and is deliberately not a dependency of any promise this module makes."*

There are exactly three ways to maintain a gauge and each one is blocked or wrong here:

1. **Increment on sign-in, decrement on sign-out.** Buildable, and it **over-counts forever**. Sessions
   end three ways — sign-out, expiry, and deletion by a tombstone or a member removal — and only the
   first has a place to decrement. Expiry has no event at all *by decision*: it is evaluated inside a
   `SECURITY DEFINER` function on every read, and a row whose `expires_at` has passed is simply not
   returned. Nothing observes the transition, so nothing can decrement. A process running for a week
   reports a monotonically rising number that is not the number of active sessions.
2. **A periodic `SELECT count(*) FROM access.session WHERE expires_at > now()`.** Correct, and it is the
   scheduled job `deployment_target` says this module does not have. Adding one also adds a job to
   `src/prope/worker.py`'s hand-written composition (D-13/D-14) for a module whose lock file says
   *"nothing in this module runs in `worker`, because it answers questions and no asynchronous work asks
   one."*
3. **Compute it on scrape**, in a `prometheus_client` collector callback. Correct and needs no scheduler
   — and it puts a database query on the `/metrics` path, so a scrape failure becomes a database
   dependency of the observability surface, and a slow database makes Prometheus time out on the one
   endpoint an operator reaches for during an incident. It also runs an unauthenticated,
   externally-triggerable query, which is the shape ADR-0043 rejected the PostgreSQL rate-limit counter
   over.

## What Phase 9 ships (plan 09-06, Task 1)

Option 1, with the drift stated at the metric and asserted honestly rather than hidden:

- The gauge is set at sign-in and at sign-out, which are the two transitions that have a place to run.
- `tests/integration/test_access_control_metrics.py::test_the_two_gauges_are_set_by_something` asserts
  **those two movements only**, and its docstring states that the value drifts upward as sessions expire
  unswept, that this question owns the gap, and that *a `Gauge` reading high is a different failure from
  one reading absent*.
- **No sweeper is invented**, no `worker` job is added, and no collector callback is registered.
- No alert is written on the gauge. The lock declares six alerts and none of them reads this series,
  which is what makes shipping a drifting value tolerable for now: nothing automated acts on it.

## What is being asked

Which of the four dispositions the project wants:

- **(a)** Keep the gauge as shipped, drifting, with the drift documented and no alert on it. Cheapest,
  and it leaves a metric on the dashboard that an operator will eventually believe.
- **(b)** Add the periodic count as a `worker` job, amending `deployment_target`'s *"no scheduled job"*
  line. It is one job with a bounded query and a written reason. The cost is that it makes the sentence
  in the lock file false, and that sentence is load-bearing elsewhere — it is why the module's `/readyz`
  has nothing to gate on and why nothing in this module runs in `worker`.
- **(c)** Compute on scrape, accepting a database query on `/metrics`.
- **(d)** **Delete the metric from the lock file's block**, taking access-control from seventeen metrics
  to sixteen. Honest, and it is the option that costs nothing to run — the value is not read by any alert
  and its consumers today are zero. It is also the option nobody proposes, because deleting a declared
  metric feels like a regression while shipping a wrong one does not.

**Phase 9 adopts (a) because it is the only one that changes no authority**, and records the question so
that (d) stays available.

## What is affected either way

- `src/prope/observability.py` (or `src/prope/access_control/observability.py`) — the gauge's definition
  and its `#:` block
- `src/prope/access_control/identity.py` / `sessions.py` — the two set sites
- `tests/integration/test_access_control_metrics.py` — the seventeen-metric count assertion, which
  becomes sixteen under (d)
- `src/prope/worker.py` — under (b) only
- `docs/modules/access-control.lock.yml` `observability_requirements.metrics` and `deployment_target` —
  **not edited by Phase 9**; (b) and (d) each require one of them to change
