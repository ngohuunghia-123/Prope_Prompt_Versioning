# OQ-077 — A-050's caps are declared as a `413` in one place and a `422` in another, and only one of them can carry the size

**Raised by Phase 14 planning, 2026-08-11.** `blocks_build: false` — plan 14-03 adopts `422` and records
it as UNCONFIRMED. Small, and worth writing down because the status code is what a client branches on and
because the two authorities disagree in a way that changes what the response can contain.

## The disagreement

`prompt-registry.lock.yml`'s last `failure_modes` row:

> **scenario**: A prompt body or change summary exceeds its limit.
> **detection**: `413` rate on the revision endpoint.
> **mitigation**: Body ≤ 32 KiB and change summary ≤ 200 chars, enforced at the edge (A-050). Truncating
> a prompt body silently would corrupt the asset the product exists to protect.

INT-024's failure line, registering the same ten routes:

> `404` for not-found and for not-permitted alike · `409` on a concurrent revision conflict · **`422` for
> validation with `details`** · `5xx` for any raised in-process seam.

## Why plan 14-03 ships `422`

**1. A `413` is about the HTTP entity; the cap is on one JSON field.** `POST /api/v1/prompts/{id}/revisions`
carries a body, a fallback answer, a change summary and a parameters object. A request whose `body` is
40 KiB and whose `fallback_answer` is another 40 KiB is comfortably inside any plausible request-size
limit and still violates A-050. A `413` would be the right code only if the rule were about the request,
and it is not.

**2. A-050 requires a message naming the actual size, and only the envelope can carry one.** The
assumption's own words are *"enforced at the edge with a message naming the actual size; neither is ever
silently truncated."* A `413` emitted by a server or by Caddy carries no envelope and no `details`; a
`422` in A-045's envelope carries `{actual_bytes, max_bytes}` and a machine `code` the `vi` catalogue has
a key for (ADR-0053).

**3. INT-024 is the interface registration for exactly these routes**, and it names `422` while listing
`409` separately for the conflict — so the author distinguished the two classes deliberately.

**4. A `413` would in practice come from somewhere else.** Under ADR-0033 Caddy is the single ingress. If
a `413` ever appears on this endpoint it will be Caddy's, for a different reason, with a different body —
which would make the failure-mode row's *detection* signal ambiguous rather than useful.

## What the answer changes

- **If `422` is right**, the `failure_modes` row's `detection` line should read *"`422` rate with code
  `body_too_large` / `change_summary_invalid` on the revision endpoint"* — which is also a **better**
  detector, because it distinguishes the two limits and cannot be confused with an ingress-level refusal.
- **If `413` is right**, then A-050's *"a message naming the actual size"* needs a home, INT-024's failure
  line needs the code added beside `422`, and somebody has to decide what a request that is under the
  ingress limit and over the field limit returns.
- **Either way there is a monitoring consequence**: the row as written tells an operator to watch a rate
  that will be zero forever under the shipped behaviour, which is the same class of defect as an alert
  reading a metric nobody increments.
