# OQ-035 — INT-006 declares `append(event) -> void`; what ships is `append(session, event) -> str`, and the returned value is an identifier the envelope does not name.

**Raised by Phase 5 planning (plan 05-01), 2026-08-11.** `blocks_build: false` — the deviation is a
widening no caller can be broken by. Raised because INT-006 is the seam **five modules** are written
against from Phase 7 onward, and a seam that ships wider than its registration should be a question
somebody answered rather than a shape somebody found.

Phase 4 shipped the write path under a placeholder name (`record_event`, D-64) and carried an eleventh
draft field, declaring both as owed to this phase (`04-…/deferred-items.md` §3 and §5: *"Phase 5 owns
INT-006's actual signature and reconciles the two — drop the field and return the minted id, or change
the spec"*). This is the reconciliation, in the only direction available to an agent who may not edit a
spec.

## The three deviations, each against a named line

### 1. The session is a parameter. `append(event)` has nowhere to put one.

`docs/modules/property-history.lock.yml` `apis.exposes`:

> `internal: append(event) -> void`. Runs on the caller's connection inside the caller's open
> transaction (ADR-0023).

The second sentence requires what the first has no room for. `docs/adr/0023-…` makes this module a
library on the **caller's** SQLAlchemy session — it opens no transaction, holds no engine, and has no
ambient connection to fall back on; INT-006's own Transport line says the same
(*"in-process, on the caller's connection inside the caller's open transaction"*). So the connection has
to arrive as an argument, and `append(session, event)` is the shortest form that says so.

**This one is arguably not a deviation at all** — the declared signature is shorthand for the seam and
the transport line is the specification. It is listed because a reader comparing the two literally will
see two arguments where the spec shows one, and should find the reason here rather than reconstruct it.

### 2. The return is the minted identifier, not `void`.

Both `apis.exposes` and INT-006 say the append returns nothing.

`append()` mints `hev_` + ULID at the write and returns it as a `str`.

The reason it cannot be `None` without cost: A-045 and ADR-0003 make the `hev_`-prefixed ULID **the
provider's to mint**, and INT-006's *Envelope carries* list does not include `id` — so a caller has no
way to know the id of the row it just wrote. On an append-only table with no natural key for *the row I
just inserted*, re-reading for it is not a real option. The lock itself relies on the id being knowable:
*"the event's id is logged; its content is not."*

### 3. `HistoryEventDraft` loses the eleventh field Phase 4 gave it.

INT-006's *Envelope carries* names exactly ten: `workspace_id`, `actor_type`, `actor_id`, `action`,
`target_type`, `target_id`, `scope_prompt_id`, `reason`, `details`, `occurred_at`, and adds *"`seq` is
database-assigned."* Phase 4's draft carried `id` as an eleventh with a `hev_`-prefixed default factory,
so `record_event` could return a value the caller already held, and declared the widening as owed here.

**It is dropped**, so the envelope matches the seam exactly. The second reason is not presentational: a
caller-supplied `id` on a table whose primary key is `id` is an identifier a caller can collide with —
two callers minting from the same clock millisecond would raise an `IntegrityError` **inside somebody
else's release transaction**, from a module they did not think they were configuring. Minting at the one
site that writes removes the question.

## What is being asked

Whether the returned identifier is the reconciliation, or whether `id` should join INT-006's envelope in
a spec change — in which case the draft carries it again, `append()` may go back to `-> void`, and the
collision hazard needs an answer (a uniqueness refusal a caller can act on, or a rule that only this
module mints).

A third possibility, stated so it is not rediscovered: `append()` could return the full `HistoryEvent`
including its `seq`. Rejected in planning because `seq` is not the caller's business — it is the sort
key, and a caller that holds one will eventually paginate with it, which is the *assignment order is not
commit order* hazard INT-007 paginates descending to avoid.

## What is affected either way

- `src/prope/property_history/append.py` and `domain.py`
- Every history test in Phases 4, 5 and 6, all of which take the id from the return value
- **Phases 7, 10, 13, 16 and 22** — the five writing modules, each of which will hold the returned id or
  not, depending on the answer, in code that has not been written
- `docs/architecture/interfaces.md` INT-006 and `docs/modules/property-history.lock.yml`
  `apis.exposes` — neither of which is edited by Phase 5
