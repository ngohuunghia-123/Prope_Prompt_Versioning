# OQ-045 — The four-and-only-four assertion names a function that cannot exist for nine more phases

**Raised by Phase 7 planning, 2026-08-11.** `blocks_build: false` — Phase 7 ships the assertion with a
declared not-yet-built list and asserts the *sanctioned* set rather than the *present* set. Raised
because the control this whole mechanism rests on is an **exact set equality**, and an exact equality
that has to be relaxed for nine phases is exactly the kind of relaxation that is never tightened again.

## The problem, stated once

The sanctioned set is `access.lookup_session`, `access.lookup_api_key`, `evaluation.claim_next_run()`,
`access.list_workspaces()`. Three of the four are in the `access` schema and land in **Phase 7**. The
fourth, `evaluation.claim_next_run()`, belongs to the `evaluation` schema, which
`tests/architecture/test_tenant_coverage.py`'s `EXPECTED_ABSENT_SCHEMAS` records as not yet built and
which ADR-0049 places in **Phase 16**.

So between Phase 7 and Phase 16 the live database contains **three** `SECURITY DEFINER` objects, and a
test written literally against the four-name set fails for nine phases on a true statement.

The naive repairs are all worse than the problem:

- `assert observed <= SANCTIONED` — passes when every one of them has been deleted, which is precisely
  the state where the authentication bootstrap is broken and no test says so.
- `assert len(observed) <= 4` — passes for any four functions, including four somebody added.
- Skipping the test until Phase 16 — the additions this control exists to catch happen in Phases 7
  through 15.

## What Phase 7 ships (D-115)

`tests/security/test_security_definer_set_is_exactly_sanctioned.py`, in the shape
`EXPECTED_ABSENT_SCHEMAS` already established in this repository for the same class of problem:

```python
SANCTIONED = ("access.list_workspaces", "access.lookup_api_key",
              "access.lookup_session", "evaluation.claim_next_run")

#: THIS LIST IS A PER-PHASE CONSTANT, NOT A PERMANENT FACT.
NOT_YET_BUILT = ("evaluation.claim_next_run",)
```

and asserts `observed == tuple(n for n in SANCTIONED if n not in NOT_YET_BUILT)` — an **exact**
equality against a set that shrinks by an edit somebody makes, so a fifth function fails it, a deleted
third function fails it, and Phase 16 removing its entry is the same visible one-line act that
Phase 7 performs on `EXPECTED_ABSENT_SCHEMAS`.

## What is being asked

Whether that is the intended reading of *"a test asserts the set is exactly these four"*, or whether
the project would rather:

- **(a)** state the rule as *"exactly the sanctioned set, minus those whose module has not shipped"*,
  in `.claude/CLAUDE.md` and in `docs/modules/access-control.lock.yml` `test_plan.security` T-003 — in
  which case Phase 7's shape is the specification and the wording follows it; or
- **(b)** create `evaluation.claim_next_run()` early, in Phase 7's migration, so the count is four from
  the moment the first one exists. Rejected in planning: it puts an `evaluation` schema object in
  access-control's migration, it would create a schema `EXPECTED_ABSENT_SCHEMAS` declares absent, and
  a function nobody calls for nine phases is a function whose signature drifts from the caller that
  eventually arrives.

## What is affected either way

- `tests/security/test_security_definer_set_is_exactly_sanctioned.py`, and the `NOT_YET_BUILT` line
  Phase 16 deletes
- `.claude/CLAUDE.md` and `docs/modules/access-control.lock.yml` T-003 — neither edited by Phase 7
- Every phase between 7 and 16 that adds a migration, which is the window this control covers
