# OQ-076 — `set_revision_status` is told to validate a transition table that no authority writes down, and to validate a `decision_id` it may not read

**Raised by Phase 14 planning, 2026-08-11.** `blocks_build: false` — plan 14-06 adopts an answer to both
halves in a `checkpoint:decision` block and records each as UNCONFIRMED.

## 1. The legal transition set is declared nowhere

ROADMAP phase 14's fourth success criterion says each of the three commands *"validates the transition
here."* INT-012 says *"the provider validates the transition"* and *"the legal state machine lives in one
module."* ADR-0008's consequences say *"invalid transitions are refused by the owner of the table."*

**What is actually declared** is the vocabulary and one edge:

- the stored statuses are `Draft | In review | Approved` (ADR-0008, A-065); `In use` is derived from the
  released pointer and never stored; `Retired` is a prompt-property status (A-049);
- **A-066**: *changes requested returns the revision to `Draft`*, because the vocabulary contains no
  rejected state and the author's fix is a new immutable revision, not an edit to the rejected one.

**What is not declared** is everything else: whether `Approved` can be left, whether a self-transition is
a no-op or an error, and whether `Draft -> Approved` may skip review.

Two facts constrain any answer and neither is a preference:

- **Phase 13's D-221 makes `Approved -> anything` impossible at the engine for a currently released
  revision**, because `released_version_status` is part of the foreign key's referenced key. Phase 13
  recorded this as a transition INT-012 has that no authority mentions.
- **A revision is immutable (ADR-0002)**; `status` is the one carve-out and every other correction in
  this product is a new revision.

**Plan 14-06 adopts the closed forward-and-back set** — `Draft -> In review`, `In review -> Approved`,
`In review -> Draft` — with `Approved` terminal and every self-transition raising (INT-012: *"not
idempotent … re-issuing a transition that has already happened raises rather than silently succeeding,
so a double-submit is visible instead of absorbed"*).

**The deciding argument was the audit vocabulary, not the workflow.** The commands append no
property-history event of their own — release-control's `revision_submitted` / `revision_approved` /
`revision_released` / `release_withdrawn` are the record — and property-history's action vocabulary is a
**closed thirty-one-name list seeded by a migration**, with ADR-0038 making a thirty-second name *"a new
revision plus a restart."* There is **no `revision_unapproved` action in it.** So under any table that
permits leaving `Approved`, a revision could be un-approved and **no event anywhere would say it had**,
on the one table this product's whole claim against a spreadsheet rests on.

## 2. `decision_id` cannot be validated from prompt-registry

INT-012's failure line requires a raise on *"a `decision_id` that does not exist"*. That check reads
release-control's `approval` or `release` row.

**prompt-registry -> release-control is a forbidden dependency**, and its stated reason is precisely this
edge:

> Would close the cycle that A-041 and ADR-0001 exist to break. The pointer is set by an inbound command;
> this module never asks who approved what.

So the check is unimplementable from the module the interface assigns it to. The same applies to
`release_id` on INT-013 and INT-014.

**A second problem rides with it**: neither id has a column. `registry.revision`'s declared fields carry
no `decision_id` and `registry.prompt_property`'s carry no `release_id`, so even accepting them without
validating leaves nothing stored. ADR-0008 says *"`decision_id` names the approval or release row that
authorised it, so a status with no decision behind it is a **detectable** defect rather than an
untraceable one"* — and its own 2026-08-09 amendment says how it is detected: **release-control's
reconciliation query**, run at startup and hourly by ADR-0051's sweep. Not by a column here.

**Plan 14-06 ships**: the ids are accepted, their **shape** is validated (non-empty, ADR-0003's prefixed
ULID), they are written to the success log line, and they are stored nowhere.

## What the answer changes

- **If `Approved` should be reversible**, release-control needs an un-approve action with its own
  permission and its own name in the thirty-one-name registry — which is a migration plus a restart
  (ADR-0038) — and `LEGAL_STATUS_TRANSITIONS` in `src/prope/prompt_registry/domain.py` grows by two
  edges. It is one migration and one table entry either way **while no workspace holds real revisions**
  (A-020 holds that line), and it gets more expensive with every week of pilot.
- **If `Approved` is terminal**, ADR-0008 or A-066 should say so in one sentence, because the next module
  to be written against `set_revision_status` will otherwise ask this question again.
- **If `decision_id` must be validated**, either the forbidden edge is reversed — which reopens the cycle
  — or the validation moves to release-control, which is the module that holds the row and is already the
  only caller. The second is almost certainly the answer and it means INT-012's failure line is assigned
  to the wrong side of the seam.
- **Either way, INT-012's failure line is not implementable as written**, and a later reader who tries
  will reach for the forbidden import.
