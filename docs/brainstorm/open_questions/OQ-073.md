# OQ-073 — The model name is case-insensitive in A-021 and case-sensitive in the lock file's constraint

**Raised by Phase 13 planning, 2026-08-11.** `blocks_build: false` — plan 13-01 adopts the stricter of
the two readings and records it as UNCONFIRMED.

## The problem, stated once

A-021: *"Every prompt property has a model name of the form `namespace/name` … unique within its
workspace **and case-insensitive**."*

`prompt-registry.lock.yml` `data.owns.prompt_property.notes`: *"`unique(workspace_id, namespace, name)` —
the model name (A-021)."*

Written as declared, that constraint is **case-sensitive**, because PostgreSQL `text` comparison is.
`ecom/agent` and `Ecom/Agent` would both register, both be globally unique model names, and both be
resolvable by the gateway — while A-021 says they are the same name.

The consequence is on the hot path, not in the schema. The gateway resolves a bare model name from a
consumer's request body (INT-009). If two properties differ only by case, either the resolver picks one
by an ordering nobody wrote down, or it matches nothing when the caller types the name in the case they
remember. A-021's own rationale is that the name *"is what consumer code hard-codes, so it is a public
contract, not a label"*.

## The two options

**A — a case-insensitive unique index**: `UNIQUE (workspace_id, lower(namespace), lower(name))`, with the
stored values left exactly as typed. Registration of a second casing is refused at the engine. Resolution
compares lowered on both sides.

**B — the declared constraint literally**, and case-insensitivity handled in application code at
registration. Rejected on this project's standing rule that the migration carries the guarantee, and on
a specific hazard: the check would be a `SELECT` before an `INSERT`, which two concurrent registrations
race straight through.

## What phase 13 shipped

**Option A.** A functional unique index satisfies the declared constraint (it is strictly stronger — any
pair the declared constraint refuses, this one also refuses) while making A-021 true, so it is the only
choice that leaves neither authority false.

The stored columns keep the author's casing, because the name is displayed and a register that silently
lower-cases what somebody typed is the same class of edit as truncating a body (A-050 forbids that
outright). `namespace` and `name` also take **no `UPDATE` privilege** for `prope_app`, which is A-021's
*"cannot be changed afterwards"* carried by the grant matrix rather than by a code review.

## What the answer changes

- **If case-insensitive is right**, the lock's `notes` line should read
  `unique(workspace_id, lower(namespace), lower(name))` and nothing in the code moves.
- **If case-sensitive is right**, A-021's clause is wrong and the index loses two `lower(` calls — but
  then the gateway needs a stated rule for which of two same-name-different-case properties resolves, and
  no authority has one.

Neither answer is expensive **until a workspace registers two names differing only by case**, at which
point one of them has to be renamed, and A-021 says a model name cannot be renamed.
