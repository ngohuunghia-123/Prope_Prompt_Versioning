# OQ-138 — the login limiter's source-address bucket is one bucket for the whole install

**Raised by the access-control build, 2026-08-11.** `blocks_build: false` — the limiter ships and
the behaviour is documented at `api._source_address`.

## The situation

A-144 counts 20 failures per **source address** per rolling 15 minutes. Caddy is the single ingress
(A-129), so every request the application sees arrives from the proxy: `request.client.host` is
Caddy's address, and the bucket is therefore shared by everybody.

The effect is **stricter** than A-144 intends — 20 failures per 15 minutes across the whole install
rather than per attacker. A busy Monday morning could lock everyone out of sign-in for fifteen
minutes.

`X-Forwarded-For` is deliberately not read. A header trusted without a configured proxy allowlist is a
limiter an attacker turns off by sending a different value on every request, which is worse than a
limiter that is merely blunt. The allowlist is knowable — there is exactly one proxy — but it is
deployment configuration this phase has not written.

Meanwhile the **per-email** bucket (5 per 15 minutes) is doing the account-targeted work, and it is
unaffected.

## What is being asked

Configure the trust boundary, which is two coordinated edits: Caddy sets `X-Forwarded-For`, and the
application reads it **only** when the peer is the configured proxy address. Then `_source_address`
returns the client's address and A-144 means what it says.

Until then, decide whether the global bucket is acceptable for the pilot. Being wrong in this
direction fails loudly — somebody notices within minutes — which is why it was chosen over the
alternative.

## What is affected either way

- `src/prope/access_control/api.py` — `_source_address`
- `deploy/Caddyfile` — the forwarding header
- `src/prope/db/engine.py`'s `Settings` — a trusted-proxy setting, if one is added
