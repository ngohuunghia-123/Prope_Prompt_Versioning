# OQ-053 — Two declared metric labels are unbounded identifier spaces, and a project-wide test forbids both

**Raised by Phase 9 planning, 2026-08-11.** `blocks_build: false` — Phase 9 decides both, in opposite
directions, with the reasoning at each metric. Raised because the decision is a deviation from a lock
file in two places and because Phase 8 was explicitly told to route it here rather than raise it itself
(`08/deferred-items.md` §5).

## The problem, stated once

`docs/modules/access-control.lock.yml`'s metrics block declares seventeen metrics. Two carry labels whose
values come from identifier spaces rather than from closed vocabularies:

```yaml
- prope_access_control_key_scope_refusal_total
  # labels: key_id
- prope_access_control_admin_count
  # gauge, labels: workspace_id — must never be 0
```

Three things in this repository point the other way:

1. **ADR-0030** bounds metric label cardinality as a stack-level rule.
2. `src/prope/observability.py`'s module docstring, written in Phase 2: *"every label declared here has a
   CLOSED set of values fixed in source, and `workspace_id` — the highest-cardinality identifier in the
   system and the one most tempting to add — is **deliberately never a label**."*
3. `tests/broker/test_publish_confirm_failures.py::test_workspace_id_is_never_a_metric_label` asserts
   that over **every** metric in the registry, project-wide.

So `admin_count{workspace_id}` fails an existing test the moment Phase 7 defines it, and
`key_scope_refusal_total{key_id}` is the same defect one identifier space over — worse by the ratio of
keys to workspaces, since a key label never shrinks as keys are created and revoked.

**This has happened once before and was resolved.** `OQ-030` raised `workspace_id` on
`prope_property_history_rows_total`; Phase 6's D-91 **dropped the label** rather than narrowing the walk.
That precedent settles the shape of the answer but not the answer, because the two metrics here are not
the same case.

## What Phase 9 decides (D-144, plan 09-06)

**`key_scope_refusal_total` drops `key_id`.** Three reasons, none of which apply to the other metric:

- **Nothing alerts on it.** The lock declares six alerts and this metric is in none of them, so the label
  serves no automated consumer.
- **The label set grows without bound and never shrinks.** `key_id` is a `key_`-prefixed ULID; every key
  ever created that is ever refused adds a permanent series.
- **The signal already exists elsewhere.** `key_id` is in `observability.LOGGABLE_FIELDS` — plan 08-03
  put it there with a written justification — and the lock file names it loggable *in the same sentence*
  that names the secret as not. *Which key is being refused* is a log query, and Phase 9 adds the log
  record at the refusal site so the signal moves rather than disappearing.

**`admin_count` keeps `workspace_id`**, under a declared exemption:

- `AccessControlAdminCountZero` pages on *"`prope_access_control_admin_count == 0` **for any
  workspace**"*, and an unlabelled gauge cannot express *for any*: a sum over workspaces is non-zero
  while one workspace is frozen, which is exactly the state the alert exists for.
- The lock is explicit that the gauge is a proof rather than a diagnostic — *"the gauge exists to prove
  the refusal is working rather than to catch a state anyone plans to recover from"* — and A-117 has no
  recovery path, because A-012 rules out building an operator surface.
- The cardinality is bounded by the workspace count at ADR-0033's single-VM pilot scale, which is a
  different order of magnitude from a key count.

The consequence is written into the test rather than around it:
`tests/broker/test_publish_confirm_failures.py` gains a `WORKSPACE_LABEL_EXEMPTIONS` mapping with
**exactly one** entry, carrying the reason and the alert that requires it, and **three** assertions —
every non-exempt metric is checked, every exempt key must exist in the registry, and the mapping must
have exactly one entry. **The walk is not narrowed**: an exemption that is asserted is a decision, and a
pattern the walk skips is a walk somebody has stopped believing. Same shape as `GLOBAL_TABLES` and
`EXPECTED_ABSENT_SCHEMAS` in `tests/architecture/test_tenant_coverage.py`.

## What is being asked

1. **Is the split answer right**, or should both be treated the same way for consistency? Consistency
   would mean either dropping `workspace_id` from `admin_count` — which makes the only alert that proves
   A-117 works unwritable — or keeping `key_id` on the refusal counter, which reintroduces the
   cardinality problem ADR-0030 exists to prevent, for a series nothing reads.
2. **Is the exemption mechanism acceptable** as the general answer for future declared-but-unbounded
   labels, given `OQ-030` set the drop-the-label precedent and this is the first exemption granted?
3. **Should the lock file's two comment lines be corrected** when this is answered? Phase 9 does not
   edit them. If the answer is *drop `key_id`*, the metrics block's comment still says `# labels: key_id`
   and the next reader will implement it again.
4. **Does the same question apply to `prope_call_ledger_unpriced_total{provider_config_id}`?** Phase 7's
   plan named it as the existing precedent for shipping a declared identifier label. If the exemption
   policy is adopted, that metric is the second candidate and nobody has looked at it under this rule.

## What is affected either way

- `src/prope/observability.py` (or `src/prope/access_control/observability.py`) — the two metric
  definitions and their `#:` blocks
- `src/prope/access_control/keys.py` — the increment site, and the log record the dropped label moves to
- `tests/broker/test_publish_confirm_failures.py` — the exemption mapping and its three assertions
- `tests/integration/test_access_control_metrics.py` — `test_key_scope_refusal_total_carries_no_labels`
- `deploy/prometheus/rules/access_control.rules.yml` — `AccessControlAdminCountZero`'s expression
- `docs/modules/access-control.lock.yml` `observability_requirements.metrics` — **not edited by Phase 9**
