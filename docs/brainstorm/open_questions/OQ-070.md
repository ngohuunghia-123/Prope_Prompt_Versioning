# OQ-070 — BR-03 as a database constraint needs a column `prompt_property` does not declare

**Raised by Phase 13 planning, 2026-08-11.** `blocks_build: false` — plan 13-01 adopts an answer and
records it as UNCONFIRMED. Raised because the declared field list and the non-negotiable cannot both be
satisfied as written, and the alternative edits a lock file by fact.

## The problem, stated once

Non-negotiable #2, `00_context.md#constraints`, ADR-0001 and INT-013 all say the same thing in the same
words: **only `Approved` revisions may be released, and the refusal is a database constraint, not
application code.** INT-013 is explicit that *"the constraint is the thing that raises"*.

PostgreSQL has exactly three mechanisms that can carry a rule of that shape:

1. A `CHECK` constraint. **Cannot be used** — a `CHECK` may only read columns of its own row, and
   `revision.status` is on another row of another table. Sub-selects in `CHECK` are refused outright.
2. A **foreign key to a subset**: `revision` publishes `UNIQUE (workspace_id, version_id, status)` and
   `prompt_property` references it with a second column pinned to the literal `'Approved'`. This is the
   standard relational encoding of *"the referenced row must also satisfy P"*, and it is fully
   declarative.
3. A **trigger**. It is code that a `psql` session with the right privileges disables
   (`ALTER TABLE … DISABLE TRIGGER`), which is the objection ADR-0025 raises against triggers for
   append-only enforcement.

Mechanism 2 is the only declarative one, and it needs a column: `released_version_status text`, pinned
by `CHECK (released_version_status IS NULL OR released_version_status = 'Approved')`. **That column is
not in the declared field list.**

## The two options

**A — add `released_version_status` and write the composite foreign key.** The Approved-only rule is
then a foreign key: `(workspace_id, released_version_id, released_version_status)` references
`registry.revision (workspace_id, version_id, status)`. A write naming a `Draft` revision is refused by
the engine with `insert or update on table "prompt_property" violates foreign key constraint`, and no
application code participates. Cost: one undeclared `text` column on the module's main table, and
`set_released_revision` / `clear_released_revision` must move three columns together rather than one.

**B — a `BEFORE INSERT OR UPDATE` trigger that reads `revision.status` and raises.** No new column, the
declared field list stays literally true, and the error message can name the revision and its status
rather than a constraint name. Cost: the guarantee is procedural. `prope_migrate` owns the table, so
`prope_app` can neither drop nor disable the trigger — but the rule then lives in a function body that
a future migration can replace without any constraint disappearing from `\d prompt_property`, and
ADR-0025 already argued in this repository that a trigger is the weaker of the two.

## What phase 13 shipped

**Option A.** Three arguments decided it, in order:

1. **The refusal must survive a writer nobody reviewed.** That is the whole content of "constraint, not
   application code". A foreign key is enforced by the same machinery that enforces a primary key; a
   trigger is enforced by a function body.
2. **`00_context.md#success` sets a target of zero unapproved revisions reaching a release, and
   `RegistryUnapprovedPointer` pages on the first.** A declarative constraint makes the alert's query
   structurally unable to return a row; a trigger makes it able to, and merely unlikely.
3. **The same column closes a second hole for free.** The pairing `CHECK` that keeps
   `released_version_id`, `released_version_status` and `released_at` NULL or non-NULL together makes
   *"a released pointer with no release time"* unrepresentable, which nothing else in the spec forbids.

Phase 13 also declines to soften it: **`clear_released_revision` exists as a separate command precisely
so this constraint needs no NULL carve-out** (A-069, ADR-0009), and Option A keeps that true.

## What the answer changes

- **If the field list should carry the column**, the edit is one line in
  `data.owns.prompt_property.fields` and nothing in the code moves.
- **If the column is unacceptable**, the replacement is Option B, which is one migration: drop the
  foreign key, drop the column, add the trigger. Cheap while the pilot holds no releases (A-020 holds
  that line), and it never gets cheaper.

**A third consequence a reader should know either way.** With the foreign key in place, an `UPDATE` of
`revision.status` **away from `Approved` on a revision that is currently released** is refused by the
engine, because it changes a referenced key. That is correct — un-approving what production is serving
should require a withdrawal first — but it means `set_revision_status` (INT-012, phase 14) has a
transition it cannot perform, and no authority says so today.
