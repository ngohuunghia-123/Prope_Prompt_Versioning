# OQ-153 - Should `model` name the provider's model, with `auto` meaning the revision's? (closed)

**Raised and closed 2026-08-19.** Recorded because it was a live design proposal for two days, it was
argued for on good grounds, and *we decided not to* is the kind of decision that stops being one if
nobody writes it down.

## What was proposed

That the gateway's `model` field carry the **provider's** model name - `openai/gpt-4o-mini`,
`google/gemini-2.5-flash` - overriding whatever the released revision binds, with the literal `auto`
meaning *use the revision's own model*. Prompt identity would move to some other channel.

The motivation was real: a product wants to choose its model per call, and a released revision fixes
one.

## Why it is closed

**Three objections, and the second is the one that would have cost the product.**

*It collides with prompt identity.* `model` is the only field a plain OpenAI client controls freely. If
it names the provider's model, nothing names the prompt, so a second channel is needed anyway - the
proposal moves the prompt out of the one field that works rather than removing a field.

*A caller-chosen model breaks the approval record.* What gets approved is a revision **bound to a
provider configuration and an upstream model**, and the reviewer sees the cost delta for that binding.
If the caller can substitute a different model at call time, the thing that ran is not the thing that
was approved and the cost delta was fiction. That is non-negotiable #1, not a preference.

*`auto` is a dangerous literal in that specific field.* It has no `/`, so under ADR-0062's entry rule an
observe-enabled key would **forward and observe** it - minting a magic name inside a field where every
slash-free name currently means *Prope holds nothing here*.

**And ADR-0065 dissolved the motivation.** The knot existed only because the OpenAI wire format was the
sole carrier of Prope-specific intent. An SDK carries intent in named arguments, so there is nothing to
overload.

## What survives

The underlying want is legitimate and is not closed by this file: a revision that permits a **bounded**
set of upstream models, chosen at call time from an allow-list on the revision or the key, with the
choice recorded in `call_record.upstream_model` - which already happens. That is a small, honest feature
and it keeps the approval record true. It is not scheduled; it needs a proposal of its own.
