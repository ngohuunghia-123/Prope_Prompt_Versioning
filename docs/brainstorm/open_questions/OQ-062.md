# OQ-062 — "A count of bound revisions" and "no query into the registry's tables" cannot both hold literally

**Raised by Phase 11 planning, 2026-08-11.** `blocks_build: false` — Phase 11 adopts a shape that
preserves every property either clause was protecting, and states the residual deviation (plan 11-05,
D-194). Raised because the deviation is against a ROADMAP success criterion, which is what the phase is
scored on.

## The problem, stated once

Three authorities describe the same refusal:

- **ROADMAP Phase 11, SC6**: *"Deleting a bound configuration is refused by the foreign key with a count
  and **no query into the registry's tables**."*
- **`apis.exposes`, the DELETE bullet**: *"The refusal comes from the foreign key
  `revision.provider_config_id`, NOT from asking prompt-registry: that direction is forbidden
  (module_map.md), so the response says **how many revisions bind the configuration** and links to the
  registry's filter rather than naming them."*
- **INT-027**: *"`409` on `DELETE` while revisions bind the configuration, **stating how many** and
  linking to the registry's filter."*

A foreign-key violation carries no count. PostgreSQL's `ForeignKeyViolationError` names the referencing
**table** in its `DETAIL` and nothing more. So the count has exactly one possible source: **counting rows
in the referencing table**, which is `registry.revision`, which is a registry table. There is no third
option — not a denormalised counter (the trigger would live on another module's table), not the error
detail, not the catalogue.

**So SC6's two clauses are jointly unsatisfiable as written.** Either the response has no count, or a
registry table is queried.

## What Phase 11 adopts (D-194, plan 11-05)

The refusal is the engine's; the count is a **post-refusal derivation** through `pg_constraint`.

1. `DELETE` issues the delete inside the transaction and lets the foreign key refuse it. No pre-flight
   count decides anything — which also removes a race, since a revision created between a check and a
   delete would otherwise be deleted out from under.
2. The handler catches the foreign-key violation, rolls back, and **then** asks `pg_constraint` which
   tables carry a foreign key whose `confrelid` is `provider.provider_config`, excluding this module's
   own children in the `provider` schema.
3. It counts rows in each, using SQLAlchemy's identifier constructs so
   `tests/architecture/test_no_sql_interpolation.py` stays green **without an exemption**.

**What is preserved of both clauses:**

- the decision is the **database's**, which is the whole of *"refused by the foreign key"*;
- **no module edge is opened** — nothing calls prompt-registry, and the forbidden dependency direction is
  untouched;
- **no registry table name appears anywhere in `src/prope/`** — the table is discovered from the
  catalogue, so the code that counts `registry.revision` in Phase 13 is byte-identical to the code
  running today;
- the rows are **never named**, only counted, and the response links to a filter path composed as a
  string;
- the query runs **only on the refusal branch** — never on the success path, and never before the delete.

**What is not preserved:** SC6's literal *"no query into the registry's tables."* One `SELECT count(*)`
is issued against whichever table the foreign key points from, after the engine has already refused.

## What is being asked

1. **Is the derived count acceptable**, given it is the only source and `apis.exposes` requires it? The
   alternative is a `409` that says *"revisions bind this configuration"* with no number, which is a
   smaller deviation from SC6 and a larger one from the lock file and INT-027.
2. **Does "no query into the registry's tables" mean "no module edge and no pre-flight lookup"**, which
   Phase 11's shape satisfies exactly — or does it mean literally zero statements touching a `registry.`
   relation, which nothing that produces a count can satisfy?
3. **Is a catalogue-driven count acceptable as a general pattern?** It is a read of another module's
   table with no knowledge of what that table means, which is a different thing from a dependency — but
   it is the first instance in this project, and the boundary rules are otherwise stated as absolutes.
4. **Should SC6's wording be corrected?** Phase 11 does not edit `.planning/ROADMAP.md`. Until it is, the
   phase's own verifier will score against a clause the implementation deliberately does not satisfy.
