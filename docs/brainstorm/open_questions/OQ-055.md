# OQ-055 — Three authorities name three different closed sets of upstream error classes

**Raised by Phase 10 planning, 2026-08-11.** `blocks_build: false` — the code ships either way, and
plan 10-02 adopts one set and records the adoption as UNCONFIRMED. Raised because this is a **closed
vocabulary that five later phases branch on and every call record stores a member of**, which is the
same shape as the event vocabulary that was found written as 30 in six places and 31 in five.

## The problem, stated once

| Authority | Rank (ORCHESTRATION §1) | The set it names |
|---|---|---|
| `docs/modules/provider-access.lock.yml` | 1 | Uses `rate_limited`, `credential_rejected`, **`invalid_request`**, **`upstream_unavailable`** in its own `failure_modes` and `external_services` prose, and names `ProviderContractViolation` in `risks`. It enumerates no list of its own. |
| `docs/architecture/interfaces.md` INT-015 | 2 | `timeout`, `rate_limited`, `credential_rejected`, **`upstream_5xx`**, **`bad_request`**, `content_filtered`, **`transport`** — **seven** |
| `docs/adr/0017` | 3 | `credential_rejected`, `rate_limited`, **`upstream_unavailable`**, `timeout`, `model_not_available`, `content_filtered`, **`invalid_request`**, `provider_contract_violation` — **eight** |

Three names differ substantively or cosmetically (`upstream_5xx` / `upstream_unavailable`,
`bad_request` / `invalid_request`, and INT-015's `transport`, which appears nowhere else). INT-015 omits
two classes the other authorities require.

## Why it matters, in one sentence each

1. **INT-015's set leaves two declared alerts unfireable.** `ProviderModelUnavailable` and
   `ProviderContractViolation` are declared in `observability_requirements.alerts` with declared metrics
   behind them (`prope_provider_access_model_unavailable_total`), and neither `model_not_available` nor
   `provider_contract_violation` is in INT-015's list. A mitigation declared in one section and absent
   from the other is a mitigation nobody built.
2. **`upstream_5xx` names a status code, not a condition.** A connection reset has no 5xx and belongs in
   the same class. `upstream_unavailable` can say that; `upstream_5xx` can only lie.
3. **`transport` duplicates a judgement `retryable` already carries.** A-053 gives evaluation *"retry
   transport errors only"* and ADR-0017 says *"Evaluation reads `retryable` and applies A-053"*. Either
   the flag carries it or the class does; two mechanisms for one judgement is what ADR-0017 rejected
   "let each caller classify" over.
4. **The gateway's own metric label disagrees with whichever set wins.**
   `prope_gateway_fallback_total{reason = upstream_5xx | …}` agrees with INT-015 on the one name where
   the two differ substantively, so **phase 19 inherits either a correction or a translation table.**

## The fifth clause: no class has `origin = prope`, and one is required

ADR-0017 declares `origin` with two values and documents `prope` as *"Prope's own admission gate
(ADR-0016)"* — but **not one of its eight classes carries that origin.** Two of the module's own
refusals therefore have nowhere to land:

- **AC-12** requires that with the KEK unavailable *"the dispatch fails with a class distinct from every
  provider-origin class"*. None of the eight is that class.
- **AC-6 / PA-06** requires a shed batch dispatch to be counted and reported, and `dispatch()` returns
  `DispatchResult | DispatchError`. A shed dispatch is neither a result nor one of the eight.

## What phase 10 shipped, and the reversal cost

Plan 10-02 adopts **ADR-0017's eight, extended to ten** with `kek_unavailable` and `admission_shed`,
both `origin = prope`, both declared with no producer (phase 12 and phase 11 produce them respectively,
on the precedent that a metric or a vocabulary member which first appears when it is non-zero has no
baseline). The deciding argument is clause 1: a smaller set that makes two declared alerts unfireable is
not a simplification.

**Reversal cost.** Phases 11, 12, 16, 18, 19, 20 and 21 branch on these names and every call record
stores one, so a rename after traffic exists is a rename **plus** a data migration over
`ledger.call_record`. It is cheap now and gets steadily less so.

## The questions

1. Should `docs/architecture/interfaces.md` INT-015's list be corrected to ADR-0017's eight? (Plan
   10-02's recommendation: yes.)
2. Should `prope_gateway_fallback_total`'s `reason` label be corrected in phase 19, or translated at the
   gateway? (Recommendation: corrected — a translation table between two closed vocabularies is a third
   vocabulary, and the drift between them is invisible because both sides keep working.)
3. Is widening the closed set to ten acceptable, or should Prope's own two refusals be reported some
   other way?
