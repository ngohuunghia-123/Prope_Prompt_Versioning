# OQ-157 - At what dismissal rate is a readiness rule retired, and who decides?

**Raised 2026-08-20 by ADR-0067.** `blocks_build: false`, `blocks_pilot: false`.

## The problem

`prompt-readiness` ships a closed catalogue of rules and a metric that counts how often each one is
dismissed. Deck 6 slide 64's prescription is unambiguous — *if people ignore it, it is worse than not
having it* — and the module treats a rule dismissed 80% of the time as **a rule to retire, not a rule
to tune**.

What is not settled is the number and the signature. A threshold nobody wrote down becomes a debate
each time, and a debate each time means the rule stays, because leaving something in place is always
the lower-effort option in an argument.

The failure this guards against is specific and it is not "too many findings". It is that the
**trifecta finding** — the one that outranks everything else on the card — gets dismissed with the same
reflex as the six ahead of it that never applied.

## The options

- **A fixed rate over a fixed window** (say: >70% dismissals over 30 days and at least 20 dismissals),
  retired by whoever ships the next catalogue version. Mechanical, and it can retire a rule that is
  dismissed *because the profile filter is wrong* rather than because the rule is.
- **The rate opens a review, a person retires it.** Slower, and it keeps the judgement where a
  false-positive diagnosis needs it. Costs a recurring task nobody owns yet.
- **Per-workspace suppression instead of retirement.** A rule dismissed everywhere in one workspace
  stops firing there. Preserves the rule for everyone else, and hides the signal — the product stops
  learning that a shipped rule is bad.
- **No threshold; read the metric when somebody complains.** Honest about the pilot's scale, and it is
  how the rule set stays wrong for a year.

## What would settle it

One month of real dismissal data from the pilot, and specifically whether dismissals cluster on one or
two rules (retirement) or spread evenly (the card is too long, which is a different fix). The metric
`prope_readiness_dismissals_total{rule_id}` ships with the first version precisely so this question is
answerable rather than argued.
