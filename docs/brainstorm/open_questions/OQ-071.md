# OQ-071 — The one declared cross-schema foreign key collides with a project-wide invariant, and phase 13 declines to write it

**Raised by Phase 13 planning, 2026-08-11.** `blocks_build: false` — plan 13-01 adopts an answer and
records it as UNCONFIRMED. This question exists because **phase 10 routed a specific piece of DDL to
phase 13 by name**, and phase 13 is refusing it in the open rather than silently not doing it.

## What phase 10 asked for

Plan 10-01 shipped `provider.provider_config.bindable boolean GENERATED ALWAYS AS (last_verified_at IS
NOT NULL) STORED` and `uq_provider_config_bindable UNIQUE (id, bindable)`. Plan 10-03's **D-171**
adopted `composite-fk` (UNCONFIRMED) and routed the other half here:

> A revision references `(provider_config_id, provider_config_bindable)` with a local
> `CHECK (provider_config_bindable)`, which makes it structurally impossible for a revision row to exist
> against a configuration that never passed verification.

and recorded, correctly, that *"a target nobody aims at is worse than no target: it looks like a
guarantee."* `OQ-057` is phase 10's own record of the same gap from the other side.

## Why phase 13 will not write it

**1. It is a foreign key leaving its schema, and that is a project-wide invariant with a written
security reason — not a stylistic preference.**
`tests/architecture/test_schema_invariants.py` asserts *no foreign key leaves the schema*, parameterised
over `GENERIC_SCHEMAS` since plan 04-01, and its docstring states the ground: *"PostgreSQL documents
that referential-integrity checks always bypass row security, so a foreign key from a tenant-scoped
table to another schema's table is a covert channel across tenants."* Phase 13 adds `registry` to that
tuple. Writing the foreign key means either a red test or an exemption written to accommodate the code —
the exact move ORCHESTRATION §5 refuses.

**2. `uq_provider_config_bindable` carries no `workspace_id`, so the covert channel is real here rather
than theoretical.** `registry.revision` holds every prompt body in Prope (T-018). A composite key of
`(id, bindable)` lets workspace A's revision reference workspace B's provider configuration, and the
referential-integrity check that confirms it runs with row security bypassed. Every intra-`registry`
foreign key phase 13 does write carries `workspace_id` in **both** halves for exactly this reason.

**3. The project has already made this call, twice, for the same identifier.**
`alembic/versions/0002_call_record.py` and `0003_ledger_tables.py` both open with *"NO FOREIGN KEY
LEAVES `ledger`. `workspace_id`, `provider_config_id` and `created_by` are values, not references."*
`ledger.call_record.provider_config_id` is a bare `text` column today. A registry that referenced the
same column by foreign key while the ledger stores it as a value would be the same identifier obeying
two rules.

**4. The dependency is declared `soft`.** `prompt-registry.lock.yml` says of provider-access:
*"If unavailable, existing revisions still resolve and a new revision may reuse the previous revision's
binding."* A foreign key is the hardest referential coupling available. It also makes a provider
configuration permanently undeletable once any revision has referenced it, because revisions are never
deleted (A-049, ADR-0002) — a real consequence nobody decided.

## What phase 13 shipped instead

`registry.revision.provider_config_id` is `text NOT NULL` with **no foreign key of any kind** — not the
composite one and not the single-column one `data.referenced_by` declares. The migration says so in the
same words the two ledger revisions use.

**AC-3's third clause is therefore not carried by the database, and phase 13 says so rather than
implying otherwise.** The remaining mechanism is the validation seam INT-016 (`get_model_catalogue`) on
the revision-create path, which is **phase 14's**, and which phase 10's own D-171 rejected as
insufficient. Phase 13 agrees it is weaker. It is also the only option left that does not put a
cross-tenant covert channel on the table holding every prompt body.

## What the answer changes

- **If the composite foreign key should be written**, three things have to move together and none of
  them is phase 13's to move: `uq_provider_config_bindable` gains `workspace_id`, the no-FK-leaves-schema
  invariant gains a declared exemption with a reason that answers §2 above, and
  `prompt-registry.lock.yml`'s `revision` field list gains `provider_config_bindable`.
- **If it should not**, `bindable` and `uq_provider_config_bindable` are dead weight in `provider` —
  harmless, but they look like a guarantee, which is the failure phase 10 named. Either delete them in a
  follow-up revision or write a `COMMENT ON CONSTRAINT` saying nothing aims at them.
- **Either way `data.referenced_by` is wrong today.** It declares a foreign key that does not exist and
  will not exist under either answer without further edits.
