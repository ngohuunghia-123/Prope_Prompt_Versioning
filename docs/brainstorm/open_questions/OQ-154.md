# OQ-154 - Where does a local step live? A conversation node that is not an LLM call

**Raised 2026-08-19 by ADR-0065.** `blocks_build: false` for the v1 SDK, which ships without it.
`blocks_pilot: false`. **Blocks the improvement-agent module entirely.**

## Why it matters more than its size suggests

The stated endgame is an agent that reads a workspace's logs and says something useful - *the retrieval
returned nothing and the model filled the gap*, or *this tool has failed 40% of the time since Tuesday*,
or *this prompt ignores its guardrail when the context is long*.

The first two of those are not statements about prompts. They are statements about **steps that are not
LLM calls**, and Prope currently has nowhere to put one. A gateway sees prompts in and completions out;
the tool that raised and the retrieval that returned nothing happened inside the customer's process. The
playground's agent mode already renders them as grey rows with **no node in the conversation graph**,
which is the honest picture of the gap.

An SDK can capture them. Nothing can store them.

## The shapes available

**A row in `ledger.call_record` with a new `source`.** Cheapest to query - the conversation graph is
already assembled from that table by `conversation_id` and `parent_call_id`. Costs the most in
integrity: five columns are non-null by contract for a call, several check constraints assume a
revision, and call-ledger is a **sink** with a forbidden outbound edge. A row that is not a call in the
table whose name is `call_record` invites every future non-call to land there too.

**A sibling table in `ledger`.** Keeps `call_record` honest and keeps the join local. The graph read
becomes a union of two tables ordered by time, which is more code in the one place ADR-0055 gave a read
path.

**A new module.** Cleanest boundary, ninth bounded context, and the heaviest thing to propose for data
that may turn out to be low-volume and low-value.

**Emit OpenTelemetry spans and store nothing.** ADR-0065 declines to reject this. The GenAI semantic
conventions already model tool calls; an SDK that emits them alongside the gateway call would let a
workspace keep local steps in whatever backend it already runs - and would mean the improvement agent
reads somebody else's store, which is a different product.

## What would settle it

One real chained application, instrumented, for a week. The questions are: how many local steps per LLM
call, how large are they, and does an answer to *why did this go wrong* actually need them - or does the
call record plus the prompt body already carry it? If the ratio is small and the value is high, a
sibling table is proportionate; if local steps outnumber calls ten to one, this is a telemetry problem
and not a ledger one.
