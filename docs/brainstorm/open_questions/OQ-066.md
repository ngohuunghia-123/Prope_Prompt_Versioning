# OQ-066 — provider-access's end-to-end journey belongs to M4 and can only run after M7

**Raised by Phase 12 planning, 2026-08-11.** `blocks_build: false` — nothing in the code depends on it.
Raised because Phase 12 **closes milestone M4** under `ORCHESTRATION.md` §9a, which requires every clause
of the lock file to be asserted or routed to a **named** phase, and routing this one crosses a milestone
boundary that nobody has agreed to.

## The problem, stated once

`docs/modules/provider-access.lock.yml`'s `test_plan.e2e` is a single clause and it is the module's whole
reason for existing:

> Register a provider from the dashboard → probe passes → the catalogue populates → **a revision binds a
> model from it** → **the gateway serves a live call through it** → **the eval runner runs a suite through
> the same configuration** → rotate the credential → within 60 s both paths use the new one, with no
> restart. This is the whole BYOK journey OQ-004 chose.

Seven steps. Three of them run through modules M4 does not contain:

| Step | Module | Milestone | Phases |
|---|---|---|---|
| register, probe, catalogue, rotate | provider-access | **M4** | 10-12 |
| a revision binds a model | prompt-registry | M5 | 13-15 |
| the gateway serves a live call | gateway | M7 | 19-21 |
| the eval runner runs a suite | evaluation | M6 | 16-18 |

**No phase of M4 can assert it.** Phase 11's `deferred-items.md` §7 records it as *"not asserted anywhere
… Unowned as a single test; phase 12 must route or declare it"*, and Phase 12 is the last phase of M4.

## What Phase 12 does (D-219, plan 12-06)

**Routes it to Phase 23**, by name, with the reason: Phase 23 is the first phase after every module the
journey crosses is built and mounted. `.planning/research/PITFALLS.md` §5 already establishes this exact
precedent for three other criteria — *"they cannot actually run until every module is mounted — i.e. not
before phase 23."*

Rejected by Phase 12: **declaring it unowned.** §9a's standard is *assert, or route with a named owner*,
and "somebody later" is not a name.

Rejected by Phase 12: **asserting a stubbed version inside M4.** Four of the seven steps would be fakes,
and a green end-to-end test that fakes the majority of its own journey is worse than no test — it is a
claim that the journey works, made by something that did not run it.

## What the routing costs, which is why this file exists

An acceptance clause belonging to **provider-access's** lock file is now assigned to a phase of
**release-control's** milestone. Three specific consequences:

1. **Phase 23's ROADMAP entry does not mention it.** Its goal, its success criteria and its requirement
   list are about release-control. A verifier walking Phase 23's success criteria would not find this, and
   a planner writing Phase 23 would not know to include it — **and Phase 23's planner has already run**,
   in the same parallel batch that produced this file.
2. **The milestone that owns the clause closes without it.** M4's exit statement says *routed*, not
   *asserted*, for the one clause that describes what the module is for. That is honest and it is not the
   same as done.
3. **Nobody owns the fixture cost.** The journey needs a provider configuration, a prompt, a revision, an
   approval, a release, a consumer key, an eval suite and a rotation — a fixture spanning six modules'
   schemas. Whoever writes it is writing the project's first genuinely cross-module test rig, and that is
   a substantial piece of work no estimate anywhere accounts for.

## What is being asked

1. **Is Phase 23 the right owner**, or should the journey get its own phase — the shape PITFALLS §3 and §4
   already argue for twice (the React SPA has no milestone; the deployment stack has no milestone)?
2. **If Phase 23 owns it, does its ROADMAP entry gain a success criterion**, so a verifier can find it?
   That is a `.planning/ROADMAP.md` edit and no sub-agent in this orchestration may make one.
3. **Are the other cross-module clauses the same decision?** PITFALLS §5 names three route-table criteria
   with the same *not before phase 23* answer, and phase 11's `OQ-063` routes the live `registry.revision`
   delete refusal to phase 13. A single answer covering all of them is cheaper than five.
4. **Does the pilot need it before the pilot runs?** A-020 forbids real corporate prompts until OQ-006 and
   OQ-013 are answered, and the BYOK journey is the thing a pilot workspace does on day one. If it is
   unasserted at pilot time, the first person to walk it is a customer.

## What is affected either way

- `.planning/ROADMAP.md` — Phase 23's success criteria, if the routing is accepted and made findable
- Phase 23's plans — the cross-module fixture and the journey itself
- `.planning/phases/12-…/deferred-items.md` — the M4 milestone audit's *routed* list, which is where this
  currently lives
- `docs/modules/provider-access.lock.yml` — `test_plan.e2e`, **not edited by Phase 12**
