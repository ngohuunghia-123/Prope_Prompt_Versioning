# OQ-057 — "Cannot be bound to a revision" has no declared mechanism, and `last_verified_at` has no declared meaning

**Raised by Phase 10 planning, 2026-08-11.** `blocks_build: false` — plan 10-03 adopts a mechanism and
records it as UNCONFIRMED. Raised because **the adopted mechanism has a half that phase 13 must build,
and a target nobody aims at looks like a guarantee.**

## Clause 1 — the declared foreign key cannot enforce the declared criterion

AC-3 requires that a configuration failing verification *"cannot be bound to a revision"*.
`data.referenced_by` declares only:

> prompt-registry: `revision.provider_config_id` -> `provider_config.id`, a foreign key.

A single-column foreign key accepts **any** `provider_config.id`, including one that has never been
probed. The declared mechanism does not implement the declared criterion.

**What phase 10 shipped.** `provider_config` carries
`bindable boolean GENERATED ALWAYS AS (last_verified_at IS NOT NULL) STORED` and a trivially-true
`UNIQUE (id, bindable)` whose only purpose is to be a composite foreign-key target. Phase 10 proves the
target works against a temporary table carrying the same key.

**Phase 13 must write the other half**, and it is spelled out here because this is the single most
likely thing in the phase to be lost across three phases of distance:

```sql
-- on registry.revision
provider_config_bindable  boolean NOT NULL DEFAULT true,
CONSTRAINT ck_revision_provider_config_is_bindable CHECK (provider_config_bindable),
CONSTRAINT fk_revision_provider_config
    FOREIGN KEY (provider_config_id, provider_config_bindable)
    REFERENCES provider.provider_config (id, bindable)
```

If phase 13 writes the single-column foreign key the lock declares instead, the column and the UNIQUE
sit there proving nothing.

**Rejected alternative:** an application-level check in prompt-registry. It puts a provider-access
invariant in the module that does not own it, and any writer that is not that code path — a backfill, a
data fix, an importer — walks around it. The project's own precedent is the non-negotiable that only
`Approved` revisions may be released, *"enforced by a database constraint, not by application code"*.

## Clause 2 — `last_verified_at` has two natural readings and only one works

*"The last verification that ran"* and *"the last verification that passed"* are both natural readings
of the name, and the field list gives neither.

Only the second is workable. `bindable` is generated from this column, and phase 13's foreign key
references `bindable` — so if a failed re-verify could null it, a configuration bound by ten released
revisions would have PostgreSQL **refuse the update**, and a transient provider blip would make it
impossible to record that the provider blipped.

**What phase 10 shipped.** `last_verified_at` is written only on a pass and never written back to NULL,
enforced by a `BEFORE UPDATE` trigger owned by `prope_migrate` (which `prope_app` cannot drop, because
it owns nothing in the schema). `verification_status` and `verification_error` carry the latest
attempt's outcome. The definition is recorded in a `COMMENT ON COLUMN` so it is discoverable from
`psql` and not only from a planning document.

**Rejected alternative:** a separate `first_verified_at` column, which is the more literal reading of
both names and adds a column `data.owns` does not declare.

The lock's own two rules are consistent with this and only with this: *"An unverified configuration
cannot be bound to a revision"* is about **ever having passed**, while *"A dispatch is admitted only for
a configuration whose status is active and whose last verification passed"* is a dispatch-time rule
reading a different column.

## Clause 3 — a verification writes no history event

The closed event vocabulary carries four provider events — `provider_configured`, `provider_updated`,
`provider_disabled`, `credential_rotated` — and none of them is a verification. So
`POST /api/v1/providers/{id}/verify`, a deliberate human action from the dashboard with an actor
attached, leaves **no audit row**. It is observable only through
`prope_provider_access_verification_total` and the row's own columns.

Either that is intended (a verification is a probe, not a state change) or the vocabulary is short by
one. **Not resolved in phase 10**, because widening a closed thirty-one-name vocabulary is exactly the
kind of edit that should be a conversation rather than a plan's side effect.

## The questions

1. Should `data.referenced_by` be corrected to declare the composite key, so phase 13's planner reads a
   spec that matches the code?
2. Should `last_verified_at`'s field entry state that it means the last verification that **passed**?
3. Is a verification meant to leave no audit row?
