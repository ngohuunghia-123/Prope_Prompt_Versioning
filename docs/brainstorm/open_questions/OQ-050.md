# OQ-050 — Four access-control criteria are assigned to Phase 9 and assert over six modules that do not exist until Phases 12-24

**Raised by Phase 9 planning, 2026-08-11.** `blocks_build: false` — Phase 9 ships the mechanism each
criterion needs, asserts it over the routes and seams that exist, and routes every remaining clause to a
named later phase. Raised because four criteria are about to be **ticked in `REQUIREMENTS.md` at the end
of Phase 9**, and three of them will still be substantially unasserted when that happens.

## The problem, stated once

`.planning/REQUIREMENTS.md` maps one requirement to one lock-file acceptance criterion and one phase.
Four of the seven it maps to Phase 9 have `given` clauses that name modules Phase 9 precedes:

| Criterion | Its own words | What it needs | Earliest phase |
|---|---|---|---|
| **AC-1** (req AC-01) | *"B calls any registry, evaluation, or release endpoint naming it — and when B searches its exact title"* | prompt-registry's endpoints and its search; evaluation's run and case endpoints; release-control's | 15, 18, 24 |
| **AC-2** (req AC-02) | *"B attempts to create a revision"* | `revision.create`, which is prompt-registry's | 13 |
| **AC-5** (req AC-05) | *"the **gateway's** response is byte-identical to its response for a model name that does not exist"* | the gateway | 19, and GATE-10 at 20 |
| **AC-11** (req AC-11) | *"when **any module** handles any request … asserted per caller, not only here"* | six modules that do not exist | 12, 15, 18, 20, 24 |

At Phase 9 exactly **two of eight** modules are mounted — call-ledger and access-control — and neither
is one of the six these clauses name.

This is not a defect in the criteria. Each is the right property and each is written from the user's
point of view, which is what an acceptance criterion should be. It is a **phase-assignment** problem: the
handoff's traceability table assigned each criterion to the phase of the module that *owns the rule*,
and for these four the module that owns the rule is not the module that can *observe* it.

The same shape has been recorded three times already and resolved the same way each time. Phase 2 routed
CL-01 and CL-02 forward to Phase 3. Phase 8 routed AC-9's second clause to Phase 15 and AC-10's
cross-module census to Phase 23, and `.planning/research/PITFALLS.md` §5 states the general form: *"They
are assigned to the phase of the module that owns the rule, but they cannot actually run until every
module is mounted — i.e. not before phase 23."*

## What Phase 9 ships

Per criterion, the mechanism plus the assertable part, with the rest routed **in the test module's own
docstring** so a reader who opens the file finds the boundary:

- **AC-1** — `src/prope/access_control/refusals.py`: one function decides between not-found and
  forbidden, and `tests/security/test_private_prompt_is_not_found_not_forbidden.py` byte-compares the
  not-found refusal for a real private subject against one for an id that names no row, over all three
  grants routes. Routed: prompt-registry's endpoints and search → **Phase 15** (PR-03 is the same
  property from the other side); evaluation → **Phase 18** (EVAL-06); release-control → **Phase 24**.
- **AC-2** — the same decision function's forbidden branch, asserted on the write operation that exists
  (`POST /prompts/{id}/grants`, which a viewer-granted actor does not hold). Routed: the
  revision-creation form → **Phase 13**.
- **AC-5** — `tests/security/test_key_scope_refusal_cannot_enumerate.py` asserts the three properties
  that make the byte-identity achievable: same value, same type with no exception, and medians within a
  factor of two, plus an AST assertion that `may_resolve`'s body has one `Return` and no `Raise`.
  Routed: the byte comparison of the gateway's two responses → **Phase 20**, GATE-10.
- **AC-11** — `tests/chaos/test_every_caller_fails_closed.py` asserts all five seams raise with the
  database unreachable, sweeps **every** route in `assembled_routes(app)` for a non-2xx, and asserts
  `check_total{result="allow"}` did not move. Routed: the per-caller form for prompt-registry
  (**15**), evaluation (**18**), provider-access (**12**), gateway (**20**) and release-control
  (**24**) — the lock file itself says *"asserted in each caller's own tests, not just promised here."*

**One part is partly self-completing and that is worth knowing.** The route sweeps in AC-1's, AC-7's and
AC-11's tests enumerate `assembled_routes(app)` rather than a hand-written list, so mounting a module
widens them with no edit. What does **not** self-complete is the per-caller *seam* assertion, because
each module calls the seams from its own code.

## What is being asked

Whether the traceability table's Phase-9 assignment for AC-01, AC-02, AC-05 and AC-11 is intended to
mean *the phase that ships the mechanism* or *the phase that closes the criterion*, and — if the second —
whether the rows should move. Three shapes are available:

- **(a)** Leave the rows at Phase 9, tick them when the mechanism ships, and rely on the later phases'
  own criteria (PR-03, EVAL-06, GATE-10) to carry the observation. Cheapest, and it is what Phase 8 did
  for AC-9. The cost is that `REQUIREMENTS.md` will show AC-01 and AC-11 complete while the assertions
  their text describes have not been made.
- **(b)** Split each row — `AC-01a` at Phase 9 for the mechanism, `AC-01b` at Phase 15 for the census.
  Honest, and it violates *"do not renumber, re-prefix, or re-group"* in `REQUIREMENTS.md`'s own header.
- **(c)** Move the rows to the phase that can close them and leave Phase 9 owning no requirement id for
  this work. Also honest, and it leaves a milestone-closing phase with three of its seven requirements
  reassigned out of the milestone, which no other phase in the roadmap does.

**Phase 9 adopts (a) and states the gap in every affected test module's docstring**, because it is the
only one of the three that changes no id and because a green test named after a criterion it half
asserts is a real risk that a docstring mitigates and a renumbering does not.

## What is affected either way

- `.planning/REQUIREMENTS.md` traceability rows for AC-01, AC-02, AC-05, AC-11 — not edited by Phase 9
- `tests/security/test_private_prompt_is_not_found_not_forbidden.py`,
  `tests/security/test_visible_subject_refusal_names_the_permission.py`,
  `tests/security/test_key_scope_refusal_cannot_enumerate.py`,
  `tests/chaos/test_every_caller_fails_closed.py` — each carries the routing in its docstring
- Phases 12, 13, 15, 18, 20 and 24, each of which inherits one or more routed clauses
- `docs/modules/access-control.lock.yml` `test_plan.e2e`, whose fourteen-step journey is the same
  problem in one line and is routed to Phases 15 and 20
