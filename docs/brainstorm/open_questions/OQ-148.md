# OQ-148 — Retention, redaction, and standing to read an observed body

**Raised 2026-08-18 by ADR-0060.** `blocks_build: false`, `blocks_pilot: true`. The module ships a
delete route and a redact route from its first commit precisely so this answer can arrive late without
a migration. What it cannot ship without an answer is a redaction pass **before** storage, because that
is real build work that either exists or does not.

## Why this is not just OQ-013 again

OQ-013 asks four things about `ledger.call_body` — retention duration, who may read one, PII and
redaction, residency. Three of the four stopped affecting the estimate when the module map was amended:
retention became a per-workspace setting with the job already built (A-106), *who may read a body*
became a question about a reader that does not exist (ADR-0018), and residency became a deployment
question. What remained was **PII and redaction before storage**, and `module_map.md` records it as the
one thing keeping call-ledger at `Estimable: no`.

**An observation reopens two of the three that had closed, on a different table.**

| | `ledger.call_body` | `observation.observation` |
|---|---|---|
| has a reader | no, by construction (ADR-0018) | **yes — that is the entire feature** |
| in the backup | no (ADR-0039) | **yes**, and deliberately (SR-3) |
| deleted by the retention job | yes | **no term defined** |
| arrived because a person chose to submit it | n/a — it is a byproduct | **no, and that is the sharp part** |

So *who may read a body* is a live question again for the first time since ADR-0018 answered it with
"nobody", and this time the answer cannot be "nobody" — a body nobody may read is an inventory nobody
can use.

## What is decided and what is not

**Decided.** The read is behind a permission check (`prompt.create`, SR-1). Bodies are never logged,
never a metric label, never in an error body. RLS scopes every read to one workspace. Delete and redact
exist. Backups include the tables (SR-3), on the reasoning that an inventory a customer spent two weeks
accumulating is exactly what they expect to survive a restore.

**Not decided, and each is a different kind of work.**

1. **A redaction pass before storage.** Build work in this module — a rule set, applied on the write
   path, that removes what it recognises before the row exists. It is the only control on this list
   that protects against the case nobody is looking at, and it is also the one that can silently
   destroy the thing being inventoried. A prompt with its API keys masked is still a useful prompt; a
   prompt with its domain vocabulary masked is not.
2. **A retention term.** A-145 lists a term per owned table and these two have none. The obvious
   candidate is *until adopted or dismissed, then N days*, which has the pleasant property that the
   inbox empties itself as it is worked — but an inbox that deletes what nobody got round to is an
   inbox that loses the long tail, which is where the interesting prompts are.
3. **Standing to read.** SR-1 borrows `prompt.create` because minting a new action is a cross-module
   schema change (OQ-079's reasoning). If observed bodies are classified as more sensitive than a
   drafted prompt, that borrowing is wrong and the action question in OQ-149 becomes this question's
   rather than a naming convenience.
4. **Whether an end user's interpolated text is in scope at all.** This is the one most likely to be
   underestimated. An observed system message is a prompt; an observed *user* message is whatever a
   customer's customer typed, and A-154 already excludes it from the fingerprint. Whether it may be
   **stored** at all — even unhashed, even briefly, even to compute the diff that infers variables — is
   a separate decision from anything above, and the conservative build is that only the system message
   is ever persisted.

## A recommendation

Answer **4 first and narrowly**: persist the system message only, and never the user turns. It costs
almost nothing — A-154's variable inference diffs system messages against each other, so the user turns
are not an input — and it removes the largest category of surprise from the table before any policy
conversation starts.

Then **2** as a workspace setting reusing A-106's job, and **1** deferred with the delete route standing
in for it, unless OQ-147 is answered in a way that puts real traffic in front of a redaction pass, in
which case 1 becomes a build blocker.
