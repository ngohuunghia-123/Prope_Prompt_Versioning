## Resolution (user, 2026-08-09, step 4)

**Option 3 — a host the group controls.** Prope runs on one group-controlled Linux VM under
docker-compose, with Caddy as the single ingress and automatic TLS. A laptop remains the development and
demo target only. Recorded in **ADR-0033**, with **A-129** for the single-ingress property.

Both sub-questions are answered:

- **TLS and secrets are in scope.** Consumer API keys travel in `Authorization` headers (A-113), so TLS
  was never optional once the system was reachable. Secrets are settled by **ADR-0032** — one `0600`
  `.env` on the host holding the KEK that ADR-0014 deferred to this step.
- **Data residency is answered by consequence: nothing leaves the host.** That is also why ADR-0030
  refused a hosted telemetry backend and ADR-0033 refused managed PaaS — both would have placed
  workspace provider credentials, stored request and response bodies, or workspace identifiers in a
  vendor's data plane in a region nobody has named, re-opening the half of **OQ-013** that
  `module_map.md` had parked as *"a deployment question step 4 owns."*

The eval runner's outbound network access is confirmed available; provider-access remains Prope's only
egress.

**What this does not settle**: availability. The VM is a single failure domain with no HA, which is the
shape `00_context.md#scope` already accepted (*"an accepted risk, not a mitigated one"*). ADR-0033 names
the revisit condition — the first consuming product that treats Prope as a hard dependency in
production.

# OQ-011 — Where does the demo run: a laptop, or something hosted?

## Question
Is the demo delivered from a local `docker-compose` on a laptop, or must it be reachable at a URL
(and if so, on which host — a free tier, a university machine, a corporate environment)? Is there any
data-residency requirement on where prompts are stored?

## Why it matters
It sets the `deploy_target` constraint, decides whether secrets management and TLS are in scope, and
whether the eval runner can assume outbound network access. A hosting requirement discovered late is
a lost day at the worst possible moment.

## What we know already
- The repo already ships a `Dockerfile` and `docker-compose.yml`, so local is the path of least
  resistance.
- `docs/guide/setup/quick-start.md` and the free-account material were deleted from the working
  tree, so the organiser's hosting expectations are no longer visible in the repo.

## Options
1. Local `docker-compose` only.
2. Hosted on a free tier, reachable by URL.
3. Deployed inside a corporate environment (implies a data-residency answer).

## Recommendation
A-019 records option 1 as the working default.
