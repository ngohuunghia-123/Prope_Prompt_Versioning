# OQ-022 — The metric block's vocabulary was written for the machinery ADR-0041 deleted

**Raised by Phase 3 plan 03-01 while defining the eighteen metrics, 2026-08-10.** The code ships
either way — `blocks_build: false` — and the deviations are recorded here rather than absorbed into
the spec, per `.planning/BSP-LINK.md` and `.planning/ORCHESTRATION.md` §5.

The `observability_requirements.metrics` block was amended on 2026-08-09 (step 4) when ADR-0041
replaced the in-process two-lane queue and the spill file with **broker-first plus a direct-write
fallback**. The amendment removed the three spill metrics and re-pointed `queue_depth` at the broker.
It did not revisit the label vocabularies that the deleted machinery had supplied, and it did not
reconcile two alerts against the series they read. **Five clauses, and a resolver can accept any one
without accepting the others.**

## Clause 1 — `body_dropped_total`'s `reason` set has no value for the fallback's body drop

Declared: `# labels: reason = queue_full | oversize`.

Neither value is true for the event Phase 3 actually produces. There is **no in-process queue to be
full** — ADR-0041 deleted it — and a body dropped because its record fell back to a direct PostgreSQL
write is **not oversize**: it may be a hundred bytes.

**What this phase built:** `BODY_DROP_REASON_FALLBACK = "fallback"` and
`BODY_DROP_REASON_OVERSIZE = "oversize"`, declared as module constants beside the counter in
`src/prope/observability.py`, with the closed-set discipline `_classify_publish_failure` models: one
place a value is chosen, so a fourth cannot appear by accident.

**`queue_full` is deliberately NOT declared as a constant.** It has no producer. Reusing it for a
queue that does not exist would be a metric whose label lies about the mechanism, which is worse than
a declared deviation. The one remaining in-process bound — `HANDOFF_MAXSIZE` — drops the whole
**record**, not its body, and is counted on `metadata_dropped_total`.

## Clause 2 — `queue_depth`'s `lane` label describes the deleted lanes

Declared: `# gauge, labels: lane = metadata | body`.

`metadata` and `body` were the two in-process lanes. The amendment re-pointed this gauge at the
broker's own queue, and **a broker queue has one depth**. `failure_modes` row 8 still reads
`queue_depth{lane=body}` in its detection line, which cannot be satisfied by any implementation of the
amended metric.

**What this phase built:** an unlabelled gauge.

## Clause 3 — `prope_call_ledger_dlq_depth` is required by T-005 and absent from the metric block

`security_requirements` T-005's mitigation names `prope_call_ledger_dlq_depth` and says *"any non-zero
value alerts"*, and `test_plan.security` requires *"a second test asserts `prope_call_ledger_dlq_depth`
exists"*. The name appears **nowhere** in `observability_requirements.metrics`, which is the list the
ROADMAP counts at seventeen.

This matters more after D-30 than before it: Phase 3 removes `metadata_dropped_total`'s two
dead-letter increments (plan 03-02), so `dlq_depth > 0` becomes **the** signal that a record was
dead-lettered. A mitigation declared in one section and absent from the other is a mitigation nobody
builds.

**What this phase built:** the gauge, as the eighteenth metric. The ROADMAP's "seventeen" is a count
of the block, not of the module's obligations.

## Clause 4 — `LedgerRetentionOverdue` compares a per-workspace threshold against an unlabelled series

The alert reads: *"`prope_call_ledger_oldest_body_age_seconds` exceeds **the workspace's** retention
window plus one day"*. The metric is declared with no labels, and D-43 keeps it unlabelled for
`metadata_dropped_total`'s reason. So the threshold is per-workspace and the series it reads is not: a
rules file can only compare against the **default** 30-day window plus one day, and a workspace with a
longer window will false-positive.

**A fact worth recording, because it changes what a cheap answer looks like:** ADR-0030's own text is
**more permissive** than `src/prope/observability.py`'s docstring here. The ADR permits `model_name`
and `workspace_id` *"at pilot scale, reviewed if either grows past hundreds"*; the module docstring
says flatly that `workspace_id` is *"deliberately never a label"*. So if the answer is "the alert is
right, fix the metric", a `workspace_id` label on **this one gauge** — set once per sweep rather than
per request — is available **without an ADR change**. That is a decision for whoever owns the metric
block, not for a phase.

## Clause 5 — `LedgerPublishFailing` cannot fire in the outage it is written about

`failure_modes` row 2 (the ADR-0041 replacement scenario) gives its detection as:

> `prope_call_ledger_publish_failed_total` rising, `LedgerPublishFailing` (ticket), and
> `prope_call_ledger_fallback_direct_write_total` rising in the same window.

**The first of those three cannot happen in the scenario the row names.** The mechanism, stated so the
question is checkable rather than a worry:

- `publish_failed_total`'s `reason` set is closed at `unroutable | nacked | timeout`, and all three are
  a broker that **answered and refused**.
- The scenario the ADR names — *"a `docker compose up -d` restarting the broker while `app` keeps
  serving"* — produces a **closed channel**. `publish_record`'s bare-`except` branch handles that
  without touching the counter, deliberately, and the comment at that branch says why: nothing was
  confirmed or refused, so the label set stays closed at three.
- And a process that starts against a broker that is already gone runs plan 03-01's adopted
  **fallback-only job**, which never calls `publish_record` at all.

So the only series that rises during an ordinary broker outage is `fallback_direct_write_total`.

**What this phase decided:** plan 03-04 makes `LedgerPublishFailing`'s `expr` subject
`fallback_direct_write_total` rising **or** `publish_failed_total` rising, with the reason written in
the rule's own description.

**Rejected: a fourth `reason` value (`unavailable`) on `publish_failed_total`.** Plan 03-01's
prohibition list keeps that set closed at three, and one extended-and-declared label set (clause 1's
`fallback`) is enough vocabulary drift for one phase. **Either answer is defensible; the asymmetry of
extending one declared label set while leaving the other silently undetectable is not**, which is what
this clause exists to refuse.

## Why this does not block the build

`blocks_build: false`. Every metric ships, every label set is closed and fixed in source, and every
deviation above is written at the constant it affects as well as here. What the answer settles is the
spec's own vocabulary — and, for clauses 4 and 5, whether two declared alerts can be written against
the series they name.
