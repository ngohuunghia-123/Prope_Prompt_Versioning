# OQ-151 - Should the migration audit ingest OpenTelemetry instead of forwarding traffic?

**Raised 2026-08-19 by ADR-0063 and ADR-0064.** `blocks_build: false`, `blocks_pilot: false`. The audit
works today by forwarding. This asks whether it should work by listening instead.

## What is already known

The research behind ADR-0063 found the market has converged on OTLP ingest rather than proxying:
Langfuse accepts traces at `/api/public/otel`, Braintrust at `/otel/v1/traces`, Phoenix natively. The
OpenTelemetry GenAI semantic conventions already standardise `gen_ai.system_instructions`,
`gen_ai.input.messages` and `gen_ai.output.messages`, and PromptLayer's own auto-instrumentation emits
them, gated by `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`.

So an application already running OpenLLMetry, OpenInference or PromptLayer's instrumentation could fill
Prope's observation inbox with **one environment variable** and no traffic rerouting, no stored provider
credential, no added latency and no single point of failure.

## Why it was rejected as the adoption path, and why it is still open as the audit path

ADR-0063 rejects OTLP as the *primary* integration because it leads to the same read-only room, more
cheaply. That argument does not apply to the audit, which is *supposed* to be read-only. As an audit
intake, OTLP is strictly better than forwarding on every axis the audit cares about.

Two things stop it being an obvious yes:

- **`ObservationDraft` has no consumer key on an ingest path.** Its `namespace` comes from the key's
  `observe_namespace` and its `consumer_key_id` is non-null. An ingest token would have to supply both,
  which is a new credential type in access-control rather than a new field.
- **It is a second intake for one module**, and two ways to produce an observation is two fingerprint
  paths to keep in step - the drift the module map avoids elsewhere. Unless the forwarding intake
  retires with it, this adds a maintenance obligation rather than replacing one.

## Two smaller questions carried here rather than given their own files

**Should observation expire?** ADR-0064 makes the audit temporary by convention - turn it on, run a
representative period, resolve the punch list, turn it off - and declines to build an expiry column,
because a timer introduces a failure mode where an audit silently stops mid-run. If audits are routinely
left switched on, the convention is not working.

**Should a registered prompt matching an observation suggest a resolution?** ADR-0064 rejects
*automatic* reconciliation: a fingerprint match is evidence, not proof, and A-154's masking makes false
matches likelier. A **suggestion on the row** that a person confirms was not rejected and is the likely
shape.

## What would settle it

The migration audit running against one real migrated application. If the punch list is short and the
audit is switched off within a week, forwarding is adequate and this closes. If teams refuse to put
Prope in front of production traffic even for a week - which is the objection ADR-0063 was written
about - then the audit needs the cheaper intake and OTLP is the answer.
